> **Назначение файла.** Самодостаточный вход для запуска новой фазы. Всё

## Цель

Генерация PDF акта приёма-передачи в приложении должна **визуально соответствовать
бумажной форме организации** (образец: `reference/act-word-source/act-sample.docx`),
с одним намеренным отличием: блок «Устройство» **переделываем под несколько
устройств в одном акте** (в образце Word — одно устройство, у нас акт может
содержать несколько позиций).

## Скоуп-решения пользователя (зафиксированы)

1. **Полное соответствие Word** — шапка с логотипом и реквизитами, заголовок,
   вводная формулировка, поля устройства, срок, блок подписей.
2. **Блок «Устройство» переделать под мультиустройство** — не жёсткий key-value
   на одно устройство, а форма/таблица, вмещающая N позиций акта.
3. Делаем **отдельной фазой** (не quick-таск).

## Анализ текущей системы (что уже есть)

Пайплайн генерации уже существует:

```
MiniJinja-шаблон (в БД, редактируемый)  →  DocSpec JSON  →  krilla  →  PDF-байты
```

- Шаблоны хранятся в БД (таблица `document_templates`, kind ∈ `act_handover` | `act_acceptance`),
  дефолты вшиты в бинарь через `include_str!` и сидируются при первом запуске.
- Ключевые файлы:
  - Дефолтные шаблоны: `crates/trackly-app/templates/act_handover.minijinja`,
    `crates/trackly-app/templates/act_acceptance.minijinja`
  - Сидинг/чтение шаблонов: `crates/trackly-app/src/services/template_service.rs`
    (`DEFAULT_TEMPLATES`, `seed_defaults_on_startup`)
  - IR для рендера: `crates/trackly-app/src/pdf/docspec.rs`
  - Рендерер krilla: `crates/trackly-app/src/pdf/renderer.rs`
  - Сбор контекста + вызов рендера: `crates/trackly-app/src/services/act_service.rs`
    (`render_pdf` ~ L1322, `render_acceptance_pdf` ~ L1411)
  - Шрифты (Cyrillic): `crates/trackly-app/src/pdf/fonts.rs`, `assets/fonts/`
  - Миграции: `migrations/V004__acts.sql`, `V007__document_templates.sql`,
    `V026__org_settings.sql` (лого-BLOB), `V027__document_templates_is_default.sql`

### Примитивы DocSpec (что рендерер умеет сейчас)
`docspec.rs::Section`:
- `Paragraph { text, style: Regular|Bold }`
- `Heading { level: 1..=3, text }`
- `KeyValueTable { rows: [{key, value}] }`
- `ItemsTable { columns: [String], rows: [[String]] }`  ← готовый примитив для мультиустройства
- `Signature { left_label, right_label, spacer_pt }`
- `Spacer { height_pt }`

`HeaderBlock` сейчас: `org_name, org_inn, org_kpp, org_address, logo_path|logo_bytes+logo_mime, act_label, date_label`.

## Гэп-анализ (что предстоит сделать)

1. **Мультиустройство в акте.**
   Использовать `ItemsTable` (уже есть) вместо key-value на одно устройство.
   Колонки нужно определить: напр. `№, Наименование, Инв.№, Серийный №, Модель,
   Комплектация, Тех.характеристики, Состояние`. Проверить перенос длинных ячеек
   в рендерере (`renderer.rs`) — «Комплектация»/«Тех.характеристики» длинные.
   **Проверить, что контекст `render_acceptance_pdf`/`render_pdf` реально отдаёт
   список позиций акта (`ActItemRow`), а не одно устройство.** В шаблоне пройтись
   циклом по позициям.

2. **Недостающие поля данных.**
   В образце есть **Комплектация**, **Технические характеристики**, **Срок до**.
   Их, вероятно, нет ни в `device`/`act`-схеме, ни в контексте шаблона.
   Нужно решить: хранить в БД (миграция + поля в форме акта/устройства) или
   вводить как свободный ввод при создании акта. → это главный вопрос для discuss.

3. **Расширенная шапка с реквизитами.**
   `HeaderBlock` знает только `org_name/inn/kpp/address`. В образце ещё
   телефон, факс, e-mail, ОКПО, ОГРН. Варианты:
   (а) впихнуть многострочно в `org_address`;
   (б) расширить `HeaderBlock` + `renderer.rs` полями phone/fax/email/okpo/ogrn.
   Реквизиты берутся из `org_settings` (V026) — проверить, какие поля там есть,
   возможно потребуется миграция для новых.

4. **Семантика документа: «выдача сотруднику», не «приём на склад».**
   Текущий `act_acceptance` = «Документ приёма устройства на склад» (Кто передал /
   Кто принял). Образец — «Акт приема-передачи» с формулировкой «Выдал / Получил»
   и вводной «Настоящим актом утверждаю, что мною <ФИО> было получено устройство».
   Решить: это новый вид (новый `kind` в `document_templates` CHECK-констрейнте +
   миграция) или переработка существующего `act_handover`/`act_acceptance`.
   Скорее всего это ближе к **`act_handover`** (передача сотруднику), а не к acceptance.

5. **Блок подписей с двухстрочными подписями (Подпись / ФИО).**
   Примитив `Signature` даёт по одному label на сторону. Либо расширить
   рендерер под двухуровневую подпись, либо собрать через `Paragraph` + линии.

6. **Номер и дата акта с прочерками.**
   В образце «№ ___ от ___». У нас номер акта присваивается системой — решить,
   печатать реальный номер/дату или оставлять поля под ручное заполнение.

7. **Логотип.** Загрузка лого организации уже поддерживается через `org_settings`
   BLOB (`logo_bytes`/`logo_mime`). Отдельной работы, вероятно, не требует, кроме
   как убедиться, что образцовый логотип загружен в настройках.

## Открытые вопросы для spec/discuss

- Где хранить «Комплектация» и «Технические характеристики» — на устройстве
  (постоянно), на позиции акта (снимок на момент акта) или свободный ввод в форме?
- «Срок до» — обязательное поле акта выдачи? Хранить в `acts`?
- Расширять `HeaderBlock`/`org_settings` реквизитами или уложить в `address`?
- Это новый `kind` документа или переработка `act_handover`?
- Печатать реальный № и дату акта или прочерки под ручное заполнение?
- Мультиустройство: таблица (`ItemsTable`) с колонками — или повтор карточек на
  каждое устройство (несколько key-value блоков)? Что читаемее при 1 vs 5 позициях.

## Критерии приёмки (черновик)

- [ ] Сгенерированный PDF воспроизводит структуру образца: шапка (лого+реквизиты),
      заголовок «Акт приема-передачи», вводная формулировка, блок устройств,
      «Сроком до», подписи «Выдал/Получил».
- [ ] Акт с несколькими устройствами корректно печатает все позиции.
- [ ] Кириллица рендерится корректно (уже покрыто embedded-шрифтом).
- [ ] Шаблон остаётся редактируемым через существующий механизм
      `document_templates` (не хардкод в Rust помимо дефолта-сида).
- [ ] Существующие тесты PDF-пайплайна проходят; добавлены тесты на новый
      шаблон/мультиустройство.
- [ ] Дефолтный шаблон обновлён в `templates/*.minijinja` и корректно сидируется.
