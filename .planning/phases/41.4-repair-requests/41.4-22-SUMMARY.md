# Phase 41.4 Plan 22: вложенный блок в ремонте и отмена на текущее место группы

Якорь вложенной группы (системный блок внутри АРМ) принимается в ремонт с перемещением, отправляется, забирается и завершается при любой вложенности; «Отменить ремонт» члена переехавшей группы возвращает его на ТЕКУЩЕЕ место группы.

## Что сделано

1. **Примитив и правило «в отъезде» (задача 1).**
   - `groups_sqlite.rs`: `away_nested_group_ids_in_tx(tx, root, root_place)` (вложенные группы поддерева с местом, отличным от места корня; при `None` пусто) и `set_groups_place_in_tx(tx, ids, place, now)` (место и версия +1 только перечисленным). `set_subtree_place_in_tx` не менялся.
   - `group_place.rs`: общая проверка целевого места `check_target_place`; `move_nested_block_in_tx` (Validation «Для корневой группы используйте перенос группы.» для корня, пакет журнала одним batch_id, аудит `move` с `nested=true`); в `propagate_group_place_in_tx` при непустом старом месте отъехавшие поддеревья вычитаются из списков групп и устройств, место групп ставится через `set_groups_place_in_tx`. При пустом `away` поведение прежнее (порядок «места групп ДО цикла устройств» сохранён).
   - `registry.rs`: `ex(GPLACE, "move_nested_block_in_tx", TX_PRIMITIVE_REASON)`.
2. **Ремонт вложенного якоря (задача 2).** В `apply_device_state_in_tx` отказ «Место вложенной группы задаётся корневой группой» снят: корневая группа едет через `move_group_in_tx`, вложенная через `move_nested_block_in_tx`. Добавлен `return_place_for_device` (D-16: якорь вложенной группы — текущее место родителя, якорь корневой — сохранённое место заявки, член группы — текущее место его группы, иначе сохранённое). `get_state` считает `suggested_return_place_id` этим помощником; `group_block_size` и раньше считался для любого якоря.
3. **Отмена ремонта (задача 3).** `cancel_repair` берёт цель из `return_place_for_device`, статус считает по ней, в аудит `custom:repair_cancel` пишет фактическое `returned_to_place_id`.

## Инварианты «место вложенной группы = место корня» (выписано до правки)

| Место | Что делает | Вывод |
|-------|-----------|-------|
| `group_service::set_parent` (около 1192) | при вложении под родителя с местом вызывает `propagate_group_place_in_tx` с местом родителя | перенос блока под родителя ставит синхронное место, отъезд снимается; блок, у которого есть свои «отъехавшие» вложенные, их не трогает (правило применяется внутри propagate) |
| `group_service` разгруппировка (около 1209) | `set_subtree_place_in_tx(.., None)` | место снимается у всего поддерева, отъезд исчезает вместе с местом; не ломает |
| `group_act_plan` (около 1249, 1423, 1439) | перенос корня актом через `propagate_group_place_in_tx` (правило «в отъезде» действует автоматически); release — `set_subtree_place_in_tx(.., None)` | отъехавший блок акт корня не стягивает; тесты `group_act_expansion` зелёные |
| `place_service` массовый перенос (около 962) | `move_group_in_tx` для корней групп | **остаточный риск:** при массовом переносе места, где стоит отъехавший блок, корень поедет, блок останется. Практически закрыт D-21: якорь блока имеет открытую ремонтную заявку, массовый перенос получает Conflict. Деталь блока без заявки отдельно не отслеживается |
| `move_group_in_tx` | по-прежнему отказывает вложенной группе (ручной перенос из UI через `GroupService::move_group`) | оставлено намеренно: D-32 касается ремонтных переходов |

`group_write_sites.rs` не перечисляет пути записи `groups.place_id` (он про HTTP-записи `devices.place_id`), поэтому записи в него вносить не пришлось; новые примитивы учтены в реестре `entities_changed_gate`.

## Deviations from Plan

**1. [Отклонение процесса] «Красный до реализации» не зафиксирован прогоном.** Сборка зависла надолго (rustc простаивает при 0% CPU, syspolicyd около 45% CPU, swap почти полон), и из-за потери времени тесты были дописаны и реализация сделана до первого запуска. Красность подтверждена мутациями M1-M3 вместо прогона до реализации. Вердикт: поведение тестами закреплено, но формального «красный до зелёного» нет.

**2. [Отклонение раскладки] Unit-тесты 4-5 задачи 1 лежат в `group_place.rs` (`#[cfg(test)]`), а не в `repair_group_move.rs`:** `move_nested_block_in_tx` имеет видимость `pub(crate)`, из интеграционного теста не вызывается. Сквозная проверка того же пути идёт через `RepairService` в repair_accept/repair_complete.

**3. [Отклонение раскладки коммитов]** Изменения задач 2 и 3 в `repair_service.rs` лежат в одном файле, раздельно закоммитить без интерактивного `git add -p` нельзя. Коммит `bec40110` содержит весь `repair_service.rs` (задачи 2 и 3), тесты задачи 3 отдельным коммитом `c01339ba`.

**4. [Окружение]** Из-за зависаний переключил запуски на `CARGO_INCREMENTAL=0` (в проектных ограничениях его нет). Это пересобрало workspace и кэш инкрементальной сборки в `target/` не затронуло.

`dto/repair.rs` не менялся: у поля `group_nested` нет комментария «перемещать нельзя», bindings не затронуты.
