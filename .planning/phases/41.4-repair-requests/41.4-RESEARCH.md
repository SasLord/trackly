## Summary

Фаза сквозная: затрагивает схему (две перестройки таблиц с CHECK + четыре новые таблицы), доменный `RequestTransitionOp`, `RequestCounts` по пяти слоям, три реестровых гейта (`entities_changed_gate`, `group_write_sites`, `http_route_parity`), файловый механизм HTML-шаблонов, шаблоны номеров 40.2 (новые тип и контекст), отчёты (девять точек регистрации), видимость заявки (все проверки «автор = вызывающий») и UI (три попапа + секция + вкладка). Главная находка: **`request_service.rs` числится в реестре как «не меняет устройства» (`entities_support/registry.rs:131`)**, а фаза делает ровно обратное — это нужно решить архитектурно (отдельный `repair_service.rs` в области гейта), иначе гейт либо красный, либо фальшиво зелёный.

Второе: **`CHECK` на `requests.request_type` и `requests.status` не расширяются без перестройки `requests`** (`V006`, `V031`), и **`CHECK` на `number_templates.type` / `number_template_contexts.context` — тоже** (`V041`). Прежняя угроза «`foreign_keys=OFF` внутри refinery-транзакции не работает» **закрыта в раннере** (`crates/trackly-infra/src/db/migrations.rs:292-370`: FK выключаются на соединении ДО refinery при наличии pending-миграций, затем сверка `foreign_key_check` с базовой линией) — но строка `PRAGMA foreign_keys = OFF` в самом файле миграции по-прежнему no-op, и защита проверена только тестом через реальный раннер.

Третье: пользовательская формулировка D-14 («исключение по статусу») меняет инвариант фазы 41 в **четырёх** местах (guard в `DeviceService::update`, цикл в `propagate_group_place_in_tx`, ветка «едет с группой» в `place_service::move_subtree_contents`, `group_membership` при вступлении), а D-21/D-22 требуют единого серверного предиката «у устройства открыта ремонтная заявка», который должны вызывать все писатели `devices.status_id/place_id`, включая `is_act_assignable`, пропускающий любого члена группы вне зависимости от статуса.

**Primary recommendation:** один новый `RepairService` (`repair_service.rs`) владеет всеми записями цикла (accept/move/send/receive/complete/cancel/reject/join/assign) и **всеми** изменениями статуса и места устройства по ремонту; `RequestService::transition/cancel` для `request_type='repair'` делегирует ему; миграция V051 — перестройка `requests` и `number_templates`/`number_template_contexts` в порядке «ребёнок раньше родителя» + новые таблицы; единый SQL-предикат открытой ремонтной заявки живёт в одном месте и импортируется всеми писателями.

### Pattern 1: Машина состояний ремонтной заявки
**Статус заявки** (`requests.status`): `open → in_progress → in_repair → in_progress → completed`; `rejected`/`cancelled` терминальны. Добавляется **`in_repair`** (CHECK, D-26/RequestCounts). Устройство: `на_ремонте` (при accept, D-01) → `в_ремонте` (send) → `на_ремонте` (receive без отметки) → по месту `в_работе`/`на_складе` (complete, D-09).
Переходы (все — одно `writer.execute` + одна транзакция + CAS по `requests.version`, как `transition_in_tx` в `requests_sqlite.rs`):
- `accept` (open→in_progress): сохранить `repair_origin_place_id` **только при первом перемещении** (D-16, REP-06), статус устройства `на_ремонте`, перемещение — по выбору попапа; D-23 — статус `на_списание`/`списано` перезаписывается.
- `move_to_storage` («Забрать на склад»), `send` (in_progress→in_repair, создаёт `repair_visits`, номер акта), `receive` (in_repair→in_progress, закрывает заход; при `return_to_workplace=true` — тут же `complete`, одно замыкание, D-08), `complete` (in_progress→completed, запрещён из `in_repair`, D-10), `cancel_repair` (D-12), `reject` (D-09: снять статус «Ожидает ремонта» по месту).
Валидация допустимости — расширить `RequestTransitionOp::validate_from_status` (`trackly-core/src/domain/printers.rs:165-229`): сейчас Reject допускает `open|in_progress`, Complete — только `in_progress`, Cancel — только `open`. Для `in_repair` Reject/Complete/Cancel (автор) запрещены.

### Pattern 2: Один владелец записей цикла + делегирование
Обобщённый `RequestService::transition` (`request_service.rs:407`) обязан **отклонять/делегировать** Accept/Reject/Complete для `request_type='repair'`, иначе вызов `requests_transition` меняет статус заявки в обход устройства (D-01/D-09 не выполнятся). Аналогично `cancel` (:687, автор, сейчас только `open`) и `delete` (:572 в месте мягкого удаления — см. Открытый вопрос 5).

### Pattern 3: Единый предикат «открытая ремонтная заявка»
Одна функция/константа в `repairs_sqlite.rs`: `open_repair_request_id_in_tx(tx, device_id) -> Option<i64>` по `request_type='repair' AND status IN ('open','in_progress','in_repair') AND deleted_at_utc IS NULL AND printer_device_id = ?`. Её вызывают: D-21 в `DeviceService::update` (статус и место), `place_service::move_subtree_contents`, `group_*` переносы (для устройства группы), D-22 в `is_act_assignable`, список опций формы и пикера актов. Не копировать SQL.

### Anti-Patterns
- **Разнести запись статуса устройства и статуса заявки по двум writer-вызовам** — ломает D-08 и атомарность.
- **Вешать ремонтные переходы на `requests_transition`** (см. Pattern 2).
- **Вычислять «склад» на фронте** (как `isStoragePlace` в `DeviceFormBody.svelte:~577`): для D-09/D-16 источник — сервер.
- **Копировать оптимистические id из UI как доверенные:** место сервиса/склада и устройство проверять по БД.

Расширить CHECK без перестройки нельзя (`V006`:`CHECK (status IN (...))`, `V031` уже перестраивала). Новые значения: `request_type += 'repair'`, `status += 'in_repair'`. - `AUTOINCREMENT`: `INSERT ... SELECT id` сохраняет id; проверить, что следующий id не откатывается.

## Атомарность, статус по месту, последний выбор

- **D-08 (забор+завершение):** одно вызов `RepairService::receive(..., return_to_workplace: true)` = один `writer.execute` с транзакцией: закрыть заход, переместить, поставить статус по месту (Pattern 1), `requests.status='completed'`, два события аудита. Единый writer гарантирует отсутствие гонок; бэкстоп — индексы. Все побочные чтения — внутри транзакции (не из reader-пула: он видит снимок до коммита).
- **D-09 / D-16 / D-18:** статус по месту — `list_storage_place_ids(&tx).contains(place)` → `на_складе`, иначе `в_работе`; id статусов искать **по `code`** (`SELECT id FROM device_statuses WHERE code=?`), не числами (V047: id = MAX+1). Для группы (D-16): предзаполнение «текущее место группы» читает сервер; для остальных — `repair_origin_place_id`. Для якоря (D-18): `move_group_in_tx(group_id,…)` переносит блок; **вложенная** якорная группа не переносится сама (`Место вложенной группы задаётся корневой…`, `group_place.rs:~205`) — случай нужно явно описать в плане (Открытый вопрос 3).
- **D-25:** ключи `app_settings` (например `repair_last_move_place_id`, `repair_last_service_place_id`) — запись при успешном действии внутри той же транзакции, чтение в командах предзаполнения; оба транспорта (одна пара «команда+маршрут»). Невалидный сохранённый id (место удалено/в архиве) → пусто, не ошибка.
- **Журнал перемещений (D-17, D-18, REP-07):** `MovementSource::Manual` + `note` «по заявке №N» (enum и отчёт «Перемещения» не трогать); у устройства без места `record_movement_if_applicable` строку не пишет — аудит `custom:*` вместо неё (прецедент `group_place_assigned`).

## Common Pitfalls

### Pitfall 1: `request_service.rs` — «не меняет устройства» в реестре гейта
**Что идёт не так:** реестр `OUT_OF_SCOPE_WRITERS` утверждает обратное тому, что делает фаза; либо `writer_owning_services_outside_scope_are_listed` красный, либо ложная причина остаётся в реестре.
**Как избежать:** новая запись в `SCOPE_FILES` для `repair_service.rs`, делегирование, правка причины.
**Признак:** красный `entities_changed_gate` или рассылка отсутствует при живом переносе (счётчики «Мест» не обновляются в соседнем окне).

### Pitfall 2: Расширение CHECK без перестройки / перестройка не через реальный раннер
**Как избежать:** V051 как выше; тест через `run_up_to(50)` → наполнение (заявки всех статусов, вложения, контексты номеров) → `run`; проверить `user_version == 51`, число строк, `template_id` контекстов, индексы, `foreign_key_check` пуст.

### Pitfall 3: Статус заявки/устройства вне единого владельца
Прямое `requests_transition` Accept на ремонтной заявке; `reject`/`cancel`/`delete` без возврата статуса устройства (D-09, Открытый вопрос 5).

### Pitfall 4: D-14 как «флаг» в одном месте
Инвариант проверяется в шести точках (таблица выше); пропуск одной (особенно `place_service` bulk и `is_act_assignable`) даёт тихое расхождение места и блок: вакуумные тесты фазы 41 по статусу не ловят — тесты D-15 должны использовать фикстуру с **разошедшимся** местом (`memory: vacuous_test_fixture_must_diverge`).

### Pitfall 5: Новая переменная в акте ломает редактор
См. §Документ п.5. Проверять `update_body`/`validate_preview` и открытие редактора в живом приложении.

### Pitfall 6: Счётчик ловит лишь часть слоёв
`RequestCounts` (`domain/requests.rs`, `RequestCountsDto` в `dto/request.rs`, `RequestService::counts` :166-176, `SqliteRequestRepository::counts` `:340-420` — отдельный `SELECT COUNT` на статус, `bindings-phase6.ts`, `api.ts`, `RequestsSearchAndTabs.svelte` TABS + `RequestsPage` загрузка счётчиков + `Tabs count`): добавить `in_repair` во все; тип `StatusTab` (union) обновить. Счётчики вкладок сейчас **не используются** (комментарий в `RequestsSearchAndTabs.svelte`: «No count»), подключение `statusCounts` к вкладке — новая работа.

### Pitfall 7: Svelte-руны не проверяются компиляцией
`svelte-check`/eslint/build не видят рантайм-ошибок рун (`memory: compile_gates_miss_svelte_runtime`). Каждый новый попап с `$state/$derived/$effect` → пункт живой проверки (запрос `$effect` с записью в читаемую же переменную, зацикливание, `bind:` на пропе). Гейты UI — **отдельные команды**: `pnpm --dir ui svelte-check`, `pnpm --dir ui lint` (**не** включает svelte-check), `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --all -- --check`.

### Pitfall 8: Попап внутри `<td>` наследует стили ячейки
Если кнопка/попап вызываются из строки таблицы — `Modal` унаследует `white-space: nowrap`/`text-align: center` (`memory`); для карточки заявки (не таблица) риска нет, для отчёта и строки списка — учесть.

### Pitfall 9: Номер акта и «регистровая» уникальность
Идентичные номера с разным регистром/пробелами (`ensure_number_free_in_tx` сравнивает `normalize_number_key`); контекст-память `remember_context_in_tx` при авто-номере не нужна, но выдача номера обязана идти внутри транзакции после проверки занятости.

### Pitfall 10: Два места «последнего выбора»
Попап «Перемещение устройства» (accept и «Забрать на склад») и «Отправить в ремонт» — разные ключи; не смешивать (иначе последнее место сервиса предложится как склад).

## Open Questions

1. **«Другое» в форме и состав дропдауна (REP-01, D-24 vs UI-SPEC §2.1).**
   - Знаем: REP-01/ROADMAP/D-24 — устройства автора + «Другое» без устройства, принимается без попапа, позже «Указать устройство». UI-SPEC §2.1 делает «Устройство» обязательным и перечисляет «принтеры и прочие устройства», «Другое» не упоминает; §3 при этом содержит строку «Другое».
   - Неясно: поле обязательное или есть вариант «Другое»; весь список или устройства автора.
   - Рекомендация: следовать CONTEXT/ROADMAP (вариант «Другое» есть, устройство не обязательно), список — по роли (staff: все; сотрудник: свои). Подтвердить у пользователя до планирования формы.
2. **«Отменить ремонт» (D-12) после уже закрытого захода (UI-SPEC §3 строка «вернулось из сервиса»).**
   - D-12: «запись о ремонте не создаётся и в отчёт не попадает» — для случая «всё исправно». Если заход уже был, запись существует.
   - Рекомендация: «Отменить ремонт» доступна только пока не было ни одного захода; после — только «Завершить». Требует решения пользователя (противоречие со строкой 3 таблицы §3).
3. **Якорное устройство и возврат блока (D-18/D-16); вложенная якорная группа.**
   - Блок уезжает через `move_group_in_tx`; у вложенной группы место задаёт корень.
   - Рекомендация: для не вложенной группы возвращать блок целиком (предзаполнение — сохранённое место до ремонта), для вложенной — отказ с понятным текстом либо перенос только устройств без смены места групп; подтвердить.
4. **Скан по заходам (A5).** Без явной связи вложение↔заход отметка «Скан» в отчёте эвристическая.
5. **Отклонение/мягкое удаление ремонтной заявки.** `Отклонить` (D-09 по умолчанию 0 UI-SPEC) обязана вернуть статус устройства по месту; `delete` (Admin, любой статус) — запретить для открытых ремонтных заявок или тоже возвращать статус. Рекомендация: запретить удаление, пока заявка открыта.
6. **Возврат/откат акта для устройства с открытой заявкой** (D-22 говорит только про включение): рекомендация — отказ с текстом.
7. **Присоединение к закрытой заявке.** D-19 — «открытая»; после `completed/rejected/cancelled` создаётся новая заявка (индекс это допускает).
8. **Отчёт: место подпункта «Ремонты»** (в «Заявках» нет «Отменённых»).
9. **Печать акта автору-сотруднику** запрещена (UI-SPEC решение 4) — подтвердить; серверный гейт `TransitionRequests`.

- Весь UI — русский; выпадающие списки только кастомный `Dropdown` (не сырой `<select>`/нативный Select); UI-SPEC не вводит новых токенов/зависимостей.
- Решения GSD: правки репозитория только через GSD-воркфлоу; исследователь ничего не коммитит.
- Память проекта: один `cargo test` за раз; `ci-full` — эталон сплошного прогона; пользователь пушит `git push origin main` без подтверждения (для оркестратора).
