# Phase 41.4 Plan 28: объединение заявок, серверная часть Summary

Серверный метод `merge_into_open` сливает заявку «Другое» (в работе, без устройства) в уже открытую заявку занятого устройства по образцу присоединения (D-20), на обоих транспортах с правом TransitionRequests.

## Что сделано

- `RepairMergeDto { request_id, version, device_id }`, `RepairMergeResultDto { request, target_request_id }`.
- `RepairService::merge_into_open`: одна транзакция writer. Проверки: repair, in_progress, без устройства, версия (OptimisticLockMismatch), устройство живое, цель = `open_repair_request_id` (нет цели -> Validation, цель == текущая -> Validation). Автор поглощаемой заявки добавляется участником цели; на цели пишется `repair_merge` (description, notes «О поломке также сообщил(а) {имя}: {описание}», merged_request_id); поглощаемая -> `cancelled` и событие `custom:repair_merged_into` («Объединена с заявкой №N»). Цель, устройство, место, статус устройства не трогаются.
- После коммита `RequestStatusChanged` по обеим заявкам (участники цели включают нового).
- `build_repairs_merge_into_open`, команда `repairs_merge_into_open`, маршрут HTTP, запись в `specta_export`, запись `ex(REPAIR, "merge_into_open", ...)` в реестре entities_changed.
- Матрица ролей: HTTP-случай `repairs_merge_into_open` (сотрудник 403, без сессии 401, Admin/Manager доходят до логики) и Tauri-путь (сотрудник Forbidden).
- Тест маршрута через настоящий `build_router`: без сессии 401 с JSON (при отсутствии маршрута spa_fallback дал бы 404 `api_route`).

## Осознанное ограничение

Вложения поглощаемой заявки остаются на ней: не переносятся и не теряются (заявка закрыта, но не удалена).
