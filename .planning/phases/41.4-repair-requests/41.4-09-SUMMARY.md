# Phase 41.4 Plan 09: основа RepairService

Создание ремонтной заявки либо присоединение к уже открытой, чтение для формы и карточки, BOLA на сервере.

## Что сделано
- `RepairService::create`: одна транзакция writer, сначала `open_repair_request_id`; есть открытая заявка, значит участник плюс `repair_join` в `audit_log` с описанием (`joined = true`); нет, значит новая заявка без категории. Устройство не обязательно («Другое», D-24). Конфликт индекса `uq_requests_open_repair_device` откатывает транзакцию и повторяется веткой присоединения, `Internal` не возвращается. WS: `NewRequest` для новой, `RequestStatusChanged` с участниками для присоединения.
- BOLA: сотрудник создаёт только на устройства из `employee_device_ids` (иначе `Forbidden`); Админ/Специалист на любое живое устройство.
- `device_options`: сотруднику только его область, персоналу все живые; поля id, name, inventory_no, type_name, place, булев in_repair (без id чужой заявки).
- `open_requests_for_devices`, `last_places` (ключи `repair_last_move_place_id` / `repair_last_service_place_id`, удалённое или архивное место даёт `None`), `get_state` (доступ автор, участник, персонал; предложенное место возврата по D-16/D-18; `can_cancel_repair`).
- Поле `repairs` добавлено во все литералы `AppCtx` (health обоих слоёв и шесть тестов).
- Реестр гейта: `repair_service.rs` в `SCOPE_FILES` (девять файлов), шесть строк `ro`, `create` как `ex` с причиной. Зашитые нижние границы (`MIN_REGISTRY_ROWS`, `MIN_FNS_IN_SCOPE` = 110) не менялись: факт вырос выше них. Обновлены только проверка «девять файлов» и тексты.

## Отклонения
- **[Rule 3] Заглушка `broadcast_entities` не добавлена.** План просил приватный `broadcast_entities`, но гейт (`DeadCodeAllowLeft`) краснит `#[allow(dead_code)]` на заглушке. Метод добавят планы 10-13 вместе с первым вызовом.
- Задачи 1 и 2 (одна файловая единица `repair_service.rs`) закоммичены одним коммитом.
- Общие сидеры вынесены в `tests/repair_support/mod.rs` (не по плану, чтобы не дублировать).
- Bindings не перегенерировались: новые DTO не привязаны к командам (команды добавят следующие планы). HTTP-маршруты и UI не менялись, проверка регистрации и UI-гейты не требовались.
