<objective>
Фронтенд gap R2-1: клик по системному уведомлению или тосту ведёт к заявке и выбирает вкладку — сообщение → «Чат», смена статуса → «Информация»; в браузере и в десктопе, для всех ролей.

Решения планировщика (записать в SUMMARY и UI-SPEC §12):
- Повторный переход на тот же hash не вызывает hashchange (svelte-spa-router), а выбор заявки в списке hash не меняет. Поэтому ссылка цели всегда уникальна: `#/requests?id=N&tab=T&n=<метка>`, где метка = `Date.now().toString(36)` + счётчик модуля (уникальна и после перезагрузки). Это закрывает и «та же заявка уже выбрана, но на другой вкладке», и повторный клик по второму уведомлению, без отдельного стора навигации.
- systemNotify.ts остаётся в lib/platform и не знает про заявки: принимает цель `NotifyTarget = { activate: () => void; href: string; label: string }` (href/label — для тоста-предложения вместо перехода).
- Переход по клику — через `runOrOffer(target)`: при открытом модальном окне (`document.querySelector('[role="dialog"][aria-modal="true"]')`) вместо перехода показывается тост `pushToast('info', body, { link: { label, href } })`; иначе `target.activate()`. Запасной механизм по фокусу переход не выполняет никогда — только тост-предложение.
- Запасной механизм по фокусу — только для десктопа не-Windows (определение: `/Windows/.test(navigator.userAgent)`, WebView2 содержит «Windows NT»); на Windows false от notify_desktop означает только путь плагина, без запасного механизма. Если живая UAT на Windows покажет, что активация не приходит, это STOP-условие плана 32 (новый gap), а не повод молча включить запасной механизм на Windows.

Purpose: уведомление ведёт туда, о чём оно сообщает.
Output: requestTarget.ts, обновлённые systemNotify/chatNotifications/EmployeeLayout/RequestsPage, правило C11, UI-SPEC §12.
</objective>
