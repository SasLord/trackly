## Summary

Фаза почти целиком строится на уже существующей инфраструктуре: вложения 41.3 (`attachments` + `AttachmentService.ingest/authorize`), участники заявки 41.4 (`request_participants`, `participant_user_ids`), единый WS-канал `WsEvent` с серверным фильтром `is_visible_to`, и реестровые гейты write-site. Новых крейтов и npm-пакетов не требуется: Package Legitimacy Audit пуст.

Главные проектные решения, которые планировщик должен принять и закрепить в планах: (1) схема V054 — `chat_messages`, `chat_reads`, `attachments.message_id` (ADD COLUMN, не перестройка); (2) атомарная отправка «текст + файлы» через черновики вложений (`parent_kind='message_draft'`), которые повышаются до `request` в одной writer-транзакции вместе со вставкой сообщения; (3) единый `ChatService` в `trackly-app/src/services/chat_service.rs` — все права, проверка статуса и лимитов там, а tauri-команды и axum-обработчики — тонкие адаптеры; (4) счётчики считаются сервером по `id`-отметкам, а не по времени; клиент только инвалидирует по WS; (5) новые WS-события и регистрация во всех гейтах (реестр write-site, паритет Tauri-команд и HTTP-маршрутов, фикстура разрешённых команд сотрудника, реестр сброса пользовательских кэшей).

**Primary recommendation:** один новый сервис `ChatService` + миграция V054 + два WS-варианта (`ChatMessage`, `ChatReadChanged`); ленту отдавать готовой с сервера (одна команда `chat_feed`), счётчики — отдельной командой `chat_unread_summary`, не добавляя поле в `RequestDto`.

### Pattern 1: Схема V054 (только CREATE/ALTER ADD COLUMN)
**What:** урок V042/V044: никаких перестроек таблиц и DROP родителей внутри refinery-транзакции (`PRAGMA foreign_keys=OFF` там не действует) [VERIFIED: memory migration_fk_off_noop_in_refinery_tx; V050 комментарий]. Последняя строка файла обязана быть `PRAGMA user_version = 54;` (иначе красные тесты в ci-full) [VERIFIED: memory migration_user_version_pragma]. Следующий номер — V054 (последний V053) [VERIFIED: `ls migrations`].
```sql
CREATE TABLE chat_messages (
  id                    INTEGER PRIMARY KEY AUTOINCREMENT,
  request_id            INTEGER NOT NULL,            -- без FK (как attachments): запись переживает всё
  author_user_id        INTEGER NULL,                -- без FK; NULL невозможен при записи через сервис (см. Pitfall 7)
  body                  TEXT    NOT NULL DEFAULT '', -- <= 4000 символов проверяет Rust
  created_at_utc        INTEGER NOT NULL,
  moved_from_request_id INTEGER NULL                 -- D-09
);
CREATE INDEX idx_chat_messages_request ON chat_messages (request_id, id);

CREATE TABLE chat_reads (
  user_id               INTEGER NOT NULL,
  request_id            INTEGER NOT NULL,
  last_message_id       INTEGER NOT NULL DEFAULT 0,
  last_audit_id         INTEGER NOT NULL DEFAULT 0,
  updated_at_utc        INTEGER NOT NULL,
  PRIMARY KEY (user_id, request_id)
);

ALTER TABLE attachments ADD COLUMN message_id INTEGER NULL;   -- D-16, from_message
CREATE INDEX idx_attachments_message ON attachments (message_id);

-- Водяной знак: события, существовавшие до фазы, не считаются непрочитанными.
INSERT INTO app_settings (key, value) SELECT 'chat_unread_baseline_audit_id', CAST(COALESCE(MAX(id),0) AS TEXT) FROM audit_log;
PRAGMA user_version = 54;
```
(Точные имена колонок `app_settings` сверить с `V0xx` — это `[ASSUMED]` по памяти о таблице; планировщик обязан открыть DDL `app_settings`.) Отсутствие строки `chat_reads` читается как `last_message_id=0`, `last_audit_id=baseline`. Без водяного знака у каждого пользователя после обновления вся история всех заявок стала бы «непрочитанной».

### Pattern 2: Лента, собранная на сервере (MSG-02)
Один запрос `chat_feed(request_id)` -> `ChatFeedDto { items, can_post, max_size_bytes, first_unread_id, resolution_notes }`. Источники (все после одной проверки доступа):
1. `chat_messages` + вложения (`attachments WHERE message_id = m.id`, с `AttachmentService::to_dto`, плюс `from_message`).
2. События: тот же запрос, что `requests_sqlite::get_history` (`audit_log`, `entity_type='request'`, `action NOT IN ('list','get')`), КРОМЕ `custom:attachment_*`.
3. События вложений: как `AttachmentService::history`, но исключая те `attachment_added`, у которых вложение имеет `message_id IS NOT NULL` (UI-SPEC §9.4: файлы сообщений отдельного блока не дают).
Сортировка: `created_at_utc`, затем «событие раньше сообщения», затем `id`. Идентификатор элемента ленты — строка-ключ вида `m{id}` / `e{id}` / `a{id}` (стабильный, уникальный). Роль автора (`admin|manager|requester|participant`) вычисляется на сервере по состоянию на момент чтения. `is_own = (author_user_id == caller.user_id)`.
Подсказка: для `complete`/`reject` в DTO события `show_notes=true` только у последнего такого события; текст — `requests.resolution_notes` (не копируется в сообщения, D-12).

### Pattern 3: Атомарная отправка «текст + файлы» через черновики (рекомендация, [ASSUMED] A1)
Требование UI-SPEC §10.3: отказ любого файла = сообщение не создаётся. Загрузка файлов — поштучная (`attachments_upload`: raw-body в Tauri, multipart в HTTP; параметры родителя в заголовках/query) [VERIFIED: `http/attachments.rs`, `tauri_cmds/attachments.rs`]. Решение:
1. Клиент по «Отправить» шлёт каждый файл существующим upload-маршрутом с `parent_kind = "message_draft"`, `parent_id = request_id`. В `ingest` для черновика: авторизация «участник + заявка открыта + тип не ad_register» (в `decide` добавить ветку `ParentKind::MessageDraft`; `Intent::Read/Delete*/ManageDeleted` для него — `Forbidden`, чтобы публичные `attachments_list/history/delete/purge` не открывали черновики); НЕ писать `audit_log` и НЕ слать `AttachmentsChanged` (иначе черновик попадёт в «Историю» и счётчики). Строки получают `parent_kind='message_draft'`, поэтому ни один существующий читатель `parent_kind='request'` (list, merge-копирование, `link_scans`, history) их не видит — менять эти читатели не нужно.
2. Любой `reject_code` -> клиент вызывает `chat_discard_drafts(request_id)` (удаляет черновики вызывающего этой заявки с учётом refcount по хешу — переиспользовать логику `purge`) и показывает ошибки.
3. Успех всех файлов -> `chat_send({requestId, text, draftAttachmentIds})`. В ОДНОЙ writer-транзакции: проверить статус заявки (TOCTOU: статус читать ВНУТРИ closure), длину, что `draftAttachmentIds` — черновики этого пользователя этой заявки; вставить `chat_messages`; `UPDATE attachments SET parent_kind='request', message_id=? ...`; для каждого файла вставить `audit_log` `custom:attachment_added` с `message_id` в `payload_json` (чтобы «История» вкладки «Информация» показала «Приложен файл», а лента/счётчик его исключили). Затем (после `await`) `ChatMessage` в WS.
4. Страховка: чистка черновиков старше N часов при старте (зарегистрировать как `ro/ex` в реестре, см. Pitfall 3) и в `chat_send` на закрытой заявке.
Альтернатива, если планировщик отвергнет черновики: отправлять текст первым, файлы дозагружать с `message_id`; цена — частичное сообщение при отказе файла (противоречит §10.3, пункт 6 «Решений на усмотрение»).

### Pattern 4: Непрочитанное (D-17..D-20, D-24)
- Отметка `chat_reads(user_id, request_id)` хранит `last_message_id` и `last_audit_id` — по `id`, а не по секундам (в `unix_seconds` много коллизий).
- `chat_unread_summary(caller)` -> `{ items: [{requestId, count}], requestsWithUnread }`. Область заявок: та же видимость, что `request_visibility_clause` (`repairs_sqlite.rs`, автор или участник) для Employee; без неё для Admin/Manager; всегда `deleted_at_utc IS NULL`, `request_type <> 'ad_register'`. Счёт = `chat_messages` чужие с `id > last_message_id` + `audit_log` (`entity_type='request'`, `entity_id`, `id > COALESCE(last_audit_id, baseline)`, `user_id IS NOT caller`, исключая `list/get` и «файлы сообщений» по маркеру `message_id` в payload; `payload_json NOT LIKE '%"message_id"%'` либо `json_extract`). Индекс `idx_audit_log_entity (entity_type, entity_id, created_at_utc)` существует [VERIFIED: V012]; добавить `idx_chat_messages_request`.
- `chat_mark_read(request_id)`: writer UPSERT текущих максимумов; затем WS `ChatReadChanged{user_id}`, видимый ТОЛЬКО этому `user_id` (остальные устройства/транспорты того же пользователя перечитывают сводку; D-19).
- D-24: все события жизненного цикла и так шлют WS (`RequestStatusChanged` через `repair_service::finish_transition` и `request_service`, `AttachmentsChanged`, `NewRequest`) [VERIFIED: grep по `repair_service.rs`/`request_service.rs`]. Клиент перечитывает сводку на `chat_message`, `request_status_changed`, `attachments_changed`, `new_request`, `chat_read_changed` — нового серверного кода для событий не нужно, но нужен тест-инвентарь «каждая запись `audit_log` entity=request сопровождается одним из этих сигналов» (Pitfall 4).
- Нет `ChatReadChanged` для чужих: `identity.user_id == Some(user_id)` (Admin не видит чужие отметки).

Обновить: ручной TS-тип `WsEvent` в `ui/src/bindings-phase6.ts` (ручной, не генерируется) [VERIFIED], юнит-тесты `is_visible_to` в `dto/printer.rs`, комментарий в `ws.ts`. Для Admin/Manager `is_visible_to` = true по ролям (D-20). Рассылка — только после `await writer.execute`, никогда внутри closure (образец: `attachments_changed_gate.rs`).
Десктопный мост в `main.rs` форвардит ВСЕ события без фильтра (десктоп = админ-идентичность) [VERIFIED: main.rs ~326]; тост на десктопе нужно сравнивать `actor_user_id` с id текущего пользователя в клиенте.

### Pattern 6: Перенос при объединении (D-09)
В `repair_service::merge_into_open` (writer-closure, `repair_service.rs` ~1672–1880): `UPDATE chat_messages SET request_id=target, moved_from_request_id=source WHERE request_id=source` (перенос, не копия); цикл копирования вложений (`list_by_parent_on` -> `insert_on`) должен сохранять `message_id` копии (`AttachmentNew` сейчас поля не имеет — добавить `message_id: Option<i64>` и поправить все вызовы `AttachmentNew{..}`); у исходных строк поглощённой заявки `message_id` остаётся — решить: обнулить (рекомендация), иначе плитка «из чата» в закрытой поглощённой заявке указывает на сообщение, которого в её чате нет. После коммита слать `ChatMessage`-подобный сигнал цели не нужно: достаточно существующих `RequestStatusChanged`/`AttachmentsChanged` по цели (клиент перечитывает ленту на любое событие по открытой заявке). Строку-исключение `merge_into_open` в реестре (`entities_support/registry.rs`) дополнить в причине упоминанием переноса сообщений. Старые `id` перенесённых сообщений меньше `last_message_id` читателей цели — они не станут «непрочитанными»; это приемлемо, зафиксировать в плане.

### Anti-Patterns to Avoid
- Копировать `resolution_notes` в `chat_messages` (D-12 запрещает).
- Класть сообщения в `audit_log` (запрещено `.planning/v1.4-GROUPS-MODEL-DECISIONS.md`).
- Проверять права в tauri-команде/axum-обработчике, а не в сервисе (расхождение транспортов = дыра BOLA).
- Слать `ChatMessage` до `await` писателя (при откате транзакции клиенты получили бы призрак).
- Считать непрочитанное на клиенте по локальным данным (D-19).
- Новый `ParentKind::Message` как родитель: ломает list/history/merge/права; родитель остаётся `request`, ссылка — `message_id`.
- Нативный `<select>`; `{@html}` для текста сообщения.

## Common Pitfalls

### Pitfall 1: Проверка прав только на одном транспорте
**What goes wrong:** HTTP-обработчик забыл вызвать сервис-проверку; сотрудник читает чужой чат (MSG-03). **How to avoid:** `ChatService` сам вызывает `authorize` в каждом публичном методе (`feed`, `send`, `mark_read`, `discard_drafts`), адаптеры не содержат логики. **Warning signs:** тест роли проходит только через `ctx.chat`, а не через `build_router()`. Тесты обязаны ходить на ОБА: сервис напрямую (Tauri-путь через `build_chat_*`) и `build_router()` с сессией сотрудника (по образцу `attachments_http.rs`, `role_endpoint_matrix.rs::attachments_role_matrix_http`).

### Pitfall 2: spa_fallback маскирует отсутствующий маршрут
**What goes wrong:** команда зарегистрирована в Tauri, маршрута в axum нет — по LAN приходит `index.html` с 200 (теперь 404 JSON после F17, но клиент `apiCall` приводит HTML к типу ответа) [VERIFIED: комментарии `http_route_parity.rs`, `check-store-response-shape.mjs`]. **How to avoid:** каждую `chat_*` команду зарегистрировать в `collect_commands!` (`specta_export.rs`) И в `http/chat.rs` + `http/mod.rs::build_router`; гейт `http_route_parity` сверит паритет; `unreadStore` обязан проверять форму ответа до записи в `$state` (HTML-строка вместо объекта).

### Pitfall 3: Реестр write-site и гейты
**What goes wrong:** новый `chat_service.rs` с `writer.execute` краснит `entities_changed_gate`: файл вне `SCOPE_FILES` и не в `OUT_OF_SCOPE_WRITERS` (проверка `writer_owning_services_outside_scope_are_listed`) [VERIFIED: `entities_support/registry.rs`]. **How to avoid:** добавить `("chat_service.rs", "<причина >= 40 символов>")` в `OUT_OF_SCOPE_WRITERS` (чат не меняет места/устройства/картриджи/группы; сигнал — отдельный `WsEvent::ChatMessage`); завести `chat_changed_gate.rs` по образцу `attachments_changed_gate.rs` (позиционная проверка «`ws send` после конца `writer.execute(...)`.await», вердикты на каждую функцию с `writer.execute`, мутационные доказательства с уникальными якорями — memory mutation_test_anchor_must_be_unique). Не вызывать `broadcast_entities`/`EntitiesChanged` (Admin-only событие дерева мест; чат ему не нужен). `merge_into_open` и `attachment_service.rs::ingest` (ветка черновика) тоже правятся — обновить причины/вердикты.

### Pitfall 4: Событие без WS-сигнала => счётчик застывает
**Why:** D-24 держится на том, что КАЖДАЯ запись `audit_log` по заявке сопровождается WS. **How to avoid:** тест-инвентарь «от сервера»: перечислить все `entity_type: "request"` вставки (repair_service: ~14 мест, request_service: 6, auth.rs — ad_register, исключены) и подтвердить сигнал у каждой (все repair-переходы идут через `finish_transition`) [VERIFIED частично: grep]. Удаление заявки (`request_service::delete`) выводит её из сводки сама.

### Pitfall 5: Двойной счёт файла сообщения
Файл сообщения порождает `custom:attachment_added` в `audit_log` (нужен «Истории» вкладки «Информация») и одновременно пузырь. Маркер `message_id` в payload обязателен; без него счётчик +2, а чат покажет и пузырь, и блок «приложил файл».

### Pitfall 6: Идемпотентность и дубли
Ответ `chat_send` и WS-событие приходят оба; UI дедуплицирует по ключу `m{id}`. Двойной клик «Отправить» = два сообщения: блокировать кнопку на время запроса (`loading`).

### Pitfall 7: Идентичность без `user_id`
`Identity.user_id` бывает `None` (`Identity::trusted_admin`). Десктоп в обычном режиме идёт как системный «Администратор» с `user_id` [VERIFIED: `resolve_tauri_identity`, `system_admin_identity`], но сервис обязан отказывать (`Forbidden`) отправке/`mark_read` при `user_id = None`, а не писать `author_user_id NULL`.

### Pitfall 8: Свёрстанный клиент-зависимый порядок и Svelte-рантайм
`svelte-check`, `pnpm lint`, `pnpm build` не видят рантайм-ошибок рун [VERIFIED: memory compile_gates_miss_svelte_runtime]; отдельные команды, `pnpm lint` НЕ включает `svelte-check` [VERIFIED: memory ui_gates_are_separate_commands]. Неактивная вкладка не монтируется (`{#if}`), поэтому черновик композера и WS-подписка счётчика живут в `RequestDetail`/сторе, а не в `RequestChat` (UI-SPEC §6.1, §10.6). Модалка/просмотрщик наследует стили ячейки: явно задавать `white-space`/`text-align` на пузыре (memory modal_inherits_table_cell_styles); `AttachmentViewer` — один экземпляр соседним элементом (гейт `check-modal-isolation.mjs`).

### Pitfall 9: UI-гейты, которые покраснеют от этой фазы
- `check-user-scoped-reset.mjs`: `unreadStore.svelte.ts` (модульное состояние + API) обязан вызывать `registerUserScopedReset()`.
- `check-employee-api.mjs` + `ui/scripts/fixtures/employee-allowed-commands.json` (сверяется Rust-тестом `role_endpoint_matrix::employee_allowed_fixture_sound`): сотрудник вызывает `chat_feed`, `chat_send`, `chat_mark_read`, `chat_unread_summary`, `chat_discard_drafts` — добавить их в фикстуру И обеспечить, что сервер действительно пускает сотрудника (иначе тест красный).
- `check-ws-disconnect-toast.mjs`, `check-modal-isolation.mjs`, `check-tokens.mjs` (только `var(--tr-*)`, ни hex, ни `rgba()` в `<style>`), `check-contrast.mjs`, `check-attachments-block.mjs` (правка `AttachmentTile`), `check-store-response-shape.mjs` (если стор подпадёт под реестр).
- Новые структурные гейты по образцу существующих (счётный гейт слеп к порядку — memory counting_gate_blind_to_order): «охрана `isComposing`/`closed` до отправки» проверять мутацией-перестановкой.

### Pitfall 10: Файл теста не подключён
`autotests = false`: новый `tests/chat_*.rs` не запустится, пока не подключён через `#[path]` в `tests/suites/<suite>.rs` (иначе краснит `suite_wiring.rs`) [VERIFIED]. Рекомендуется новый suite `chat` (`[[test]] name = "app_chat"` в `crates/trackly-app/Cargo.toml`) + строки в `suites/chat.rs`; гейт-файлы — в `suites/gates.rs`.

## Open Questions

1. **Что делать с `message_id` у исходных вложений поглощённой заявки при объединении?**
   - Known: копии получают `message_id` (иначе теряется значок D-16 в целевой). Unclear: оставлять ли у оригиналов. Recommendation: обнулить.
2. **Нужен ли отдельный upload-маршрут для черновиков или достаточно нового `parent_kind`?**
   - Recommendation: переиспользовать существующий upload с `parent_kind=message_draft` (меньше дублирования; только ветка в `decide`).
3. **Эмитить ли `ChatMessage` при переносе сообщений в merge?** Recommendation: нет, достаточно `RequestStatusChanged`/`AttachmentsChanged` по цели; клиент перечитывает ленту.

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| BOLA: чтение чужой переписки по id заявки | Info disclosure | проверка в сервисе при каждом методе; тест на HTTP и сервис; код отказа без утечки существования |
| Отправка в закрытую заявку / гонка со сменой статуса | Tampering | проверка статуса ВНУТРИ writer-closure |
| Подмена `draftAttachmentIds` (чужие/другой заявки/уже повышенные файлы) | Tampering / Elevation | в транзакции проверять `parent_kind='message_draft' AND parent_id=? AND uploaded_by_user_id=?` и что `message_id IS NULL` |
| Stored XSS через текст сообщения / ссылку `javascript:` | Tampering | вывод только как текст (`{text}`), автоссылки только `http(s)://`, `rel="noopener noreferrer"`; тест `linkify` на `javascript:` |
| Утечка через WS | Info disclosure | `is_visible_to` на каждом новом варианте + юнит-тесты на роль/автора/участника/чужого |
| Спам/флуд сообщениями | DoS | лимит длины; (опционально) ограничение частоты — не требуется решениями, зафиксировать как принятый риск |
| Перебор `id` черновиков/сообщений | Info disclosure | права по заявке, а не по id сообщения |
| Утечка реальных данных в репозиторий | — (проектное условие) | только вымышленные имена/тексты в фикстурах и `.planning/`; прогнать `scripts/check-privacy.mjs` до коммита |

## Project Constraints (from CLAUDE.md)
- Публичный репозиторий: реальные данные организации/людей не попадают в код, тесты, фикстуры, скриншоты, `.planning/` (только вымышленные имена).
- Стек фиксирован: Rust + Tauri 2 + Svelte 5 + SCSS + SQLite; `rusqlite` + единственный writer (не sqlx); WAL; запись только через бэкенд-слой.
- Одна бизнес-логика на два транспорта (Tauri invoke + HTTP), адаптеры тонкие.
- Portable: без записи в `%APPDATA%`; чат ничего не пишет вне БД и каталога вложений.
- Только русский язык UI; ошибки сервера по машинному коду, не английским текстом.
- Версии зависимостей — по `Cargo.toml` (rusqlite 0.38, refinery 0.9), не по CLAUDE.md.
- GSD-процесс: правки только через GSD-команды.
- Проектная память: миграции с `PRAGMA user_version`; реестр инвалидации (INV-7); не запускать два `cargo test` одновременно; UI-гейты — отдельные команды; Dropdown вместо нативного `<select>`; auto_advance может закрыть human-verify без запуска приложения — чек-пункты отдать пользователю.
