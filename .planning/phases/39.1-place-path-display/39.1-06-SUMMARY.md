# Phase 39.1 Plan 06: Печатная форма акта показывает сокращённый путь Summary

**`ActService::render_pdf` now shortens the frozen `place_path_snapshot` by the CURRENT `place_effective_variant` for `acts.place_id` (never the variant at act-create time), with a mandatory pre-change `_legacy_defaults/v27/` snapshot so existing portable installs still receive the upgrade.**

## Performance

- **Duration:** ~30 min
- **Completed:** 2026-08-28
- **Tasks:** 2
- **Files modified:** 6 (2 created, 4 modified)

## Accomplishments
- `crates/trackly-app/templates/_legacy_defaults/v27/act_handover.html` captured byte-for-byte from `act_handover.html`'s pre-edit body, registered as the last entry for `act_handover.html` in `KNOWN_LEGACY_DEFAULTS` (`html_templates.rs`) — this happened as the literal first sub-step of Task 1, before any template edit, per Pitfall 2.
- New `compute_place_path_short()` free function in `act_service.rs`: given `place_id`/`place_path_snapshot`, resolves the effective variant via a single `SELECT effective_variant FROM place_effective_variant WHERE place_id = ?1` lookup; if that lookup fails (no `place_id`, or the place has since been soft-deleted — Pitfall 4, the view's base case filters `deleted_at_utc IS NULL`) it falls back to `app_settings.place_path_variant` (hardcoded `"ends"` if that too is missing); unexpected/corrupt variant tokens fall back to `PathDisplayVariant::Ends` rather than aborting. The whole chain uses `.ok()`/`.unwrap_or_else()` — no `.expect()`/`.unwrap()`/`?` anywhere on this path, so a printed act can never fail to render because of this cosmetic field.
- `render_pdf` calls this helper via `tokio::task::spawn_blocking` (same pattern as `get()`'s reader-pool access) and inserts `"place_path_short"` into the render context alongside the pre-existing, unmodified `"place_path"` key (Pitfall 3 — `place_path` itself was never touched or removed).
- `templates/act_handover.html`'s «Расположение:» field-row now reads `act.place_path_short` (both the value interpolation and the truthiness check that gates the blank-underline fallback).
- 3 new integration tests in `crates/trackly-app/tests/acts_place_path_short.rs`, all exercising the real `ActService::render_pdf` production pipeline (file-template load + live minijinja render + live DB queries, no mocking):
  1. `render_pdf_uses_current_variant_not_create_time_variant` — creates a 3-segment place, creates the act (frozen snapshot captured), THEN changes the room's own `path_variant_override` twice (`last_two`, then `ends`) and re-renders each time, proving the printed variant tracks the CURRENT DB state, not act-create time.
  2. `render_pdf_falls_back_to_org_default_when_place_disappeared` — soft-deletes the act's place after creation (Pitfall 4) and proves `render_pdf` falls back to the org default variant without panicking.
  3. `render_pdf_with_no_place_renders_blank_underline` — sanity check that the pre-existing D-27 blank-underline fallback (act with no place at all) is unaffected.

## Decisions Made
- The plan's acceptance criterion calling for a "throwaway `#[ignore]`-тест + PNG-осмотр через qlmanage" targets the pre-Phase-16 krilla/PDF rendering era; `render_pdf` now produces an HTML string, and no headless-render/screenshot tool exists in this codebase for the HTML pipeline. Substituted with non-ignored integration tests that call the real production pipeline end-to-end and assert on the exact rendered field-row HTML — stronger coverage (runs in CI) for the same D-20 guarantee.
- Updated `acts_place_snapshot.rs`'s `seeded_default_template_renders_place_path_field_row` assertion to expect the new shortened form — this is the intended contract change this plan makes (D-20 supersedes the prior D-27 full-path expectation on the field-row), not a regression.

## Issues Encountered
- First draft of `acts_place_path_short.rs`'s `ends`-variant assertion expected a literal `" // "` in the escaped HTML, but minijinja's autoescaper (`build_safe_html_env`, T-16-01) encodes each `/` character individually as `&#x2f;` — a two-slash separator therefore renders as `&#x2f;&#x2f;`, not a single combined entity. Caught immediately by the RED/GREEN test run before any commit; fixed the test expectation, no production code was affected.
