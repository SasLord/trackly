## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Где разрешается наследование

- **D-01:** Наследование разрешает **бэкенд**, и отдаёт клиенту **готовую короткую строку**
  (`place_path_short`) рядом с полным путём — не «эффективный вариант», не карту дерева на фронте.
  Причина: строки отчётов несут путь строкой без `place_id`
  ([report_service.rs:1160](crates/trackly-app/src/services/report_service.rs:1160)), а CSV/PDF/печать
  генерируются на бэкенде — единая точка сокращения покрывает все транспорты сразу.
- **D-02:** Сокращение считается **на каждом запросе** (как `place_full_paths`, который никогда не
  бывает устаревшим). Новый WS-broadcast не заводим: смена умолчания или варианта видна при
  следующей загрузке списка.
- **D-03:** Наследование **динамическое**: место со значением «Как у родителя» при перемещении
  подхватывает вариант нового родителя. Ничего не снапшотится, инвалидировать нечего.
- **D-04:** Переопределение места **не сбрасывается** при перемещении, в том числе при переносе
  на верхний уровень — там дропдаун тоже доступен (см. D-06), скрытого состояния не возникает.
- **D-05:** В форме Места **не показываем**, во что разрешается «Как у родителя» — ни подписи,
  ни примера, ни названия унаследованного варианта в пункте.

#### Настройки организации и форма Места

- **D-06:** Дропдаун «Вариант сокращения» есть у **всех** мест, включая места верхнего уровня;
  у них «Как у родителя» ссылается на умолчание организации. Отдельного корневого элемента с
  именем организации в разделе «Места» нет и не появляется — корень это Организация,
  и настраивается он в Настройках.
- **D-07:** Умолчание организации живёт **новым подразделом внизу «Настройки → Организация»**
  (`ui/src/features/settings/OrgSettings.svelte`): выбор варианта + предпросмотр.
- **D-08:** Разделитель — **отдельное поле на каждый вариант**: одно для «Крайние», одно для
  «Два последних». Не одно общее поле, как предполагал SC#2 роадмапа.
- **D-09:** Умолчания разделителей: «Крайние» = ` // `, «Два последних» = ` / `. Пробелы значимы,
  значение `, ` даёт перечисление через запятую.
- **D-10:** Пустой разделитель **запрещён** — поле обязательное, сохранение отклоняется с
  сообщением об ошибке.
- **D-11:** Предпросмотр показывает **все три варианта разом на двух образцах** (сетка 3×2):
  «Здание А / 1 этаж / 1-05» и «Территория А / Объект Х / помещение 3». Оба поля разделителей
  видны в действии сразу, без переключения радио-кнопок.
- **D-12:** Права на изменение варианта у места — **те же, что и на редактирование Места**
  (не отдельный ManageSettings). Поле сохраняется тем же вызовом, что название и тип.

#### Формула сокращения

- **D-13:** Разделитель варианта **соединяет показанные сегменты**, а не отмечает пропуск как
  особый символ. Но ставится он **только когда что-то реально выброшено** — правило из
  quick 260827-ui3 сохраняется.
- **D-14:** Следствие D-13: путь из 2 сегментов при варианте «Крайние» отдаётся как
  «Здание А / 1 этаж» со штатным ` / ` — выбрасывать нечего, разделитель варианта не появляется.
- **D-15:** «Последнее» для пути из одного сегмента показывает его же («Склад»), без маркера
  сокращения.
- **D-16:** «Два последних» на пути из 3+ сегментов даёт «1 этаж / 1-05» (свой разделитель из D-09);
  «Крайние» на том же пути — «Здание А // 1-05».

#### Охват — где путь сокращается

- **D-17:** Сокращается: экранные списки (Отчёты, Содержимое места, Устройства, Картриджи) —
  как сейчас, плюс **печать и PDF отчётов** (`reports_export_pdf`, HTML-рендер на бэкенде),
  плюс **печатные формы актов**.
- **D-18:** **CSV-экспорт отчётов отдаёт полный путь** — файл уходит третьим лицам, подсказки при
  наведении в нём нет, сокращение теряло бы информацию безвозвратно.
- **D-19:** Остаются **полными**: детальные экраны (ActDetail, CartridgeDetail, PrinterDetail),
  выбор места в PlacePicker/ReturnModal, результаты поиска в дереве мест. Граница из
  quick 260827-ui3 не двигается.
- **D-20:** В акте сокращается **снимок пути** (`place_path_snapshot`, заморожен по D-16 фазы 39),
  а вариант берётся по **текущему** состоянию `acts.place_id`; если `place_id` пуст или место
  исчезло — умолчание организации. Задевает minijinja-шаблоны актов, а они лежат **в БД** —
  сид шаблонов придётся трогать (см. Integration Points).
- **D-21:** Полный путь остаётся в `title` во всех экранных местах — без изменений (SC#5).

#### Переезд с конфига

- **D-22:** Ключ `[organization] place_path_display` **просто удаляется** — ни разового импорта в
  БД, ни warn-хука на старте. Приложение не в проде, ключу один день.
- **D-23:** После миграции: организация = «Крайние», **все существующие места = «Как у родителя»**
  (ноль переопределений). Система ведёт себя ровно как сегодня при дефолтном конфиге.

## Summary

Фаза переносит вариант сокращения пути места из `trackly.config.toml` в БД, с двумя новыми
измерениями: умолчание организации (3 значения — вариант + 2 разделителя, редактируется в
Настройках) и необязательное переопределение варианта на любом месте (наследуется по цепочке
предков). Кодовая база уже даёт готовый скелет для обоих измерений: `app_settings` key/value
(миграция V016) с парой `settings_get_/set_low_stock_basis` — канонический трёхкратно копируемый
образец для умолчаний организации; `place_full_paths` — рекурсивный CTE-вью (миграция V037),
пересчитываемый на каждом чтении, — образец для нового вью `place_effective_variant`, вычисляющего
эффективный вариант по цепочке предков с фолбэком на умолчание организации ПРЯМО в SQL (без
дополнительного Rust-обхода и без N+1).

Главная находка — объём затрагиваемых read-путей больше, чем можно предположить по CONTEXT.md:
`place_full_paths` заджойнена в ~13 местах в `devices_sqlite.rs`/`cartridges_sqlite.rs`/
`report_service.rs`/`places_sqlite.rs`, и не все из них — экранные списки; часть (autocomplete,
FTS-поиск, snapshot restore) относится к границе D-19 (детальные экраны/пикеры остаются
полными) и НЕ должна получать `place_path_short`. Вторая находка — существует ТРЕТИЙ CSV-экспорт
(`DeviceService::export_csv`, `device_service.rs:838`), не упомянутый явно в решениях D-17/D-18
(те говорят только про «Отчёты»); он тоже отдаёт `full_path` третьим лицам без всплывающей
подсказки — по духу D-18 его следует оставить ПОЛНЫМ, но это требует явного подтверждения на
этапе планирования, а не молчаливого решения. Третья находка — акт печатается из ДВУХ разных
шаблонных механизмов: активный HTML-пайплайн (`templates/act_handover.html`, файл на диске +
`include_str!`-дефолт, апгрейд через `KNOWN_LEGACY_DEFAULTS`) и замороженный
krilla/DocSpec-пайплайн (`document_templates` в БД) — D-20 трогает ТОЛЬКО первый, но
CONTEXT.md/память проекта цитируют формулировку «шаблоны в БД», которая относится ко ВТОРОМУ
(замороженному) механизму — риск спутать их при планировании реален и должен быть явно снят.

**Primary recommendation:** Хранить переопределение места как один nullable-столбец
`places.path_variant_override` (миграция V039), умолчания организации — как 3 ключа в
`app_settings` (копия паттерна `low_stock_basis` ×3), эффективный вариант вычислять новым
рекурсивным SQL-вью `place_effective_variant` (мирроринг `place_full_paths`, с фолбэком на
`app_settings` внутри самого SQL через скалярный подзапрос — единый JOIN на каждый существующий
read-путь, без N+1 и без Rust-обхода предков), а саму формулу сокращения — одной чистой Rust-
функцией `shorten_place_path(full_path, variant, sep_ends, sep_last_two) -> String` в
`trackly-core::domain::places`, вызываемой из каждого места, где сегодня селектится
`pfp.full_path`.

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Хранение умолчания организации (вариант + 2 разделителя) | Database (`app_settings`) | API/Backend (settings_org service) | Единый источник истины, переживает portable-перенос БД; сервис — тонкий адаптер поверх готового паттерна `low_stock_basis` |
| Хранение переопределения на месте | Database (`places` таблица) | API/Backend (`PlaceService`) | Часть жизненного цикла места; мутируется вместе с остальными полями места, а не как отдельная настройка |

| Формула сокращения строки (peel first/last segment) | API/Backend (Rust, `trackly-core`) | Browser/Client (TS, ТОЛЬКО для live-предпросмотра в Настройках, D-11) | D-01: клиент получает готовую строку `place_path_short`, не вычисляет сам; TS-копия существует ИСКЛЮЧИТЕЛЬНО для мгновенного превью двух образцов до сохранения — сознательное дублирование, а не архитектурная утечка |
| Валидация непустого разделителя (D-10) | API/Backend | Browser/Client (UX-подсказка) | Источник истины — сервер (единая точка для обоих транспортов); фронт может блокировать submit заранее, но не обязан |

### Pattern 1: `app_settings` key/value для умолчаний организации (переиспользуемый скелет)

**What:** Три новых ключа в `app_settings` (`place_path_variant`, `place_path_sep_ends`,
`place_path_sep_last_two`), каждый со своей парой `build_settings_get_*`/`build_settings_set_*`
в `tauri_cmds/settings_org.rs` + тонкими HTTP-хендлерами в `http/settings_org.rs`.

**When to use:** Ровно тот случай, для которого паттерн уже написан трижды (порог, база подсчёта
low-stock) — скалярная настройка организации, читаемая часто, редактируемая редко, без реляционных
ограничений.

**Канонический пример (буквальный код для копирования 3×):**
```rust
// Source: crates/trackly-app/src/tauri_cmds/settings_org.rs:241-296 (GET/SET low_stock_basis)
pub async fn build_settings_get_low_stock_basis(ctx: &AppCtx) -> Result<String, AppError> {
    let readers = ctx.readers.clone();
    tokio::task::spawn_blocking(move || -> Result<String, AppError> {
        let conn = readers.acquire();
        let result: rusqlite::Result<Option<String>> = conn.query_row(
            "SELECT value FROM app_settings WHERE key = 'low_stock_basis'",
            [], |r| r.get(0),
        );
        let basis = match result {
            Ok(Some(s)) => LowStockBasis::parse(s.trim()).unwrap_or(LowStockBasis::DEFAULT),
            Ok(None) => LowStockBasis::DEFAULT,
            Err(rusqlite::Error::QueryReturnedNoRows) => LowStockBasis::DEFAULT,
            Err(e) => return Err(map_rusqlite(e)),
        };
        Ok(basis.as_str().to_string())
    }).await.map_err(|e| AppError::Internal { source_chain: format!("spawn_blocking: {e}") })?
}

pub async fn build_settings_set_low_stock_basis(
    ctx: &AppCtx, caller_identity: &Identity, basis: String,
) -> Result<(), AppError> {
    authorize(caller_identity, &Action::ManageSettings)?;
    let parsed = LowStockBasis::parse(&basis).ok_or_else(|| AppError::Validation {
        field: "basis".to_string(),
        message: format!("Недопустимое значение базы подсчёта: {basis}"),
    })?;
    let now = ctx.clock.unix_seconds();
    let value = parsed.as_str().to_string();
    ctx.writer.execute(move |conn| {
        conn.execute(
            "INSERT INTO app_settings (key, value, created_at_utc, updated_at_utc) \
             VALUES (?1, ?2, ?3, ?3) \
             ON CONFLICT(key) DO UPDATE SET value = ?2, updated_at_utc = ?3",
            rusqlite::params!["low_stock_basis", value, now],
        ).map(|_| ()).map_err(map_rusqlite)
    }).await
}
```
Обёртки: `#[tauri::command]` в том же файле (строки 535-550), HTTP-хендлер + payload struct
+ роут в `http/settings_org.rs` (`SetLowStockBasisPayload`, `handler_get/set_low_stock_basis`,
роуты `/api/v1/settings_get_low_stock_basis` / `/api/v1/settings_set_low_stock_basis` —
`http/settings_org.rs:376-430`). Регистрация в `specta_export.rs:171-172`. Покрытие ролевой
матрицей — `role_endpoint_matrix.rs:1506-1521` (Case 44, Employee → 403). Копировать 3 раза: одна
GET/SET-пара на вариант, по одной на каждый разделитель — **или** объединить в один
`settings_get/set_place_path_defaults(OrgPathDisplayDto)` (patch-объект из 3 полей, как
`OrgPatch`/`settings_save_org_fields`), что даёт 1 сетевой round-trip на сохранение вместо 3.
Рекомендация: объединённый patch-эндпоинт (мирроринг `OrgPatch`) — экран Настроек сохраняет все
3 значения одним нажатием «Сохранить» (D-07/D-11 показывают все значения на одном экране), отдельные
round-trip'ы на каждое поле не нужны.

### Pattern 2: рекурсивный CTE-вью для наследования (мирроринг `place_full_paths`)

**What:** Новый вью `place_effective_variant`, вычисляющий для каждого `place_id` итоговый
вариант, поднимаясь по `parent_id`, пока не найдётся первое непустое `path_variant_override`;
если дошли до корня и всё ещё `NULL` — фолбэк на `app_settings.place_path_variant` ПРЯМО в SQL.

**When to use:** Везде, где сегодня используется `place_full_paths` для получения `full_path`
строки — те же ~13 join-точек получают ещё один `LEFT JOIN`.

**Обоснование выбора против Rust-обхода:** `place_full_paths` уже доказала на практике (D-02,
PLC-05), что «пересчёт на каждом чтении, без кэша» дёшево при ~300 строках (комментарий в
`migrations/V037__places.sql:24-27`). Вынос в Rust означал бы либо (а) для каждой строки списка
устройств отдельный запрос по цепочке предков — классический N+1, либо (б) загрузку всего дерева
мест в память на каждый read-путь и обход в Rust — рабочий, но избыточный вариант, дублирующий
логику, которую SQLite уже вычисляет через индекс `idx_places_parent`. SQL-вью даёт то же самое
за одно и то же исполнение запроса, без дополнительных round-trip'ов — не N+1 в смысле лишних
обращений к БД (то же соединение, тот же `EXPLAIN`-план, что и текущий `LEFT JOIN place_full_paths`).

**Пример (новый код, для справки планировщику, НЕ буквальная реализация фазы — она пишет код):**
```sql
-- Source: mirrors migrations/V037__places.sql:24-40 (place_full_paths), extended
-- with early-exit-on-resolve + org-default fallback baked into the terminal SELECT.
CREATE VIEW place_effective_variant AS
WITH RECURSIVE walk(id, parent_id, variant) AS (
  SELECT id, parent_id, path_variant_override
  FROM places WHERE deleted_at_utc IS NULL
  UNION ALL
  SELECT w.id, p.parent_id, p.path_variant_override
  FROM walk w
  JOIN places p ON p.id = w.parent_id
  WHERE w.variant IS NULL AND p.deleted_at_utc IS NULL
)
SELECT id AS place_id,
       COALESCE(
         variant,
         (SELECT value FROM app_settings WHERE key = 'place_path_variant')
       ) AS effective_variant
FROM walk
WHERE variant IS NOT NULL OR parent_id IS NULL;
```
Корректность условия `WHERE variant IS NOT NULL OR parent_id IS NULL`: recursion естественно
останавливается для каждого `id`, как только либо (а) найден override (условие `w.variant IS NULL`
в рекурсивном члене становится ложным — новых строк для этого `id` не генерируется), либо
(б) `w.parent_id` стал `NULL` (JOIN не находит родителя — рекурсия обрывается сама). На каждом
промежуточном шаге `parent_id` результирующей строки НЕ NULL (мы только что успешно
присоединились к родителю) И `variant` NULL (иначе рекурсия бы остановилась) — то есть
промежуточные строки исключаются предикатом автоматически, остаётся ровно одна терминальная
строка на `id`. Разделители (`sep_ends`/`sep_last_two`) в вью НЕ нужны — по D-08 они существуют
только на уровне организации (без переопределения на месте), поэтому читаются ОДИН раз за вызов
read-пути (не на строку), как в Pattern 1, и передаются в `shorten_place_path` вместе со
значением из этого вью.

### Pattern 3: единая функция сокращения (перенос `placePath.ts` на Rust)

**What:** `shorten_place_path(full_path: &str, variant: PathDisplayVariant, sep_ends: &str,
sep_last_two: &str) -> String` в `crates/trackly-core/src/domain/places.rs`, портирующая
`ui/src/lib/utils/placePath.ts:shortenPlacePath` дословно с уточнениями D-13..D-16 (см. таблицу
ниже). Единственная точка истины на бэкенде — вызывается из каждого места, где сегодня читается
`pfp.full_path`, плюс из `act_service.rs::render_pdf` (D-20, отдельный вызов на замороженном
`place_path_snapshot`).

**Формула «вход → ожидаемый выход» (основа юнит-тестов):**

| Сегментов | Вариант | Вход | Выход | Разделитель использован |
|-----------|---------|------|-------|--------------------------|
| 1 | ends | «Склад» | «Склад» | — (нечего сокращать, D-15 аналог) |
| 1 | last_two | «Склад» | «Склад» | — |
| 1 | last | «Склад» | «Склад» | — (D-15, буквальный пример) |
| 2 | ends | «Здание А / 1 этаж» | «Здание А / 1 этаж» | обычный ` / `, НЕ sep_ends (D-14 — нечего выбрасывать) |
| 2 | last_two | «Здание А / 1 этаж» | «Здание А / 1 этаж» | обычный ` / `, НЕ sep_last_two (симметрично D-14) |
| 2 | last | «Здание А / 1 этаж» | «1 этаж» | — (последний сегмент, всегда без разделителя) |
| 3 | ends | «Здание А / 1 этаж / 1-05» | «Здание А // 1-05» | sep_ends (по умолч. ` // `, D-16 буквальный пример) |
| 3 | last_two | «Здание А / 1 этаж / 1-05» | «1 этаж / 1-05» | sep_last_two (по умолч. ` / `, D-16 буквальный пример) |
| 3 | last | «Здание А / 1 этаж / 1-05» | «1-05» | — |
| 4+ | ends | «Территория А / Объект Х / Здание 1 / помещение 3» | «Территория А // помещение 3» | sep_ends |
| 4+ | last_two | «Территория А / Объект Х / Здание 1 / помещение 3» | «Здание 1 / помещение 3» | sep_last_two |
| 4+ | last | «Территория А / Объект Х / Здание 1 / помещение 3» | «помещение 3» | — |

**Значимость пробелов в разделителе (D-09/D-10):** сериализация должна пройти без `.trim()` на
всём пути — TS `<input>` → JSON `fetch`/Tauri `invoke` → Rust `String` (serde не тримит) →
`INSERT INTO app_settings` (SQLite TEXT хранит побайтово) → обратное чтение → TS. Проверить явно:
значение `", "` (запятая+пробел) должно пережить весь путь без обрезки, чтобы дать «Здание А,
1 этаж, 1-05». Единственная точка, где допустима проверка — это **непустота** (`!value.is_empty()`,
НЕ `!value.trim().is_empty()`) на этапе валидации сохранения (D-10): разделитель из одних пробелов
(`"   "`) должен ПРОЙТИ валидацию (не путать «пустой» и «состоящий из пробелов» — разные вещи).

**Anti-Patterns to Avoid:**
- **Путать старый `PlacePathDisplay::Full` с новым вариантом `last`:** старый `full` = «не
  сокращать вообще» (весь путь). Новый третий вариант в CONTEXT.md называется «Последнее» и
  означает «показать ТОЛЬКО последний сегмент» — семантически противоположная операция при том же
  порядковом номере варианта (третий из трёх). Явно проверить в код-ревью, что никто не
  скопировал старую ветку `variant === 'full' => return fullPath` при переносе.
- **Тримить разделитель «для аккуратности»:** любой `.trim()` на пути разделителя ломает D-09/D-10
  контракт (см. выше).
- **Вызывать `shorten_place_path` внутри цикла по предкам в Rust:** формула работает на уже
  готовой строке `full_path` (из `place_full_paths`) и уже разрешённом `variant` (из
  `place_effective_variant`) — она НЕ ходит в БД и НЕ обходит дерево сама; обход дерева живёт
  только в SQL-вью (Pattern 2).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Обход предков места в Rust с ручными запросами | Рекурсивная функция `fn resolve_parent_chain(place_id) -> Vec<PlaceRow>` + Rust-цикл | Рекурсивный CTE-вью (Pattern 2) | `place_full_paths` уже доказал, что SQLite справляется с этим быстрее и без лишних round-trip'ов; Rust-версия — это N+1 в лучшем случае и повторная реализация того, что движок БД делает нативно |
| Сериализация/валидация разделителя | Собственный `TrimmedString`-обёрточный тип | `String` + явная проверка `!s.is_empty()` в хендлере (без `.trim()`) | Обёрточный тип рискует незаметно затримить значение где-нибудь в `Deref`/`Display` — риск для D-09/D-10 слишком велик, чтобы вводить лишний слой абстракции |
| Кэш эффективного варианта («на случай, если CTE окажется медленным») | Any in-memory/DB cache invalidated on place move | Ничего — пересчёт на каждом чтении (D-02) | Прямое требование владельца продукта; кэш вводит инвалидацию, которую придётся синхронизировать при `places_move`/`places_set_path_variant`/смене умолчания организации — источник багов, которого CTE-подход избегает по конструкции |

**Key insight:** Всё, что уже решено для `place_full_paths` (пересчёт на лету, никакого кэша,
никаких WS-broadcast) — прямой прецедент для этой фазы. Задача планировщика — не изобретать новый
паттерн, а систематически применить существующий к ~13 read-путям и 3 write-путям.

## Common Pitfalls

### Pitfall 1: Devices CSV-экспорт не покрыт явным решением D-17/D-18
**What goes wrong:** `DeviceService::export_csv` (`crates/trackly-app/src/services/
device_service.rs:838-915`) отдаёт `device.full_path` (полный, несокращённый) в CSV со списком
устройств — это ОТДЕЛЬНЫЙ экспорт, не «Отчёты» (`report_service.rs`), и CONTEXT.md его явно не
называет. Если реализовать по букве D-17 («экранные списки сокращаются») и не заметить, что этот
конкретный код-путь строит CSV, а не экран, можно случайно сократить путь в файле, который уходит
третьим лицам — то есть повторить именно ту ошибку, которую D-18 предотвращает для отчётов.
**Why it happens:** CONTEXT.md перечисляет интеграционные точки по имени `report_service` — легко
пропустить второй, структурно похожий CSV-путь в `device_service`.
**How to avoid:** Планировщик должен явно решить (и зафиксировать как задачу с тестом) — оставить
`DeviceService::export_csv` на ПОЛНОМ пути, по духу D-18 (третьи лица, нет hover-подсказки,
безвозвратная потеря информации). Именно поэтому этот путь получает статус ASSUMED, а не CITED —
не подтверждён явным решением владельца продукта.
**Warning signs:** Тест на этот экспорт молчит про D-18 — регрессия не будет замечена автотестами,
пока кто-то не откроет CSV руками.

### Pitfall 2: Два разных шаблонных механизма актов — легко перепутать
**What goes wrong:** В проекте ОДНОВРЕМЕННО существуют (а) активный HTML-пайплайн
(`crates/trackly-app/templates/act_handover.html`, встроен через `include_str!` в
`DEFAULT_HTML_TEMPLATES`, `pdf/html_templates.rs:30-40`, материализуется как ФАЙЛ рядом с
исполняемым файлом, апгрейд untouched-копий через `KNOWN_LEGACY_DEFAULTS` +
`upgrade_untouched_defaults_on_startup`) и (б) замороженный krilla/DocSpec-пайплайн
(`template_service.rs`, таблица `document_templates` В БД, явно помечен как «frozen but not
removed» в `pdf/html_templates.rs:6-9`). Память проекта («DB-backed templates upgrade trap») и
формулировка в CONTEXT.md («шаблоны актов… лежат в БД») описывают риск, исторически верный для
пайплайна (б) — но D-20 правит рендер актов, который сегодня идёт через пайплайн (а), файловый, а
не БД-шный.
**Why it happens:** Терминология «шаблоны в БД» — устаревшая для активного пути; ловушка
переносится по формулировке, а не по факту.
**How to avoid:** Планы фазы должны трогать ТОЛЬКО `crates/trackly-app/templates/act_handover.html`
+ соответствующий `KNOWN_LEGACY_DEFAULTS`-снапшот (новая версия v25 или следующая свободная — см.
`html_templates.rs:70-90` для формата), а НЕ `document_templates`/`template_service.rs`. Класс
риска («правка бандл-дефолта не доходит до существующих инсталляций») СОХРАНЯЕТСЯ, но механизм
другой: для файлового пайплайна нужно (1) обновить `act_handover.html` (добавить вызов
сокращения в шаблон ИЛИ, что правильнее — передавать УЖЕ сокращённую строку из Rust-контекста, см.
Pitfall 3), (2) зафиксировать ПРЕДЫДУЩУЮ версию файла в новой `_legacy_defaults/vNN/
act_handover.html` папке и добавить её в `KNOWN_LEGACY_DEFAULTS` (иначе существующие portable-
инсталляции с уже материализованным на диске файлом молча не получат апгрейд — `html_templates.rs`
`Extension point` комментарий, строки 54-59, явно предупреждает об этом же классе ошибки).
**Warning signs:** Тесты на свежесозданной БД/директории (freshly materialized templates dir)
ЗЕЛЕНЫЕ независимо от того, добавлена ли `_legacy_defaults` запись — этот класс регрессии виден
только на «уже существующей» (не пустой) директории `templates/`, что `html_templates.rs`'s
собственный набор тестов (`every_default_template_has_a_known_legacy_defaults_entry` и парные
`upgrade_*`-тесты) уже явно проверяет — переиспользовать этот тестовый паттерн для новой ревизии
`act_handover.html`.

### Pitfall 3: логика сокращения НЕ должна попадать в minijinja-шаблон
**What goes wrong:** Соблазн добавить Jinja-фильтр/условие прямо в `act_handover.html`
(`{% if ... %}{{ act.place_path[:N] }}...{% endif %}`) вместо того, чтобы передавать УЖЕ
сокращённую строку из Rust-контекста (как сегодня делает `report_service.rs::export_pdf`, которое
строит `table_rows` через `row_field`, а не логику форматирования в самом `report.html`).
**Why it happens:** Кажется локально проще один раз поправить шаблон, чем провести значение через
Rust-контекст.
**How to avoid:** `act_service.rs:2694` (`"place_path": act.place_path_snapshot`) — единственная
точка изменения: вычислить `place_path_short` В RUST (используя `place_id` акта — ТЕКУЩИЙ, не из
снапшота, для определения эффективного варианта, см. D-20) и положить в контекст рядом со старым
полем: `"place_path": act.place_path_snapshot, "place_path_short": <вычислено>`. Шаблон
(`act_handover.html:257`) переключается на `{{ act.place_path_short }}` вместо `{{ act.place_path
}}` — само условие `{% if act.place_path %}...{% else %}<span class="value-blank"/>{% endif %}`
(строка 257) остаётся структурно тем же, меняется только имя используемого поля. Никакой бизнес-
логики форматирования пути в `.html`-шаблоне быть не должно — minijinja здесь используется как
чистый layout-движок, вся арифметика (peel first/last segment) остаётся в Rust, тестируемая юнит-
тестами из Pattern 3, а не в шаблонных тестах.

### Pitfall 4: `acts.place_id` может указывать на МЯГКО удалённое (архивное/удалённое) место
**What goes wrong:** `acts.place_id` — жёсткий FK с `ON DELETE RESTRICT`
(`migrations/V038__places_migrate_devices_acts_cartridges.sql:17`), и `subtree_stats_impl`
(`places_sqlite.rs:124-158`) считает акты, ссылающиеся на поддерево, в блокировку HARD-DELETE —
поэтому `place_id` физически НЕ может пережить `places_delete`. Но `deleted_at_utc` (SOFT-delete,
если он вообще применим к местам — проверить в планировании: `places.deleted_at_utc` существует в
схеме V037, но UI-эндпоинт `places_delete` вызывает `delete_hard`, а не soft; ЕСТЬ отдельные
`places_archive`/`places_unarchive`, работающие через `archived_at_utc`, НЕ через
`deleted_at_utc`) — значит колонка `deleted_at_utc` в реальности может не иметь UI-пути её
установки для мест вообще. Тем не менее `place_full_paths`/новый `place_effective_variant`
фильтруют `WHERE deleted_at_utc IS NULL` — если когда-либо появится путь мягкого удаления места
(или гипотетическая рассинхронизация данных), `full_path`/`effective_variant` для такого
`place_id` вернут `NULL` (LEFT JOIN не находит строку), а не ошибку.
**Why it happens:** D-20 формулирует «если place_id пуст ИЛИ место исчезло — умолчание
организации» — важно реализовать ОБА условия единообразно: `place_id IS NULL` (акт без места) и
«JOIN на `place_effective_variant` не нашёл строку» (гипотетическое «место исчезло») ДОЛЖНЫ вести
к одному и тому же фолбэку — org default — а не к панике/ошибке рендера акта.
**How to avoid:** В `act_service.rs::render_pdf` резолвить эффективный вариант через
`Option`-цепочку: `act.place_id.and_then(|pid| lookup(pid)).unwrap_or(org_default)` — НЕ
`.expect()`/`?` на отсутствующей строке. Юнит/интеграционный тест: акт с `place_id = NULL`
рендерится без паники, акт с валидным `place_id` — использует его текущий (не замороженный)
эффективный вариант.

### Pitfall 5: `row_field` — общая функция для CSV И PDF отчётов, легко случайно сократить оба или ни одного
**What goes wrong:** `row_field(row, col, tz)` (`report_service.rs:1016-1038`) сегодня вызывается
ОДИНАКОВО из `export_csv` (`report_service.rs:849`, через `row_field(row, col, tz)`) и
`export_pdf` (`report_service.rs:961`, через тот же вызов). Если добавить сокращение прямо внутрь
`row_field` без параметра-переключателя, оба вывода станут короткими (нарушение D-18) — если
забыть добавить сокращение вообще, оба останутся полными (нарушение D-17).
**Why it happens:** Общая функция — хороший DRY-паттерн для 90% случаев, но именно здесь два
вызывающих контекста должны сознательно РАСХОДИТЬСЯ, и общий сигнатурный контракт этого не
показывает.
**How to avoid:** Добавить явный параметр `shorten: bool` в сигнатуру `row_field(row, col, tz,
shorten)`; `export_csv` передаёт `false`, `export_pdf` — `true`. Для колонки `"place_path"`:
`if shorten { row.place_path_short... } else { row.place_path... }`. Для `"printer_place"`
(`combine_printer_and_place`, `report_service.rs:283-293`): сокращать ТОЛЬКО второй аргумент
(`printer_place`/место), `printer_name`/`device_name` передавать без изменений всегда — тест
`combine_printer_and_place_appends_place` (`report_service.rs:2316-2323`) и его соседи должны
получить пару новых кейсов на `shorten=true` с идентичным именем принтера и сокращённым местом.
Тест-регрессия на асимметрию: один и тот же `ReportResponse` экспортируется в CSV и PDF, для
колонки `place_path`/`printer_place` значения ДОЛЖНЫ различаться (CSV длиннее либо равен PDF,
никогда наоборот).
