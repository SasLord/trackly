# Phase 39.1 Plan 03: Экранные списки устройств получают сокращённый путь Summary

**`list()`, `search_fts()`, and all three `list_grouped()` SQL branches now LEFT JOIN `place_effective_variant` and compute `place_path_short` via the shared `shorten_place_path` formula, while `autocomplete`/`get`/`list_by_ids`/`restore_from_snapshot_in_tx` and CSV export stay untouched on the full path (D-19/D-24), with 6 new integration tests proving both halves of that boundary.**

## Performance

- **Duration:** ~35 min
- **Completed:** 2026-08-28
- **Tasks:** 2
- **Files modified:** 4 (1 created, 3 modified — plus 1 existing test file extended)

## Accomplishments
- `DeviceRow` (trackly-core) and `DeviceDto` (trackly-app) both gained `place_path_short: Option<String>`, populated identically to `full_path`'s existing null-when-no-place semantics.
- `devices_sqlite.rs::SELECT_DEVICES` grew a second `LEFT JOIN place_effective_variant` alongside the pre-existing `place_full_paths` join, adding `effective_variant` as column index 16. The shared `from_row` free function was left untouched (always sets `place_path_short: None`) so `get`/`get_in_tx`/`list_by_ids`/`restore_from_snapshot_in_tx` are unaffected by construction, not by an added exclusion check — exactly matching D-19's intent.
- A new `from_row_with_short_path(sep_ends, sep_last_two)` wraps `from_row`, reads column 16, and calls `shorten_place_path` when both `full_path` and `effective_variant` are present. `list()` and `search_fts()` (which builds its own row SQL rather than using `SELECT_DEVICES`, so it got the same JOIN added by hand) both use this wrapper.
- `list_grouped()`'s three static SQL branches (`sql_grouped_by_model_no_query`, `sql_grouped_by_model_with_query`, `sql_without_condition`) each gained a second `LEFT JOIN place_effective_variant pev ON pev.place_id = (...)` using the identical correlated `MAX(d2.place_id)` subquery already present for `place_full_paths` in that branch, plus a `pev.effective_variant AS place_variant` column appended at the end of the SELECT list (after `inv_no`/`serial_no`, matching where the tuple field was appended in `GroupRowTuple`/`group_row_tuple`). The assembling loop computes `place_path_short` once per group using a `read_path_display_separators(conn)` call made once before the loop, not per row.
- A new `read_path_display_separators(conn)` helper reads `place_path_sep_ends`/`place_path_sep_last_two` from `app_settings` once per query call, mirroring `CartridgeRepository::low_stock`'s guarded-read shape (`cartridges_sqlite.rs:930`), with V039-seeded defaults `" // "`/`" / "` as a defensive fallback.
- Task 2 added `export_csv_place_column_stays_full_path_not_shortened` to the existing `devices_csv_export.rs` integration-test file: creates a 3-segment place, sets an explicit `path_variant_override = 'ends'` on the leaf via raw SQL through `svc.writer` (no service method exists yet for that mutation — Plan 04+), creates a device there, and asserts the CSV "Место" cell equals the full path and explicitly is NOT the shortened form. `device_service.rs::export_csv` itself was not touched.

## Decisions Made
- Put the D-24 test in the existing `devices_csv_export.rs` file rather than a new `mod tests` block inside `device_service.rs` (see key-decisions above) — same effective coverage, reuses established fixture helpers (`make_service`, `seed_place`), zero duplication.
- Implemented the plan's "post-processing" instruction (option b) as a thin row-mapper wrapper around the existing `from_row` rather than a second pass over `Vec<DeviceRow>` — functionally identical outcome, avoids reallocating the whole result vector, and keeps `from_row`'s signature and all its other callers completely unchanged.

## Issues Encountered
- First pass at extending `list_grouped`'s three SQL branches placed the new `pev.effective_variant AS place_variant` column immediately after `pfp.full_path AS place_path` in the SELECT list, but appended the corresponding tuple field at the *end* of `GroupRowTuple`/`group_row_tuple` (after `inv_no`/`serial_no`). This is a classic column-index/tuple-index mismatch (Rule 1 bug, caught by a failing `list_grouped_returns_shortened_path_both_branches` test written in the same commit before it was ever staged) — fixed by moving the SQL column to the end of each SELECT list to match where the tuple field was appended, rather than reordering the tuple. Caught entirely within this task's own TDD cycle; never reached a commit.
