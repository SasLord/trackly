> Сгенерировано gsd-ui-researcher, проверяется gsd-ui-checker.

токенов, цветов, шрифтов, отступов или радиусов — только новую композицию из уже существующих

## Поверхность 1: «Настройки → Организация» — подраздел «Формат отображения пути места»

### Визуальный фокус

Главный визуальный якорь подраздела — **таблица предпросмотра 3×2**: она отвечает на вопрос,
ради которого пользователь сюда пришёл («как это будет выглядеть»). Радио-группа и два поля
разделителей — вспомогательные органы управления НАД ней; они настраивают якорь, а не конкурируют
с ним за внимание. Отсюда порядок блоков (радио → разделители → предпросмотр → «Сохранить»):
результат стоит последним и читается как следствие сделанных выше выборов.

### Расположение и структура DOM

Файл: `ui/src/features/settings/OrgSettings.svelte`. Новый блок — прямой сосед `.logo-section`,
идёт СРАЗУ ПОСЛЕ него внутри того же `<section class="settings-section">`:

**Важно:** радио-группа выбирает УМОЛЧАНИЕ организации (какой из трёх вариантов действует, если
место и все его предки — «Как у родителя»). Оба поля разделителей — НЕ привязаны к выбранному
радио-пункту: они всегда оба видимы и оба активны одновременно, независимо от того, какой вариант
сейчас выбран умолчанием. Причина: разделители — общие константы, которые применяются к ЛЮБОМУ
месту, разрешившемуся (через наследование или явное переопределение) в «Крайние» или «Два
последних», а не только к тому варианту, что выбран умолчанием организации. Именно поэтому они
вынесены в отдельный `.form-grid`-блок под радио-группой, а не вложены построчно под
соответствующие радио-пункты — вложение создало бы ложное впечатление, что поле «Два последних»
неактивно, пока выбрано «Крайние», а это неверно (D-11 требует показывать оба разделителя «в
действии» одновременно в предпросмотре независимо от выбранного радио).

### Проблема 1 — значимые пробелы в поле разделителя

**Контракт:** поле разделителя расширяет существующий `Input.svelte` новым необязательным
булевым пропом `mono` (по умолчанию `false`, не меняет поведение всех прочих 30+ использований
`Input` в проекте):

```ts
// Input.svelte — добавить в Props
mono?: boolean;
```
```svelte
<input class="input" class:invalid class:mono ... />
```
```scss
.input.mono {
  font-family: var(--tr-font-mono);
}
```

**Почему моноширинный шрифт one, но не единственная мера:** моноширинный шрифт делает пробел
визуально таким же по ширине символом, как любой другой — в проекциональном шрифте пробел на
краю поля «сливается» с padding'ом поля и незаметен; в моноширинном он остаётся считываемой
ячейкой сетки. Этого недостаточно самого по себе (край поля всё равно обрезает восприятие
крайнего пробела визуально) — поэтому под полем добавляется **вторая, независимая мера**: строка
`.field-hint.tr-mono`, показывающая ТЕКУЩЕЕ значение разделителя в кавычках-«ёлочках» с каждым
пробелом (U+0020), замещённым на видимый символ середины строки «·» (U+00B7) **только в этом
readout**, не в самом инпуте:

```ts
function monoReadout(v: string): string {
  return v.replace(/ /g, '·');
}
```

Пример: значение ` // ` (пробел, слэш, слэш, пробел) отображается в подсказке как `«·//·»`.
Значение `, ` (запятая, пробел) — как `«,·»`. Эта строка read-only, не интерактивна, не требует
отдельной ARIA-разметки — реальное значение поля остаётся доступным screen reader'ам через сам
`<input>` (посимвольное озвучивание значения, включая пробелы, — штатное поведение браузера/AT).

Живой предпросмотр (сетка 3×2, ниже) — **третья**, финальная мера: она физически показывает
результат применения текущего значения разделителя к двум образцам, так что пользователь видит
итог, даже если не обратил внимания на readout. Три меры (моно-шрифт + readout-в-кавычках +
живой предпросмотр) взаимно избыточны намеренно — каждая закрывает слепую зону предыдущей
(шрифт — восприятие ширины; readout — точную границу значения; предпросмотр — конечный
результат), а не дублируют друг друга без причины.

**Валидация (D-10):** пустая строка (`value.length === 0`) отклоняется с ошибкой «Разделитель не
может быть пустым — введите хотя бы один символ.» Значение из ОДНИХ пробелов (например, `"   "`)
— ДОПУСТИМО, ошибки не показывает. Клиентская проверка — `!value.length`, НЕ `!value.trim().length`
(эта разница критична и должна быть явно закрыта юнит-тестом на фронте, если таковые в проекте
для этого компонента заводятся; на бэкенде — уже отражено в RESEARCH.md).

### Проблема 2 — поле разделителя варианта «Последнее»

У «Последнее» разделителя нет вообще — ни как отдельного поля, ни как строки-заглушки рядом с
радио-пунктом «Последнее». Радио-строка «Последнее» ничем визуально не отличается от двух других
(тот же `.path-radio-row`, без дополнительного текста после неё) — потому что поля разделителей
структурно не привязаны к радио-строкам (см. «Важно» выше), а «Последнее» просто не участвует в
блоке `.path-sep-fields` (там ровно 2 поля, не 3). В таблице предпросмотра колонка «Последнее»
показывает единственный сегмент без какого-либо разделителя — визуально это очевидно
(в примере «1-05» / «помещение 3»), дополнительных пояснений в UI не требуется.

### Проблема 3 — раскладка сетки предпросмотра 3×2 на узких экранах

**Контракт:** предпросмотр — семантическая HTML `<table>` (4 столбца: подпись образца + 3
варианта; 2 строки данных), обёрнутая в `<div class="path-preview-wrap">`:

```scss
.path-preview-wrap {
  overflow-x: auto; // единственный адаптивный механизм — горизонтальный скролл, без реструктуризации DOM
  -webkit-overflow-scrolling: touch;
}

.path-preview {
  width: 100%;
  min-width: 480px; // варианты + образцы не должны схлопываться нечитаемо теснее этого
  border-collapse: collapse;

  th, td {
    padding: var(--tr-space-xs) var(--tr-space-sm);
    border-bottom: 1px solid var(--tr-border);
    text-align: left;
    white-space: nowrap;
  }

  thead th {
    font: var(--tr-text-label);
    color: var(--tr-text-secondary);
  }

  tbody th {
    font: var(--tr-text-body);
    color: var(--tr-text-secondary);
    font-weight: var(--tr-font-weight-medium);
  }
}
```

**Почему горизонтальный скролл, а не реструктуризация DOM в карточки:** `.settings-section` уже
ограничена `max-width: 640px`, а `.path-preview-wrap` живёт внутри неё — то есть таблица УЖЕ
тесная по умолчанию, независимо от ширины окна приложения. Решение — не заводить точку слома
(`$bp-sm`/`$bp-md` из `_breakpoints.scss`) с условной пересборкой разметки (стек карточек вместо
таблицы), а держать таблицу с гарантированным `min-width: 480px` и давать ей скроллиться
горизонтально внутри `.path-preview-wrap`, когда фактическая ширина `.settings-section` меньше
этого порога — что происходит уже на десктопе при `max-width: 640px` минус padding, и тем более
в узком LAN-браузере. Это **чисто CSS-решение без условной реактивности** (никаких
`$state`/`$derived` на брейкпоинт, никакого пересоздания DOM-узлов) — одинаково ведёт себя в
WKWebView и в WebView2/обычном браузере, не имеет risk-класса «рантайм-ошибка рун», о котором
предупреждает `platform_notes`. Родительский скролл-контейнер `.settings-content` (уже
`overflow: auto` по вертикали, см. `SettingsPage.svelte`) не конфликтует с горизонтальным
скроллом таблицы — оси независимы.

**Что требует живой проверки (per platform_notes):** сам расчёт 6 ячеек предпросмотра —
`$derived`-выражения, пересчитывающиеся на каждый keystroke в двух полях разделителей
(живой предпросмотр, D-11). Логика чистая (строковые операции, без побочных эффектов), но как
любая реактивная цепочка на рунах — её стоит визуально проверить в запущенном приложении (не
статическим гейтом), особенно межу переключением темы (light/dark) и при вводе разделителя из
одних пробелов.

### Формула для JS-предпросмотра (зеркалит Rust `shorten_place_path`, RESEARCH.md Pattern 3)

С разделителями по умолчанию (`sep_ends = ' // '`, `sep_last_two = ' / '`) предпросмотр обязан
показать РОВНО эти шесть значений (буквальный образец для code review / gsd-ui-checker):

| Образец | Крайние | Два последних | Последнее |
|---|---|---|---|
| «Здание А / 1 этаж / 1-05» | «Здание А // 1-05» | «1 этаж / 1-05» | «1-05» |
| «Территория А / Объект Х / помещение 3» | «Территория А // помещение 3» | «Объект Х / помещение 3» | «помещение 3» |

Полная таблица «вход → выход» для всех длин пути и трёх вариантов — см.
`.planning/phases/39.1-place-path-display/39.1-RESEARCH.md` § Pattern 3 (D-13..D-16), фронтовый
JS-расчёт для превью должен давать те же результаты построчно.

## Поверхность 2: `PlaceFormModal.svelte` — дропдаун «Вариант сокращения»

### Расположение в форме

Копирует паттерн существующего дропдауна «Тип» (тот же `variant="select"`, `flat={true}`,
`groups`/`getGroupId`/`getGroupName`/`isGroupSelected`/`onPickGroup` контракт). В отличие от
«Тип»/«Родительское место»/«Уровень»/«Складское место»/«Порядок» (которые видны ТОЛЬКО в режиме
`create`, см. комментарий в шапке файла про «create-time-only fields»), поле «Вариант сокращения»
видно и редактируемо в ОБОИХ режимах — `create` И `rename` — потому что, в отличие от
типа/родителя/уровня, оно мутируемо после создания места (D-12) через тот же вызов сохранения,
которым сегодня сохраняется только «Название» в режиме `rename`.

Порядок полей:
1. Название (существует, без изменений — единственное поле, видимое сегодня в `rename`)
2. **Вариант сокращения** (новое поле, видимое в ОБОИХ режимах)
3. *(только `create`)* Тип
4. *(только `create`)* Родительское место
5. *(только `create`, если Тип = «Этаж»)* Уровень
6. *(только `create`)* Складское место
7. *(только `create`)* Порядок

```svelte
<div class="form-field">
  <label class="form-label" for="pf-path-variant">Вариант сокращения</label>
  <Dropdown
    id="pf-path-variant"
    variant="select"
    flat={true}
    value={pathVariantLabel}
    placeholder="Как у родителя"
    searchable={false}
    groups={PATH_VARIANT_OPTIONS}
    getGroupId={(o) => o.value}
    getGroupName={(o) => o.label}
    getGroupCount={() => 0}
    isGroupExpandable={() => false}
    isGroupSelected={(o) => o.value === pathVariant}
    onExpandGroup={() => []}
    getMemberId={(o) => o.value}
    getMemberName={(o) => o.label}
    onSearch={() => {}}
    onPickGroup={pickPathVariant}
    onPickMember={() => {}}
    disabled={saving}
    loading={false}
  />
</div>
```

```ts
const PATH_VARIANT_OPTIONS = [
  { value: null, label: 'Как у родителя' },
  { value: 'ends', label: 'Крайние' },
  { value: 'last_two', label: 'Два последних' },
  { value: 'last', label: 'Последнее' },
];
```

**Жёсткий запрет (D-05):** НИКАКОГО `field-hint` под этим дропдауном. НИКАКОГО динамического
суффикса к пункту «Как у родителя» (не «Как у родителя (Крайние)», не «Как у родителя — умолчание
организации»). Пункт называется буквально «Как у родителя» во всех случаях — включая места
верхнего уровня, для которых родителя как узла нет, но которые (по D-06) наследуют умолчание
организации молча, без индикации этого в самой форме. Это единственное место во всей фазе, где
явный продуктовый запрет важнее интуитивной «помощи пользователю» — не компенсировать его
собственной инициативой (иконкой info, tooltip и т.п.) — это прямо противоречит решению владельца.

**searchable={false}:** список из 4 пунктов не нуждается в поле поиска внутри панели дропдауна
(как у «Тип» с 6 пунктами) — уменьшает визуальный шум для короткого списка (тот же паттерн,
что рекомендован для «коротких, полностью видимых списков» в самом `Dropdown.svelte` (см.
JSDoc `searchable` пропа: «short, fully-visible option lists»).

**Сохранение:** значение поля входит в тот же вызов `handleSubmit()`, что и «Название» (и, в
режиме `create`, «Тип»/«Родитель»/т.д.) — одна кнопка «Создать»/«Сохранить», без отдельного
действия сохранения для этого поля (в противоположность подразделу «Формат пути» в Настройках,
где действует отдельная кнопка «Сохранить формат пути» — там отдельная кнопка оправдана тем, что
это отдельный backend-эндпоинт с иной семантикой прав; здесь, по D-12, семантика прав ровно та
же, что у «Название», и одна кнопка — правильный UI-контракт независимо от того, как планировщик
решит разбить это на 1 или 2 RPC-вызова на бэкенде).

### Права доступа

Дропдаун виден и активен у ЛЮБОГО пользователя, которому доступна форма редактирования места
вообще (тот же гейт, что у поля «Название» — `Action::MutatePlaces`, НЕ `Action::ManageSettings`).
Нет отдельного readonly-состояния «видно, но не редактируется» — если модал вообще открыт для
данного пользователя, поле активно.

## Состояния (states matrix)

| Состояние | Поверхность 1 (Настройки) | Поверхность 2 (PlaceFormModal) |
|---|---|---|
| Загрузка | Радио/поля/предпросмотр показывают последние сохранённые значения сразу после `onMount` fetch (тот же `loadOrg()`-паттерн, без отдельного skeleton — форма и так short) | Дропдаун показывает текущее значение переопределения места (или «Как у родителя», если `NULL`) сразу при открытии модала (данные уже есть в `place`, переданном пропом) |
| Пустой разделитель (D-10) | `Input` получает `invalid={true}` (красное кольцо, существующий паттерн Input.svelte), `.field-error` под полем: «Разделитель не может быть пустым — введите хотя бы один символ.», кнопка «Сохранить формат пути» не блокируется превентивно (клик всё равно можно нажать — ошибка всплывает под конкретным полем, как и остальные поля формы в проекте) | Не применимо — дропдаун не текстовое поле, невалидных состояний нет (закрытый список из 4 значений) |
| Ошибка сервера | `pushToast('error', msg)` — тот же паттерн, что `saveOrg()`/`uploadLogo()` | `serverErr` + `.server-error` блок — тот же паттерн, что уже есть в `PlaceFormModal.svelte` (`mapServerError`) |
| Успех | `pushToast('success', 'Формат пути сохранён')` | Тост не нужен отдельно — общий тост «Место создано»/«Место переименовано» уже покрывает и это поле, так как оно часть того же submit |
| Disabled (во время сохранения) | Оба поля разделителя + радио-группа получают `disabled` на время `savingPath` | Дропдаун получает `disabled={saving}` — тот же флаг, что уже управляет остальными полями формы |
