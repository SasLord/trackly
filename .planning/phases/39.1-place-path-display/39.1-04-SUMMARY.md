# Phase 39.1 Plan 04: place_path_short в списке картриджей Summary

**`SqliteCartridgeRepository::list()` now LEFT JOINs `place_effective_variant` and computes `place_path_short` via the shared `shorten_place_path` formula, mirroring plan 03's device treatment exactly — `get`/`search_fts` stay on the full path.**

## Performance

- **Duration:** ~20 min
- **Completed:** 2026-08-28
- **Tasks:** 1
- **Files modified:** 3 (1 created, 3 modified)

## Accomplishments
- `CartridgeRow` (trackly-core) and `CartridgeDto` (trackly-app) both gained `place_path_short: Option<String>`, placed right after `full_path` in both structs, with identical null-when-no-place semantics.
- `cartridges_sqlite.rs::SELECT_CARTRIDGES` grew a `LEFT JOIN place_effective_variant pev ON pev.place_id = c.place_id` alongside the pre-existing `place_full_paths` join, adding `pev.effective_variant AS place_variant` as column index 18. The shared `map_row` function was left untouched (always sets `place_path_short: None`), so `get()` and `search_fts()` — both of which also format `SELECT_CARTRIDGES` into their own SQL — are unaffected by construction.
- A new `map_row_with_short_path(sep_ends, sep_last_two)` wraps `map_row`, reads column 18, and calls `shorten_place_path` when both `full_path` and `effective_variant` are present. `list()` is the only caller.
- A new `read_path_display_separators(conn)` helper reads `place_path_sep_ends`/`place_path_sep_last_two` from `app_settings` once per `list()` call, mirroring the guarded-read shape of this same file's `low_stock` method (and `devices_sqlite.rs`'s identically-named helper from plan 03), with V039-seeded defaults `" // "`/`" / "` as a defensive fallback.
- New integration test file `crates/trackly-infra/tests/cartridges_place_path_short.rs` with 2 tests: a 3-segment place proving `place_path_short = "Здание А // 1-05"` (org default variant `ends`, default separator `' // '`) while `full_path` stays untouched, and a cartridge with no place proving `place_path_short: None`.

## Decisions Made
- Extended the single shared `SELECT_CARTRIDGES` constant (rather than duplicating it) since `get()`/`search_fts()` also build their SQL from it — the extra column is harmless there because those call sites keep using bare `map_row`, which never reads index 18. This is a cheaper, lower-risk change than introducing a second SELECT constant, and matches the plan's explicit scope (only `list()` computes `place_path_short`).
