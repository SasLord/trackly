## Accomplishments

- `PlaceRow.path_variant_override: Option<PathDisplayVariant>` (domain) и `PlaceDto.path_variant_override: Option<String>` (wire) — round-trip'ится через `places_set_path_variant` → `places_get`, показывает форме текущее сырое значение (не разрешённый эффективный вариант).
- `PlaceRepository::set_path_variant` (порт + `SqlitePlaceRepository` impl) — CAS-UPDATE, буквальный близнец `rename`: тот же `WHERE id = ?3 AND version = ?4 AND deleted_at_utc IS NULL`, та же `resolve_cas_failure` при `affected == 0`.
- `PlaceService::set_path_variant` — `authorize(&Action::MutatePlaces)` первой строкой (D-12, НЕ `ManageSettings`), валидация токена через `PathDisplayVariant::from_str` (пропускается при `None` — сброс на «Как у родителя»), audit-запись `action: "set_path_variant"` внутри единственного writer-closure, мирроринг `rename`.

- Место верхнего уровня (`parent_id: None`) принимает мутацию без специальной обработки (D-06) — покрыто тестом.
- `PlaceContentRow`/`PlaceContentDto` выросли на `place_path_short: String`. `list_subtree_contents_impl` во всех трёх UNION-ветках (device/printer/cartridge) добавил `LEFT JOIN place_effective_variant pev` и вычисляет `place_path_short` через ту же формулу `shorten_place_path`, что и `devices_sqlite.rs`/`cartridges_sqlite.rs` (отдельная приватная копия `read_path_display_separators`, читающая `app_settings` один раз на вызов — установленная в фазе конвенция «каждый read-репозиторий держит свою копию»).

## Decisions Made

- **HTTP payload casing:** `SetPathVariantPayload` uses `#[serde(rename_all = "camelCase")]` like every other flat Payload struct in this file (`RenamePayload`, `MovePayload`) — the JSON body key is `pathVariantOverride`. The plan's Task 2 `<action>` text showed a snake_case example body (`{"id": 1, "path_variant_override": "ends", "version": 1}`); this was treated as illustrative prose, not literal code, since the file's own established convention (already demonstrated literally by `MovePayload`'s `newParentId` in the pre-existing Case 45 test) takes precedence for consistency. Case 50's test body uses `pathVariantOverride` accordingly.
- Field-name remapping (like Plan 02's `path_variant` → `variant` remap for the org-settings DTO) was NOT applied here — `PathDisplayVariant::from_str`'s `AppError::Validation { field: "path_variant", .. }` surfaces unchanged, since the DTO field is also named `path_variant_override` (no naming mismatch to bridge, unlike Plan 02's `variant`-named DTO field).
- Repo-level test coverage for the new `set_path_variant` CAS mutation and `place_path_short` computation was written into existing service-level integration test surfaces (`place_service.rs`'s own `mod set_path_variant` unit-test block, and `places_contents.rs`) rather than a new `trackly-infra` test file — this matches the phase's own precedent (Plan 03's `cargo test -p trackly-infra devices_sqlite` verify command also resolves 0 direct matches; real coverage lives in `devices_place_path_short.rs`/service-layer tests instead).
