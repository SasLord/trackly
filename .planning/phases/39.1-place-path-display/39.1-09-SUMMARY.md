# Phase 39.1 Plan 09: UI-половина PLC-08 — дропдаун «Вариант сокращения» в PlaceFormModal Summary

**Дропдаун «Вариант сокращения» доступен в create И rename режимах формы Места, сохраняется вторым RPC-вызовом `places_set_path_variant` внутри одного `handleSubmit`, без утечки унаследованного значения в UI (D-05).**

## Performance

- **Duration:** ~20 мин
- **Completed:** 2026-08-28
- **Tasks:** 1/1
- **Files modified:** 1

## Accomplishments

- `PATH_VARIANT_OPTIONS` (4 пункта, первый — `{ value: null, label: 'Как у родителя' }`) + `pathVariant: $state<string | null>` — инициализируется из `place?.path_variant_override ?? null` в режиме rename, `null` в режиме create.
- Новый `<Dropdown>` «Вариант сокращения» рендерится СРАЗУ ПОСЛЕ поля «Название», ВНЕ блока `{#if !isRename}` — единственное поле формы, видимое и редактируемое в обоих режимах (в отличие от Типа/Родителя/Уровня/Складского места/Порядка, которые остаются create-time-only).
- `pickPathVariant` мирроринг `pickKind`; сам `<Dropdown>` буквально копирует контракт «Тип» (`variant="select" flat={true} groups getGroupId getGroupName getGroupCount isGroupExpandable isGroupSelected onExpandGroup getMemberId getMemberName onSearch onPickGroup onPickMember`), с `searchable={false}` (короткий список из 4 пунктов).
- `handleSubmit`: после успешного `places_rename`/`places_create` (переменная `saved`) добавлен безусловный второй вызов `apiCall('places_set_path_variant', { id: saved.id, pathVariantOverride: pathVariant, version: saved.version })` — использует `version` из результата ПЕРВОГО вызова, не исходный `place.version`. Оба вызова в одном `try/catch`, ошибка любого попадает в тот же `mapServerError`/`.server-error` путь.
- Заголовочный комментарий файла обновлён: устаревшее утверждение «`places_rename` мутирует ТОЛЬКО `name`» дополнено абзацем про новое исключение (вариант сокращения, план 07/09, второй RPC).
- D-05 соблюдён: рядом с новым `<Dropdown>` нет `field-hint`/tooltip/подсказки — grep подтверждает, что все существующие `.field-hint` в файле относятся к уровню/складу/порядку (create-only поля), не к новому блоку.

## Decisions Made

- `getGroupId`/`getMemberId` для нового дропдауна возвращают `o.value ?? '__inherit__'` — `Dropdown.svelte` типизирует id-геттеры как `(g: TGroup) => string | number`, а значение опции «Как у родителя» само по себе `null`; сентинел используется исключительно как ключ идентификации пункта списка, вся реальная логика выбора (`isGroupSelected`, `pickPathVariant`) сравнивает/устанавливает сырое `o.value` (включая `null`) — поведенческого расхождения с UI-SPEC нет.
- `pushToast('success', ...)` перенесён с места сразу после первого RPC на место после ВТОРОГО RPC (единственный тост на весь submit, как и раньше по количеству, но теперь после обоих запросов) — иначе пользователь увидел бы «Место создано»/«Место переименовано» раньше, чем реально сохранён вариант сокращения, а при ошибке второго RPC тост об успехе оказался бы ложным.
- Arg-ключ второго RPC — `pathVariantOverride` (camelCase), не `path_variant_override` — согласно прецеденту и явной пометке из 39.1-07-SUMMARY.md (bindings.ts генерирует `placesSetPathVariant(id, pathVariantOverride, version)`, HTTP `SetPathVariantPayload` тоже `rename_all = "camelCase"`).
