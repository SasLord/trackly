### Locked Decisions
- **D-00** Типы: АРМ (container) — любые устройства и принтеры; «Системный блок» (substitute) — якорь + члены; «Разбор» (teardown) — якорь-донор, внутри создаются детали. Якорь из группы не выводится (D-14 фазы 41.1).
- **D-01** «Вывести из группы» — любому прямому участнику любой группы, кроме якоря; роли MutateGroups (admin, manager).
- **D-02** Подпись «Вывести из группы» везде; «Вывести из состава» исчезает из UI; словарные гейты и golden-фикстура обновляются вместе с подписью.
- **D-03** Секция меню «Вывести из группы» → «Переместить в группу» сразу после «Печать документа приёма» (или «Редактировать»), за разделителем; порядок `buildMenuSections` и golden обновить.
- **D-04** «Переместить в группу» = `AddToGroupModal` в режиме переноса; текущая группа и «Разбор» не предлагаются; перенос — ОДНА серверная операция (вывод+ввод в одной транзакции, одна запись аудита; на неё опирается 41.10); пункт есть у участника (не якоря) и у вложенной группы.
- **D-05** Таблица состава: двойной клик = просмотр как в «Устройствах», правый клик/кебаб = тот же `DeviceRowMenu`/`buildMenuSections`; после любого действия состав, дерево, счётчики «Мест» обновляются.
- **D-06/D-07** Правый клик по узлу дерева = кебаб узла; вложенной группе — «Вывести из группы», «Переместить в группу» (смена родителя с проверкой цикла и запретом «Разбора»), «Списать» по D-21. `GroupMoveModal` (перенос на МЕСТО) не меняется.
- **D-08** «Разбор» — только донор: сервер отказывает в `addDevices` для teardown, кроме детали с `origin_group_id` = этот разбор (D-15); закрывает ветку записи происхождения произвольному устройству.
- **D-09** Группу teardown нельзя вложить в другую (сервер отказывает в `set_parent` / переносе).
- **D-10..D-15** Призрак = устройство с `origin_group_id` = разбор, не прямой член. Вычисляется, не хранится. В конце состава, вне счётчиков, только просмотр + «Вернуть в разбор»; разбор с любой деталью (живой/призраком) не удаляется (текст отказа называет причину); призрак остаётся после списания/удаления детали; возврат двумя путями (меню призрака; строка добавления разбора ищет только детали этого разбора). Удалённую деталь вернуть нельзя.
- **D-16** Попытка ввести занятое устройство ИЛИ ГРУППУ → попап «Отменить»/«Переместить» (danger). Сервер без явного флага отказывает и для групп (сейчас `setParent` молча забирает). Отказ машинно различим.
- **D-17** Teardown нигде не предлагается как цель (UI прячет, сервер отказывает).
- **D-18** `GroupAddDevicesModal`: один попап «N устройств уже в других группах», «Переместить» — всё или ничего, одной операцией.
- **D-19..D-22** «Списать»: у «На списание» всегда с подтверждением; участник — выбор «оставить списанным»/«вывести»; у группы — списывается якорь (substitute: группа расформировывается, члены освобождаются; teardown: запись остаётся); одна серверная операция в обоих транспортах + аудит + INV-7 + WS.
- **D-23/D-24** Общий модификатор неактивной строки в `TableRow` (токен, контраст, текстовая пометка); применяется к призракам и списанным участникам.
- **D-25** Вложенная группа видна и по месту вложения, и полноценным узлом своего типа с подписью «в {родитель}»; ключи узлов различаются; учитывается в счётчике типа.

## Summary

Фаза целиком ложится на существующую модель: **миграций не нужно** (`devices.origin_group_id` и индекс `idx_devices_origin` есть с V048; FK `ON DELETE SET NULL` на `groups`; текущая версия схемы `PRAGMA user_version = 56`). Призраки вычисляются запросом по `devices.origin_group_id`, счётчики дерева/«Мест» уже считают только членов (`group_devices`-JOIN), поэтому «вне счётчиков» достигается тем, что запрос призраков НЕ трогает существующие счётчики. `group_counts_by_type` и `count_groups_of_type` уже считают все группы типа, включая вложенные, так что D-25 про счётчик — только UI-ключи и узел-двойник.

Главная серверная работа — четыре правила в `crates/trackly-app/src/services/group_service.rs` (`add_devices`, `set_parent`, `delete_group`, новая операция переноса) плюс операция «Списать». Главная скрытая ловушка: **«Создать деталь» сегодня работает как «создать устройство с `origin_group_id = NULL`, затем `addDevices` в teardown, где сервер и пишет происхождение»**. D-08 запрещает ровно эту ветку, поэтому без изменения создания деталь перестанет добавляться в разбор (Pitfall 1).

Главная клиентская работа — три компонента: `GroupContentsTable.svelte` (714 строк; уходит локальный `ActionMenu`, приходит `DeviceRowMenu`, призраки, строка возврата), `GroupTree.svelte`/`GroupTreeNode.svelte` (контекстное меню, двойники по D-25) и `AddToGroupModal.svelte` (режим `move` + шаг «уже в группе»). Новый машинный отказ «уже в группе» требует нового варианта `AppError` (Pattern 2), потому что `Conflict{reason: String}` и `Validation{field,message}` не несут структурированных `group_id`/`group_name`.

**Primary recommendation:** Сделать пять серверных изменений в одном сервисе (`GroupService`) с общим приватным примитивом «ввод одного устройства в группу в транзакции» (вынести из тела `add_devices`), добавить две новые команды (`groups_move_devices`, `groups_write_off`) плюс флаг переноса в `groups_set_parent`, и пустить весь UI через уже существующие `DeviceRowMenu`/`AddToGroupModal`/`Modal`/`TableRow`.

### Pattern 1: единый примитив «ввод одного устройства» и операция переноса
**What:** тело цикла `add_devices` (проверки «удалено / уже в группе / Списано / На списание», `add_device_in_tx`, запись происхождения, `apply_group_place_to_device_in_tx`) вынести в приватную функцию `add_one_in_tx(tx, deps, group, target_behavior, device, mode, user_id, now)`, где `mode = Plain | MoveOccupied`. `add_devices` вызывает с `Plain`; `move_devices` — с `MoveOccupied`; D-18 (массовое с переносом) — тот же примитив.
**Перенос устройства (рекомендация):** новая `GroupService::move_devices(caller, target_group_id, device_ids) -> GroupMoveDevicesResultDto { moved, added, changed_place_ids }`. Внутри ОДНОЙ транзакции: для каждого устройства — охрана якоря (`anchor_group_of_device_in_tx` → `Validation` как в `remove_devices`), снять членство `remove_device_in_tx` (НЕ `release_device_in_tx`: тот пишет собственный аудит `custom:group_member_released`, а D-04 требует ОДНУ запись), затем ввод с теми же правилами, что `add_devices` (teardown-цель по D-08, «Списано», «На списание»), затем ровно одна запись `audit_log` (`entity_type:"group"`, `action:"move_devices"`, payload `{device_ids, from: {device_id→group_id}, to_group_id}`) и одно `broadcast_entities("move_devices", place_ids, device_ids, [target + все исходные группы])`. Для D-18 «все или ничего» достаточно: ошибка → ранний `return Err` → транзакция не коммитится (так уже устроен `add_devices`: «занятое… отменяет весь пакет»).
**Единый источник (разрешённый D-15 возврат):** в teardown-цели принимается только деталь с `origin_group_id == target.id`; иначе `Validation{field:"device_ids", message: «В разбор нельзя добавить существующее устройство: детали появляются только через «Создать деталь».»}` (текст из UI-SPEC §15.3).
**Source:** `group_service.rs:943-1083` (`add_devices`), `1086-1159` (`remove_devices`) [VERIFIED: чтение кода].

### Pattern 2: машинно различимый отказ «уже в группе»
**What:** добавить вариант
`AppError::AlreadyInGroup { items: Vec<OccupiedItem> }` где `OccupiedItem { kind: "device"|"group", id: i64, name: String, group_id: i64, group_name: String }`. `code()` → `"ALREADY_IN_GROUP"`, `details_value()` → `{ "items": [...] }`, `error_axum.rs` → 409. Бросать:
- `add_devices` без флага (вместо текущего `device_ids_error("…Сначала выведите его из состава.")`);
- `set_parent` без флага `replace_parent`, когда у вкладываемой группы уже есть родитель, отличный от целевого (сегодня `set_parent` молча меняет родителя — `group_service.rs:1168-1257`, проверки родителя нет вообще).
Собрать ВСЕ занятые устройства пакета в одном отказе (для D-18: «N устройств уже в других группах» со списком) — а не падать на первом.
**Клиент:** `parseAppError(e).code === 'ALREADY_IN_GROUP'` → читать `details.items` (тип `AppError.details?: Record<string, unknown>` уже есть в `ui/src/lib/api/errors.ts`). Список «устройство → группа» не требует доп. запросов (UI-SPEC §10.3).
**Not-vacuous:** добавить тест формы `serialize_shape_*` в `error.rs` (там уже есть паттерн тестов `code()`/сериализации) и тест на `add_devices` с занятым устройством, проверяющий `code` и `details.items[0].group_name`.
**Source:** `crates/trackly-core/src/error.rs:34-125, 300-340`; `error_axum.rs:34-46` [VERIFIED].

### Pattern 3: призраки в `groups.composition`
**What:** в `GroupCompositionDto` добавить `ghosts: Vec<GroupGhostDeviceDto>` (пустой для не-teardown). Запрос в `SqliteGroupRepository` (рядом с `member_devices`, `groups_sqlite.rs:813`):

```sql
SELECT d.id, COALESCE(dt.name,''), d.name, d.inventory_number, d.serial_number,
       d.place_id, pfp.full_path, ds.name, ds.code,
       (d.deleted_at_utc IS NOT NULL) AS is_deleted,
       cg.id, cg.name
FROM devices d
LEFT JOIN device_types dt ON dt.id = d.type_id
LEFT JOIN device_statuses ds ON ds.id = d.status_id
LEFT JOIN place_full_paths pfp ON pfp.place_id = d.place_id
LEFT JOIN group_devices gd ON gd.device_id = d.id
LEFT JOIN groups cg ON cg.id = gd.group_id
WHERE d.origin_group_id = ?1
  AND NOT EXISTS (SELECT 1 FROM group_devices m WHERE m.device_id = d.id AND m.group_id = ?1)
ORDER BY is_deleted, d.name, d.id
```
Один запрос, без N+1, включает soft-deleted (D-14). Индекс `idx_devices_origin` (partial `WHERE origin_group_id IS NOT NULL`) покрывает фильтр [VERIFIED: V048]. Короткий путь места — тем же `compute_place_path_short_with_conn`, что у членов (`composition`, `group_service.rs:329`).
**Дата вывода:** отдельной колонки нет; есть только `audit_log` `custom:group_member_released` с `{group_id}` в payload. UI-SPEC допускает «если даты нет — по имени» — рекомендация: НЕ делать подзапрос к аудиту, сортировать по имени (простота, нет риска регресса по скорости).
**Счётчики:** `member_devices`, `direct_device_counts`, `tree_counts` и `places_group_members` строятся от `group_devices` — призраки в них не попадают, трогать их не надо [VERIFIED: groups_sqlite.rs:786-873].
**Не забыть:** `GroupGhostDeviceDto` — новый тип для specta (`Type`), он попадёт в `bindings.ts` через `export_bindings`.

### Pattern 5: `DeviceRowMenu` внутри таблицы состава (GRW-01)
`DeviceRowMenu` принимает `device: DeviceDto | null` ИЛИ `deviceId`; при `device === null` меню подтягивает устройство через `prepare()` (`devices.get`) — но **только на путях `openAt`/`openFromElement`/`openView`**. Кебаб `trigger="button"` открывается самим `ActionMenu`, МИМО `prepare()` (см. комментарий в `onMount`), и с `device === null` пункты посчитаются по пустому `dev`. UI-SPEC §7.1 прямо требует, чтобы кебаб прошёл через `prepare()`. Рекомендация: в `GroupContentsTable` использовать `trigger="none"` + собственную кнопку-кебаб, вызывающую `menuRef.openFromElement(button)`; правый клик — `openAt(e.clientX, e.clientY)` с `preventDefault()`; охрана `isRowOverlayEvent`/`isOwnKeyEvent` первым оператором обработчиков строки (правило [F] golden-гейта; модалки `DeviceRowMenu` рендерятся внутри `<td>`).
`DeviceListRow.svelte` — эталон обработчиков (`oncontextmenu`, `ondblclick`, `onkeydown` на первой ячейке) — скопировать структуру.
**Единый `onChanged`:** после любого действия — `loadComposition()` + `onChanged?.()` страницы + `notifyPlaceContentChanged` там, где сервер вернул `changed_place_ids`.

### Pattern 6: меню узла дерева и правый клик (GRW-03)
`GroupTreeNode.svelte` строит два `ActionMenu` (тип — стр. 199, группа — 220) c `variant="ghost-sm"`; `ActionMenu` умеет `openAt(x, y)` (строка 77) и всегда портальный (`use:portal`). Добавить `bind:this` на оба меню, `oncontextmenu` на `treeitem` (`preventDefault` только если меню непусто — иначе родное меню, R-02 фазы 41.1) и `ContextMenu`/`Shift+F10` в `handleRowKeydown`. Разделитель — элемент `<hr role="separator">`, прежний `border-top` у `.menu-danger` снять (иначе две линии, UI-SPEC §8.1). Новые пункты узла: «Вывести из группы» (сейчас `onRemoveFromParent` → `GroupsPage.removeFromParent`), «Переместить в группу», «Списать» (по якорю — нужен `anchor_status_code` или чтение якоря; см. Open Question 2).

### Pattern 7: общий модификатор неактивной строки (D-23/D-24)
`TableRow.svelte` (183 строки, нормальный режим — `<tr class="tr-row …" class:selected …>`): добавить проп `inactive?: boolean` (по умолчанию `false`) и `class:inactive`. CSS по UI-SPEC §5.2 в форме `.tr-row.inactive :global(> td:not(.tr-cell-solid)) { opacity: var(--tr-row-inactive-opacity); color: var(--tr-text-primary) }` — `.tr-row` остаётся в своей области видимости; **не `:has()`** (Svelte вырезает селектор на внутренности дочернего компонента, см. memory «:global внутри :has»). Токен `--tr-row-inactive-opacity: 0.65` в `:root` `_tokens.scss` (проверено расчётом в UI-SPEC §5.3: 0.6 краснит светлую тему). Гейты: `check-tokens.mjs` (нет литерала `opacity: 0.65` в `<style>`), `check-contrast.mjs` правило R4 с мутантом 0.6 в `--selftest`. Ячейки статуса, пометки-причины и действий — класс `tr-cell-solid`.

### Pattern 8: вложенная группа узлом своего типа (D-25)
`GroupTree.svelte` `treeData` (стр. 123-180): вложенная группа сейчас идёт только в `nestedByParent`. Добавить: каждая вложенная группа (`parent_group_id !== null && byId.has(...)`) дополнительно попадает в `rootsByType` как «двойник» с ключом `in-type-{id}` (потомки — `in-type-{aliasRootId}-group-{childId}`), поля `TreeItem`: `aliasOf: parentName`. `itemByKey`/`parentOf` должны получить ОБА ключа; глубокая ссылка `#/groups?id=` и «Открыть группу» выбирают ОСНОВНОЙ узел (`groupKey(id)`), поэтому `focusNode`/`expandPathTo` не меняются. Счётчик типа — уже серверный `group_count` и уже включает вложенные [VERIFIED: `count_groups_of_type`]; поиск по дереву считает **группы**, а не узлы (`countHits` в `searchResult` — не считать двойника второй раз). Подпись «в {родитель}»: имя родителя берётся клиентски из `byId` — серверное поле не нужно.

### Pattern 9: «Списать» (D-19..D-22)
Две команды (рекомендация), обе — `MutateGroups` + права на правку устройства:
1. `devices_write_off(device_id, version, group_action: "keep" | "release")` или — если планировщик хочет держать мутации групп в одном сервисе — `groups_write_off_device`. Одна транзакция: проверки (статус == `на_списание`, иначе «Списать можно только устройство со статусом «На списание».»; **нет открытой ремонтной заявки** — тот же отказ, что в `DeviceService::update`, `open_repair_request_id`, фаза 41.4 D-21), `devices_repo.set_status_in_tx(&tx, id, written_off_status_id, now)` (примитив уже используется в `create_group`: поиск `SELECT id FROM device_statuses WHERE code = ?1`), при `release` — вывод через `remove_device_in_tx` с охраной якоря; ОДНА запись аудита; `broadcast_entities`.
2. `groups_write_off(group_id, version)` — списывает якорь группы: `substitute` → в той же транзакции расформировать (общая с `delete_group` функция `delete_group_in_tx`+аудит; вынести, не копировать), `teardown` → только статус якоря; у `container` (нет якоря) — `Validation`. Ответ — число освобождённых и имена для Toast.
**Решения по `code`, не по подписи** (D-02 фазы 41.1): `STATUS_CODE_WRITTEN_OFF`/`STATUS_CODE_TO_WRITE_OFF` уже константы в `group_service.rs:62-63`; есть и общие `DEVICE_STATUS_CODE_*` в `trackly-core/src/domain/repairs.rs:14-18` — использовать их при выносе.
**Версия устройства / CAS:** `devices.update` — оптимистичная по `version`; `write_off` должен принимать `version` устройства (или группу — `version` группы) и возвращать `OptimisticLockMismatch`, как остальные мутации.
**Обратите внимание:** статус «Списано» НЕ входит в `is_repair_exempt_status_code` (там только «на_ремонте», «в_ремонте», «на_списание»). Списанный участник, оставленный в группе с местом, подпадает под обычный замок места («Место задаётся группой», `device_service.rs:~1500`). Это не ошибка, но тест на D-20 «оставить в группе» должен это учесть.

### Anti-Patterns to Avoid
- **Два вызова клиента вместо одной операции** (`removeDevices` + `addDevices`) — запрещено D-04; сломает 41.10.
- **Новая проверка в `set_parent_in_tx` репозитория для D-09/D-16** — этим же методом пользуется план актов (`group_act_plan.rs:994, 1008, 1234, 1505`), см. Pitfall 3.
- **Заводить `release_device_in_tx` для переноса** — пишет вторую запись аудита и содержит охрану якоря, зажатую стражами `s11_*` (см. комментарий «между двумя публичными release-функциями» в `group_membership.rs`); писать перенос на примитивах репозитория.
- **Разбор текста отказа на клиенте** для «уже в группе» — только `code` + `details`.
- **`opacity` на `<tr>`** — погасит кебаб и бейдж (UI-SPEC R-02).
- **Фильтр `deleted_at_utc IS NULL` в запросе призраков и в счётчике D-13.**

## Common Pitfalls

### Pitfall 1: «Создать деталь» ломается от D-08
**What goes wrong:** `GroupContentsTable.handleDetailSaved` создаёт устройство через `DeviceFormModal` (`originGroup` — только отображение, в `DeviceFormBody` он показывает ссылку на происхождение), затем зовёт `groups.addDevices`. Сегодня сервер сам пишет `origin_group_id` при вводе в teardown. После D-08 такое устройство (`origin = NULL`) будет отклонено, и новая деталь перестанет попадать в разбор.
**How to avoid:** передавать `origin_group_id` в `devices.create`/`bulkCreate` (серверная валидация: группа существует и `behavior = teardown`; поле пишется ТОЛЬКО при создании, правке недоступно — D-33), после чего `addDevices` проходит по правилу «origin == target». Прямой `addDevices` существующего устройства с чужим/пустым origin отказывает. Проверить, что у `DeviceFormModal` в режиме правки поле origin не отправляется.
**Warning signs:** тест `anchor_*` в `groups_anchor.rs` (стр. 943-955, 1036, 1052-1081) сегодня проверяет, что `add_devices` в teardown ЗАПИСЫВАЕТ origin — эти ожидания надо переписать, не удалять (см. Validation).

### Pitfall 2: существующие тесты кладут устройства в teardown через `add_devices`
Файлы с `teardown`: `groups_anchor.rs`, `groups_membership.rs`, `groups_types_service.rs`, `role_endpoint_matrix.rs`, `devices_container_hide.rs`, а в `trackly-infra` — `groups_repo.rs`, `group_types_repo.rs`, `groups_migration.rs`. Тесты, вводящие в teardown устройство с пустым origin, станут красными по замыслу. Планировщик должен выделить задачу «починка существующих тестов» ПЕРЕД основной проверкой, иначе исполнитель увидит красный пакет и решит, что сломал не то.

### Pitfall 3: D-09 в репозитории ломает восстановление акта
`SqliteGroupRepository::set_parent_in_tx` вызывается из `group_act_plan.rs` (строки 994, 1008, 1234 — вывод в корень; **1505 — вложение `Some(parent_id)` при откате акта**). Если запретить вкладывание teardown на уровне репозитория, откат акта над УЖЕ вложенным в БД teardown (унаследованные данные, правило раньше не действовало) станет ошибкой. Проверку D-09 и D-16 держать в `GroupService::set_parent`, а в репозитории оставить как есть. Открытый вопрос — что делать с уже вложенными teardown в живых БД (Open Question 1).

### Pitfall 4: write-site гейты считают по именам
Память «Инвентарь гейта write-site: вердикты» и «Путь без теста невидим для аудита»: новые мутирующие маршруты регистрируются в нескольких таблицах по ИМЕНАМ. Полный список — в разделе «Регистрация новой команды» ниже. Сверять от репозитория (`rg "groups_" crates/trackly-app/src/http/groups.rs`), не от этого документа.

### Pitfall 5: `spa_fallback` и незарегистрированный `/api/v1/` маршрут
С фазы 41.7 незарегистрированный `/api/v1/*` отвечает 404 JSON (а не `index.html` 200), но это не отменяет: команда без маршрута ломает ровно LAN-режим. `tests/http_route_parity.rs` сверяет множества ТОЧНО по `collect_commands!` в `specta_export.rs` и `.route(...)` в `http/*.rs` — обе стороны + вердикты в таблице теста обновлять вместе.

### Pitfall 6: кебаб `DeviceRowMenu` мимо `prepare()` (см. Pattern 5)
Меню из кебаба без загруженного `DeviceDto` показывает пункты, посчитанные по `null`.

### Pitfall 7: Modal в `<td>` наследует `white-space: nowrap` и `text-align: right` колонки `.col-menu`
Память «Modal наследует стили ячейки таблицы». Все тела новых модалок (перенос, «уже в группе», «Списать») задают `white-space: normal; text-align: left` явно (UI-SPEC §7.3). Модалки `DeviceRowMenu` уже рендерятся внутри `<td>` — новые из этого же компонента этой ловушки не избегают.

### Pitfall 8: двойной клик по строке вложенной группы
`TableRow group` вешает `onclick={onToggleGroup}` на `<tr>`; двойной клик = два `click` = раскрыть и тут же свернуть. UI-SPEC §8.4: переключать только при `event.detail <= 1`, `dblclick` на строках групп не назначать.

### Pitfall 9: миграции
Фаза миграций не требует. Если планировщик всё же решит добавить (например, `devices.origin_released_at_utc` для даты вывода): последняя строка SQL обязана быть `PRAGMA user_version = 57;` (память «Миграция обязана ставить user_version»: без неё 10 красных в ci-full, точечные тесты слепы), перестройка таблиц с `DROP` родителя в транзакции refinery каскадно стирает детей (`FK OFF` внутри транзакции — no-op), а `build.rs` пересобирает крейт при новом `.sql` (до 2026-11-17 не пересобирал). **Рекомендация: миграций нет** (дата вывода не обязательна).

### Pitfall 10: теги и версии
`GroupDto.version` — CAS; `groups.search` возвращает кандидата БЕЗ `version`, `attachGroup` перечитывает `groups.get` (`GroupContentsTable.attachGroup`). Операция переноса группы должна принимать `version` и не терять эту охрану.

### Pitfall 11: вакуумные тесты
Память «Вакуумный тест из-за фикстуры» и «Якорь мутационной проверки обязан быть уникальным»: тест D-08/D-13 должен проверять, что ДО фикса он краснел (разные фикстуры для «чужой origin» / «пустой origin» / «свой origin»); мутации реального исходника — `replace(anchor, …)` по уникальному якорю (`matches(anchor).count() == 1`).

1. **Уже вложенные teardown-группы и teardown-группы с «чужими» деталями в живых БД.**

2. **«Списать» у группы в дереве: откуда узел знает статус якоря?** `GroupDto` несёт `anchor_device_id`/`anchor_device_name`, но НЕ статус якоря. Варианты: добавить `anchor_status_code: Option<String>` в `GroupDto` (один JOIN в `group_dto_on`/`GroupSnapshot` — затронет все места, строящие `GroupDto`) или показывать пункт всегда и проверять на сервере. Рекомендация: добавить поле (D-21 требует, чтобы пункт появлялся именно при «На списание»); учесть, что `GroupDto` — часть golden-DTO в `dto/*` тестах сериализации.

3. **Роль для «Списать» устройства.** UI-SPEC сноска 3: «требует прав на правку устройства и, для участников/якорей, MutateGroups». Рекомендация: `authorize` по тому же правилу, что `devices.update` (`UpdateDevices`/аналог — сверить с `role_endpoint_matrix`), плюс `MutateGroups` при `group_action = release` или `groups_write_off`.

4. **`groups.search` не возвращает поведение типа.** `GroupSearchHitDto` — `{id,name,type_name,device_count,has_parent,place_path_short}`; D-17 (не предлагать teardown) для строки добавления состава потребует `type_behavior` (или серверной фильтрации по умолчанию). 5. **Двойной клик: «открыть просмотр, правка — оттуда»** — `PlaceEntityViewModal` уже встроен в `DeviceRowMenu` (`openView()`), отдельного обработчика `onOpenDevice` страницы можно не оставлять. Проверить, что `GroupsPage` не использует `onOpenDevice` для перехода в «Устройства».
