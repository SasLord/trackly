## Реализация

- `statusMenuOptions`: по элементу на статус в порядке справочника; текущий отмечен; для якоря «списано» неактивно с текстом отказа «спишите через группу»; при открытой ремонтной заявке (число) неактивны все варианты с «Статус меняется заявкой на ремонт.» (приоритет над причиной якоря); `null`/отсутствие поля правило не включает.
- `canChangeStatus`: admin и manager; employee, null, пустая и неизвестная роль дают false.
- `buildMenuSections`: при `status === true` пункт `{kind:'status', label:'Статус'}` после «Печать документа приёма» (без печати после «Редактировать»), секции членства и хвоста не сдвинуты. Существующие кейсы фикстуры не менялись (только добавления: 7 новых кейсов).
- Гейт `check-device-status-menu`: 18 кейсов, паритеты (код «списано» = STATUS_WRITTEN_OFF, роли = MUTATE_ROLES, текст якоря = anchorWriteOffRefusal, текст заявки = REPAIR_STATUS_NOTE через регулярное выражение по исходнику), правило «без import», 15 мутантов с проверкой единственности якоря. Подключён в lint перед `check-lint-selftest-wiring` (тот зелёный: 67 гейтов).
- В `check-device-row-menu` добавлены 2 мутанта (флаг status, порядок относительно печати). Реальная мутация `deviceRowMenu.ts` (снята вставка пункта; копия в scratchpad, восстановление `cp`, `cmp` чистый) краснит 3 кейса со `status: true`.
- Серверные тесты (`status_only_patch_*`): обычная смена (место и прочее не тронуты, версия +1); участник без выбора даёт Validation `group_write_off` (состояние не изменено); Keep оставляет в группе без аудита вывода, Release выводит с аудитом `custom:group_member_released`; якорь (с выбором и без) отклоняется Validation `status_id` с «спишите»; возврат из «В ремонте» с разошедшимся местом переносит на место группы (D-17); устаревшая версия даёт OptimisticLockMismatch; открытая ремонтная заявка даёт Conflict; employee через `build_devices_update` получает Forbidden, manager проходит (контроль несущей способности). В каждом сценарии исходное состояние утверждается до вызова.
