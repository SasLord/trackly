## Сводка

Проверены серверные операции фазы (`move_devices`, `write_off_device`, `write_off_group`, D-16 в `set_parent`, D-08 в `add_one_in_tx`, призраки и D-13), их транспорт (Tauri и HTTP), DTO, ошибка `AlreadyInGroup` и клиентская часть: меню строки, попапы «уже в группе», модалки списания, дерево с двойниками.

Серверное ядро в целом согласовано с решениями. Перенос идёт одной транзакцией, все занятые элементы пакета приходят в одном отказе, разбор принимает только свои детали, удаление разбора с призраками запрещено. Найдены два дефекта уровня BLOCKER:

1. Устройство, которое по D-20 оставили в группе со статусом «Списано», по-прежнему разворачивается в единицы акта и проходит проверку `is_act_assignable` («член живой группы при любом статусе»). Акт приёма-передачи молча вернёт его в «В работе».
2. D-18 недостижим из интерфейса. Модалка массового добавления блокирует чекбоксы занятых устройств и снимает их с выбора, поэтому новый шаг «N устройств уже в других группах → Переместить» открывается только в гонке.

Остальное: обход общего примитива освобождения (нет записи аудита по устройству), потеря выбора на узле-двойнике, порядок проверок, из-за которого попап переноса предлагает заведомо отклоняемое действие, а также мелочи.

Известный пробел UAT-11 (смена статуса на «Списано» через обычную форму без выбора «оставить/вывести») повторно не заявляется. CR-01 его усугубляет: тем же путём в группе появляется списанный участник, и акт его тоже «оживит».

## Critical Issues

### CR-01: списанный участник группы попадает в акт и молча теряет статус «Списано»

**Файлы:**
- `crates/trackly-app/src/services/group_service.rs:987-1001` (`write_off_device`, ветка `release_from_group = false`)
- `crates/trackly-app/src/services/act_service.rs:90-117` (`is_act_assignable`)
- `crates/trackly-app/src/services/group_service.rs:467-531` (`act_expansion`) и `group_act_plan.rs:634` (`act_units`), в обоих нет фильтра по статусу
- `ui/src/features/acts/ActFormItemsTable.svelte:742-790` (`pickGroupHit` вставляет все `exp.units`)

**Проблема:** D-20 вводит новое легальное состояние: участник группы со статусом «Списано». Существующие пути акта для такого устройства не рассчитаны:
- `act_units` и `act_expansion` отдают всех прямых и вложенных участников без проверки статуса, и форма акта при выборе группы добавляет их все;
- `is_act_assignable` возвращает `true` для любого члена живой группы «при любом статусе» (комментарий в строках 93-95);
- путь передачи (`act_service.rs:761`) вызывает `update_status_and_place_in_tx(..., in_work_status_id, ...)` для каждого устройства.

В итоге акт передачи АРМ, где оставлен списанный монитор, ставит этому монитору «В работе» и новое место. Отказа и предупреждения нет. Нарушена целостность учёта: списание отменяется без следа в UI. До этой фазы списанный участник мог появиться только через UAT-11, теперь его создаёт штатная серверная операция.

**Исправление:** запрет нужен на сервере (граница безопасности), скрытие в UI — дополнительно:
```rust
// act_service.rs, is_act_assignable — до ветки «член группы»:
let code: String = tx.query_row(
    "SELECT code FROM device_statuses WHERE id = ?1",
    rusqlite::params![device.status_id], |r| r.get(0),
).map_err(map_rusqlite)?;
if code == "списано" {
    return Ok(false);
}
```
Плюс фильтр в `act_units`/`load_snapshot` (или в `act_expansion`): `ds.code <> 'списано'`. Тогда форма акта не предложит такое устройство, а планировщик группы не потащит его в перенос. Нужен регрессионный тест: группа с участником «Списано», создать акт передачи группы, проверить, что статус «Списано» сохранился (или пришёл отказ).

### CR-02: D-18 недостижим, занятые устройства в модалке нельзя выбрать

**Файл:** `ui/src/features/groups/GroupAddDevicesModal.svelte:125-135, 448-455`

**Проблема:** D-18 требует: если среди выбранных есть устройства из других групп, открыть один попап «N устройств уже в других группах» с кнопкой «Переместить». Фаза добавила этот шаг (`step = 'confirm'`, `moveAll`, строки 258-330), но оставила прежнюю блокировку:
```svelte
<Checkbox checked={selected.has(d.id)} disabled={busyIn !== undefined || busy} … />
```
и `loadOccupancy` снимает занятые устройства с выбора («выбранным оставаться не может»). Занятое устройство выбрать нельзя, поэтому `ALREADY_IN_GROUP` от `groups.addDevices` приходит только в гонке, когда устройство заняли между подсказкой и отправкой. Сценарий «выбрать устройства из других групп и перенести пакетом» из интерфейса не воспроизводится. Решение D-18 по факту не выполнено, а новый код шага подтверждения почти мёртвый.

**Исправление:** не блокировать занятые строки, оставить только пометку «Уже в группе «…»»:
```svelte
<Checkbox checked={selected.has(d.id)} disabled={busy} onchange={(v) => toggle(d.id, v)}>
```
и убрать в `loadOccupancy` фильтрацию `selected`. Исключение — устройства, которые уже в ЭТОЙ группе: их стоит блокировать (сравнивать `m.group_id === group.id`), иначе `move_devices` отклонит весь пакет с «Устройство уже входит в эту группу.».

## Warnings

### WR-01: перенос и списание освобождают членство мимо `release_device_in_tx`, без записи аудита по устройству

**Файлы:** `crates/trackly-app/src/services/group_service.rs:1531-1533` (`move_devices`), `:996-1001` (`write_off_device`), `:1084-1095` (`write_off_group`, расформирование)

**Проблема:** все остальные пути вывода (`remove_devices`, удаление устройства, акт) идут через `group_membership::release_device_in_tx`, а он пишет по устройству `custom:group_member_released` с `group_id`. Новые операции вызывают `deps.groups.remove_device_in_tx` напрямую и пишут одну запись уровня группы (`move_devices`) или устройства без снимков (`write_off`, `before_json/after_json = None`). При этом путь создания разбора (строки 760-781) для той же смены статуса пишет `action: "update"` со снимками «до/после». Журнал устройства получается неоднородным, а фаза 41.10 (история событий) строится как раз на этих операциях (D-04, D-22).

**Исправление:** в `move_devices` и `write_off_device` освобождать через `release_device_in_tx(&tx, &deps.groups, &deps.audit, id, None, user_id, now)`: охрана якоря уже внутри, так что ручная проверка в `move_devices` станет лишней. Для `write_off` писать `before_json/after_json` устройства, как в ветке создания разбора. Если реестровый гейт S11 привязан к областям, обновить его вместе с кодом.

### WR-02: выбор узла-двойника теряется после «Вывести из группы» или переноса, панель закрывается

**Файлы:** `ui/src/features/groups/GroupTree.svelte:175-196` (ключ `in-type-{id}`), `:416-420`

**Проблема:** выбор хранится по ключу узла. Если выбрать двойника вложенной группы (`in-type-B`) и вывести B из родителя, то после `loadAll` B становится корнем с ключом `group-B`, ключа `in-type-B` больше нет. Срабатывает ветка `selectedKey !== null && !treeData.itemByKey.has(selectedKey)`: выбор сбрасывается, `onSelect(null)`, панель группы закрывается, хотя группа жива. То же происходит с ключами потомков двойника `in-type-{root}-group-{id}`.

**Исправление:** при пропаже ключа вернуться к основному узлу той же группы:
```ts
} else if (selectedKey !== null && !treeData.itemByKey.has(selectedKey)) {
  const prev = selectedItemId; // id выбранной группы
  const fallback = prev !== null ? groupKey(prev) : null;
  if (fallback && treeData.itemByKey.has(fallback)) { selectedKey = activeKey = fallback; }
  else { selectedKey = null; activeKey = null; onSelect(null); }
}
```

### WR-03: попап «уже в группе» предлагает перенос, который сервер заведомо отклонит

**Файл:** `crates/trackly-app/src/services/group_service.rs:1293-1322` (`add_one_in_tx`)

**Проблема:** в режиме `Plain` устройство, занятое другой группой, классифицируется как `Occupied` ДО проверок статуса («Списано» и «На списание» вне разбора). Устройство «Списано» или «На списание», оставленное в АРМ, при вводе в другую группу возвращает `ALREADY_IN_GROUP`. Клиент показывает попап «Переместить?», пользователь подтверждает, `move_devices` отказывает текстом про статус. Это лишний шаг с гарантированным отказом. С D-20 такие устройства появляются штатно.

**Исправление:** проверки статуса вынести выше ветки `group_of_device_in_tx`, чтобы отказ по статусу приходил сразу, без попапа переноса:
```rust
if device.status_code == STATUS_CODE_WRITTEN_OFF { return Err(...); }
if device.status_code == STATUS_CODE_TO_WRITE_OFF && target_behavior != Some(GroupBehavior::Teardown) { return Err(...); }
if let Some(existing) = deps.groups.group_of_device_in_tx(tx, device_id)? { ... }
```

### WR-04: «Создать деталь» из двух неатомарных вызовов, а D-13 делает сбой необратимым

**Файлы:** `ui/src/features/groups/GroupContentsTable.svelte:625-667`, `crates/trackly-app/src/services/device_service.rs:727-753, 888`

**Проблема:** `origin_group_id` теперь записывается при создании (`devices.create*` / `bulkCreate`), ввод в разбор идёт вторым вызовом `groups.addDevices`. Если второй вызов упал (сеть, `WRITE_QUEUE_BUSY`, гонка удаления), деталь уже есть с происхождением, но не в составе. Это призрак, и по D-13 разбор больше нельзя удалить. До фазы такой сбой оставлял свободное устройство без последствий, теперь он навсегда блокирует запись разбора. Сервер принимает `origin_group_id` от любого вызова создания и не требует, чтобы устройство в итоге оказалось в разборе.

**Исправление:** одна серверная операция «создать деталь разбора» (создание и `add_device_in_tx` в одной транзакции писателя) либо параметр `add_to_origin_group: true` в create, который вводит деталь в состав той же транзакцией. Клиентский второй вызов тогда не нужен.

### WR-05: подтверждение списания «Системного блока» не перечисляет вложенные группы, `released_devices` учитывает якорь

**Файлы:** `ui/src/features/groups/WriteOffGroupModal.svelte:46-69`, `crates/trackly-app/src/services/group_service.rs:1084-1087`

**Проблема:** D-21 требует, чтобы подтверждение перечисляло состав. Расформирование (`delete_group_in_tx_audited`) освобождает и устройства, и вложенные группы (они становятся корневыми), но модалка строит список только из `comp.devices`, `comp.child_groups` не показан. Кроме того, `released = before.direct_device_count` включает сам якорь: он член `group_devices`, но списан, а не освобождён. Счётчик в ответе и в аудите завышен на 1, а в списке модалки якорь стоит среди освобождаемых.

**Исправление:** в модалке добавить строки `comp.child_groups` («группа … станет самостоятельной») и исключить `anchor_device_id` из списка. На сервере считать `released = direct_device_count - 1` при наличии якоря-члена.

### WR-06: `AddToGroupModal` показывает конфликт версии и NOT_FOUND как сбой связи

**Файл:** `ui/src/features/groups/AddToGroupModal.svelte:176-187`, вызов из `GroupContentsTable.svelte:791-795` (`moveGroupTarget = child`)

**Проблема:** для переноса вложенной группы из строки состава `subjectGroup` берётся из снимка `composition` вместе с `version`. После любого изменения группы во второй сессии (или после переименования) `setParent` вернёт `OPTIMISTIC_LOCK_MISMATCH`, а модалка покажет тост «Не удалось переместить. Проверьте подключение и повторите.». Это ложная причина, и повтор не поможет.

**Исправление:** перед `setParent` в `doMove` брать свежую версию (`groups.get(subjectGroup.id)`), как это уже делают `attachGroup` и `GroupsPage.openMoveToGroup`. Коды `OPTIMISTIC_LOCK_MISMATCH` и `NOT_FOUND` показывать текстом в `fieldErr`, а не тостом про связь.
