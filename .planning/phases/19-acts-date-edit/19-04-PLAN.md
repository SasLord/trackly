<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Untrusted client (Tauri webview forged invoke, or raw HTTP POST from any LAN host) → `/api/v1/acts_update` / Tauri `acts_update` | First reachable entry point into `ActService::update` (built in Plan 19-03). Both transports MUST enforce identical session + role checks — this is exactly the boundary CLAUDE.md's dual-transport rule exists to protect ("Tauri command handlers and axum HTTP handlers are thin adapters; the service module owns the single writer"). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-19-09 | Spoofing / Tampering | Unauthenticated raw HTTP POST to `/api/v1/acts_update` | mitigate | `session_identity(&session)` is called first in `handler_update`, mirroring every other mutation handler in this file — a request with no/invalid session cookie is rejected before `build_acts_update` (and thus `ActService::update`) is ever invoked. Same mechanism already protects `acts_create`/`acts_delete`/`acts_return`. |
| T-19-10 | Elevation of Privilege | Employee-role session calling `acts_update` directly (Tauri invoke OR raw HTTP), attempting to bypass the "Редактировать" button's client-side gating | mitigate | `authorize(caller, &Action::MutateActs)` inside `build_acts_update` — the SAME check already used by `create`/`do_return`/`delete_soft` — is enforced identically regardless of transport, because both `acts_update` (Tauri) and `handler_update` (axum) call the same `build_acts_update`. Regression-proofed by the new `role_endpoint_matrix.rs` case (Task 2). |
| T-19-11 | Tampering | Divergence between the Tauri and HTTP transport's validation/authorization logic (a class of bug this codebase has previously guarded against via the `build_*` shared-helper convention) | mitigate | `build_acts_update` is the SINGLE function both `acts_update` and `handler_update` call — there is no duplicated authorize/validate logic to drift out of sync (S-1 pattern, enforced by code structure, not just convention). |

D-07/D-08's actual enforcement logic lives inside `ActService::update` (Plan 19-03) — this plan only makes that method reachable, with the correct authn/authz gates in front of it on both transports.
</threat_model>
