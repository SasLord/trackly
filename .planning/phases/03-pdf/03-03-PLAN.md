## Phase Goal

**As a** сотрудник, **I want to** оформить возврат устройств (полный или частичный) по акту приёма-передачи с галочкой «Применить ко всем» и per-row override, а также иметь возможность удалить акт (handover или return) с автоматическим восстановлением состояния устройств, **so that** учёт возвратов и undo работают одной кнопкой без ручного редактирования таблиц — это вторая половина дифференцирующей ценности Phase 3 (закрывает ACT-06, ACT-07, ACT-08, ACT-09, ACT-10).

> **Vertical slice (MVP mode):** этот план поставляет пользователю две новые возможности — «Оформить возврат» (ReturnModal с bulk+per-row) и «Удалить акт с откатом» (confirm modal + audit_log replay). После него полностью работает lifecycle: create handover → partial return → full return → auto-archive → undo возврата → un-archive.

<objective>
Returns + auto-archive + undo вертикальный слой поверх плана 02: расширить ActService методом `do_return` (sub_number sequencing + bulk apply + per-row override + auto-archive в той же tx), переписать `delete_soft` с полным undo через audit_log replay (для handover и return), добавить tauri command `acts_return` + UI ReturnModal, и проверить D-Numbering-01 «в»/«в1/2» display-rule в format_act_number с retroactive promotion.

Purpose: Закрыть требования ACT-06 (delete handover restores), ACT-07 (suffix «в»/«в1/2»), ACT-08 (bulk apply + per-row override), ACT-09 (auto-archive), ACT-10 (delete return restores).

Output: В UI работает «Возврат» из ActDetail → ReturnModal с галочкой «Применить ко всем» (по умолчанию ВКЛ); создание возврата возвращает devices на склад с новым состоянием/локацией; full return авто-архивирует исходный акт; «Удалить» (handover или return) восстанавливает devices к prior-state; lifecycle round-trip green.
</objective>

ВАЖНО: в БД `number` для return-акта может быть либо родительский (как parent.number) либо новый из counter. Из RESEARCH §«Sub-number for return»: `parent_number` JOIN'ится для display; в БД return-акт хранит свой собственный `number` = parent.number (повторение). Confirm with PATTERNS / RESEARCH — выбираем РАСХОД: return-акт имеет `number = parent.number` (повторение) и `sub_number = N+1`. UNIQUE индекс на (number, COALESCE(sub_number,0)) делает это валидным: (42, 0) = handover, (42, 1) = return, (42, 2) = next return. Counter act_number НЕ инкрементируется на returns.

- pub async fn delete_soft(&self, id: i64, version: i64) -> Result<(), AppError>
  Body (writer.execute):
  1. tx; act = acts_repo.fetch_full_in_tx(&tx, id); если deleted_at_utc.is_some() → NotFound
  2. if act.version != version → OptimisticLockMismatch
  3. **Undo all device mutations attributable to this act:**
     - rows = audit_log_repo.select_device_mutations_for_act(&tx, id)
     - for (device_id, before_json) in rows.iter().rev() { devices_repo.restore_from_snapshot_in_tx(&tx, device_id, &before)? + INSERT audit_log action='custom:undo' }
     - **Order matters:** rev() важно — если был sequence A→B→C, восстанавливаем в обратном порядке: B'→A'. НО для handover/return каждого акта обычно только один mutation на device — поэтому простой forward loop тоже работает. Используем простой forward для предсказуемости.
     - **Edge: act_items.complectation_at_time/condition_at_time** — не используется для undo (D-Undo-01).
  4. **Cascade delete dependent return-acts** (если act — handover): SELECT id FROM acts WHERE parent_act_id = ? AND deleted_at_utc IS NULL → для каждого: recursive delete_soft вызов (или inline той же логики в одной tx). **Прямой подход:** соберите list_returns_for_parent → для каждого return сделайте подъобёртки undo + soft_delete_act_in_tx + DELETE act_items. ВАЖНО: возможно UI deletes handover с активными returns — это допустимо, нужно очистить и returns; либо отказать с Conflict «Сначала удалите возвраты». **DECISION (claude's discretion per D-Schema):** разрешаем cascade — handover delete = handover undo всех своих device mutations + cascade soft-delete всех returns (без отдельного undo для returns, потому что их undo приводит к тому же state «как при handover», а потом handover undo к pre-handover; делать undo последовательно в обратном порядке — return undo первым, handover undo вторым).
  5. **Implementation:** для handover delete: (a) если есть returns — для каждого делать full undo (read audit by return.id, restore devices); (b) затем сделать handover undo (read audit by handover.id, restore devices); (c) soft-delete handover + cascade soft-delete returns + DELETE act_items для всех; (d) INSERT audit_log acts(delete).
  6. For return-act delete (act.act_type == Return): undo just this return's audit mutations → soft-delete act + DELETE act_items → recompute_parent_archived(parent_act_id) → INSERT audit_log acts(delete).
  7. tx.commit.

recompute_parent_archived (acts_sqlite.rs) — B-2 update: SUM(quantity) semantics:
- pub fn recompute_parent_archived(tx: &Transaction, parent_act_id: i64, devices_repo: &SqliteDeviceRepository) -> Result<bool, AppError>
  Возвращает новое значение archived. **SUM(quantity) семантика per B-2** — учитываем act_items.quantity column (добавлена V014 в plan 02):
  in_work_status_id = SELECT id FROM device_statuses WHERE code='в_работе'   -- B-1: code column из V014
  remaining = COALESCE((SELECT SUM(ai.quantity) FROM act_items ai
                          JOIN devices d ON d.id = ai.device_id
                         WHERE ai.act_id = ?1 AND d.status_id = ?2), 0)
  archived = if remaining == 0 { 1 } else { 0 }
  UPDATE acts SET archived=?, updated_at_utc=?, version=version+1 WHERE id=?
  **Объяснение:** «остаток в работе» = сумма quantity по тем act_items handover-акта, у которых соответствующий device всё ещё в status='в_работе'. Когда полный возврат вернул все позиции → их devices переведены в 'на_складе' → SUM становится 0 → archived=1. Это поведение совместимо с D-Archive-01 и масштабируется на multi-quantity rows.
