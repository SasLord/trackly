## ITEM-1 — Разделение вызовов listGrouped: флаг group_by_condition

### Текущее состояние SQL (VERIFIED по коду)

Файл: `crates/trackly-infra/src/repos/devices_sqlite.rs`, строки 903–1069.

Функция `list_grouped` (метод `DeviceRepository::list_grouped`) имеет GROUP BY (строки 964):
```sql
GROUP BY d.type_id, d.name, d.condition
```

Это DEF-2B изменение (фаза 03.2-02). Именно это разбивает группы в DevicesPage по Состоянию.

### Рекомендуемый подход: Вариант A — флаг `group_by_condition` в DeviceFilter

**Почему Вариант A лучше Варианта B (отдельный метод):**
- Вариант B удваивает сигнатуры: `list_grouped` и `list_grouped_no_condition` в трейте, адаптере, сервисе, двух транспортных файлах и API-клиенте фронтенда. Это 5+ дополнительных точек изменений.
- Вариант A: одна новая булева поле в `DeviceFilter`, одно условие в SQL, все остальное передаётся автоматически.
- `DeviceFilter` уже сериализуется через specta/serde, флаг будет автоматически доступен в TypeScript-биндингах.

### Цепочка изменений Варианта A (полная)

**1. `trackly-core/src/domain/devices.rs` (строка 47, структура `DeviceFilter`):**
```rust
pub struct DeviceFilter {
    // ... существующие поля ...
    pub include_deleted: bool,
    /// Если true — GROUP BY включает d.condition (для акт-формы).
    /// Если false (по умолчанию) — GROUP BY по (type_id, name) без разбивки по condition.
    pub group_by_condition: bool,
}
```

**2. `trackly-app/src/dto/device.rs` (структура `DeviceFilter`, строки 191–204):**
```rust
pub struct DeviceFilter {
    // ... существующие поля ...
    pub include_deleted: bool,
    pub group_by_condition: bool,  // добавить
}
```
Поскольку `DeviceFilter` имеет `#[derive(..., Type)]`, TypeScript-биндинги обновятся автоматически.

**3. `trackly-infra/src/repos/devices_sqlite.rs` (функция `list_grouped`, строки ~930–966):**

SQL нужно сделать условным. Два подхода:

- **Подход A1 (рекомендуется):** Разные SQL-строки через Rust `if`:
```rust
fn list_grouped(&self, conn, filter, page) -> ... {
    let group_by_clause = if filter.group_by_condition {
        "GROUP BY d.type_id, d.name, d.condition"
    } else {
        "GROUP BY d.type_id, d.name"
    };
    // Также нужно изменить SELECT и LEFT JOIN subquery:
    // Когда !group_by_condition, condition в GROUP BY отсутствует,
    // поэтому `d.condition AS condition` нужно заменить на
    // `MAX(d.condition) AS condition` для агрегации.
    // LEFT JOIN subquery тоже убирает `AND d2.condition IS d.condition`.
```

- **Подход A2:** Использовать `(?4 = 0 OR d.condition IS d.condition)` трюк SQLite. Не рекомендуется — нечитаемо и сложно тестировать.

**ВАЖНО про LEFT JOIN subquery:** Когда `group_by_condition = false`, LEFT JOIN subquery (строки 953–961) должен убрать фильтр `AND d2.condition IS d.condition`. Иначе location_name будет неверным. Это означает что нужно генерировать разные SQL-строки, не patch-запрос.

**Рекомендация реализации: две строковые константы SQL или один `format!` с условным подставлением.** Проще всего — написать функцию, возвращающую SQL-строку в зависимости от флага.

**4. `trackly-app/src/services/device_service.rs` (метод `list_grouped`, строки 505–513):**

Добавить в маппинг domain_filter:

### Поле «разное» в свёрнутой группе (ITEM-1 дополнение)

**Архитектурное решение: вычислять на клиентской стороне.**

Когда `group_by_condition = false`, бэкенд возвращает `repr.state = MAX(d.condition)` — одно произвольное значение из членов группы. Клиент не знает, все ли члены группы имеют одинаковый condition.

**Нужен ли дополнительный бэкенд-поле?** Да — для корректного «разное» нужно знать, есть ли в группе несколько разных condition. Самый лёгкий путь: добавить поле `condition_distinct_count: i64` в SQL (`COUNT(DISTINCT d.condition) AS condition_distinct_count`) и вернуть его в `DeviceGroupRow`/`DeviceGroup`.

**Изменения:**

В SQL (когда `!group_by_condition`):
```sql
COUNT(DISTINCT d.condition) AS condition_distinct_count
```

В `DeviceGroupRow` (domain):
```rust
pub condition_distinct_count: i64,  // добавить
```

В `DeviceGroup` (DTO):
```rust
pub condition_distinct_count: i64,
```

В `DeviceGroupRow.svelte`:
```ts
// В collapsed состоянии:
const conditionDisplay = $derived(
    group.condition_distinct_count > 1 ? 'разное' : (group.repr.state ?? '—')
);
```

**Альтернатива:** Не добавлять поле, а после expand через `listByIds` проверять уникальность. Минус — «разное» будет видно только после expand, что противоречит задаче (в collapsed должно быть «разное»). Значит поле в SQL необходимо.

**Когда `group_by_condition = true` (акт-форма):** `condition_distinct_count` будет всегда 1 (каждая группа уже однородна по condition по определению GROUP BY). Это корректно, не сломает акт-форму.

## ITEM-4 — Автокомплит «Расположение»: вторая секция всех локаций

### Текущая ситуация (VERIFIED по коду)

**Что есть в бэкенде:** `DeviceService::locations_autocomplete` (`device_service.rs` строки 367–412) — уже СУЩЕСТВУЕТ. Запрашивает `SELECT name FROM locations WHERE deleted_at_utc IS NULL AND name LIKE ?1`. Таuri command `locations_autocomplete` (строки 180–186 `tauri_cmds/devices.rs`) уже зарегистрирована. HTTP handler не обнаружен в явном виде в `http/devices.rs` (нет в router), но команда Tauri есть.

**`LocationAutocomplete.svelte`** (строки 35–37): вызывает `apiCall<string[]>('locations_autocomplete', { prefix })` — прямо обращается к Tauri команде.

**`DeviceAutocompleteField.svelte`** (строка 112): для `field="location"` вызывает `devices.autocomplete('location', ...)` — это контекстный автокомплит (по устройствам с JOIN locations, с фильтром по contextName/statusId).

**`DeviceFormBody.svelte`** (строки 322–330): поле «Расположение» использует `DeviceAutocompleteField` с `field="location"`, `contextName={name.trim() || undefined}`, `contextStatusId={parseInt(statusId, 10) || null}`.

### Решение: расширить DeviceAutocompleteField для field="location"

Добавить вторую секцию в dropdown `DeviceAutocompleteField` только когда `field === 'location'`:

**Логика:**
1. Основной fetch (строки 109–126): контекстный автокомплит (по устройствам с contextName) — остаётся секцией «Ранее использовалось с «{contextName}»».
2. Новый параллельный fetch к `locations_autocomplete` (строки 35–37 из LocationAutocomplete): секция «Все расположения».

**HTTP route для `locations_autocomplete` отсутствует в router.** Нужно проверить, добавлен ли он в `http/devices.rs`. Из кода видно что router в `http/devices.rs` (строки 294–321) не содержит `/api/v1/locations_autocomplete`. Для HTTP-транспорта нужно добавить handler.

**Подход к реализации:**

Вариант A (рекомендуется): добавить отдельный `allLocationSuggestions: string[]` state в DeviceAutocompleteField, делать параллельный fetch к `locations_autocomplete` когда `field === 'location'`, отображать в виде второй секции в dropdown.

```ts
// Внутри $effect или handleFocus для field="location":
let allLocationSuggestions = $state<string[]>([]);

// В fetch эффекте, когда field === 'location':
if (field === 'location') {
    const allLocs = await apiCall<string[]>('locations_autocomplete', { prefix: v });
    // Фильтровать чтобы не дублировать то, что уже в основных suggestions
    allLocationSuggestions = allLocs.filter(l => !suggestions.includes(l));
}
```

В разметке dropdown:
```svelte
<!-- Существующая секция (contextual) -->
{#if suggestions.length > 0}
    <header class="dropdown-header">Ранее использовалось с «{contextName}»:</header>
    {#each suggestions as s, i (s)}...{/each}
{/if}

<!-- Новая секция (все локации) — только для field="location" -->
{#if field === 'location' && allLocationSuggestions.length > 0}
    <header class="dropdown-header">Все расположения:</header>
    {#each allLocationSuggestions as s, i ('all_' + s)}...{/each}
{/if}
```

**Нужен ли HTTP route?** Да — для browser-mode. Добавить в `http/devices.rs`:
```rust
pub async fn handler_locations_autocomplete(
    State(ctx): State<AppCtx>,
    Json(payload): Json<LocationsAutocompletePayload>,
) -> Result<Json<Vec<String>>, AppErrorResponse> { ... }
```
И в router:
```rust
.route("/api/v1/locations_autocomplete", post(handler_locations_autocomplete))
```

## Типичные ошибки (Pitfalls)

### Pitfall 1: Не обновить `condition_distinct_count` в сериализации

**Что пойдёт не так:** Добавить поле в `DeviceGroupRow` (domain), забыть в `DeviceGroup` (DTO) или не добавить в SQL SELECT — runtime panic или всегда 0.

**Профилактика:** Изменения в трёх местах синхронно: SQL SELECT, `DeviceGroupRow` (domain crate), `DeviceGroup` (DTO crate). Тест в `devices_grouping.rs` должен проверять `condition_distinct_count`.

### Pitfall 2: Неправильный colspan после двух правок одновременно

**Что пойдёт не так:** Добавить «Состояние» (+1 колонка) и убрать условно «Статус» — loading-row colspan в DeviceGroupRow останется 7 вместо динамического.

**Профилактика:** Таблица colspan выше. Все места: skeleton в DeviceList, loading row в DeviceGroupRow, `colspan="4"` в GroupRow (не меняется!).

### Pitfall 3: `groupStableKey` в DeviceGroupRow зависит от `group.repr.state`

**Что пойдёт не так:** Когда `group_by_condition=false`, repr.state становится MAX(condition) — произвольное значение. Если оно меняется между двумя загрузками (напр. после edit), стабильный ключ группы изменится, expandedGroups сбросится. Это не баг, это допустимо — expanded state это UI ephemeral state, сброс при refresh приемлем.

**Что делать:** Оставить как есть. Документировать в комментарии.

### Pitfall 4: HTTP route для locations_autocomplete отсутствует

**Что пойдёт не так:** В browser-режиме (не Tauri) вторая секция автокомплита вернёт 404.

**Профилактика:** Добавить HTTP route ОБЯЗАТЕЛЬНО вместе с фронтенд-изменением.

### Pitfall 5: DeviceFilter.Default() не выставит group_by_condition

**Что пойдёт не так:** `#[derive(Default)]` выставит `false` — это именно то что нам нужно для DevicesPage. Но тест в `devices_grouping.rs` создаёт `DeviceFilter::default()` — старые тесты будут проверять behaviour без condition разбивки. Нужно добавить тест явно с `group_by_condition: true`.

**Профилактика:** Старые тесты (`condition_key_splits_groups`, `grouping_groups_devices_with_same_name_and_different_condition`) нужно обновить чтобы передавать `group_by_condition: true` — иначе они упадут, так как теперь default = false (нет разбивки по condition).

### Текущий SQL list_grouped (для справки при модификации)

`crates/trackly-infra/src/repos/devices_sqlite.rs`, строки 934–966 [VERIFIED]:
```sql
SELECT
  MIN(d.id)                       AS repr_id,
  COUNT(*)                        AS cnt,
  GROUP_CONCAT(d.id)              AS id_list,
  d.type_id, d.name,
  MAX(d.model)                    AS model,
  MAX(d.notes)                    AS notes,
  MAX(d.complectation)            AS complectation,
  d.condition                     AS condition,      -- станет MAX(d.condition) когда !group_by_condition
  MAX(d.location_id)              AS location_id,
  MAX(d.status_id)                AS status_id,
  MAX(d.version)                  AS version,
  MAX(d.created_at_utc)           AS created_at_utc,
  MAX(d.updated_at_utc)           AS updated_at_utc,
  l.name                          AS location_name,
  MAX(d.inventory_number)         AS inv_no,
  MAX(d.serial_number)            AS serial_no
FROM devices d
LEFT JOIN locations l ON l.id = (
  SELECT MAX(d2.location_id)
  FROM devices d2
  WHERE d2.type_id = d.type_id
    AND d2.name = d.name
    AND d2.condition IS d.condition   -- убрать когда !group_by_condition
    AND d2.deleted_at_utc IS NULL
    AND (?1 IS NULL OR d2.status_id = ?1)
)
WHERE d.deleted_at_utc IS NULL
  AND (?1 IS NULL OR d.status_id = ?1)
GROUP BY d.type_id, d.name, d.condition   -- условный
```
