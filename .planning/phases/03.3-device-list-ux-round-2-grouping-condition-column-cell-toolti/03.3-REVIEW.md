# Phase 03.3: Code Review Report

**Reviewed:** 2026-06-07
**Depth:** standard
**Files Reviewed:** 11
**Status:** issues_found

## Summary

Reviewed the device-list grouping / condition-column / cell-tooltip / autocomplete round-2 work spanning the Rust data/service/repo layers and the Svelte UI. The grouping logic is broadly correct and well-tested, but I found one correctness bug that produces wrong displayed data (representative location can be borrowed from an unrelated device in non-condition grouping mode), several robustness gaps in autocomplete (unescaped LIKE wildcards, keyboard-navigation index drift on the location field), an unreachable-by-design `select` race in the autocomplete dropdown filter, and a number of quality issues (duplicated status-label maps, duplicated SELECT column lists, dead CSS, a misleading `update` location-clear contract). No injection vulnerabilities were found — all SQL is parameterized and the autocomplete column name comes from a whitelisted enum.

## Narrative Findings (AI reviewer)

## Critical Issues

### CR-01: `list_grouped` LEFT JOIN can attach a location from an unrelated condition group

**File:** `crates/trackly-infra/src/repos/devices_sqlite.rs:968-999` (the `sql_without_condition` branch)
**Issue:** In `group_by_condition = false` mode (the DevicesPage default), the group key is `(type_id, name)` and the representative `location_name` is resolved with:

```sql
LEFT JOIN locations l ON l.id = (
  SELECT MAX(d2.location_id)
  FROM devices d2
  WHERE d2.type_id = d.type_id
    AND d2.name = d.name
    AND d2.deleted_at_utc IS NULL
    AND (?1 IS NULL OR d2.status_id = ?1)
)
```

The displayed `location_id` of the group comes from `MAX(d.location_id)` (line 978), but the displayed location *name* comes from the `locations` row whose id equals `MAX(d2.location_id)` computed by the correlated subquery. These two `MAX` computations are over the *same* set, so they agree here — but the deeper problem is semantic: when a group collapses devices with **different locations**, the row shows a single arbitrary location (the one with the largest `location_id`), silently hiding the fact that members live in different places. The `condition` column got a `condition_distinct_count` / «разное» affordance for exactly this reason (line 977, 943), but `location` did not. A user looking at the Устройства list will believe all N collapsed devices share one location when they do not. This is wrong displayed data, not just a style nit — and the test `grouping_groups_devices_with_same_name_and_different_location` (tests line 464-495) explicitly asserts the collapse happens but never checks which location is shown.

**Fix:** Either (a) add a `location_distinct_count` aggregate analogous to `condition_distinct_count` and render «разное» when `> 1`, or (b) document and intentionally show «разное» / blank for mixed-location groups. Minimal correctness fix:

```sql
COUNT(DISTINCT d.location_id) AS location_distinct_count,
```

and in `DeviceGroupRow.svelte` render `location_distinct_count > 1 ? 'разное' : (group.repr.location ?? '—')`, mirroring `conditionDisplay`.

## Warnings

### WR-01: Autocomplete LIKE pattern does not escape `%` / `_` / `\`

**File:** `crates/trackly-infra/src/repos/devices_sqlite.rs:771`
**Issue:** `let like_pattern = format!("{prefix}%");` builds the LIKE pattern directly from raw user prefix with no `ESCAPE` clause. A user typing `%` or `_` turns the prefix into a wildcard, so `autocomplete("name", "%")` returns essentially everything, and `_` matches any single char. The sibling `locations_autocomplete` in the service (device_service.rs:378-391) correctly escapes these and uses `ESCAPE '\\'`; this repo path does not. It is parameterized (no injection), but the matching is semantically wrong and inconsistent with the locations path.
**Fix:** Escape wildcards and add `ESCAPE '\\'` to every `LIKE ?` clause in this function, mirroring the locations service:

```rust
let escaped: String = prefix.chars()
    .flat_map(|c| if matches!(c, '%' | '_' | '\\') { vec!['\\', c] } else { vec![c] })
    .collect();
let like_pattern = format!("{escaped}%");
// ... and: format!("{col} LIKE ?1 ESCAPE '\\'")
```

### WR-02: `DevicePatch.location` clear (`Some(None)`) is silently ignored

**File:** `crates/trackly-app/src/services/device_service.rs:233-242` and dto/device.rs:130-143
**Issue:** The `DevicePatch` doc comment (dto/device.rs:127-130) and the field doc say `Some(None)` means "clear the location". The service only handles `Some(Some(ref loc))`:

```rust
if let Some(Some(ref loc)) = location_patch {
    if !loc.trim().is_empty() { ... }
}
```

`Some(None)` (explicit clear) and `Some(Some(""))` (empty string) both fall through and do nothing, while `domain_patch.location_id` stays `None`, which the SQL `COALESCE(?8, location_id)` interprets as "keep current". So a user clearing the location field gets no effect — a silent data-update failure that contradicts the documented contract. The inline comment at line 235 even admits "clear not yet supported," directly contradicting the struct doc.
**Fix:** Decide on one contract and implement it. To honor the doc, handle the clear branch by setting `domain_patch.location_id = None` *and* threading an explicit "set NULL" through the patch (the domain `DevicePatch.location_id` is a flat `Option<i64>`, so it cannot currently express "set NULL" vs "no change" — that is the root limitation, see WR-03). At minimum, fix the struct doc to state that clearing is unsupported so callers do not rely on it.

### WR-03: Domain `DevicePatch` cannot express "set field to NULL"

**File:** `crates/trackly-core/src/domain/devices.rs:31-43`, mapping at dto/device.rs:150-188
**Issue:** The DTO `DevicePatch` uses `Option<Option<String>>` to distinguish "no change" / "set NULL" / "set value", but the `From<DevicePatch>` impl collapses it into the domain's flat `Option<String>` (e.g. line 162-164 assigns `p.inventory_no = inner` where `inner: Option<String>`). The repo then uses `COALESCE(?3, inventory_number)` (devices_sqlite.rs:193), which treats `NULL` as "keep". Net effect: `Some(None)` (explicit clear) and `None` (no change) become indistinguishable at the SQL layer — you can never clear `inventory_no`, `serial_no`, `model`, `specs`, `kit`, or `state` once set. This is a latent data-integrity gap across all nullable fields, not just location.
**Fix:** Either drop the `COALESCE` pattern in favor of building the `SET` clause dynamically from the fields actually present in the patch, or change the domain patch nullable fields to carry sentinel "clear" semantics. This is a structural fix; flag for follow-up if out of phase scope, but the `Option<Option<T>>` DTO shape is currently a lie.

### WR-04: Location-field keyboard navigation can select the wrong item after re-fetch

**File:** `ui/src/features/devices/DeviceAutocompleteField.svelte:69-71, 217-259, 327-360`
**Issue:** For `field === 'location'`, `allItems = [...suggestions, ...allLocationSuggestions]` and keyboard nav indexes into `allItems`. The dropdown renders `suggestions` first (indices `0..suggestions.length`) then `allLocationSuggestions` at offset `suggestions.length`. The two arrays are populated by two separate awaits (lines 119 and 122); `suggestions` is set first, then `allLocationSuggestions` after a second await. Between those awaits `allItems` is recomputed, and `activeIndex` is only reset to `-1` after both complete (line 133). If a user presses ArrowDown in the brief window after `suggestions` resolves but before `allLocationSuggestions` resolves, `activeIndex` can point past the then-current `allItems.length`, and `select(allItems[activeIndex])` (line 239) may read `undefined`, calling `onChange(undefined)`. Low-probability but reachable under slow LAN fetches.
**Fix:** Reset `activeIndex = -1` immediately when a new fetch begins (before the awaits), and guard `select` against `allItems[activeIndex] === undefined`.

### WR-05: Dropdown `onmousedown` index and `select` ignore the live filter in ActFormItemsTable

**File:** `ui/src/features/acts/ActFormItemsTable.svelte:217-236`
**Issue:** The dropdown re-filters `suggestionsByRow[idx]` inline (`.filter((g) => !g.ids.some(...))`) at render time (line 219), but `suggestionsByRow[idx]` was *already* filtered at fetch time (line 117-118) against `getSelectedIds(idx)`. Re-filtering on every render against `getSelectedIds(idx)` recomputes a `Set` each render (also a minor perf smell) and, more importantly, the visible list can diverge from the stored `suggestionsByRow[idx]` if another row's `picked`/`group_ids` changes without a re-fetch of this row — leading to a stale dropdown where clicking an option calls `pickGroup` with a group that is now claimed by another row. There is no post-pick validation that the group's ids are still free.
**Fix:** Filter once into a `$derived` per-row visible list and validate in `pickGroup` that none of `g.ids` are in `getSelectedIds(idx)` before committing; otherwise drop the selection and re-fetch.

### WR-06: `exportCsv` device count is derived by splitting on newlines — wrong for quoted multiline cells

**File:** `ui/src/features/devices/DevicesPage.svelte:205`
**Issue:** `csvContent.split('\n').filter(...).length - 1` counts data rows by newline. The CSV is produced by the Rust `csv` writer which quotes fields containing newlines (e.g. a multiline `specs`/`notes` value). A single device with an embedded newline in `specs` inflates the count, so the success toast reports more devices than were exported. The BOM-prefixed first line is also counted as content, but the `- 1` only subtracts the header, so a device whose first cell starts right after the BOM is fine — the newline-in-cell case is the real defect.
**Fix:** Have `export_csv` return a row count alongside the CSV (or have the caller use the known result length), instead of re-parsing the serialized CSV in the UI.

### WR-07: `$effect` in DevicesPage double-fires refresh and races with search

**File:** `ui/src/features/devices/DevicesPage.svelte:108-120, 125-129`
**Issue:** `refresh()` and `refreshCounts()` are called from three places: the `$effect` (line 113-114, reacting to `statusFilter`/`grouped`), `onMount` (line 118-119), and `handleSearchChange` (line 127-128). On initial render both the `$effect` and `onMount` fire, issuing duplicate `list`/`statusCounts` requests. More importantly, `handleSearchChange` calls `refresh()` directly while the `$effect` may also be mid-flight after a `statusFilter` change; there is no request-sequencing (no abort / latest-wins), so a slow earlier response can overwrite a faster later one, showing stale results.
**Fix:** Drop the redundant `onMount` (the `$effect` already runs on mount), and add a monotonically-increasing request token so only the latest `refresh()` result is applied.

### WR-08: `condition_distinct_count` counts NULL inconsistently — all-NULL groups report 0, never «разное» but also masks mixed NULL/value

**File:** `crates/trackly-infra/src/repos/devices_sqlite.rs:943, 977`
**Issue:** `COUNT(DISTINCT d.condition)` ignores NULLs. A group containing devices with `state = NULL` and `state = "Новое"` yields `condition_distinct_count = 1` (only the non-NULL distinct value counts), so the UI shows "Новое" instead of «разное», hiding the fact that some devices have no condition set. This is a correctness gap in the very feature this phase added (the condition column / mixed-group indicator).
**Fix:** Count NULL as a distinct bucket, e.g. `COUNT(DISTINCT d.condition) + (CASE WHEN COUNT(*) FILTER (WHERE d.condition IS NULL) > 0 THEN 1 ELSE 0 END)`, or `COUNT(DISTINCT COALESCE(d.condition, '\x00__null__'))`. Add a test for the mixed NULL/value case.

## Info

### IN-01: Duplicated status-label / status-variant maps across three components

**File:** `ui/src/features/devices/DeviceListRow.svelte:32-44`, `ui/src/features/devices/DeviceGroupRow.svelte:61-72`, and the Rust `status_id_to_name` (device_service.rs:912-919)
**Issue:** `STATUS_LABELS` / `STATUS_VARIANTS` are copy-pasted between `DeviceListRow` and `DeviceGroupRow`, and the same 1..4 → label mapping is independently hardcoded in Rust. Three sources of truth for the same enum invites drift.
**Fix:** Extract a shared `statusMeta.ts` module for the UI maps; derive the Rust labels from the seeded `device_statuses` table rather than a hardcoded match.

### IN-02: Duplicated SELECT column list between `SELECT_DEVICES` and `search_fts`

**File:** `crates/trackly-infra/src/repos/devices_sqlite.rs:30-37` vs `736-742`
**Issue:** `search_fts` re-spells the entire column list that `SELECT_DEVICES` already defines, and both must stay in lockstep with `from_row` (line 41-60) by positional index. Any column reorder silently corrupts `from_row` mapping in one path. The `list_grouped` manual SELECT (line 934-999) has the same positional-coupling risk.
**Fix:** Reuse `SELECT_DEVICES` in `search_fts` (append the FTS JOIN/WHERE), and add a comment block or compile-time guard tying column order to `from_row` indices.

### IN-03: `AutocompleteField::sql_column()` returns a misleading value for `Location`

**File:** `crates/trackly-core/src/domain/devices.rs:161-172`
**Issue:** For `Self::Location` the method returns `"location_id"` with a comment saying "this fallback is unused." Returning a plausible-looking column name for a variant that must never reach this code is a footgun; a future caller who forgets the `is_location()` check would silently query `location_id` instead of erroring.
**Fix:** `unreachable!("Location resolved via JOIN; call is_location() first")` or return a `Result`/panic for the `Location` arm.

### IN-04: Dead CSS rule `.hint-warn` in ActFormItemsTable

**File:** `ui/src/features/acts/ActFormItemsTable.svelte:419-423`
**Issue:** `.hint-warn` is defined but no element in the template uses it. Dead style; svelte may warn about unused selectors.
**Fix:** Remove the rule or wire up the warning element it was meant for.

### IN-05: `makeEmpty()` omits optional fields, relying on `undefined` semantics

**File:** `ui/src/features/acts/ActFormItemsTable.svelte:69-71`
**Issue:** `makeEmpty()` returns a `FormItemRow` without `has_serial`, `stock_available`, `group_ids`. These are optional in the interface, so it type-checks, but `qtyMax`/`handleQtyInput` rely on the exact `undefined` vs number distinction. It works today but is implicit; an explicit initialization documents intent.
**Fix:** Initialize the optional fields explicitly (`has_serial: false`, `stock_available: undefined`, `group_ids: undefined`) or add a comment that they are intentionally absent until a device is picked.
