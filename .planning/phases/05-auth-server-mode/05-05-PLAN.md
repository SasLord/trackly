| authStore→UI gating | authStore.user drives UI display; source of truth for security is server-side session |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-20 | Info Disclosure | password in LoginPage form state | mitigate | Password field type="password" (browser masking); form $state not persisted to localStorage; cleared on submit completion |
| T-05-21 | Elevation of Privilege | UI-only auth gating (no server check) | accept | Sidebar filtering is UX-only per D-RBAC-03; server-side authorize() is the security source of truth (enforced in Plan 04) |
| T-05-22 | Spoofing | authStore manipulated via browser console | accept | authStore manipulation only affects UI display; all mutations still go through server authorize() which checks session |
| T-05-23 | Denial of Service | First-run wizard bypass (direct API call) | mitigate | bootstrap check in auth_status on every load; server only allows users_create with admin role from trusted-admin (Tauri) context; HTTP users_create with no session → 401 |
| T-05-24 | Info Disclosure | cert fingerprint displayed in plain text | accept | Fingerprint is intentionally displayed for user verification of self-signed cert (D-Server-04); not sensitive |
| T-05-25 | Elevation of Privilege | desktop lock toggle UI bypassed | accept | UI toggle calls desktop_set_lock Tauri command which calls authorize(ManageSettings) server-side; UI bypass does not affect security because lock flag is read from DB at boot time |
