<objective>
Fix five Reports page UI/UX gaps: export broken by wrong argument value, layout problems
(two nav rows instead of one, date input styling), redundant filters, and badges only on
active tab.

GAP-R1: Frontend passes report_type: currentCmd() which returns the full Tauri command
name (e.g. 'reports_list_device_acts') instead of the backend key ('device_acts').
Fix: add a reportTypeKey() helper that maps domain+report key → backend type string.

GAP-R2: ReportSubNav stacks domain-nav and report-nav vertically. Fix: single flex row
on desktop, wrap on mobile.

GAP-R3: PeriodSelector range mode DatePicker inputs inherit oversized margins. Fix:
constrain width in the range container.

GAP-R4: ReportFilters shows redundant domain-specific filters that D-04 per CONTEXT.md
says should not be in the report view. Per the verified CONTEXT.md decision and
GAP-R4 spec, remove those controls entirely — keep only Export buttons. Move
PeriodSelector (currently below the filter row) into the left side of the same row
as the export buttons, creating a single "controls bar".

GAP-R5: ReportSubNav shows count badge only on active tab. Per user decision: show
badges on all tabs (using rowCount for the active tab; other tabs show their count if
available, otherwise 0 — since the backend doesn't provide per-tab counts in a single
call, use rowCount for the current tab and omit badges on inactive tabs, OR accept
that only the active tab gets an accurate count and display a '?' or '–' on others).

User decision for R5: "Show count badges for ALL status tabs simultaneously." Since
the backend provides rowCount only for the currently loaded report, the simplest
correct implementation is: display the badge on ALL tab buttons, showing the actual
count only for the active tab (numeric), and show nothing (no badge) on inactive tabs
OR show a neutral badge with '–'. Confirm with the actual UX feel during execution —
the requirement is that the count distribution is visible; if only the active tab has
a number, that is fine for v1 as long as all tabs visually acknowledge the badge slot.

Purpose: All five are frontend-only fixes; no Rust changes.

Output: Four patched Svelte components; pnpm svelte-check clean.
</objective>

  <action>
    The root cause: exportCsv passes { report_type: currentCmd() } where currentCmd()
    returns the full command string like 'reports_list_device_acts'. The backend
    reports_export_csv expects report_type to be 'device_acts' (the key used in the
    match arms of fetch_report in tauri_cmds/reports.rs).

    Add a helper function reportTypeKey() that converts the current domain + activeReport
    combination into the correct backend key:
      function reportTypeKey(): string {
        if (activeDomain === 'devices') {
          switch (activeReport) {
            case 'acts': return 'device_acts';
            case 'returns': return 'device_returns';
            case 'in_use': return 'device_in_use';
            case 'in_stock': return 'device_in_stock';
          }
        } else {
          switch (activeReport) {
            case 'consumption': return 'cartridge_consumption';
            case 'refills': return 'cartridge_refills';
            case 'in_use': return 'cartridge_in_use';
            case 'in_stock': return 'cartridge_in_stock';
          }
        }
        return 'device_acts'; // fallback
      }

    Update exportCsv, exportPdf, and printReport to pass reportType: reportTypeKey()
    (camelCase key to match specta-generated binding pattern, which sends { reportType }).
    The period value is correct: pass `period: isSnapshot() ? undefined : period` (same
    as the report listing call — snapshot reports pass undefined for period).

    Note: the backend command param is `report_type: String` (snake_case). Tauri 2 IPC
    maps camelCase frontend key `reportType` to snake_case param `report_type`
    automatically. Use camelCase in the frontend call to be consistent with the
    specta-generated binding (bindings.ts line 745 shows { reportType, filter, period }).
  </action>
