## Справочное: точное поведение вью `place_effective_variant` в обоих состояниях WR-02

Это ключевой результат плана для Фазы 40 — поведение проверено на реальной SQLite-БД
(`test_db()` с применённой V039), а не выведено из чтения SQL.

**WR-02a — soft-deleted предок.** Дерево «Здание А» ← «2 этаж» ← «214», org-дефолт `ends`,
ни одного override:

| Состояние | Корень | Средний уровень | Живой лист |
|---|---|---|---|
| всё живое | `Some("ends")` | `Some("ends")` | `Some("ends")` |
| средний уровень soft-deleted | `Some("ends")` | **строки во вью нет** | **строки во вью нет** |

То есть исчезает не только удалённое место, но и его ЖИВОЙ потомок: рекурсивный член
фильтрует `p.deleted_at_utc IS NULL`, обход обрывается на промежуточной строке
(`variant IS NULL AND parent_id IS NOT NULL`), а терминальный предикат
`variant IS NOT NULL OR parent_id IS NULL` именно такие строки и отбрасывает.
Форма отказа — **отсутствие строки** (`query_row` → `QueryReturnedNoRows`).

**WR-02b — нет строки `place_path_variant` в `app_settings`.** Строка во вью
**присутствует** (`SELECT COUNT(*) ... = 1`), но колонка `effective_variant` равна **NULL**:
`COALESCE(variant, (SELECT value FROM app_settings WHERE key = ...))` отдаёт NULL при пустом
подзапросе. Форма отказа — **NULL в колонке**, а не отсутствие строки.

Практический вывод для читателей (план 04, WR-01): деградация обязана быть двухуровневой —
одного `.optional()` или одного `Option<String>` по отдельности недостаточно, состояния разные.

## Decisions Made

- **Миграция V039 не правится** — решение фазы, подтверждено проверкой на HEAD: ни один
  путь записи не проставляет `places.deleted_at_utc` (единственный `UPDATE places SET
  deleted_at_utc` во всём дереве — в тестовом файле `acts_place_path_short.rs:146`), места
  удаляются только `delete_hard` и только пустые; ключ `place_path_variant` сеется V039 и
  дальше пишется upsert'ом. Deviation-триггер плана НЕ сработал.
- **Ветка `places.kind` оставлена строгой** — у неё есть CHECK constraint в схеме, её
  строгость обоснована; ослабление касается только столбца без CHECK.
- **`place_id` в `warn!` читается через `row.get(0).unwrap_or(-1)`** — логирование не должно
  само становиться источником `Err` в маппере строки.
