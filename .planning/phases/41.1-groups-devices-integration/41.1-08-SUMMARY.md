# Phase 41.1 Plan 08: Rust-гейт хардкода статусов устройств Summary

Гейт `device_status_vocabulary_gate` сканирует все `crates/*/src` и краснит на подписи статуса устройства, `match` по `status_id` и числовой id статуса в Rust и SQL; освобождения самоинвалидируются, гейт доказан мутациями копии реального дерева, реального файла на диске и дерева до фазы.

## Область гейта и правила

Область: все `crates/*/src/**/*.rs`, список выводится обходом (в тесте проверяется, что новый файл с хардкодом краснит). Корень можно подменить переменной `VOCAB_GATE_ROOT` (копия дерева для мутаций, дерево до фазы).

Порядок обработки файла: (1) вырезание блоков `#[cfg(test)]` целиком; (2) лексер: отбрасывает `//`, `///`, `//!`, вложенные `/* */`, разбирает обычные, сырые и байтовые строки, отличает `'"'` и времена жизни `'a` от строк; `//` внутри строки хвост не обрезает.

| Правило | Что ловит |
|---|---|
| R1 | литерал, равный одной из семи подписей (в SQL: подпись в одинарных кавычках). Многословные подписи без учёта регистра, однословное «Списано» только заглавной |
| R2 | `match` / `matches!` по выражению с `status_id` |
| R3 | в коде: `status_id: N`, `== N`, `!= N`, `= N`, `N == x.status_id`. Проверка валидности `status_id <= 0` не флагается |
| R4 | в SQL-литерале: `status_id = N`, `<> N`, `IN (N, ...)`; в литерале с `device_statuses` ещё `id = N` |

Машинные code (`на_складе`, `в_работе`, `на_ремонте`, `на_списание`, `списано`) разрешены.

## Освобождения (полный перечень, собран запуском гейта по репозиторию)

Каждая запись: файл + правило + точный текст срабатывания (если задан) + подстрока контекста + точное число + причина (не короче 20 символов, проверяется). Лишнее вхождение, пропавшее вхождение, а также запись без единого срабатывания краснят гейт.

Решение по `printers.rs:171`: область гейта НЕ сужена до `device_service.rs`, сайт освобождён точной записью. Это единственный сайт устройств, где остаётся числовой статус. Он не переведён на code: сайт вне файлов плана, правка продакшен-пути SNMP-приёма без плана не допускается. Когда его переведут на code, запись станет устаревшей и гейт потребует её удалить. Это явный долг для плана 20 или следующей правки (перевод на поиск `на_складе` через справочник).

`type_id` (1 = Устройство, 2 = Расходник) гейт не трогает: он ищет только `status_id`.

## Находки при построении гейта от репозитория (грепом инвентарь был неполон)

1. `group_service.rs:60`: `STATUS_CODE_WRITTEN_OFF = "списано"` — нижний регистр однословной подписи совпал с машинным code. Решение: для однословных подписей регистр различается.
2. `cartridges_sqlite.rs:1850`: SQL собран `format!` на константе `SELECT_CARTRIDGES`, слова `cartridges` в литерале нет. Освобождение по контексту дополнено отдельной записью.
3. Мой первый вариант проверки «неузнанной формы» сам принимал `fn ... {` как блок; тест на «неузнанную форму» исправлен на форму, которая правда не распознаётся.

## Отступления от плана

1. **[Rule 2 - строже плана] R3 и R4 сверх R1/R2.** Без них числовой id (`status_id: 3`, SQL `status_id = 3`) возвращался бы зелёным, а брифинг явно требовал решить судьбу `printers.rs:171`.
2. **[Rule 2] Лексер вместо `split("//")`.** Прежний приём из `group_write_sites.rs` обрезает строки с `//` внутри (URL) и не знает про блочные комментарии.
3. **[Rule 2] Вырезание блока тестового модуля, а не хвоста после первого маркера.** В `act_service.rs` два тестовых модуля; хвостовая обрезка скрыла бы продакшен-код между и после них.
4. **Одна задача-коммит вместо двух** (см. выше).
5. Файл после `rustfmt` длиннее оценки плана (форматирование разворачивает длинные строки): это только форма.
