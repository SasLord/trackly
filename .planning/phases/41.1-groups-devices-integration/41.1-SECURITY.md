> Per-phase security contract: threat register, accepted risks, and audit trail.

Реестр заведён на этапе планирования: `<threat_model>` присутствует во всех 33 планах фазы
(`register_authored_at_plan_time: true`), поэтому аудит работал в режиме проверки митигаций,

## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| миграция → пользовательская БД | существующая БД организации обновляется на месте при первом запуске новой версии | учётные строки устройств, актов, групп |
| клиент → команда/роут | один и тот же вызов доступен из Tauri-команды и из `/api/v1/*` по локальной сети | полезная нагрузка запроса, роль вызывающего |
| сервер → UI | ответы `list` / `listGrouped` могут прийти не в порядке запросов | состав списков и якорей |
| сервис → БД | построение SQL в сервисном слое | фильтры, идентификаторы, флаги |
| сервис → сеть (SNMP) | поллер обращается к принтеру по IP с сохранённой community | community-строка, адрес устройства |
| сообщение сервера → DOM / тост | текст ошибки и имена сущностей попадают в разметку | имена групп, сообщения об ошибках |
| вызывающий код → `pushToast` | тост принимает ссылку `href` | навигационная ссылка |
| пользовательский CSV → импорт | внешний файл разбирается и выгружается обратно | произвольный текст (риск формул) |
| employee-сессия → ReadData-команда | сотрудник с минимальной ролью дёргает справочные команды | справочники статусов и подписей |
| репозиторий → публичный GitHub | код, тесты, фикстуры и `.planning/`-артефакты уходят в публичную историю | тестовые данные, артефакты планирования |
| человек ↔ агент | исполнитель отчитывается о пройденных гейтах | утверждения о зелёности прогонов |

## Раунд исправлений 18.10.2026

Аудит дал шесть вердиктов PARTIAL. Две из них — настоящие дыры в коде; закрыты в этом же
проходе. Остальные четыре приняты как долг и занесены в журнал ниже (AR-23…AR-26).

### T-41.1-22-02 — опрос SNMP по требованию обходил мягкое удаление (закрыта)

Периодический `poll_all` берёт выборку из отфильтрованного `repo.list`, а `poll_single`
резолвил переданный вызывающим id через намеренно неотфильтрованный `repo.get` (он такой,
чтобы не ломались детальная карточка и возврат устройства, D-37). Итог: держатель
`ReadPrinters`, передав id скрытого принтера в `printers_refresh` (оба транспорта), заставлял
поллер отправить SNMP-запрос с сохранённой community на адрес уже удалённого устройства.
Из UI строка недоступна, поэтому severity low — но путь был достижим.

Закрытие: в порт добавлен `PrinterRepository::get_live` — тот же `SELECT`, но с
`AND d.deleted_at_utc IS NULL`; `poll_single` резолвит id только через него. `get` оставлен
неотфильтрованным, карточка и возврат не затронуты.

Доказательство, а не утверждение: тест `printers_soft_delete_on_demand_poll_skips_deleted`
(`crates/trackly-app/tests/printers_soft_delete_visibility.rs`). Проверен на вакуумность —
мутация `get_live` → `get` в `poll_single` даёт `left: 1, right: 0`, то есть скрытый принтер
действительно опрашивался до правки; остальные 7 тестов файла при той же мутации остаются
зелёными, значит гарантию несёт именно новый тест. После отката мутации 8/8 зелёные.

### T-41.1-G29-01 — гонка поколений в `loadAnchorMembers` (закрыта)

`refresh()` и `reloadExpandedAnchors()` отбрасывают устаревшие ответы по номеру поколения,
но `loadAnchorMembers` писала `anchorMembers` после `await` на той же границе без всякой
проверки, и её ветка `catch` звала `failAnchor` безусловно. Быстрое «раскрыть / свернуть /
раскрыть» одного якоря или раскрытие на фоне перечитывания позволяли старому ответу лечь
поверх свежего состава.

Закрытие: введено поколение на якорь (`anchorLoadSeq` + `bumpAnchorLoad`). `loadAnchorMembers`
снимает своё поколение и снимок `anchorsSeq` ДО первого `await`, а каждая запись состояния
после `await` — и успешная, и `failAnchor` в `catch` — проходит через охрану `current()`,
сверяющую три условия: своё поколение якоря, неизменность поколения перечитывания и то, что
якорь всё ещё раскрыт. `reloadExpandedAnchors` двигает поколение всех перечитываемых якорей,
иначе отставший одиночный ответ лёг бы поверх свежего состава.

Удержание: правило `[H6]` в `ui/scripts/check-device-list-mode.mjs`. Оно чувствительно к
порядку (перестановка охраны и записи краснеет) и требует СВОЕЙ охраны для каждой записи —
иначе страж успешной ветки «прикрывал» бы голый `failAnchor(` в `catch`. Девять мутантов
добавлены в selftest (структурных мутантов 40 → 49), обе половины правила проверены мутацией
настоящего `DevicesPage.svelte`, а не только фикстуры: снятие охраны `catch` и снятие
`bumpAnchorLoad` в перечитывании дают FAIL.
