# Фаза 41.1: отчёт о ревью кода

**Проверено:** 2026-10-17
**Глубина:** deep (сквозной разбор вызовов Rust и Svelte; тесты и гейты не перезапускались, как оговорено в задании)
**Файлов:** 51 (основные) из диффа `d54e9512..HEAD` (crates/, ui/, migrations/). Тесты и скрипты-гейты читались выборочно, только как контекст.

## Резюме

Блокирующих дефектов (BLOCKER) не найдено. Серверная часть сделана аккуратно: охраны якоря стоят до записи и внутри одной транзакции writer'а на всех обозначенных путях, пять SQL-источников строки устройства и `search_fts` согласованы по `status_code` и `origin_group_id`, миграции V047 и V048 безопасны (только `ADD COLUMN`, `UPDATE`, `INSERT`, `CREATE INDEX`). Все существенные находки лежат на стороне UI. Три из них являются вариантом пункта 4 задания: непроизводные, ранее существовавшие механизмы (эффект «место хранения → статус», `td onclick` у принтера, наследование стилей `td.cell` модалками) частично обесценивают новое поведение.

Что проверено и признано корректным, чтобы не перепроверять:

- **Охраны якоря.** `DeviceService::delete_soft` (`device_service.rs:1130-1146`): охрана после чтения `before`, до `delete_soft_in_tx`, в той же транзакции. `release_device_in_tx` (`group_membership.rs:27-45`): охрана первым оператором, раньше `remove_device_in_tx`, закрывает акты, restore и удаление устройства. `remove_devices` (`group_service.rs:1012-1032`): охрана раньше `release_device_in_tx` и только для якоря ЭТОЙ группы. `delete_group` (`group_service.rs:678-693`): проверка деталей разбора раньше `DELETE FROM groups`. Откат при ошибке гарантирован: `tx` не коммитится и уничтожается при `return Err`.
- **`create_group` с источником.** Все проверки источника (удалён, не «Устройство», «Списано», «На списание», уже в группе) стоят до `insert_group_in_tx`. Якорь и смена статуса выполняются в той же транзакции. Событие несёт `device_ids = [sid]` и место источника, что соответствует реальным изменениям. Правило «происхождение пишется, только пока NULL» реализовано условием `WHERE origin_group_id IS NULL` (`groups_sqlite.rs:305-316`).
- **Чтение.** `SELECT_DEVICES`, `search_fts`, `get_in_tx`, `list_by_ids` читают 17-й и 18-й столбцы одинаково. В `list_grouped` флаги применены и во внешний `WHERE`, и в подзапросы `d2`. `search_fts` флагов не принимает намеренно (`hidden_member_count = 0`). `export_csv` явно сбрасывает все четыре флага.
- **Обратная совместимость CSV.** Старая подпись «На ремонте» отображается псевдонимом на `code = на_ремонте`; сопоставление регистронезависимо через Rust `to_lowercase()`; round-trip всех шести статусов покрыт тестами.
- **Размеченные принятые решения** (`D-20` «считаем по членству, зазор осознанный» и т. п.) повторно не фиксируются.
- **Приватность.** В добавленных строках нет реквизитов организации и ФИО (проверено grep по ИНН/КПП/ОГРН/«ООО»/e-mail/телефонам).

## Предупреждения

### WR-01: эффект «место хранения → статус „На складе“» затирает статус якоря и детали разбора (пост-фактум не откатывается)

**Файл:** `ui/src/features/devices/DeviceFormBody.svelte:432-448` (эффект), `:528-555` (загрузка `storagePlaceIds` и `membership`)
**Проблема:** эффект не тронут фазой, но фаза превратила его в источник порчи данных. Он работает и в режиме правки (`target !== null`), и пока `membership === null` условие `!lockedByGroup` истинно. Две загрузки в `onMount` идут параллельно: `cartridge_storage_place_ids` и `groups.forDevices([target.id])`. Эффект защищён от «закрытия» статусом только после того, как придёт второй ответ, а откатить уже записанный `statusId` нечем.

**Сценарий:** создаём группу «На разбор» от устройства, стоящего на складе. Сервер ставит устройству статус «На списание» и делает его якорем; место группы = место склада. Открываем якорь на правку (меню → «Редактировать»), чтобы поправить, например, модель. Ответ `storagePlaceIds` приходит первым (запрос отправлен первым), `isStoragePlace` становится истинным, `storageStatusSuggested` по умолчанию `true`, `lockedByGroup` ещё `false` → `statusId` перезаписывается на «На складе». Затем приходит `membership`, `lockedByGroup` становится `true` и чекбокс скрывается, но `statusId` уже «На складе». Пользователь не может снять галочку (она скрыта) и при сохранении записывает якорю разбора статус «На складе». То же самое с любым устройством в статусах «В ремонте» и «На списание», стоящим на складе: эффект переводит его в «На складе» без возможности отказаться, пока форма не пройдёт гонку в нужную сторону.

**Исправление:** (1) не применять неявную смену статуса в режиме правки вовсе (`target === null` в условии эффекта) либо применять только по явному действию пользователя (смена места или клик по чекбоксу); (2) независимо от этого дождаться завершения загрузки `membership` до применения эффекта:

```ts
let membershipLoaded = $state(target === null || readonly);
// ... в .then/.catch/.finally загрузки membership: membershipLoaded = true;
$effect(() => {
  const storageId = statusIdByCode('на_складе');
  if (target === null && membershipLoaded && !readonly && !lockedByGroup &&
      isStoragePlace && storageStatusSuggested && storageId !== null) {
    statusId = String(storageId);
  }
});
```

### WR-02: клики внутри модалок меню строки принтера всплывают в `td onclick` и перевыбирают принтер

**Файл:** `ui/src/features/printers/PrinterListRow.svelte:105-107, 136, 150-160`
**Проблема:** `DeviceRowMenu` смонтирован внутри первой ячейки, у которой висит `onclick={handleClick}` (выбор принтера). `Modal` не портальный (рендерится на месте), поэтому каждый клик в «Просмотр», «Добавить в группу», «Создать группу», подтверждении удаления всплывает до `td` и вызывает `onSelect(printer.id)`. Для `keydown` охрана `isOwnKeyEvent` поставлена, для `click` нет. Асимметрия при том, что фаза заявляет единый принцип «охрана первым оператором в обработчиках строки».

**Сценарий:** выбран принтер A. Правый клик по принтеру B → «Просмотр»; любой клик по просмотру B (в том числе по кнопке «Закрыть» модалки) выбирает B и подгружает панель деталей B, хотя пользователь выбирал только действие. В «Добавить в группу» клик по выпадающему списку делает то же. Если принтер потом удалён/добавлен в группу, `handleMenuChanged` дополнительно обнуляет выбор, и пользователь теряет контекст.

**Исправление:**

```ts
function handleClick(e: MouseEvent) {
  if (isRowOverlayEvent(e.target)) return;
  onclick();
}
// <td ... onclick={handleClick}>
```

Те же две строки нужны у `td.cell-status` (`:162`) и `td.cell-toner` (`:165`), если модалка может оказаться внутри них; сейчас она в первой ячейке, поэтому достаточно первой. Добавить в гейт `check-device-row-menu.mjs` правило «обработчик click строки принтера начинается с `isRowOverlayEvent`».

### WR-03: корневая причина трёх найденных вручную UI-дефектов не устранена, остальные модалки меню страдают так же

**Файл:** `ui/src/features/devices/DeviceListRow.svelte:164-176` (меню в `td.cell-actions`), `:186-196` и `:241-245` (стили `.cell`/`.cell-actions`); `ui/src/features/printers/PrinterListRow.svelte:150` (меню в `td.cell-name`)
**Проблема:** `DeviceRowMenu` рендерит свои `Modal` (`GroupFormModal`, `AddToGroupModal`, `PlaceEntityViewModal`, подтверждение удаления) прямо внутри `<td>`. Модалка наследует по каскаду `white-space: nowrap` от `.cell` и `text-align: center` от `.cell-actions`. Принятые пробелы («callout переполняет `GroupFormModal`», «разное выравнивание подписей в просмотре и правке») являются симптомами именно этого наследования. В `DeviceRowMenu.svelte` локально сброшены стили только у `.confirm-body` (`white-space: normal`, `text-align: center`), а у остальных модалок такого сброса нет: в `AddToGroupModal` (`.callout`, `.empty-body`, `.field-error` с длинными серверными сообщениями вида «Устройство «…» уже входит в группу «…». Сначала выведите его из состава.» и путём места), в `GroupFormModal` (`.field-error`, `.field-hint`), в формах просмотра и правки, открываемых из просмотра. Каждый новый текст модалки будет ломаться так же, а правка по месту (как с `.confirm-body`) воспроизводит класс дефектов вместо его устранения.

**Исправление:** убрать наследование у корня, а не лечить каждый блок: в `Modal.svelte` на `.modal-backdrop` (или `.modal`) задать `white-space: normal; text-align: start; font: inherit; max-width: none; overflow: visible`, либо монтировать `DeviceRowMenu`-модалки через `use:portal` (как ActionMenu). Тогда дефекты №2 и №3 из принятого списка закрываются одним изменением, а локальные сбросы вроде `.confirm-body` можно удалить.

### WR-04: DevicesPage.refresh() не защищён от гонки ответов; в режиме свёртки фаза удвоила запросы

**Файл:** `ui/src/features/devices/DevicesPage.svelte:114-158` (refresh), `:259-272` (эффект и `onMount`)
**Проблема:** `refresh()` вызывается из `$effect` (при смене `statusFilter`/`grouped`), из `onMount`, из `handleSearchChange`, из `onSaved`/`onDelete`. Номера поколения нет, поэтому последним записывает состояние тот ответ, который пришёл последним, а не тот, что запрошен последним. В режиме свёртки фаза добавила второй вызов (`Promise.all([listGrouped, list(anchors)])`), что делает такой запрос заметно длиннее плоского.

**Сценарий:** включена «Свернуть одинаковые», пользователь быстро снимает галочку. Запрос A (grouped) ещё в полёте, запрос B (flat) возвращается первым. Затем приходит A и записывает `groups = …; items = []; total = 0; anchorItems = …`. При `grouped === false` `DeviceList` читает `items` и показывает «Устройств пока нет», хотя на сервере устройства есть, до следующего обновления. Аналогично `reloadExpandedAnchors()` из устаревшего `refresh` перезапишет `anchorMembers` устаревшим составом.

**Исправление:**

```ts
let refreshSeq = 0;
async function refresh() {
  const seq = ++refreshSeq;
  loading = true;
  try {
    /* ... await ... */
    if (seq !== refreshSeq) return; // устаревший ответ
    /* присвоения items/groups/total/anchorItems/hiddenMemberCount */
    void reloadExpandedAnchors();
  } finally {
    if (seq === refreshSeq) loading = false;
  }
}
```

Заодно убрать двойной первый вызов (`onMount` + эффект, который выполняется сразу после монтирования).

### WR-05: экспорт CSV тихо обрезается до 200 устройств; комментарий в коде утверждает обратное

**Файл:** `crates/trackly-app/src/services/device_service.rs:1815` (комментарий) и `:1834-1837` (`limit: 1_000_000`), `crates/trackly-infra/src/repos/devices_sqlite.rs:821` (`page.limit.min(200)`)
**Проблема:** (дефект существовал до фазы, но он находится в функции, которую фаза изменила, и прямо подрывает заявленный принцип «выгрузка по ВСЕМ устройствам: отчёт не должен терять детали», который фаза записала рядом, `device_service.rs:1826-1827`.) `export_csv` зовёт `repo.list`, а `list` ограничивает `limit` числом 200. Комментарий «bypasses the 200-item pagination cap by calling the repo directly» неверен: ограничение стоит в самом репозитории.

**Сценарий:** в базе 450 устройств, пользователь нажимает «Экспорт CSV» — файл содержит 200 строк, без ошибки и без предупреждения. Тест `export_list_all_created_devices` создаёт малое число устройств и этого не ловит.

**Исправление:** в репозитории выделить метод без потолка (`list_all(conn, filter)`) либо выгружать циклом по страницам по 200 до `total`; обновить комментарий; добавить тест на 201+ строку.
