## Что происходит с CSV, где остался «На ремонте» (правило 5)

Файл **принимается**: подпись «На ремонте» (в любом регистре) сопоставляется статусу с code `на_ремонте`, который после V047 называется «Ожидает ремонта». Порядок разбора подписи: (1) совпадение с текущим именем из справочника без учёта регистра; (2) псевдоним «на ремонте»; (3) иначе статус по умолчанию `на_складе`. Покрыто тестом `import_accepts_legacy_repair_label_as_alias` (три регистра). Подпись «Ожидает ремонта» тоже даёт `на_ремонте`. Пустая и неизвестная подпись ведут себя как раньше (`на_складе`), тест `import_unknown_or_empty_status_falls_back_to_in_stock`.

Побочное следствие, не новое поведение, а свойство справочника: если администратор переименует статус, старая подпись в CSV перестанет совпадать и импортируется как «на складе» (тест `import_follows_dictionary_rename`). Раньше этого не было, потому что имена были зашиты в код.

## Как перечислены чтения статуса бэкендом (правило 6)

Не по одному идентификатору, а тремя заходами по `crates/*/src/**/*.rs`:

1. SQL, обращающийся к `device_statuses` (кроме комментариев): 12 файлов.
2. Числовые литералы статуса: `status_id = N`, `status_id: N`, `!=`/`==` с числом.
3. Русские имена и коды статусов в строковых литералах.

Результат после плана:

- Чтение статуса по code (корректно): `act_service.rs`, `acts_sqlite.rs`, `group_service.rs` (`STATUS_CODE_*`), `report_service.rs` (фильтры по code), `device_service.rs` (фильтр `status_in` по code, `list_statuses`, `StatusLookup`), `devices_sqlite.rs` (`status_code`).
- Чтение имени статуса только для показа (не сопоставление): JOIN `device_statuses` в `report_service.rs` (2 места), `number_template_service.rs`, `places_sqlite.rs` (2), `groups_sqlite.rs`.
- Картриджи (`cartridge_statuses`, `c.status_id = 1/2/3/4`) — отдельный справочник, D-07, не трогались; `dashboard_service.rs:121` (`ORDER BY s.name` для картриджей) оставлен по той же причине.

## Остаточные чтения статуса по имени или числу — для плана 08

В `device_service.rs` после плана (весь файл, кроме комментариев):

- `STATUS_CODE_DEFAULT = "на_складе"` и `STATUS_CODE_LEGACY_REPAIR = "на_ремонте"` — машинные code, не имена;
- `LEGACY_REPAIR_LABEL_LOWER = "на ремонте"` — ЕДИНСТВЕННЫЙ литерал русского имени статуса, нужен для обратной совместимости CSV. Гейт плана 08 должен либо искать только заглавные формы «На складе»/«В работе»/«На ремонте»/«Списано» и числовые id, либо явно освободить эту константу, иначе он покраснеет на легитимном коде;
- числовых id статуса нет; `if new.status_id <= 0` (строка ~457) — проверка валидности, не сопоставление статуса.

Вне `device_service.rs`, **не тронуто, вне файлов плана**:

- `crates/trackly-app/src/tauri_cmds/printers.rs:171` — `status_id: 1` при автосоздании устройства-принтера из SNMP-опроса (комментарий «status_id=1»). Это числовой id статуса «На складе» в бэкенде. Если гейт плана 08 ограничен `device_service.rs`, он этого не увидит; если он шире, этот сайт нужно перевести на code (например, через `StatusLookup`-подобный поиск `на_складе`) отдельной правкой.
- `type_id` в CSV (`resolve_type_id` / `type_id_to_name`: 1 = Устройство, 2 = Расходник) остаётся числом по плану: это типы, не статусы.
