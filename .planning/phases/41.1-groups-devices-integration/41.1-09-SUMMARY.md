# Phase 41.1 Plan 09: серверная охрана якоря Summary

Якорь группы больше нельзя ни удалить мягко, ни вывести из состава (`remove_devices`, акт, restore), а запись разбора с живыми деталями не удаляется; всё проверяется в транзакции writer, а страж источника ловит и удаление охраны, и её перестановку ниже записи.

## Инвентаризация write-site'ов (правило 4)

Перечислено ОТ СЕРВЕРНЫХ МУТАЦИЙ, а не от имён: `grep` по `crates/*/src` на `delete_soft_in_tx`, `UPDATE devices SET deleted_at_utc`, `DELETE FROM group_devices`, `remove_device_in_tx`, `release_device_in_tx`, `release_if_locked_device_in_tx`, `delete_group_in_tx`, `DELETE FROM groups`, `DELETE FROM devices`, а затем разбор каждого вхождения и каждого вызывающего. Найдено 5 серверных путей, которыми якорь может покинуть группу, и 1 путь удаления самой группы:

1. `DeviceService::delete_soft` -- охрана добавлена (единственный вызов `delete_soft_in_tx` в сервисах).
2. `group_membership::release_device_in_tx` -- охрана добавлена; через неё идут все остальные пути:
   - 8 вызовов в `act_service.rs` (create, update added/removed, do_return, update_return x3, undo; три из них через `release_if_locked_device_in_tx`);
   - вызов из `delete_soft` (п. 1);
   - вызов из `remove_devices` (п. 3).
3. `GroupService::remove_devices` -- охрана добавлена до `release_device_in_tx` (своя, чтобы дать сообщение про `device_ids` и не выводить якорь из ЭТОЙ группы).
4. Трейтовый `DeviceRepository::delete_soft(conn, ..)` (devices_sqlite.rs, без транзакции): производственных вызовов нет (подтверждено grep'ом), охрана не нужна; остаётся замечанием на будущее.
5. `SqliteGroupRepository::remove_device_in_tx` -- сырое удаление из `group_devices`, вызывается только из `release_device_in_tx` (п. 2).
6. `GroupService::delete_group` -- единственный вызов `delete_group_in_tx`; добавлен запрет по числу деталей для разбора. Жёстких `DELETE FROM devices` в коде нет (только в тесте миграций), поэтому `ON DELETE CASCADE` на `group_devices` не достижим.

### Мутационная проверка (тесты не вакуумны)

Якоря мутаций уникальны (`assert count == 1`), исходники восстановлены из копии и сверены `cmp`. Снятие всех четырёх охран (`.filter(|_| false)` на вызове якоря; `count_live_parts_in_tx(..)? * 0`) краснит ровно ожидаемые тесты: `anchor_delete_soft_*`, `anchor_http_devices_delete_*`, `anchor_remove_devices_*`, `anchor_act_handover_*`, `anchor_teardown_group_*`; два не зависящих (`anchor_after_group_delete_*`, `anchor_non_teardown_*`) остались зелёными.

Страж `s11_anchor_guard_mutations_are_detected` проверяет на каждой из четырёх охран две мутации: удаление и ПЕРЕСТАНОВКУ строки охраны ниже строки записи. Счётчик вхождений перестановку пропускает (в тесте это утверждено явно), порядковая проверка -- нет.
