## How auto-approval is actually prevented (two layers — do not delete either)

This project's `.planning/config.json` currently has `workflow.auto_advance: true`. Marking this plan
`autonomous: false` with an ordinary `gate="blocking"` would NOT prevent a repeat of the 24-07
incident — auto-approval keys on checkpoint TYPE (`references/checkpoints.md:11`), and
`gate="blocking"` is boilerplate on every checkpoint example in that file, not a magic value.

**Layer 1 (PRIMARY) — `gate="blocking-human"` on Task 3.** `~/.claude/agents/gsd-executor.md:298`:
under auto-mode, `checkpoint:human-verify` auto-approves *"except ... If checkpoint has
`gate="blocking-human"` OR its purpose indicates package legitimacy verification ... do not
auto-approve. STOP and return checkpoint_return_format for explicit human confirmation."* The
condition is an **OR**, so the gate attribute alone is sufficient by the literal rule as written, and
it holds regardless of config state.

> **Recorded caveat — do not resolve away.** That exemption was authored for *package-legitimacy*
> checkpoints (see `gsd-executor.md:189` example and `:201` guidance). We rely on the attribute half
> of its OR outside that originally-intended domain. Legitimate under today's rule, but if GSD later
> narrows the exemption to package-legitimacy only, this checkpoint loses its primary protection —
> which is exactly why Tasks 2 and 4 stay in place rather than being deleted as redundant. This
> mirrors the caveat recorded in `24-11-PLAN.md`.

**Layer 2 (DEFENSE-IN-DEPTH) — config flip in Tasks 2 and 4.** Tasks 2/4 set
`workflow.auto_advance` to `false` across the checkpoint and restore it afterward, covering the
orchestrator-level re-read at `execute-phase.md:967`. **This layer alone would NOT suffice:**
`gsd-executor.md:273-280` reads `AUTO_CFG` *at executor start* and stores it for checkpoint handling,
before Task 2 can mutate it, and Pattern B (`gsd-executor.md:114`) runs Tasks 1-4 in one continuous
executor session — so the executor would self-auto-approve internally and never bubble the checkpoint
up to the orchestrator's fresh read. Expect the executor's own cached value to remain stale; this
layer protects the orchestrator's independent re-read, not the executor's internal decision.
In-repo precedent: commits `6875fcb` (flip) / `af56c14` (restore) for Phase 24's 24-11 checkpoint.

**Human-verify-mode deviation (intentional).** This project's config sets
`workflow.human_verify_mode: "end-of-phase"`, under which planners normally fold human checks into
`<verify><human-check>` sub-blocks rather than emit a standalone `checkpoint:human-verify` task. This
plan deliberately opts into the mid-flight checkpoint pattern instead, because the flip → halt →
restore design structurally requires a synchronous mid-plan stop between Tasks 2 and 4 that
end-of-phase's batched harvest cannot provide. Same justified override as 24-11 — not a conformance
error.
