<objective>
Extend the DocSpec IR and krilla renderer with the three rendering primitives Phase 15
needs: (1) a reusable two-column header function (logo left, requisites right) replacing
the current hardcoded inline header draw calls, (2) a real word-wrap primitive for long
device fields (Комплектация/Технические характеристики/Состояние) built on `ttf-parser`
font metrics (NOT the existing `truncate_to_width`, which stays pinned/untouched), and
(3) a two-line signature render for «Подпись»/«ФИО» sublabels under «Выдал»/«Получил»
(D-07), extending `Section::Signature` with backward-compatible optional fields.

This plan produces the **rendering capability** only — no template rewrite, no
act_service wiring, no test extension of the full pipeline (that's 15-02/15-03). It is
the "define the contract, implement against it" foundation the later plans depend on.

Purpose: Phase 14 already threads specs/kit/condition/requisites/logo-BLOB into the
render context, but the renderer has nowhere to draw them (RESEARCH: WR-01/WR-02 root
cause — data computed, then dropped at the renderer boundary). This plan closes that gap
at the renderer/IR layer.
Output: `docspec.rs` with extended `Signature`, `renderer.rs` with `render_header_two_column`,
`wrap_text_to_width`, and updated `Section::Signature` render arm; `ttf-parser` promoted
to a direct dependency with a human-verified legitimacy checkpoint.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| document_templates (DB, admin-editable) → DocSpec JSON → renderer.rs | Template body is admin-supplied (ManageSettings-gated) but still "untrusted content" relative to the render pipeline — a malformed or adversarial template must not crash the renderer or leak PDF-operator injection |
| logo_bytes/logo_mime BLOB → image decode (image crate) | Org-settings BLOB is admin-supplied; unexpected/oversized/mismatched MIME must degrade gracefully, not crash the process (this plan does not change the logo-BLOB source, only the anchor position it's drawn at — the existing decode/validation path is reused unchanged) |
| Long text fields (specs/kit/condition) → wrap_text_to_width | Arbitrary-length device notes/specs strings (control chars, very long single tokens) feed the new word-wrap primitive — must not infinite-loop or panic |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-01 | Denial of Service | `wrap_text_to_width` | mitigate | Pathological single-word-longer-than-max_width case explicitly handled (returns the word as its own line, no infinite loop) — covered by acceptance criteria in Task 2 |
| T-15-02 | Denial of Service | `Face::from_slice` (ttf-parser) | mitigate | Renderer already holds only its own embedded, trusted font bytes (DEJAVU_SANS_REGULAR/BOLD) — `Face::from_slice` is never called on untrusted/external bytes in this plan; a parse failure (should never occur on trusted embedded bytes) is handled via graceful `tracing::warn!` + unwrapped-text fallback, never a panic |
| T-15-03 | Tampering | `Section::Signature` extension (docspec.rs) | mitigate | New fields remain part of the typed serde enum (no raw/string PDF-operator escape hatch) — a malicious template can only supply arbitrary *label text*, never arbitrary rendering instructions, consistent with the existing DocSpec design constraint (RESEARCH: "Section — типизированный enum... шаблон не может произвести raw_pdf_op") |
| T-15-04 | Information Disclosure | `render_header_two_column` requisite skip logic | accept | Skipping empty requisite lines is a pure formatting choice with no security implication — no sensitive data is newly exposed or hidden beyond what HeaderBlock already carried in Phase 14 |
| T-15-SC | Tampering | `ttf-parser` cargo dependency promotion | mitigate | Blocking human-verify checkpoint (Task 0) before `cargo add`/Cargo.toml edit — confirms crates.io publisher/repo/license and that the package is already a compiled transitive dependency, not a new addition to the supply chain |

</threat_model>
