<objective>
Close the single verified gap from 15-VERIFICATION.md (score 4/5, gaps_found): the renderer
has zero vertical pagination. `render_docspec` builds exactly one krilla page and never
compares the running y-cursor against `A4_HEIGHT_PT - MARGIN_PT` anywhere in `render_docspec`
or `render_section`. For any realistic multi-device act (~4-5+ devices with populated long
Комплектация/Технические характеристики/Состояние fields — well within the app's 100-item
limit), content is silently drawn past the visible/printable page area: a data-loss/overlap
defect that defeats roadmap Success Criterion #2 ("без обрезки/наложения текста"). This is
the same defect flagged as WR-05 in 15-REVIEW.md and escalated to a phase-blocking gap by
the verifier because text-extraction assertions (the phase's own existing tests) cannot
detect content drawn off-page — `pdf_extract` reads the content stream irrespective of
whether the y-coordinate falls within the visible page area.

Purpose: PDFA-02 requires that an act with 2+ devices prints all positions "without clipping
or overlapping text" — a requirement that is only actually met if the renderer paginates
when content overflows a single A4 page. This plan adds that pagination logic and a
regression test that measures real rendered page count (via `pdf_extract`'s page-tree-aware
`extract_text_from_mem_by_pages`, NOT string-content assertions), closing both the
implementation gap and the test-blind-spot the verifier identified.

Output: `render_docspec`/`render_section` gain page-break logic (new page started, y reset to
`MARGIN_PT`, whenever the next section/card would overflow `A4_HEIGHT_PT - MARGIN_PT`);
`DeviceCard` sections are measured and kept atomic across page boundaries (never split
mid-card); a new page-count regression test in `pdf_render_act.rs`; `act_42.sha256`
regenerated only if the existing single-page fixture's bytes actually change.
</objective>

// plan 04 may add page breaks if a real act overflows.
{
    let mut page = doc.start_page_with(page_settings);
    let mut surface = page.surface();

    let mut y = MARGIN_PT + HEADING_SIZE_PT;

    y = render_header_two_column(&mut surface, &spec.header, &font_regular, &font_bold, y);

with the same `page_settings` is the entire mechanism.

<!-- The exact per-line height arithmetic render_section already uses for DeviceCard —
     reuse this to PREDICT a card's total height before drawing it (measure-then-place). -->
From crates/trackly-app/src/pdf/renderer.rs (lines 536-608, current DeviceCard render arm):
Heading line: `(HEADING_SIZE_PT - 2.0) + 8.0` advance.
Each identification KvRow: `BODY_SIZE_PT + 4.0` advance.
Each long_fields KvRow: one label line (`BODY_SIZE_PT + 4.0`) + `wrap_text_to_width(...)`'s
returned line count, each wrapped line advancing `BODY_SIZE_PT + 2.0`.
Trailing: `+ 8.0`.
A card's total height can therefore be computed WITHOUT drawing, by running the same
`wrap_text_to_width` calls used at draw time (already available as a `pub fn` in this same
module) purely for line-counting, then summing the same constants render_section uses.
