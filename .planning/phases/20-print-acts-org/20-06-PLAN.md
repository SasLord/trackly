<objective>
Deliver D-12 (20-CONTEXT.md, revision): an auto-upgrade-untouched-defaults mechanism for the file-based HTML templates (`act_handover.html`, `act_acceptance.html`, `report.html`), so that Plan 20-03's header/`address_line2` bundle-default changes actually reach installs that already materialized these files on disk in Phase 16/17 — not just fresh installs. `materialize_defaults_on_startup` (existing, insert-only) never overwrites an existing file and `load_template` always prefers the on-disk copy, so without this plan PRN-01/ORG-02 stay broken for every current user.

Purpose: This is the blocker-resolution plan from the plan-checker's PRN-01/ORG-02 gap finding — the exact shape of the previously-documented `[[db_backed_templates_upgrade_trap]]`, now recurring for file-based (not DB-based) templates.
Output: `html_templates.rs` gains `KNOWN_LEGACY_DEFAULTS` (a registry of byte-for-byte pre-Phase-20 default bodies, one snapshot file per template under `templates/_legacy_defaults/v20/`) and `upgrade_untouched_defaults_on_startup` (overwrites an on-disk file with the current bundled default ONLY if that file's content is byte-identical to a known-prior default — i.e. provably untouched by the user). Wired into `context.rs`'s startup sequence immediately after the existing `materialize_defaults_on_startup` call. Regression-tested against a pre-materialized OLD file (not a fresh TempDir), closing the false-confidence gap the plan-checker identified in Plan 20-05.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Existing on-disk template file (possibly user-customized via Settings' template editor, `update_body`) -> `upgrade_untouched_defaults_on_startup` -> overwritten in place | Every app startup now performs a conditional overwrite of files that may contain user-authored content; the byte-identity check is the only guard preventing data loss |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-20-06-01 | Tampering (destructive overwrite of user customization) | `html_templates.rs::upgrade_untouched_defaults_on_startup` | mitigate | Exact byte-for-byte comparison against `KNOWN_LEGACY_DEFAULTS` (not fuzzy/hash-truncated matching) — ANY difference from every known-shipped default, including a single trailing-whitespace byte, is treated as user-customized and left untouched (fail-closed). Regression-locked by Task 3's Test 2 (`upgrade_leaves_user_customized_file_untouched`). |
| T-20-06-02 | Tampering (registry goes stale, future phase forgets to add a legacy snapshot) | `html_templates.rs::KNOWN_LEGACY_DEFAULTS` | accept | Documented extension point in the const's doc-comment (Task 1) instructs future phases to append a new snapshot when `DEFAULT_HTML_TEMPLATES` bodies change again; worst-case failure mode if forgotten is a MISSED upgrade (file stays on the older-but-still-valid content), never a wrongful overwrite — asymmetric risk favors safety over freshness. |
| T-20-06-03 | Denial of Service (startup failure if snapshot files missing/corrupt) | `include_str!` of `_legacy_defaults/v20/*.html` | accept | `include_str!` is a compile-time embed — a missing snapshot file fails the BUILD, not a running deployment; this can never manifest as a runtime DoS. |
</threat_model>
