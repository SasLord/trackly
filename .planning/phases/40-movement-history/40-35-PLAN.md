Tauri command (via apiCall, camelCase args): cartridges_to_refill_last_send() -> ToRefillLastSendDto
(no arguments). ToRefillLastSendDto shape (snake_case JSON, S-2): { given_by_name: string | null,
given_to_name: string | null, place_id: number | null } — all three values come from the SAME
audit_log row (the single most recent custom:to_refill transition, of any cartridge).

cartridges_operation_default_place(op: string, cartridgeId: number | null) -> number | null is
UNCHANGED on the wire (same Tauri command name, same axum route) — but plan 40-33 removed its
"to_refill" branch server-side, so passing op !== 'from_refill' now returns a Validation error.
This plan narrows the TypeScript-level api.ts wrapper so op can no longer be passed at all from
the frontend — the wrapper always sends 'from_refill' internally, taking only cartridgeId as its
public parameter. No frontend code should ever construct the op='to_refill' payload again.

Current api.ts wrapper being replaced (ui/src/features/cartridges/api.ts, current lines ~47-52):
operationDefaultPlace: (op: 'to_refill' | 'from_refill', cartridgeId: number | null) =>
apiCall<number | null>('cartridges_operation_default_place', { op, cartridgeId }).

Current OperationModal.svelte combined $effect (lines ~190-214, full body already read by the
planner) handles BOTH to_refill and from_refill through one call to
cartridges.operationDefaultPlace(op, op === 'from_refill' ? effectiveCartridge.id : null) and only
ever writes placeId/placeAutofilled. This plan SPLITS it: the from_refill half keeps writing only
placeId/placeAutofilled (narrowed call, no op argument); a NEW to_refill effect writes
givenByName/givenToName/placeId/placeAutofilled independently, each field gated on its own current
emptiness at promise-resolution time (mirrors the existing placeId === null check, applied
per-field: givenByName === '' / givenToName === '' / placeId === null — three independent guards,
not one combined guard, so a partial manual edit made while the request was in flight is
respected field-by-field).

Existing DEC-B cross-effect clobber history (lines ~154-189, ~292-321 of the current file, already
read by the planner in full) — the install-printer-place-autofill effect's early-return branch is
ALREADY scoped to op === 'install' (fixed by commit 19f64449, round-3 gap-closure) and reads
placeAutofilled. The new split effects in THIS plan continue to write placeAutofilled exactly the
same way the old combined effect did (true whenever placeId gets autofilled) — no new interaction
with the install-effect's branch is introduced, since that branch's gate already excludes every op
other than 'install'. Do not remove or alter the op === 'install' scoping in that branch — this
plan does not touch it.

Form-state fields already present (unchanged): let givenByName = $state(''); let givenToName =
$state(''); let placeId = $state<number | null>(null); let placeAutofilled = $state(false). Reset
effect (lines ~128-152) already clears all four to ''/''/null/false on every open/op change — both
split effects in this plan run AFTER that reset, same ordering the current combined effect already
relies on (declaration order, unchanged).
