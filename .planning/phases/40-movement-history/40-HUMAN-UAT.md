## Gaps

### UAT3-01. Дефолтное место при отправке на заправку и при возврате с неё
status: failed
severity: major
surface: диалог отправки картриджа на заправку; диалог «Получение с заправки»

Сейчас поле «Место» не подставляет осмысленный дефолт. Нужно:
- **Отправка на заправку** — предлагать по умолчанию место, которое чаще всего
  используется при отправке (наиболее частое из истории), с возможностью изменить.
- **Возврат с заправки** — предлагать место, на котором картридж находился ДО отправки
  на заправку. Пример из UAT: картридж лежит на Складе → отправлен на Заправку → при
  возврате в поле «Место» должен предлагаться Склад.

Заметка: у фазы уже есть похожая механика для авто-возврата картриджа при установке
нового (`last_known_storage_place_in_tx`, план 40-28) — вероятный кандидат на
переиспользование/расширение, а не на второй параллельный источник правды.

### UAT3-02. LAN-печать/экспорт PDF отчёта «Перемещения»: дублируется первая страница
status: failed
severity: major
surface: браузер по LAN, отчёт «Перемещения», экспорт/печать PDF
regression_of: план 40-27 (закрывал ровно этот дефект), подтверждён «VERIFIED» в
`40-VERIFICATION.md` только чтением кода — живого повторного прогона не было

Печать отчёта идёт через `ui/src/features/acts/PdfPreviewModal.svelte`
(`ReportsPage.svelte` открывает его в `mode="report"`). 40-27 добавил безусловную
очистку `printRoot`/`activePolisher` в начале каждого прогона и guard `printing` от
повторного клика — этого оказалось недостаточно.

Открытая зацепка из код-ревью раунда 2: WR-04 — слушатель `afterprint` предыдущего
прогона снимается только внутри самого `cleanup`, то есть при незавершившемся прогоне
может остаться висеть.

Важное методическое замечание: этот дефект живёт именно в LAN-браузере, а это НАСТОЯЩИЙ
браузер (в отличие от десктопного WKWebView). Значит, в кои-то веки его МОЖНО честно
воспроизвести локально — поднять серверный режим и открыть отчёт в браузере, — а не
только на Windows. Обычная оговорка «синтетический харнесс ≠ верификация» здесь не
применяется.

### UAT3-03. Счётчики в дереве «Места» не обновляются после переноса содержимого
status: failed
severity: minor
surface: раздел «Места», дерево; кнопка «Перенести всё содержимое в…»

Причина установлена чтением кода (не гипотеза): в `ui/src/features/places/PlaceTree.svelte`
`statsCache` — это `$state<Record<number, number>>`, который заполняется РОВНО ОДИН РАЗ на
каждое место и никогда не инвалидируется:

    if (statsCache[id] !== undefined || statsInFlight.has(id)) continue;   // ~line 317

Значит, это не сбой реактивности рун, а кэш без инвалидации. После bulk-переноса
(`PlaceContents.svelte`, «Перенести всё содержимое в…», план 40-19) счётчики и у
источника, и у приёмника, и у всех их предков остаются старыми до перезагрузки.

Нужна инвалидация затронутого поддерева (источник + приёмник + все их предки) после
успешного переноса — и, вероятно, после любой другой операции, меняющей состав места
(создание/удаление/перемещение устройства или картриджа).

### UAT3-01a. Дефолт «Получение с заправки» возвращает саму Заправку, если она помечена складом
status: failed
severity: major
found: живая проверка чекпоинта плана 40-31 (2026-09-04), одноразовый инстанс, реальный браузер
surface: диалог «Получение с заправки»

`crates/trackly-infra/src/repos/cartridges_sqlite.rs::last_known_storage_place_in_tx` (~962-999)
выбирает `CASE WHEN p_to.is_storage = 1 THEN pm.to_place_id ELSE pm.from_place_id END` по самому
свежему движению. Если место заправки ТОЖЕ помечено `is_storage = 1` — а это ничем не запрещено и
естественно, когда картриджи физически лежат в пункте заправки — возвращается `to_place_id`, то
есть сама Заправка, а не место «до отправки».

Воспроизведено дважды, обе ветки:
- место заправки с `is_storage = 1` → дефолт «Заправка» (НЕВЕРНО, ожидался «Склад»);
- место заправки без `is_storage` → дефолт «Склад» (верно).

Причина в постановке, а не в исполнении: план 40-30 переиспользовал
`last_known_storage_place_in_tx` для вопроса, на который она не отвечает. «Последнее известное
СКЛАДСКОЕ место» и «место, где картридж был ДО отправки на заправку» — разные вопросы.
Правильный источник для дефолта `from_refill`: `from_place_id` самого свежего движения этого
картриджа, помеченного как переход `to_refill` (константа `TO_REFILL_MOVEMENT_NOTE` уже заведена
планом 40-30), БЕЗ фильтра по `is_storage` у места назначения.

### UAT3-03a. Инвалидация счётчиков уходит в бесконечный цикл эффекта
status: failed
severity: major
found: живая проверка чекпоинта плана 40-32 (2026-09-04)
surface: раздел «Места», дерево, после «Перенести всё содержимое в…»

`ui/src/features/places/PlaceTree.svelte` (~351-361): новый `$effect` инвалидации одновременно
ЧИТАЕТ `statsCache` (`const next = { ...statsCache }`) и БЕЗУСЛОВНО его перезаписывает
(`statsCache = next`) на каждом срабатывании. Каждая перезапись — новая ссылка на объект, эффект
видит собственную зависимость изменившейся и перезапускается. Svelte 5 обрывает цикл ошибкой
`effect_update_depth_exceeded`, после чего реактивность страницы замирает целиком.

Наблюдаемо: после переноса счётчики не просто устаревают, а ПРОПАДАЮТ, панель содержимого
источника продолжает показывать уже перенесённые картриджи, в консоли —
`Uncaught ... svelte.dev/e/effect_update_depth_exceeded`.

Бэкенд корректен: свежие `places_subtree_stats` после переноса отдают правильные числа
(общий предок неизменен, источник обнулился, приёмник вырос) — подтверждено и по сети, и полной
перезагрузкой страницы.

Ровно тот класс дефекта, который `svelte-check`/`eslint`/`pnpm build` не ловят.
