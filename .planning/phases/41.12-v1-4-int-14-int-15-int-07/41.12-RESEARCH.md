## Резюме

Три находки аудита от 2026-10-20 подтверждены по исходникам. У всех одна природа: код расходится с источником истины, а гейт либо смотрит не туда, либо перечисляет охват фиксированным списком.

**INT-14 (critical).** Справочник `device_types` содержит ровно две строки: `(1,'Устройство')`, `(2,'Принтер')`. Миграций, меняющих таблицу, нет. Отдельной сущности «расходник» в домене устройств нет: расходники — это `cartridges` со своим справочником видов. Поэтому справочник остаётся двухзначным, **миграция не нужна**: код приводится к справочнику. Хардкод неверен в трёх местах из аудита, а инвентаризация от репозитория нашла ещё одно: `GroupAddDevicesModal.svelte` держит собственный массив `TYPE_OPTIONS` (подписи верные, но тоже копия справочника). Сервер уже умеет отдавать справочник статусов (`device_statuses_list`); для типов такого пути нет — нужен зеркальный `device_types_list` (Tauri-команда + HTTP-маршрут + стор). Критичный нюанс совместимости: до фикса экспорт печатал «Расходник» на каждом принтере, а импорт читал «Расходник» как `type_id 2`. Значит, **старые выгрузки приложения при повторном импорте дают принтеры только по слову «Расходник»**; чистое удаление литерала превратит их в молчаливые «Устройства». Нужно решение (см. Открытые вопросы, Q1).

**INT-15 (warning).** Единственный клиентский вызов `devices.delete(` лежит в `DeviceRowMenu.handleDelete`, и меню обслуживает **две** страницы — «Устройства» и «Принтеры». Фикс «в `DevicesPage.onDelete`», как написано в аудите, закрыл бы только одну из двух и не сделал бы обрамляющую функцию маркера охранной. Правильное место — тело `handleDelete` (там известны `dev.place_id`). Для картриджа аналогично: `CartridgesPage.handleConfirmDelete` и `confirmDeleteCartridge.place_id`. Инвентаризация от серверных мутаций (`broadcast_entities` с непустыми `place_ids`) других непокрытых классов не нашла: группы `update`/`delete`/`removeDevices`/`setValues` шлют пустой `place_ids` (проверено по комментариям и коду сервиса), создание принтера из SNMP-обнаружения идёт с `place_id: None`.

**INT-07 (warning).** `check-place-path-short.mjs` держит `ROW_COMPONENTS` из четырёх файлов + `ReportTable`, понимает только `<td>`-ячейки и не имеет `--selftest` (и в `pnpm lint` подключён без него). Скан `ui/src/**/*.svelte` показывает 24 файла, упоминающих семейство `place_path_short`/`full_path`/`place_path`; из них 9 — потребители сокращённого пути (4 файла вне охвата, 5 мест использования, включая `MovementTimeline.svelte` в `lib/components`, а не в `features`). Образец «реестр + скан» в этом репозитории — не один гейт, а два: `check-place-tree-invalidation.mjs` (реестр поверхностей + скан дерева) даёт форму реестра, а `check-device-status-labels.mjs` (таблица `EXEMPT` с причиной, устаревшее освобождение краснит само, `MIN_*` против вакуума, `--selftest` с мутантами по уникальным якорям) даёт форму вердиктов. Гейт пути нужно строить из их сочетания.

**Основная рекомендация:** три независимых направления, одна волна параллельных планов (кроме общей строки `lint` в `ui/package.json`): (1) справочник типов — `TypeLookup` в `DeviceService` + `device_types_list` + стор + данные-ведомые тесты + новый гейт `check-device-type-labels.mjs`; (2) `devices.delete(`/`cartridges.delete(` в `DIRECT_CALL_MARKERS` + вызовы `notifyPlaceContentChanged` в `handleDelete`/`handleConfirmDelete` + позиционное правило «после мутации»; (3) переписать `check-place-path-short.mjs` на скан `ui/src` с вердиктами и `--selftest`.

- **Приватность (жёстко, репозиторий публичный).** В фикстурах и тестах только вымышленные данные («Иванов И.И.»); перед коммитом `node scripts/check-privacy.mjs --hashes scripts/privacy-tokens.sha256` (есть pre-commit и шаг CI). В этом документе реальных данных нет. Агентские артефакты (REVIEW/VERIFICATION) нужно грепать до коммита.
- **Стек фиксирован:** Rust + Tauri 2 + Svelte 5 (руны) + SCSS + SQLite. Версии брать из `Cargo.toml` и `ui/package.json`, не из CLAUDE.md (там дрейф: фактически `rusqlite 0.38`, `refinery 0.9`).
- **Единый слой записи:** запись только через `WriterHandle`; чтение через `ReaderPool`. Новый `list_types` — чтение (`readers`), как `list_statuses`.
- **Русский язык** в UI и артефактах. UI-правила проекта: кастомный `Dropdown`, не нативный `<select>`.
- **GSD-процесс:** правки репозитория только через GSD-команды.
- **Гейты — разные команды** (память `ui_gates_are_separate_commands`): `pnpm --dir ui lint` НЕ включает `svelte-check`; `cargo clippy --workspace --all-targets -- -D warnings` и `cargo fmt --all -- --check` — отдельные шаги. Базовый уровень `svelte-check` на конец 41.1: 0 ошибок / 70 предупреждений.
- **Один `cargo test` одновременно;** полный прогон workspace ~80 минут — скоупить по целям, полный — один раз на границе волны, в фоне. При ошибке линковки `exit 69` — префикс `DEVELOPER_DIR=/Library/Developer/CommandLineTools`.
- **Тесты `trackly-app`** требуют `TRACKLY_AD_MOCK=1 TRACKLY_SNMP_MOCK=1` и реально собранный `ui/dist` (`pnpm build`).
- **`ui/src/bindings.ts` генерируется** тестом `export_bindings` (gitignored, не на Windows). После добавления команды: `cargo test -p trackly-app --test export_bindings`, иначе `svelte-check` не видит типов.

## Решение D: миграция `device_types` — НЕ нужна [VERIFIED: codebase]

**Решение: справочник остаётся двухзначным; код приводится к справочнику.**

Доказательства:
1. Сущности «расходник» отдельно от картриджей в домене устройств нет. Расходники — это `cartridges` + `cartridge_models.kind` (1 = Картридж, 2 = Фотобарабан, V017), со своим жизненным циклом и статусами. Затронуты только **строки, уже импортированные через ошибочный `resolve_type_id`** (принтер из CSV мог попасть как «Устройство»; «Расходник» — как принтер со строкой `printers`). Правила:
- **[P1] полнота.** Каждый `.svelte` под `src`, где текст без комментариев содержит SHORT_RE или FULL_RE, обязан иметь запись. Новый файл без вердикта — красный.
- **[P2] контракт вида.** ROW_CELL: `<td>` с SHORT в тексте и идентификатором семейства full в `title=`; full не в тексте (прежние INV-1..3, но «любое имя из семейства full», иначе `GroupContentsTable` с `place_path` ложно краснеет). LINK_BUTTON: текст читает `*_short`, `title` — full. REPORT_TABLE: прежний INV-4. PASSTHROUGH: в `<script>` одновременно ключи `full_path:` и `place_path_short:`.
- **[P3] устаревание.** Файл записи не найден, либо идентификатор семейства из файла исчез (для FULL_BY_DESIGN, DATA_ONLY, PASSTHROUGH) — красный.
- **[P4] качество причины.** `reason` >= 20 символов, каталог оканчивается на `/`.
- **[P5] антивакуум.** Файлов-потребителей short не меньше `MIN_SHORT_CONSUMERS` (сегодня 9), записей не меньше `MIN_VERDICTS`.
- **`--selftest`** — мутанты по реальным файлам через `mutate()` с единственным якорем.

## Не изобретать заново

| Проблема | Не писать | Использовать | Почему |
|----------|-----------|--------------|--------|
| Подписи типа и id | новая `match`-карта | `TypeLookup` по образцу `StatusLookup` | тест «каждая строка справочника» ловит любую карту |
| Загрузка справочника в UI | локальный `$state` в странице | `deviceTypes.svelte.ts` по образцу `deviceStatuses.svelte.ts` | ленивая загрузка, один запрос, один тост об ошибке; запись в `$state` только из async-продолжения |
| Якорь мутации в selftest | `str.replace(a, b, 1)` | `mutate()` из `check-place-tree-invalidation.mjs` (завершает процесс, если якорь не ровно один) | урок «якорь обязан быть уникален» |
| Разбор разметки Svelte | свой парсер | `stripComments`, `allTagBlocks`, `attrValue`, `balancedBraces`, `enclosingFunction`, `functionBody`, `markupOnly`, `collectCells` | отлажены на реальных файлах; **скопировать** в новый гейт (гейты zero-dependency и друг друга не импортируют) |

**Ключевая мысль:** гейт с фиксированным списком занижает инвентарь. Перечислять нужно **от скана**, а освобождения кодировать **вердиктом с причиной и самоустареванием**.

## Частые ошибки

### 1. Совместимость со старыми выгрузками
**Что идёт не так:** после удаления литерала «Расходник» из импорта старая выгрузка (принтеры подписаны «Расходник») тихо превращается в «Устройства» — порча данных в обратную сторону.
**Как избежать:** решение по Q1 (псевдоним `LEGACY_EXPORT_PRINTER_LABEL_LOWER` в импорте по образцу `LEGACY_REPAIR_LABEL_LOWER`, либо явная ошибка строки). Тест на выбранное поведение обязателен.
**Признак:** строка «Расходник» в CSV создаёт `type_id = 1`.

### 2. Вакуумный тест из-за фикстуры
**Что идёт не так:** тест «принтер экспортируется как Принтер» зелёный на старом коде, если принтер в фикстуре не создан или проверяется подстрока.
**Как избежать:** до правки кода тесты обязаны быть КРАСНЫМИ (зафиксировать красный первый прогон в плане). Для данных-ведомого теста вставить в `device_types` строку, которой нет ни в одной карте (`Монитор`, id 3) — любая новая `match`-карта краснеет. Ожидаемую подпись читать из `device_types`, не хардкодить.

### 3. Счётный гейт слеп к порядку
**Что идёт не так:** `notifyPlaceContentChanged` перед `await devices.delete(...)` проходит `body.includes`; при отказе сервера счётчики инвалидируются до успеха.
**Как избежать:** позиционное правило `notifyAfter` + мутант-перестановка (вызов перенесён выше `await`), а не только мутант-удаление.

### 4. SKIP-able файл молчит навсегда
**Что идёт не так:** запись реестра указывает на файл, из которого вызов убрали; гейт «проверяет» ноль мест.
**Как избежать:** `minSites`; для вердиктов — «идентификатор семейства всё ещё в файле»; отсутствие файла — красный, не пропуск.

### 5. `devices.delete(` как подстрока
**Что идёт не так:** литеральный маркер совпадёт с `pickedDevices.delete(...)` (Set/Map) — ложное красное.
**Как избежать:** проверка символа слева (`(?<![\w$.])`); в selftest — кейс «`Set.delete` с похожим именем не краснит».

### 6. Место теряется
**Что идёт не так:** `confirmDeleteCartridge = null` выполняется до вызова — место взять неоткуда; `dev.place_id === null` даёт вызов с `[null]`.
**Как избежать:** взять `placeId` в локальную переменную до `await`; `if (placeId !== null)`; аргумент с идентификатором, чтобы пройти INV-9.

### 7. `svelte-check` не входит в `lint`
**Как избежать:** в чек-листе каждой волны отдельно `pnpm --dir ui exec svelte-check --threshold error`; перед ним `cargo test -p trackly-app --test export_bindings` (иначе в `bindings.ts` нет `DeviceTypeDto`).

### 8. Рантайм Svelte-рун невидим компиляционным гейтам
**Что идёт не так:** запись в `$state` стора синхронно в `$effect` -> `effect_update_depth_exceeded`; `svelte-check`, `eslint`, `build` этого не видят.
**Как избежать:** копировать паттерн `deviceStatuses.svelte.ts` (запись только в `.then()`); экраны «Отчёты» и «Добавить устройства в группу» проверить в запущенном приложении (human-verify); синтетический харнесс верификацией не считается.

### 9. Один `cargo test` за раз
Параллельные запуски конфликтуют по `target/`; полный workspace ~80 минут — один прогон на границе волны в фоне.

## Риски, порядок и распараллеливание

**Независимость.** INT-14, INT-15, INT-07 независимы по коду. Точки пересечения:
- **Строка `lint` в `ui/package.json`** (INT-14 добавляет новый гейт, INT-07 добавляет `--selftest`): править одним планом или строго последовательно, иначе конфликт слияния.
- `check-place-tree-invalidation.mjs` правит только INT-15; `check-place-path-short.mjs` — только INT-07.
- `GroupAddDevicesModal.svelte` правит INT-14 (`TYPE_OPTIONS`), а гейт INT-07 его только читает — `<td>`-ячейку пути в этом файле не трогать.
- `DeviceRowMenu.svelte` правит INT-15 (`handleDelete`); гейт INT-07 читает его как PASSTHROUGH (объект `showView`) — этот блок не трогать.

**Жёсткий порядок внутри INT-14:** `TypeLookup` + команда + тесты (красные первыми) -> `cargo test -p trackly-app --test export_bindings` -> UI (стор, `ReportsPage`, `GroupAddDevicesModal`) -> новый UI-гейт (его `MIN_CONSUMERS` считается после перевода экранов) -> фикстуры CSV (вместе с тестами, иначе промежуточный красный).

**Рекомендуемые волны:**
1. Волна 1 (параллельно): (A) INT-14 backend: `TypeLookup`, `list_types`, команда/маршрут/specta, тесты (красные первыми), правка фикстур; (B) INT-15 целиком (UI-правки + гейт + selftest); (C) INT-07 целиком (переписать гейт + selftest, без правки `package.json`).

**Что ломает существующие тесты и гейты:**
1. `utf8*.csv`, `malformed_mixed_rows.csv`, `cp1251_*.csv` — тесты не проверяют тип, красными не станут, но фикстуры обязаны быть приведены (критерий 1).

### Открытые вопросы
1. **Q1. Псевдоним «Расходник» в импорте.** Известно: до фикса экспорт печатал «Расходник» на принтерах, импорт читал «Расходник» как `type_id 2`, то есть round-trip старых выгрузок работал именно по этому слову. Неясно: нужна ли эта совместимость. Рекомендация: **добавить именованную константу-псевдоним в импорте** (по образцу `LEGACY_REPAIR_LABEL_LOWER`, с комментарием и освобождением в гейтах), а критерий 1 читать как «нет карты id -> подпись; единственное вхождение слова — документированный псевдоним импорта». Альтернатива — ошибка строки «тип «Расходник» не поддерживается». Подтвердить с пользователем ДО планирования: от решения зависят формулировка критерия 1 и мутант критерия 2.
2. **Q2. Неизвестная подпись.** Рекомендация: умолчание «Устройство» (как у статусов); ошибку строки не вводить без решения пользователя.
3. **Q3. Позиционное правило `notifyAfter` для всех маркеров?** Рекомендация: только для двух новых. У `groups.addDevices` в `GroupContentsTable` есть задокументированное исключение (вызов осознанно стоит ДО второго вызова).
4. **Q4. Точный перечень `FULL_BY_DESIGN`.** Таблица выше — черновая; окончательный список даёт первый прогон нового гейта по репозиторию (запустить в режиме отчёта и свериться).

### Критерии успеха -> наблюдаемый сигнал -> мутация гейта

Общий принцип невакуумности: **красный-первым.** Каждый новый тест и гейт сначала прогоняется на ТЕКУЩЕМ (дефектном) коде и обязан быть красным, затем на исправленном — зелёным. Якоря мутаций, существующие сегодня, проверены grep'ом на уникальность (вхождений ровно 1); якоря новых строк проверяет `mutate()` в selftest (`count == 1`).

| № | Критерий | Наблюдаемый сигнал | Мутация реального исходника (якорь, вхождений) | Ожидаемый красный |
|---|----------|--------------------|-----------------------------------------------|-------------------|
| 1a | Экспорт: подпись из справочника | `device_types_dictionary::csv_export_label_equals_dictionary_name_for_every_type` (в т.ч. вставленный тип 3 «Монитор») | вернуть `2 => "Расходник",` в `type_id_to_name` (`device_service.rs`, 1); либо в новом коде заменить чтение справочника на `match` | тест красный: принтер «Расходник» вместо «Принтер»; тип 3 не напечатан |
| 1b | Импорт: резолв из справочника | `device_types_dictionary::import_resolves_every_dictionary_label` (круг: экспорт -> импорт, `type_id` каждой строки) | вернуть `Some("Расходник") \| Some("расходник") => 2,` (1) | красный: «Принтер» -> 1 |
| 1c | Список типов в фильтре отчётов из справочника | `device_types_role_matrix` (200, массив из 2 строк) + `check-device-type-labels.mjs` | вернуть `{ id: 2, name: 'Расходник' },` в `ReportsPage.svelte` (1) | гейт [T1]/[T3] красный (кейс в `--selftest`) |
| 1d | Копий справочника в UI нет | `check-device-type-labels.mjs` [T1] | вернуть `{ id: 2, label: 'Принтер' },` в `GroupAddDevicesModal.svelte` (1) | [T1] красный |
| 1e | Литерала «Расходник» нет | приёмочный `grep -rIn "Расходник" crates ui/src` -> пусто (или только документированный псевдоним, Q1) + [T3] | вернуть слово в `utf8.csv` (строка 5) | приёмочный grep не пуст (файл-фикстура гейтом не сканируется — это пункт приёмки) |
