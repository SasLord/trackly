## Narrative Findings (AI reviewer)

## Summary

Проверено: production-код фазы (V057, домен, репозиторий, `history_events.rs` и все места записи в
act/device/group/group_place/group_act_plan/place/repair-сервисах, `HistoryService` и транспорты, UI-лента,
попап, Modal) и тесты/гейты на вакуумность. Новые тест-файлы подключены к suite-бинарникам (`autotests = false`):
пустых целей нет. Ролевой гейт `ReadPlaces` стоит в обоих транспортах, есть строки в `role_endpoint_matrix`.
Рантайм-импортов `bindings.ts` нет. Реальных ФИО и реквизитов в диффе нет: только «Иванов И.И.»,
«Петров П.П.», «Сидоров С.С.».

Главная проблема в правке живого акта (D-24 (a)). Членство и вложенность меняются там молча: вывод в
режиме `Suppressed` и `restore_*` без события. При этом событие самого акта (`group_left` / `group_unnested`
с `act_id`) остаётся в ленте. Лента показывает «выведено», а устройство или группа уже снова в составе.
Гейт мест записи это не ловит: освобождения записаны с причиной «откат акта», хотя тот же код идёт и из правки.
Остальное: неверный текст образования безъякорной группы в ленте группы, мёртвый вызов, который держит
реестровый гейт зелёным, и нарушения D-04 (одна операция показывается двумя строками).

## Critical Issues

### CR-01: Правка живого акта меняет членство устройства молча, а событие акта остаётся. Лента противоречит составу

**File:** `crates/trackly-app/src/services/act_service.rs:1626-1680` (и зеркало для возвратного акта `:3183-3240`); `crates/trackly-app/src/services/group_membership.rs:256-267`, `:388`
**Issue:** D-24 (a): «Правка акта (не откат) пишет обычные события». При снятии позиции из живого акта:
1. `release_if_locked_device_in_tx(...)` безусловно передаёт `ReleaseHistory::Suppressed` (group_membership.rs:266). Если восстановленное место расходится с местом группы, устройство выходит из группы, а `group_left` не пишется.
2. `restore_membership_in_tx(...)` (act_service.rs:1650/3207) возвращает устройство в группу по эффекту `release` без `group_joined`.

Сценарий: акт №N передаёт члена группы А. Пишется `group_left(act_id=N)`. Затем правка акта снимает эту
позицию, и устройство молча возвращается в А. Событие `group_left` акта №N живёт, пока акт не удалят. Лента
показывает последней записью состава «Выведено из группы «А» · актом №N», хотя устройство в А. Статус в
этой же ветке пишется (`record_act_status_event`), поэтому лента рассогласована именно по составу. Тестов
на правку акта в `history_act_undo.rs` / `history_group_act.rs` нет, покрыты только create и delete.

**Fix:** различать откат и правку на уровне режима истории:
```rust
// group_membership.rs: принять режим вместо жёсткого Suppressed
pub(crate) fn release_if_locked_device_in_tx(..., effect: ReleaseEffect, history: ReleaseHistory<'_>)
// act_service.rs (правка, акт жив):
release_if_locked_device_in_tx(&tx, ..., Some(payload.id), user_id_opt, now, release_mode,
                               ReleaseHistory::Default)?;
// после RestoreOutcome::Restored в правке — record_group_joined_in_tx(..., act_id = Some(payload.id))
// с HistoryReason::Act; в undo_device_mutations_for_act (:5212) оставить Suppressed.
```
Добавить интеграционный тест: создать акт с членом группы, отредактировать акт без этой позиции и
проверить, что последнее событие состава — `group_joined`. Ещё лучше удалять `group_left` именно этой позиции.

### CR-02: Правка акта возвращает вложенность группы молча, `group_unnested` акта остаётся

**File:** `crates/trackly-app/src/services/group_act_plan.rs:1641-1646` (вызывается из `act_service.rs:1514`, `:3074`)
**Issue:** `apply_split_move_in_tx` / `apply_plan_in_tx` пишут `group_unnested` с `act_id`
(`record_act_unnested`, :1082/:1106/:1342). Если правка живого акта снимает всё покрытие группы,
`revert_detach_effect_in_tx` вызывает `set_parent_in_tx(.., Some(parent_id))` без события. Комментарий
`// D-24: возврат вложенности при откате акта событий не пишет` неверен для этого вызова: акт жив и
`delete_by_act_id_in_tx` не сработает. В ленте группы и родителя остаётся «Выведена из группы «…» ·
актом №N», хотя группа снова вложена. То же с `forget_group_move_rows_in_tx` (:1545): строки перемещения
акта удаляются, а события акта по этой группе остаются.
**Fix:** передавать в `revert_detach_effect_in_tx` / `revert_move_effect_in_tx` признак «правка / откат».
При правке либо писать `group_nested` (`HistoryReason::Act`, `act_id = Some(act_id)`), либо удалять
события акта по этой группе: `DELETE FROM history_events WHERE act_id = ?1 AND (subject_type='group' AND subject_id = ?2)`.
Метод нужен в `SqliteHistoryEventsRepository`, чтобы SQL удаления остался в одном месте.

## Warnings

### WR-01: Лента группы показывает «Группа образована от устройства «<имя самой группы>»» для безъякорной группы

**File:** `ui/src/lib/historyEvents.ts:101-106`; источник данных — `crates/trackly-app/src/services/history_events.rs:225-234`, `group_service.rs:856-864`
**Issue:** у безъякорной группы `record_group_formed_in_tx(HistorySubject::Group{id})` пишет
`subject_type='group'` и `subject_label = имя группы` (`subject_parts`). В варианте `group` UI проверяет
только непустой `subject_label`, а `subject_type` не смотрит. Получается текст «Группа образована от
устройства «АРМ-5»», где «АРМ-5» — сама группа. `splitParts` ещё и сделает это имя ссылкой (кандидат с
`type: 'group'`, id ≠ groupId не выполняется, но совпадение по label с to_group даст ссылку на эту же
группу, если `groupId` не передан). Гейт `check-history-event-labels` строит сегмент всегда с
`subject_type: 'device'` и этот случай не видит.
**Fix:**
```ts
group_formed: (seg, ctx) => {
  if (ctx.variant === 'group') {
    return seg.subject_type === 'device' && (seg.subject_label?.trim() ?? '').length > 0
      ? `Группа образована от устройства${quoted(seg.subject_label)}`
      : 'Группа образована';
  }
  ...
```
Добавить в гейт фикстуру `subject_type: 'group'`.

### WR-02: Мёртвый вызов `record_status_change_in_tx(before, before)` держит реестровый гейт зелёным

**File:** `crates/trackly-app/src/services/place_service.rs:905-924`; `crates/trackly-app/tests/history_write_sites_gate.rs:437`
**Issue:** статус в ветке «Места» не меняется: `update_status_and_place_in_tx(.., before.status_id, ..)`.
Вызов события передаёт `before.status_id` дважды, поэтому по построению никогда ничего не пишет.
Единственное назначение вызова — дать `STATUS_EVENT_REGISTRY` число 1 для `place_service.rs`. Это класс
«код, которым закрыли гейт, сам ничего не делает»: если здесь когда-нибудь появится настоящая смена
статуса, гейт останется зелёным, а события не будет. Каждая операция при этом создаёт неиспользуемый UUID.
**Fix:** удалить вызов и закодировать вызов писателя как освобождение в `EXEMPT_CALLS` гейта:
`("update_status_and_place_in_tx(", "…/place_service.rs", 1, "статус не меняется: передаётся before.status_id (ST-11)")`.
Тогда гейт покраснеет, если сюда добавят реальную смену статуса.

### WR-03: Вердикты освобождений в гейте неверны. «Откат акта» на деле покрывает и правку живого акта

**File:** `crates/trackly-app/tests/history_write_sites_gate.rs:399-416`
**Issue:** освобождения `add_device_in_tx` в `group_membership.rs` («restore состава при откате акта»),
`set_parent_in_tx` в `group_act_plan.rs` («возврат вложенности при откате акта») и
`restore_from_snapshot_in_tx` ×3 в `act_service.rs` вызываются и из правки акта (`restore_membership_in_tx`,
`revert_detach_effect_in_tx`). Гейт считает вызовы по файлам и не различает путь вызова. Поэтому неверная
причина закрепила дыры CR-01/CR-02 как «по дизайну». Это повторение известного антипаттерна «счётный гейт
занижает инвентарь».
**Fix:** после исправления CR-01/02 разделить примитивы, например `restore_membership_on_undo_in_tx` и
`restore_membership_on_edit_in_tx`, и выдать вердикты по имени примитива, а не по файлу. Мутационная
проверка: удалить запись события из пути правки, гейт должен покраснеть.

### WR-04: D-04 нарушено. Для устройств, переехавших с группой актом, статус и перемещение — две строки ленты

**File:** `crates/trackly-app/src/services/act_service.rs:863-891` (и `:1319-1347`, `:2506-2534`, `:3498-3526`, `:3707-3735`)
**Issue:** для `applied.moved_device_ids` строку `place_movements` пишет пакет группы
(`apply_group_place_inner` возвращает `movement_id` в `DevicePlaceChange`). Но `ApplyOutcome` наружу его
не отдаёт, и `record_act_status_event` получает `movement_id = None`. В ленте устройства получаются две
записи одной операции: «Склад → Каб. 12 · актом №N» и «Статус: На складе → В работе · актом №N». Склейка
по `operation_id` не помогает: у строки перемещения его нет (D-25). Аналогично в `group_service.rs:2132-2167`
(`set_parent`): событие `group_nested/unnested` пишется ДО `propagate_group_place_in_tx` без
`movement_id`, вопреки порядку D-25.
**Fix:** собирать в `apply_plan_in_tx` карту `device_id -> movement_id` из `DevicePlaceChange.movement_id`
и передавать её в `record_act_status_event`. Для `set_parent` писать событие после переноса места с
`movement_id` строки группы.

### WR-05: Одно и то же списание устройства получает разные причины в зависимости от экрана

**File:** `crates/trackly-app/src/services/device_service.rs:1626-1638`, `:1738-1757`; ср. `group_service.rs:1118-1156`
**Issue:** `group_service::write_off_device` пишет статус и `group_left` с `HistoryReason::DeviceWriteOff`
