### `crates/trackly-core/src/domain/history_events.rs` (model, transform)

**Analog:** `crates/trackly-core/src/domain/place_movements.rs:23-75`

Копировать форму: `enum` + `pub const ALL: [T; N]` + `as_str()` + `from_str_lenient() -> Option<Self>`. Гейт паритета парсит именно эти четыре элемента регулярками (`pub enum X {`, `pub fn as_str(&self) -> &'static str {`, `pub const ALL: [X; N] = [...]`), поэтому формат записи копировать буквально.

```rust
pub const ALL: [MovementSource; 6] = [ Self::Manual, Self::Act, /* ... */ ];

pub fn as_str(&self) -> &'static str {
    match self { Self::Manual => "manual", /* ... */ }
}

pub fn from_str_lenient(s: &str) -> Option<Self> {
    match s { "manual" => Some(Self::Manual), /* ... */ _ => None }
}
```

Нужно два enum: `HistoryEventKind` (8 видов) и `HistoryReason` (9 причин). Чистый домен: без I/O (`tests/no_io_deps.rs`).

### `crates/trackly-infra/src/repos/history_events_sqlite.rs` (repo, write-in-tx + read)

**Analog:** `crates/trackly-infra/src/repos/place_movements_sqlite.rs`

**Шапка и импорты** (стр. 1-26): unit-struct без полей, все записи — `*_in_tx(&self, tx: &Transaction<'_>, ...)`, ошибки через `map_rusqlite`.
```rust

use crate::error_conversions::map_rusqlite;

#[derive(Debug, Default, Clone)]
pub struct SqlitePlaceMovementsRepository;
```

**Core insert** (стр. 89-122): структура `NewX<'a>` + один `INSERT` через `params!`.

**Единственный владелец SQL отката по акту** (стр. 324-330): `delete_by_act_id_in_tx` — зеркалить для `history_events` (D-24). Больше нигде `DELETE FROM history_events WHERE act_id` не писать.
```rust
pub fn delete_by_act_id_in_tx(&self, tx: &Transaction<'_>, act_id: i64) -> Result<usize, AppError> {
    tx.execute("DELETE FROM place_movements WHERE act_id = ?1", ...)
```

**Возврат id перемещения (D-25).** `record_inner` (стр. 224-298) сейчас возвращает `Result<()>` и делает ранний `return Ok(())` при `!is_reportable_place_change`. Изменить `insert_in_tx` и `record_inner` на возврат `Result<Option<i64>>` (`Some(tx.last_insert_rowid())` после INSERT, `None` при раннем выходе). Три публичных обёртки (`record_movement_if_applicable`, `record_batch_movement_if_applicable`, `record_repair_movement_if_applicable`) пробросить так же. Существующие вызовы с `?;` не ломаются, но компилятор подсветит `unused` только для `#[must_use]`; проверить clippy `-D warnings`.

**Снимок ФИО с мягкой деградацией** (стр. 262-270) — копировать дословно в `history_events.rs`, никогда `?`:
```rust
let actor_name_snapshot = user_id.and_then(|uid| {
    tx.query_row("SELECT full_name FROM users WHERE id = ?1", params![uid], |r| r.get::<_, String>(0)).ok()

```

### `crates/trackly-app/src/services/history_events.rs` (service-helper, write-in-tx)

**Analog:** `place_movements_sqlite.rs::record_inner` (решение «писать ли» внутри функции) + `group_membership.rs:95-135` (`release_inner`, где рядом с `remove_device_in_tx` пишется audit).

Файл **вне девяти файлов области `entities_changed_gate`** и не владеет `writer.execute` (иначе потребует строк в `tests/entities_support/registry.rs`). Каждая функция самодостаточна: сама решает «писать ли» (`before == after` -> `Ok(())`), сама снимает снимки, принимает `operation_id`, `now`, `user_id`.

Точка вставки у подсистемы состава — сразу после успешного `remove_device_in_tx` (`group_membership.rs:108-112`) рядом с audit:
```rust
if !groups.remove_device_in_tx(tx, device_id)? { return Ok(None); }
let payload = serde_json::json!({ "group_id": group.id, "act_id": act_id });
audit.insert(tx, AuditEntry { entity_type: "device", entity_id: device_id,
    action: "custom:group_member_released", user_id, ..., created_at_utc: now })?;
```
Для «тихого» освобождения при переносе (D-05) внутренней функции `release_inner` добавить параметр режима истории (`Record(reason)` / `Suppressed`); `release_device_in_tx` остаётся обёрткой с причиной по умолчанию.

Точка вставки у статуса при переносе группы — рядом с audit `custom:group_move_status_changed` (`group_place.rs:~306-322`):
```rust
if let Some(to) = status_to {
    let payload = serde_json::json!({ "group_id": group_id, "batch_id": batch_id,
        "status_from": before.status_code, "status_to": to });
    deps.audit.insert(tx, AuditEntry { entity_type: "device", entity_id: device_id,
        action: "custom:group_move_status_changed", ... })?;
}
```

**Порядок записи (D-25):** на каждом месте, где меняются и место, и статус, сначала `record_*_movement_*` (получить `Option<i64>` movement id), потом `record_status_change_in_tx(.., movement_id)`.

**Точки отката акта (D-24):** три `place_movements_repo.delete_by_act_id_in_tx(&tx, ...)` в `act_service.rs` (~4135, 4174, 4208, пример выше: «D-03/HST-03: undo means the movement never effectively happened») — рядом добавить `history_events_repo.delete_by_act_id_in_tx`. Групповой аналог — `forget_group_move_rows_in_tx` в `group_act_plan.rs:~1482`. Примитивы `restore_from_snapshot_in_tx` / `restore_membership_with_policy_in_tx` событий не пишут.

Инвентарь всех write-site'ов (ST-1..ST-11, MB-1..MB-8) — в `41.10-RESEARCH.md` §«Инвентарь write-site'ов»; здесь не дублируется.
