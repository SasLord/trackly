## Границы доверия

| Граница | Описание | Что пересекает |
|---------|----------|----------------|
| сервис -> SQLite (`history_events`) | kind/source/снимки/автор/act_id проставляет только сервер; клиентского маршрута записи событий нет | токены событий, снимки имён и ФИО (ПДн сотрудников) |

| сервер -> UI (лента) | токены kind/source строками, возможно от более новой версии; имена групп/устройств | текст |
| localStorage -> UI | флаг `trackly:view-history` недоверенный | булев UI-флаг |
| репозиторий (публичный) | артефакты фазы, фикстуры, витрина | риск утечки реальных данных |

### Примечания

1. **T-41.10-21 — отклонение от формулировки плана.** План требует «DELETE строго по act_id единственным методом репозитория». После UAT-1..3 в `history_events_sqlite.rs` методов удаления пять: `delete_by_act_id_in_tx`, `delete_by_movement_ids_in_tx`, `delete_by_act_and_subject_in_tx`, `delete_by_act_and_subject_except_kind_in_tx`, `delete_by_act_subject_and_kind_in_tx`. Суть митигации (нельзя удалить чужие события) сохранена: SQL удаления только в репозитории (гейт), все методы параметризованы и скоупнуты по act_id/movement_id, вызывающие стороны закреплены реестрами `ERASE_SCOPED_EXEMPTS`/`MOVEMENT_ERASER_CALLS`. Формулировку реестра стоит обновить.
2. **Имена тестов.** Тесты `release_with_act_carries_act_id`, `restore_silent`, `delete_group_cascade`, `single_event`, `unknown_kind_degrades` из планов существуют под префиксными именами (`history_act_undo_group_left`, `history_act_undo_restore_silent`, `history_membership_delete_group_cascade`, `history_membership_move_is_single_event`, `history_timeline_unknown_kind_degrades`). Все файлы `history_*.rs` подключены в suite-бинарники (`tests/suites/{acts,devices,groups,places,repairs,reports,gates}.rs`, `trackly-infra/tests/suites/infra.rs:68`).
