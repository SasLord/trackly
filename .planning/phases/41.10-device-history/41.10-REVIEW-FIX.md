## UAT-2: исключение позиции правкой дописывало возвратную строку перемещения (продолжение UAT-1)

**Дефект:** после UAT-1 правка, исключившая устройство из акта №N, дописывала возвратную строку в `place_movements` с тем же act_id. В ленте места и в отчёте «Перемещения» (HST-04) оставалась пара «перемещено в Б» / «перемещено обратно в А» по акту №N.

**Решения пользователя (2026-11-23):**
1. Строки `place_movements` акта живут ровно столько, сколько строка акта. Правка, исключившая устройство, удаляет строки этого акта по устройству, возвратную строку не пишет: устройство «не перемещалось». Удаление акта тоже должно убирать его строки.
2. Исключение: если после акта устройство действительно сменило место или группу, а правка возвращает его в состояние «до акта», это настоящее изменение. Оно пишется обычной строкой и событиями с act_id, в порядке D-25.

**Коммит:** 479bd91f
**Файлы:** `trackly-infra/.../place_movements_sqlite.rs`, `act_service.rs`, `group_membership.rs`, тесты `place_movements_repo.rs`, `history_act_edit.rs`, `acts_groups.rs`, `place_movements_act_link.rs`, `history_write_sites_gate.rs`.

**Что сделано:**
- Репозиторий: новый `forget_act_entity_rows_in_tx(act_id, kind, entity_id)`. Он работает как D-48 `forget_group_move_rows_in_tx`: ближайшая более поздняя строка той же сущности (другого акта или без акта), у которой «откуда» равно «куда» забываемой строки, получает «откуда» забываемой. После этого строки акта по сущности удаляются. Итог `ForgottenActRows { deleted, moved_after, first_from_place_id }`. Общая часть вынесена в `forgettable_rows` / `rebase_successors`, `forget_group_move_rows_in_tx` переписан на них без изменения поведения. SQL остаётся только в репозитории.
- `act_service`, функции `update` и `update_return_with_split`: блок возвратной строки после restore удалён. Вместо него перед restore вызывается помощник `forget_excluded_device_movements_in_tx`. Он забывает строки акта по устройству и пишет строку с act_id, только если устройство перемещали после акта (`moved_after`): из текущего места в место снимка. Без перемещения после акта «откуда» равно месту «до акта», и guard D-04 строку не пишет. Вызов стоит после `snapshot_keeping_group_place_in_tx` (место снимка уже учитывает D-48) и до `snapshot_keeping_written_off_in_tx` (соседство гейтов `group_write_sites` сохранено).
- Вывод из группы при правке теперь получает `ReleaseHistory::AfterMovement(excluded_movement_id)`. Это новый вариант: причина как у `Default`, плюс `movement_id` возвратной строки. Строка пишется раньше события (D-25), и лента склеивает их в одну запись.
- Снятие всего покрытия группы правкой (оба пути): после `revert_move_effect_in_tx`, если перенос обращён (группа возвращена или перенос забыт), вызывается `forget_group_move_rows_in_tx(act, group)`. Удаляются строки переноса и только что записанного обратного переноса по группе, вложенным группам, составу и картриджам.
- Конфликт якоря (D-09): строки акта не трогаются, место осталось таким, каким его сделал акт. Так было и в UAT-1.
- Удаление и откат акта не менялись: `delete_by_act_id_in_tx` уже вызывается после undo в каждой точке LIFO-цикла. Строки, записанные откатом, несут тот же act_id и тоже удаляются. Тест это подтверждает.
- Картриджи: позиции акта — только устройства (`act_items.device_id`). Одиночная передача картриджи принтера не каскадирует. Картриджные строки бывают только у переноса группы (с `group_id`) и забываются через `forget_group_move_rows_in_tx`.
- Висячие `movement_id`: FK нет (V057). События акта по устройству со ссылкой на его строки (status_changed) стирает UAT-1. `group_left` из `release_inner` раньше шёл с `movement_id: None`, теперь ссылается только на новую возвратную строку. ## UAT-3: удаление акта молча возвращало устройство, которое перемещали после акта

**Дефект:** акт №N перевёл устройство А -> Б, потом его вручную перевели Б -> В. При удалении акта откат молча возвращал устройство в А и стирал строки акта, а ручная строка «Б -> В» оставалась. В ленте было «в В», хотя устройство стояло в А.

**Решение пользователя (2026-11-23):** если устройства акта перемещали после акта, сервер ничего не меняет и возвращает конфликт, как в случае `needs_group_restore`. UI показывает попап, выбор действует сразу на все перечисленные устройства.

**Коммиты:** 73a20331 (сервер + гейт), bae105fe (тесты), 21618693 (UI).

**Сервер:**
- В `ActDeleteResultDto` добавлено поле `needs_moved_after_choice: { devices: [{ device_id, name, current_place_path, before_place_path }] }`. Пути полные.
- Выбор передаётся в `MovedAfterActChoiceDto` (`return_erase` | `return_mark` | `keep`). Транспорт: `movedChoice` в Tauri `acts_delete` и в `/api/v1/acts_delete`. Роли проверяются как раньше (`MutateActs`).
- Кандидаты определяются по журналу мест. Это устройства, у которых есть строка другого акта или строка без акта, с id больше первой строки удаляемого каскада (сам акт и его возвраты). Метод `entities_moved_after_acts_in_tx`.
- Спрашиваем только о тех, кого откат действительно сдвинет. Для этого каскад сначала прогоняется пробно под `SAVEPOINT`, и в конфликт попадают устройства, чьё место после пробы отличается от текущего. Без пробы члены группы, перенесённой после акта, ошибочно попадали бы в конфликт: шесть тестов `acts_groups` покраснели. Откат и так оставляет их на месте группы (D-09/D-48). Место «до акта» в попапе — это место после пробного отката. Каскад вынесен в `delete_cascade_in_tx`.
- **Вернуть + стереть (`return_erase`):** откат к снимку, как раньше. До каскада `erase_rows_after_in_tx` удаляет все строки устройства позже первой строки каскада, кроме строк самого каскада (их удаляет `delete_by_act_id_in_tx`). Вместе со строками стираются события с их `movement_id` (`delete_by_movement_ids_in_tx`). История кончается состоянием «до акта».
- **Вернуть без отметки (`return_mark`):** откат к снимку. В каждой точке каскада строки акта по устройству забываются (`forget_act_entity_rows_in_tx`, ближайший преемник получает их «откуда»). После каскада пишется одна строка от конца журнала к месту устройства.
  - Источник строки — новый токен `act_delete`, `act_id = NULL`, номер акта в `note`. Подпись: «при удалении акта №N».
  - Затем событие `status_changed` с причиной `act_delete` и `movement_id` этой строки (D-25), если статус сменился.
  - Лента: «А -> В вручную», «В -> А при удалении акта №N».
- **Оставить (`keep`):** снимок, вывод из группы и возврат в состав для этих устройств пропускаются (`MovedAfterPlan.kept`, фильтр в `restore_released_members_in_tx`). Строки акта забываются, лента показывает «А -> В». Если журнал всё же разошёлся с местом (возврат каскада был последним), пишется сводящая строка `act_delete`.
- Устройства, которые после акта не перемещали, откатываются как раньше.
- **Оба конфликта:** первый ответ несёт оба перечня. UI показывает попапы по очереди: сначала выбор по перемещённым, затем повторный вызов. Если сервер ещё просит выбор по группе (с учётом выбора по перемещённым; при «Оставить» список групп может сократиться), показывается попап групп. Последний вызов несёт оба выбора. Пока выбора нет, ничего не удаляется.
