# Phase 22: Правка возвратов (return-act-edit) - Context

**Gathered:** 2026-07-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Фаза 22 доставляет одну вещь (**ACT-03**): существующий **return-акт можно
редактировать**. Кнопка «Редактировать» на карточке возврата активна; клик
открывает диалог «Возврат по акту №XXX», предзаполненный текущими значениями
возврата (состав возвращённых устройств, состояние, расположение, кто
возвращал/принимал, дата возврата). Изменённый возврат сохраняется без ошибок,
эффекты на устройства (статус/локация/история) **пересобираются по дельте**, а
derived-флаги (в т.ч. `archived` родительского акта) остаются согласованными.

**Отменяет D-07 (Фаза 19)** в части «return-акты нередактируемы».

**Не в scope:** правка handover-актов (уже сделана в Фазе 19), новые типы актов,
изменение нумерации возвратов (`№42в1`), печать/шапка организации (Фаза 20),
редактирование «технических характеристик» устройства (`devices.notes`, вне scope
как и в Фазе 19).
</domain>

<decisions>
## Implementation Decisions

### Семантика правки возврата (общая)
- **D-01:** Правка возврата = **полная правка по дельте**, по образцу
  `ActService::update()` для handover-актов (Фаза 19, D-06). Сравнить старый и
  новый состав/значения; применить только дельту к устройствам и истории; каждое
  изменение пишет запись аудита. Транзакция одна, через единый writer
  (`act_service`), Tauri- и HTTP-адаптеры тонкие.
- **D-02:** Оптимистическая конкурентность через поле `version` (как в
  `delete_soft(id, version)` и `update()` Фазы 19) — применить и к правке
  возврата.

### Дата возврата (новое поле)
- **D-03:** У возврата появляется **собственная «Дата возврата»** —
  редактируемое поле с попапом выбора даты (календарь), **по умолчанию =
  сегодня**. Семантика: «когда реально вернули устройства по этому возврату».
  Не связана с `created_at_utc` (момент создания записи) и больше **не
  наследуется** от `handover_date_utc` родителя.
- **D-04:** Поле «Дата возврата» присутствует в **общем диалоге** «Возврат по
  акту №XXX» — то есть и при **создании** возврата (default = сегодня), и при
  **правке** (предзаполнено сохранённым значением). Реализация ACT-03 требует
  добавить это поле в текущий `ReturnModal.svelte` (сейчас поля даты в нём нет).
- **D-05:** **Отображаемая «Дата» возврата** (карточка `ActDetail.svelte:43`,
  список `ActListRow.svelte`, печать) = «Дата возврата», а не дата родителя.
  **Рекомендуемый подход (planner discretion):** хранить «Дату возврата» в
  существующей колонке `handover_date_utc` для строк `act_type='return'` —
  консистентно с Фазой 19 D-01 («Дата акта = `handover_date_utc` везде») и не
  требует нового столбца; в `do_return` сейчас туда пишется дата родителя
  ([act_service.rs:1232](crates/trackly-app/src/services/act_service.rs:1232)) —
  заменить на введённую дату возврата.
- **D-06:** **Сортировка списка «Возвраты»** — по «Дате возврата» (введённой
  пользователем), а не по `created_at_utc`/дате создания акта.
- **D-07:** **Дата архивации** родительского акта формируется **от «Даты
  возврата» полного/последнего возврата** (когда все устройства вернулись и
  `recompute_parent_archived` выставляет `archived`). Сейчас `archived` — это
  булев флаг без даты; появление «даты архивации» — новый derived-атрибут.
  **Разрешение хранения — planner discretion:** предпочтительно вычислять на
  чтении как MAX «Даты возврата» среди возвратов при полном возврате (без новой
  миграции), либо хранить `archived_at_utc` — на усмотрение планировщика.
- **D-08:** **Миграция существующих возвратов** (у которых нет собственной даты,
  сейчас наследуют дату родителя): backfill «Даты возврата» = `created_at_utc`
  (фактический момент оформления возврата — единственный доступный сигнал «когда
  вернули» для исторических данных). После backfill отображение/сортировка
  переключаются на «Дату возврата».

### Объём правки состава
- **D-09:** Полный **superset**: в диалоге правки можно
  1. **убрать** устройство из возврата (снять галочку) — **un-return**: устройство
     возвращается «в работу» на родительском акте с восстановлением прежнего
     статуса/локации/истории (откат эффектов возврата по дельте);
  2. **изменить** состояние/расположение уже возвращённого устройства;
  3. **добавить** в этот же возврат ещё не возвращённые (**outstanding**)
     устройства родителя — эффект как при `do_return` (устройство → «на складе» +
     состояние/локация).
- **D-10:** **Запрет пустого возврата.** Нельзя сохранить возврат, из которого
  сняты все устройства (0 позиций). Кнопка сохранения заблокирована при пустом
  составе. Чтобы убрать возврат целиком — **отдельное действие «Удалить»**
  (существующий `delete_soft` для возвратов), а не правка «в ноль».

### Валидация против последующей истории устройства
- **D-11:** Если возвращённое устройство **после** этого возврата уже участвует в
  другой истории (снова выдано новым актом, сменило статус/локацию так, что откат
  нарушил бы согласованность) — при попытке **убрать** его из возврата или
  **изменить** его эффект операция **блокируется с понятной ошибкой** (аналог
  D-08 Фазы 19 — валидация правки против существующих зависимостей). Force-override
  не делаем. Точное определение «конфликта» (напр. устройство больше не в том
  состоянии/локации, которое возврат установил; либо device_id завязан на более
  поздний handover-акт) — уточняется researcher/planner на основе путей
  side-effect'ов.

### Поля диалога правки
- **D-12:** Редактируемы: **«Кто возвращает» / «Кто принимает»** (ФИО;
  предзаполнены сохранёнными значениями возврата, сейчас в create наследуются от
  родителя со swap — см. [ReturnModal.svelte:59-63](ui/src/features/acts/ReturnModal.svelte:59)).
- **D-13:** Сохраняются **оба режима** ввода состояния/расположения: bulk
  «Применить ко всем» (`apply_to_all`) и per-row overrides — как в текущем
  create-возврате; в edit предзаполнены фактическими значениями возврата.
- **D-14:** **«Комплектация» позиций НЕ редактируется** — консистентно с Фазой 19
  D-09 (в форме правки handover-акта комплектация убрана из UI). Не добавляем поле
  комплектации в форму правки возврата.

### Claude's Discretion
- Переиспользовать ли `ReturnModal.svelte` в edit-режиме (prefill + submit в
  новый update-путь возврата) или отдельный компонент — переиспользование
  предпочтительно для консистентности (визуально диалог правки = диалог создания,
  как сделали для handover в Фазе 19 D-10).
- Форма нового backend-пути: отдельная команда `acts_update_return` /
  расширение `do_return` / переиспользование `ActReturnDto` + id возврата —
  на усмотрение планировщика (следовать паттерну delta-recompute из
  `ActService::update()`).
- Механизм хранения «даты архивации» (compute-on-read vs `archived_at_utc`
  столбец) — см. D-07.
- Точный date-picker компонент для «Даты возврата» — переиспользовать тот же
  паттерн, что для «Когда отдали» в `ActFormBody.svelte` (Фаза 19).
</decisions>

## Existing Code Insights

### Reusable Assets
- `ReturnModal.svelte` / `ReturnItemsTable.svelte` / `returnPayload.ts`: create-форма
  возврата уже собирает состав + состояние + расположение + ФИО — основа для
  edit-режима (prefill фактическими значениями возврата + submit в update-путь).
- `ActService::update()` (Фаза 19): готовый паттерн delta-recompute с валидацией
  против зависимостей, version-концуренцией и аудитом — прямой образец для правки
  возврата (D-01, D-11).
- `ActService::delete_soft` ветка `Return`: уже откатывает эффекты возврата
  (устройства обратно «в работу», `recompute_parent_archived`) — образец un-return
  дельты (D-09.1).
- date-picker «Когда отдали» из `ActFormBody.svelte` (Фаза 19) — переиспользовать
  для «Даты возврата» (D-03).

### Established Patterns
- Все записи через единый `act_service`, тонкие Tauri/HTTP-адаптеры, одна
  транзакция, один writer.
- `recompute_parent_archived(&tx, parent_id, now)` — единая точка пересчёта
  `archived` родителя; вызывать после любой дельты возврата (create/edit/un-return).
- «Дата акта = `handover_date_utc` везде» (Фаза 19 D-01) — распространяется на
  возврат: его `handover_date_utc` становится «Датой возврата» (D-05).
- Status-guard «в_работе» при возврате и обратный переход при un-return — учитывать
  в дельте.

### Integration Points
- Новый backend-путь правки возврата: Tauri-команда + `/api/v1` HTTP-хэндлер +
  клиент в `api.ts`.
- `onEdit` для возвратов: разблокировать кнопку в `ActDetail` для `act_type==='return'`,
  пробросить через `ActsPage` в `ReturnModal` в edit-режиме.
- Смена источника даты возврата затрагивает: список «Возвраты» (сортировка),
  карточку, печать возврата, логику даты архивации родителя.
- Миграция backfill «Даты возврата» существующих возвратов (D-08).

<specifics>
## Specific Ideas

- «Дата возврата» = когда **реально вернули** устройства по этому возврату; попап
  выбора даты (календарь), default = сегодня; независима от даты создания акта и от
  даты родителя (прямая цитата пользователя 2026-07-12).
- Список «Возвраты» сортируется по «Дате возврата», не по дате создания.
- Дата архивации родителя = «Дата возврата» полного/последнего возврата.
- Правка возврата визуально = тот же диалог «Возврат по акту №XXX», только
  предзаполненный (как в Фазе 19 диалог правки handover = диалог создания).

</specifics>
