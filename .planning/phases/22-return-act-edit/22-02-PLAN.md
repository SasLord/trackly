<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Payload → ActService::update_return | Untrusted `ActUpdateReturnDto` (device_ids, version, item values) crosses into the single-writer transaction; authorization happens at the transport layer (Plan 22-03), but ALL business-rule validation (D-10/D-11/type-guard/CAS) must be enforced here, inside the transaction, independent of any caller |
| ActService::update_return → devices/act_items/audit_log tables | All mutations happen inside one `BEGIN IMMEDIATE` transaction via the single writer task |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-22-02-01 | Tampering | update_return CAS check | mitigate | `act.version == payload.expected_version` checked before any mutation; reused `update_act_header_in_tx`'s `WHERE version=?` clause enforces it atomically at the header write too |
| T-22-02-02 | Tampering / business-rule bypass | D-11 device-drift guard | mitigate | 3-field snapshot compare (status_id + location_id + state) against the return's own `after_json`, run for every `removed`/changed-`retained` device BEFORE any mutation; `AppError::Conflict` aborts the whole transaction, no partial apply, no force-override path exists |
| T-22-02-03 | Tampering (type confusion) | update_return act_type guard | mitigate | Explicit `act.act_type != ActType::Return` check rejects a payload aimed at a handover act's id, mirroring update()'s own inverse guard |
| T-22-02-04 | Tampering (business-rule bypass) | D-10 empty-item-set guard | mitigate | `validate_update_return` rejects `items.is_empty()` before the transaction opens; a raw HTTP payload with an empty array cannot force-clear a return outside of the dedicated `delete_soft` path |
| T-22-02-05 | Repudiation | audit_log inserts per delta (add/remove/edit + final act-update row) | mitigate | Every device mutation (restore-on-remove, insert-on-add, update-on-retained-edit) writes a before/after audit row inside the same transaction, same convention as update()/do_return()/delete_soft() |
</threat_model>
