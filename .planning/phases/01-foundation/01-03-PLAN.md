Author the full v1 SQLite schema as 12 refinery forward-only migrations (V001..V012) covering every entity used by Phase 1 through Phase 8, write the PRAGMA application helpers, the refinery `run()` wrapper, the tempfile-backed `test_db()` helper, and the four schema-invariant integration tests that enforce the cross-cutting rules from D-Schema-01..05. **Downgrade protection** (PRAGMA user_version check on open) is implemented in Plan 04 alongside the writer/AppCtx; this plan just makes sure every migration writes the right `user_version`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Embedded SQL files → SQLite engine | Every `.sql` statement runs with full privileges at app startup; a malicious or malformed migration corrupts the DB |
| Future contributors → migration files | The forward-only invariant means a wrong migration can never be fixed in place — only superseded; a careless edit to an existing V0XX file could cause checksum drift (refinery detects this) |
| Migration runtime → user data integrity | A failed mid-migration leaves the schema in a partial state; downstream code assumes all-or-nothing |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Tampering | A future contributor edits an already-applied migration file (V001), changing its checksum and breaking refinery on existing DBs | mitigate | Refinery 0.8 records each migration's checksum in `refinery_schema_history`; on next run a mismatched checksum errors loudly. The error message is propagated as `AppError::Internal` and aborts startup. Documented in plan SUMMARY as "edits to V0XX files must be made via a new V0(N+1) migration" |
| T-03-02 | Denial of Service | A migration's CREATE INDEX on a 1M-row table hangs at startup (Phase 1 has no such risk; future phases might) | accept | Phase 1 tables are empty at first launch; index builds are instant. Phase 2+ documentation will note that schema migrations on >100k rows must be tested with a fixture DB before merge |
| T-03-03 | Tampering | Schema invariant violation slips into a later migration (e.g., a new user-mutable table missing `version`) | mitigate | `per_record_invariants.rs` test enumerates all user-mutable tables and asserts the four required columns; CI fails any PR that violates D-Schema-04 |
| T-03-04 | Information Disclosure | Sensitive data (e.g., AD passwords) accidentally written into `audit_log.before_json` / `after_json` | mitigate (Phase 5+) | Phase 1 establishes audit_log schema with no enforcement; Phase 5 introduces `Secret<T>` discipline in the service layer that serializes secrets as `"***"` before they reach the audit JSON. The clippy ban on `Debug` for `Secret<T>` blocks accidental log leakage |
| T-03-05 | Tampering | WAL/journal files left in inconsistent state after partial migration failure | mitigate | Refinery wraps each migration in its own transaction (default `set_grouped(false)` per RESEARCH Assumption A3); SQLite rolls back on error. Test `migration_idempotency.rs` confirms the second run picks up cleanly even after a successful first run; the inverse (failed-then-retry) is tested in Plan 04's downgrade-protection test |
| T-03-06 | Information Disclosure | DB file accessible to other processes on the same machine — Phase 1 puts DB in `<exe_dir>` per portable mode | accept | This is a deliberate design choice (portable mode = single-user single-machine usage); multi-user lockdown is out of scope until Phase 5's server mode introduces HTTPS+sessions. ASVS V8 partially addressed by `paths.rs` UNC rejection (Plan 02) |
| T-03-SC | Tampering | `refinery 0.8` itself compromised via supply-chain | mitigate | Listed in RESEARCH `## Package Legitimacy Audit` as Approved (CLAUDE.md pin + github.com/rust-db/refinery); `cargo-deny.yml` (Plan 01) checks advisories daily |

**Block on `high` severity:** T-03-01 and T-03-03 are mitigated by automated tests + refinery checksum tracking. T-03-04 is deferred to Phase 5 with explicit Phase 1 acceptance.
