# Phase 41.3: Вложения - Context

**Gathered:** 2026-11-07
**Status:** Ready for planning

<domain>
## Phase Boundary

Дать приложению хранение файлов, которого в нём нет: каталог вложений рядом с БД (имя файла =
хэш содержимого), метаданные в БД, безопасная отдача под сессией в обоих режимах (Tauri и LAN),
просмотр фото и PDF в попапе, деградация при потерянном файле, исключение каталога из git и
покрытие privacy-гейтом, обновлённая инструкция по переносу/бэкапу (ATT-01, ATT-02, ATT-03).

По итогам обсуждения вложения в 41.3 получают **видимых родителей уже сейчас**: заявка,
устройство, принтер, картридж. Фазы 41.4 (результаты ремонта) и 41.5 (вложения к сообщениям
переписки) переиспользуют ту же инфраструктуру и добавляют своих родителей.

Вне границы: печатная форма передачи в ремонт (GRPX-01), переписка (41.5), ремонтный цикл (41.4).

</domain>

<decisions>
## Implementation Decisions

### Родители и права доступа
- **D-01:** Вложения в 41.3 крепятся к четырём видам родителей: заявка, устройство, принтер,
  картридж. Модель привязки должна допускать добавление новых видов родителя (сообщение
  переписки в 41.5) без перестройки таблиц. Конкретную схему (универсальная `parent_kind +
  parent_id` или связующие таблицы) выбирает планировщик.
- **D-02:** Заявка: прикладывать файлы могут автор заявки и специалисты (роли Admin и Manager)
  **в любом статусе**, включая завершённые и отменённые (акт из сервиса может прийти позже).
- **D-03:** Устройство / принтер / картридж: прикладывают только специалисты (Admin, Manager).
  Сотрудник (Employee) **только просматривает** вложения устройств своих АРМ и привязанных к
  нему принтеров — ровно тот набор, что виден в его разделе «Устройства» (решение 10 модели
  групп). Вложения картриджей сотруднику не видны.
- **D-04:** Право на чтение/скачивание файла = право на чтение родителя. Проверка выполняется на
  сервере при каждой отдаче файла, миниатюры и списка вложений, на Tauri- и HTTP-транспорте
  одним кодом (паттерн D-REQ-01 / BOLA из `request_service.rs`). Знание хэша или id не даёт доступа.

### Загрузка
- **D-05:** Способы добавления: кнопка (системный диалог), перетаскивание в блок, вставка из
  буфера Ctrl+V (скриншоты).
- **D-06:** Несколько файлов за раз; каждый проверяется отдельно, отклонённый файл не срывает
  загрузку остальных и получает понятное сообщение. Предела числа файлов на родителя нет.
- **D-07:** Лимит размера одного файла по умолчанию 20 МБ; администратор меняет его в
  настройках. Проверка — на сервере (UI проверяет заранее только для удобства).
- **D-08:** Белый список: JPEG, PNG, WebP, GIF, HEIC/HEIF (конвертируется, D-10), PDF,
  DOC/DOCX, XLS/XLSX, ODT/ODS, TXT/CSV/LOG, ZIP, 7z. Исполняемые и прочие типы отклоняются.
  Тип определяется на сервере по содержимому (сигнатуре), а не только по заявленному MIME и
  расширению.
- **D-09:** WebP хранится как есть и открывается в попапе просмотра наравне с JPEG/PNG.
- **D-10:** HEIC/HEIF конвертируется в JPEG **на сервере** через libheif. Ограничение
  portable-сборки (никаких внешних DLL) сохраняется: исследователь проверяет статическую сборку
  libheif из исходников (например, `libheif-rs` с встроенной сборкой libheif) на трёх ОС CI
  (Windows MSVC, macOS aarch64, Linux). Если статическая сборка невозможна, нужно вернуться к
  пользователю, а не молча поставить DLL. Хэш и имя на диске считаются от сконвертированного
  JPEG; исходное имя сохраняется с заменой расширения на .jpg.

### Просмотр и отображение
- **D-11:** Блок «Вложения» в карточке родителя — плитки: у фото миниатюра, у остальных иконка
  типа; под плиткой имя, размер, кто и когда приложил. Миниатюры генерирует сервер при загрузке.
- **D-12:** Фото (JPEG/PNG/WebP/GIF и сконвертированный HEIC) и PDF открываются в попапе
  просмотра. В попапе можно листать стрелками ←/→ по просматриваемым вложениям того же
  родителя, есть кнопка «Скачать», фото увеличивается по клику. Остальные типы скачиваются.
- **D-13:** Потерянный файл (строка есть, файла нет) показывается плиткой «Файл не найден» и
  сообщением в попапе, без ошибки экрана и без красных тостов на каждом рендере.
- **D-14:** Приложение, удаление и восстановление вложения пишутся в «Историю» родителя
  событием через `audit_log` («Иванов И.И. приложил файл скан.pdf»). Имя файла в событии
  кликабельно, пока вложение не удалено.
- **D-15:** Новое, удалённое или восстановленное вложение доезжает до других открытых карточек
  без перезагрузки через существующий механизм `entities_changed` по WebSocket. Каждая новая
  мутация регистрируется в реестре инвалидации и гейте write-site.

### Удаление, восстановление, дубли
- **D-16:** Мягкое удаление: загрузивший (только своё вложение, только у родителя, к которому у
  него есть доступ) и специалисты (Admin, Manager, любое). Для них удалённое вложение исчезает
  из интерфейса полностью.
- **D-17:** Администратор (Admin) видит удалённые вложения с пометкой, кто и когда удалил, и
  может **восстановить** или **удалить навсегда**. Manager так не может.
- **D-18:** Файл на диске не трогается при мягком удалении. Он стирается только после «удалить
  навсегда» и только если на тот же хэш не ссылается ни одна другая строка (включая мягко
  удалённые). Одинаковое содержимое хранится на диске один раз.
- **D-19:** Вложения следуют за родителем: при мягком удалении родителя остаются и возвращаются
  при его восстановлении; при безвозвратном удалении родителя удаляются навсегда вместе с ним
  (с тем же правилом стирания файла по последней ссылке, D-18).
- **D-20:** Проверка целостности: при запуске фоново и в логе — файлы без строк старше суток
  удаляются (сироты после сбоя), строки без файлов помечаются потерянными (D-13). В настройках у
  администратора отчёт: число потерянных файлов, число сирот и занимаемое место.

### Хранение, бэкап, перенос
- **D-21:** Каталог по умолчанию — `attachments/` рядом с **файлом БД** (`db_path`), а не рядом
  с .exe: при переносе БД через конфиг вложения едут вместе с ней. В `trackly.config.toml`
  появляется необязательный `attachments_path` для отдельного диска. Путь резолвится
  без `dirs::*`, в духе `Paths` (portable-дисциплина).
- **D-22:** Авто-бэкап и ручной бэкап (`BackupService`) копируют вложения **инкрементно** в один
  общий каталог `attachments/` рядом с копиями БД: докопируются только отсутствующие файлы (имя
  = хэш, файлы неизменяемы). Любая хранимая копия БД находит в нём свои файлы. Ретенция копий БД
  этот каталог не чистит.
- **D-23:** `.gitignore` исключает каталог вложений; privacy-гейт отклоняет любой
  закоммиченный файл под `attachments/` по пути (бинарное содержимое гейт по тексту не
  проверяет). `README-portable.md` и `trackly.config.toml.example` называют каталог вложений и
  `attachments_path` в разделах переноса и бэкапа.

### Claude's Discretion
- Схема таблиц (D-01), формат хэша (SHA-256 рекомендован), раскладка каталога по подпапкам
  префикса хэша, размер и формат миниатюр, транспорт загрузки (multipart в axum и
  соответствующий путь для Tauri invoke), механизм отдачи файла в десктопе (asset/custom
  protocol или blob через invoke), где хранится настройка лимита (`app_settings`).
- Где именно в карточке устройства/принтера/картриджа/заявки стоит блок «Вложения» —
  определяет UI-SPEC по существующей компоновке карточек.

## Existing Code Insights

### Reusable Assets
- `crates/trackly-infra/src/paths.rs` (`Paths`): portable-резолв путей, отказ от UNC; сюда
  добавляется путь каталога вложений.
- `crates/trackly-app/src/services/backup_service.rs` (`BackupService`): бэкап БД через
  `rusqlite::backup` + ретенция; расширяется инкрементной копией вложений (`std::fs::copy`
  запрещён clippy — учесть).
- `crates/trackly-app/src/services/entities_broadcast.rs`: рассылка `entities_changed` (D-15).
- `ui/src/lib/components/Modal.svelte`: основа попапа просмотра (учесть
  `check-modal-isolation.mjs`).
- `ui/src/lib/utils/saveFile.ts`: скачивание в обоих режимах.

### Established Patterns
- Проверка доступа сотрудника к заявке: `request_service.rs` (D-REQ-01 / BOLA) — тот же
  принцип для вложений (D-04).
- Роли: `crates/trackly-core/src/auth.rs` — Admin, Manager, Employee.
- Один сервисный слой для Tauri и `/api/v1` (`crates/trackly-app/src/http/*`,
  `crates/trackly-app/src/tauri_cmds`); все записи через writer worker.
- UI-гейты `ui/scripts/check-*.mjs` в `pnpm lint`; гейт write-site
  `scripts/check-write-site-gate-untouched.mjs`.
- Миграции refinery; последняя V049. Перестройка таблиц с DROP родителя в транзакции
  refinery опасна (V042 стёр детей) — новые таблицы создавать, а не перестраивать.

### Integration Points
- Загрузки файлов (multipart) в проекте нет нигде — новый путь в axum (лимит тела запроса
  согласовать с D-07) и в Tauri.
- `spa_fallback` отдаёт index.html с 200 на неизвестный `/api/` — маршруты вложений покрыть
  тестом, иначе их отсутствие будет незаметно.
- Карточки: `ui/src/features/requests`, `devices`, `printers`, `cartridges`; настройки —
  `ui/src/features/settings` (лимит D-07, отчёт D-20, удалённые вложения D-17).

## Specific Ideas

- «Удалить навсегда» — так называется действие администратора для безвозвратного удаления.
- Удалённое вложение для загрузившего и Manager исчезает полностью; администратор видит его с
  пометкой и решает: восстановить или удалить навсегда.
- Вставка скриншота из буфера — частый случай в заявках.
