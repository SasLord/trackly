# Phase 41.3 Plan 09: Удаление, восстановление, очистка и история вложений Summary

Мягкое удаление (автор или Admin/Manager), восстановление и очистка (только Admin) с подсчётом ссылок на хеш внутри писателя, audit-записи и событие строго после коммита, закреплённое позиционным гейтом.

## Что сделано

- **Задача 1** (ba9d8d67): `delete` (Read + DeleteAny для персонала, иначе DeleteOwn с проверкой, что родитель ещё читаем), `restore`, `purge` (ManageDeleted = Admin; не удалённая строка -> `Validation`), `history`. Audit `custom:attachment_deleted/restored/purged` пишется в той же транзакции (payload: attachment_id + name). D-26: функций purge-for-parent нет. Тесты `attachments_lifecycle` (7): soft_delete, idempotent, restore (порядок сохраняется), purge_refcount, близнец с мягко удалённой строкой, race (6 раундов join upload vs purge: у живой строки блоб всегда есть), audit/history/events.
- **Задача 2** (969e72d5): `attachments_changed_gate` (8 тестов). Гейт A - каждый вызов `notify_changed(` стоит после конца `writer.execute(...)` с `.await`, `.send(` есть только в `notify_changed`. Гейт B - инвентарь от кода: каждая функция с `writer.execute(` обязана быть в таблице вердиктов (ingest, delete, restore, purge). Гейт C - нет `EntitiesChanged`, `broadcast_entities(`, `send_entities_changed`, `std::fs::copy` в attachment_service.rs и attachment_admin.rs.

## Результаты мутаций

Мутации в памяти (якорь проверяется на единственность внутри функции):
- `notify_changed(` внутри замыкания purge -> гейт A красный.
- send перед writer в delete (счёт вызовов +1) и чистый перенос (счёт тот же) -> красный в обоих случаях, то есть проверка позиционная.
- сырой `ws_tx...send(` в restore -> красный.
- лишний `writer.execute` в max_bytes -> гейт B красный.
- `broadcast_entities(` и `EntitiesChanged` -> гейт C красный.

Мутация реального файла на диске: `notify_changed` перенесён перед writer в restore -> реальные гейты A и B красные; файл восстановлен из копии, `git status` чист.
