## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Вложения в 41.3 крепятся к четырём видам родителей: заявка, устройство, принтер, картридж. Модель привязки должна допускать добавление новых видов родителя (сообщение переписки в 41.5) без перестройки таблиц. Конкретную схему (универсальная `parent_kind + parent_id` или связующие таблицы) выбирает планировщик.
- **D-02:** Заявка: прикладывать файлы могут автор заявки и специалисты (роли Admin и Manager) **в любом статусе**, включая завершённые и отменённые (акт из сервиса может прийти позже).
- **D-03:** Устройство / принтер / картридж: прикладывают только специалисты (Admin, Manager). Сотрудник (Employee) **только просматривает** вложения устройств своих АРМ и привязанных к нему принтеров - ровно тот набор, что виден в его разделе «Устройства» (решение 10 модели групп). Вложения картриджей сотруднику не видны.
- **D-04:** Право на чтение/скачивание файла = право на чтение родителя. Проверка выполняется на сервере при каждой отдаче файла, миниатюры и списка вложений, на Tauri- и HTTP-транспорте одним кодом (паттерн D-REQ-01 / BOLA из `request_service.rs`). Знание хэша или id не даёт доступа.
- **D-05:** Способы добавления: кнопка (системный диалог), перетаскивание в блок, вставка из буфера Ctrl+V (скриншоты).
- **D-06:** Несколько файлов за раз; каждый проверяется отдельно, отклонённый файл не срывает загрузку остальных и получает понятное сообщение. Предела числа файлов на родителя нет.
- **D-07:** Лимит размера одного файла по умолчанию 20 МБ; администратор меняет его в настройках. Проверка - на сервере (UI проверяет заранее только для удобства).
- **D-08:** Белый список: JPEG, PNG, WebP, GIF, HEIC/HEIF (конвертируется, D-10), PDF, DOC/DOCX, XLS/XLSX, ODT/ODS, TXT/CSV/LOG, ZIP, 7z. Исполняемые и прочие типы отклоняются. Тип определяется на сервере по содержимому (сигнатуре), а не только по заявленному MIME и расширению.
- **D-09:** WebP хранится как есть и открывается в попапе просмотра наравне с JPEG/PNG.
- **D-10:** HEIC/HEIF конвертируется в JPEG **на сервере** через libheif. Ограничение portable-сборки (никаких внешних DLL) сохраняется: исследователь проверяет статическую сборку libheif из исходников (например, `libheif-rs` с встроенной сборкой libheif) на трёх ОС CI (Windows MSVC, macOS aarch64, Linux). Если статическая сборка невозможна, нужно вернуться к пользователю, а не молча поставить DLL. Хэш и имя на диске считаются от сконвертированного JPEG; исходное имя сохраняется с заменой расширения на .jpg.
- **D-11:** Блок «Вложения» в карточке родителя - плитки: у фото миниатюра, у остальных иконка типа; под плиткой имя, размер, кто и когда приложил. Миниатюры генерирует сервер при загрузке.
- **D-12:** Фото (JPEG/PNG/WebP/GIF и сконвертированный HEIC) и PDF открываются в попапе просмотра. В попапе можно листать стрелками ←/→ по просматриваемым вложениям того же родителя, есть кнопка «Скачать», фото увеличивается по клику. Остальные типы скачиваются.
- **D-13:** Потерянный файл (строка есть, файла нет) показывается плиткой «Файл не найден» и сообщением в попапе, без ошибки экрана и без красных тостов на каждом рендере.
- **D-14:** Приложение, удаление и восстановление вложения пишутся в «Историю» родителя событием через `audit_log` («Иванов И.И. приложил файл скан.pdf»). Имя файла в событии кликабельно, пока вложение не удалено.
- **D-15:** Новое, удалённое или восстановленное вложение доезжает до других открытых карточек без перезагрузки через существующий механизм `entities_changed` по WebSocket. Каждая новая мутация регистрируется в реестре инвалидации и гейте write-site.
- **D-16:** Мягкое удаление: загрузивший (только своё вложение, только у родителя, к которому у него есть доступ) и специалисты (Admin, Manager, любое). Для них удалённое вложение исчезает из интерфейса полностью.
- **D-17:** Администратор (Admin) видит удалённые вложения с пометкой, кто и когда удалил, и может **восстановить** или **удалить навсегда**. Manager так не может.
- **D-18:** Файл на диске не трогается при мягком удалении. Он стирается только после «удалить навсегда» и только если на тот же хэш не ссылается ни одна другая строка (включая мягко удалённые). Одинаковое содержимое хранится на диске один раз.
- **D-19:** Вложения следуют за родителем: при мягком удалении родителя остаются и возвращаются при его восстановлении; при безвозвратном удалении родителя удаляются навсегда вместе с ним (с тем же правилом стирания файла по последней ссылке, D-18).
- **D-20:** Проверка целостности: при запуске фоново и в логе - файлы без строк старше суток удаляются (сироты после сбоя), строки без файлов помечаются потерянными (D-13). В настройках у администратора отчёт: число потерянных файлов, число сирот и занимаемое место.
- **D-21:** Каталог по умолчанию - `attachments/` рядом с **файлом БД** (`db_path`), а не рядом с .exe: при переносе БД через конфиг вложения едут вместе с ней. В `trackly.config.toml` появляется необязательный `attachments_path` для отдельного диска. Путь резолвится без `dirs::*`, в духе `Paths` (portable-дисциплина).
- **D-22:** Авто-бэкап и ручной бэкап (`BackupService`) копируют вложения **инкрементно** в один общий каталог `attachments/` рядом с копиями БД: докопируются только отсутствующие файлы (имя = хэш, файлы неизменяемы). Любая хранимая копия БД находит в нём свои файлы. Ретенция копий БД этот каталог не чистит.
- **D-23:** `.gitignore` исключает каталог вложений; privacy-гейт отклоняет любой закоммиченный файл под `attachments/` по пути (бинарное содержимое гейт по тексту не проверяет). `README-portable.md` и `trackly.config.toml.example` называют каталог вложений и `attachments_path` в разделах переноса и бэкапа.

## Summary

Фаза строит новую подсистему «файлы на диске + метаданные в БД» поверх существующего каркаса: один сервисный слой (`AttachmentService`, новый файл в `crates/trackly-app/src/services/`), тонкие адаптеры Tauri (`tauri_cmds/attachments.rs`) и axum (`http/attachments.rs`), запись только через `WriterHandle`. Схема - одна таблица `attachments` (полиморфный `parent_kind + parent_id`, без внешних ключей на изменяемые родители - конвенция V049), новая миграция V050 (только CREATE, никаких DROP/перестроек). Файлы: `attachments/<2 hex>/<64 hex sha256>` без расширения, миниатюры `attachments/thumbs/<hash>.jpg`, временные `attachments/.tmp/`. Критично для корректности: финальный `rename` из temp в хэш-путь и физическое стирание по последней ссылке выполняются **внутри замыкания writer** (writer однопоточный) - это закрывает гонку «загрузка дубликата vs удалить навсегда».

Самая рискованная часть - **D-10 (HEIC без DLL)**. Проверено: `libheif-sys 5.3.1` с `embedded-libheif` собирает libheif 1.23.1 из исходников через cmake, **но не встраивает декодер HEVC (libde265)** - он берётся из системы; без него HEIC (HEVC) не декодируется. На macOS embedded-сборка подтянула из Homebrew x265/x264 (GPL), aom, dav1d... и на этой машине не слинковалась. На Windows MSVC флаг `embedded-libheif` игнорируется: build.rs идёт через vcpkg. Статическая сборка без DLL **реалистична только на Windows** (vcpkg-триплет `x64-windows-static-md`, `libheif[core,libde265]`, вручную - не через `cargo-vcpkg`, потому что дефолтные фичи порта включают `hevc` = x265, GPL-2.0+). На macOS/Linux «без внешних библиотек» недостижимо без собственной сборки libde265. Плюс лицензии: libheif и libde265 - LGPL-3.0, и HEVC-патентный риск. **Это решение нужно вернуть пользователю** (см. Open Questions Q1); план должен содержать спайк-волну и Cargo-фичу `heic`.

**Primary recommendation:** Реализовать всё, кроме HEIC, на pure-Rust стеке (`sha2` + `infer 0.22` + `image 0.25.10` с `webp`/`gif`), вынести HEIC в опциональную Cargo-фичу `heic` (libheif-rs 3.0, Windows через vcpkg-статик, остальные платформы - отказ `heic_failed` до решения пользователя), загрузку делать «один файл на запрос, родитель в query», отдачу - `ServeFile::new_with_mime` (HTTP) и custom URI scheme `trackly-att` (Tauri), событие D-15 - новым вариантом `WsEvent::AttachmentsChanged` (см. Q2).

### Pattern 1: Схема V050 (выбор планировщика D-01 - рекомендация)
**What:** одна таблица, полиморфная привязка, без FK на изменяемые таблицы (V049: «перестройка родителя не должна каскадом стереть детей»).
```sql
-- Source: конвенция V049__act_group_effects.sql (внутренняя)
CREATE TABLE attachments (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  parent_kind        TEXT    NOT NULL,            -- 'request' | 'device' | 'cartridge' (+ 'message' в 41.5); БЕЗ CHECK - валидация в Rust
  parent_id          INTEGER NOT NULL,            -- БЕЗ FK (полиморфная привязка)
  original_name      TEXT    NOT NULL,            -- уже санитизированное, <=255 символов
  mime               TEXT    NOT NULL,            -- итоговый (после конвертации HEIC), из сигнатуры
  size_bytes         INTEGER NOT NULL,
  content_hash       TEXT    NOT NULL,            -- sha256 hex (нижний регистр, 64 символа) сохранённых байтов
  uploaded_by_user_id INTEGER NULL,               -- БЕЗ FK; NULL = unlocked desktop (Identity.user_id None)
  created_at_utc     INTEGER NOT NULL,
  deleted_at_utc     INTEGER NULL,
  deleted_by_user_id INTEGER NULL
);
CREATE INDEX idx_attachments_parent ON attachments(parent_kind, parent_id, created_at_utc, id);
CREATE INDEX idx_attachments_hash   ON attachments(content_hash);
```
`uploaded_by_name`/`deleted_by_name` в DTO - LEFT JOIN `users` (`full_name`); `null` -> «Пользователь удалён» (UI-SPEC §12). Колонки `version`/`updated_at_utc` не нужны: строка неизменяема, кроме soft-delete/restore (последние - идемпотентные UPDATE `WHERE deleted_at_utc IS [NOT] NULL`). Принтер - это строка `devices` (таблица `printers.device_id UNIQUE REFERENCES devices`), поэтому `parent_kind='device'` покрывает принтеры (UI-SPEC так и пишет) [VERIFIED: migrations/V020__printers.sql].

### Pattern 2: Файловая раскладка и пайплайн (ATT-01)
```
<attachments_dir>/
  ab/abcdef...(64 hex, без расширения)   # финальные файлы
  thumbs/<hash>.jpg                      # производные, пересоздаются лениво; в бэкап НЕ копируются
  .tmp/<random>                          # загрузка в процессе; чистится сканом (>24ч)
```
Имя на диске - только валидированная hex-строка (`^[0-9a-f]{64}$`); оригинальное имя на диск не попадает никогда (нет path traversal, нет зарезервированных имён Windows, нет исполняемых расширений).

Пайплайн `ingest(parent, name, stream)`:
1. **До чтения тела:** `authorize_attach(identity, parent)` (роль + родитель живой), лимит из `app_settings` (по умолчанию 20 МиБ, потолок 100 МиБ).
2. Стрим в `NamedTempFile::new_in(.tmp)`, считая байты; превышение лимита -> прерывание, `too_large`; 0 байт -> `empty`.
3. `spawn_blocking` (+ `Semaphore(2)` на тяжёлые изображения): прочитать голову 8-64 КиБ -> sniff (§Sniffing) -> при HEIC конвертация во второй temp -> SHA-256 финальных байтов потоком -> миниатюра (только фото) в `thumbs/`.
4. `writer.execute(move |conn| { tx; INSERT attachments; INSERT audit_log; если финального файла нет - rename temp->final иначе удалить temp; commit })`.
5. После `.await?` и **вне** замыкания - рассылка события (правило D-04 41.7).
`fsync` (`File::sync_all`) на temp перед rename. Windows: rename может падать с `ERROR_ACCESS_DENIED/SHARING_VIOLATION` из-за антивируса - 3 повтора по 50-200 мс. Если коммит упал после rename - остаётся сирота, его уберёт скан через сутки.

### Pattern 3: Авторизация (D-02/D-03/D-04/D-16/D-17)
Один метод `AttachmentService::authorize(parent: ParentRef, caller: &Identity, intent: Read|Attach|Delete|ManageDeleted) -> Result<Perms, AppError>`; **все** пути (list, file, thumb, upload, delete, restore, purge, Tauri protocol, HTTP GET) обязаны идти через него. Матрица:

| Родитель | Read | Attach | Delete чужое / своё | Restore / Purge |
|----------|------|--------|---------------------|-----------------|
| request | Admin, Manager, Employee-автор (`requested_by_user_id == caller.user_id`; повторить логику `RequestService::get`) | то же (в любом статусе, D-02) | Admin/Manager - любое; загрузивший - своё | Admin |
| device/printer | Admin, Manager; Employee - только устройства своего набора (см. Q3) | Admin, Manager | Admin/Manager - любое; Employee - никогда | Admin |
| cartridge | Admin, Manager | Admin, Manager | Admin/Manager | Admin |
Родитель soft-deleted -> `NotFound`/`Forbidden` для всех на чтение/загрузку (вложения «возвращаются при восстановлении», D-19). Заявки `request_type='ad_register'` - вложения запрещены (Admin-only жизненный цикл, WR-04 в `request_service.rs`) [ASSUMED]. «Загрузивший удаляет своё» - сравнение `uploaded_by_user_id == caller.user_id` **и** повторная проверка доступа к родителю (D-16).

### Pattern 4: Отдача файла - HTTP (LAN)
```rust
// Source: tower-http 0.6 ServeFile::new_with_mime (docs.rs/tower-http) [CITED]; заголовки - RFC 6266
GET /api/v1/attachments/{id}/file    // inline для фото/PDF, attachment для остальных
GET /api/v1/attachments/{id}/thumb   // image/jpeg; ленивая регенерация если файла миниатюры нет
```
Обработчик: `session_identity` -> загрузить строку -> `authorize(Read)` -> путь строится ТОЛЬКО из `content_hash` строки БД (валидация hex) -> `ServeFile::new_with_mime(path, &mime).oneshot(req)` -> переопределить заголовки:
- `Content-Type` - из БД (из сигнатуры), никогда от клиента;
- `Content-Disposition`: `inline` только для `image/{jpeg,png,webp,gif}` и `application/pdf`, иначе `attachment`; `filename="<ascii-fallback>"; filename*=UTF-8''<percent-encoded>`; из имени убрать CR/LF/`"`/`\`;
- `X-Content-Type-Options: nosniff` (уже глобально);
- `Cache-Control: private, no-store` для file (доступ может быть отозван); для thumb допустим `private, max-age=...` - но тоже только `private`.
Файла нет (`NotFound` от ServeFile / `metadata` ошибка) -> 404 JSON `AppError::NotFound{entity:"attachment_file"}`, UI показывает «Файл не найден» (D-13). Список возвращает флаг `missing` через `Path::exists()` на каждую строку (дёшево, всегда актуально; отдельный постоянный флаг в БД не нужен, иначе устареет после возврата файла из бэкапа).

### Pattern 5: Отдача - десктоп (Tauri)
`tauri::Builder::register_asynchronous_uri_scheme_protocol("trackly-att", |ctx, req, responder| ...)`: парсит `/<id>/<file|thumb>`, берёт `AppCtx` из `ctx.app_handle().state()`, identity - `resolve_tauri_identity(&ctx)`, вызывает **тот же** `AttachmentService::open_for_read` и отвечает байтами (Range не реализуем; ≤100 МиБ в память допустимо). Заголовки ответа: `Content-Type`, `X-Content-Type-Options: nosniff`, **`Access-Control-Allow-Origin: *`** (иначе `fetch()` из `tauri://localhost`/`http://tauri.localhost` на другую схему блокируется - документ Tauri: origins различаются по платформам [CITED: docs.rs/tauri Builder]). URL на фронте через `convertFileSrc('<id>/thumb','trackly-att')` из `@tauri-apps/api/core` (формирует `trackly-att://localhost/...` на macOS/Linux и `http://trackly-att.localhost/...` на Windows) [CITED: v2.tauri.app JS API core]. В браузере `attachmentUrl()` возвращает `/api/v1/attachments/<id>/...`. Скачивание в обоих режимах: `fetch(url)` -> `arrayBuffer` -> существующий `saveFile` (один путь). Tauri-CSP в `tauri.conf.json` = `null` - ограничений нет [VERIFIED: tauri.conf.json].

### Pattern 6: Загрузка - транспорт
- **LAN:** `POST /api/v1/attachments_upload?parent_kind=request&parent_id=5` (имя маршрута = имя Tauri-команды, чтобы гейт `http_route_parity.rs` прошёл), тело `multipart/form-data` с **одним** полем-файлом. Родитель в query -> авторизация и лимит проверяются до чтения тела. Маршрут оборачивается `DefaultBodyLimit::max(100 МиБ + 1 МиБ)` (axum по умолчанию режет Multipart на 2 МБ [CITED: axum multipart.rs docstring]); точный лимит из `app_settings` проверяется в цикле `field.chunk()`; заранее смотреть `Content-Length`. Второе файловое поле -> ошибка.
- **Tauri:** команда с `tauri::ipc::Request`; фронт: `invoke('attachments_upload', uint8array, { headers: { 'x-att-parent-kind': 'request', 'x-att-parent-id': '5', 'x-att-name': encodeURIComponent(name) } })`; тело - `InvokeBody::Raw` [CITED: v2.tauri.app/develop/calling-rust]. Имя в заголовке - percent-encoded (кириллица в заголовках недопустима). Лимит - сравнить `body.len()` до записи на диск.
- Файлы грузятся строго последовательно (UI-SPEC §7.3), прогресса нет.
Один и тот же `AttachmentService::ingest(reader: impl AsyncRead|Bytes, ...)`; HTTP отдаёт поток, Tauri - `Cursor`.

### Pattern 7: D-14 события и D-15 рассылка
- **audit_log**: `AuditEntry { entity_type: "request" | "device" | "cartridge", entity_id: parent_id, action: "custom:attachment_added" | "custom:attachment_deleted" | "custom:attachment_restored" | "custom:attachment_purged", payload_json: {"attachment_id":N,"name":"..."} }` в той же транзакции writer. Заявка: `get_history` выбирает все строки `entity_type='request'` и просто отдаёт их `action` - нужна только нотация метки в UI (`actionLabel`) [VERIFIED: requests_sqlite.rs:462]. Для устройств/принтеров общей истории нет - новый запрос `attachments_history(parent)` по `audit_log` с префиксом `custom:attachment_` (UI-SPEC §10.3). Признак состояния события (`active/deleted/purged`) считать JOIN-ом к `attachments` по `attachment_id` из payload; «стёрт навсегда» = строки нет.
- **WS (D-15)**: см. Q2 - существующий `WsEvent::EntitiesChanged` несёт только `placeIds/deviceIds/groupIds`, виден только Admin/Manager и по D-17 41.7 пустой `placeIds` означает «перезагрузить дерево мест» - для вложений заявок/картриджей непригоден. Рекомендация: **добавить вариант** `WsEvent::AttachmentsChanged { parent_kind, parent_id, requested_by_user_id: Option<i64> }` (camelCase, snake_case тег) с `is_visible_to`: Admin/Manager - всегда; Employee - только если `requested_by_user_id == identity.user_id` (по образцу `RequestStatusChanged`, BOLA T-11-03-I). Рассылка - после коммита, вне замыкания; `ws.ts`/`bindings-phase6.ts` - добавить вариант в union; Tauri-мост пересылает без изменений.

### Anti-Patterns to Avoid
- **Имя файла пользователя как путь на диске** - только `content_hash`.
- **Rename/purge вне writer** - гонка «дубликат vs удалить навсегда» теряет файл.
- **`std::fs::copy`** - запрещён clippy (`disallowed_methods`); для копирования использовать `std::fs::File::open` + `File::create` + `std::io::copy` (не запрещён) в temp-имя с последующим `rename`.
- **Доверие `Content-Type` клиента** и отдача `inline` для чего-либо кроме растровых фото и PDF; SVG/HTML/JS не в белом списке.
- **Постоянный флаг `missing` в БД как источник правды** - устаревает; считать при чтении.
- **Рассылка внутри `writer.execute`** (нарушает D-04 41.7: на откате возникает ложное событие).
- **Перестройка существующих таблиц в V050** (урок V042).
- **Вставка JSON-массивов байтов** для файлов (`apiCall` превращает бинарный ответ в `number[]`): для файлов не использовать `apiCall` ни в одну сторону.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Определение типа по сигнатуре (OOXML/ODF/OLE2/7z) | собственные magic-таблицы | `infer 0.22` | Разбор OOXML/ODF/OLE2 нетривиален; тесты на мутантах |
| Multipart-парсинг | ручной разбор boundary | `axum::extract::Multipart` (multer) | Вложенные границы, лимиты, потоковость |
| Range/If-Modified/Content-Length | собственный стриминг | `tower_http::services::ServeFile` | PDF-просмотрщики шлют Range |
| Ресайз/декод изображений, EXIF-ориентация | свой декодер | `image 0.25` (+`Limits`) | Безопасность декодеров, bomb-лимиты |
| SHA-256 | свой | `sha2` | - |
| Percent-encoding для `filename*` | «на глаз» | `percent-encoding` | RFC 5987 набор символов |
| Атомарная запись | запись сразу в финальное имя | temp в том же каталоге + `rename` | Обрыв посреди записи |
| HEIC-декод | собственный HEVC | `libheif` (Q1) | Невозможно в объёме фазы |

**Key insight:** весь риск фазы сидит на стыках (доступ - отдача - заголовки - WebView), а не в самих алгоритмах; каждый стык должен иметь тест с реальным `build_router`/`AppCtx` (HTTP) и проверкой заголовков.

## Sniffing: белый список D-08 (ATT-01)

Правило: тип = результат сигнатуры по первым байтам; расширение и заявленный MIME только подсказка/нормализация имени.

| Класс | Сигнатура / решение | Хранимый mime | inline |
|-------|---------------------|---------------|--------|
| JPEG/PNG/GIF/WebP | `infer::image::is_jpeg/png/gif/webp` + проверка заголовка `image` (размеры читаются) | `image/jpeg` ... | да |
| HEIC/HEIF | `infer::image::is_heif` (бренды `heic/heix/mif1`-совместимые); `avif` **не** принимать | после конвертации `image/jpeg` | да |
| PDF | `%PDF-` в начале | `application/pdf` | да |
| DOCX/XLSX | `infer::doc::is_docx/is_xlsx` | OOXML mime | нет |
| ODT/ODS | `infer::odf::is_odt/is_ods` (первая запись zip `mimetype`) | `application/vnd.oasis.opendocument.*` | нет |
| DOC/XLS | `infer::doc::is_doc/is_xls` - **открывает CFB и требует весь файл** (`cfb::CompoundFile::open`) | `application/msword`, `application/vnd.ms-excel` | нет |
| ZIP | `infer::archive::is_zip` (всё прочее zip, вкл. PPTX/ODP/неопознанный OOXML - как обычный ZIP, скачивается) | `application/zip` | нет |
| 7z | `37 7A BC AF 27 1C` | `application/x-7z-compressed` | нет |
| TXT/CSV/LOG | сигнатуры нет: принять, если расширение из {txt,csv,log} и в первых 8 КиБ нет NUL-байта и ни один бинарный матчер не сработал; кодировку не требовать (cp1251 допустима) | `text/plain` | нет |
Всё прочее (MZ/PE, ELF, Mach-O, `#!`-скрипты, SVG/HTML, `.bat/.ps1/.js` с text-содержимым) -> `type_not_allowed`. Для OLE2 (`D0 CF 11 E0 A1 B1 1A E1`) дочитать файл целиком из temp (≤ лимит) и подать `infer` весь буфер; **тест на усечённый буфер обязателен** (на неполных данных `is_doc` вернёт `false`). OOXML-эвристика `infer` ищет внутренние заголовки в окнах до ~6 КБ - подавать голову минимум 32 КиБ. Если сигнатура даёт ZIP, а расширение `.docx` - принять как ZIP (скачивается; безопасности не вредит). Расширение/имя не пере-пишем (кроме HEIC -> `.jpg`).

## Целостность при старте (D-20)
Запуск: `tokio::spawn` после `AppCtx::build` (не в горячем пути старта, не блокирует окно). Шаги в `spawn_blocking`: (1) обход `<h2>/*`: имя -> (размер, mtime), `.tmp/` - отдельно; (2) один read-запрос `SELECT content_hash, SUM(size_bytes)..., COUNT(*) GROUP BY content_hash` (включая soft-deleted); (3) **сироты** = файлы не из множества И `mtime` старше 24 ч -> удалить (+ их миниатюры; temp в `.tmp/` старше 24 ч); моложе суток не трогать (идущая загрузка/сбой коммита); (4) **потерянные** = хэши из БД без файла -> число строк; (5) занято на диске (сумма размеров) и число файлов; (6) отчёт JSON в `app_settings` (`attachments_integrity_report`: `{checked_at_utc, files, bytes, lost, orphans_removed, orphans_young, deleted_rows, deleted_bytes}`) одной записью через writer; (7) `tracing::info!/warn!`. Удаление сирот должно проверять имя на `^[0-9a-f]{64}$` и что путь внутри каталога (не следовать symlink-ам: `symlink_metadata`). Если каталог недоступен (диск отключён) - **не удалять ничего** и не помечать все строки потерянными: скан завершается отчётом `unavailable` (защита от «каталог не примонтирован -> всё сирота/потеряно»). Ошибка скана не падает приложение.

## Common Pitfalls

### Pitfall 1: `X-Frame-Options: DENY` глобально ломает PDF в `<iframe>` по LAN
**What goes wrong:** слой `security_headers` в `http/mod.rs` через `SetResponseHeaderLayer::overriding` ставит `x-frame-options: DENY` и жёсткий CSP на **каждый** ответ, включая файл вложения; DENY запрещает даже same-origin фрейм - PDF в попапе пустой. Существующее `frame-src 'self' blob:` относится к документу-родителю, а не к ответу-фрейму.
**How to avoid:** для маршрута `/api/v1/attachments/{id}/file` ответ должен нести `X-Frame-Options: SAMEORIGIN` (и CSP `frame-ancestors 'self'`). Реализация: заменить `overriding` на `if_not_present` для `x-frame-options` (и/или исключить путь) - с обновлением теста `security_headers.rs` (сейчас ожидает DENY на всё). Для `<img>` фрейминг не нужен.
**Warning signs:** в консоли браузера «Refused to display ... in a frame because it set 'X-Frame-Options' to 'deny'». [VERIFIED: чтение кода http/mod.rs]; поведение PDF-плагина под строгим CSP в Chrome/Edge/Firefox - [ASSUMED], проверить живьём.

### Pitfall 2: Встроенный PDF-просмотр в WKWebView/WebView2 не подтверждён
В проекте **нет** ни одного рабочего `<iframe>` с PDF (только `srcdoc` HTML и blob-скачивание) [VERIFIED: grep]. PDF из custom-схемы в WKWebView/WebView2 - не проверено (LOW). UI-SPEC §8.4 уже допускает деградацию «Скачать»; план должен включить human-verify пункт и запасной вариант (временный файл + `shell open`, паттерн уже есть для печати).

### Pitfall 3: Гонка дубликат/purge
Два пути записи (upload и purge) работают с одним файлом-по-хэшу. Все проверки «файл есть? ссылок ноль?» и все rename/remove - только внутри `writer.execute` (сериализованы). Тест: параллельный upload того же содержимого + purge последнего ссылающегося ряда.

### Pitfall 4: Ранний отказ 413 без чтения тела
Если сервер отвечает, не дочитав тело, браузер может увидеть сброс соединения вместо 413 («Failed to fetch»). Смягчение: UI уже проверяет размер заранее (§7.2); серверный отказ в тестах проверять через `oneshot`, а в UAT - файлом чуть больше лимита.

### Pitfall 5: Multipart лимит 2 МБ по умолчанию и порядок полей
Без `DefaultBodyLimit` на маршруте загрузка >2 МБ падает; `Multipart` должен быть последним extractor-ом. Родитель - в query, не в полях multipart (иначе нужно требовать порядок полей).

### Pitfall 6: Кириллица в заголовках Tauri `invoke`
Имя файла в `headers` - только percent-encoded ASCII; декодировать на сервере и **затем** санитизировать (basename по `/` и `\`, управляющие символы, длина ≤255).

### Pitfall 7: `infer` на неполных данных
`is_doc/is_xls` - только на полном файле; OOXML/ODF - голова ≥32 КиБ. Тесты на усечённом буфере.

### Pitfall 8: Windows - антивирус и блокировки
Свежесозданный файл может быть занят сканером: rename/remove с повтором; не держать открытые дескрипторы; `remove_file` на открытом файле (просмотр в другом потоке) - ошибка, не паника.

### Pitfall 9: Скан целостности при недоступном каталоге
Отключённый диск превращает все строки в «потерянные», а при перемонтировании пустого каталога - все файлы в «сироты». Скан сначала проверяет доступность корня и ничего не удаляет при сомнении; сироты - только старше 24 ч.

### Pitfall 10: Идентификатор доступа для Employee-устройств не определён (Q3)
Набор «устройства своих АРМ + привязанные принтеры» определяет фаза 41.6, каталог которой пуст. Реализовывать «по догадке» - риск утечки. Запись по умолчанию - запрет.

### Pitfall 11: Миграции и FK
V050 - только `CREATE`; без FK на `requests/devices/cartridges/users` (V042: DROP родителя в refinery-транзакции каскадом стирает детей; `PRAGMA foreign_keys=OFF` внутри транзакции refinery не действует) [VERIFIED: комментарий V049, память проекта].

### Pitfall 12: CLAUDE.md расходится с Cargo.toml
Реальные версии: rusqlite 0.38, refinery 0.9, tower-sessions 0.15, tauri-specta rc.21 - смотреть `Cargo.toml`, не CLAUDE.md.

### Загрузка в temp с лимитом (axum)

```rust
// Source: axum 0.8 Multipart docs (axum/src/extract/multipart.rs) [CITED]
async fn handler_upload(State(ctx): State<AppCtx>, session: Session,
                        Query(q): Query<UploadQuery>, mut mp: Multipart)
                        -> Result<Json<AttachmentDto>, AppErrorResponse> {
    let who = session_identity(&session).await?;
    let perm = ctx.attachments.authorize_attach(&who, q.parent()).await?;      // ДО чтения тела
    let limit = ctx.attachments.max_bytes().await?;
    let mut field = mp.next_field().await?.ok_or(bad("attachment_empty"))?;
    let name = field.file_name().unwrap_or("файл").to_owned();
    let mut staged = ctx.attachments.begin_staging()?;                         // NamedTempFile::new_in(.tmp)
    while let Some(chunk) = field.chunk().await? {
        staged.write(&chunk, limit)?;                                          // Err(too_large) при превышении
    }
    if mp.next_field().await?.is_some() { return Err(bad("single_file_only")); }
    Ok(Json(ctx.attachments.ingest(&who, perm, name, staged).await?))
}
```

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | косвенно | сессии `tower-sessions` (cookie `Secure`, `HttpOnly`, `SameSite=Strict`) |
| V3 Session Management | да | GET файлов/миниатюр только под сессией; Tauri - desktop identity |
| V4 Access Control | **да (ядро)** | `AttachmentService::authorize` на каждом пути; BOLA как `RequestService::get` |

| V14 Config | да | потолок размера, `DefaultBodyLimit` |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Обход каталога через имя файла | Tampering | Путь только из `content_hash` по `^[0-9a-f]{64}$`; имя - только в БД и в заголовке (санитизированное) |
| IDOR/BOLA по id вложения | Info disclosure | `authorize(parent)` на list/file/thumb/upload/delete; тесты на оба транспорта |
| Stored XSS через SVG/HTML/текст | Elevation | В белом списке их нет; `inline` только растровые фото и PDF; `nosniff`; остальное `attachment` |
| Подмена типа (`.pdf` с PE внутри) | Spoofing | Тип по сигнатуре, mime из БД, не от клиента |
| Header injection в `Content-Disposition` | Tampering | Убрать CR/LF/`"`/`\`; `filename*` через percent-encoding |
| Decompression bomb (изображения), zip bomb | DoS | `image::Limits`; архивы не распаковываются; лимит тела |
| Исчерпание диска/памяти большими загрузками | DoS | Потолок 100 МиБ, `DefaultBodyLimit`, раннее отклонение по `Content-Length`, семафор на декод; файловый I/O вне writer |
| Гонка dedup/purge -> потеря файла | Tampering | rename/remove только в замыкании writer |
| CSRF на multipart-загрузку (CORS-«простой» запрос) | Tampering | `SameSite=Strict` cookie; нет CORS-разрешений |
| Утечка через логи/аудит | Info disclosure | Имена файлов в `audit_log`/логе допустимы (не в репозитории); в тестах и фикстурах только вымышленные имена |
| Вредоносные Office/ZIP-вложения | Elevation | Не распаковываются и не исполняются; скачивание как есть; антивирусная проверка вне области (принятый остаточный риск) |
| Реальные данные в репозитории | Info disclosure | privacy-гейт по пути; фикстуры генерируются; `.gitignore` |
