<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Sidebar navigation -> `/showcase` route | Client-side UI gate only, matching the existing `/users`/`/settings` precedent exactly. A `manager`/`employee` who manually edits the URL hash to `#/showcase` would render the page client-side (same as they could today with `#/users`) — this is a pre-existing, accepted app-wide pattern, not a new gap introduced by this plan. |
| Showcase page content | No privileged/business data is rendered anywhere on this page — every section renders hardcoded Russian demo strings and locally-scoped `$state`. There is no `apiCall`/Tauri `invoke`/axum fetch anywhere in the showcase feature tree. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|--------------|-----------------|
| T-24-07-01 | Elevation of Privilege | `/showcase` route + sidebar entry | accept | Client-side-only gating via `getVisibleItems(role)` with `roles: ['admin']`, identical mechanism and identical residual risk to the already-shipped `/users`/`/settings` routes (Phase 5/7). No new authorization pattern is introduced; actual protection of any sensitive data remains server-side per the project's existing "all API calls go through backend authorization regardless of UI sentinel" design note (App.svelte D-Desktop-01/02). Because the showcase renders zero privileged data, a `manager` reaching it via manual URL edit gains no information they didn't already have access to via the UI chrome itself — this exactly matches the accepted risk profile of the 2 precedent routes. |
| T-24-07-02 | Information Disclosure | Showcase demo content | accept | All demo text/values are hardcoded static strings compiled into the bundle; nothing rendered is derived from a live API response, a database row, or any other runtime data source. |
| T-24-07-03 | Tampering (XSS) | Section components (`{@render children?.()}` / `{tab.label}` interpolation) | accept | No `{@html}` is used anywhere in this plan's files or any of the 5 section components built in Plans 24-02..06 (verified via `grep -rln "@html" ui/src/lib/components ui/src/pages` returning empty) — all interpolation is Svelte's default-escaped text binding. No XSS sink is introduced. |

No new ASVS-relevant control surface beyond the pre-existing, already-accepted sidebar-filter pattern (V4,
minor) is introduced by this plan.
