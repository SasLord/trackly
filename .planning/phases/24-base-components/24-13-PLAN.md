<objective>
Close two WARNING-level regressions introduced by this phase's own prior gap-closure plans (24-REVIEW.md
WR-05 and WR-06):

- **WR-05** (introduced by 24-09) — `.badge-m-success.badge-m-count` / `.badge-m-warning.badge-m-count` /
  `.badge-m-danger.badge-m-count` / `.badge-m-accent.badge-m-count` each redeclare `height`/`font-size`/
  `padding`/`border-radius` at specificity (0,2,0), which beats `.badge-m-sm`'s (0,1,0) — so
  `<Badge size="sm" appearance="count">` silently renders at `md` dimensions for 4 of 5 tones. Separately, the
  neutral tone's base `.badge-m-count` has no border while the other 4 do, so a row of same-appearance badges
  in different tones has mismatched height/border — the showcase's `BadgeSection` exists specifically to catch
  this and currently normalizes it as "how it looks."
- **WR-06** (introduced by 24-08) — 24-08 changed `Input.svelte` to use native `bind:value` to fix two-way
  binding (CMP-02). For `<input type="number">`, Svelte's `bind:value` applies its own numeric coercion at the
  DOM level (empty string → `null`, otherwise → `Number(...)`) regardless of the component's own `Props.value:
  string` contract — `svelte-check` cannot see this because the coercion is chosen by the element's runtime
  `type` attribute value, not statically known at compile time. `ActNumberField.svelte:74-80` (the one real
  `type="number"` consumer) is unaffected today only because it already avoids `bind:value` and uses one-way
  `value={displayValue}` + `oninput`; any future consumer following the showcase's `bind:value` example on a
  numeric field would silently receive `number | null` where `string` was promised.

Purpose: These are polish/consistency defects (not blockers), but both are the kind of silent-failure primitive
bug 24-REVIEW.md's WR-15 warns are exactly what the missing regression-test gate cannot catch — fixing them now
while the two files are fresh in context is cheaper than after phases 25-30 build on top of them.
Output: `Badge.svelte` where `size` genuinely controls `appearance="count"` dimensions for all 5 tones with a
single, resolved answer on borders; `Input.svelte` where the `value: string` contract holds for every `type`,
including `"number"`.

    - ui/src/features/acts/ActNumberField.svelte lines 71-82 — the one real `type="number"` consumer. It passes
      `value={displayValue}` (one-way, NOT `bind:value` on `<Input>`) and relies entirely on the `oninput`
      callback prop — confirms this consumer is unaffected by removing the native element's `bind:value` in
      favor of an explicit assignment, and confirms `type` must stay `'text' | 'number' | 'search'` (narrowing
      it would make this file fail to compile).
    - 24-REVIEW.md WR-06 section — the exact defect (Svelte's `bind:value` numeric coercion on
      `<input type="number">` writes `number | null` regardless of the component's own `string` contract,
      invisible to `svelte-check` because the coercion is chosen by the DOM element's runtime `type`) and its
      two suggested remedies (narrow `type` + new `NumberInput`, or normalize before the contract boundary).
      This task implements a third, more surgical option: remove the native element's `bind:value` entirely
      (which is what triggers Svelte's type-conditional coercion) and replace it with a one-way `value={value}`
      display binding plus an explicit `value = v;` assignment inside the existing `oninput` handler — `$bindable()`
      propagates to the parent's bound state on ANY assignment to the destructured `value` variable, not only
      via the `bind:` template directive on a native element, so two-way binding for parent consumers
      (`<Input bind:value={x} />`) keeps working exactly as 24-08 fixed it, for every `type` including
      `"number"`, because `e.currentTarget.value` is defined by the DOM spec to always be a string regardless
      of the element's `type` attribute.
  </read_first>
  <action>
    On the native `<input>` element: remove the `bind:value` attribute and replace it with a one-way `{value}`
    binding (i.e. `value={value}`, or the equivalent shorthand `{value}`). Inside the existing `oninput`
    handler (which already computes `const v = (e.currentTarget as HTMLInputElement).value;`), add `value = v;`
    as the first statement before the existing `oninput?.(v);` call — this is the imperative two-way sync that
    replaces what `bind:value` used to do automatically, but using the always-string
    `HTMLInputElement.value` getter instead of Svelte's type-conditional `bind:value` coercion. Do not change
    the `Props` interface, the `type` prop's union, or any other prop.
  </action>
