## Warnings

### WR-01: Догрузка по смещению теряет и дублирует строки при изменении списка другим пользователем

**File:** `ui/src/features/devices/DevicesPage.svelte:401-408` (также `:462-466`, `:587-593`)
**Issue:** `loadMore` склеивает порции по `portionOffset`, а страница не подписана на
`entities_changed`: из стора `placeContentEvents` она импортирует только `notifyPlaceContentChanged`.
Если другой пользователь LAN добавит устройство выше границы порции, последняя строка уедет в
следующую порцию и придёт второй раз, а значит в `{#each rows ... (key)}` (`DeviceList.svelte:328`)
окажется дублирующийся ключ `d<id>`. В dev-сборке Svelte на этом падает, в production поведение
keyed-списка не определено. При удалении строки выше границы одна строка, наоборот, пропадёт из
выдачи, что противоречит D-07 («весь список достижим»). Исправлять список некому: фоновой
перезагрузки нет. Те же склейки по смещению есть в составе группы (`fetchMembersState`, `loadRest`).
Комментарии, обещающие обратное, неверны для этой страницы: `DevicesPage.svelte:148`
(«WS-инвалидация») и `DeviceRowMenu.svelte:274` («остальные клиенты получают WS-событие»).
**Fix:** при добавлении порции отбрасывать уже известные ключи и подписать страницу на инвалидацию,
которая вызывает `refresh()`:
```ts
const keyOf = (e: DeviceEntryDto) =>
  e.kind === 'container' ? 'c' + e.container.group_id : 'd' + e.device.id;
const seen = new Set(rows.map(keyOf));
rows = [...rows, ...p.rows.filter((r) => !seen.has(keyOf(r)))];
```

### WR-02: Раскрытие группы после быстрого свёртывания навсегда остаётся в «Загрузке…»

**File:** `ui/src/features/devices/DevicesPage.svelte:490-499`, `:557`
**Issue:** `loadAnchorMembers` записывает `{ loading: true }`, а ответ принимает только при
`expandedAnchors.has(groupId)`. Последовательность: раскрыть, свернуть до ответа, ответ пришёл и
отброшен. В кеше остаётся `{ loading: true }`. При следующем раскрытии проверка
`if (!anchorMembers[groupId])` считает запись загруженной и запроса не делает: строка показывает
«Загрузка…» до следующего `refresh()`. Теперь это действует и на каждый вложенный уровень D-11.
**Fix:** перезапускать загрузку для незавершённой записи (устаревший ответ отсечёт поколение
`anchorLoadSeq`):
```ts
const cached = anchorMembers[groupId];
if (!cached || cached.loading) void loadAnchorMembers(groupId, kind);
```

### WR-03: Вложенный якорь внутри якорной группы теперь раскрывается и дублирует уже показанные строки

**File:** `ui/src/features/devices/DeviceList.svelte:218-231`, `ui/src/features/devices/DevicesPage.svelte:436-450`
**Issue:** состав якорной группы плоский: `group_subtree_members_sql!` отдаёт всё поддерево и исключает
только якорь самой группы (`devices_sqlite.rs:65-81`). В него входят якорь вложенной группы и её
члены. До фазы у строк состава не было `onToggleExpand`; теперь `entryRows` рекурсивно передаёт его на
любую глубину. Раскрытие такой строки повторно выводит устройства, которые уже стоят в плоском списке
родителя. Появляются дубли `id="device-row-N"`, а `getElementById` для подсветки и возврата фокуса
попадает в первый из них. D-11 прямо говорит, что вид состава якорных групп на верхнем уровне не
меняется.
**Fix:** раскрывать вложенные строки только под родителем-АРМ: передавать в `entryRows` вид родителя
и для детей якорной группы не давать шеврона и `onToggleExpand`.

### WR-04: Рекурсия непустых групп с `UNION ALL` не завершается на цикле в `parent_group_id`

**File:** `crates/trackly-infra/src/repos/devices_sqlite.rs:170-182`
**Issue:** `nonempty_group_ids_sql!` засевает closure всеми живыми группами и рекурсирует через
`UNION ALL`. При цикле a→b→a запрос никогда не закончится: читающее соединение и поток
`spawn_blocking` заняты навсегда, а при повторных открытиях раздела пул читателей исчерпается. Запрос
стоит на основном пути раздела «Устройства» и в `group_children_keys`. Запись циклы отвергает, но
проект считает испорченные данные реальным случаем: `groups_sqlite.rs:359` («даже уже испорченные
данные с циклом не зациклят запрос»), а `anchor_members_sql!` в этом же файле специально использует
`UNION`.
**Fix:** заменить `UNION ALL` на `UNION` в `nonempty_group_ids_sql!`: пары `(root, id)` конечны, и
результат для дерева не меняется. Для единообразия то же в `container_count_cte`.

### WR-05: Новые эндпоинты принимают `DeviceFilter`, но выполняют его лишь частично

**File:** `crates/trackly-infra/src/repos/devices_sqlite.rs:200-209`, `:536-539`, `:496-517`; `crates/trackly-app/src/services/device_service.rs:346`, `:1178-1181`, `:1152`
**Issue:** публичные `devices_list_entries` и `devices_list_containers` принимают весь фильтр, но:
- строки АРМ добавляются без учёта `type_id`, `place_id`, `state`, `name_prefix`, `exclude_anchors` и
  `group_members_only`, поэтому при `place_id = X` в выдачу попадают АРМ из других мест;
- `count_hidden_anchor_members` не учитывает `place_id`, `state` и текст, поэтому «+K» не соответствует
  отфильтрованному списку;
- при `include_deleted = true` ключи считают удалённые устройства, а `list_by_ids` их отбрасывает.
  Строка молча пропадает, `has_more` остаётся `true`, и цикл догрузки по `focusId`
  (`DevicesPage.svelte:336`) не имеет гарантии завершения при `step = 0`.

Сегодня `rawFilter` страницы шлёт эти поля пустыми, поэтому дефект скрыт, но контракт уже опубликован
в HTTP и Tauri, а тесты эти комбинации не покрывают.
**Fix:** включать строки АРМ только когда перечисленные фильтры пусты и `include_deleted = false`
(дополнить `with_containers` и `show_containers` общей функцией), либо отклонять такие фильтры ошибкой
`Validation`. В клиентском цикле прерываться при `step === 0`.

### WR-06: Усечение блока АРМ в поиске проходит молча

**File:** `ui/src/features/devices/DevicesPage.svelte:291-298`
**Issue:** `ContainerListResponse.truncated` документирован как «молчаливого усечения нет», и режим
свёртки показывает тост. `fetchSearchContainers` поле игнорирует: при совпадении более 1000 АРМ
пользователь получит неполную выдачу без какого-либо сигнала.
**Fix:** вернуть `truncated` из `fetchSearchContainers` и записать его в `acc.truncated`, как в ветке
`fetchHead`.
