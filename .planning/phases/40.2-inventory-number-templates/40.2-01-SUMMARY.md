## Accomplishments
- `TemplateType`/`TemplateContext` enums with `as_str()`/`from_str()` round-trip, matching the V041 `CHECK` constraints byte-for-byte
- `TemplateContext::template_type()` as the single source of truth for which template type each UI "Вставка" popup shows — prevents later plans from re-deriving this matrix independently

- 4 migration integration tests, including one that proves `ON DELETE SET NULL` works at the schema level by actually deleting a template row and re-reading the context (not just reading DDL text)

## Decisions Made
- Removed `Copy` from the three new domain types during implementation to match the plan's literal derive list (`Debug, Clone, PartialEq, Eq`) exactly, mirroring the existing `Role` precedent which also omits `Copy`.
- Unit tests compare `from_str(...).expect(...)` against the plain value rather than `assert_eq!(Result, Ok(...))`, because `AppError` does not implement `PartialEq` (pre-existing, out of scope to change here) — `Result<T, AppError>` therefore cannot be compared directly with `assert_eq!`.

## Issues Encountered

**`counters` table removal breaks 16 pre-existing `trackly-infra` tests (expected, tracked for Plan 06/07).**

Task 2 drops `counters` in the same migration per D-15, exactly as specified. `crates/trackly-infra/src/repos/acts_sqlite.rs` (act-number increment) and `crates/trackly-infra/src/repos/cartridges_sqlite.rs` (`assign_code_in_tx` for cartridge/drum codes) still query the `counters` table directly — these call sites are NOT touched by this plan; per `40.2-06-PLAN.md` and `40.2-07-PLAN.md` they are migrated to `NumberTemplateService` in later waves of this same phase (see `40.2-CONTEXT.md` "Миграции и counters" and `40.2-RESEARCH.md` NUM-13 grep-gate).

Verified the failure is isolated and matches expectation exactly:
- `cargo test -p trackly-core` (full suite): **105 passed, 0 failed** (101 lib + 1 no_io_deps + 3 secret_zeroize).
- `cargo check --workspace`: clean, no errors.
- `cargo test -p trackly-infra` (full suite, `TRACKLY_AD_MOCK=1 TRACKLY_SNMP_MOCK=1`): **133 passed, 16 failed** — all 16 failures are `rusqlite: no such table: counters` panics in `repos::acts_sqlite::tests::increment_counter_returns_one_first` (1) and `repos::cartridges_sqlite::tests::*` (15, all touching `assign_code_in_tx`/auto-return/code-generation paths). No failures outside these two counters-dependent modules (places, devices, printers, requests, act CRUD not touching numbering, etc. all green).

This is not fixed in this plan — doing so would require pre-building the `NumberTemplateService` compute-next-number logic that Plan 03 owns and wiring it into `act_service.rs`/`cartridge_service.rs`, which is explicitly Plan 06/07's scope per the phase's own task decomposition. Fixing it here would be Rule 4 (architectural) scope creep into later plans' territory. Tracked here for the orchestrator/next executor: **`cargo test -p trackly-infra` will stay red on these 16 tests until Plan 06 (acts) and Plan 07 (cartridges) land.**
