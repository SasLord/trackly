## Post-plan fix: NUM-11 for devices/printers

**Defect (found post-close, gap-fix between plans 13 and 14):** this plan's `device_service.rs::create_single_with_number_check()` deliberately skipped the D-01 template-mismatch check for devices/printers, with a doc-comment claiming "SPEC/D-01 scopes that check to acts/cartridges only." That claim was wrong. CONTEXT D-01 and SPEC NUM-11 apply whenever a template is active in the field, regardless of entity family — NUM-11's own acceptance example (template `ОРГ-00-[XXXXXX]`, value `ИНВ-7` → popup; «Продолжить» saves `ИНВ-7` and the context remembers «без шаблона») is exactly the device/printer inventory-number case. This SUMMARY's own frontmatter (`tech-stack.patterns`) and Deferred UAT step 4 both propagated the wrong claim as though it were an intentional design decision rather than a gap.

**Fix (fictional org/data only, per CLAUDE.md privacy rule):**

1. **Backend** (`crates/trackly-app/src/services/device_service.rs::create_single_with_number_check`): inserted the mismatch check between `reject_if_occupied` and `script_mix_warning`, mirroring `ActService::create()`/`CartridgeService::create()`'s exact pattern (synthetic `NumberTemplateRow`, `NumberTemplateService::check_mismatch`, `NumberWarningDto{kind: Mismatch, ...}`). A confirmed mismatch (`confirm_mismatch: true`) now resets NUM-08 context memory to «без шаблона» instead of always remembering the supplied `template_id`. Fixed the misleading doc-comments at the top of the method and in `script_mix_warning`'s neighbourhood. `update()` (D-05, edit) is **unchanged** — edit forms genuinely have no mismatch concept per SPEC, this was correct all along.
2. **Tests** (`crates/trackly-app/tests/devices_numbering.rs`, +4 new): mismatch → `NeedsConfirmation` → confirmed → `Created` + context reset to `None`; `device_create`/`printer_create` NUM-08 context isolation (a confirmed mismatch in one context must not touch the other's memory); D-01 order — occupied beats mismatch, mismatch beats script-mix. Also fixed a pre-existing test (`create_single_with_number_check_full_chain`) whose "confirmed script-mix" scenario incidentally also mismatched its own template and now needs `confirm_mismatch: true` to reach the script-mix code path it was actually testing — its `remember_context` assertion changed from `Some(template_id)` to `None` to match the corrected NUM-08/NUM-11 semantics.
3. **UI**: `NumberTemplateField.svelte`'s `onSelectedTemplateChange` callback extended to a second `mask: string | null` argument (minimal interface addition, same pattern as the earlier `export function focus()` addition) so the host form can build `NumberMismatchPopup`'s props without needing access to the field's internal template list. `DeviceFormBody.svelte`: `activePopup` gains a `'mismatch'` state; `submitSingleCreate()` now opens `NumberMismatchPopup` (number, selected template's mask, «Новое устройство»/«Новый принтер» context label) instead of falling through to a generic error toast; «Поправлю» returns to the form, «Продолжить» sets `confirmMismatch=true` and resubmits, continuing the D-01 chain (mismatch → script-mix → save). Edit path (`submitEdit`, D-05) is untouched. `DeviceFormModal.svelte`: renders `<NumberMismatchPopup>` as a top-level `Modal` sibling, same containing-block-trap workaround already used for `NumberTakenPopup`/`NumberScriptWarningPopup`.
