## Decisions Made

- **`NumberTemplateService` wired into `AppCtx` here, not in Plan 04.** Plan 04 built the service but never added it to the composition root — the `build_*` helpers this plan's `<action>` calls for (e.g. `ctx.number_templates.create(...)`) could not compile without it. Added `number_templates: Arc<NumberTemplateService>` to `AppCtx`, its construction (mirrors `PlaceMovementService`'s ordering-independence — no cross-entity dependencies), and updated every hand-built `AppCtx` test literal across the codebase (7 files) that would otherwise fail to compile with a missing-field error.
- **`action_for_context` is a single pure function**, not inlined per `build_*`, per the plan's explicit instruction — both `tauri_cmds::number_templates` and `http::number_templates` import the SAME function (the HTTP handlers reuse it transitively through the shared `build_*` functions, never re-implementing the match).
- **Group A endpoints accept no `context` parameter** — `number_templates_create`/`_update_mask`/`_delete`/`_list`/`_preview_mask` have no field that could be manipulated to redirect the authorization check, closing T-40.2-09 (Elevation of Privilege) structurally.
- **`preview_mask`'s `today_utc` comes from `ctx.clock.unix_seconds()` inside the `build_*` helper**, never as a transport parameter — matches the plan's Task 1 literal signature (`(template_type, mask) -> Result<NextNumberDto, AppError>`, no `today_utc`).
- **REQUIREMENTS.md was NOT updated**, same precedent as Plan 04. This plan's frontmatter lists `NUM-01/03/06/08/09/10/12`, but none are end-to-end delivered by transport wiring alone — no UI exists yet to exercise them (the Settings CRUD screen is Plan 10, the "Вставка" menu and popups are Plans 11-14). `REQUIREMENTS.md` checkboxes remain untouched; `requirements-completed` above is populated per the SUMMARY template's own instruction (copy the plan's `requirements` frontmatter), not as a claim of end-to-end delivery.
