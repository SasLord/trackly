# Phase 40.2 Plan 08: Devices/Printers on NumberTemplateService (V044 migration + occupied/script-mix wiring) Summary

## Accomplishments

- `migrations/V044__devices_inventory_number_dedup_unique.sql` — the last of the three Wave 5 "introduce uniqueness" migrations (after V042 acts, V043 cartridges), and the only one starting from ZERO prior constraint. Dedup rename via a TEMP TABLE staging step (avoids self-referencing-subquery-during-UPDATE ambiguity) + `ROW_NUMBER() OVER (ORDER BY group_first_id, id)` for ONE continuous sequence across all duplicate groups; one `audit_log` row per rename (`user_id=NULL`, `custom:inventory_number_dedup`, both old/new numbers in `payload_json`). **Discovered a real, previously-unverified bug in the plan's own literal reading**: SQLite's built-in `LOWER()` does not fold Cyrillic case at all (bundled amalgamation has no ICU) — fixed with a pure-SQL 33-`REPLACE()`-pair Cyrillic case-fold used identically in both the dedup grouping key and the final index, after explicitly rejecting a Rust-registered custom SQL function (unbounded connection-registration blast radius) per the coordinator's own stated preference for pure SQL. 5 new tests reproduce SPEC NUM-15's literal id 3/8/12 example plus audit/NULL/case-insensitivity coverage.
- `DeviceService::create()`/`bulk_create()`/`update()`/`create_single_with_number_check()` (new): D-08 explicit `.trim()` (not `normalize_str`) on every write path; occupied check (`reject_if_occupied`) unconditional, case-insensitive (Rust `.to_lowercase()`, already correct — only the SQL index needed the Cyrillic fix above), live-only, and skipped entirely for empty values (D-16). Script-mix confirmation (`script_mix_warning`) only wired into the two paths with an interactive confirm flag (`update()`, `create_single_with_number_check()`) — `create()`/`bulk_create()` enforce occupied but silently accept script-mix, since their only callers (CSV import, the legacy two-step printer-create flow, and `DeviceFormBody.svelte` until Plan 13) have no confirmation UI. `update()` (D-05): number re-check only runs when the trimmed value actually changed; structurally has no `template_id`/mismatch concept (`DeviceNumberEditInput` has no such field) and never calls `remember_context` (NUM-08 is create-only). `WsEvent::NumberSpaceChanged` (`device_create`+`printer_create` contexts together) broadcasts on every successful number write across all four methods.
- `DevicePatch.inventory_no` → `number_input: Option<DeviceNumberEditInput>` (app DTO); domain `DevicePatch.inventory_no` widened `Option<String>` → `Option<Option<String>>` (mirrors the existing `place_id` CR-03 double-Option pattern) — a genuine NEW correctness fix this plan's own pipeline required: without it, an explicit clear-to-empty submission would write literal `''` (not `NULL`), and two cleared devices would falsely collide under the new partial unique index. `devices_sqlite.rs`'s `update_in_tx` AND the parallel `DeviceRepository::update` trait method both got the CASE-WHEN fix (mirrors `place_id`'s existing pattern in the same SQL).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] SQLite's built-in `LOWER()` does not fold Cyrillic case at all**
- **Found during:** Task 1, first test run of `post_migration_index_is_case_insensitive_and_trims`
- **Issue:** A literal `LOWER(TRIM(inventory_number))` index (D-08's surface reading) left Cyrillic uppercase letters unchanged (`sqlite3 :memory: "SELECT LOWER('ОРГ-00-000007')"` returns the string byte-for-byte identical) — the app's ENTIRE alphabet, silently making the "new" case-insensitive index case-SENSITIVE for Russian text.
- **Fix:** Pure-SQL 33-`REPLACE()`-pair Cyrillic case-fold (`LOWER()` for ASCII first, then each Cyrillic uppercase letter А-Я+Ё mapped to lowercase), used identically in the dedup CTE and the final index. A Rust-registered custom SQL scalar function was drafted, then explicitly rejected per the coordinator's stated preference for pure SQL if reasonably achievable — it would require registration on every connection before migrations run, an unbounded blast radius.
- **Files modified:** `migrations/V044__devices_inventory_number_dedup_unique.sql`
- **Verification:** `cargo test -p trackly-infra --test devices_inventory_dedup_migration` — 5/5 passed, including the case-insensitivity assertion.
- **Committed in:** `8a869291` (Task 1 commit)

**2. [Rule 2 - Missing Critical] `DevicePatch.inventory_no` (domain) needed the double-Option pattern, not a flat `Option<String>`**
- **Found during:** Task 2, while designing `update()`'s number-clearing path
- **Issue:** This plan's own `number_input` pipeline makes clearing a device's number to empty a REAL, reachable code path for the first time (previously the ambiguous outer `Option<Option<String>>` DTO shape discouraged exercising it in practice, and the pre-existing repo SQL used plain `COALESCE`, which cannot distinguish "not touched" from "explicit NULL"). Left as a flat write, a cleared device would get literal `''` in the column, and a SECOND cleared device would then falsely collide under the new V044 partial unique index (which excludes `NULL`, not `''`).
- **Fix:** Widened `trackly_core::domain::devices::DevicePatch.inventory_no` to `Option<Option<String>>` (mirrors the existing `place_id` CR-03 pattern) and switched `devices_sqlite.rs`'s `update_in_tx` (used by the transactional write path) AND the parallel `DeviceRepository::update` trait method (a non-tx variant reachable via the same trait, kept consistent even though no production caller currently uses it) from `COALESCE` to the same CASE-WHEN "flag+value" pattern `place_id` already uses.
- **Files modified:** `crates/trackly-core/src/domain/devices.rs`, `crates/trackly-infra/src/repos/devices_sqlite.rs`, `crates/trackly-app/src/dto/device.rs`
- **Verification:** Full `trackly-app`/`trackly-infra` regression, no new failures; `devices_numbering.rs`'s occupied/self-exclude tests exercise the write path end-to-end.
- **Committed in:** `12b69698` (Task 2 commit)

**3. [Rule 3 - Blocking] `ui/src/features/devices/DeviceFormBody.svelte` failed `svelte-check` with a real TS error**
- **Found during:** Post-implementation UI verification (`pnpm --dir ui exec svelte-check`)
- **Issue:** This component constructs the typed `DevicePatch` object literal directly (unlike `ui/src/lib/api/devices.ts`'s loosely-typed `apiCall<T>` wrapper) — 1 hard TypeScript error (`inventory_no` does not exist on type `DevicePatch`).
- **Fix:** Rewired the field to build `number_input: { value: inventoryNo.trim(), confirm_script_mix: false }`, doc-commented as a compat shim (occupied check works end-to-end today; the script-mix confirmation popup is Plan 13's job), mirroring `ActFormBody.svelte`/`CartridgeFormBody.svelte`'s own documented Plan 06/07 gap for the identical reason.
- **Files modified:** `ui/src/features/devices/DeviceFormBody.svelte`
- **Verification:** `pnpm --dir ui exec svelte-check` — 0 errors; `pnpm --dir ui build`/`lint` both clean.
- **Committed in:** `d2d7f477`
