## Summary

Проверена серверная половина фазы 40.2: миграции V041–V044, `NumberTemplateService`, D-01/D-05/D-06 цепочки в `act_service`/`cartridge_service`/`device_service`, транспорты Tauri/HTTP, `text::{mask,sequence,homoglyphs}`.

Главная проблема — миграции-перестройки V042 и V043. Они полагаются на `PRAGMA foreign_keys = OFF` внутри файла миграции. Но refinery 0.9.1 оборачивает каждый файл в `conn.transaction()`: `refinery-core-0.9.1/src/drivers/rusqlite.rs`, `Transaction::execute`. Внутри транзакции SQLite игнорирует этот PRAGMA, а `apply_writer_pragmas` включает `foreign_keys=ON` ещё до `migrations::run` (`context.rs:189-192`). Воспроизведено на sqlite 3.51 (см. BE-CR-01/BE-CR-02). На реальной БД это приводит либо к **молчаливой потере всех строк `act_items`**, либо к **падению миграции и отказу приложения стартовать**. Тесты этого не видят: `acts_number_text_migration.rs` применяет SQL вне транзакции и на таблице без FK, а остальные тесты гоняют миграции только на пустой БД.

Дальше идут: пропущенная ветка NUM-12 (двойник без смешения алфавитов), неполная инвалидация D-14, отсутствие trim у маски, отсутствие проверки «тип шаблона ↔ контекст», и D-06, соблюдаемое только в одну сторону.

Приватность (публичный репозиторий): в изменённом бэкенд-коде реальных реквизитов и ФИО не найдено. В тестах только вымышленные «Иванов И.И.», «Петров П.П.», «Сидоров С.С.», «Кузнецов К.К.», в примерах — `ОРГ-00-…`, `C-…`.

Авторизация проверена: CRUD шаблонов = `ManageSettings` на обоих транспортах; usage = `action_for_context`; все HTTP-обработчики идут через те же `build_*`. Замечания к подмене `context` — в BE-WR-01.

## Critical Issues

### BE-CR-01: V042 при обновлении стирает все `act_items`, обнуляет `place_movements.act_id`, а при наличии возвратов падает

**File:** `migrations/V042__acts_number_text.sql:47,82,96`. Также `crates/trackly-infra/src/db/migrations.rs:52-57` и `crates/trackly-app/src/context.rs:189-192`
**Issue:** `PRAGMA foreign_keys = OFF` — no-op внутри транзакции, а refinery выполняет каждый файл внутри `self.transaction()`. Поэтому `DROP TABLE acts` работает при включённых FK и делает неявный `DELETE FROM acts`, который запускает FK-действия:
- `act_items.act_id REFERENCES acts(id) ON DELETE CASCADE` (V004:36) — **удаляются все позиции всех актов**. Миграция при этом «успешна», ошибок нет.
- `place_movements.act_id … ON DELETE SET NULL` (V040:59) — история перемещений теряет связь с актами.
- Если есть хотя бы один возврат (`parent_act_id … ON DELETE RESTRICT`), `DROP TABLE` падает с `FOREIGN KEY constraint failed`. Refinery откатывает V042, но V041 уже закоммичена (counters удалена). `AppCtx::build` возвращает ошибку, и приложение не стартует.

Воспроизведено на тех же конструкциях (BEGIN; PRAGMA foreign_keys=OFF; CREATE acts_new; INSERT…SELECT; DROP TABLE acts; RENAME; COMMIT). Без возвратов `act_items` становится 0 строк, `pm.act_id` — NULL. С возвратом — `FOREIGN KEY constraint failed (19)`.

Тест `crates/trackly-infra/tests/acts_number_text_migration.rs` это маскирует: он применяет SQL через `execute_batch` вне транзакции и создаёт `acts` без FK и без дочерних таблиц. Его docstring неверно утверждает, что fresh-DB тест доказывает работу «PRAGMA foreign_keys = OFF/ON dance».
**Fix:** выключать FK на уровне соединения до refinery, затем проверить целостность и включить обратно. Сами PRAGMA из V042/V043 можно убрать или оставить как документацию.
```rust
pub fn run(conn: &mut Connection) -> Result<MigrationReport, AppError> {
    conn.pragma_update(None, "foreign_keys", "OFF").map_err(map_rusqlite)?;
    let result = migrations::runner().run(conn);
    // проверяем целостность ДО включения FK обратно
    let violations: i64 = conn
        .query_row("SELECT COUNT(*) FROM pragma_foreign_key_check", [], |r| r.get(0))
        .map_err(map_rusqlite)?;
    conn.pragma_update(None, "foreign_keys", "ON").map_err(map_rusqlite)?;
    let report = result.map_err(|e| AppError::Internal { source_chain: format!("refinery migration failed: {e}") })?;
    if violations > 0 { return Err(AppError::Internal { source_chain: format!("{violations} FK violations after migrations") }); }
    // ...
}
```
И добавить регрессионный тест: полная цепочка до V041, засев акта + возврата + `act_items` + `place_movements`, затем `migrations::run`. Проверить, что число `act_items` и значения `place_movements.act_id` не изменились.

### BE-CR-03: NUM-12 — двойник не ищется, если в номере нет смешения алфавитов

**File:** `crates/trackly-app/src/services/number_template_service.rs:473-475`
**Issue:** `detect_warnings` сразу возвращает `None`, если `has_script_mix(candidate) == false`. SPEC NUM-12: предупреждение показывается, если номер смешивает алфавиты, **или** если после замены похожих букв он совпадает с живым номером. Реальный сценарий: засеянные шаблоны `C-[XXXX]`/`D-[XXXX]` латинские, а пользователь на русской раскладке набирает `С-0005` (кириллическая С). Смешения нет. `is_occupied` сравнивает `с-0005` и `c-0005` и считает их разными. В итоге сохраняется визуальный дубль без какого-либо предупреждения. То же с инвентарными `ОРГ-…` против `OPГ`, если все буквы набраны одним алфавитом, например `CO-1` против `СО-1`.
**Fix:**
```rust
let mixed = homoglyphs::has_script_mix(candidate);
let doppelganger = /* find_doppelganger(...) всегда */;
if !mixed && doppelganger.is_none() { return Ok(None); }
// message: если mixed — текст про смешение; если есть двойник — абзац про двойника
```

### BE-CR-05: маска с краевыми пробелами ломает шаблон — сервер выдаёт номер, который сам же считает «не по шаблону» и «занятым»

**File:** `crates/trackly-app/src/services/number_template_service.rs:133,199` (`validate_mask` без trim); `crates/trackly-core/src/text/mask.rs:143-160,241-247,256-277`
**Issue:** маска сохраняется как есть. Пусть админ ввёл `ОРГ-[XXX] ` с хвостовым пробелом (типичная случайность при копировании). Тогда `render_number` выдаёт `"ОРГ-001 "`. Сервисы при сохранении делают `.trim()` и пишут `"ОРГ-001"`. А `extract_digits` сравнивает префикс и суффикс маски без trim (`suffix_lower = " "`) с уже обрезанным кандидатом. Итог:
1. Ни одна сохранённая запись не попадает в последовательность, `first_free` всегда 1. Поле раз за разом предлагает уже занятый номер, и каждое сохранение заканчивается «Номер занят».
2. `check_mismatch` для собственного сгенерированного номера возвращает `true`, и появляется попап «Не соответствует шаблону». После «Продолжить» контекст сбрасывается в «без шаблона».
**Fix:** в `create`/`update_mask` нормализовать `let mask_str = mask_str.trim().to_string();` до `validate_mask` и проверки дубля. Либо отклонять маски с краевыми пробелами в `validate_mask`. Заодно ограничить длину маски (см. BE-WR-10).

### BE-WR-02: память контекста пишется отдельной транзакцией после коммита записи — ошибка после успешного создания

**File:** `act_service.rs:718-735`, `cartridge_service.rs:306-318`, `device_service.rs:419-432`
**Issue:** CONTEXT («запоминание контекста в той же транзакции») не выполнен. Если `remember_context` падает, клиент получает ошибку, хотя акт, картридж или устройство уже закоммичены. Пример: шаблон удалён между проверкой и записью, `FOREIGN KEY constraint failed` превращается в `Conflict`. Событие D-14 при этом тоже не отправляется, потому что `?` выходит раньше. ### BE-WR-03: D-06 соблюдается только в одну сторону; подсказка D-02 для актов не видит возвраты

**File:** `act_service.rs:1272-1300` (каскад номера на возвраты), `act_service.rs:1444` (`do_return`), `act_service.rs:2884` (удаление возврата меняет «42в1/42в2» на «42в»), `act_service.rs:150-219`, `tauri_cmds/number_templates.rs:177-190`
**Issue:**
- Переименование акта `42` в `43` каскадно даёт его возвратам отображение `43в`. Живой акт передачи с номером `43в` не проверяется, и появляются два акта с одинаковым видимым номером. То же при создании возврата и при удалении соседнего возврата.
- Doc-комментарий `is_act_number_occupied_including_returns` говорит, что возвраты исключённого родителя пропускаются. Код исключает только `id == exclude_id`, поэтому переименование `42` в `42в` при собственном возврате `42в` блокируется ложно.
- `number_templates_is_occupied` для `ActCreate` вызывает только базовый `is_occupied` (без возвратов). Живая подсказка и предпроверка D-01 молчат, а сохранение падает простым `Conflict` без карточки.
**Fix:** вынести проверку «отображаемый номер занят» в функцию, работающую внутри транзакции. Вызывать её для новых отображаемых номеров в каскаде, `do_return` и `delete_soft`, а также в `build_number_templates_is_occupied` для `ActCreate`. Возвраты исключённого родителя пропускать по `parent_act_id`.

### BE-WR-04: окончательная проверка уникальности идёт вне writer-транзакции, а DB-страховка слабее Rust-правила

**File:** `number_template_service.rs:443-459` (reader pool); `device_service.rs:136-151`; `act_service.rs:267-274`; `cartridge_service.rs:200-210`; `V043:88`; `V042:88-90`; `V044:140-150`
**Issue:** все occupied-проверки читают через `readers` до открытия writer-транзакции (TOCTOU). Страховки в БД:
- картриджи — индекс по `code` как есть, с учётом регистра: параллельные `c-0001` и `C-0001` пройдут оба;
- акты — сырой `number`, без учёта регистра и без отображаемых номеров возвратов;
- устройства — `TRIM` в SQL срезает только U+0020 (Rust `.trim()` — любые Unicode-пробелы), а свёртка регистра покрывает только ASCII и русский алфавит (Rust `to_lowercase` — всё; `І/і`, `Ґ/ґ`, латиница с диакритикой не сворачиваются).

Комментарий V044:66–67 («matches is_occupied semantics») неточен. SPEC п. 9 требует гарантию именно при параллельных запросах. Проигравший гонку к тому же получает сырое `UNIQUE constraint failed: index '…'` вместо русского сообщения.
**Fix:** повторять `find_occupying_record` на `&tx` внутри writer-замыкания: писатель один, так что гонка исчезает целиком. В `map_rusqlite` (или в месте вызова) переводить нарушение `idx_*_live`/`idx_acts_number_sub_unique` в русский `Conflict`.

### BE-WR-05: V044 — `''` и строки из одних пробелов попадают в уникальный индекс

**File:** `migrations/V044__devices_inventory_number_dedup_unique.sql:78-80,150`
**Issue:** дедуп исключает `TRIM(inventory_number) = ''`, а индекс фильтрует только `IS NOT NULL`. Если в старой БД у двух живых устройств лежит `''` или `'  '`, дедуп их не трогает, `CREATE UNIQUE INDEX` падает, и приложение не стартует. Такое значение могло появиться через старый `COALESCE(?3, inventory_number)` с `''` от HTTP-клиента — об этом прямо говорит новый комментарий в `devices_sqlite.rs:265-276`.
**Fix:** перед созданием индекса выполнить `UPDATE devices SET inventory_number = NULL WHERE TRIM(inventory_number) = '';` и добавить `AND TRIM(inventory_number) <> ''` в `WHERE` индекса.

### BE-WR-06: `restore_from_snapshot_in_tx` пишет `inventory_number` в обход проверки занятости

### BE-WR-07: переполнение u64 в `compute_next` при ручном номере для `[X]`

## Critical Issues

### FE-CR-01: `pendingConfirm` не сбрасывается — мягкие предупреждения пропускаются для другого номера

**File:** `ui/src/features/devices/DeviceFormBody.svelte:514-550` (также `ui/src/features/acts/ActFormBody.svelte:396-432`, `ui/src/features/cartridges/CartridgeFormBody.svelte:469-505`)

**Issue:** флаги `pendingConfirm.mismatch` / `scriptMix` сбрасываются только после успешного
сохранения (`:595`, `:637`). Их не сбрасывают `closeMismatchPopup`, `closeScriptWarningPopup`,
`closeTakenPopup`, `handleTakeNext`, правка номера и ошибка в `catch`. Воспроизводимый сценарий
(создание):
1. Номер не по шаблону → «Продолжить» (`mismatch=true`).
2. Сервер отвечает `script_mix` → «Поправлю».
3. Пользователь вводит *другой* номер, который тоже не подходит под шаблон, → «Создать».
4. Запрос уходит с `confirmMismatch: true`, попап «Не соответствует шаблону» не появляется, и
   сервер запоминает контекст «без шаблона».

Второй сценарий: «Продолжить» в попапе кир/лат → гонка → `CONFLICT` → «Закрыть» → новый номер со
смешением алфавитов сохраняется без предупреждения (`confirm_script_mix: true`). В правке
(`submitEdit`) то же самое для `scriptMix`. Это нарушает D-01/D-04: подтверждение даётся для
конкретного номера, а не для сессии формы.

**Fix:** привязать подтверждение к номеру, а не к сессии:
```ts
let pendingConfirm = $state<{ value: string; mismatch: boolean; scriptMix: boolean } | null>(null);
function confirmsFor(v: string) {
  const ok = pendingConfirm && pendingConfirm.value === v.trim();
  return { mismatch: !!ok && pendingConfirm!.mismatch, scriptMix: !!ok && pendingConfirm!.scriptMix };
}
// continueMismatch: pendingConfirm = { value: inventoryNo.trim(), mismatch: true, scriptMix: pendingConfirm?.scriptMix ?? false }
// closeMismatchPopup / closeScriptWarningPopup / closeTakenPopup / handleTakeNext: pendingConfirm = null
```
Или хотя бы сбрасывать `pendingConfirm = { mismatch: false, scriptMix: false }` во всех `close*`,
в `handleTakeNext` и в `$effect`, который следит за изменением значения номера.

### FE-CR-02: `isConflictError` считает любой `CONFLICT` «Номер занят» и скрывает настоящую причину

**File:** `ui/src/features/acts/ActFormBody.svelte:308-310, 474-481, 547-554` (также `DeviceFormBody.svelte:409-411, 585-592, 627-634`; `CartridgeFormBody.svelte:365-367, 532-539`)

**Issue:** все пути сохранения превращают *любой* `AppError` с кодом `CONFLICT` в попап «Номер
занят». Но `act_service.rs` возвращает `Conflict` и по причинам, не связанным с номером:
- `:547` «Устройство id=… больше не на складе — обновите список и повторите» (создание);
- `:979` то же при правке;
- `:1127` «Устройство … уже возвращено по акту возврата — редактирование позиции невозможно».

Номер при этом свободен, поэтому `number_templates_is_occupied` возвращает `null`. Пользователь
видит карточку-заглушку («Вид: —») и заголовок «Номер «…» уже занят», а после «Закрыть» поле
номера помечается «Номер уже занят.». Настоящее сообщение сервера теряется: пользователь правит
номер, ошибка повторяется, и понять причину невозможно.

**Fix:** показывать попап, только если номер действительно занят. Остальные конфликты
отправлять в общий обработчик:
```ts
} catch (e) {
  if (isConflictError(e)) {
    const record = await apiCall<OccupyingRecordDto | null>('number_templates_is_occupied', {...}).catch(() => null);
    if (record) { showTakenPopup(record, ...); return; }
  }
  throw e; // generic toast с err.message
}
```
Лучше — отдельный маркер от сервера (`details.field === 'number'` или отдельный вариант ошибки),
но это уже на стороне backend.

### FE-CR-03: Escape в меню «Вставка» закрывает всю модалку создания — несохранённые данные теряются

**File:** `ui/src/lib/components/ActionMenu.svelte:77-79, 111-114`; `ui/src/lib/components/Modal.svelte:152-165`

**Issue:** `NumberTemplateField` встраивает `ActionMenu` внутрь `Modal` во всех формах создания.
При нажатии Escape в открытом меню срабатывают два обработчика:
- `onPanelKeydown` вызывает только `preventDefault()` + `close(true)`, без `stopPropagation()`;
- document-listener `onKey` просто вызывает `close(true)`.

Затем событие всплывает до `<svelte:window onkeydown>` модалки формы. Она на вершине стека
(`isTop`) и не проверяет `defaultPrevented`, поэтому вызывает `onClose()`. «Новое устройство»,
«Новый акт» (с заполненной таблицей позиций) или «Новый картридж» закрываются без подтверждения,
и всё введённое пропадает. UI-SPEC §3 требует от Esc «закрыть меню с возвратом фокуса».

**Fix:** в `ActionMenu` при открытом меню гасить событие:
```ts
function onKey(e: KeyboardEvent) {
  if (e.key === 'Escape' && open) { e.stopPropagation(); e.preventDefault(); close(true); }
}
// onPanelKeydown: Escape → e.stopPropagation() тоже
```
Дополнительно в `Modal.handleKeydown`: `if (e.defaultPrevented) return;` перед обработкой Escape.

### FE-CR-04: пустое поле считается «не правленым» — WS заново заполняет стёртый номер и сбрасывает количество

**File:** `ui/src/lib/components/NumberTemplateField.svelte:119-125, 198-209`; `ui/src/features/devices/DeviceFormBody.svelte:271-276, 767`

**Issue:** `isValueUnedited()` возвращает `true` для пустой строки. D-14 разрешает тихую замену,
только если значение «всё ещё равно ранее предложенному», а пустая строка предложенной не была.
Сценарий в «Новом устройстве»:
1. Номер подставляется автоматически, поэтому «Количество» заблокировано: `quantityDisabled`
   истинно, пока инвентарный номер не пуст.
2. Чтобы создать N штук, пользователь стирает номер (шаблон остаётся выбранным) и вводит
   количество 5.
3. Любое `number_space_changed` (другой пользователь создал запись) вызывает
   `refreshCurrentSuggestion()`, и тот записывает номер в пустое поле. Поле при этом `disabled`,
   но это не мешает.
4. Эффект `:271` сбрасывает количество до 1, а `handleSubmit` берёт `qty = 1`.

Итог: без какого-либо сигнала создаётся одно устройство с номером вместо пяти без номеров.

**Fix:** различать «пусто изначально» и «стёрто вручную». Для WS-обновления требовать точного
совпадения с последним предложением:
```ts
function isValueUnedited(allowEmpty: boolean): boolean {
  const norm = normalize(value);
  if (norm === '') return allowEmpty && lastSuggested === null; // пусто, и мы ещё ничего не предлагали
  ...
}
// refreshCurrentSuggestion → preserveManualEdits с allowEmpty=false
```
Также не обновлять значение, пока поле `disabled`.

### FE-CR-05: нет защиты от устаревших ответов при смене контекста — поздний ответ перезаписывает значение и `templateId`

**File:** `ui/src/lib/components/NumberTemplateField.svelte:87-100, 163-193, 225-238, 294-313`

**Issue:** `loadTemplates`, `applyContextDefault` (два последовательных запроса),
`refreshCurrentSuggestion` и `selectTemplate` не проверяют, что контекст за время запроса не
сменился. В «Новом картридже» быстрое переключение «Картридж → Фотобарабан» (а также
«Устройство ↔ Принтер») запускает два параллельных `applyContextDefault`. Если ответ для
`cartridge_create` приходит последним (обычное дело для LAN-HTTP), то в контексте `drum_create`:
- `value` становится `C-00NN`;
- `selectedTemplateId` становится id шаблона картриджей и уходит родителю через
  `onSelectedTemplateChange`;
- меню «Вставка» может показать шаблоны другого типа (`templates` от последнего пришедшего ответа).

Сохранение отправляет `templateId` шаблона картриджей вместе с кодом фотобарабана. В
`number_template_service.rs::remember_context` проверки «тип шаблона ↔ контекст» я не нашёл,
поэтому контекст «Новый фотобарабан» может запомнить чужой шаблон, а запись сохраниться с
неверным префиксом. Это нарушает приёмку SPEC п. 8 («картридж ↔ фотобарабан — заменяется
всегда»).

**Fix:** вести счётчик поколений контекста и отбрасывать чужие ответы:
```ts
let ctxGen = 0;
$effect(() => { const ctx = context; const gen = ++ctxGen; void loadTemplates(ctx, gen); ... applyContextDefault(ctx, ..., gen) });
// в каждом await-продолжении:
if (gen !== ctxGen) return;
```
То же для `refreshCurrentSuggestion` / `selectTemplate`: запоминать `context` и `selectedTemplateId`
до `await` и сверять их после.

**File:** `ui/src/features/devices/DeviceFormBody.svelte:476-497` (аналогично `ActFormBody.svelte:363-384`, `CartridgeFormBody.svelte:431-452`)

### FE-WR-08: `OrgSettings.loadTemplates` без защиты от устаревших ответов

### FE-WR-09: утечка refcount у `connectWs`, если компонент размонтирован до резолва промиса или промис отклонён

**File:** `ui/src/lib/components/NumberTemplateField.svelte:250-265`; `ui/src/features/settings/OrgSettings.svelte` (`onMount`)

**Issue:** `connectWs()` синхронно увеличивает `refCount` (`ws.ts:116`), а release приходит только
после `await import(...)` / `listen`. Если форма закрылась раньше, `wsRelease` при cleanup равен
`null`, и refcount навсегда больше нуля. На ветке `.catch` release тоже не вызывается. Поле
монтируется в каждом попапе создания, поэтому быстрые открытия и закрытия копят утечку.

**Fix:**
```ts
let disposed = false;
connectWs().then((r) => { if (disposed) r(); else wsRelease = r; });
return () => { disposed = true; unsubscribeWs(); wsRelease?.(); };
```

### FE-WR-10: фокус в попапах цепочки не соответствует UI-SPEC

**File:** `ui/src/lib/components/NumberMismatchPopup.svelte:24-34`; `ui/src/lib/components/NumberScriptWarningPopup.svelte:48-64`; `ui/src/lib/components/NumberTemplateField.svelte:315-318`

**Issue:**
- (а) UI-SPEC §6 требует фокус по умолчанию на «Поправлю». `Modal` фокусирует первый элемент
  диалога, а это кнопка «×» в заголовке. Destructive-кнопка «Продолжить» стоит в двух Tab от
  фокуса без явной защиты.
- (б) После «Поправлю» / «Закрыть» формы вызывают `focusNumberField()` синхронно, а cleanup-эффект
  размонтируемого `Modal` затем делает `prevFocus?.focus()`. Это может увести фокус с поля
  (зависит от того, что было в фокусе при открытии попапа). Нужна проверка в WKWebView.
- (в) `selectNoTemplate` фокусирует поле синхронно, после чего `onclick` панели `ActionMenu`
  (`close(true)`) переводит фокус на кнопку-триггер. UI-SPEC п. 13 требует фокус в поле.

**Fix:** добавить в `Modal` проп `initialFocus` (селектор или ref) и передавать «Поправлю».
Фокус поля ставить после размонтирования попапа (`tick()` / `queueMicrotask`). В `selectNoTemplate`
выполнять `queueMicrotask(focusInputAtEnd)`.

### FE-WR-11: глобальный Escape-обработчик `ActionMenu` крадёт фокус, даже когда меню закрыто

### FE-WR-14: `Button iconOnly ghost` не совпадает с `ActionMenu ghost-md` по конструкции, вопреки UI-SPEC §10

**File:** `ui/src/lib/components/Button.svelte:43`; `ui/src/styles/global.scss:108-132`

**Issue:** в комментарии `ActionMenu` верно сказано, что scoped-селекторы (`.btn.svelte-x`,
