## Decisions Made

- **`*SaveOutcome` fixed as a documented convention, not implemented here.** Task 1's plan explicitly forbids creating `DeviceSaveOutcome`/`ActSaveOutcome`/`CartridgeSaveOutcome` in this plan (they need `DeviceDto`/`ActDto`/`CartridgeDto`, owned by Plans 06-08) — the module doc-comment on `dto/number_template.rs` is the single place this convention is now written down, so three plans don't invent three different response shapes for the same D-01 confirmation chain.
- **`preview_mask` reuses `compute_next_for_template` via a synthetic `id: 0` row** instead of extracting a `compute_next_raw` helper inside Plan 03's `number_templates_sqlite.rs` (which the plan's `<action>` suggested) — that file is outside this plan's declared `files_modified` scope. The synthetic-row approach achieves the same "no duplicated logic" goal without touching Plan 03's file, verified by `preview_mask_validates_without_persisting`'s explicit `list()` count-unchanged assertion.
- **`is_occupied`/`detect_warnings` designed as async self-methods (readers pool + `spawn_blocking`), not `&Connection`-parameterized functions.** Wave 5's own plans (06/07/08) call them as pre-checks before opening their own writer transaction (mirrors the existing `cartridge_service.rs::model_delete` live-count pre-check pattern) — this accepts the same small TOCTOU window that pattern already accepts elsewhere in the codebase, not a new risk introduced here.
- **REQUIREMENTS.md was NOT updated.** Although this plan's frontmatter lists `NUM-01/03/08/09/10/11/12`, none are end-to-end delivered by the service layer alone — Plan 05 gates these methods behind `authorize()` at the transport boundary, and Plans 06-08/10/11/13/14 build the actual CRUD screen and confirmation popups a user interacts with. Per this session's explicit instruction ("do not mark requirements complete unless the plan fully delivers them end-to-end"), the `requirements-completed` field above is populated per the SUMMARY template's own instruction (copy the plan's own `requirements` frontmatter) but `REQUIREMENTS.md`'s checkboxes were deliberately left untouched — precedent: Plan 01's SUMMARY listed `NUM-01`/`NUM-13` the same way without checking their boxes either.
- **`detect_warnings` never returns `NumberWarningKind::Mismatch`.** The plan's `<behavior>` scopes Task 3 to script-mix detection only, with `check_mismatch` as a separate pure boolean — Wave 5 callers build the actual `NumberWarningDto{kind: Mismatch, ...}` themselves because only they know the context-specific "Следующее окно «{контекст}» откроется без шаблона." text (which names the NEXT popup context, something this generic service has no knowledge of).

## Issues Encountered

**Test assumption error, caught and fixed before commit (not a deviation — normal TDD iteration).** The first version of `remember_and_get_context_round_trip_then_clears_on_delete` used `TemplateContextDto::ActCreate` and asserted `get_context` returns `None` before any `remember_context` call. Fixed by switching the test to `TemplateContextDto::DeviceCreate`, which has no seeded default — confirmed correct behavior, not a service bug.

**`trackly-app` full-suite baseline established for the first time since V041 dropped `counters` (Plan 01).** Ran `cargo test -p trackly-app --no-fail-fast -- --skip login_remember_persistent_cookie` (with `TRACKLY_AD_MOCK=1 TRACKLY_SNMP_MOCK=1`): **860 passed, 65 failed**. Every one of the 65 failures' panic message contains `"no such table: counters"` (verified by extracting every panic message line and confirming zero contain anything else) — `acts_crud`/`acts_numbering`/`acts_returns`/`acts_suggest`/`cartridges_crud`/`cartridges_history`/`cartridges_low_stock`/`cartridges_lifecycle`/`cartridges_numbering`/`cartridges_search`/`place_movements_bulk_move`/`place_movements_write_sites_cartridges`, all downstream of `act_service.rs`/`cartridge_service.rs` still calling the dropped `counters` table for act-number/cartridge-code assignment.
