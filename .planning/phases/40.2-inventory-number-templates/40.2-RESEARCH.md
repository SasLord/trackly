## Summary

This phase adds zero new external dependencies. It is 100% internal application work on top of
the stack already locked in `CLAUDE.md`: Rust (rusqlite/refinery/axum/tauri-specta) + Svelte 5
runes + SQLite. `40.2-SPEC.md` and `40.2-CONTEXT.md` already fully specify *what* to build and
*which* implementation decisions are locked; `40.2-UI-SPEC.md` fully specifies the visual/copy
contract. This document exists to answer *how the existing codebase's conventions constrain the
plan* — exact files, exact patterns to mirror, and the specific traps a planner would not see
from the spec alone.

The single highest-risk finding is a **width mismatch between the old cartridge/drum numbering
scheme and the new mask-matching rule** (see Pitfall 1) — if not handled explicitly in the
seed migration, NUM-13's continuity acceptance criterion ("«Новый картридж» — следующий
C-NNNNNN, как было до обновления") will silently fail on any DB that already has cartridges.
The second-highest-risk finding is an **authorization split** between template CRUD
(`Action::ManageSettings`, Admin-only) and template *use* inside creation popups
(`Action::MutateDevices/MutateActs/MutateCartridges`, Admin **or** Manager) — gating both on
the same Action would either lock Managers out of templates or let them edit templates through
a back door (Pitfall 3). Third, `acts.number` changing from `INTEGER` to `TEXT` cannot use
`ALTER TABLE ... ALTER COLUMN` (SQLite has no such statement) — this repo already has a proven
12-step rebuild recipe for exactly this situation (`migrations/V030__...sql`), reusable
near-verbatim (Code Example 1).

**Primary recommendation:** Follow existing patterns file-for-file — `acts_peek_next_number`
(Tauri+HTTP pair) as the template for the two new "next number" endpoints; `V030`'s
create-copy-drop-rename recipe for the `acts.number` type change; `cartridge_service.rs`'s
`CartridgeModelCreateDto`/`CartridgeModelPatchDto` CRUD shape for `NumberTemplate` CRUD; and
`AuditEntry` with a new `custom:*` action string for every new audit trail. Do not invent new
architectural shapes — this phase is additive within an already-mature codebase.

No new supporting libraries required. Two capabilities that *might* tempt a new dependency are
explicitly out of scope for one:

| Capability | Don't add | Use instead |
|---|---|---|
| Cyrillic/Latin homoglyph detection | `unicode-security` crate or similar | CONTEXT D-04 already locks a **hand-rolled, closed table** of ~12 look-alike letter pairs in Rust (the set is small and fixed — А/A, В/B, Е/E, К/K, М/M, Н/H, О/O, Р/P, С/C, Т/T, Х/X, У/Y + lowercase). A crate would be overkill for a closed 12-pair table and adds a new supply-chain surface for zero benefit. |
| Mask parsing / regex | `regex` crate (already a transitive dep via `tracing-subscriber`) | A hand-written parser is safer here: the token set is closed and literal (`[YYYY]`, `[YY]`, `[MM]`, `[DD]`, `[X…]` in exact uppercase), and regex would need careful escaping of arbitrary literal text around tokens. A small explicit scanner (split on `[`/`]`, whitelist token bodies) is simpler to get exactly right and to unit-test exhaustively than a regex with capture groups. If `regex` is used anyway (it's already in the dependency tree), keep the pattern anchored and tested against SPEC NUM-02's exact acceptance strings — do not introduce a second regex dependency. |

### Pattern 1: Dual-transport thin adapter (mirror exactly)

**What:** Every mutation/query is exposed as a plain `async fn build_X(ctx: &AppCtx, caller:
&Identity, ...) -> Result<T, AppError>` that does `authorize(caller, &Action::Y)?` then calls
into the service. Both the Tauri command and the axum handler call this **same** function.
**When to use:** Every new endpoint this phase adds (peek-next, live-occupied-check, template
CRUD, context memory read).
**Example (existing code to mirror verbatim, `crates/trackly-app/src/tauri_cmds/acts.rs`):**
```rust
// Source: crates/trackly-app/src/tauri_cmds/acts.rs:120-123 (existing, verified in repo)
pub async fn build_acts_peek_next_number(ctx: &AppCtx, caller: &Identity) -> Result<i64, AppError> {
    authorize(caller, &Action::ReadData)?;
    ctx.acts.peek_next_number().await
}

// Tauri wrapper — crates/trackly-app/src/tauri_cmds/acts.rs:264-267
#[tauri::command]
#[specta::specta]
pub async fn acts_peek_next_number(state: tauri::State<'_, AppCtx>) -> Result<i32, AppError> {
    let caller = /* session identity */;
    let next = build_acts_peek_next_number(state.inner(), &caller).await?;
    Ok(next as i32) // NOTE: i32 cast — tauri-specta forbids usize/i64-as-BigInt in some contexts, verify per DTO
}

// HTTP wrapper — crates/trackly-app/src/http/acts.rs:239-249
pub async fn handler_peek_next_number(
    State(ctx): State<AppCtx>,
    session: Session,
) -> Result<Json<i64>, AppErrorResponse> {
    let identity = session_identity(&session).await.map_err(AppErrorResponse::from)?;
    Ok(Json(build_acts_peek_next_number(&ctx, &identity).await.map_err(AppErrorResponse::from)?))
}
```
The new `peek_next(template_id_or_context, ...)` and `is_occupied(space, number)` endpoints for
this phase should follow this exact three-part shape (`build_*` fn, Tauri wrapper, HTTP wrapper
+ route registration in `router()`), registered in `specta_export.rs` and asserted in
`tests/export_bindings.rs` like every other command (grep `acts_peek_next_number` in that test
file for the exact assertion shape to copy).

### Pattern 2: Table rebuild for a column type change (no `ALTER COLUMN` in SQLite)

**What:** SQLite has no `ALTER TABLE ... ALTER COLUMN TYPE`. `acts.number INTEGER` → `TEXT`
requires the 12-step rebuild: create `_new` table with the target schema, `INSERT INTO ...
SELECT` (explicit column list, **preserving `id`** so `act_items.act_id`/`parent_act_id`
FKs stay valid), `DROP TABLE`, `RENAME TO`, all wrapped in `PRAGMA foreign_keys = OFF/ON`.
**When to use:** NUM-14's `acts.number` type change; potentially also useful if a partial
UNIQUE index needs restructuring on `cartridges.code` (NUM-09's "unique among live only" vs.
today's "unique globally including deleted" — that's an index change, not a column type change,
so a simple `DROP INDEX` old-unique-constraint + `CREATE UNIQUE INDEX ... WHERE
deleted_at_utc IS NULL` may suffice there instead of a full rebuild — check whether `code`'s
`UNIQUE` is a column-level constraint (it is: `code TEXT NOT NULL UNIQUE` in the original
`CREATE TABLE`) — a column-level `UNIQUE` **cannot** be dropped without a table rebuild either,
so `cartridges` likely needs the same 12-step treatment as `acts`).
**Example (this exact recipe already exists in this repo, reuse near-verbatim):**
```sql
-- Source: migrations/V030__printers_drop_connectivity_check.sql (existing, verified in repo)
PRAGMA foreign_keys = OFF;

CREATE TABLE acts_new (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  number            TEXT    NOT NULL,          -- was INTEGER (NUM-14)
  sub_number        INTEGER NULL,
  parent_act_id     INTEGER NULL REFERENCES acts_new(id) ON DELETE RESTRICT,
  -- ... every other column unchanged, copied verbatim from current CREATE TABLE acts ...
  version           INTEGER NOT NULL DEFAULT 1
);

INSERT INTO acts_new (id, number, sub_number, parent_act_id, /* ...all columns... */ version)
SELECT id, CAST(number AS TEXT), sub_number, parent_act_id, /* ... */ version
FROM acts;

DROP TABLE acts;
ALTER TABLE acts_new RENAME TO acts;

-- Recreate the partial unique index (lost on DROP TABLE — indexes are not renamed with the table)
CREATE UNIQUE INDEX idx_acts_number_sub_unique
  ON acts(number, COALESCE(sub_number, 0))
  WHERE deleted_at_utc IS NULL;

PRAGMA foreign_keys = ON;
```
**Critical detail verified in the existing V030 file's own comment:** refinery runs one
migration file per transaction (`set_grouped(false)`), so the `PRAGMA foreign_keys = OFF` /
`= ON` pair is safely scoped to this single file and never overlaps user traffic — do not spread
the rebuild across two migration files with the pragma toggle split between them.
**Also verify:** any other table with a FK to `acts(id)` (`act_items.act_id`,
`place_movements.act_id`) resolves FKs by table name, not rowid — per V030's own comment,
`RENAME TO acts` transparently restores FK integrity for those tables without touching them,
**provided every `acts.id` value is preserved exactly** in the `INSERT ... SELECT` (which it is,
since `id` is explicitly selected, not omitted for autoincrement).

### Anti-Patterns to Avoid

- **Do not compute "next number" or validate mask syntax in the Svelte client.** UI-SPEC
  explicitly locks the preview and validation to a server round-trip (300ms debounce) precisely
  to avoid a second implementation of NUM-02's grammar (`js_rust_mirror_needs_fixture_gate`
  project memory). The client's only local logic should be simple string equality (is the
  current field value still equal to what the server last suggested?) for the ↑/↓ visibility
  and the D-14 "silent replace" guard — never re-derive the number itself.
- **Do not gate template CRUD and template use on the same `Action`.** See Pitfall 3.
- **Do not reuse `normalize_str`'s existing meaning as "already trims."** See Pitfall 4.

## Don't Hand-Roll

| Problem | Don't build | Use instead |
|---|---|---|
| Dual Tauri+HTTP command wiring | A new abstraction/macro for "one business fn, two transports" | The existing three-part `build_*` / `#[tauri::command]` / axum-handler pattern (Pattern 1) — every one of ~15 existing feature areas does it this way; a new abstraction here would be inconsistent with the rest of the codebase for zero benefit |
| SQLite schema migration mechanics | Manual `ALTER TABLE` attempts for type/constraint changes | The already-proven 12-step rebuild recipe (`V030`) — SQLite genuinely cannot do `ALTER COLUMN` or drop a column-level `UNIQUE`/`CHECK`, this is not a style choice |
| Cross-request atomic uniqueness | Optimistic client-side "check then insert" | The DB-level partial `UNIQUE INDEX ... WHERE deleted_at_utc IS NULL`, exactly as `idx_acts_number_sub_unique` already does — this is what makes NUM-09's "exactly one of two parallel requests succeeds" true by construction, not by hoping the app-layer check wins the race |

**Key insight:** every "don't hand-roll" here is really "don't deviate from this codebase's own
20-migration-deep precedent" — the risk in this phase is not exotic external tooling, it's a
planner inventing a new shape where an old one already fits.

## Common Pitfalls

### Pitfall 1: Seed-mask digit width can silently break numbering continuity (HIGH — directly threatens NUM-13's acceptance criterion)

> **RESOLVED 2026-09-18 (user decision, plan-phase):** seed masks are `C-[XXXX]` / `D-[XXXX]` (fixed literal width 4, matching the current `{seq:04}` format) — NOT `[XXXXXX]` and NOT a dynamically computed width. Existing codes are never rewritten. CONTEXT D-16, SPEC and NUM-13 updated accordingly. The analysis below is kept for history.

**What goes wrong:** CONTEXT D-16 and SPEC NUM-13 specify seeding `C-[XXXXXX]` (6 digits) and
`D-[XXXXXX]` (6 digits) for cartridges/drums. But the **actual current code format**
(`crates/trackly-infra/src/repos/cartridges_sqlite.rs::assign_code_in_tx`) is
`format!("{prefix}-{seq:04}")` — a **minimum**-width-4 format that grows unpadded past 4 digits
(codes `C-0001` .. `C-9999`, then `C-10000` with no re-padding). NUM-02/NUM-04's mask-matching
rule requires **exactly** N digits for a record to belong to a `[X…N]` sequence ("на месте
`[X…]` стоят ровно N цифр"). If a live DB has existing codes like `C-0001`..`C-0512` (4 digits)
and the seed migration creates the template with mask `C-[XXXXXX]` (exactly 6 digits required),
**none of the existing 4-digit codes match** the new template's sequence, so `compute_next`
returns `1` (no matching live records) instead of `513` — silently resetting the counter and
violating NUM-13's explicit acceptance criterion ("«Новый картридж» — следующий C-NNNNNN, как
было до обновления").
**Why it happens:** the old scheme used *minimum-width* padding (unbounded growth), the new
scheme uses *exact-width* matching (SPEC-locked, cannot be changed by the planner). These are
not equivalent semantics, and the literal `[XXXXXX]` in CONTEXT/SPEC's prose is illustrative,
not a verified-against-real-data width.
**How to avoid:** the V041/V042 seed step must **compute** N dynamically per kind, as
`MAX(LENGTH(numeric suffix))` across existing live `cartridges` rows of that kind (default to a
safe width, e.g. 4 or 6, when the table is empty — this only matters on upgrade of an existing
DB, not a fresh install), and use that computed N to build the seeded mask string
(`format!("C-[{}]", "X".repeat(n))`). Do the equivalent check for any org that has *already*
exceeded 9999 cartridges (mixed 4-and-5-digit codes existing simultaneously) — if that's found
in dev/test fixtures, flag it as an edge case requiring either a one-time re-pad of historical
codes to a uniform width (acceptable since NUM-13 only guarantees *next-number* continuity, not
that historical codes are visually preserved character-for-character, unlike acts under NUM-14)
or documented as an accepted gap.
**Warning signs:** a migration test against a DB fixture seeded with realistic (4-digit)
existing cartridge codes that asserts the post-migration "next code" equals the pre-migration
"next code" — this is exactly the kind of test NUM-13's acceptance criterion demands, and it
will fail immediately if N is hardcoded to 6.

### Pitfall 2: `cartridges.code UNIQUE` is a column-level constraint — widening it to "live-only" needs a table rebuild, not an index tweak

**What goes wrong:** `code TEXT NOT NULL UNIQUE` (from the original `cartridges` `CREATE TABLE`)
declares uniqueness as an implicit SQLite index tied to the column definition. Attempting
`DROP INDEX sqlite_autoindex_cartridges_N` on an autoindex, or simply adding a new partial
`UNIQUE INDEX ... WHERE deleted_at_utc IS NULL` alongside the existing column-level constraint,
leaves the OLD global-uniqueness constraint still enforced (a soft-deleted cartridge's code
would still block reuse — NUM-09 requires soft-deleted codes to free the code).
**Why it happens:** SQLite has no `ALTER TABLE ... DROP CONSTRAINT`, same limitation as V030's
`CHECK` removal.
**How to avoid:** apply the same 12-step rebuild pattern (Pattern 2 / V030) to `cartridges`:
new table without the column-level `UNIQUE`, explicit partial `UNIQUE INDEX (code) WHERE
deleted_at_utc IS NULL` created afterward, preserving `id` for `cartridge_states`/
`printer_cartridge_models`/`place_movements` FK integrity via table-name-based FK resolution.
**Warning signs:** a test that soft-deletes a cartridge and then creates a new live one with the
same code — if it fails with a `UNIQUE constraint failed: cartridges.code` referencing the
*column* (not a named partial index), the old constraint is still present.

### Pitfall 3: Template CRUD and template *use* need different `Action` gates — conflating them either blocks Managers or grants them settings access

**What goes wrong:** `crates/trackly-core/src/auth.rs`'s permission matrix (verified in repo)
shows `Action::ManageSettings` is **Admin-only**, while `Action::MutateDevices` /
`Action::MutateActs` / `Action::MutateCartridges` are **Admin | Manager**. NUM-01 says template
CRUD in Settings uses "права... как на остальные поля «Настройки / Организация»" → this is
`Action::ManageSettings`, Admin-only. But NUM-06/NUM-08's "Вставка" menu, next-number preview,
and context memory are used inside the *same* four creation popups a **Manager** already has
access to (Manager has `MutateDevices`/`MutateActs`/`MutateCartridges`). D-13's own text
("Для пользователя без прав на настройки — тот же текст, без ссылки") is written for exactly
this Manager case. If the planner gates the template-list-read and peek-next endpoints on
`Action::ManageSettings`, Managers creating a device/act/cartridge would see the D-13
"no permission" empty state permanently and never get autofill — a functional regression, not
just a wrong error message.
**Why it happens:** it's tempting to treat "number templates" as one feature with one
permission, when the spec actually implies two distinct capabilities gated by two distinct
existing `Action`s.
**How to avoid:** gate `number_templates_create/update/delete` (and the Settings-page list
fetch) on `Action::ManageSettings`. Gate `number_templates_peek_next`,
`number_templates_list_by_type` (for the "Вставка" menu), `number_template_contexts_get/set`,
and `number_is_occupied` on the **same** `Action` as the popup they're embedded in
(`MutateDevices` for device/printer, `MutateActs` for act, `MutateCartridges` for
cartridge/drum) — i.e. these read/use endpoints have **no single shared Action**; each is gated
per calling context, matching who can already open that specific creation popup.
**Warning signs:** the existing `role_endpoint_matrix.rs` test file (referenced in STATE.md for
Phase 40 Plan 14, `crates/trackly-app/tests/`) is exactly where a Manager-can-use-templates /
Manager-cannot-CRUD-templates case belongs; if that matrix doesn't get new rows for this
phase's new endpoints, the split is unverified.

### Pitfall 4: `normalize_str` does NOT trim — reusing it as-is silently violates D-08

**What goes wrong:** `crates/trackly-infra/src/repos/devices_sqlite.rs::normalize_str` is:
```rust
fn normalize_str(s: Option<&str>) -> Option<&str> {
    s.and_then(|v| if v.trim().is_empty() { None } else { Some(v) })
}
```
It only uses `.trim()` to test for *emptiness* — it returns the **original, untrimmed** slice
when non-empty. CONTEXT D-08 requires the server to store the number with edges trimmed
(`" ОРГ-00-000001 "` → `"ОРГ-00-000001"`). A planner who assumes `normalize_str` already does
this (a reasonable assumption from its name) will ship a bug where the DB stores untrimmed
values, and NUM-09's own acceptance test ("`орг-00-000001 ` с пробелом" must collide with
`ОРГ-00-000001`) will only pass if the *comparison* trims on both sides but the *stored* value
still has a trailing space — inconsistent with D-08's "trim, регистр как ввели" storage rule.
**Why it happens:** the helper's name implies more normalization than it performs; it predates
this phase and was written only to convert blank strings to `NULL`.
**How to avoid:** the new number-field write path must call a **new**, explicit
`v.trim().to_string()` (case preserved, per D-08) before storing in `devices.inventory_number` /
`acts.number` / `cartridges.code` — do not route through `normalize_str` and assume trimming
happened. Uniqueness comparisons additionally need `LOWER(TRIM(...))` in SQL (or a normalized
computed column) since D-08 also requires case-insensitive comparison at the DB level for the
race-safe partial index to work correctly for e.g. `ОРГ-00-000001` vs `орг-00-000001`.
**Warning signs:** a live-duplicate test with mixed case AND surrounding whitespace in the same
input string (not just one or the other) will catch this if the two behaviors are conflated.

### Pitfall 5: CSV within-file duplicate detection (NUM-16) needs its own seen-set — the create() uniqueness error alone can't produce "(повтор строки M)"

**What goes wrong:** `DeviceService::import_csv_commit` (verified in repo,
`crates/trackly-app/src/services/device_service.rs:673`) processes CSV rows **one at a time**,
calling `self.create(new_device).await` per row inside the loop (not one big transaction). This
means NUM-09's own uniqueness check, once wired into `create()`, will *already* reject a row
whose number duplicates an earlier row in the same file (because the earlier row was already
committed live by the time the later row is processed) — for free. But the resulting error from
`create()` is a generic `AppError::Conflict` with no knowledge of *which* earlier row caused it,
so it cannot alone produce UI-SPEC's required message shape `«Строка {N}: номер уже занят —
{номер} (повтор строки {M})»`.
**Why it happens:** the uniqueness gate lives in the single-record `create()` path, which has no
visibility into the CSV batch's row numbering.
**How to avoid:** `import_csv_commit` needs its own `HashMap<normalized_number, row_index>`
built incrementally as rows are validated (BEFORE calling `create()`), so it can distinguish
"duplicate of an earlier row in this file" (produce the `(повтор строки {M})` suffix) from
"duplicate of a pre-existing DB record" (the plain `«номер уже занят»` message, per UI-SPEC's
two distinct copy templates). The DB-level `create()` uniqueness check remains the authoritative
safety net either way (race-safety per NUM-09), but the friendlier message needs this extra
client-of-the-loop bookkeeping in the import service itself.
**Warning signs:** SPEC's own acceptance example (row 3 duplicates DB, row 5 duplicates row 1) —
a test that doesn't distinguish these two message shapes will pass even if the "(повтор строки
M)" variant is never actually produced.

### Pitfall 6: The two "invalidation mechanisms" in this codebase are NOT interchangeable — CONTEXT's "существующий механизм" is ambiguous between them

**What goes wrong:** this codebase has **two** distinct things a planner might call "the
invalidation mechanism":
1. `ui/src/lib/stores/placeContentEvents.svelte.ts` — a module-level Svelte `$state` store,
   explicitly documented in its own header comment as **NOT a WebSocket** and **NOT
   cross-client**: "Invalidation solves a same-tab/same-session staleness problem... it is not
   cross-client sync." It only helps two components in the *same browser tab* stay in sync.
2. `WsEvent` (`crates/trackly-app/src/dto/printer.rs`) + `ctx.ws_broadcast` — a genuine
   server-pushed, cross-client, cross-session WebSocket broadcast (already used for
   `NewRequest`, `RequestStatusChanged`, `PrinterAlert`), each variant gated by
   `is_visible_to(&identity)` for role-based visibility.

CONTEXT D-14 says the number field should silently refetch "по событию инвалидации
(существующий механизм)" — singular, unspecified which one. If the field is a **cross-user**
concern (user A creates a device consuming the number user B's already-open popup is showing),
only mechanism #2 (`WsEvent`) can actually observe that — mechanism #1 is explicitly scoped to
same-tab and would never fire from another user's action.
**Why it happens:** the CONTEXT document's own phrasing implies a single existing mechanism, but
the two are architecturally very different (session-scoped ephemeral state vs. real
server-to-client push) and serve different problems elsewhere in the codebase.
**How to avoid:** the planner must explicitly decide which of the two D-14 needs — most likely a
**new `WsEvent` variant** (e.g. `NumberSpaceChanged { space, template_id }`) broadcast from
`NumberTemplateService`/`act_service`/`cartridge_service`/`device_service` after any mutation
that touches a number-bearing table, since the realistic race D-14 describes ("another user
just took the number my popup is showing") is inherently cross-client. If the scope is narrowed
to same-tab only (e.g. two forms in the same session), mechanism #1 suffices and is much
cheaper. This ambiguity should be resolved explicitly in the plan, not left implicit — since
D-14 is Claude's-Discretion-adjacent (CONTEXT frames it as a UX nicety, not a hard acceptance
criterion), it is acceptable to scope it down to same-tab-only for cost reasons, but the plan
must say so rather than silently picking one.
**Warning signs:** a plan that wires `notifyPlaceContentChanged`-style same-tab invalidation and
labels it as satisfying "D-14 cross-user refresh" without noting the scope reduction.

### Pitfall 7: `AppError::Conflict`/`AppError::Validation` already carry only `reason`/`field`+`message` strings — D-04's "structured warning, not an error" needs a new response shape

**What goes wrong:** every existing uniqueness/validation failure in this codebase
(`act_service.rs`, `cartridge_service.rs`) returns `AppError::Conflict { reason: String }` or
`AppError::Validation { field, message }` — both are unconditionally treated as failures by
existing frontend error-handling (toasts, inline field errors). CONTEXT D-04 requires the
homoglyph/doppelganger check to return something the client can distinguish as a **soft
warning** (blocks nothing, needs a confirm-and-retry flow) rather than a hard error — reusing
`AppError::Conflict` here would make the frontend treat it as a save failure requiring a fix,
not a "confirm to continue" popup.
**Why it happens:** the existing `AppError` enum was designed for pass/fail semantics; this
phase's D-01 chain (occupied → mismatch → script-mix) is the first place in the app that needs a
three-state result (ok / soft-warn-needs-confirmation / hard-fail) from a single save call.
**How to avoid:** per CONTEXT's own "Claude's Discretion" note ("Форма ответа-предупреждения...
лишь бы одинаково в Tauri и HTTP"), introduce a distinct success-with-warning DTO shape (e.g.
the create/update response becomes `Result<CreateOutcome, AppError>` where `CreateOutcome` is an
enum `{ Created(Dto), NeedsConfirmation(WarningDto) }`, or a `confirm: bool` flag threaded
through the request payload — the "Продолжить" button re-sends the same request with
`confirm_script_mix: true`). Whichever shape is chosen, it must be identical across Tauri and
HTTP per the Dual access path constraint — do not let one transport encode it as an HTTP status
code and the other as a Rust enum variant.
**Warning signs:** a plan that reuses bare `AppError::Conflict` for the script-mix warning and
expects the client to distinguish it from a real occupied-number conflict by parsing the
`reason` string — this is fragile and will break the moment message copy changes.

## Open Questions

1. **Which invalidation mechanism does D-14 actually require?**
   - What we know: two mechanisms exist in this codebase with very different scope (same-tab
     `$state` store vs. cross-client `WsEvent` broadcast) — see Pitfall 6.
   - What's unclear: CONTEXT's own text doesn't disambiguate, and D-14 is framed as a UX nicety
     rather than a hard acceptance criterion (no SPEC acceptance test covers it explicitly).
   - Recommendation: the plan should explicitly choose and document one, defaulting to
     same-tab-only (`$state` store pattern, cheaper) unless the discuss-phase output or the
     planner judges the cross-user race scenario common enough to warrant a new `WsEvent`
     variant. Either choice is defensible; only *silence* on the choice is a problem.

2. **Does the seed-mask width computation (Pitfall 1) need to handle mixed-width existing data?**
   - What we know: the old `assign_code_in_tx` format is minimum-width-4, unbounded growth — in
     practice, for any org that hasn't created more than 9999 cartridges of a kind, all existing
     codes share one width (4 digits).
   - What's unclear: whether any current dev/test/production-shaped fixture actually has mixed
     widths (this would require verifying against a real or representative DB snapshot, which
     this research pass did not have access to — per CLAUDE.md, no real org data may be used for
     this verification anyway).
   - Recommendation: the migration should compute N defensively (`MAX` of observed widths) and
     the plan should include a test fixture with realistic small counts (≤ 4 digits) as the
     primary case; treat mixed-width as a documented edge case rather than blocking on it, since
     realistic org scale (per CLAUDE.md's "20 concurrent LAN users" framing) makes 5+ digit
     cartridge counts implausible.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---|---|---|
| Race condition on number allocation (two users grab the same "first free" number simultaneously) | Tampering / Repudiation (data integrity) | DB-level partial `UNIQUE INDEX` is the actual safety boundary (NUM-09) — the server-side pre-check (D-02) is a UX nicety, not the security control; the final `INSERT`/`UPDATE` inside the writer transaction must always re-check via the index, never trust a client-supplied "I already checked" flag |
| Elevation of privilege via mis-gated Action | Elevation of Privilege | Pitfall 3's fix — verify with `role_endpoint_matrix.rs`-style tests for both transports, since this project has a documented history (IN-02 gap, Phase 40 Plan 14) of new endpoints missing role-matrix coverage on first pass |
| Information disclosure via "Номер занят" popup card | Information Disclosure | The popup card (NUM-10) surfaces another record's name/place/status to whoever can create a record in that space — this is Admin/Manager-only data already visible to those roles elsewhere in the app (device/act/cartridge lists), so no new disclosure boundary is crossed; confirm the card doesn't leak fields beyond what Admin/Manager can already see via `Action::ReadData`/`ReadPlaces` (e.g. do not surface an act's `giver_name`/`receiver_name` if that act belongs to a request-flow the current user role can't otherwise read — unlikely given Manager already has `ReadData`, but worth a one-line check in the plan) |
