<objective>
Реализовать адаптер `SqliteNumberTemplateRepository`: CRUD над `number_templates` /
`number_template_contexts` в транзакции (по образцу `cartridges_sqlite.rs`'s
`insert_model_in_tx`/`update_model_in_tx`), и мост «текстовая колонка БД → числовая
последовательность» — `fetch_matching_values` читает сырые строки, `compute_next_for_template`
прогоняет их через `mask::extract_digits` + `sequence::compute_next` (план 02) и возвращает
`NextNumberResult` (план 01).

Purpose: единственное место в кодовой базе, которое знает, как SQL-таблицы превращаются в
последовательность шаблона — сервис (план 04) и все дальнейшие потребители зовут только эти
методы, не пишут SQL сами.
Output: `SqliteNumberTemplateRepository` + repo-level тесты, table-driven по числам из SPEC.
</objective>

      `SELECT inventory_number FROM devices WHERE deleted_at_utc IS NULL AND inventory_number IS
      NOT NULL`.
    - `fetch_matching_values(conn, TemplateType::CartridgeCode, today)` И
      `fetch_matching_values(conn, TemplateType::DrumCode, today)` ОБА читают
      `SELECT code FROM cartridges WHERE deleted_at_utc IS NULL` — БЕЗ `WHERE kind...` — колонка
      общая для обоих типов шаблонов (см. must_haves.truths этого плана и doc-комментарий из
      плана 01 Task 1).
    - `compute_next_for_template(conn, template: &NumberTemplateRow, today_utc: i64) ->
      Result<NextNumberResult, AppError>`: `mask::parse_and_expand(template.mask, today_utc)` →
      `fetch_matching_values(...)` → для каждого значения `mask::extract_digits(&parsed, &v)`,
      собрать `Vec<u64>` из `Some(...)` (несовпавшие по маске значения — например, ручные номера
      не по шаблону — молча пропускаются, они не часть ЭТОЙ последовательности) →
      `sequence::compute_next(&taken, parsed.digit_width)`.
    - Table-driven тест, буквально по числам SPEC: живые `…01..16` + `…20` (маска
      `ОРГ-00-[XXXXXX]`) → repo вернёт `first_free=17, max_plus_one=21`. Живые только
      `…500..510` → `first_free=1, max_plus_one=511`. `[YYYY]/[MM]-[X]` с живыми записями за
      `2026/08-*` не влияет на подсчёт для `2026/09-*` (разный развёрнутый префикс — разные
      последовательности, проверить оба месяца одновременно в базе).
    - Мягко удалённая запись (`deleted_at_utc` не NULL) не попадает в `fetch_matching_values` ни
      для одного пространства — тест: занять `…002`, мягко удалить, следующий свободный снова
      `…002`.
  </behavior>
