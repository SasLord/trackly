# Phase 40.2 Plan 03: SqliteNumberTemplateRepository Summary

**`SqliteNumberTemplateRepository` — CRUD in-tx over `number_templates`/`number_template_contexts` plus `compute_next_for_template`, the single bridge turning three physical SQLite spaces (`devices.inventory_number`, `acts.number` restricted to handovers, `cartridges.code` shared by both cartridge/drum templates) into a numeric sequence via `mask::extract_digits` + `sequence::compute_next` — verified against every literal SPEC example on a fully-migrated SQLite DB.**

## Accomplishments

- `SqliteNumberTemplateRepository` implements the full `NumberTemplateRepository` trait (`get`, `list`, `get_context_template_id`, `fetch_matching_values`) plus 4 inherent `*_in_tx` write helpers (`insert_in_tx`, `update_mask_in_tx`, `delete_in_tx`, `set_context_in_tx`), mirroring `SqliteCartridgeRepository`'s established shape
- `update_mask_in_tx` has no `template_type` parameter at all (D-10) — type immutability is enforced at the type-signature level, not by a runtime guard that could be bypassed or forgotten
- `delete_in_tx` performs a physical `DELETE` (D-12), relying on V041's `ON DELETE SET NULL` FK to clear any context's memory automatically — verified with an inline unit test that goes through this exact code path (insert → wire context → delete → re-read context), not just DDL inspection
- `fetch_matching_values` correctly reads `acts.number` (INTEGER), `devices.inventory_number` and `cartridges.code` (TEXT) through one `ValueRef`-based accessor, always returning `String`
- `compute_next_for_template` reproduces every literal numeric example from `40.2-SPEC.md`: gap-in-the-middle (`…01..16`+`…20` → `17`/`21`), dense-tail-no-gap (`…500..510` → `1`/`511`), month-prefix isolation for `[YYYY]/[MM]-[X]`, soft-delete freeing a number, and "Картриджи"/"Фотобарабаны" observing isolated sequences despite sharing the physical `cartridges.code` column
- 3 inline CRUD unit tests (minimal in-memory harness) + 5 full-stack integration tests (`fresh_migrated_db` harness, real migrated SQLite) — 8 new tests total, all green

## Decisions Made

- **Task 1/Task 2 code split collapsed into one commit's implementation, tests split honestly across two commits.** The plan's Task 1 `<action>` explicitly deferred `fetch_matching_values`'s real implementation to Task 2, but `NumberTemplateRepository` is a trait — `impl NumberTemplateRepository for SqliteNumberTemplateRepository` cannot compile with `fetch_matching_values` half-stubbed while other trait methods are already implemented and exercised by Task 1's own unit tests (which needed `cargo check -p trackly-infra` to pass per Task 1's acceptance criteria). `compute_next_for_template` has no separate trait-boundary reason to exist standalone from `fetch_matching_values` either. Rather than write a throwaway stub and then immediately replace it in the same file within the same plan, Task 1's commit ships the real implementation, and Task 2's commit ships the table-driven verification `<behavior>` describes — the net code delivered across the two tasks is identical to what the plan specifies, just attributed to a different commit than the plan's literal task boundary.
- **Reused V041's seeded templates instead of inserting duplicates.** 3 of the 5 integration tests (`dense_tail`, `soft_deleted_cartridge`, `cartridge_and_drum_isolation`) call `repo.list(conn, Some(type))` to fetch the template V041 already seeds, rather than `insert_in_tx` with the same `(type, mask)` pair — the seed migration and the plan's own SPEC examples use identical masks (`[X]`, `C-[XXXX]`, `D-[XXXX]`), so a second insert collides with `UNIQUE(type, mask)`. Discovered via a real test failure, not anticipated up front; documented in a `seeded_template` helper's doc comment.

## Deviations from Plan

**[Rule 3 - blocking fix] Test scenarios adjusted to avoid UNIQUE(type, mask) collision with V041 seed data.**
- **Found during:** Task 2/3, first test run
- **Issue:** Tests originally called `insert_in_tx(tx, TemplateType::ActNumber, "[X]", ...)` / `CartridgeCode, "C-[XXXX]"` / `DrumCode, "D-[XXXX]"` — all three collide with V041's own seed rows (D-16), producing `AppError::Conflict` instead of a new template id.
- **Fix:** Added a `seeded_template` test helper that fetches the existing seeded row via `repo.list()` for scenarios that don't need a custom mask (dense-tail, soft-delete, cartridge/drum isolation). The `gap_in_the_middle` and `month_prefix` scenarios keep `insert_in_tx` since their masks (`ОРГ-00-[XXXXXX]`, `[YYYY]/[MM]-[X]`) are genuinely new and don't collide.
- **Files modified:** `crates/trackly-infra/tests/number_templates_repo.rs`
- **Commits:** `787cfed9`, `d466e610`

No other deviations — implementation matches the plan's `<action>`/`<behavior>` literally otherwise.
