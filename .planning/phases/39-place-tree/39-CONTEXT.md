# Phase 39: Дерево мест - Context

**Gathered:** 2026-08-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Фаза заменяет свободнотекстовое «Размещение» на дерево мест произвольной вложенности и
переводит на него все места приложения, где сегодня фигурирует `locations` или текстовое
`location`: формы устройства/картриджа/акта, автокомплиты, фильтры отчётов, полнотекстовый
поиск, печатные формы.

**Никакой графики.** Чертежи, планы этажей, SVG-редактор и подложки — фазы 43–44. Здесь только
семантика: узел дерева существует и работает независимо от того, есть ли для него чертёж.

**Не входит в фазу:** история перемещений (Фаза 40), АРМ (Фаза 41), ранжирование принтеров в
заявке по месту автора (Фаза 42). Фаза 39 обязана лишь не мешать им — схема готовится так,
чтобы фазы 40–42 не переделывали её.

</domain>

<decisions>
## Implementation Decisions

### Модель дерева

- **D-01 (Вложенность — свободная):** жёстких запретов «какой тип в какой» НЕТ. Любой узел
  может лежать в любом. UI при создании подсказывает типичный тип потомка по родителю
  (в здании → этаж, на этаже → помещение), но не блокирует иное. Прямо следует формулировке
  PLC-01 «произвольная вложенность» и не ломается на реальных странностях (пристройка,
  антресоль, бокс во дворе).
- **D-02 (Типы — закрытый enum):** ровно шесть типов — территория / зона / здание / этаж /
  помещение / уличный объект. Расширяемого справочника типов НЕТ: фазы 41–44 будут опираться
  на типы (план 1:1 привязан к этажу/зоне/территории), и произвольные типы сломают эту логику.
- **D-03 (Много корней):** `parent_id` NULL допустим для узла ЛЮБОГО типа. Автоматического
  корня-«Организация» нет. Заполнение базы можно начать сразу со зданий, а территорию добавить
  позже перемещением — это не миграция, а обычная операция.
- **D-04 (Уникальность имени в братьях):** два узла с одинаковым именем у одного родителя
  запрещены (`UNIQUE(parent_id, name)` с учётом soft-delete). «214» в разных зданиях —
  нормально; два «214» на одном этаже — ошибка. Это делает полный путь из PLC-03 однозначным
  идентификатором для человека.
- **D-05 (Порядок братьев):** по умолчанию — `level` (если задан), затем натуральное сравнение
  имени, где числовая часть сравнивается как число («2» раньше «10», не побуквенно).
  Дополнительно у узла есть НЕОБЯЗАТЕЛЬНЫЙ ручной `sort_order`: если он задан, он побеждает
  автоматический порядок. Ручной порядок — это опция, а не обязанность заполнять на каждом
  кабинете.
- **D-06 (Привязка к любому узлу):** устройство и картридж привязываются к узлу ЛЮБОГО уровня,
  не только к листу. «Сервер в Здании А» без указания комнаты — валидное состояние. Ограничения
  «только листья» нет: добавление подузла не должно задним числом делать существующие привязки
  невалидными.
- **D-07 (Место — необязательное поле):** `place_id` NULL допустим, как и сегодняшний
  `location_id`. Системного узла-карантина «Не разобрано» НЕ вводим.

### Склад

- **D-08 (Склад — не тип узла):** склад НЕ становится седьмым типом. Это обычный узел дерева
  (обычно тип «помещение») с булевым признаком `is_storage`. Склад живёт в реальной географии
  и в фазе 43 попадёт на план этажа наравне с остальными помещениями.
- **D-09 (Склад внутри кабинета — вложенный узел):** «небольшой склад для картриджей в
  кабинете» оформляется как вложенный узел («Кабинет 214 / Шкаф-склад») с `is_storage=true`,
  а НЕ флагом на самом кабинете. Иначе рабочие АРМ в этом кабинете начали бы числиться
  складскими.
- **D-10 (Складское место ≠ «не в эксплуатации»):** на складском месте могут стоять рабочие
  АРМ и устройства в работе. Признак `is_storage` НЕ определяет статус того, что там лежит.
- **D-11 (Что меняет `is_storage` в фазе 39):**
  1. **Форма возврата акта** — складские места подняты наверх списка / подставляются по
     умолчанию (сегодня это `acts.bulk_location_id`).
  2. **Отчёты и фильтры** — быстрый фильтр «на складе / в эксплуатации» без перечисления
     конкретных узлов.
  3. **Статус устройства — только как предложение:** при перемещении на складское место форма
     ПРЕДЛАГАЕТ статус «на складе» по умолчанию, но пользователь может снять. Автоматической
     принудительной смены статуса НЕТ (см. D-10).
  4. **Наследование `is_storage` вниз по дереву (уточнение 2026-08-22):** предмет считается
     находящимся в складском месте, если `is_storage=true` у его собственного места ИЛИ у любого
     его предка. Это заставляет работать вложенность внутри склада («Склад / Стеллаж 3 / Полка B»)
     и не конфликтует с D-09: пометка ставится на вложенный узел-склад, поэтому рабочий кабинет
     и его соседние узлы складскими не становятся. Запрос — recursive CTE по предкам, а не
     сравнение одного `place_id`.
  5. **Два разных фильтра, не смешивать (уточнение 2026-08-22):** «лежит в складском месте»
     (география, `is_storage` по D-11.4) и статус предмета «на складе» (`device_statuses.code =
     'на_складе'`) — независимые измерения (прямое следствие D-10). В одной комнате могут
     одновременно находиться рабочие АРМ в эксплуатации и картриджи на хранении. UI и отчёты
     должны называть их по-разному и позволять фильтровать по каждому отдельно.

### Картриджи

- **D-12 (Собственный `place_id` всегда):** у картриджа своё место, как у устройства — не
  вычисляемое из принтера. При операции Install место подставляется из принтера, дальше живёт
  самостоятельно. Одна схема хранения места на обе сущности → Фаза 40 пишет историю
  перемещений одинаково для устройства и картриджа.
- **D-13 (Операции картриджа — выбор места вместо текста):** текстовое `location` в
  `CartridgeTransitionOp` (Install / ReturnToStock / ToRefill / FromRefill / WriteOff) заменяется
  выбором места из дерева с разумным предзаполнением: Install → место принтера,
  ReturnToStock → складское место. Место НЕ вынимается из операций в отдельное действие.

### Удаление и архивация

- **D-14 (Удаление запрещено, пока узел не пуст):** попытка удалить место с содержимым или
  подузлами возвращает ошибку с точным счётчиком («в месте 12 устройств и 2 вложенных места»)
  и кнопкой «Показать содержимое» (ведёт на экран из D-22). Никакого каскада и никакого
  автоподъёма содержимого в родителя.
- **D-15 (Архивация отдельно от удаления):** действие «Архивировать» прячет узел из выпадайки
  выбора места (PlacePicker), но оставляет его в дереве, в карточках и в истории. Жёсткое
  удаление доступно только для пустых узлов без истории. Кабинет закрыли — архивируем, а не
  удаляем.
- **D-16 (Акт хранит снимок пути):** акт хранит и `place_id`, и текстовый снимок полного пути
  на момент выписки. Печатная форма показывает СНИМОК — документ не меняется задним числом при
  переименовании узла; навигация в приложении работает по `place_id`. Прямое следствие
  PLC-05: переименование обновляет живые списки и поиск, но НЕ уже выписанные документы.
  **Гранулярность (уточнение 2026-08-22):** снимок хранится НА УРОВНЕ АКТА — один `place_id` и
  один текстовый путь на весь акт, а не по позициям `act_items`. Это совпадает с текущим
  контрактом печатной формы; позиционные места в фазу 39 не входят.

### Интерфейс выбора места

- **D-17 (Один общий PlacePicker):** `LocationAutocomplete.svelte` заменяется единственным
  компонентом на всё приложение (формы устройства, картриджа, акта, операций картриджа,
  фильтров отчётов). Поведение: по фокусу — раскрываемое дерево; при наборе текста —
  переключение в плоский список совпадений по ПОЛНОМУ пути («Здание А / 2 этаж / 214»).
  Двух разных контролов для «дерево» и «поиск» быть не должно.
- **D-18 (Создание места из PlacePicker — только Admin):** когда совпадений нет, в выпадайке
  доступно «Создать "214" в "Здание А / 2 этаж"». Действие видно ТОЛЬКО роли Admin — Manager
  только выбирает существующие узлы. Резко ускоряет первичное заполнение базы, не давая дереву
  зарастать мусором.

### Раздел «Места»

- **D-19 (Свой пункт в сайдбаре):** отдельный раздел «Места» рядом с «Картой», НЕ вкладка в
  Настройках. Места — рабочие данные, а не конфигурация: туда же ведёт PLC-06 (содержимое
  места), и в фазе 43 рядом встанет «Карта». Заглушку `/map` НЕ трогаем — граница доступа
  Карты (MAP-05) отличается от границы Мест.
- **D-20 (Доступ):** Admin редактирует дерево; Manager видит дерево и содержимое, но без кнопок
  редактирования; Employee не видит раздел вообще (решение вехи, подтверждено). Гейт — на
  бэкенде, на обоих транспортах, как в существующей модели ролей.
- **D-21 (Перемещение узла — И drag-n-drop, И диалог):** drag-n-drop по дереву как быстрый
  путь + диалог «Переместить в…» (тот же PlacePicker в модалке) как клавиатурно-доступная
  альтернатива и обязательный a11y-паритет (Фаза 30). Диалог показывает последствия до
  подтверждения («переедет 3 вложенных места и 47 устройств»).

### Экран содержимого места (PLC-06)

- **D-22 (Две панели в разделе «Места»):** слева дерево, справа содержимое выбранного узла.
  Один экран закрывает и PLC-01 (построение), и PLC-06 (содержимое); клик по узлу не
  перезагружает страницу.
- **D-23 (Одна таблица с колонкой «Тип»):** содержимое показывается буквально «одним списком» —
  строки разных сущностей (устройство / принтер / картридж) в одной таблице с колонкой типа и
  фильтром-чипами. Фаза 41 добавит в эту же таблицу тип «АРМ», не переделывая экран.
- **D-24 (Вложенные — по умолчанию да, с тумблером):** по умолчанию показываются вложенные
  места (как требует PLC-06), рядом тумблер «только здесь». Тумблер нужен не только для
  удобства — без него непонятно, почему узел не удаляется (D-14).
- **D-25 (Счётчики на узлах дерева):** у каждого узла показывается суммарный счётчик С УЧЁТОМ
  вложенных («2 этаж · 47»). Сразу видно, где густо и какие узлы пусты (кандидаты на удаление).

### Отображение места

- **D-26 (В таблицах — сокращённый путь + tooltip):** в ячейке два последних сегмента
  («2 этаж / 214»), полный путь — в `title`/tooltip и в карточке сущности. Колонка остаётся
  читаемой при 100–150 устройствах на этаж.
- **D-27 (В печатных формах — полный путь):** в акте приёма-передачи печатается ПОЛНЫЙ путь.
  Документ должен быть однозначен без доступа к базе — это и есть снимок пути из D-16.
- **D-28 (Фильтр по месту — включая вложенные):** выбор «Здание А» в фильтре списка или отчёта
  захватывает всё здание целиком, включая вложенные узлы. Согласуется с D-24 и PLC-06.

### Поиск

- **D-29 (Место — в обоих FTS-индексах):** глобальный поиск по «214» находит И устройства,
  И картриджи по месту. Сегодня `cartridges_fts` индексирует текстовое `location`, а
  `devices_fts` место не индексирует вообще — паритет восстанавливается. Переименование или
  перемещение узла обновляет ОБА индекса без ручной переиндексации (PLC-05).

### Claude's Discretion

Пользователь не высказывался — решают researcher и planner:

- **Способ хранения дерева в SQLite:** adjacency list + рекурсивный CTE, денормализованная
  колонка пути, closure table или materialized path. Требование — выполнить D-29/PLC-05
  (переименование и перемещение мгновенно отражаются в поиске и списках без ручной
  переиндексации) на масштабе ~4–5 зданий × 2–3 этажа × ≤20 кабинетов.
- **Защита от циклов** при перемещении узла (нельзя переместить узел в собственного потомка) —
  обязательна, реализация на усмотрение.
- **Механика синхронизации FTS** для D-29: триггеры vs пересчёт в сервисном слое; ключевое
  ограничение — переименование одного узла не должно требовать полного ребилда индекса.
- **Форма хранения снимка пути в акте** (D-16): колонка в `acts` / в `act_items` / в обеих.
- **Названия таблиц и колонок** (`places`, `place_id`, `is_storage`, `level`, `sort_order` —
  рабочие имена из обсуждения, не обязательство).

## Existing Code Insights

### Reusable Assets
- **Dropdown из Фазы 25** — кастомный компонент, база для PlacePicker (D-17). В проекте есть
  устойчивая обратная связь: мигрировать `<select>` на кастомный Dropdown, а не на обёртку над
  нативным select.
- **`LocationAutocomplete.svelte`** — готовое поведение выпадайки (portal, dropdownAnchor,
  debounce, ArrowDown-навигация, очистка таймера на unmount). PlacePicker наследует механику,
  меняет источник данных и рендер строки.
- **Паттерн FTS-триггеров из `V013`** — три AFTER-триггера + фильтр по `deleted_at_utc IS NULL`.

### Established Patterns
- **Единый сервисный слой:** Tauri-команды и axum-хендлеры — тонкие адаптеры над сервисом; все
  записи идут через одного писателя. Новые операции над деревом обязаны появиться на ОБОИХ
  транспортах одновременно (`specta_export.rs` + `http/*.rs`).
- **Ролевой гейт на бэкенде** — граница безопасности, а не гейт маршрута в UI (см. бэклог
  999.1). D-20 реализуется серверной проверкой.
- **`refinery`-миграции с `PRAGMA user_version`** — следующий номер `V037`.

## Specific Ideas

- **Формулировка пути** из PLC-03 взята за канон: `«Здание А / 2 этаж / 214»` — разделитель
  ` / `, порядок от корня к листу.
- **Реальный масштаб (подтверждён пользователем):** ~4–5 зданий × 2–3 этажа, ≤20 кабинетов и

  склады внутри кабинетов (в первую очередь для картриджей), и при этом на складе стоят рабочие
  АРМ. Все три случая должны работать без натяжек (D-08…D-11).

  эксплуатации, все акты в БД тестовые, значения размещения обнуляются. Не тратить план на
  конвертацию `locations` → `places`.
