# Phase 44: Link — транспорт, пин сертификата и вход - Context

**Gathered:** 2026-11-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Link из каркаса Фазы 42 становится фоновым клиентом:
- живёт в трее и стартует свёрнутым при входе в систему;
- работает в одном экземпляре на пользователя сеанса (RDS — по экземпляру на сеанс);
- говорит с сервером Trackly только через Rust-часть и только при совпадении закреплённого SPKI-отпечатка;
- впускает сотрудника автоматически (SPNEGO на доменном Windows-ПК) или по логину и паролю (вне домена), запоминает вход;
- даёт администратору отозвать вход;
- сам переподключается и после сна догружает пропущенное.

Требования: LNK-02, LNK-03, LNK-04, LNK-05, LNK-06, LNK-07, LNK-08, LNK-09, LNK-11.

Не входит в фазу:
- установщик с параметрами, GPO, подпись, автообновление, сборки и каналы, полный список клиентов с версиями (Фаза 45);
- чат и его UI (Фазы 47–51);
- системные уведомления и счётчики в трее (Фаза 51).

</domain>

<decisions>
## Implementation Decisions

### Сервер, отпечаток и первая настройка
- **D-01:** Источник адреса сервера и отпечатка — **конфиг, иначе экран первой настройки**. Конфиг имеет приоритет. Если конфига нет, окно Link показывает экран первой настройки. Установщик с параметрами — Фаза 45; в 44 клиент только читает конфиг.
- **D-02:** Конфиг ищется в двух местах по порядку:
  1. **машинный** — один на ПК; его кладёт администратор или GPO, на RDS-хосте он действует для всех пользователей, сотрудник его не правит;
  2. **пользовательский** — в каталоге данных пользователя; его пишет экран первой настройки.

  Точное место машинного конфига (`HKLM` или `%ProgramData%`) и его формат выбирает исследователь с учётом установки без прав администратора (ADR 0005).
- **D-03:** Экран первой настройки принимает **одноразовый код-приглашение**, а не ручной ввод отпечатка и не TOFU. Код несёт адрес сервера и SPKI-отпечаток, имеет срок действия и используется один раз. Отпечаток, полученный при подключении, сверяется с отпечатком из кода; без совпадения ничего не сохраняется. Кнопки «Доверять» нет.
- **D-04:** Код-приглашение даёт **только настройку**: сервер, отпечаток и регистрацию устройства. Код не привязан к сотруднику и не входит в учётную запись. После настройки сотрудник входит как обычно: через SSO или паролем.
- **D-05:** Коды выпускает администратор в **новом разделе «Link»** в Trackly — его заводим уже в Фазе 44. Фаза 45 добавит туда сборки, каналы и полный список клиентов. Сам раздел и его видимость только администратору — в этой фазе.
- **D-06:** Закрепляется **SPKI-отпечаток** (SHA-256 открытого ключа листового сертификата), а не всего сертификата (ADR 0002). Сейчас сервер показывает SHA-256 всего DER-сертификата (`server/tls.rs`, `NetworkSettings.svelte`). Нужно:
  - показывать администратору SPKI-отпечаток для Link;
  - при перевыпуске самоподписанного сертификата **сохранять ключ**, чтобы продление сертификата не ломало закреплённые клиенты.

  Смена ключа — редкое ручное событие: после неё клиентам нужен новый код или новый конфиг.
- **D-07:** Если отпечаток не совпал, показывается **только ошибка**: «сертификат сервера изменился, обратитесь к администратору», ожидаемый и полученный отпечатки (для администратора). Принять новый сертификат сотрудник не может. Запросов и данных Link не отправляет — ни вход, ни токен, ни SPNEGO.
- **D-08:** Адрес сервера — **DNS-имя или IP**, допустимы оба. Доменный вход возможен только по имени (SPN). Если адрес — IP, Link не пытается SSO и сразу предлагает пароль с причиной (см. D-09). Имя хоста при проверке TLS не сверяется: доверие держится только на пине.

### Вход и отзыв
- **D-09:** Если автоматический вход на доменном ПК не удался (нет SPN, адрес по IP, SSO выключен на сервере, учётная запись не сопоставлена, ошибка Kerberos), Link показывает **форму логина и пароля**:
  - с короткой понятной причиной, почему автовход не вышел;
  - с кнопкой «Повторить автовход».

  При следующем запуске SSO пробуется снова. Пароль никогда не отправляется повторно автоматически (риск блокировки учётной записи).
- **D-10:** Вне домена вход **запоминается всегда**, без галочки. Вход живёт до «Выйти» или до отзыва. Пароль нигде не сохраняется; в хранилище ОС лежит только токен (ADR 0002). Если хранилища ОС нет (Linux без Secret Service), токен живёт только в памяти.
- **D-11:** У сотрудника есть пункт **«Выйти из учётной записи»**: он стирает токен локально и отзывает его на сервере. После этого можно войти другим логином. На доменном ПК после «Выйти» автовход **не срабатывает сам**, пока сотрудник не нажмёт «Войти автоматически».
- **D-12:** Администратор отзывает вход **двумя путями**:
  1. в разделе «Link» — список активных входов (сотрудник, компьютер, способ входа, когда) с кнопкой «Отозвать»;
  2. в карточке пользователя — «Отозвать входы Link», все сразу.

  Блокировка пользователя тоже отзывает все его входы Link.
- **D-13:** **Отзыв означает запрет устройства.** Отозванное устройство не может войти ни паролем, ни автовходом, пока администратор не разрешит его снова. Механику повторного допуска (кнопка «Разрешить» в разделе «Link» и/или новый код-приглашение) выбирает планировщик. Обычный «Выйти» сотрудника устройство не запрещает.
- **D-14:** Отзыв или блокировка срабатывают **на лету**: сервер разрывает WS и сессию этого входа, Link стирает токен и открывает окно с экраном входа и надписью «Вход отозван администратором». Автовход после отзыва не повторяется.
- **D-15:** macOS и Linux — **только вход паролем**: клиентский Kerberos вне Windows не входит в объём (исследование, PITFALLS M-5). Доменный вход проверяется только живьём на Windows с AD; по моку он не считается проверенным.

### Трей и окно
- **D-16:** Трей:
  - **левый клик** показывает или прячет окно;
  - **правый клик** открывает меню: «Открыть Link», строка состояния (ФИО · в сети / нет связи), «Выйти из учётной записи», «Закрыть».

  «Закрыть» — единственный способ завершить Link (LNK-04). На платформах без события клика (Linux) остаётся только меню. Подсказка иконки — «Trackly Link» (D-08 Фазы 42).
- **D-17:** **Автозапуск всегда включён**, отключить его в Link нельзя, пункта меню нет. При старте Link проверяет запись автозапуска и восстанавливает её, если её удалили. На Windows это запись автозапуска текущего пользователя, на macOS — login item, на Linux — autostart `.desktop`.
- **D-18:** Свёрнутым в трей Link стартует, **только если всё готово**: конфиг есть, и вход есть или пройдёт сам по SSO. Окно открывается само, если нужно действие сотрудника: код-приглашение, пароль, отпечаток не совпал, вход отозван.
- **D-19:** Повторный запуск показывает и фокусирует окно уже работающего экземпляра. Экземпляр один на пользователя **сеанса**: на RDS у каждого пользователя свой (ADR 0004).
- **D-20:** **Linux без системного трея** (GNOME без расширения AppIndicator): Link ведёт себя как обычное приложение. Окно видно на панели, закрытие окна сворачивает его, а не прячет «в никуда». Выход — пунктом внутри окна Link. Подсказку «установите расширение» не показываем. macOS — без значка в Dock, иконка в строке меню.
- **D-21:** Пока чата нет, после входа окно показывает каркас Фазы 42: заглушку «Здесь скоро будет чат» и служебную строку (D-16 Фазы 42). В шапке добавляются:
  - ФИО и способ входа (доменный / пароль);
  - сервер;
  - состояние связи.

  Этого достаточно для живой проверки на Windows. Отдельной диагностической панели нет.

### «Нет связи» и переподключение
- **D-22:** Потеря связи показывается в двух местах:
  - **плашкой в окне** — «Нет связи с сервером · переподключение…» с кнопкой «Повторить сейчас»;
  - **серой иконкой трея** с подсказкой «Trackly Link — нет связи».

  Системных уведомлений о связи нет.
- **D-23:** Индикация появляется **с задержкой ~5 с**: короткие обрывы (перезапуск сервера, моргнул Wi-Fi) проходят молча. Переподключение идёт с нарастающей паузой до ~30 с. После сна ПК или смены сети пауза сбрасывается и Link подключается сразу. Это повторяет D-14/D-15 Фазы 43.
- **D-24:** После переподключения или сна Link **догружает пропущенное** через механизм Фазы 43: `hello`, `resync_required`, ресинк по курсору. Ресинк тихий (D-09 Фазы 43).
- **D-25:** Если связи нет при старте, а вход уже был (есть токен или доступен SSO), Link **тихо ждёт сеть** в состоянии «нет связи». Форму пароля из-за обрыва он не показывает. Пароль спрашивается, только когда сервер сам ответил, что вход недействителен или отозван.

### Claude's Discretion
- Формат кода-приглашения (строка или ссылка, длина, кодировка), его срок по умолчанию и хранение на сервере (хэш).
- Схема серверных сущностей устройства и входа (`link_devices`, токены устройства, `link_resume`). Ориентир — ARCHITECTURE.md §«Аутентификация не-браузера»; имена и детали решает планировщик.
- Крейты SSPI, keyring-store, tray, autostart, single-instance и способ различать экземпляры по сеансу RDS — по исследованию.
- Набор иконок трея (обычная и серая) — от знака Link (D-12 Фазы 42), под DPI Windows. Пересоздание иконки после перезапуска Explorer — по исследованию.
- Тексты ошибок и причин неудачного автовхода. Тон — как в Trackly, без технических деталей Kerberos для сотрудника; детали — в лог (без токенов и SPNEGO-заголовков).

</decisions>

## Existing Code Insights

### Reusable Assets
- `crates/link-app/src/main.rs`, `crates/link-app/tauri.conf.json` — каркас Link. Окно `visible:false`, `tauri-plugin-window-state`, CSP без сети. Сюда добавляются трей, single-instance, autostart, сетевой слой и команды.
- `link-ui/` + `packages/{design,kit,transport}` — UI Link и общий транспорт. `packages/transport` из Фазы 43 уже умеет ресинк и интерфейс источника событий.
- `crates/trackly-app/src/http/sso.rs` — серверная сторона SPNEGO (`GET /api/v1/auth_ad_sso`, 401 Negotiate → токен). Сервер переиспользуется; меняется только то, что сессия выдаётся клиенту Link.
- `crates/trackly-app/src/http/auth.rs` — `build_auth_login` (вход паролем, rate-limit, `remember` → 30 дней), `session_identity`.
- `crates/trackly-app/src/server/tls.rs` — генерация и загрузка самоподписанного сертификата, `compute_fingerprint` (сейчас SHA-256 всего DER). Нужен SPKI-вариант и сохранение ключа при перевыпуске.
- `ui/src/features/settings/NetworkSettings.svelte` — где администратор сейчас видит отпечаток.
- `crates/trackly-app/src/http/ws.rs` — WS с `hello`/ping/`resync_required` (Фаза 43). Нужен разрыв соединения при отзыве (D-14).

### Established Patterns
- Сессии `tower-sessions` и `session_identity()` в каждом защищённом хендлере. Клиент Link держит cookie в Rust (cookie jar), а не в webview.
- Миграции: только CREATE, каждая с `PRAGMA user_version = N` (память: migration_user_version_pragma); FK на `users` не ставить.
- Новые мутирующие маршруты попадают в реестровые гейты (`entities_changed_gate`, инвентарь write-site) — сверять от репозитория.
- `spa_fallback` маскирует отсутствующие `/api/` маршруты (отдаёт index.html с 200): новые маршруты Link покрывать тестом, а не проверять в браузере.

### Integration Points
- Новый раздел «Link» в UI Trackly: маршрутизация и меню администратора, коды-приглашения, список входов.
- Карточка пользователя (`ui/src/features/users/`): кнопка «Отозвать входы Link»; блокировка пользователя → отзыв.
- Мост Rust → webview в Link (`emit('link-event')`, как `trackly-event` у десктопа) и `invoke('api_call')` в Rust-транспорт.

<specifics>
## Specific Ideas

- Код-приглашение выбран вместо ручного ввода отпечатка и вместо TOFU. Сотрудник ничего не сверяет глазами, а пин при этом доставляется по каналу, который контролирует администратор.
- Отзыв делаем строгим («запрет устройства»), а не просто «выкинуть сеанс». Иначе на доменном ПК автовход сразу вернул бы отозванного.
- Живые проверки (SPNEGO на доменном ПК, трей Windows и перезапуск Explorer, RDS с двумя пользователями, автозапуск) — human-UAT на Windows. По моку и стенду они не считаются проверенными (память: auto_advance авто-одобряет human-verify).

</specifics>
