<objective>
Close the single biggest risk this phase's research identified: the LAN-mode axum
`Content-Security-Policy` header currently sets `script-src 'self'` with no `'unsafe-inline'`,
and `<iframe srcdoc>` documents inherit their creator's CSP regardless of the `sandbox` attribute
— so the inline Paged.js bootstrap script Plan 33-03 will inject into the preview iframe would be
silently blocked in server mode without this fix (D-14). Also lands the independent D-13
structural regression guard (all three print templates must declare an identical `@page` block).

Purpose: make LAN-mode pagination actually executable, with a hash-drift guard that fails CI
loudly instead of the feature silently degrading; and guard against future desync of print
margins across document types.
Output: one new Rust test file, one new Node lint script, `http/mod.rs`'s CSP extended by exactly
one hash-source token, `security_headers.rs` extended with a regression assertion.

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| LAN client browser ↔ axum server | The `Content-Security-Policy` response header (`crates/trackly-app/src/http/mod.rs`) — this plan's core change. |
| User-editable HTML template (Phase 16 D-03) ↔ preview `<iframe srcdoc>` | Pre-existing boundary, unchanged by this plan; referenced here because the CSP change interacts directly with it (see T-33-02-04). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-33-02-01 | Tampering | `content-security-policy` `script-src` directive (`http/mod.rs`) | mitigate | Add exactly one `'sha256-<digest>'` source scoped to the literal static text of `PAGED_PREVIEW_INLINE_SCRIPT` (Plan 33-01) — NOT `'unsafe-inline'`. A hash source only authorizes script text that byte-matches the hash; an attacker-injected inline script (e.g. via a compromised/malicious HTML template, the pre-existing Phase 16 D-03 trust boundary) produces a different hash and stays blocked. `'unsafe-inline'` was already deliberately rejected once for this exact reason (the WR-07 comment already in `http/mod.rs`) and this plan does not reopen that decision — this is the core reason (c) a hash source is used instead. |
| T-33-02-02 | Tampering (defense-in-depth erosion) | Hash constant vs. actual shipped script bytes drifting apart (pagedjs version bump, hand-edit to `bootstrapScript.js`) | mitigate | `ui/scripts/check-pagedjs-csp-hash.mjs` (Task 1) independently recomputes the hash from the same two source files using the identical concatenation formula as `pagedPreviewBootstrap.ts`, reads the hardcoded constant out of `http/mod.rs`, and fails `pnpm lint` (CI gate) on mismatch. This is risk (a) from the security requirement: a silent drift failure mode presents as LAN-mode preview hanging on the loading spinner until Plan 33-03's 8s timeout (D-02) degrades it — the WYSIWYG/pagination guarantee (PRV-01) would be silently lost for every LAN user until the lint gate (or a human) notices. |
| T-33-02-03 | Elevation of Privilege (scope check) | New CSP source applies only to `script-src`, not any other directive | accept | This is risk (b) from the security requirement: the diff is additive-only to `script-src`; all other directives (`style-src 'unsafe-inline'` pre-existing and unrelated, `img-src data:`, `connect-src wss:`, `frame-src`/`object-src blob:`) are untouched — confirmed by Task 2's `security_headers.rs` assertion, which isolates the `script-src` segment specifically before checking for `sha256-`/absence of `unsafe-inline`, so a regression that accidentally widens a different directive would not be masked by this check. |
| T-33-02-04 | Elevation of Privilege | Compensating control: preview `<iframe>` sandbox posture (D-05, wired in Plan 33-03) | accept | This is risk (d) from the security requirement: the CSP hash only grants *permission for the specific script to run* — the actual capability of that script remains bounded by `sandbox="allow-scripts"` **without** `allow-same-origin`, giving the iframe document an opaque origin (no `document.cookie`/`localStorage`/parent-DOM access; `postMessage` with strict `event.source` validation is the only cross-boundary channel — Plan 33-01's `pagedPreviewBridge.ts`). This matters specifically because the rendered document originates from a **user-editable HTML template on disk** (`crates/trackly-app/templates/*.html`, editable via Settings → TemplateEditor per Phase 16 D-03) — a semi-trusted content source. The CSP hash-source and the iframe sandbox attribute are two independent, stacked mitigations for that same trust boundary; this plan changes only the first and does not treat it as sufficient on its own. |
| T-33-02-SC | Tampering | npm/pip/cargo installs | accept | No new package-manager installs in this plan (`pagedjs` already added and legitimacy-verified in Plan 33-01); `check-pagedjs-csp-hash.mjs` is zero-dependency (`node:crypto`/`node:fs`/`node:path`/`node:url` only, matching the existing `check-tokens.mjs` convention) — nothing new to audit. |
