# Phase 33 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder:** this spec covers ONLY the print-preview modal chrome and pagination
UX in `PdfPreviewModal.svelte` — backdrop, sheet chrome, loading/progress state, page
counter, hint line, error/empty states, dark theme, a11y, responsiveness. It does NOT
specify the document's own internal typography/layout (owned by the HTML templates,
`crates/trackly-app/templates/*.html`, locked by D-01 — not touched this phase).

## Spacing Scale

Using the project's existing 11-level `--tr-space-*` scale (not the generic 7-level template
scale — this project's token system supersedes the template default).

| Token | Value | Usage in this phase |
|-------|-------|----------------------|
| `--tr-space-md` | 16px | Backdrop padding around the sheet stack (top/left/right), matches existing `.pdf-page-frame` padding of `var(--tr-space-md) 0` (kept) |
| `--tr-space-xl` | 24px | Inter-sheet vertical gap (Claude's Discretion, D-09) — matches Word/Chrome print-preview's visually generous page separation, and matches the modal's own `--tr-space-xl` padding rhythm used in `.modal-body`/`.modal-header` |
| `--tr-space-xl` | 24px | **Added post-UAT round 5 (debug session `print-preview-always-degrades.md`, defect #5 cause B):** horizontal gutter on `.pagedjs_pages` (`padding: 16px 24px`, was `16px 0`), reusing the same token value as the inter-sheet vertical gap above. Without horizontal room, the per-sheet shadow (D-09) had nowhere to paint — clipped at the iframe edges and forcing horizontal overflow. `.pdf-iframe`/`.pdf-scale-inner` width grew from 794px to 842px (794 + 2×24) to match, and the D-11 `scaleFactor` divisor was updated from 794 to 842 accordingly. Literal `24px` is used inside the opaque-origin iframe's injected `<style>` (cannot resolve `--tr-*` custom properties across that boundary), matching this file's existing literal-hex convention for backdrop/shadow colors. |
| `--tr-space-sm` | 12px | Horizontal gap between page-counter text and hint-line text in the footer (if both render on one line — see Copywriting) |
| `--tr-space-xs` | 8px | Gap between Spinner and progress text in the loading state (already the existing `.state { gap: var(--tr-space-md) }` value stays for the icon↔heading gap; `--tr-space-xs` is for the new secondary progress line, see Typography) |

Exceptions:

1. The sheet's own internal margins (20mm/15mm, from `@page` in the HTML templates) are NOT
   part of this spacing scale — they are physical print units owned by D-01/D-13, not
   `--tr-space-*` tokens. Do not attempt to reconcile the two systems; they answer different
   questions (chrome spacing vs. document print margins).
2. `--tr-space-3xs` (2px, used for the page-counter ↔ hint-line gap in the footer — see
   Modal Chrome) is deliberately off the 4px grid. It is a real, pre-existing token from the
   project's approved 11-level scale (Phase 23), not an invented value, and 2px is the correct
   optical gap for two stacked de-emphasized meta lines. Flagged explicitly so the executor
   does not "correct" it to `--tr-space-2xs`.

Reusing existing typography roles — no new roles introduced.

| Role | Size | Weight | Line Height | Token | Usage |

**Weight budget for this phase: 400 and 500 only.** The 600-weight "Heading (error)" row above

**Color split on this surface:** backdrop (`--tr-surface-sunken`) is dominant, the white sheet
stack is the secondary surface, and accent (`--tr-accent`) is reserved exclusively for the
existing "Печать" button — roughly a 60/30/10 dominant/secondary/accent read. No other element
on this surface may claim accent.

### Dark-theme note on the shadow (Claude's Discretion, flagged risk)

`--tr-elev-2` in dark theme is `0 3px 10px rgba(0,0,0,.55), 0 1px 2px rgba(0,0,0,.5)` — a
**black** shadow. Against `--tr-surface-sunken` dark (`#0a0d12`, itself near-black), a
black shadow has very low contrast and may visually fail to separate the white sheet from
the backdrop the way it clearly does in light theme (where the shadow sits on a light-grey
`#e4e8f0` backdrop). CONTEXT.md D-09 locks `--tr-elev-2` as the shadow token and does not
ask for a swap — so this spec does **not** override the locked decision. Mitigation within
the lock: rely primarily on the **hard color boundary** (pure white sheet vs. near-black
backdrop is already ~19:1 contrast, which is the dominant separation cue), with the shadow
as a secondary depth cue rather than the primary one. If UAT (D-13) finds the dark-theme
separation genuinely reads as flat/undifferentiated, the fallback is a **1px `--tr-border`
outline on the sheet in dark theme only** (`[data-theme='dark'] .pdf-iframe { border: 1px
solid var(--tr-border) }`) — flagged here as an open item for the executor to apply *only
if* the shadow-alone approach fails manual UAT, not applied proactively (D-09's "no border"
instruction is written as a light-theme-derived rule reacting to the *current* stock
`interface.css` look, not a considered light+dark call — but this spec defers to the lock
by default and only escalates if visually necessary).

## Loading / Progress State (Claude's Discretion + D-07)

Replaces the plain `<Spinner /><p>Генерируем PDF…</p>` with a two-line progress state that
transitions smoothly into the rendered sheet stack.

**Layout** (reuses existing `.state.state-loading` flex-column-centered container, no new
wrapper class needed beyond what already exists):

```
        [Spinner size="md"]
        Готовим документ…              ← --tr-text-body, --tr-text-secondary (existing style)
        Страница 3…                    ← --tr-text-label, --tr-text-tertiary (NEW, secondary line)
```

- Primary line copy: **"Готовим документ…"** (changed from current "Генерируем PDF…" —
  the document is no longer literally becoming a PDF at this step, it's being paginated by
  Paged.js; "Готовим документ" stays accurate whether the eventual action is preview or
  print).
- Secondary line copy: **"Страница {N}…"** where `{N}` is the 1-indexed count of pages
  Paged.js has rendered so far (from the `renderedPage` event via the `postMessage` bridge,
  per RESEARCH.md Pattern 1/2). Before the first `renderedPage` event arrives, render the
  secondary line as **"Разбиваем на страницы…"** (covers the gap between srcdoc-set and
  first progress event — Paged.js's `removeStyles()`/`Polisher` setup work has no
  page-granularity progress to report yet).
- Gap between the two lines: `--tr-space-xs` (8px) — tighter than the `--tr-space-md` gap
  between Spinner and the first line, to visually group "primary status + its live detail"
  as one unit distinct from the spinner icon.
- `aria-live="polite"` on the state container (matches the established project pattern —
  `detail-loading`, `CartridgeDetail.svelte:106` et al. — see Accessibility section).
- **Button state during loading:** "Печать" stays `disabled` (existing `disabled={loading ||
  errorMsg !== null}` binding — extend the disabling condition to also cover "pagination in
  progress but `htmlContent` already set", i.e. keep it disabled until the `trackly-pagedjs-
  done` message arrives, per D-07's explicit requirement that print must wait for pagination
  completion, not just for the HTML string to arrive).

**Transition to rendered state (no jarring jump):** on receiving `trackly-pagedjs-done` (with
`total` page count and `height`), swap from the loading state to the sheet-stack state in a
single Svelte reactive update (conditional block swap, same pattern as the existing `{#if
loading}...{:else if...}` chain) — no separate fade/crossfade animation is specified (none
exists elsewhere in this modal's states today, and Phase 30's reduced-motion rule
(`global.scss:47`) would suppress any new transition-duration content anyway, so a plain
swap is both simpler and consistent). The one thing that must NOT jump is layout height: the
`.pdf-page-frame` container should already be sized close to its final scrolling viewport
(it's inside the fixed-size `.modal-pdf-preview`, D-12, which does not resize) — so there is
no reflow of the modal itself, only of the content inside the already-fixed frame. No
additional spec action needed beyond keeping `.modal-pdf-preview`'s fixed dimensions (D-12,
already locked).

## Page Counter & Hint Line (Modal Chrome — D-10, D-03, Claude's Discretion)

Both live in the modal's existing `footer` snippet region — NOT inside `Modal.svelte` itself
(D-12 locks `Modal.svelte` as unchanged) — meaning both are rendered by
`PdfPreviewModal.svelte`'s own `{#snippet footer()}` block, to the LEFT of the existing
"Закрыть" / "Печать" button pair (which stay `justify-content: flex-end` per
`Modal.svelte`'s `.modal-footer` — the new elements need their own flex item that pushes the
buttons right, not a change to `Modal.svelte`'s CSS).

**Placement:** footer, not header. Rationale: the header already carries the modal title
(`title` prop — e.g. "Акт приёма-передачи №..." per caller) and the close (×) button; adding
a page counter there crowds a title that can already be long (device/act numbers). The footer
has clear horizontal room to the left of the two action buttons and is the more natural place
for print-adjacent meta info per D-03's own precedent (the hint line was already specified to
live in the footer).

**Footer layout (new `.pdf-preview-footer-meta` block, left-aligned, footer becomes a 2-zone
flex row: meta block | button group):**

```
┌────────────────────────────────────────────────────┬─────────────┬─────────┐
│ 3 страницы                                          │  Закрыть    │ Печать  │
│ Печать использует масштаб 100% и поля по умолчанию  │             │         │
│ страницы — проверьте эти настройки в диалоге печати │             │         │
└────────────────────────────────────────────────────┴─────────────┴─────────┘
```

- Page-counter copy (D-10): **"{N} страниц{ы/а/ей}"** — Russian plural agreement required
  (1 → "страница", 2–4 → "страницы", 5+ → "страниц"; standard RU pluralization, same rule
  family already needed elsewhere in the app for counts — implement with the same
  pluralization helper pattern if one already exists in the codebase, otherwise a small local
  helper). Rendered in `--tr-text-label` (13px/500), color `--tr-text-secondary`.
- Hint-line copy (D-03): **"Печать использует масштаб 100% и поля по умолчанию — проверьте
  эти настройки в диалоге печати."** Rendered in `--tr-text-caption` (12px/500), color
  `--tr-text-tertiary` (deliberately quieter than the page counter — it's a secondary caveat,
  not primary status).
- Vertical stack: page counter above hint line, `--tr-space-3xs` (2px) gap (tight — these two
  lines read as one meta block, not two separate pieces of information).
- The meta block is hidden entirely while `loading === true` or `errorMsg !== null` (no
  page count or print-dialog hint makes sense before pagination succeeds) — `{#if !loading &&
  errorMsg === null && htmlContent !== null}` guard, mirroring the existing state-gating
  pattern already used for the body content.
- Meta block gets `flex: 1 1 auto; min-width: 0` so long hint text wraps rather than pushing
  the buttons off the visible footer on narrow widths (see Responsive section).

## Error & Empty States (D-02 degraded path)

The component already has `state-error` / `state-empty` (existing CSS classes, unchanged
visual treatment: centered column, `--tr-space-md` gap, `--tr-text-secondary` body color).
This phase adds **one new distinguishable sub-case** without adding a new top-level state
class — the render-call error (existing, HTTP/backend failure) and the pagination-timeout
degraded path (new, D-02) are visually different outcomes and must not be conflated:

| Case | Trigger | Visual treatment | Copy |
|------|---------|-------------------|------|
| **Render error** (existing, unchanged) | `renderCall()` promise rejects — backend/network failure | `.state-error`, `--tr-danger` heading | "Не удалось сгенерировать PDF" / `{errorMsg}` detail (unchanged) |
| **Pagination degraded** (NEW, D-02) | `htmlContent` loaded successfully, but no `trackly-pagedjs-*` message arrives within the timeout window (RESEARCH.md Pitfall 1 — CSP-blocked script gives no error event, only silence) | **NOT** `.state-error`. Falls back to showing the document **unpaginated in the iframe**, exactly as it rendered before this phase (`sandbox=""`, no Paged.js chrome, no page counter, no scale-to-fit) — this is a silent, graceful fallback per D-02's explicit wording ("модалка показывает документ как раньше... а не пустой экран"), not an error banner. |
| **Empty** (existing, unchanged) | `htmlContent === null` after a `ready` state with no error (edge case, existing) | `.state-empty` (unchanged) | "Нет данных для предпросмотра." (unchanged) |

**Important distinction for the executor:** the degraded path is NOT a copy/UI change to the
error state — it is a *branch* that intentionally looks like the *pre-Phase-33* UI (current
`.pdf-page-frame`/`.pdf-iframe` treatment, `sandbox=""`, no backdrop/page-counter chrome).
Do not add a "проблема с пагинацией" toast, banner, or badge — D-02 explicitly wants this to
be invisible/non-alarming to the user, since the document is still fully usable for reading
and (if the browser's own native print pagination still works) still printable, just without
the new WYSIWYG guarantee. The one place this *is* surfaced is developer-facing: log a
`tracing`/console warning so the CSP-hash-drift failure mode (RESEARCH.md Pitfall 1) is
diagnosable, but that is a logging concern, not a visual-spec concern.

**Timeout value:** not locked by CONTEXT.md (Claude's Discretion territory, though not
explicitly listed — treating as an open item). Recommend **8 seconds** from `srcdoc` being
set to receiving the first `trackly-pagedjs-progress` OR `trackly-pagedjs-done` message,
given RESEARCH.md's Open Question #3 confirms no custom font loading is involved (should
resolve near-instantly under normal conditions) — 8s gives comfortable margin above normal
pagination time for a multi-page A4 document while not leaving the user staring at the
loading spinner indefinitely if something silently failed. **Flagging as an open item**: this
number should be confirmed/tuned during Wave 0 manual UAT (per RESEARCH.md's Wave 0 gaps),
not treated as final.

## Dark-Theme Rendering (D-08 mechanics)

| Element | Light | Dark | Notes |
|---------|-------|------|-------|
| Backdrop | `#e4e8f0` (`--tr-surface-sunken`) | `#0a0d12` (`--tr-surface-sunken`) | Theme-scoped token, resolves automatically via existing `[data-theme]` CSS cascade on the **parent** document. |
| Sheet | `#ffffff` always | `#ffffff` always | Never theme-scoped — hardcode `--tr-n-0` (theme-invariant token) or literal `#fff`, do NOT use `--tr-surface` (which DOES flip to dark). This is the exact bug being fixed (`PdfPreviewModal.svelte:325` currently uses `--tr-surface`). |
| Sheet shadow | `--tr-elev-2` light values | `--tr-elev-2` dark values | See Color section's dark-theme risk note above. |
| Page counter / hint text | `--tr-text-secondary` / `--tr-text-tertiary` | same tokens, auto-resolve | Theme-scoped tokens, no manual handling needed. |

**Mechanics for propagating the backdrop color INTO the opaque-origin `srcdoc` iframe
(Claude's Discretion, D-08):** per RESEARCH.md's Anti-Patterns section, do NOT reassign
`iframe.srcdoc` on theme toggle (destroys in-progress/completed Paged.js pagination state,
forces a full reflow — Pitfall 5). Instead:

1. On initial `srcdoc` construction, read the CURRENT resolved theme
   (`document.documentElement.dataset.theme`, per `ui/src/lib/stores/theme.svelte.ts`'s
   existing resolution mechanism) and inline the matching backdrop color as a literal hex
   value into the bootstrap `<style>` block baked into `srcdoc` (e.g.
   `body { background: #e4e8f0 }` for light, `#0a0d12` for dark) — NOT a CSS custom property
   reference, since the iframe's opaque-origin document does not inherit the parent's
   `:root` custom properties at all.
2. If the user toggles the app theme while the preview modal is open (edge case, low
   frequency but must not break), send a live `postMessage` from parent → iframe with the
   new backdrop hex (`{ type: 'trackly-theme-update', backdrop: '#0a0d12' }`), and have the
   bootstrap script's message listener update `document.body.style.background` in place. This
   requires `targetOrigin: '*'` on the parent→iframe send (the iframe has no addressable
   origin, per RESEARCH.md Pattern 2) — acceptable since the payload is a non-secret CSS
   color string, not user data.
3. Do NOT attempt to make the iframe "follow" the parent's theme via any CSS mechanism (no
   such mechanism exists across an opaque-origin boundary) — the `postMessage` bridge is the
   only channel, confirmed by RESEARCH.md's C-01 constraint.

## Accessibility

Aligning with Phase 30's established a11y conventions (AA-contrast, focus-ring patterns) and
the project's existing `aria-live="polite"` idiom (`CartridgeDetail.svelte`, `ActDetail.svelte`,
`ToastHost.svelte`, etc.).

| Concern | Treatment |
|---------|-----------|
| **Loading/progress announcement** | The `.state.state-loading` container keeps/gains `aria-live="polite"` (matches the project's existing `detail-loading` idiom exactly — same pattern, same politeness level). Screen readers will announce "Готовим документ… Страница 3…" as the text updates — acceptable verbosity for a bounded, short-lived state (contrast with `aria-live="assertive"`, which is reserved for errors per `Toast.svelte`'s `roleMap`). Do not add a *second* separate `aria-live` region for progress-only — one region covering both lines is sufficient and avoids double-announcement noise. |
| **iframe accessible name** | Existing `title="Document Preview"` attribute on `<iframe>` is stale English copy left over from Phase 16 — **update to Russian**: `title="Предпросмотр документа"` (this app is RU-only per `CLAUDE.md` constraint "UI и шаблоны документов — только русский в v1"; leaving an English-only accessible name on a screen-reader-exposed attribute is a defect, not a stylistic choice). |
| **Focus order / Tab trap** | `Modal.svelte`'s `TRAP_FOCUSABLE_PARTS` already includes `'iframe'` (confirmed, line 36) — the `sandbox` attribute change (`""` → `"allow-scripts"`) does not affect this; Tab order remains: close (×) → iframe (if focusable content inside — opaque-origin iframes with `allow-scripts` but no `allow-same-origin` are still individually Tab-stoppable as a single unit, same as before) → footer meta block (NOT focusable, plain text — do not add `tabindex` to the page-counter/hint-line block) → "Закрыть" → "Печать". No change needed to `Modal.svelte` itself (consistent with D-12's lock). |
| **Scroll/keyboard over multi-page backdrop** | The `.pdf-page-frame` container keeps `overflow: auto` (existing) — vertical scroll through the sheet stack is native browser scroll, reachable via standard keyboard scroll (Space/PageDown/arrow keys) once the frame or its scrollable ancestor has focus. No custom keyboard handler is needed or should be added — this is a plain scrollable region, not a custom widget requiring roving tabindex or arrow-key paging. |
| **Reduced motion** | Already covered globally (`global.scss:47`, `prefers-reduced-motion: reduce` zeroes all animation/transition durations app-wide) — the `Spinner` component's `spin` keyframe and any state-swap are automatically covered; no phase-specific override needed. |
| **Color contrast (new text)** | Page-counter (`--tr-text-secondary` on `--tr-surface`, footer background) and hint-line (`--tr-text-tertiary` on same) reuse existing token pairs already validated by Phase 30's `check-contrast.mjs` gate — no new pairing introduced, so no new contrast risk. Verify via `pnpm --dir ui lint` (runs the existing contrast check) as part of this phase's own verification, not a new manual check. |

## Responsive Behavior

D-12 locks `.modal-pdf-preview` at `min(95vw, 1100px) × min(90vh, 920px)` — this spec does
not change modal sizing, only how content behaves inside that fixed envelope, per D-11
(fit-to-width scale, capped at 100%, no horizontal scroll ever).

| Viewport | Behavior |
|----------|----------|
| Wide desktop (modal reaches its 1100px cap) | Sheet renders near/at natural size (794px page width fits comfortably inside the ~1050px inner frame width after `--tr-space-md` padding) — scale factor ≈ 1 (capped, per D-11), no visible shrinkage. |
| Narrow desktop / laptop (modal at 95vw, e.g. 1024px-wide window) | Scale factor slightly `<1` — sheet shrinks to fit frame width, vertical scroll through the (now-shorter, scaled) page stack as before. |
| LAN browser on a narrow laptop/tablet (explicit focus area per orchestrator prompt) | Same `transform: scale()` mechanism applies — this is viewport-agnostic (D-11's scale calculation is `min(1, frameWidth / naturalPageWidthPx)`, per RESEARCH.md Pattern 3), so tablet-width windows get a smaller scale factor automatically. **No breakpoint-specific CSS needed** — the scale is computed at runtime from measured frame width, not from a media query. Footer meta block (page counter + hint) wraps its text at narrow widths (per the `min-width: 0` flex rule specified above) rather than truncating or overflowing — verify no clipping down to the practical minimum modal width implied by `95vw` on small tablet viewports (~768px range). |
| Vertical space | The fixed `90vh` height means the sheet-stack scroll region shrinks proportionally on short viewports (e.g. laptop with browser chrome eating vertical space) — this is existing, accepted `.pdf-page-frame { overflow: auto }` behavior, unchanged by this phase. |

**No new horizontal scroll under any circumstance** — D-11 is explicit and absolute on this
point; if the scale calculation ever produces `frameWidth < naturalPageWidthPx * 1`, the
scale factor must clamp down, never let the sheet overflow its frame horizontally.
