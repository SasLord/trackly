<objective>
Реализовать управление жизненным циклом заявки (GAP-12-07, A4) — самый крупный пункт Round 2: (1) разрешить отклонение заявки из статуса «В работе» (не только «Новая»); (2) добавить удаление заявок для Admin/Manager в ЛЮБОМ статусе (soft-delete, по аналогии с `CartridgeService::delete()`); (3) добавить отмену СОБСТВЕННОЙ заявки для Employee, только пока статус «Новая» (новый отдельный переход, отдельная авторизация — НЕ через общий `transition()`, который закрыт для Employee).

Это backend-план (домен + сервис + dual-transport эндпоинты + RBAC-тесты). UI-кнопки и confirmation-модалки — отдельный план 12-15 (зависит от этого плана).

Purpose: специалисты и администраторы получают полный контроль над жизненным циклом заявок без обращения к БД напрямую; сотрудники могут исправить ошибочно созданную заявку без вмешательства администратора.
Output: расширенный `RequestTransitionOp` (Reject из двух статусов + новый Cancel), новые сервисные методы `delete()`/`cancel()`, новые dual-transport эндпоинты `requests_delete`/`requests_cancel`, новые RBAC regression-тесты.
