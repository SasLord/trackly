<interfaces>
SQLite не поддерживает `ALTER TABLE ... DROP CONSTRAINT`. Единственный способ снять CHECK — пересобрать таблицу:
1. `CREATE TABLE printers_new (...)` — идентичная DDL из V020, БЕЗ строки `CHECK (ip_address IS NOT NULL OR usb_host_device_id IS NOT NULL)`.
2. `INSERT INTO printers_new SELECT * FROM printers;` — копия всех строк и колонок 1:1.
3. `DROP TABLE printers;`
4. `ALTER TABLE printers_new RENAME TO printers;`

`printer_readings.printer_id` и `printer_alerts.printer_id` ссылаются на `printers(id)` через `REFERENCES printers(id) ON DELETE CASCADE`. SQLite резолвит FK по имени таблицы+колонки в момент INSERT/UPDATE (не по rowid), поэтому переименование `printers_new` → `printers` восстанавливает FK-целостность без изменений в `printer_readings`/`printer_alerts`. НО: рефinery выполняет файл миграции в одной транзакции с `PRAGMA foreign_keys=ON` (включено на уровне соединения по конвенции проекта — CLAUDE.md), и SQLite по умолчанию проверяет FK сразу (immediate, не deferred) — `DROP TABLE printers` при включённых foreign_keys и существующих ссылающихся строках может быть заблокирован. Поэтому миграция должна обернуть реконструкцию в `PRAGMA foreign_keys=OFF;` ... `PRAGMA foreign_keys=ON;` явно внутри файла (нет ни одного существующего прецедента в migrations/, действовать по этой явной инструкции, не искать аналог).

`printer_cartridge_models` (V029) ссылается на `devices(id)`, НЕ на `printers(id)` — не затрагивается этой миграцией.
</interfaces>
