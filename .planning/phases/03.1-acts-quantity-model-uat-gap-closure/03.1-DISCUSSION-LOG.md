### Area 1: G-12 — Quantity model for devices in acts (ARCHITECTURAL)

**Question presented:** Как моделировать quantity для устройств в актах? (это основной ADR)

**Options:**
- **C — гибрид devices.is_unique flag (Recommended)** — `devices.is_unique` BOOL; unique=1 → qty всегда 1; unique=0 → qty>1 разрешён, но condition/location едины per item.
- **A — devices.quantity column** — самое устройство как агрегат; per-unit tracking невозможен.
- **B — clone-on-handover (N rows)** — handover qty=3 создаёт 3 independent device rows; per-unit tracking идеален; для расходников может размножать rows.

**User selected:** **B — clone-on-handover (N rows)**

**Rationale (inferred):** User приоритезировал точный per-unit tracking (даже для расходников) над простотой агрегации. Это совпадает с pre-discussion preference на «возврат через выбор конкретных устройств, а не quantity counting».

**Locked decisions:**
- При handover qty>1 backend клонирует device rows внутри той же writer-tx.
- `act_items.quantity` остаётся denormalized; canonical source — `count(distinct device_id)` per item.
- Migration V015 — data migration для существующих acts с qty>1 (clone retrospectively).
- ReturnModal: выбор конкретных device_id (чекбоксы), не quantity.
- `recompute_parent_archived` пересчитывается на count distinct.
- Display rule (G-7) автоматически работает на новой модели (partial = returned_count < handover_count).
