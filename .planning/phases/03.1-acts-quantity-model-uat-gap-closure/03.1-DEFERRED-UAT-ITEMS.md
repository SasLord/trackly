## DEF-1: Autocomplete on focus — все поля с autocomplete

**Текущее поведение:** `LocationAutocomplete` (новый) открывает dropdown
сразу на focus (даже empty prefix → top 20). `PersonAutocomplete` (giver/receiver)
и `DeviceAutocompleteField` (device picker в ActFormItemsTable) — НЕТ:
требуют ≥1 символа ввода.

**Желаемое:** одинаковое поведение во ВСЕХ autocomplete полях. Фокус → сразу
показать первые 20 suggestions с current value (или empty prefix).

**Скоуп:**
- `ui/src/lib/components/PersonAutocomplete.svelte` — добавить `handleFocus`
  + scheduleFetch на onfocus.
- `ui/src/features/devices/DeviceAutocompleteField.svelte` — то же самое.
- Backend `acts.suggestPerson` уже поддерживает empty prefix (frequency DESC).
- Backend `devices.search`/`listGrouped` могут требовать non-empty prefix —
  проверить и снять restriction если есть.

**Estimated effort:** ~15-20 мин.

## DEF-2: Device picker — индивидуальные devices в группе с разным condition

**Часть A (small): Dedupe уже-добавленных devices в dropdown.**
Текущее: в ActFormItemsTable можно добавить ту же группу в две строки.
Backend validate_create отлавливает (HashSet dedup), но UI должен скрывать.

- Filter: в `pickGroup` + suggestions list исключать `group.repr.id`/`group.ids`
  уже выбранные в других items.
- ~10 мин.

**Часть B (architectural): Выбор конкретного device при различающихся condition.**

Сценарий: 2 устройства «DVD-ROM ASUS» в группе. Одно ранее выдавалось,
вернулось с condition='Хорошее'. Второе — condition='Новое'. UI showing
«DVD-ROM ASUS ×2» как ОДНУ группу не позволяет различить.

При создании нового handover клоны inherit `state` (= condition) source
device. Если pickGroup выбирает первое устройство группы как `repr`,
то новый акт получит condition того представителя — не выбора.

**Варианты решения:**

**Вариант 1 (UI expansion):** При клике на групповой entry — раскрывать
список индивидуальных devices в группе (показывать `condition` каждого).
User выбирает конкретно. Стоит в payload: device_ids = выбранные user-ом.
Семантически чисто, но dropdown UX усложняется.

**Вариант 2 (sub-grouping по condition):** В `DeviceGroup` группировать
по `(name, model, condition)` вместо `(name, model)`. Тогда «DVD-ROM ASUS,
Хорошее ×1» и «DVD-ROM ASUS, Новое ×1» — две отдельные группы. Проще
UX, но `condition` приходится включать в group key — изменения в
`SqliteDeviceRepository::list_grouped` SQL.

**Рекомендация:** Вариант 2 как initial fix (минимальный UX impact),
Вариант 1 как future enhancement если кейс «mixed pick» появится.

**Estimated effort:** Вариант 2 — ~45 мин (SQL group key + UI tooltip
показывает condition). Тесты для list_grouped с new key.

## DEF-3: Devices table показывает Расположение из активного handover

**Текущее:** Таблица «Устройства» отображает `devices.location_id`.
Когда устройство выдано через handover-акт с `location_id=X`, поле
`devices.location_id` НЕ обновляется → table показывает старое
(pre-handover) расположение, не место текущей выдачи.

**Желаемое:** Для устройств с `status='в_работе'` отображать
`location` активного handover-акта.

**Архитектурный выбор:**

**Вариант A (update on handover):** ActService::create UPDATE-ит
`devices.location_id` при handover для каждого device_id (тот же UPDATE
что меняет status). На return — UPDATE обратно (resolved location или
NULL). Простой data flow, devices table «just works».
- **Минус:** требует careful tracking pre-handover location, чтобы
  return мог восстановить (если location_id_override=null → куда?).
  Сейчас `do_return` пишет resolved_location в `devices.location_id` —
  значит этот путь уже частично существует.

**Вариант B (derive on read):** Devices.list/get JOIN с активным
handover-актом и для status='в_работе' replaces location_id из акта.
- **Плюс:** acts остаются source of truth.
- **Минус:** complicated SELECT (find active handover per device:
  WHERE deleted_at_utc IS NULL AND archived=0 AND any act_item with
  this device_id). N+1 query risk если делать в Rust loop.

**Рекомендация:** Вариант A — apparently уже implemented partially
(do_return пишет в devices.location_id). Проверить и убедиться, что
handover UPDATE тоже пишет туда. Скорее всего просто missing
`location_id: payload.location_id (resolved!)` UPDATE в ActService::create
inner loop.

**Estimated effort:** ~30 мин если Вариант A; ~45 мин если Вариант B
(SQL + N+1 prevention).
