# Phase 03.1: Code Review Report

**Reviewed:** 2026-05-31

## Summary

Phase 03.1 — это вертикальный слайс из 13 cross-cutting gap-фиксов плюс
крупный архитектурный сдвиг G-12 (clone-on-handover quantity model). Код
тщательно прокомментирован, тесты покрывают как новый G-12 контракт
(`acts_clone_handover.rs`), так и legacy-fallback path (`acts_returns.rs`),
LIKE-injection защита (`acts_suggest.rs`), и B-3 byte-identity invariant
(`pdf_column_overflow.rs`).

Однако adversarial review нашёл **4 BLOCKER** уровня (миграционный
data-loss, отсутствие `shell:` scope в Tauri capability, тонкий конфликт
recompute_parent_archived/legacy returns и timezone-несовпадение между
двумя датапикерами), плюс 11 предупреждений по корректности UX/SQL/edge
cases. До отгрузки V015 в прод эти 4 BLOCKER должны быть закрыты.

## Critical Issues

### CR-01: V015 migration breaks already-archived pre-V015 acts

**File:** `migrations/V015__acts_clone_on_handover.sql:60-120`
**Issue:** Миграция размножает `act_items` оригинала с `quantity>1` в N
строк (квоты клонов), но **НЕ обновляет существующие return-`act_items`**.
Сценарий регрессии:
1. Pre-V015: handover act_item с `quantity=3, device_id=X`. К нему был
   создан return act с `act_items(device_id=X, quantity=3)` →
   `recompute_parent_archived` (pre-V015 формула на основе SUM(quantity))
   архивировал parent.
2. V015 применяется → handover теперь имеет 3 act_items (`device_id=X`,
   `device_id=Y_clone`, `device_id=Z_clone`).
3. Любой следующий вызов `recompute_parent_archived` (post-V015 формула —
   `COUNT(*) FROM act_items` vs `COUNT(DISTINCT device_id)` из returns)
   видит: handover_total=3, returned_total=1 (только `X`). Parent
   **un-archived** автоматически на ближайшем return undo /
   create-cascade.
4. UAT-claim «forward-only, no-op when no qty>1» неверен для базы
   _с архивированными актами и quantity>1_.

**Fix:** Расширить V015 — после клонирования handover act_items нужно
также «развернуть» каждую return-acts строку `WHERE device_id=X AND
quantity>1` в N строк, распределив возвращённые экземпляры по клон-IDs
(в порядке появления). Альтернатива: пересчитать `archived` по новой
формуле и временно использовать `SUM(quantity)` в `recompute_parent_archived`
как fallback для return-актов созданных pre-V015 (маркировать в audit_log).

```sql
-- Pseudocode: после блока 4d добавить data-migration для returns:
INSERT INTO act_items (act_id, device_id, quantity, ...)
SELECT ra_id, clone_dev_id, 1, ...
FROM (recursive enumeration of return rows where quantity > 1
      paired 1:1 with handover clone_ids in stable seq order);

UPDATE act_items SET quantity = 1
  WHERE act_id IN (SELECT id FROM acts WHERE act_type='return')
    AND quantity > 1;
```

### CR-02: `shell:allow-open` granted без scope — universal open vulnerability

**File:** `crates/trackly-app/capabilities/main.json:9`
**Issue:** Capability `"shell:allow-open"` объявлен без `allow`-блока —
то есть **любая** строка из frontend может быть передана в
`tauri-plugin-shell::open`. В коде `PdfPreviewModal.handleOpen` уже
строится путь конкатенацией `${tmp}${filename}` (line 209), где
`filename` форматный (`trackly-preview-${Date.now()}.pdf`) — здесь
безопасно, но **любая** другая часть frontend (или скомпрометированный
XSS-вектор через MiniJinja safe-mode bypass / future server-mode browser
input) может позвать `openShell('https://attacker.com')`, `openShell('cmd.exe')`,
`openShell('file:///etc/passwd')` и т. д.

CONTEXT.md G-8b явно говорит: «capability `shell:allow-open` ограниченным
на `.pdf` файлы в temp dir (security)». Этот scope не реализован.

**Fix:** Добавить URL-scope с regex (Tauri 2 поддерживает `urls` массив с
паттернами):
```json
{
  "identifier": "shell:allow-open",
  "allow": [
    { "name": "open-pdf-temp", "cmd": { "program": "", "args": [] }, "url": "$TEMP/**/*.pdf" }
  ]
}
```
Точная JSON-схема — см. `tauri-plugin-shell` capability docs (v2). На
крайний случай — обёртка в Rust-команду, валидирующая путь по `canonicalize +
starts_with(temp_dir)` перед делегированием в `shell::open`.

### CR-03: `do_return` quantity-bound check ломает partial-return для
legacy (pre-V015) handovers со взятым qty>1

**File:** `crates/trackly-app/src/services/act_service.rs:675-704`
**Issue:** Когда клиент шлёт legacy-payload (`device_ids: []`, `quantity: N`)
для возврата по handover-акту, который был СОЗДАН ДО V015 (когда
ActService::create клонирования не делал — qty>1 жил в одной act_item с
denormed quantity), backend гарантирует `SUM(quantity)`-based bound.
Однако:
- При **частичном возврате** (например, `quantity=2` из 5): первая
  попытка проходит (2+0 ≤ 5), создаёт return-act с `act_items(quantity=2)`.
- Вторая попытка (`quantity=2`) теперь читает `already_returned = SUM(quantity)=2`
  и `handover_qty=5` → 2+2 ≤ 5 — пропускает. Но при этом **status guard**
  (`before.status_id != in_work_status_id`) срабатывает на устройстве,
  которое уже было переведено в «на_складе» первым возвратом → **Conflict
  «уже не в работе»**. Партиальный возврат на legacy-данных невозможен.

В новой G-12 модели проблема не воспроизводится (1 device_id ↔ 1 act_item ↔
status guard корректно различает clones), но **legacy fallback path
существует для backward-compat** (см. doc-comment dto/act.rs:135-141 и
acts_returns.rs Test 12 `return_quantity_exceeds_handover_rejected`).
Таким образом legacy fallback _неработоспособен для partial returns_ —
только full-quantity returns на единственный device пропустят. Это
противоречит обещанию backward-compat.

**Fix:** Либо
- (а) Документировать, что legacy fallback поддерживает только
  full-quantity return (one-shot), и enforce этого: если
  `device_ids.is_empty()`, требовать `quantity == handover_qty -
  already_returned`, иначе вернуть `Validation`.
- (б) В legacy mode при partial return клонировать devices on-the-fly
  во время do_return (зеркало handover clone logic): создать N-1 клонов
  device-row, обновить act_item.quantity=1, и записать N return act_items.
  Сложнее, но честнее.
- (в) Полностью удалить legacy fallback и потребовать UI миграцию.

### CR-04: V015 step 4c полагается на `MAX(id)+seq` ≠ AUTOINCREMENT row id

**File:** `migrations/V015__acts_clone_on_handover.sql:86-120`
**Issue:** Шаг 4b пишет `id_floor = COALESCE(MAX(id), 0) FROM devices`.
Шаг 4d затем считает что новые devices, вставленные в порядке `tc.seq`,
получают `id = id_floor + tc.seq`.

Это **верно ТОЛЬКО для INTEGER PRIMARY KEY БЕЗ AUTOINCREMENT** (где id =
MAX(id)+1 reuses gaps), но **неверно для AUTOINCREMENT** колонки. SQLite
AUTOINCREMENT использует `sqlite_sequence.seq` (max-ever-assigned), а не
`MAX(id)`. После операций «вставить devices до id=100 → удалить id=100 →
запустить V015» получим:
- `id_floor = MAX(id) = 99`.
- Новый insert получит `id = sqlite_sequence(devices).seq + 1 = 101`,
  а не 100.
- Act_items insert использует `device_id = id_floor + seq = 99 + 1 = 100`,
  ссылаясь на **несуществующее** устройство (id=100 удалено).

Если `devices.id` объявлен как `INTEGER PRIMARY KEY` без AUTOINCREMENT —
проблема меньше, но всё равно проявляется при concurrent miss и
deleted-row reuse. Эту инвариантность нужно либо доказать (читая
`migrations/V001__schema.sql` на тип `devices.id`), либо переписать на
гарантированный паттерн.

**Fix:** Заменить шаг 4c+4d на per-row insert внутри recursive trigger /
курсор-эмуляции, либо использовать `RETURNING id` (SQLite 3.35+):
```sql
-- Modern path: SQLite 3.35+ RETURNING
INSERT INTO devices (...) SELECT ... RETURNING id INTO ...;
```
Альтернативно — проверить декларацию `devices.id`: если это
`INTEGER PRIMARY KEY` без AUTOINCREMENT и без soft-delete-induced gaps,
явно задокументировать инвариант в комментариях миграции и добавить
sanity assertion (`SELECT COUNT(*) FROM act_items WHERE device_id NOT IN
(SELECT id FROM devices)` после миграции — должно быть 0, иначе rollback).

## Warnings

### WR-01: Modal backdrop-mouseup state never resets on drag-out

**File:** `ui/src/lib/components/Modal.svelte:27-36`
**Issue:** `handleBackdropMouseup` сбрасывает `mouseDownOnBackdrop = false`
только если mouseup произошёл на backdrop. Если пользователь mousedown'ит
на backdrop и mouseup'ит **за пределами окна** (drag out of viewport),
флаг остаётся `true`. Следующий просто-click anywhere по backdrop вызовет
закрытие модала (потому что mouseup-обработчик увидит уже-true флаг).
Edge case, но реальный.

**Fix:** Слушать `mouseup` на `document` или `window` вместо backdrop:
```svelte
$effect(() => {
  if (!open) return;
  const onUp = () => { mouseDownOnBackdrop = false; };
  document.addEventListener('mouseup', onUp, true);
  return () => document.removeEventListener('mouseup', onUp, true);
});
```

### WR-02: `ActFormBody.isoToUnix` использует UTC midnight, DocumentAcceptanceModal — MSK midnight

**File:** `ui/src/features/acts/ActFormBody.svelte:72-76`
+ `ui/src/features/acts/DocumentAcceptanceModal.svelte:56-60`
**Issue:** Два DatePicker-конвертера живут отдельно:
- `ActFormBody.isoToUnix(iso)` = `Date.parse(iso + 'T00:00:00Z') / 1000` —
  даёт UTC-полночь выбранного календарного дня.
- `DocumentAcceptanceModal.dateLocalToUtcSeconds(iso)` — даёт «MSK-полночь»
  (UTC midnight − 3h), с подробным комментарием почему нужно вычитать.

Backend `format_ru_date` использует
`time::OffsetDateTime::from_unix_timestamp` (UTC). Для даты, переданной
из ActFormModal как UTC-midnight, день рендера в RU = тот же календарный
день UTC. Для пользователя в МСК (UTC+3) выбранный день _визуально_ —
тот же. **ОК** для format_ru_date.

НО: если пользователь работает в timezone, отличной от MSK (например,
поехал в командировку UTC+5 — Калининград наоборот UTC+2), ISO-значение
`<input type="date">` отдаёт строку локального дня браузера. Backend
получит unix-seconds = «локальная полночь как UTC». При timezone shift
календарный день и день рендера в PDF могут разойтись на ±1 сутки.

DocumentAcceptanceModal **знает** про MSK-special-case и вычитает 3h,
ActFormBody — нет. Inconsistency между двумя датапикерами на одном экране
— симптом, что есть ещё не пойманный bug в MSK-only deployment'е сегодня.

**Fix:** Вынести в `ui/src/lib/utils/date.ts` единственную функцию
`localIsoToMskSeconds(iso)`, использовать в обоих местах. Дополнительно
для Phase 5+ (multi-tz) — рассмотреть отказ от `<input type="date">` в
пользу tz-aware решения.

### WR-05: `recompute_parent_archived` инкрементит version даже когда archived не менялся

**File:** `crates/trackly-infra/src/repos/acts_sqlite.rs:438-475`
**Issue:** Doc-комментарий: «Идемпотентно: если значение не изменилось,
`version` всё равно инкрементируется». Это **намеренный** выбор, но он
ломает optimistic-lock contract для UI:
- Frontend читает act → version=5, archived=false.
- Backend получает return для другой позиции → recompute видит no-op
  (archived=false → false), но всё равно `UPDATE ... version=version+1`.
- Frontend пытается update notes → шлёт version=5 → backend выдаёт
  `OptimisticLockMismatch` (actual=6).

UAT может пожаловаться на «случайные» 409 при безобидных операциях.

**Fix:** Сделать UPDATE условным:
```sql
UPDATE acts SET archived = ?1, updated_at_utc = ?2, version = version + 1
 WHERE id = ?3 AND archived != ?1;
```
Если row не affected — версия не меняется, дисплей пересчитывается из
других сигналов. Если действительно нужна аудит-видимость, оставить
явную audit_log-запись `action='custom:recompute_no_change'`.

### WR-06: `PdfPreviewModal` — `pdfBytes` всегда `null`, save всегда re-render'ит

**File:** `ui/src/features/acts/PdfPreviewModal.svelte:120-169` +
`171-193`
**Issue:** В `$effect` блоке (line 137-160) PDF bytes
**не сохраняются** в `pdfBytes` state — только blob URL. Комментарий
(line 145-149) явно говорит «Stash bytes for save/open without
re-rendering» / «For now, attach» — но attach так и не сделан.
Результат:
- `handleSave` → `pdfBytes ?? (await renderCall())` — всегда вызывает
  renderCall, заново генерирует PDF.
- `handleOpen` — то же самое.

Не баг по корректности, но waste из ~500ms генерации каждого вызова +
лишняя нагрузка на minijinja+krilla.

**Fix:** В `$effect` после `fetchPdfBlob` сохранить bytes:
```ts
const result = await fetchPdfBlob(renderCall());
// fetchPdfBlob нужно расширить — вернуть и URL и bytes.
pdfBytes = result.bytes;
blobUrl = result.url;
```

### WR-07: `truncate_to_width` неточен — B-3 invariant хрупок для Cyrillic

**File:** `crates/trackly-app/src/pdf/renderer.rs:341-357`
**Issue:** Approximation `avg_glyph_w = 0.5 * font_size` справедлива для
DejaVu Sans на латинице, но для кириллицы средняя ширина глифа ближе к
0.55-0.6 \* font_size (capital Cyrillic letters заметно шире). Это:
- Делает B-3 byte-identity invariant хрупким: cell-text «Иванов И.И.»
  (12 символов × 5pt = 60pt оценка) может рассчитываться как _подходящий_
  в 56pt колонку, но физически overlap'ить соседа.
- Тест `truncate_to_width_adds_ellipsis_for_long_text` использует только
  `'X'` (латиница) — pure latinic approximation.

В рамках Phase 3.1 word-wrap отложен (CONTEXT G-8a), но ellipsis-truncation
для CYR должен быть более conservative.

**Fix:** Поднять estimate до 0.55:
```rust
let avg_glyph_w = 0.55 * font_size;  // empirical for mixed RU/EN content
```
Альтернативно — использовать `krilla::Font::measure` если API доступен,
для точного measure. Добавить тест на CYR-overflow в pdf_column_overflow.rs.

### WR-08: `populate_outstanding_device_ids` — outstanding не учитывает clones, появившиеся ПОСЛЕ создания return

**File:** `crates/trackly-app/src/services/act_service.rs:1585-1612`
**Issue:** SQL EXCEPT работает на `act_items WHERE act_id = parent` минус
`act_items` returns. В G-12 модели каждый clone это 1 act_item с
собственным `device_id`. Если **между** созданием return-акта (которое
soft-delete'ит returned device's act_item snapshot) и follow-up `acts.get`
кто-то добавит новые act_items в parent (теоретически невозможно — handover
locked), картинка корректна.

НО: если `delete_soft` для return-акта _не_ удаляет return's `act_items`
строки физически (а из код `soft_delete_in_tx:359` явно `DELETE FROM
act_items WHERE act_id = ?1`), то после soft-delete return-акта его строки
исчезают физически — EXCEPT правильно возвращает outstanding=полный
набор. Тест `undo_return_restores_archived_to_false` это и проверяет.

Тем не менее: docstring говорит «soft-delete filter применяется ТОЛЬКО
на acts через JOIN», что неверно — после soft-delete return-акта его
act_items физически удалены, а EXCEPT-подзапрос всё ещё имеет JOIN с
`acts ra ON ra.id = rai.act_id WHERE ra.deleted_at_utc IS NULL`. Это
правильно но избыточно. Documentation drift.

**Fix:** Уточнить docstring: «`act_items` для soft-deleted return-актов
**удаляются физически** в `soft_delete_in_tx`, поэтому JOIN с `acts.deleted_at_utc`
работает как **belt-and-braces**.» Дополнительно — добавить тест:
«populate_outstanding после повторного soft-delete + re-return сохраняет
консистентность».

### WR-09: `ReturnModal.handleSubmit` — toast suffix logic небезопасен для Cyrillic

**File:** `ui/src/features/acts/ReturnModal.svelte:122-124`
**Issue:**
```ts
const suffix = ret.number.replace(/^\d+/, ''); // «в» / «в1»
pushToast('success', `Создан акт возврата №${ret.number_raw}${suffix}. ...`);
```
Если `ret.number = "42в"`, suffix = `"в"`. Toast: `"Создан акт возврата
№42в. ..."`. OK.

Но если будущий формат сменит prefix-pattern (например, на UUID или
другой language), regex `/^\d+/` сломается тихо: suffix = весь
`ret.number`, в результате toast: `"Создан акт возврата №42<полный
display>. ..."`. Регресс fragile.

Дополнительно: `ret.number_raw` — это raw counter, для return это
`number` (которое = parent.number в текущей реализации `do_return`).
Toast выглядит правильно, но если `format_act_number` контракт изменится,
toast станет misleading.

**Fix:** Использовать `ret.number` целиком вместо `ret.number_raw + suffix`:
```ts
pushToast('success', `Создан акт возврата №${ret.number}. ...`);
```

### WR-10: `MAX_CLONE_QTY=1000` UI не отражает остаток на складе для serialised devices

**File:** `ui/src/features/acts/ActFormItemsTable.svelte:32-122`
**Issue:** При выборе устройства с `serial_no`, UI клампит qty=1

### WR-11: `handleQtyInput` UI игнорирует `Infinity` / `NaN` корректно, но позволяет 0 ⇒ 1 silently

**File:** `ui/src/features/acts/ActFormItemsTable.svelte:115-124`
**Issue:** `qty = parseInt(v); finite && >0 ? parsed : 1` — если
пользователь ввёл `0`, qty silently превращается в 1 без UX feedback.
Может вызвать confusion («я ввёл 0 — почему backend пишет 1?»).

бы вернул Validation. UI clamp скрывает ошибку.

- (б) оставить введённое значение в state, дать backend rejected с
