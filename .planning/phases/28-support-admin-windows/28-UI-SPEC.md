> Визуальный и интеракционный контракт четырёх окон поддержки и администрирования (Заявки,
> Отчёты, Настройки, Пользователи). Составлен gsd-ui-researcher, проверяется gsd-ui-checker.

> **Макета нет** (как в Фазе 27) — токены/примитивы уже мигрированы глобально Фазой 23 (0

## 1. Характер фазы

Токенов/hex в четырёх целевых окнах — **ноль** (скаут Фазы 28, подтверждено 28-CONTEXT.md). Это
не миграция значений, а **адаптация общих примитивов и консистентность** поверх уже-токенизированной
поверхности. Формула, унаследованная от Фазы 27: **форма из системы, содержание из приложения.**

Перенос из Фазы 27 (Заявки, Пользователи — D-01…D-05) и переносится 1:1, не переоткрывается здесь —
см. `28-CONTEXT.md` §Decisions и `27-PATTERNS.md` для точных сниппетов миграции (`Tabs`, `Table`/
`TableRow`, `DetailPanel`, поверхность `--tr-surface-raised`).

Ниже — то, чего у Фазы 27 не было: две серые зоны компонентных решений (§4 Tabs, §5 Table) и
исчерпывающий копирайт-контракт четырёх окон (§7).

## 2. Границы: что этот контракт НЕ покрывает

- Изменение полей/действий/workflow/API/бэкенда любого из четырёх окон — фаза чисто визуальная (SC #1–4).
- Область редактирования (`textarea`/код) и механика превью `TemplateEditor` — см. §6 (D-08).
- Мобильная адаптивность Заявок/Отчётов/Настроек/Пользователей — WIN-06…09 её не требуют (в отличие
  от WIN-12 для Дашборда/Устройств). Master-detail Заявок сохраняет текущий `<1100px` fallback.
- AA-контраст, focus-ring по новому дизайну, паритет Tauri vs LAN-браузер — QA-02/QA-03, Фаза 30.
- Логика отчётов/периодов, DB-backed seed/upgrade шаблонов актов — не трогается никак.

## 6. Component Contracts — разрешение серых зон

### 6.1 `Tabs` (D-06) — примитив уже покрывает всё нужное, расширение НЕ требуется

Проверено по `ui/src/lib/components/Tabs.svelte`: встроенный `count`-слот **уже** даёт accent-тон
активному счётчику (`.tab.active .tab-count { background: var(--tr-accent-soft); color:
var(--tr-accent-text) }`) и нейтральный тон неактивным. Это **дословно** совпадает с текущим
поведением `ReportSubNav` (`<Badge variant={active ? 'accent' : 'default'}>`). Вывод из
28-CONTEXT.md D-06 подтверждён кодом: **форкать/расширять `Tabs` не нужно** — принять примитив как
есть, `Badge` внутри табов больше не используется.

Сопоставление вариантов `Tabs` → потребитель:

| Потребитель | Файл | Вариант `Tabs` | count |
|---|---|---|---|
| Тип отчёта (Акты/Возвраты/В работе/На складе или Расход/Заправки/…) | `ReportSubNav.svelte` `report-nav` | `underline` | да (`statusCounts[key] ?? 0`) |
| Домен отчёта (Устройства/Картриджи) | `ReportSubNav.svelte` `domain-nav` | `segmented` | нет |
| Раздел настроек (7 штук) | `SettingsSubNav.svelte` | `underline` | нет |
| Режим периода (Месяц/Год/Диапазон) | `PeriodSelector.svelte` `period-buttons` | `segmented` | нет, но `disabled` при `isSnapshot` (уже поддержано пропом `Tab.disabled`) |
| Фильтр заявок (Все/Новые/…) | `RequestsSearchAndTabs.svelte` | `underline` | да (перенос D-05 из Фазы 27, механически) |

**Контракт, который не должен измениться:** debounce/переключение домена-типа-раздела-режима,
значения счётчиков, ARIA (`tablist`/`aria-selected` для `underline`, `role="group"` для
`segmented` — `Tabs` уже расставляет корректно по варианту).

### 6.2 `Table`/`TableRow` (D-07) — расширение примитива НЕ требуется; отдельная задача — разделитель-строка

`Table.svelte` уже принимает `columns: number` + `head: Snippet` + `children: Snippet` — оба слота
рендерят **произвольную** разметку, поэтому динамические колонки `ReportTable` (набор `Column[]`,
меняющийся по типу отчёта) ложатся на существующий API без правок: `head` рендерит `{#each columns
as col}<th>{col.label}</th>{/each}`, тело — `{#each columns as col}<td>{value}</td>{/each}` внутри
`<TableRow>`. Итоговой строки в текущем `ReportTable.svelte` нет (только заголовок + данные) — `footer`
слот `Table` не требуется в этой фазе; вводить его ради «на будущее» не нужно (SC #4 — не изобретать
функциональность).

**Настоящая серая зона, которую 28-CONTEXT.md не called по имени:** `ReportTable` вставляет
**статичные строки-разделители** по месяцу (temporal-отчёты) или локации (snapshot-отчёты) —
`{ type: 'separator'; label }`. Это **не** групповая строка `TableRow group` (там chevron +
сворачивание/счётчик — чужая семантика для статичного ярлыка).

**Решение (рекомендация исследователя, применить как контракт):** разделитель рендерится как
обычный `<tr>` **внутри** `Table`'s `children`-сниппета, рядом с обычными `<TableRow>`, **не через**
`TableRow group={true}`:

```svelte
{#each grouped as item}
  {#if 'type' in item && item.type === 'separator'}
    <tr class="report-separator" aria-hidden="true">
      <td colspan={columns.length}>{item.label}</td>
    </tr>
  {:else}
    <TableRow>...</TableRow>
  {/if}
{/each}
```

```scss
.report-separator td {
  padding: var(--tr-space-2xs) var(--tr-space-md);
  height: var(--row-height-dense);
  background: var(--tr-surface-sunken); // было --tr-surface-sunken уже — сверить дословно
  font-size: var(--tr-font-size-body);
  font-weight: var(--tr-font-weight-semibold);
  border-top: 1px solid var(--tr-border-strong);
  color: var(--tr-text-primary);
}
```

**Обоснование:** `group`-режим `TableRow` — контракт сворачивания с состоянием (`groupExpanded`,
`onToggleGroup`) и по семантике, и по коду; разделитель месяца/локации не сворачивается и не имеет
счётчика. Форсировать его в `group`-режим потребовало бы либо расширять `TableRow` необязательными
пропами ради одного нетипичного потребителя, либо городить фиктивный `onToggleGroup`. Голый `<tr>`
внутри `children`-сниппета — валидный HTML (`Table` уже допускает произвольное содержимое `tbody`
через `children`), не расширяет и не форкает `Table`/`TableRow`.

**Действие для планировщика:** сверить финальную колонку/строку разделителя пиксель-в-пиксель с
существующим `.month-separator` (уже приведён выше) — переносится **без изменения значений**, только
оборачивается в `Table`.

### 6.3 `TemplateEditor` (D-08) — граница подтверждена кодом

`TemplateEditor.svelte` уже использует `Modal` + `Button variant="destructive"` для «Сбросить до
умолчания» → confirm-модалка «Сбросить шаблон?» / «Отмена» / «Сбросить». Это established паттерн —
**не менять**, только подтвердить, что `Button`/`Modal`/область валидации-превью (`iframe
sandbox=""`) уже на примитивах (видно из грепа — да). Работа D-08 сводится к ре-токенизации
`Select`/`Input` вокруг (выбор `kind` шаблона, поле body) — **не** к области `textarea`/превью.

### 6.4 Перенос из Фазы 27 — не переоткрывается

`DetailPanel`/`DetailSection`/`DetailField` (D-01), поверхность `--tr-surface-raised` + `elev-1`
для master-detail (D-02), `Table`/`TableRow` для списков (D-03), ре-токенизация модалок (D-04) —
см. `27-PATTERNS.md` для точных сниппетов (копируются механически). Единственное новое здесь —
`UsersList`/`UserListRow` не имеют master-detail (окно проще — список+модалка), поэтому D-02 к
Пользователям **не применяется**; D-01/D-03 применяются только к Заявкам (детальная панель есть),
D-03 — к обоим (Заявки, Пользователи).

**`UsersList` — единственная структурная деталь, отсутствующая в Фазе 27:** текущее пустое
состояние — одна строка («Пользователи не найдены»), без раздельных heading/body. При переносе на
`Table` использовать **только `emptyTitle`** (дословный текст), `emptyBody` не задавать — введение
второй строки без прецедента было бы новым копирайтом, не предусмотренным SC #4.

### 7.5 Деструктивные действия — сводка (для чекера)

| Действие | Окно | UI-паттерн | Подтверждение |
|---|---|---|---|
| Отклонить заявку / восстановление | Заявки | `Modal` (динамический заголовок/тело/кнопка по контексту) | «Отклонить заявку?» / «Отклонить восстановление?» / «Отклонить и удалить пользователя?» → кнопки «Отмена» / «Отклонить» или «Удалить пользователя» (`variant="destructive"`) |
| Сбросить шаблон до умолчания | Настройки | `Modal` | «Сбросить шаблон?» → «Отмена» / «Сбросить» (`variant="destructive"`) |
| Удалить пользователя | Пользователи | inline-подтверждение в строке (не модалка) | «Удалить?» → «Да» (`--tr-danger`) / «Нет» |

Три разных механики подтверждения (модалка с контекстным текстом / модалка фиксированная / инлайн)
**сохраняются как есть** — это не несогласованность дизайн-системы, а разная тяжесть последствий
(отклонение заявки затрагивает данные заявителя и, в одном случае, аккаунт; сброс шаблона — файл;
удаление пользователя в списке — established паттерн, уже принятый в Фазах 26/27 для аналогичных списков).
Унификация механик подтверждения — **вне объёма** (D-04 запрещает менять поведение).
