## Phase Boundary

Фаза 28 переводит **четыре окна поддержки и администрирования** на дизайн-систему Фаз 23–25 и
оболочку Фазы 26, продолжая плейбук Фазы 27:

- **Заявки** (`ui/src/features/requests/`) — master-detail, список, деталь, форма-модалка.
  Требование **WIN-06**.
- **Отчёты** (`ui/src/features/reports/`) — суб-навигация (домен + тип), фильтры, выбор периода,
  таблица данных. Требование **WIN-07**.
- **Настройки** (`ui/src/features/settings/`) — суб-навигация (7 разделов) + панели: Сеть,
  Организация, Хранилище, Бэкапы, Порог остатка, Шаблоны (редактор), Active Directory.
  Требование **WIN-08**.
- **Пользователи** (`ui/src/features/users/`) — список, форма-модалка. Требование **WIN-09**.

**Ключевой факт из скаута (меняет характер фазы):** legacy-токенов
(`--space-/--radius-/--font-size-`) и захардкоженных hex во всех четырёх окнах — **ноль**.
Токены мигрированы глобально ещё Фазой 23. Поэтому Фаза 28 — это **не миграция токенов, а
адаптация общих примитивов и консистентность компонентов** поверх уже-токенизированной
поверхности. SC говорит «токены/**компоненты**» — здесь вес именно на компонентах.

**Отличие окон от Фазы 27:**
- **Заявки** структурно ИДЕНТИЧНЫ окнам Фазы 27 (master-detail + список + SearchAndTabs) →
  плейбук Фазы 27 применяется 1:1 (D-01…D-05 ниже, «Перенос из Фазы 27»).
- **Пользователи** — упрощённое окно (список + модалка, без detail/master-detail).
- **Отчёты** и **Настройки** вводят элементы, которых у Фазы 27 не было: внутриоконная
  суб-навигация, таблица отчётов с динамическими колонками, редактор шаблонов, выбор периода.
  Здесь — реальные серые зоны (D-06…D-08 ниже).

**В границах фазы:**
- Перевод четырёх окон на токены/примитивы **повсеместно** — без остатков bespoke-классов (SC #1–#4).
- Заявки: полный плейбук Фазы 27 (detail-примитивы, master-detail surface, список→Table,
  SearchAndTabs→Tabs, ре-токенизация внутренностей модалок) — закрывает регресс D-13 Фазы 26 ещё
  для одного окна.
- Пользователи: список→Table, форма-модалка→ре-токенизация.
- Отчёты/Настройки: суб-навигация→`Tabs`, таблица отчётов→`Table`, редактор шаблонов→строго
  визуально, панели настроек→ре-токенизация внутренностей.
- Обе темы (светлая и тёмная) — унаследовано от D-17 Фазы 26.

**Вне границ:**
- **Любое изменение полей, действий, workflow, бизнес-логики, API, бэкенда** — фаза чисто
  визуальная. Особенно строго — редактор шаблонов и его превью (D-08), логика отчётов/периодов.
- **Редизайн раскладок** (новая иерархия секций, перекомпоновка форм/панелей, смена master-detail
  на full-width) — сознательно не берётся.
- **Мобильная переработка этих окон** — не в объёме (WIN-06…09 про токены/компоненты, не про
  адаптивность; WIN-12 покрыл только Дашборд/Устройства). Master-detail Заявок сохраняет текущий
  `<1100px` fallback.
- **Окна Фазы 29** (Логин/Pending/Blocked/FirstRunWizard, EmployeeLayout).
- AA-контраст, focus ring по новому дизайну, паритет Tauri vs LAN-браузер — QA-02/QA-03, Фаза 30.

## Implementation Decisions

### Перенос из Фазы 27 (Заявки + Пользователи) — механически, не переобсуждалось

Эти решения зафиксированы Фазой 27 и применяются 1:1; переспрашивать не нужно.

- **D-01 (Заявки):** `RequestDetail.svelte` сейчас bespoke (НЕ использует примитивы). Перевести на
  уже существующие примитивы `DetailPanel`/`DetailSection`/`DetailField` (извлечены в D-01 Фазы 27).
  Структура и поля не меняются.
- **D-02 (Заявки):** `RequestsMasterDetail.svelte` сейчас master `--tr-surface` / detail `--tr-bg`
  (тот же принятый регресс D-13 Фазы 26). Обе панели → `--tr-surface-raised` + border +
  `box-shadow var(--tr-elev-1)` (как D-02 Фазы 27). **Проверить обе темы** (урок D-17). Grid 35/65
  сохраняется.
- **D-03 (Заявки + Пользователи):** списки не на `Table`. `RequestsList`/`RequestListRow`,
  `UsersList` (сырой `<table>`)/`UserListRow` → семантика `<table>` + примитивы `Table`/`TableRow`
  со своими колонками. **Осторожно:** `Table`/`TableRow` — общие компоненты (Устройства, витрина,
  `ActFormItemsTable`, окна Фазы 27) — не сломать существующих потребителей.
- **D-04 (везде):** ре-токенизация внутренностей модалок и виджетов **целиком**, без остатков
  bespoke-классов: `RequestFormModal`, `UserFormModal`, панели Настроек (`OrgSettings` 508,
  `NetworkSettings` 452, `BackupSettings` 337, `ActiveDirectorySettings` 361, `StorageSettings` 203,
  `ThresholdSettings` 120), `ReportFilters`, месяц/год-`<select>` в `PeriodSelector` → `Select`.
  Функция и раскладка не меняются.
- **D-05 (Заявки):** `RequestsSearchAndTabs.svelte` — bespoke табы → примитив `Tabs` (как D-05
  Фазы 27 / D-10 Фазы 26). Поведение фильтров/поиска/счётчиков не меняется.

### Серая зона A — Суб-навигация и сегментные переключатели

- **D-06:** ReportSubNav (2 уровня: домен + тип отчёта со счётчиками), SettingsSubNav (7 разделов),
  а также сегментный переключатель `PeriodSelector` (Месяц/Год/Диапазон) — сейчас везде самописные
  `<button class="tab">`. **Решение: адоптировать примитив `Tabs` повсеместно** — `underline` для
  типов отчётов/разделов настроек, `segmented` для домена отчётов и режимов периода.
  **Счётчики типов отчётов** (сейчас через компонент `Badge` с accent-тоном у активного) —
  через встроенный count-slot `Tabs`; **если нужен accent-тон, расширить примитив `Tabs`, а не
  форкать** его или оставлять bespoke.
  **Обоснование:** единые компоненты — прямая цель milestone; продолжение D-05. Оставлять три
  разных таб-паттерна против цели. Отклонено «оставить bespoke, только ре-токенизация».
  **Действие для планировщика:** сопоставить домен-нав/тип-нав/разделы/режимы с вариантами `Tabs`;
  решить, нужно ли расширение count-slot под Badge-тон (расширение примитива — предпочтительнее
  форка). Поведение навигации (переключение домена/типа/раздела/режима, ARIA `tablist`/`aria-selected`)
  не должно измениться.

### Серая зона B — Таблица отчётов

- **D-07:** `ReportTable.svelte` — сырой `<table>` с **динамическими колонками** под каждый тип
  отчёта (+ итоги/экспорт). **Решение: перевести на общий примитив `Table`/`TableRow`** — как D-03,
  но колонки строятся динамически из описания отчёта. Переиспользуются обёртка/border/radius/elev,
  пустые состояния, футер-итог.
  **Обоснование:** архитектурная консистентность таблиц между всеми окнами; общая инфраструктура
  бесплатно. Отклонено «специализированная таблица только с ре-токенизацией».
  **Действие для планировщика:** сверить, что API `TableRow` тянет динамический набор колонок,
  строку итогов и текущий экспорт **без изменения данных/логики отчёта** (SC #4). Если динамические
  колонки/итоги плохо ложатся на текущий `TableRow` API — расширить примитив под этот кейс (как в
  D-06 для Tabs), а не форкать.

### Серая зона C — Редактор шаблонов

- **D-08:** `TemplateEditor.svelte` (462 стр.) — редактор HTML-шаблонов актов; **шаблоны живут в
  БД**, есть известная ловушка seed/upgrade. **Решение: строго визуально — хрома + форм-контролы.**
  Кнопки/поля/селекты редактора → примитивы (`Button`/`Input`/`Select`), общая хрома/токены.
  **Область правки (textarea/код) и механику предпросмотра НЕ трогать.**
  **Обоснование:** редактор функционально-чувствителен (DB-backed шаблоны, seed/upgrade-ловушка);
  глубже — прямой риск нарушить SC «чисто визуальный». Отклонено «переработать область редактора».

### Claude's Discretion
- Точное сопоставление колонок каждого списка/таблицы с API `TableRow` (D-03, D-07); нужно ли и как
  расширять `Table`/`TableRow` под динамические колонки отчётов.
- Нужно ли расширение count-slot `Tabs` под accent-тон счётчиков и его форма (D-06).
- Точный состав секций `RequestDetail` при переносе на `DetailPanel`/`DetailSection`/`DetailField`
  (без изменения отображаемых полей).
- Дробление на волны/планы. **Порядок по прецеденту D-19 Фазы 26 / Claude's Discretion Фазы 27:**
  сперва общие/разделяемые артефакты (любые правки примитивов `Tabs`/`Table`/`TableRow` под новые
  кейсы), затем четыре окна параллельно — чтобы волны не дрались за общие файлы.
- Конкретные значения ре-токенизации там, где нет прецедента — выводятся из `_tokens.scss` и окон
  Фаз 26–27.

## Existing Code Insights

### Reusable Assets
- **Примитивы Фаз 24–25 + артефакты Фазы 27 покрывают почти всё:** `Tabs` (D-06), `Table`/`TableRow`
  (D-03/D-07), `DetailPanel`/`DetailSection`/`DetailField` (D-01 — созданы Фазой 27), `Modal`,
  `Input`/`Select`/`Checkbox`/`Radio`/`Button`/`Badge`, `DatePicker` (уже в `PeriodSelector`),
  `PageHeader`. Новых примитивов, скорее всего, не нужно — максимум расширение `Tabs`/`Table` под
  свои кейсы.
- **Заявки структурно = окна Фазы 27** — работа сводится к повторению уже проверенных D-01…D-05.
- **Пользователи** — самое простое окно (список + модалка).

### Established Patterns
- Legacy-токены и hex во всех четырёх окнах = **0** (Фаза 23). Фаза 28 = адаптация примитивов, а не
  переименование токенов.
- Стили — scoped `<style lang="scss">` в каждом компоненте; глобальных классов почти нет.
- Пропсы — Svelte 5 runes (`$props`, `$bindable`, `$derived`), `Snippet` для children.
  **Ловушка Фазы 24:** `const` vs `let` при `$bindable()` — контракт, не стилистика.
- **Фронтенд-тестов нет.** Гейты: `pnpm lint`, `pnpm svelte-check`, `pnpm --dir ui build`,
  `check-tokens.mjs`. Проверка визуала — только глазами (D-18 Фазы 26).
- **`:global()` в plain `.scss` не работает** (урок Фазы 24). CI-гейта на это нет.
- **Гоча (память проекта):** перед проверкой через LAN-браузер нужен `pnpm --dir ui build` —
  серверный режим отдаёт `ui/dist`, `cargo tauri dev` хотрелоадит только desktop-webview.
  `prebuild` тянет `cargo test -p trackly-app --test export_bindings`.
- **DB-backed шаблоны актов** — известная ловушка seed/upgrade (правка bundled-шаблона не трогает
  существующие БД). Причина строгой границы D-08.

### Integration Points
- **`Tabs`/`Table`/`TableRow` — общие примитивы** нескольких потребителей (Устройства, витрина,
  `ActFormItemsTable`, окна Фазы 27). D-06/D-03/D-07 добавляют новых потребителей и, возможно,
  расширяют API — регресс проверять во всех.
- **Оболочка (`Layout`/`Sidebar`/`PageHeader`) — общая, готова из Фазы 26** — окна наследуют, менять
  не нужно.
- Витрина живёт за ролью admin — известный долг: гейт на пункте меню, но не на маршруте
  (24-LEARNINGS, backlog 999.1).

<specifics>
## Specific Ideas

- **Характер фазы: компоненты, не токены.** Токены уже мигрированы (0 legacy/hex); Фаза 28 — про
  адаптацию общих примитивов и консистентность. SC «токены/**компоненты**» читать с весом на
  компонентах.
- **Правило расширения примитива, а не форка:** где текущий вид требует большего, чем даёт примитив
  (accent-тон счётчиков Tabs D-06, динамические колонки Table D-07), — расширять общий примитив, а не
  плодить bespoke-варианты. Единые компоненты — цель milestone.
- **Строгость SC #4 (чисто визуально):** особенно у редактора шаблонов (D-08, DB-backed +
  seed/upgrade) и логики отчётов/периодов — структура/поля/workflow сохраняются.
- **Все серые зоны решены рекомендованными опциями** — набор консервативный и последовательный с
  Фазами 26–27.
