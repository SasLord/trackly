<objective>
Implement the forced-admin provisioning state machine: extend `AuthService` with an
`admin_logins` set (via a builder method, not a new constructor arg), a pure local
membership check, and a 5-branch state machine that overrides Phase 31's existing
`on_ad_bind_success` branching for any login on the list — covering unknown, pending,
blocked/soft-deleted, active-non-admin, and already-active-admin states, each with the
correct SQL transition, a mandatory `audit_log` entry, and closure of any dangling
`ad_register` request. Wire the config field from Plan 01 into `AppCtx::build`.

Purpose: This is the core of SSO-02 — solves the "first administrator" problem for
AD-only organizations by making a deployment-time login list an authoritative,
auditable admin-grant mechanism, independent of directory reachability.
Output: `AuthService::on_ad_bind_success` forces admin for any listed login, on both
the SSO (passwordless) and LDAPS (password-bind) entry points, with full audit trail.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `trackly.config.toml` -> `AuthService.admin_logins` | Deployment-time config, loaded once at `AppCtx::build()`, baked into an in-memory `Arc<HashSet<String>>` (Plan 01's boundary, threaded here). |
| AD bind result -> `on_ad_bind_success` | Both SSO (passwordless, Kerberos-authenticated by the caller) and LDAPS (password-verified by `ad_client.authenticate`) entry points funnel into this single provisioning seam — the `login`/`display_name` strings here are already authenticated identities, not untrusted input, by the time they reach `is_admin_login`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-03 | Elevation of Privilege (intentional) | `force_admin_provisioning` (all 5 branches) | mitigate | This IS an explicit, config-authored privilege escalation path (the feature's whole purpose, D-07). Standard control is NOT "prevent escalation" but "make it deterministic, auditable, and unreachable except via deployment-time config": local-only set check (D-10, cannot be influenced by a compromised/unreachable directory), no runtime/UI mutation path (D-01/D-03), mandatory audit_log row per transition (T-32-04). |
| T-32-04 | Repudiation | every write branch of `force_admin_provisioning` | mitigate | Every branch except the active-admin no-op writes an `audit_log` row (`action='ad_auto_admin'`, `payload_json` capturing `prior_state`) in the SAME writer transaction as the `users` mutation — never best-effort/fire-and-forget. This is the only durable record that a human didn't approve this specific elevation (ASVS V9). |
| T-32-05 | Tampering / Repudiation | pending -> forced-admin transition | mitigate | The dangling open `ad_register`/`register` request is closed (`status='completed'`) in the SAME writer transaction as the `users` promotion (Pitfall 2) — prevents an admin later "approving" or "rejecting" a request for a user who is already an active Administrator. |
| T-32-06 | Tampering (race, low severity) | concurrent logins for the same newly-listed login | accept | Single-writer serialization (project-wide architecture, CLAUDE.md) already guarantees both concurrent requests funnel through the same `WriterHandle`/`spawn_blocking` worker — no new race surface introduced by this phase. |
| T-32-07 | Denial of Service (low) | repeated logins for an already-active-admin user | mitigate | The no-op branch explicitly skips the write when the user is already active admin — prevents unnecessary `version`/`updated_at_utc` churn on every login (idempotency, not a security control but prevents audit-log noise that could mask real escalation events). |
