# Phase 41.6: Раздел «Устройства» для сотрудника - Context

**Gathered:** 2026-11-20
**Status:** Ready for planning

<domain>
## Phase Boundary

Роль «Сотрудник» в веб-интерфейсе получает второй раздел — «Устройства»: плоский список всех
устройств всех его групп (АРМ) и связанных с ними принтеров, с полным описанием, карточкой
просмотра и меню строки, из которого создаются заявки «Ремонт» (любое устройство) и «Замена
картриджа» (принтер) с подставленным устройством. Дерево мест, чужие устройства и прочие
разделы сотруднику по-прежнему недоступны; сервер отдаёт только устройства его области обоими
транспортами (Tauri invoke и HTTP).

Требования: EMP-01, EMP-02, EMP-03 (`.planning/REQUIREMENTS.md` §«Устройства сотрудника (EMP)»).

**Граница уточнена в обсуждении 2026-11-20 по решению пользователя:** сверх буквы EMP-01..03
в фазу входят счётчик непрочитанного на вкладке «Заявки» у сотрудника (D-03), уровень тонера
принтера (D-17, D-18), меню строки с правым кликом (D-09, пересматривает решение по умолчанию
брифинга групп) и мобильная вёрстка карточками (D-21).

**Вне границы:** история перемещений/актов устройства для сотрудника, IP/community/прочие SNMP-
поля, создание заявки «Другое» из строки, правка устройств сотрудником, карта.

</domain>

<decisions>
## Implementation Decisions

### Навигация сотрудника
- **D-01:** Переключение разделов — две вкладки-ссылки «Заявки» и «Устройства» в существующей
  шапке `EmployeeLayout.svelte` (рядом с «Trackly»). Шапка остаётся самостоятельным компонентом,
  `Sidebar`/`sidebar-config` сотруднику не подключаются. Активная вкладка подсвечивается по
  текущему маршруту.
- **D-02:** Стартовый раздел после входа — «Заявки», как сейчас. В `employeeRoutes` добавляется
  `/devices`; `*` и любые иные маршруты по-прежнему отдают «Доступ запрещён».
- **D-03:** У вкладки «Заявки» сотрудника — счётчик заявок с непрочитанным, тот же источник,
  что у сайдбара персонала (`unreadStore.requestsWithUnread`, компонент `UnreadBadge`, фаза 41.5).

### Список: колонки и вид
- **D-04:** Колонки: наименование, тип, модель, серийный номер, инвентарный номер, место,
  статус (7 полей EMP-02) + колонка «АРМ» — имя группы (групп), через которую устройство попало
  в область сотрудника; если групп несколько (например, общий принтер), — все имена через
  запятую. Список остаётся плоским, без группировки по АРМ.
- **D-05:** У принтеров — пометка происхождения связи с группой той же логикой и приоритетом,
  что в карточке группы (41.13 PGR: **USB > ссылка > в составе**, одна пометка на строку).
- **D-06:** Без поиска и без сортировки по колонкам; фиксированный порядок — по типу, затем по
  наименованию (как `repairs.deviceOptions`).
- **D-07:** Если по устройству есть открытая заявка, в строке метка «Заявка №N» со ссылкой на
  неё — номер отдаётся ТОЛЬКО для заявок, где сотрудник участник (BOPLA, как 41.4 D-20
  `participant_user_ids`); по чужой открытой заявке — метка без номера и ссылки (например,
  «В ремонте»/«Есть заявка»; точную подпись — на усмотрение планировщика).
- **D-08:** Пустое состояние (EMP-02): сотрудник ни в одной группе — подсказка обратиться к
  администратору. Подпись статуса сервер присылает в DTO строки (41.4 D-38: справочник статусов
  `device_statuses_list` сотруднику закрыт и не открывается).

### Действия из строки
- **D-09:** Меню строки — кебаб в строке И правый клик по строке, одно и то же меню; двойной
  клик открывает карточку. **Это пересматривает решение по умолчанию брифинга групп**
  (`.planning/v1.4-GROUPS-MODEL-DECISIONS.md`: «в списке сотрудника только двойной клик») —
  решение пользователя 2026-11-20. Меню — через `ActionMenu` с порталом (общий дефолт, см.
  память «opt-in дефолт плодит регрессии»).
- **D-10:** Пункты меню (порядок на усмотрение планировщика, «Открыть» — первым):
  «Открыть» (карточка), «Заявка на ремонт», «Замена картриджа» (только если строка — принтер),
  «Перейти к заявке №N» (только при открытой заявке, где сотрудник участник),
  «Скопировать инв. номер».
- **D-11:** «Заявка на ремонт» по устройству с уже открытой ремонтной заявкой ведёт себя как
  форма «Ремонт» 41.4 для `in_repair`: та же блокировка и та же причина в подсказке; вторая
  заявка не создаётся. Один источник правды — тот же признак `in_repair`/серверная проверка.
- **D-12:** Заявка из строки открывает ТУ ЖЕ форму `RequestFormModal.svelte` с подставленными
  типом заявки и устройством/принтером; сотрудник может их сменить. Вторая форма не заводится —
  форме добавляется предзаполнение (сейчас его нет).
- **D-13:** После успешного создания — остаёмся в «Устройствах», тост «Заявка №N создана» со
  ссылкой «Открыть заявку» (`requestTargetHref`); в строке появляется метка заявки (D-07).
- **D-14:** Серверная проверка принадлежности при создании уже есть (ремонт — `repair_service`,
  картридж — `RequestService::create`, 41.13 D-41) и не дублируется; новая точка чтения списка
  обязана фильтровать по той же `SqliteRepairRepository::employee_device_ids` — вторая
  реализация области не заводится.

### Карточка устройства
- **D-15:** Двойной клик / «Открыть» — модалка только для чтения: все поля строки, АРМ,
  пометка происхождения (для принтера), список заявок по этому устройству, где сотрудник
  участник, и те же кнопки создания заявок, что в меню.
- **D-16:** История перемещений и актов сотруднику НЕ показывается.
- **D-17:** Для принтера сотруднику показывается ТОЛЬКО уровень тонера (по цветам, с датой
  последнего опроса). IP, community, серийники SNMP и прочие SNMP-поля не уходят с сервера
  (граница Phase 10/11, T-11-02-I, сохраняется) — DTO сотрудника минимальный (BOPLA).
- **D-18:** Тонер виден и в карточке (полосы по цветам — как `TonerGauge` в «Принтерах»), и в
  строке (компактный индикатор минимального уровня).
- **D-19:** Список и карточка обновляются вживую по существующим WS-событиям
  `entities_changed` (устройства, группы, заявки) — событие только сигнал на перечитывание,
  данные в нём не передаются.

### Состав и вёрстка
- **D-20:** Устройства в статусе «Списано» в списке сотрудника скрыты. «На списание» и прочие
  статусы показываются. Фильтр — в запросе списка, НЕ в общей `employee_device_ids` (она общая
  с формами «Ремонт»/«Картридж» и её менять нельзя без пересмотра их области).
- **D-21:** На узком экране (< ~640px) строки списка складываются в карточки; меню и двойной
  клик/тап работают и там.

### Claude's Discretion
- Точные подписи меток заявки (D-07) и пустого состояния; порядок пунктов меню после «Открыть».
- Можно ли создавать заявки на устройство в статусе «На списание» — следовать текущим серверным
  правилам формы «Ремонт», новых запретов не вводить без нужды.
- Форма DTO строки (одна новая команда/маршрут чтения для сотрудника, оба транспорта), способ
  вычисления колонки «АРМ» и пометки происхождения — переиспользовать логику карточки группы,
  не плодить вторую.
- Порог/вид компактного индикатора тонера в строке.
- Точный брейкпоинт мобильной вёрстки.

</decisions>

- Сотрудник не вызывает staff-only команды вовсе (41.4 D-38) — гейт `ui/scripts/check-employee-api.mjs`

  — новый подписчик/маршрут учесть в реестре.

  (`EmployeeLayout` `.employee-content` сейчас `overflow:auto`).

- `ui/src/features/layout/EmployeeLayout.svelte` — вкладки в шапке + счётчик.
- Новая команда Tauri + маршрут `/api/v1/...` (оба транспорта, тонкие адаптеры над сервисом).
- Серверный тест BOLA: запрос чужого устройства/карточки отклоняется на обоих транспортах
  (критерий успеха 5).

  пора просить картридж.
