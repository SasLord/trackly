## Summary

Фаза почти целиком композиция существующего: область сотрудника (`employee_device_ids`), форма заявки (`RequestFormModal`), счётчик (`unreadStore`), меню (`ActionMenu`), полосы тонера (`TonerGauge`), ссылка на заявку (`requestTargetHref`). Новое на сервере — ОДНА read-команда с DTO строки (устройства области + АРМ + происхождение + тонер + метки заявок); новое на клиенте — страница `EmployeeDevicesPage`, карточка, меню строки сотрудника и пропсы предзаполнения формы.

Три факта из кода, которые меняют план относительно CONTEXT.md (подробно ниже): (1) `WsEvent::EntitiesChanged` по `is_visible_to` виден ТОЛЬКО Admin|Manager — сотруднику D-19 в текущем виде не доставляется; нужен новый payload-less сигнал или иной путь; (2) форма «Ремонт» при `in_repair` НЕ блокирует, а ПРИСОЕДИНЯЕТ к общей заявке (D-20 41.4, `joined`), формулировка D-11 «блокировка» расходится с кодом; (3) на десктопе Tauri-команды идут от системного администратора (`resolve_tauri_identity`), поэтому «отклонять чужие на обоих транспортах» проверяется на `build_*` с `Identity` сотрудника и на HTTP, а не на живом Tauri-вызове.

**Primary recommendation:** Один новый сервис с read-only методом `list_for_employee(caller)` (новый файл `services/employee_device_service.rs`, без `writer`, вне области гейта `entities_changed_gate`), команда `employee_devices_list` по схеме S-1 (`build_*` + Tauri + axum), разрешение `Action::CreateRequest`, скоуп ВСЕГДА по `caller.user_id` (без staff-обхода), фильтр «списано» в SQL запроса списка, не в `employee_device_ids`.

### Pattern 2: Скоуп сотрудника
Образец — `RepairService::device_options`: `employee_device_ids(&conn, user_id)` -> `HashSet` -> `retain`. ### Pattern 3: «АРМ» и происхождение — ОДИН источник
`employee_device_ids` — единый SQL-union (members подгрупп + `device_refs` связанных групп + USB-принтеры членов). Логика «USB > ссылка > в составе» живёт ВНУТРИ функции карточки группы в `group_service.rs` (~стр. 1480-1545): три цикла по `usb_printers_for_group` / ссылки (`ref_devices_for_group` + `live_printer_device_ids`) / `member_printers_for_group` с дедупом через `seen`, порядок циклов = приоритет. Эта логика не выделена в публичную функцию.
Рекомендация: добавить в `repairs_sqlite.rs` рядом `employee_device_origins(conn, user_id) -> Vec<DeviceOriginRow { device_id, group_id, group_name, source: Usb|Link|Member }>` (ПО КАЖДОЙ привязанной группе пользователя, а не по подгруппам: «АРМ» = группа, где сотрудник указан в свойстве `users`), и написать инвариант-тест: множество `device_id` из origins ∪ == результат `employee_device_ids` (одна истина, вторая реализация не расходится). Приоритет считать единым выбором на уровне строки: по каждой паре (устройство, группа) источник; пометка строки — для принтеров, наилучшая по приоритету среди групп; имена всех групп — через запятую (D-04). Альтернатива «вынести приоритет в чистую функцию, вызываемую и карточкой группы» — рискованнее (правка карточки 41.13, повторный UAT); брать только если планировщик готов покрыть её тестами `groups_values_card`.
Неоднозначность (Open Question 2): если устройство лежит в ПОДгруппе привязанной группы — «АРМ» = привязанная группа (родитель), рекомендовано.

### Pattern 4: Минимальный DTO (BOPLA)
`EmployeeDeviceDto`: `id, name, type_name, is_printer, model, serial_number, inventory_number, place (full_path), status_code?, status_name, arm_names: Vec<String>, printer_origin: Option<"usb"|"link"|"member">, toner: Option<EmployeeTonerDto{levels: Vec<{label, percent: Option<i32>}>, polled_at_utc: Option<i64>}>, in_repair: bool, my_requests: Vec<{id, request_type, status}>, other_open_request: bool`. Никаких `ip_address`, `community_configured`, `snmp_version`, `oid_profile_id`, `usb_host_*` (имя USB-хоста — не включать: это поле чужого устройства области, но оно не нужно; D-05 нужна только метка). Серийник устройства (`devices.serial_number`) — НЕ SNMP-серийник; D-04 его явно требует. Тонер брать из `printer_readings` (последнее чтение, `ts_utc`) — как `PrinterService` (printer_service.rs:179-230), но собственным запросом: НЕ вызывать `PrinterService`/`PrinterDto` (он несёт IP/ssid-подобные поля). `toner_levels` — JSON `{label: level}` с encoding percent (так показывает `PrinterDetail.svelte`); значения `< 0` = неизвестно. [VERIFIED: dto/printer.rs, PrinterDetail.svelte]

### Pattern 5: Метки заявок (D-07, D-15)
Открытая ремонтная — `OPEN_REPAIR_CLAUSE` (`status IN ('open','in_progress','in_repair')`, `request_type='repair'`, не удалена); пары `(device, request_id)` даёт `open_repair_requests_for_devices`. Участие — `request_participants` / `request_visibility_clause(user_param)` (автор ИЛИ участник; `repairs_sqlite.rs:33-40`). Для сотрудника: `my_requests` = открытые заявки устройства (ремонт и, по усмотрению, «замена картриджа» по принтеру), где он автор/участник; `other_open_request = in_repair && нет такой моей`. Номер чужой заявки НЕ отдавать. Для карточки «список заявок по этому устройству, где участник» — вернуть в той же строке (не вторым эндпоинтом), без закрытых старше разумного предела (рекомендация: открытые + последние 10 закрытых, ограничение серверное).

### Pattern 6: Сервисная проверка создания уже есть
Ремонт: `repair_service.rs:702` (`employee_device_ids` при создании); картридж: `request_service.rs:398-420`. НЕ дублировать (D-14). Клиент обрабатывает `Forbidden` как в `RequestFormModal` (printerError + перезагрузка).

### Pattern 7: Предзаполнение `RequestFormModal`
Сейчас форма сбрасывает состояние в `$effect` при открытии (`requestType = 'cartridge_replace'`, `printerDeviceId = null`, `repairChoice = null`). Добавить необязательный проп `prefill?: { type: 'repair'|'cartridge_replace'; deviceId: number }` и применять ВНУТРИ того же reset-блока после сброса (иначе сброс затрёт предзаполнение). Для `repair` — выставить `requestType='repair'`, вызвать `loadRepairDevices()` (список читается лениво только при `selectType`), `repairChoice = String(deviceId)`; для `cartridge_replace` — `printerDeviceId = deviceId` после `loadPrinters()`. `onSuccess` отдаёт `{id,status}`; для текста тоста использовать этот `id` и `res.joined` (форма сама пушит тост «Заявка отправлена»/«Вы присоединились…» — для D-13 нужен тост со ссылкой: либо не дублировать (подавить внутренний тост при заданном prefill/`suppressToast`), либо расширить `onSuccess`). Единственный вызывающий сейчас — `RequestsPage.svelte:332`.

## Common Pitfalls

### Pitfall 1: WS `EntitiesChanged` не доходит до сотрудника (D-19 под угрозой)
**What goes wrong:** `WsEvent::is_visible_to` (`dto/printer.rs:449`) -> `EntitiesChanged` только Admin|Manager; `desktop_event_bridge` и axum-WS фильтруют тем же методом. Сотрудник не получит событие, список не обновится «вживую».
**Options:** (a) расширить видимость на Employee — НЕЛЬЗЯ как есть: событие несёт `place_ids/device_ids/group_ids` чужих сущностей (утечка идентификаторов, нарушает 41.5-итог secure-phase «мост десктопа фильтрует события»). (b) РЕКОМЕНДАЦИЯ: новый payload-less вариант (например `EmployeeScopeChanged {}`) с `is_visible_to` = Employee, посылаемый из того же `send_entities_changed` (единственная точка, значит все мутации уже покрыты реестровым гейтом и новых «слепых» мест нет); клиент перечитывает список с дебаунсом. Проверить побочные тесты, считающие события (`assert_one_entities`, `ws_http_single_broadcast`, `entities_changed_ws`) — добавят второе событие; либо слать новый вариант только в тех же условиях и обновить счётчики тестов. Добавить вариант в `bindings-phase6` (генерация specta; `export_bindings` тест) и в обработчик UI. (c) запасной минимум без серверных правок: перечитывать список по `request_status_changed`/`chat_message` (доходят автору/участнику) + при возврате фокуса окна + ручной «Обновить». Не закрывает «админ переместил/переименовал устройство».
Решение выносится на подтверждение пользователя — см. Open Questions.
**Warning signs:** тест «сотрудник получает событие» зелёный на `is_visible_to` юнит-уровне, но не на живом WS-роутере.

### Pitfall 2: D-11 «блокировка» против присоединения
Форма 41.4 при `inRepair` показывает «уже в ремонте» и при отправке ПРИСОЕДИНЯЕТ сотрудника к общей заявке (`joined=true`, тост «Вы присоединились к заявке на ремонт»); второй заявки не создаётся. Это и есть «одна заявка на устройство». Буквальная блокировка пункта меню оставила бы сотрудника без возможности присоединиться. Рекомендация: в меню пункт НЕ дизейблить; подпись/подсказка «уже в ремонте — вы присоединитесь к заявке» (если участник — вместо этого «Перейти к заявке №N»). Подтвердить у пользователя (Open Question 1).

### Pitfall 3: Десктоп-идентичность
Tauri-команда резолвит `resolve_tauri_identity` = системный администратор. Любая «сотруднику отказ на Tauri» проверяется ТОЛЬКО на `build_*(&ctx, &Identity{Employee,..})` (как `repairs_role_matrix_tauri_path`, role_endpoint_matrix.rs:5724) и на HTTP; живой десктоп сотрудника не существует. Скоуп по `caller.user_id` даёт админу пустой список — это нормально.

### Pitfall 4: Гейты UI не видят новую страницу
`check-employee-api.mjs` строит замыкание от ТРЁХ входов (`RequestsPage`, `EmployeeLayout`, `LoginPage`); `routes.ts` не входит. Если страница подключена только из `routes.ts`, гейт её НЕ проверит (вакуумно). Либо импортировать страницу/компоненты из `EmployeeLayout`, либо добавить `EmployeeDevicesPage.svelte` в `ENTRIES` (+ при необходимости поднять `MIN_FILES/MIN_CALLS`). Новую команду добавить в обе стороны фикстуры: `ui/scripts/fixtures/employee-allowed-commands.json` И `employee_ui_commands()` в `role_endpoint_matrix.rs` (список обязан быть отсортирован; `TRACKLY_UPDATE_FIXTURES=1` перепишет JSON; тест `employee_allowed_fixture_sound` проверит, что команда не даёт 401/403 сотруднику).
Также: `check-employee-api` требует, чтобы вызовы staff-only команд были под охраной; новая команда в фикстуре разрешённых — охрана не нужна.

### Pitfall 5: Тесты и suite-разводка
`autotests = false`: каждый новый `tests/*.rs` должен быть подключён `#[path]` в `tests/suites/<suite>.rs` (алфавитно), иначе молча не запускается (гейт `suite_wiring`). Подходящие suite: `app_repairs` (скоуп/DTO) и `app_server`/`app_gates` (HTTP/матрица). Полный cargo ~4,5-6 ч и `timeout` на машине нет — гонять `cargo test -p trackly-app --test app_repairs <фильтр>`, по одному `cargo test` за раз; полный прогон один раз на границе волны в фоне, вывод в файл.

### Pitfall 6: Вакуумные тесты BOLA
Тест «чужие отклонены» обязан иметь второго сотрудника со СВОИМ устройством И заведомо видимое своё (иначе пустой список проходит тест). Проверять: сотрудник A не видит устройства B; Manager/Admin-идентичность получает пустой список (скоуп по user_id); `user_id=None` -> Forbidden; «Списано» скрыто, «На списание» показано; устройство, достижимое только через USB-хост/`device_refs`, присутствует; несколько групп -> `arm_names` содержит все; происхождение приоритет USB>ссылка>состав; JSON ответа не содержит ключей `ip`, `community`, `snmp`, `oid` (проверка по сериализованному JSON — класс «инвариант требует пробы»: добавить мутацию «DTO с лишним полем» и убедиться, что проба краснеет).

### Pitfall 7: Мёртвый CSS и свёртка колонок
Правило с `:has` на содержимом дочернего компонента без `:global` вырезается Svelte (память `svelte_global_in_has_dead_rule`); `.row-actions { opacity: 0 }` требует формы `:has(:global([aria-expanded='true']))` (гейт [F]). Для мобильных карточек (D-21) layout только внутри `@media (max-width: 639px)` или через контейнер; смотреть пример `@media (max-width: 1099px)` в `CartridgesMasterDetail.svelte`. Готовых карточных строк таблиц в репозитории нет (проверено grep) — новый паттерн; верификация только в запущенном приложении/браузере (память «Synthetic harness not verification»; стенд — `browser_uat_harness`).

### Pitfall 8: Скролл
`.employee-content` сейчас `overflow:auto`; страница по паттерну оболочки: `height:100%; min-height:0`, прокручивает свою область (память `app_shell_scroll_pattern`), иначе двойной скролл.

### Pitfall 9: Двойной клик и контекстное меню в строке
Образец защиты — `DeviceListRow.svelte`: охрана `isRowOverlayEvent(e.target)` первым оператором обработчиков; гейт `check-device-row-menu` читает любую `ondblclick=` как привязку строки — прочесть его правила до написания разметки (могут применяться к новым файлам или потребовать расширения области). Порядок «охрана до preventDefault» (память `counting_gate_blind_to_order`).

## Security Domain

### Applicable ASVS Categories
| Category | Applies | Control |
|----------|---------|---------|
| V4 Access Control | yes | `authorize(CreateRequest)` + скоуп по `user_id`; BOLA/BOPLA тесты |
| V5 Input Validation | минимально | команда без параметров (или `deviceIds` не принимать — список только свой); карточка из строки списка, без запроса по id |
| V3 Session | уже есть | `session_identity` |
| V2/V6 | нет | — |

### Known Threat Patterns
| Pattern | STRIDE | Mitigation |
|---------|--------|------------|
| BOLA: чужие устройства | Info disclosure | единый `employee_device_ids`, нет эндпоинта «по id» |
| BOPLA: SNMP/IP в DTO | Info disclosure | минимальный DTO + тест по JSON |
| Номер чужой заявки | Info disclosure | номер только при участии |
| Утечка id через WS | Info disclosure | payload-less сигнал; НЕ расширять `EntitiesChanged` на Employee |
| `spa_fallback` маскирует отсутствие маршрута (200 index.html) | — | `http_route_parity` + тест через `gt_post` проверяет JSON |

Карточка читает данные из строки списка (без отдельной команды «get by id») — так исключается класс BOLA по id целиком; если планировщик всё же заведёт `get`, он обязан фильтровать по тому же скоупу и иметь отрицательный тест.
