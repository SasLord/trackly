<objective>
Дать серверу возможность ИЗМЕНИТЬ и СТЕРЕТЬ IP (и community) принтера при редактировании
устройства. Серверная половина находки F-1 живой UAT (принтер, заведённый с IP, не получает
USB-хост никогда) - решение D-13.

Purpose: без записи IP на пути обновления форма (план 12) нечем кормить: изменить или стереть IP
сохранённого принтера нельзя (жалоба 'IP убрать не получается', D-13).
Output: валидатор IP, метод репозитория, два поля DevicePatch, запись в DeviceService::update,
та же нормализация на создании.

Решения плана (записать в SUMMARY):
1. Тип IP в патче - Option<Option<String>> с serde_with::rust::double_option (образец: serial_no и
   usb_host_device_id в том же DevicePatch). Три состояния: ключа нет / null / значение.
   Пустая строка трактуется как null (форма может прислать пустое поле).
2. community - Option<String>, не двойной Option: отдельного состояния 'сбросить в public' нет,
   потому что сброс происходит неявно при стирании IP. Это и есть правило device_service.rs:594.
3. Литералов DevicePatch без ..Default::default(), которые обязаны получить ДВА новых поля: пять
   (acts_update_return.rs x1, devices_type_conversion.rs x1 в type_patch,
   place_movements_write_sites_devices.rs x3), те же пять, что правил план 03; точное число
   подтвердить cargo check, лишних мест быть не должно. Литералы PrinterCreateBlockDto не меняются.
4. Валидация формата - МЯГКАЯ и общая для создания и обновления (решение координатора вместо
   моего первоначального 'только IPv4'): отклоняется только то, что опасно или не работает:
   двоеточие (порт: real.rs:40-43 при наличии двоеточия не дописывает :161 и передаёт строку
   AsyncSession как есть, значит 'адрес:порт' направил бы UDP на произвольный порт; IPv6 тем же
   образом не работал и раньше) и пробелы или управляющие символы. Имена хостов НЕ запрещаются:
   они работают сегодня, и отказ на пути создания был бы регрессом под видом ужесточения. Уже
   сохранённые значения не трогаются, пока их не меняют (стирать можно любое).
5. IP и USB-хост НЕЗАВИСИМЫ (D-15, поправка пользователя 2026-11-01). Раньше в этом плане стояли
   сначала сброс хоста при задании IP, затем отказ в IP при заданном хосте - оба решения основаны на
   ложной посылке 'IP либо хост' и отменены. На сервере нет НИКАКОЙ связи между двумя записями:
   ни отказа, ни сброса, ни чтения хоста при записи IP.
</objective>
