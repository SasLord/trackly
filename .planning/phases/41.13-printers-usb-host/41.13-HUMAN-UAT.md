## Находки

### F-1 (существенная) — принтер, заведённый с IP, хост получить не может

Дословно от пользователя: «При редактировании Принтера поле IP не отображается совсем, поле IP
получается задать при создании принтера, а потом убрать IP не получается».

Разбор по коду:

- Блок «SNMP / Сеть» (IP + community) существует **только при создании**:
  `ui/src/features/devices/DeviceFormBody.svelte:1353`, `{#if !isEdit}`. Это НЕ регресс фазы —
  на коммите `41bc7d79` (до любого кода 41.13) условие уже было
  `{#if typeId === PRINTER_TYPE_ID && !isEdit}`. Сделано сознательно решением **D-03 фазы 40.3**
  (комментарий там же: «Optional, create+Принтер ONLY (D-03): IP/SNMP block — DOM absent
  otherwise»), серверного пути менять IP у принтера тоже нет: `printer_override` читается только
  в ветке создания `sync_printer_row_in_tx`.
- Поле хоста при правке видно только когда у сохранённого принтера IP пустой:
  `usbHostPicker.ts:183`, `return ctx.printerLoaded && (ctx.loadedPrinterIp ?? '').trim() === '';`

Вместе это даёт тупик, которого раньше не было, потому что поля хоста не было вообще: принтер с
непустым IP не показывает ни поля IP (убрать нельзя), ни поля хоста (скрыто из-за непустого IP).
Такой принтер USB-хост не получит никогда.

**Почему это важно именно здесь.** Обоснованием решения D-07 (хост редактируется, а не только
задаётся при создании) было ровно это: «у всех существующих принтеров хост пуст, и без режима
редактирования функция не починит ни одной существующей записи». Для принтеров с IP цель фазы
не достигнута. Поэтому **PGR-03 остаётся не закрытым полностью.**

### F-2 (запрос пользователя) — показывать, с каким устройством связь

Пункт 4, дословно: «Хотелось бы там ещё подписывать с каким устройством связь, если это не
сложно, то можно сразу, либо отложить на правку позже».

Сейчас в колонке «Связь» карточки группы стоит чип «USB» без имени хоста. Имя хоста есть в
`PrinterDto` (добавлено планом 02: `usb_host_name`, `usb_host_inventory_no`), но строка карточки
группы — это другой DTO, `GroupPrinterDto` (`crates/trackly-app/src/dto/groups.rs:280-297`), и
имени хоста в нём нет. Значит нужно: поле в `GroupPrinterDto` + join в запросе карточки +
отрисовка + гейт.

Отмечу для истории: в UI-SPEC похожий пункт (имя хоста на строке СПИСКА ПРИНТЕРОВ, §8.2) был
намеренно вырезан проверяющим как раздувание объёма. Запрос пользователя — про другое место
(карточка группы) и исходит от самого пользователя, так что это не возврат вырезанного.

## Наблюдения (без кода)

### O-1 — пункт 15 построен на ложной посылке (моей)

Пользователь: «В поле „Ссылки на устройства“ я не могу выбрать „Принтер #1“, так как он уже в
составе группы».

То есть выпадающий список свойства `device_refs` исключает устройства, уже состоящие в этой
группе, и сценарий «поставить ссылку на члена группы и увидеть переключение пометки
„В составе“ → „Ссылка“» через интерфейс недостижим. Это не дефект: поведение осмысленное, а
приоритет `USB > ссылка > в составе` всё равно проверен пунктами 3-4. Пункт чеклиста был
сформулирован мной без учёта этого фильтра.

Следствие для F-2 и для известного ограничения: случай «член группы И явная ссылка» достижим
только если ссылку поставили ДО добавления устройства в состав, либо правкой данных в обход
интерфейса.

### O-2 — пункт 13 остаётся открытым продуктовым вопросом

Пользователь: «Верно и вроде как — правильно. Хотя может я и ошибаюсь, пока не понял, как лучше.
Пусть так и остаётся пока».

Речь о принятом ограничении: у пользовательского типа с двумя свойствами «Ссылки на устройства»
принтер-член со ссылкой только во втором не показывается в списке первичного свойства. Решение
оставлено как есть по желанию пользователя; если позже захочется иначе — это расширение
`GroupPrinterDto` (нести все происхождения, а не одно по приоритету).
