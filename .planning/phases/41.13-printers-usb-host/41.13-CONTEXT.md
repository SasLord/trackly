# Phase 41.13: Принтеры: подключение к АРМ — Context

**Gathered:** 2026-10-28
**Status:** Ready for planning

<domain>
## Phase Boundary

Принтер, стоящий в составе группы, должен быть виден в «Подключённых принтерах» этой группы, и у
принтера должна быть возможность явно указать устройство-USB-хост.

Полное описание происхождения дефекта, собранные факты по коду с номерами строк и границы объёма —
в секции `### Phase 41.13` файла `.planning/ROADMAP.md`. Здесь только то, что решено сверх неё.
</domain>

<decisions>
## Implementation Decisions

### Два механизма, а не один

Решение пользователя 2026-10-28: делать **оба**, они не взаимоисключающие.

1. **Членство = подключён.** Принтер в составе ЛЮБОЙ группы попадает в «Подключённые принтеры»
   этой группы. Рядом с каждой строкой — пометка происхождения: «в составе» / «по USB» /
   «ссылка». Пометка обязательна: для групп-контейнеров вида «Стойка» принтер физически просто
   стоит рядом, и пользователь должен видеть, почему строка здесь оказалась. Правило намеренно
   НЕ привязано к коду типа группы — иначе чужой пользовательский тип, похожий на АРМ, работать
   не будет.
2. **Явный выбор USB-хоста** — чтобы при желании уточнить, в какой именно системный блок принтер
   воткнут.

### Набор устройств в выборе USB-хоста

Решение пользователя 2026-10-28, дословно: «Любое устройство, поиском. Но если принтер состоит в
группе, то первыми пунктами должна отображаться группа устройств этой группы, в которой состоит
этот принтер».

То есть:

- Выбор идёт по **всем** устройствам, с поиском. Жёсткого фильтра нет — ни по группе, ни по типу.
  Причина: принтер часто заводят до того, как собрали АРМ, и любой фильтр по группе дал бы в этот
  момент пустой список. Фильтр по типу тоже отпадает: справочник `device_types` содержит только
  `(1,'Устройство')` и `(2,'Принтер')`, отдельного типа «Системный блок» у устройств нет —
  фильтровать не по чему.
- Если принтер уже состоит в группе, устройства **этой** группы идут **первой секцией** списка,
  с собственным заголовком; остальные устройства — ниже. Это именно порядок и группировка, а не
  ограничение: нужное под рукой, но доступно всё.
- В проекте уже есть и секционированные списки (выпадающий список акта с заголовками «Группы» /
  «Устройства со склада» / «Устройства в составе групп»), и `GroupedPrinterSelect.svelte` —
  планировщику искать образец там, а не изобретать свой.

### Claude's Discretion

- Форма представления пометки происхождения (значок, текстовая метка, колонка) — на усмотрение,
  лишь бы читалось без наведения мыши и работало в обеих темах.
- Конкретный способ сложить три происхождения в один список на сервере (UNION в SQL против сборки
  в сервисе) — на усмотрение, при условии дедупликации: принтер, одновременно член группы и
  USB-привязанный, обязан дать ОДНУ строку, а не две.
- Приоритет пометки для такой строки (что показать, если происхождений несколько) — на усмотрение,
  но решение записать в SUMMARY.
</decisions>

## Specific Ideas

- Текст пустого состояния `ui/src/features/groups/GroupPrintersList.svelte:178` сейчас обещает
  «USB-принтеры появятся здесь сами, как только будут привязаны к устройству состава» — то, чего
  интерфейс не умеет вообще. После фазы он обязан описывать реальное поведение.
- `ui/src/features/printers/PrinterDetail.svelte:435` печатает «Подключён по USB к: устройство #22»
  — сырой идентификатор вместо имени устройства.

## Мины, которые нельзя пропустить

- `sync_printer_row_in_tx` (`crates/trackly-app/src/services/device_service.rs:569`) — мина не
  там, где казалось. Проверено по исходнику 2026-10-28: ветка создания строки `printers` обёрнута
  в `if !printer_repo.exists_for_device_in_tx(...)` (`device_service.rs:579`), поэтому вызов с
  `None` на пути обновления (`device_service.rs:1106`) существующую строку НЕ затирает; а
  `device_service.rs:2197` — это `bulk_create`, не обновление.
  Ловушка обратная: из-за того же гарда наивное «сохраним хост через sync_printer_row_in_tx» при
  РЕДАКТИРОВАНИИ молча не сделает ничего — строка уже есть, ветка не выполнится, пользователь
  увидит «сохранено» и пустой хост. Путь обновления обязан писать хост сам. Тест «обновление не
  затирает хост» на нынешнем коде НЕ упадёт: это защита новой реализации, и чтобы мутационная
  проверка была не вакуумной, у принтера в фикстуре заранее должен стоять непустой хост.
- Паритет транспортов: операция существует и как Tauri-команда, и как `/api/v1/*` маршрут.
  SPA-fallback отдаёт `index.html` с кодом 200 вместо 404, поэтому забытый маршрут молча не
  работает по LAN, а тест на код 200 этого НЕ ловит — проверять тело ответа.
</specifics>
