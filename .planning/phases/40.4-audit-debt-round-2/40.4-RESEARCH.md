## Summary

Это фаза долга, не новой функциональности — источник истины: `.planning/v1.4-MILESTONE-AUDIT.md`
(аудит 2026-09-23, раздел «Что стоит сделать до Фазы 41»). Все четыре находки (NEW-1, N-3, NEW-3,
NEW-2) перечитаны в реальном коде на HEAD в этом research-сеансе. Прецедент по процессу и
структуре планирования — Фаза 40.3 (та же схема долга, закрывала WR-03/N-1/N-2/N-4 предыдущего
раунда аудита); там же — уже готовый паттерн `CASE WHEN` для double-Option полей, который эта фаза
достраивает на третий SQL-путь.

Главные уточнения этого research-сеанса относительно того, что было в тексте аудита:

1. **NEW-1** — баг НЕ в `serde`-границе (как WR-03/40.3), а в ручном чтении `serde_json::Value`:
   `restore_from_snapshot_in_tx` использует `snapshot.get("field").and_then(|v| v.as_str())`,
   что схлопывает «ключ отсутствует» и «ключ есть, значение `null`» в один и тот же `None` —
   тот же класс бага, что и double-Option в WR-03, но механизм схлопывания другой (нет
   `#[serde(with=...)]` — нужно возиться с `serde_json::Value::get().is_some()` напрямую).
   Функция ОДНА и разделяется всеми тремя вызывающими (`update`, `update_return`, undo) — значит
   это не «третий SQL-путь» в смысле третьей копии SQL-запроса, а единственная точка, просто
   третья по счёту РОЛЬ (после `update_in_tx`/`update`), которая ещё несёт `COALESCE`.
2. **N-3** — «шторм событий» и «отсутствие инвалидации» имеют РАЗНЫЕ владения кода: инвалидация —
   чисто клиентский фикс (один вызов `notifyPlaceContentChanged` + одна строка реестра INV-7);
   группировка `NumberSpaceChanged` — чисто серверный рефакторинг цикла `import_csv_commit`.
   Оба фикса требуют знания РАСПРЕДЕЛЕНИЯ мест по строкам CSV — сегодня клиент этого не знает
   (`CsvImportReport` не несёт `place_id`), это единственный пункт фазы, требующий изменения DTO,
   а не только внутренней логики.
3. **NEW-3** — в файле уже реализован (для стрелки ↑/↓, NUM-07) ГОТОВЫЙ строковый компаратор
   «значение поля совпадает с живым серверным предложением» (`matchesLast`/`matchesAlt` в
   `NumberTemplateField.svelte`) — это ровно нужный сигнал «автоподставлено vs введено вручную»,
   просто не прокинут наружу. **Критический риск регрессии, не описанный в тексте аудита**:
   бэкенд уже ЖЁСТКО отклоняет `bulk_create` с `count > 1` и непустым `inventory_no`
   (`bulk_create_rejects_when_inventory_no_set`, `device_service.rs:1560-1579`) — если фикс
   ослабит `quantityDisabled`, не очистив `inventoryNo` перед сборкой `DeviceNew` для
   bulk-пути, пользователь получит серверную ошибку валидации при каждой попытке массового
   создания с автоподставленным номером. Дублирования номеров это НЕ допустит (бэкенд уже
   страхует), но полностью ломает UX, который эта находка должна чинить.
4. **NEW-2** — `render_pdf`'s локальная переменная `act` уже ЕСТЬ `ActDto` (`self.get(act_id)`),
   чьё поле `.number` уже вычислено через канонический `format_act_number` — ТОТ ЖЕ, что использует
   `resolve_movement_act_number` (единый источник для таймлайна И отчёта «Перемещения»,
   `act_number_display.rs`). Фикс не требует новой логики форматирования вообще — только положить
   уже готовое значение `act.number` в контекст под новым ключом `act.number_display` и
   перевести 3 места в `act_handover.html`. Проектный механизм версионирования шаблонов
   (`_legacy_defaults/vNN` + `KNOWN_LEGACY_DEFAULTS`) требует ОБЯЗАТЕЛЬНОГО снепшота тела ПЕРЕД
   правкой (иначе ломается `every_default_template_has_a_known_legacy_defaults_entry` и апгрейд
   молча перестаёт доходить до необновлённых инсталляций) — следующий свободный номер: **v29**
   (`v28` уже занят снепшотом `report.html`, `_legacy_defaults` — общая для всех файлов сквозная
   нумерация, не отдельная на каждый файл). Отдельно — `demo_context_for_kind` в
   `template_service.rs` (превью редактора шаблонов, `UndefinedBehavior::Strict`) ОБЯЗАН получить
   тот же новый ключ, иначе `validate_preview_act_handover_returns_html_with_title_marker` и живой
   предпросмотр в TemplateEditor молча падают — это ровно ловушка из project memory

**Primary recommendation:** для каждой из четырёх находок — точечная правка по уже установленному
в кодовой базе паттерну (CASE WHEN, single-broadcast-after-loop, "value matches server suggestion"

## Находка 1 (NEW-1): undo акта воскрешает очищенные поля устройства

### Текущее состояние (подтверждено чтением)

`crates/trackly-infra/src/repos/devices_sqlite.rs:430-484`, метод
`SqliteDeviceRepository::restore_from_snapshot_in_tx`:

```rust
// Строки 449-453 — извлечение из snapshot схлопывает presence:
let state: Option<&str> = snapshot.get("state").and_then(|v| v.as_str());
let kit: Option<&str> = snapshot.get("kit").and_then(|v| v.as_str());
let name: Option<&str> = snapshot.get("name").and_then(|v| v.as_str());
let model: Option<&str> = snapshot.get("model").and_then(|v| v.as_str());
let serial_no: Option<&str> = snapshot.get("serial_no").and_then(|v| v.as_str());
let specs: Option<&str> = snapshot.get("specs").and_then(|v| v.as_str());

// Строки 458-478 — SQL:
"UPDATE devices SET \
   type_id          = COALESCE(?1, type_id), \
   name             = COALESCE(?2, name), \
   serial_number    = COALESCE(?3, serial_number), \
   model            = COALESCE(?4, model), \

`status_id` и `place_id` уже применяются БЕЗ COALESCE (прямая перезапись) — это осознанно
(комментарий над запросом: «BE-WR-06: inventory_number is deliberately NOT restored»,
`inventory_no`/`type_id` вообще не читаются из snapshot для перезаписи места/номера). Пять полей
из формулировки Success Criteria (`serial_number`, `model`, `condition`, `complectation`,
`notes`) — это РОВНО пять полей выше с `COALESCE`, привязанные к JSON-ключам
`serial_no`/`model`/`state`/`kit`/`specs` (имена столбцов и имена JSON-ключей расходятся —
`condition` столбец = `state` ключ, `complectation` столбец = `kit` ключ, `notes` столбец =
`specs` ключ — важно не перепутать при написании CASE WHEN).

**Единственный писатель snapshot-формата**, `device_snapshot_json`
(`crates/trackly-app/src/services/act_service.rs:3591-3606`), ВСЕГДА кладёт все 12 ключей через
`serde_json::json!({...})` с полями `DeviceRow` напрямую (`Option<String>` сериализуется как
строка ИЛИ явный JSON `null`, но КЛЮЧ никогда не опускается). То есть на практике (для любого
snapshot, записанного этой канонической функцией — а другого писателя в коде нет) ключ
физически ВСЕГДА присутствует; «поле отсутствует» — гипотетический случай для очень старых
`audit_log`-записей, предшествующих текущей форме этой функции (введена в Фазе 03-03,
`bfc700c9`, задолго до текущей 40-й фазы — в реальной эксплуатационной БД такого практически не
бывает, но код обязан деградировать безопасно на этот случай, как и сегодня).

### Эталон (уже закрыт Фазой 40.3, использовать буквально этот паттерн)

`devices_sqlite.rs:278-288` (`update_in_tx`) и `:704-714` (`update`, trait impl) — оба уже
переведены на:

```sql
serial_number    = CASE WHEN ?5 = 1 THEN ?6 ELSE serial_number END,
```

где `?5` — булев флаг `patch.serial_no.is_some() as i64` (источник — `Option<Option<String>>`
DTO/domain поле). **Важное отличие для NEW-1**: источник флага здесь не `Option<Option<T>>`
структуры, а присутствие JSON-ключа в `serde_json::Value`. Правильный флаг:

```rust
let state_present = snapshot.get("state").is_some(); // ключ есть (в т.ч. со значением null)
let state: Option<&str> = snapshot.get("state").and_then(|v| v.as_str()); // None и для null, и для отсутствия — используется ТОЛЬКО вместе с флагом
```//
Итоговый SQL — тот же CASE-паттерн, но с параметрами `(flag, value)` на пять полей вместо
`COALESCE`; `type_id`/`name` можно оставить как есть (`COALESCE`) — они не входят в Success
Criteria (не clearable-поля пользовательской формы, всегда непустые) и не упомянуты аудитом;
Claude's discretion — либо оставить `type_id`/`name` на `COALESCE` (минимальный по объёму фикс,
буквально соответствует формулировке SC1), либо перевести и их «за компанию» на тот же паттерн
для консистентности файла (как поступила Фаза 40.3 Plan 06 с `place_id`/`email` — «раз уж
трогаем файл»). Рекомендация: минимальный фикс (5 полей), т.к. `type_id`/`name` физически не
могут быть переданы как `null` ни одним текущим вызывающим (`DeviceRow.type_id: i64`,
`DeviceRow.name: String` — оба non-nullable в БД), поэтому расширение туда — работа без
измеримой пользы.

### Open Question — интерпретация «резурекции» из текста аудита (требует явного решения, не додумывать за пользователя)

Текст находки в `v1.4-MILESTONE-AUDIT.md` содержит формулировку «Пользователь чистит серийный №
(теперь реально пишется NULL) → undo акта → значение воскресает» — при разборе в этом
research-сеансе выявлено, что это МОЖЕТ описывать два разных сценария с разными
следствиями для объёма фикса:

1. **Симметричный double-Option баг** (то, что фикс выше решает полностью): snapshot был записан
   с `null` (поле было пустым В МОМЕНТ создания акта), пользователь позже (независимо от акта)
   ЗАПОЛНИЛ поле реальным значением, затем undo акта пытается вернуть его к пустому — сегодня
   не может (COALESCE(NULL, current) = current), CASE WHEN чинит это ровно.
2. **Восстановление легитимного исторического значения переживает независимую последующую
   правку** (фикс выше НЕ решает — и это НЕ обязательно баг): snapshot был записан с реальным
   значением «SN-12345» (поле было заполнено до акта), пользователь ПОСЛЕ акта (независимой
   правкой устройства, не связанной с актом) очистил поле до `null`, затем undo ЭТОГО акта
   восстанавливает «SN-12345» — snapshot-значение НЕ null в обоих случаях (COALESCE и CASE WHEN
   дают ОДИНАКОВЫЙ результат, когда значение не null), так что смена COALESCE→CASE НИКАК не
   меняет это поведение. Это следствие самой архитектуры «restore из полного snapshot конкретного
   акта» (см. doc-комментарий `restore_from_snapshot_in_tx`: «Дополнительные поля... применяются,
   если присутствуют») — сегодня документировано как НАМЕРЕННОЕ поведение, не баг.

**Рекомендация планировщику:** реализовать фикс №1 (CASE WHEN по presence, буквально совпадает с
формулировкой «эталон — те же два пути, закрытые в 40.3» и с SC1's «по тому же правилу»). Если
сценарий №2 тоже входит в объём (то есть undo НЕ должен трогать поля, изменённые НЕЗАВИСИМОЙ
правкой после акта, даже если snapshot несёт непустое значение) — это архитектурно другая задача
(нужно либо не восстанавливать эти 5 полей из undo вообще, как уже сделано для
`inventory_number`, либо сверяться с `audit_log`, было ли поле изменено ПОСЛЕ snapshot другой,
не-актовой мутацией) и заметно дороже. Регресс-тест должен явно проверить сценарий №1 (это
однозначно в объёме); сценарий №2 — обсудить на этапе `/gsd-discuss-phase` или явно
зафиксировать как discretion-решение планировщика с объяснением выбора в CONTEXT/PLAN.

### Как проверить

Существующий scaffold: `crates/trackly-app/tests/acts_undo.rs` — 5 тестов, все используют
хелпер `DeviceSnap`/`read_device_snap` (строки 120-144), который СЕГОДНЯ читает только
`status_id`/`place_id`/`condition`. Нужно расширить `DeviceSnap` до `serial_number`/`model`/
`complectation`/`notes` и добавить НОВЫЙ тест-кейс по образцу
`delete_handover_restores_devices_to_pre_handover` (строки 153-193), но с шагом «очистить поле
ПОСЛЕ handover, ДО undo» — сценарий №1 из Open Question выше:

1. Seed device с `serial_number = 'SN-INITIAL'`.
2. Create handover (snapshot captures `serial_no: null`... — ВАЖНО: для сценария №1 snapshot
   должен captured `null`, то есть поле должно быть ПУСТЫМ на момент создания акта, а
   заполненным — ПОСЛЕ. Порядок: seed с `serial_number = NULL` → create handover (snapshot.serial_no
   = null) → отдельный `devices.update` (или прямой SQL) записывает `serial_number = 'SN-LATER'`
   → `delete_soft` акта (undo) → assert `serial_number IS NULL` (было `COALESCE` = осталось
   `'SN-LATER'`, баг; стало `CASE WHEN` = `NULL`, фикс).
3. Аналогично зеркальный тест-кейс (значение НЕ теряется, если snapshot реально что-то нёс —

### Часть B — шторм `NumberSpaceChanged` (сервер)

**Текущее состояние:** `device_service.rs::import_csv_commit` вызывает
`self.create(new_device).await` (строка ~1211) для КАЖДОЙ успешной строки. `create()`
(строки 375-392) безусловно шлёт `broadcast_number_space_changed()` при
`new.inventory_no.is_some()`:

```rust
// device_service.rs:183-189
fn broadcast_number_space_changed(&self) {
    if let Some(ws_tx) = &self.ws_tx {
        let _ = ws_tx.send(WsEvent::NumberSpaceChanged {
            contexts: vec!["device_create".to_string(), "printer_create".to_string()],
        });
    }
}
```

Канал — `tokio::sync::broadcast::channel::<WsEvent>(128)` (`context.rs:214`) — ФИКСИРОВАННАЯ
ёмкость 128. Импорт 300 строк с номерами шлёт 300 событий; ЛЮБОЙ LAN-клиент, не успевший
вычитать канал за время импорта (реалистично — импорт может занять секунды на 100+ строк), ловит
`RecvError::Lagged`, теряя ВСЕ события за это окно — включая `NewRequest`/`PrinterAlert`,
которые делят с `NumberSpaceChanged` ОДИН канал.

**Эталон (уже реализован в этом же файле):** `bulk_create_with_printer`
(`device_service.rs:1532-1651`) вставляет `count` строк в ОДНОМ цикле внутри ОДНОЙ транзакции и
шлёт `broadcast_number_space_changed()` РОВНО ОДИН раз ПОСЛЕ цикла (строка 1650), если
`trimmed_nonempty.is_some()`. CSV-импорт не может буквально скопировать этот паттерн (каждая
строка — независимая транзакция с независимой обработкой ошибок, не групповая вставка с общим
`inventory_no`), но принцип «один broadcast после цикла, не внутри» переносится прямо.

**Рекомендация:** завести приватный метод без broadcast (например,
`create_without_broadcast(&self, new: DeviceNew) -> Result<DeviceSaveOutcome, AppError>` —
идентичен телу `create()` минус финальный `if number_set { self.broadcast_number_space_changed() }`),
`create()` становится тонкой обёрткой над ним + broadcast (аналогично тому, как `bulk_create` —
обёртка над `bulk_create_with_printer`). `import_csv_commit` вызывает
`create_without_broadcast` внутри цикла, копит локальный `any_number_set: bool` (true, если ХОТЯ
БЫ одна успешно вставленная строка имела непустой `inventory_no` — то есть ту же семантику, что
и сегодняшний per-row флаг, просто агрегированную), и делает ОДИН
`self.broadcast_number_space_changed()` после цикла, если `any_number_set`.

**Risk of regression (важно для плана):** проверить, что `PrinterCreateModal.svelte`'s legacy
create-путь (`create()`, оставшийся вызывающий помимо CSV-импорта — см. 40.3-RESEARCH.md) НЕ
пострадает — `create()` остаётся публичным с тем же broadcast-поведением, меняется только CSV
импорт, использующий новый внутренний метод напрямую.

### Как проверить

регистрацию автоматически после добавления строки в `MUTATING_COMPONENTS` + вызова

**Часть B:** новый тест в `crates/trackly-app/tests/devices_csv_import.rs` (файл существует,

  type_id: typeId,
  name: name.trim(),
  inventory_no: inventoryNo.trim() || null,   // ⚠️ не очищается при qty>1 сегодня
  serial_no: serialNo.trim() || null,

};

await devices.bulkCreate(newDevice, qty);
```

Сегодня эта ветка НИКОГДА не достигается с непустым `inventoryNo`, потому что `quantityDisabled`
уже блокирует «Количество» > 1 при ЛЮБОМ непустом номере. После ослабления `quantityDisabled`
(разрешить qty>1 при автоподставленном, не тронутом номере) эта строка ВПЕРВЫЕ сможет передать
непустой `inventory_no` в `bulkCreate` с `qty > 1`.

Бэкенд УЖЕ страхует от дублей: `bulk_create_with_printer`
(`device_service.rs:1560-1579`) жёстко отклоняет именно эту комбинацию:

```rust
if count > 1 {
    let inv_nonempty = new.inventory_no.as_deref().map(|s| !s.trim().is_empty()).unwrap_or(false);
    let ser_nonempty = new.serial_no.as_deref().map(|s| !s.trim().is_empty()).unwrap_or(false);
    if inv_nonempty || ser_nonempty {
        return Err(AppError::Validation {
            field: "count".to_string(),

```

Регрессионный тест уже существует и закрепляет это: `bulk_create_rejects_when_inventory_no_set`
(`crates/trackly-app/tests/devices_bulk_create.rs:99-136`). **Значит: дублирования номеров эта
находка допустить не может (бэкенд не даст) — но если фронт не очистит `inventoryNo` перед
сборкой `newDevice` для qty>1 пути, ПОЛЬЗОВАТЕЛЬ НЕМЕДЛЕННО получит эту серверную ошибку
валидации при каждой попытке массового создания с автоподставленным номером** — то есть
находка формально «починена» (Количество разблокировано), но реальный сценарий использования
(«ввести Количество > 1 и сохранить») продолжает падать, просто с другой, более
непонятной пользователю ошибкой. Фикс ОБЯЗАН включать явную очистку/обнуление `inventoryNo`
(программно, через `setValueProgrammatically`-подобный путь в дочернем компоненте, или просто
`newDevice.inventory_no = null` в самой `handleSubmit` для qty>1 ветки, не полагаясь на
`inventoryNo.trim()`) — второе (форсировать `null` в payload для bulk-ветки безусловно) проще и
безопаснее: количество ЛЮБОГО автоподставленного номера теряет смысл при массовом создании
(сервер не умеет присвоить РАЗНЫЕ номера N устройствам за один вызов), так что обнуление —
корректная семантика, а не костыль.

`serialNo`/`ipAddress` — обычные (не шаблонные) поля, авто-заполнения не имеют, их условия в
`quantityDisabled` трогать не нужно.

### Как проверить

**Клиент:** нет существующего теста на `quantityDisabled`-логику (Svelte runtime, project memory
`compile_gates_miss_svelte_runtime` — `svelte-check`/`eslint` этого не ловят). Manual-only
чек-поинт в `cargo tauri dev`: запомнить шаблон для «Новое устройство» → открыть попап → номер
автоподставлен → увеличить «Количество» до >1 → сохранить → N устройств созданы БЕЗ инвентарного
номера (не с дублирующимся). Затем: вручную стереть/изменить номер (сделать значение
НЕ совпадающим с предложением) → «Количество» снова заблокировано.

**Сервер:** регрессия не требуется (бэкенд-валидатор уже покрыт), но стоит явно прогнать
`cargo test -p trackly-app --test devices_bulk_create bulk_create_rejects_when_inventory_no_set`
на границе волны, чтобы подтвердить: guard остаётся на месте и не был случайно ослаблен при
любых сопутствующих правках `bulk_create_with_printer`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Различение «ключ отсутствует» vs «ключ = null» в `serde_json::Value` | Кастомный враппер над `Value::get` | `snapshot.get(key).is_some()` как флаг + `.and_then(as_str)` как значение — два вызова, не один | Ровно та же идея, что `serde_with::rust::double_option` решает для serde-derive границы (40.3), но здесь serde_json::Value уже НАТИВНО сохраняет presence на уровне `.get()` — не нужна вообще никакая доп. библиотека |

| Определение «поле автоподставлено vs введено вручную» | Новая эвристика на фронте (diff/timestamp/dirty-flag) | Существующий `isValueUnedited()`/`matchesLast`/`matchesAlt` в `NumberTemplateField.svelte`, уже прокидываемый наружу способом `onSelectedTemplateChange` | NUM-07 уже решил ровно эту задачу для стрелки ↑/↓ — переиспользовать, не изобретать параллельный компаратор |

**Key insight:** все четыре фикса — «доиспользовать существующий паттерн в третьем/четвёртом
месте», ни один не вводит новую абстракцию. Риск фазы не в сложности, а в том, чтобы НЕ
пропустить со-фиксы (demo-контекст, legacy-снепшот, очистка `inventoryNo` перед bulk), которые
не упомянуты в тексте аудита, но обнаруживаются прямым чтением вызывающего/тестового кода.

## Common Pitfalls

### Pitfall 1: presence-флаг для snapshot должен читаться из `serde_json::Value`, не из структуры

**Что идёт не так:** попытка скопировать буквальный код 40.3's CASE-WHEN-фикса (который берёт
флаг из `patch.field.is_some()` — `Option<Option<T>>` domain/DTO структуры) без адаптации под
то, что здесь источник — сырой `serde_json::Value`, а не типизированная структура.
**Как избежать:** `let x_present = snapshot.get("x").is_some();` — ОДИН явный вызов на поле,
отдельный от `.and_then(|v| v.as_str())`, который используется ТОЛЬКО для значения, не для флага.
**Предупреждающие знаки:** если регресс-тест (сценарий №1 из Open Question NEW-1) не проходит
после правки — вероятно, флаг всё ещё вычислен из `value.is_some()` (после `.and_then`), что
эквивалентно старому багу под новым именем переменной.

### Pitfall 2: `import_csv_commit`'s per-row `create()` вызов нельзя заменить на `bulk_create` целиком

**Что идёт не так:** соблазн «раз есть batch-паттерн в `bulk_create_with_printer` — просто
собрать все строки CSV в один вызов `bulk_create`» — не работает: `bulk_create` вставляет
`count` КОПИЙ ОДНОГО `DeviceNew` (одно имя, одно место, один номер) — CSV-строки все РАЗНЫЕ
(разные имена/места/номера per-row), и per-row ошибки (occupied-число, место не найдено)
обрабатываются НЕЗАВИСИМО, не как единая транзакция «всё или ничего».
**Как избежать:** сохранить per-row цикл с индивидуальной обработкой ошибок, только вынести
broadcast за пределы цикла через новый non-broadcasting внутренний метод.

### Pitfall 3: снепшот шаблона ДО правки, не после (иначе гейт `every_default_template_has_a_known_legacy_defaults_entry` не защищает существующие инсталляции)

**Что идёт не так:** отредактировать `act_handover.html` первым, затем «вспомнить» про снепшот и
скопировать УЖЕ ОТРЕДАКТИРОВАННОЕ содержимое в `_legacy_defaults/v29/` — снепшот в этом случае
бесполезен (совпадает с новым дефолтом, не с прежним), апгрейд для существующих инсталляций
остаётся сломанным, а тест на MISSING legacy entry по-прежнему проходит (структурно запись есть),
маскируя проблему.
**Как избежать:** Task 0 плана — `git show HEAD:crates/trackly-app/templates/act_handover.html`
(или просто скопировать файл ДО первой правки) → сохранить как `_legacy_defaults/v29/...` →
ТОЛЬКО ПОТОМ править активный файл.

### Pitfall 4: демо-контекст редактора шаблонов — забыть про него сломает ДРУГОЙ тест, не тот, что кажется очевидным

**Что идёт не так:** написать/прогнать только `render_pdf`-ориентированные тесты (реальные акты),
получить зелёный результат, посчитать NEW-2 закрытым — `demo_context_for_kind` живёт в
`template_service.rs` (другой сервис) и покрыт `validate_preview_act_handover_returns_html_with_title_marker`
— тест не упомянут ни в аудите, ни в ROADMAP, легко пропустить при беглом гит-грепе на
`act.number`.
**Как избежать:** явный grep `grep -rn '"number"' crates/trackly-app/src/services/template_service.rs`
на этапе Wave 0/планирования — этот файл ДОЛЖЕН попасть в список затрагиваемых.

## Open Questions

1. **NEW-1: восстанавливать ли undo непустые исторические значения, если поле было независимо
   изменено ПОСЛЕ акта (сценарий №2 из раздела «Находка 1»)?**
   - Что мы знаем: CASE WHEN по presence решает только «snapshot=null» сторону; «snapshot=реальное
     значение, но пользователь его позже стёр независимо от акта» — undo сегодня (и после
     минимального фикса) продолжит восстанавливать историческое значение.
   - Что неясно: входит ли это в объём Success Criteria («не воскрешает поля... которые
     пользователь очистил после создания акта») — буквальное прочтение говорит «да», но
     архитектурно это другая, более дорогая задача (см. раздел выше).
   - Рекомендация: минимальный фикс (presence-based CASE WHEN) в план по умолчанию; explicit
     discuss-вопрос или explicit discretion-решение планировщика с обоснованием — не оставлять
     молча нерешённым.

2. **N-3: DTO-довесок `affected_place_ids` — новое поле в `CsvImportReport` или отдельный
   HTTP/Tauri-вызов?**
   - Что мы знаем: backend уже знает `place_id` каждой успешной строки внутри цикла
     `import_csv_commit` — данных достаточно, вопрос только в способе доставки клиенту.
   - Рекомендация: новое поле в существующем DTO (`CsvImportReport.affected_place_ids: Vec<i64>`)
     — минимальный, аддитивный, специта-совместимый (нужно добавить `#[specta(type = ...)]`
     аннотацию по образцу соседних `u64`-полей файла, если специфика типа i64 vs u32 потребует
     этого — сверить с `inserted: #[specta(type = u32)] pub inserted: u64` двумя полями выше).

### Known Threat Patterns for стека

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| Потеря данных при undo/restore (NEW-1: молчаливое «не восстановилось» вместо ожидаемого поведения) | Tampering / Repudiation (пользователь думает, что undo вернул устройство «как было», а поле не изменилось) | Явное различение «ключ отсутствует»/«ключ = null» на SQL-слое — уже стандарт проекта для `update_in_tx`/`update` (40.3), NEW-1 доводит третий путь до того же стандарта |
| Broadcast-канал общего назначения, который один «шумный» клиент/операция может забить (N-3) | Denial of Service (локальный, для LAN-подписчиков WS) | Батчинг событий на уровне операции — не полагаться на неограниченную ёмкость `broadcast::channel`, эталон уже есть (`bulk_create_with_printer`) |
| Клиентская валидация (`quantityDisabled`), не подкреплённая на сервере (NEW-3) | Tampering (обход UI-инварианта прямым вызовом API) | Уже мимо этой находки — backend (`bulk_create_with_printer`) независимо валидирует `count>1 + inventory_no`, UI-фикс не ослабляет серверную гарантию, только чинит UX-путь к её достижению |
| Хрупкий парсинг форматированной строки вместо использования канонического значения (NEW-2: `display.find('в')`) | Tampering/Information Disclosure (в теории — неверно отрендеренный номер акта на юридически значимом документе) | Единый источник истины (`format_act_number` через `ActDto.number`) вместо повторного парсинга/реконструкции строки — тот же принцип, что уже закрыл N-1 в 40.3 (`ReturnModal.svelte`) на клиенте; NEW-2 закрывает симметричный случай на сервере |
