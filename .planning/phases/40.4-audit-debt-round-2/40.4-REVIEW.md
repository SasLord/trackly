# Phase 40.4: Code Review Report

**Reviewed:** 2026-09-26
**Depth:** standard
**Files Reviewed:** 16 source files (17 paths incl. the frozen snapshot)
**Status:** issues_found

## Summary

Phase 40.4 closes four audit-debt defects (NEW-1 presence-based undo restore, N-3 CSV-import
broadcast batching + place-tree invalidation, NEW-3 bulk-create-on-autofilled-number, NEW-2
canonical `act.number_display`). The backend halves are mostly sound:

- **NEW-1** is correct for all five clearable fields. I traced every writer of
  `audit_log.before_json` that `select_device_mutations_for_act` can select
  (`act_service.rs` lines 610, 961, 1160, 1725, 2264, 2318, 2406, 3555 — all go through
  `device_snapshot_json`, which emits every key unconditionally via `json!`), so
  presence is always `true` in practice and "key absent" (legacy rows) still degrades to
  keep-current. `type_id`/`name`/`status_id`/`inventory_number` semantics are undisturbed.
  `trackly-infra` type-checks clean.
- **NEW-2** snapshot `_legacy_defaults/v29/act_handover.html` is **byte-identical** to the
  pre-change active template (verified against `280349e8^`), and the v27→v29 chain has no
  gap (`git log` on `act_handover.html` shows 39.1-06 as the last prior edit). The
  strict-undefined demo context was patched; `act_handover.html` has exactly one context
  builder (`ActService::render_pdf`), so no other render path breaks.
- **N-3 server**: `create()` / `create_without_broadcast()` did not drift — the broadcast
  predicate moved from the pre-insert `new.inventory_no.is_some()` to the post-insert
  `dto.inventory_no.is_some()`, which is equivalent because the trim/empty-filter already
  ran. The single post-loop broadcast has no early-return path that can skip it.
- **specta annotations**: `affected_place_ids` is the only new `i64`-bearing DTO field and
  it carries `#[specta(type = Vec<i32>)]`; the regenerated `ui/src/bindings.ts` confirms
  `number[]`. No other new field is missing the annotation.

The two BLOCKERs are both on the **client** side and both are invisible to the project's own
gates: the Svelte `$effect` that was *not* updated for NEW-3 silently defeats the feature
NEW-3 shipped, and the CSV modal's dismiss path bypasses the place-tree invalidation that
N-3 added. Separately, the headline NEW-2 regression test is **vacuous** — it cannot fail on
the pre-fix template.

## Critical Issues

### CR-01: NEW-3 is silently defeated — the unchanged `quantity = 1` effect resets «Количество» on every programmatic autofill

**File:** `ui/src/features/devices/DeviceFormBody.svelte:335-340` (interacting with
`:309-314` and `ui/src/lib/components/NumberTemplateField.svelte:354-373`)

**Issue:**
`quantityDisabled` was correctly relaxed to `(inventoryNo.trim() !== '' && inventoryNoEditedByHand)`,
but this pre-existing effect was left untouched:

```js
// Reset quantity to 1 when inv/serial become non-empty.
$effect(() => {
  if (inventoryNo.trim() !== '' || serialNo.trim() !== '') {
    quantity = 1;
  }
});
```

Before NEW-3 this effect was harmless: `quantityDisabled` was already `true` for any
non-empty `inventoryNo`, so the user could never have a quantity > 1 to lose. After NEW-3
the quantity input is *enabled* while an autofilled number sits in the field, so every
**programmatic** change to `inventoryNo` now silently stomps the user's quantity back to 1.

Two reachable triggers:

1. **Mount-autofill race.** `autofillOnMount` defaults to `true` and
   `applyContextDefault()` is `await`-ed over two `apiCall`s
   (`number_template_contexts_get` → `number_templates_peek_next`). A user who types
   «Количество» = 5 before the suggestion lands (entirely normal on a LAN browser) has it
   reset to 1 the moment the number appears.
2. **Type switch with a quantity already set.** With quantity = 5 the user flips
   «Устройство»→«Принтер» via `DeviceFormModal`'s `titleExtra` ActionMenu (no remount —
   Discretion #8). `numberContext` changes → the effect at `NumberTemplateField.svelte:354`
   calls `applyContextDefault(ctx, preserveManualEdits=true, gen)` → `isValueUnedited()` is
   `true` (autofilled) → `setValueProgrammatically(dto.rendered)` → `inventoryNo` changes →
   quantity silently becomes 1. Note that `refreshCurrentSuggestion()` has an explicit
   `if (disabled) return;` guard (FE-CR-04) for exactly this class of problem, but
   `applyContextDefault()` has **no such guard**, so the disabled-field protection does not
   apply here.

Result: the user presses «Создать» and gets **1** device instead of N, with no error. This is
precisely the workflow NEW-3 was written to unblock.

**Fix:** gate the reset on the same "edited by hand" signal the new `quantityDisabled` uses,
so only a hand-typed number (or a serial number) forces quantity back to 1:

```js
// NEW-3: only a HAND-EDITED number may force quantity back to 1 — a
// programmatic autofill/re-peek must leave the user's «Количество» alone.
$effect(() => {
  if ((inventoryNo.trim() !== '' && inventoryNoEditedByHand) || serialNo.trim() !== '') {
    quantity = 1;
  }
});
```

Additionally add the missing `if (disabled) return;` guard to `applyContextDefault()` in
`NumberTemplateField.svelte` so a context switch never rewrites a field the user cannot see
or edit, matching `refreshCurrentSuggestion()`'s FE-CR-04 contract.

### CR-02: dismissing the CSV-import result screen skips the N-3 place-tree invalidation *and* the list refresh

**File:** `ui/src/features/devices/DeviceImportCsvModal.svelte:167-175`,
`ui/src/features/devices/DevicesPage.svelte:324-333`

**Issue:**
The new `placeIds` payload is only delivered on the `handleDone()` path, which is wired to
the single «Готово» button at step 4:

```js
function handleDone() {
  onImported(report?.affected_place_ids ?? []);   // invalidation happens here only
  resetState();
}

function handleClose() {
  onClose();                                      // DevicesPage: () => (csvModalOpen = false)
  resetState();
}
```

`<Modal ... onClose={handleClose}>` — and `Modal.svelte` invokes `onClose` on **Escape**
(line 178/183), **backdrop mousedown+mouseup** (line 197) and the **× button** (line 224).
All three are live on step 4, i.e. *after* `import_csv_commit` has already committed N rows.
Taking any of them leaves:

- the place-tree counters stale (`notifyPlaceContentChanged` never called — the exact hole
  N-3 was created to close),
- the device list and status counts stale (`refresh()`/`refreshCounts()` never called),
- no completion toast.

The INV-7 gate cannot see this: it only proves that the `onImported` prop's handler calls
`notifyPlaceContentChanged`, which it does. `node scripts/check-place-tree-invalidation.mjs`
passes (0 violations) with this hole open.

**Fix:** make dismissal after a successful commit take the same path as «Готово»:

```js
function handleClose() {
  // A committed import must invalidate/refresh even when the result screen is
  // dismissed with Escape / backdrop / × instead of «Готово» (step 4 only).
  if (report !== null) {
    onImported(report.affected_place_ids);
  } else {
    onClose();
  }
  resetState();
}
```

(`onImported` in `DevicesPage` already sets `csvModalOpen = false`, so the modal still
closes.) Consider also adding a `DIRECT_CALL_MARKERS`-style check, or an INV-7 rule that a
`MUTATING_COMPONENTS` entry's *other* exit props (`onClose`) cannot bypass the invalidating
handler once a mutation has landed.

## Warnings

### WR-01: the NEW-2 regression test is vacuous — it cannot fail on the pre-fix template

**File:** `crates/trackly-app/tests/html_act_render.rs:1421-1475`

**Issue:** `html_return_act_prints_number_display_with_suffix_not_lost` asserts
`html.contains(&return_act.number)` (e.g. `"1в"`). But `do_return` inserts the return act with
`number: parent.number` (`act_service.rs:1529` — «number = parent.number, повторяем»), so for
this fixture `number_raw == parent_number == "1"`. `compute_suffix_from_display("1в", "1")`
takes the `strip_prefix` branch and returns `"в"`, so the **old** template's
`{{ act.number }}{{ act.suffix }}` rendered `"1" + "в" = "1в"` — identical to
`number_display`. The test would pass unchanged against `_legacy_defaults/v29/act_handover.html`.
The doc-comment's claim that this proves the fix is not supported.

The scenario that actually diverges is: create handover №1 → return it (return row stores
`number = "1"`) → **edit the parent handover's number to "77"**. `update_act_header_in_tx`
is `WHERE id = ?10` with no propagation to children (`acts_sqlite.rs:403-405`), so the
return's `number_raw` stays `"1"` while the joined `parent_number` becomes `"77"`:
`display = "77в"` but old-template output = `"1" + "в" = "1в"`. That is the live defect, and
no test covers it (consistent with the still-open TODO captured in commit `13d26504`).

**Fix:** add a test that renumbers the parent after the return exists and asserts the
rendered HTML contains the new `return_act.number` and does **not** contain the stale
`format!("{}{}", return_act.number_raw, "в")`:

```rust
// after do_return, edit the parent's number, then re-read the return act
let reread = p.acts.get(return_act.id).await.expect("reread");
let html = p.acts.render_pdf(return_act.id).await.expect("render");
assert!(html.contains(&reread.number), "must print canonical display number");
assert!(!html.contains("№1в"), "must not print number_raw + suffix reconstruction");
```

### WR-02: `restore_from_snapshot_in_tx` doc-comment still documents the COALESCE semantics the phase removed

**File:** `crates/trackly-infra/src/repos/devices_sqlite.rs:417-421`

**Issue:** The doc-comment above the function still reads «Дополнительные поля (`name`,

```rust
/// `name`/`type_id` — COALESCE (не обнуляемые): отсутствие ключа ИЛИ null

/// `serial_no`/`model`/`state`/`kit`/`specs` — presence-based CASE WHEN
/// (NEW-1, фаза 40.4): ключ ОТСУТСТВУЕТ → сохранить текущее; ключ ЕСТЬ со
/// значением null → ОЧИСТИТЬ колонку.
```

### WR-03: `place_id` in the same function still collapses "key absent" and "key null" — the very bug NEW-1 fixed, six lines above it

**File:** `crates/trackly-infra/src/repos/devices_sqlite.rs:444` and `:483`

**Issue:**
```rust
let place_id: Option<i64> = snapshot.get("place_id").and_then(|v| v.as_i64());
...
place_id = ?14,     // unconditional write
```
A snapshot that lacks the `place_id` key entirely is indistinguishable from one carrying
`"place_id": null`, and both write `NULL` — i.e. undo *wipes the device's place*. Today
`device_snapshot_json` always emits the key so this is unreachable, but that is exactly the
assumption NEW-1 refused to rely on for the other five fields. Leaving the two halves of the
same function on opposite conventions invites the next partial-snapshot writer to silently
destroy `place_id`.

**Fix:** either apply the same presence gate (`place_id = CASE WHEN ?n = 1 THEN ?m ELSE place_id END`)
or make the key mandatory alongside `status_id`:

```rust
let place_id_present = snapshot.get("place_id").is_some();
if !place_id_present {
    return Err(AppError::Internal { source_chain:
        format!("undo: snapshot for device {device_id} lacks place_id") });
}
```

### WR-04: NEW-1 only proves 2 of the 5 clearable fields, and `#[allow(dead_code)]` permanently hides the gap

**File:** `crates/trackly-app/tests/acts_undo.rs:120-131`

**Issue:** `DeviceSnap` gained four fields, but grep shows `model` and `notes` are **never**
asserted anywhere in the file, and `condition` is only asserted for *restore-a-value*
(`Some("Новое")`, lines 181/202/266), never for the present-but-null *clearing* path. So the
NEW-1 change is proven for `serial_number` + `complectation` only; `model`, `notes` and the
clearing of `condition` are unproven. The blanket `#[allow(dead_code)]` on the whole struct
removes the one signal (an unused-field warning) that would have surfaced this, and will
keep hiding it for every field added in future.

**Fix:** extend the new test to set/clear all five columns in one pass (the snapshot already
carries all five keys, so one `UPDATE devices SET serial_number=…, model=…, condition=…,
complectation=…, notes=…` post-act edit plus five `assert_eq!(…, None)` after undo covers
it), then delete the `#[allow(dead_code)]` so the compiler keeps enforcing that every field
in the fixture is actually asserted.

### WR-05: `affected_place_ids` is returned in non-deterministic `HashSet` order

**File:** `crates/trackly-app/src/services/device_service.rs:1308`

**Issue:** `report.affected_place_ids = affected_place_ids.into_iter().collect();` —
`std::collections::HashSet` uses a per-process random `SipHash` seed, so the order of this
DTO field (and therefore of the JSON response and of every `ui/src/bindings.ts` consumer)
varies between runs. The existing convention in this codebase for the identical concept is
the opposite: `act_service::dedupe_place_ids` sorts explicitly and documents that sorting
«makes the response deterministic for tests/debugging». `import_commit_failed_row_place_not_in_affected_place_ids`
only compares a single-element vector, so the drift is currently invisible — the first test
that asserts two elements without sorting will flake.

**Fix:**
```rust
let mut affected: Vec<i64> = affected_place_ids.into_iter().collect();
affected.sort_unstable();
report.affected_place_ids = affected;
```

### WR-09: the new `onEditedByHandChange` effect can report a stale value — `clearedByUser` is a plain `let`, not `$state`

**File:** `ui/src/lib/components/NumberTemplateField.svelte:188, 197-203, 210-212`

**Issue:** The effect re-runs only on `value` / `lastSuggested` / `altSuggested`. The
`norm === ''` branch of `isValueUnedited()` returns `!clearedByUser`, and `clearedByUser`
(line 188) is a non-reactive `let`. `setValueProgrammatically('')` sets
`clearedByUser = false` and assigns `value = ''`; when `value` is *already* `''` Svelte 5's
primitive equality check means no update fires, so the effect never re-runs and the host
keeps the previous (`true`) `inventoryNoEditedByHand`. Reachable via: user clears the field
by hand → picks «Без шаблона» in «Вставка» (`clearSelection({ preserveManualEdits: false })`).
Currently benign because the host's `quantityDisabled` also requires a non-empty
`inventoryNo`, but the callback's published contract («вызывается реактивно при каждом
изменении этого результата в любую сторону») is not met.

**Fix:** make the flag reactive — `let clearedByUser = $state(false);` — so the effect tracks
it like every other input to `isValueUnedited()`.

### WR-11: the NEW-2 permanent gate is whitespace-exact and trivially bypassed

**File:** `crates/trackly-app/tests/html_act_render.rs:1486-1492`

**Issue:** `!ACT_HANDOVER_HTML.contains("{{ act.number }}{{ act.suffix")` matches one exact

### WR-12: `<title>` guards on `act.number` (raw) but prints `act.number_display`

**File:** `crates/trackly-app/templates/act_handover.html:95`

**Issue:**
```html
<title>Акт приема-передачи{% if act.number %} №{{ act.number_display }}{% endif %}</title>
```
The condition and the output now read different keys. `act.number` is `number_raw` (a free
TEXT value since NUM-14, so it can be empty), while `number_display` is the canonical
`ActDto.number`. A return act whose `number_raw` is empty but whose display number is
`«42в»` renders a title with no number, while the subtitle at line 219 prints it
unconditionally. The two places that print the number should be guarded by the same key
they print.

**Fix:** `{% if act.number_display %} №{{ act.number_display }}{% endif %}`.

### WR-13: user-customized `act_handover.html` files keep printing the wrong return-act number, with nothing detecting it

**File:** `crates/trackly-app/src/pdf/html_templates.rs:44-72` (mechanism),
`crates/trackly-app/src/services/act_service.rs:3163-3167` (context)

**Issue:** `upgrade_untouched_defaults_on_startup` only rewrites bodies that are
byte-identical to the current default or to a registered legacy default. Any install whose
`templates/act_handover.html` was hand-edited (the documented, supported workflow — the file
lives next to the exe precisely so users can edit it) keeps `{{ act.number }}{{ act.suffix }}`
and therefore keeps printing the wrong number for the divergent-parent case in WR-01. The
`TemplateEditor` variable description was updated («сырое значение, без суффикса»), which
helps, but nothing detects an affected file or tells the user to switch.

**Fix:** at startup, when a `act_handover.html` is classified as user-customized *and* still
contains the raw+suffix concatenation, emit a `tracing::warn!` (and/or surface a one-line
notice in the Templates settings screen) pointing at `act.number_display`. A silent
"your printed return acts are wrong" state is not acceptable for a printed legal document.

### WR-14: the test-only `auto_map` helper is a divergent duplicate of the UI's `autoMapHeaders`

**File:** `crates/trackly-app/tests/devices_csv_import.rs:681-711` vs
`ui/src/features/devices/DeviceImportCsvModal.svelte:53-94`

**Issue:** The two mapping tables disagree. The Rust helper accepts
`"Расположение" | "Местоположение" | "Место" | "location" | "place"`; the UI accepts only
`"Место" | "место" | "Place" | "place"`. The new
`import_commit_collects_affected_place_ids` / `import_commit_failed_row_place_not_in_affected_place_ids`
tests use the header `Расположение`, which the real import modal would leave **unmapped** —
so the tests exercise a mapping the product does not auto-produce. Conversely the UI accepts
lowercase `место` and `Place`, which the tests do not. This is the same JS-mirrors-Rust
divergence class the project already has a gate discipline for.

**Fix:** either drive both from one shared fixture (a JSON list of header→field aliases
consumed by the Rust test and validated against the Svelte table by a `check-*.mjs` gate), or
at minimum align the two alias sets and switch the new tests to a header the UI actually
auto-maps (`Место`).
