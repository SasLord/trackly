# Deferred items — Phase 40.4 (audit-debt-round-2)

## NEW-1 сценарий 2 — undo может воскресить историческое значение, изменённое НЕЗАВИСИМО от акта

**Найдено во время:** планирования 40.4 (`40.4-RESEARCH.md`, «Находка 1 (NEW-1)» → Open Question),
на основе явного решения пользователя D-01 (зафиксировано в `<locked_decisions>` планирования).

**Вне объёма Фазы 40.4 — решение пользователя, не находка планировщика.**

Текст находки аудита («Пользователь чистит серийный № → undo акта → значение воскресает») имел
две возможные интерпретации:

1. **Сценарий 1 (в объёме Фазы 40.4, закрыт планом 40.4-01):** snapshot акта нёс `null` (поле
   было пустым НА МОМЕНТ создания акта), пользователь ПОСЛЕ акта заполнил поле реальным
   значением, затем undo акта пытается вернуть поле к пустому — сегодня не может
   (`COALESCE(NULL, current) = current`), потому что `restore_from_snapshot_in_tx` не отличает
   «ключ в JSON отсутствует» от «ключ есть, значение `null`». Presence-based `CASE WHEN`
   (буквально по эталону `update_in_tx`, Фаза 40.3) чинит это ровно.

2. **Сценарий 2 (НЕ в объёме, решение D-01):** snapshot нёс РЕАЛЬНОЕ значение (поле было заполнено
   ДО акта), пользователь ПОСЛЕ акта очистил поле НЕЗАВИСИМОЙ правкой устройства (никак не
   связанной с актом), затем undo ЭТОГО акта восстанавливает историческое значение из snapshot —
   snapshot-значение не `null` в обоих случаях, поэтому `COALESCE` и `CASE WHEN` дают ОДИНАКОВЫЙ
   результат (никакой фикс на уровне presence-флага это не меняет). Это прямое следствие самой
   архитектуры «restore из полного snapshot конкретного акта» — существующий doc-комментарий
   `restore_from_snapshot_in_tx` уже документирует это как НАМЕРЕННОЕ поведение, не баг.

**Почему это не «просто расширить фикс»:** закрытие сценария 2 требует либо (а) вообще не
восстанавливать эти 5 полей из undo (как уже сделано для `inventory_number`, BE-WR-06), теряя
часть ценности undo как «отменить акт полностью», либо (б) сверяться с `audit_log`, было ли поле
изменено ПОСЛЕ snapshot какой-то другой, НЕ-актовой мутацией, и восстанавливать выборочно —
архитектурно другая, заметно более дорогая задача (не «доиспользовать существующий паттерн в
N-й раз», а новая логика сверки с историей мутаций).

**Пользовательское решение (D-01, зафиксировано при планировании 40.4):** в объём Фазы 40.4 —
только сценарий 1. Сценарий 2 переносится долгом дальше, не переоткрывается в рамках этой фазы.

**При будущем закрытии:** нужно решить между вариантом (а) (симметрично `inventory_number`,
дёшево, но undo перестаёт восстанавливать эти поля вообще в любом случае независимой правки) и
вариантом (б) (сверка с `audit_log`, дороже, но точнее следует духу «undo = отменить именно этот
акт»). Регресс-тест на сценарий 1 (Фаза 40.4, план 01) должен остаться зелёным при любом выборе.
