<objective>
Закрыть серверную половину N-3: `device_service.rs::import_csv_commit` вызывает `self.create(...)`
для КАЖДОЙ успешно вставленной CSV-строки, а `create()` безусловно шлёт
`WsEvent::NumberSpaceChanged` при непустом `inventory_no` — импорт 100+ строк с номерами шлёт
столько же событий в `broadcast::channel::<WsEvent>(128)` фиксированной ёмкости, рискуя
`RecvError::Lagged` у любого LAN-клиента, не успевшего вычитать канал: теряются ВСЕ события за
это окно, включая `NewRequest`/`PrinterAlert`, делящие тот же канал. Эталон уже есть в этом же
файле — `bulk_create_with_printer` шлёт broadcast РОВНО ОДИН раз ПОСЛЕ цикла вставки, не внутри.

Одновременно закрывается DTO-часть N-3 (данные для клиентской инвалидации дерева мест, реализуемой
отдельным планом 40.4-03): `CsvImportReport` сегодня не несёт `place_id` успешно вставленных строк
— backend уже знает эти `place_id` внутри цикла `import_csv_commit`, не хватает только поля для
передачи клиенту. Per D-03 (локальное решение пользователя): новое АДДИТИВНОЕ поле
`affected_place_ids: Vec&lt;i64&gt;` в существующем `CsvImportReport`, а не отдельный вызов.

Pitfall (из RESEARCH, НЕ повторять): `import_csv_commit`'s per-row цикл НЕЛЬЗЯ заменить единым
вызовом `bulk_create` — тот вставляет `count` КОПИЙ ОДНОГО `DeviceNew` (одинаковое имя/место/номер),
CSV-строки все РАЗНЫЕ, а per-row ошибки (занятый номер, место не найдено) обрабатываются
независимо, не как единая транзакция «всё или ничего». Per-row цикл сохраняется, выносится ТОЛЬКО
broadcast.

Purpose: массовый импорт устройств из CSV не должен «глушить» соседние WS-уведомления у LAN-клиентов
и должен давать клиенту достаточно данных для точечной инвалидации дерева мест без перехода на
другой экран.
Output: `CsvImportReport.affected_place_ids`; `DeviceService::create_without_broadcast` +
батчированный broadcast в `import_csv_commit`; два новых интеграционных теста.
</objective>
