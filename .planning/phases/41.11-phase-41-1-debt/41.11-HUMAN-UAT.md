# Фаза 41.11: живая проверка трёх пунктов

## Правила этого документа (читать первым)

1. **Пункты отмечает ТОЛЬКО пользователь, и только после того, как запустил приложение и сам выполнил шаги.** Одобрение, пересказанное агентом или оркестратором («пользователь сказал, что всё хорошо»), не принимается. Пункт без запуска приложения считается непройденным.
2. Под каждым пунктом одна строка результата. Допустимы ровно две формы: `result: passed` (после неё можно дописать комментарий) и `result: issue — описание`. Исходное значение `[pending]` заменяется целиком.
3. Если что-то не совпало с «Ожидается», не правьте шаги и не подгоняйте условие: запишите `result: issue — что именно увидели` и напишите, на каком транспорте (десктоп или LAN-браузер) и в какой теме.
4. План 12 читает эти строки машинно: в документе должно остаться ровно три строки результата, и пока хотя бы одна из них `[pending]` или `issue`, волна 4 не стартует. Не добавляйте других строк, начинающихся с этого слова, и не переносите примеры форматов в начало строки.
5. В описании дефекта не пишите реальные названия организации, ФИО, реквизиты и содержимое рабочей БД. Репозиторий публичный. Достаточно «ФИО обрезалось», «в строке такого-то места».
6. Все данные в шагах вымышленные («Тестовая деталь 1», «Тестовый монитор», «Кабинет 1»). Заведите их сами в пустой или тестовой БД.
7. Если по итогам проверки потребуется правка кода, пункт AR-25 (план 12) нужно будет выполнить заново после неё.

Подготовка, общая для пунктов 1 и 2: проверки в LAN-браузере идут против `ui/dist`, а не против HMR-бандла `cargo tauri dev`. После любых правок интерфейса выполните `pnpm --dir ui build`; если браузер всё ещё показывает старый интерфейс, перезапустите приложение и обновите вкладку с очисткой кеша.

### 1. AR-23 (критерий успеха №4 ROADMAP): сбой между созданием детали и добавлением в состав группы

Что проверяется: «Создать деталь» в записи разбора делает ДВА вызова подряд: сначала создаёт устройство, затем добавляет его в состав группы. Атомарной операции нет намеренно. Если второй вызов упал, деталь уже существует и лежит в месте группы; интерфейс обязан честно это сказать и не оставить устаревших счётчиков.

Почему не «остановить сервер»: создание устройства завершается внутри модалки, после чего обработчик без паузы идёт ко второму вызову. Остановка сервера уронила бы уже ПЕРВЫЙ вызов (создание), то есть AR-23 не проверила бы. Поэтому второй вызов блокируется точечно, средствами DevTools браузера, а код продукта не меняется.

**Подготовка (по шагам):**

1. Выполните `pnpm --dir ui build`, чтобы LAN-браузеру отдавался актуальный `ui/dist`.
2. В приложении откройте «Настройки» -> вкладка «Сеть» -> раздел «Серверный режим». Если статус «Остановлен», нажмите «Запустить сервер». Порт по умолчанию 8443; «Bind-адрес» `0.0.0.0 (все интерфейсы)` нужен для доступа с другой машины, `127.0.0.1 (только localhost)` годится, если браузер на этой же машине.
3. В браузере (нужен Chromium-семейство: Chrome, Edge) откройте адрес сервера, например `https://localhost:8443`. Самоподписанный сертификат принять («Дополнительно» -> «Перейти на сайт»). Войдите под учётной записью администратора.
4. Условие, при котором дефект воспроизводим. Раздел «Группы». Нужна запись с типом с поведением «Разбор» (в форме типа поле «Поведение», значение «Разбор»; у таких групп в таблице состава есть кнопка «Создать деталь», у остальных её нет). Если такого типа нет, создайте тип с поведением «Разбор», затем «Создать группу» этого типа с названием вроде «Тестовый разбор 1». У записи должно быть место, например «Кабинет 1» (для записи, созданной от устройства, место берётся у устройства).
5. Откройте карточку этой записи. Запомните два числа: сколько устройств в таблице состава и какое число показано у места «Кабинет 1» в дереве раздела «Места» (счётчик содержимого).
6. В браузере откройте DevTools (F12) -> вкладка «Network». Откройте панель «Network request blocking»: правый клик по любому запросу -> «Block request URL» либо Ctrl+Shift+P / Cmd+Shift+P -> «Show Network request blocking». Добавьте шаблон `*groups_add_devices*` и убедитесь, что блокировка включена (галочка стоит, а в списке запросов блокируемый запрос будет показан красным).

**Действие:** в таблице состава нажмите «Создать деталь», заполните форму (наименование «Тестовая деталь 1», остальные обязательные поля любые вымышленные), сохраните.

**Ожидается (наблюдаемое, все шесть утверждений):**

1. Появляется тост-ошибка, в тексте которого названо созданное устройство: «Устройство «Тестовая деталь 1» создано, но не добавлено в запись разбора: …причина…. Добавьте его вручную через поиск в составе.» Причина будет технической, скорее всего `Failed to fetch`; английская подстрока здесь ожидаема и дефектом не считается.
2. Устройство «Тестовая деталь 1» существует: оно видно в разделе «Устройства» и в дереве «Места» в месте «Кабинет 1».
3. Счётчик места «Кабинет 1» увеличился ровно на 1 (инвалидация стоит до второго вызова, поэтому сбой второго её не отменяет).
4. В таблице состава группы «Тестовая деталь 1» НЕТ, число строк состава не изменилось относительно шага 5.
5. Страница не упала и не зависла; состав группы перечитан (нет вечной «Загрузки…»), остальные строки состава на месте.
6. Снимите блокировку (выключите шаблон `*groups_add_devices*` в «Network request blocking») и добавьте «Тестовая деталь 1» через поиск в таблице состава. Она добавляется, дубликата устройства «Тестовая деталь 1» в «Устройствах» нет, счётчик места не ушёл в двойной учёт.

**Если не совпало:** запишите, какое из шести утверждений нарушено (например, «тост не называет устройство» или «счётчик места не изменился»), и скопируйте текст тоста без реальных данных.

### 2. CR-02 (критерий успеха №1 ROADMAP): правка ребёнка раскрытой свёртки видна без перезагрузки страницы

Что проверяется: в раскрытой свёртке одинаковых устройств строки детей кешируются. После правки одного из них кеш обязан обновиться сам (поколение списка `listGen`), без перезагрузки страницы. Сборка, `svelte-check` и `eslint` рантайм рун не видят, поэтому это доказывается только в запущенном приложении.

**Подготовка (условие, при котором дефект воспроизводим):**

1. Раздел «Устройства», вкладка «Все». Включите флажок «Свернуть одинаковые».
2. Создайте не менее трёх устройств с ОДИНАКОВЫМИ типом и наименованием («Тестовый монитор») и РАЗНЫМИ серийными номерами и инвентарными номерами; поле «Состояние» у части «Б/У», у части другое. Так они сложатся в одну строку-свёртку со счётчиком.
3. Раскройте свёртку: шеврон слева в строке-группе (или двойной клик по ней). Под ней должны показаться отдельные строки детей.
4. Правьте только те поля, которые НЕ входят в ключ группировки, иначе ребёнок законно уйдёт из свёртки и вы не отличите это от дефекта. Вне ключа: «Состояние», «Статус», «Место», «Серийный №», «Инвентарный №». Наименование и тип входят в ключ; «Модель» в части режимов тоже входит в ключ, поэтому её правьте последней (см. ниже, это отдельная проверка).

**Действие:** у ребёнка в раскрытой свёртке откройте меню строки (кебаб справа, правый клик или двойной клик) -> «Редактировать». По очереди, с сохранением после каждого, измените: «Состояние», «Статус» (например, на «В ремонте»), «Место», «Серийный №», «Инвентарный №». Затем:

- смените «Наименование» у одного ребёнка на «Тестовый монитор Б»;
- удалите одного ребёнка через меню строки.

**Ожидается:**

1. После КАЖДОГО сохранения новое значение видно в строке этого ребёнка сразу, без перезагрузки страницы (F5/Cmd+R не нажимать). Допустима короткая задержка на один запрос; старое значение не «залипает», строка не остаётся в «Загрузке…».
2. Строка-свёртка остаётся раскрытой, остальные дети не пропали и не перемешались.
3. Ребёнок, у которого сменили наименование («Тестовый монитор Б»), исчез из раскрытого состава этой свёртки (он законно ушёл в другую группу) и счётчик свёртки уменьшился.
4. После удаления ребёнка он пропал из раскрытого состава, счётчик свёртки уменьшился.
5. В консоли DevTools (в LAN-браузере F12 -> «Console»; в десктопе правый клик -> «Inspect» в режиме `cargo tauri dev`) нет ошибки `effect_update_depth_exceeded`.
6. Всё то же повторено на втором транспорте: сначала десктоп (`cargo tauri dev`, HMR отдаёт актуальный код), затем LAN-браузер после `pnpm --dir ui build`.

**Если не совпало:** запишите, какое именно поле после сохранения осталось старым и на каком транспорте. Это и есть воспроизведённый CR-02.

### 3. CR-01 / D-16 / D-29 / D-33 / D-34: различимость шести чипов статуса в двух темах

Что проверяется: после правки токенов цвета (D-29) пара «ожидающий / действующий» по цвету почти не различается (контраст 4.62 против 4.62: цвет пару НЕ различает), поэтому единственный постоянный признак различия это тонкая рамка (D-16) у приглушённых чипов. Суждение «видна ли рамка и читается ли пара» делается глазом, в запущенном приложении (синтетический харнесс не заменяет WKWebView/WebView2).

Шесть статусов, как они называются в интерфейсе: «На складе», «В работе», «Ожидает ремонта», «В ремонте», «На списание», «Списано». Приглушённые (с рамкой): «Ожидает ремонта» и «На списание». Активные (без рамки): «В ремонте» и «Списано».

**Подготовка:**

1. Приложение с актуальным UI: десктоп `cargo tauri dev` или LAN-браузер после `pnpm --dir ui build`.
2. Заведите вымышленные устройства так, чтобы был хотя бы один в КАЖДОМ из шести статусов (статус выбирается в форме устройства, поле «Статус»). Нужный статус проще всего выставить через меню строки -> «Редактировать».
3. Нужны шесть фонов, на которых чип должен читаться: обычная строка, строка под курсором (наведите мышь), строка-свёртка (включите «Свернуть одинаковые» в «Устройствах» и сделайте так, чтобы в свёртку попали несколько устройств; чипы статуса показываются и в раскрытых детях). Гейт контраста считает шесть токенов фона (`--tr-bg`, `--tr-surface`, `--tr-surface-raised`, `--tr-surface-sunken`, `--tr-row-hover`, `--tr-group`); глазом достаточно пройти три вида строк выше плюс те места, где чип лежит на поверхности другого уровня (карточка, модалка, панель), если такие встретятся.
4. Переключатель темы («Светлая» / «Системная» / «Тёмная») находится в боковой панели. Пройдите весь список ниже в обеих темах, «Системную» отдельно не проверяйте.

**Действие:** откройте «Устройства», «Места» и те экраны с чипами статуса, до которых дотягиваетесь (дашборд, «Отчёты»), в светлой теме, затем в тёмной. Смотрите на все шесть чипов на всех трёх видах строк.

**Ожидается:**

1. Пары «Ожидает ремонта» / «В ремонте» и «На списание» / «Списано» различимы НЕ только оттенком: у «Ожидает ремонта» и «На списание» видна тонкая рамка по контуру чипа, у «В ремонте» и «Списано» рамки нет.
2. Текст каждого из шести чипов читается на всех трёх видах строк (обычная, под курсором, свёртка) в обеих темах.
3. Рамка не увеличивает чип: высота строк таблицы одинакова у чипов с рамкой и без, строки при наведении не «прыгают».
4. Цвета текста «В ремонте», «Ожидает ремонта», «Списано», «На списание» и «зелёных» статусов (токен `--tr-success-text` затемнён по D-33) после правки токенов остаются узнаваемыми (предупреждающий остаётся янтарным, опасный красным, а не серым или коричневым до неразличимости).
5. D-34, режим forced-colors. В Chromium-браузере (LAN) откройте DevTools -> три точки -> «More tools» -> «Rendering» -> «Emulate CSS media feature forced-colors» = `active` (на Windows то же даёт включённая высокая контрастность).
