## Summary

Ревью изменений фазы 40.5 (`git diff c7f5726e..HEAD`). Ядро фазы сделано корректно:

- Формула `format_act_number` действительно стала чистой функцией от `(act_type, sub_number, parent_number)`; ветка «единственный возврат теряет цифру» удалена; параметр `sibling_return_count` вычищен из домена, порта, репозитория и всех трёх вызовов формулы (компилятор подтверждает — `cargo check --tests` зелёный).
- **D-16 проверен вручную и сходится:** после удаления коррелированного подзапроса `SELECT_ACTS` отдаёт ровно 19 колонок (0..18), `from_row` читает `handover_date_utc` = 17, `place_path_snapshot` = 18. Единственный маппер — `from_row`; все 5 мест использования `SELECT_ACTS` (включая CTE-вариант на `acts_sqlite.rs:297`) идут через него. Второго `from_row`-подобного места со старыми индексами нет. Добавленный юнит-тест проверяет ЗНАЧЕНИЯ (`now - 3_600`, непустой snapshot), а не только отсутствие паники — это правильный способ поймать сдвиг индексов.
- **Конкурентность:** `next_sub_number_for_parent` + `insert_act_in_tx` живут в одной транзакции одного `WriterHandle` (`writer_worker.rs:57-60` — один `Connection`, jobs сериализуются через `mpsc`), поэтому окно между вычислением и вставкой закрыто структурно. Пути, где два возврата получили бы один `sub_number`, я не нашёл: `next_sub_number_for_parent` имеет ровно один вызов.
- `smallest_free` алгоритмически корректен, включая устойчивость к дублям и неположительным значениям (хотя тестами эти случаи не покрыты).
- **Приватность: чисто.** Во всём дифе `crates/` добавлены только вымышленные ФИО («Иванов И.И.», «Петров П.П.») и обезличенные пути мест; реквизитов организации нет.

Ключевые претензии — не к формуле, а к её обвязке: одна ветка проверки коллизий стала мёртвой с вводящим в заблуждение обоснованием, новый аллокатор «наименьшего свободного» создаёт тупик, из которого пользователь не выходит сам, док-комментарий утверждает гарантию (`BEGIN IMMEDIATE`), которой в коде нет, и три из добавленных «анти-вакуумных» тестов вакуумны — то есть ровно тот дефект, от которого D-14 и память `vacuous_test_fixture_must_diverge` предостерегали.

## Warnings

### WR-01: Проверка коллизии в ветке удаления возврата стала мёртвой, обоснование в комментарии неверно

**File:** `crates/trackly-app/src/services/act_service.rs:2963-2969`

**Issue:** После D-01 отображаемый номер живого возврата не зависит от соседей. Значит, при soft-delete возврата множество отображаемых номеров семьи только СОКРАЩАЕТСЯ: `own` теряет один элемент, остальные не меняются, `others` (чужие семьи) не трогается вовсе. Следовательно `ensure_act_family_display_free_in_tx(&tx, parent_id)` в этой ветке не может обнаружить НОВУЮ коллизию — он может сработать только на коллизии, которая существовала ДО удаления.

Комментарий («the post-check guards the family against a collision with an unrelated act») называет причину, которая к пути удаления не относится: новых номеров тут не появляется. D-03 требовал: «Если какая-то точка требует параметра по ДРУГОЙ причине — план обязан назвать эту причину явно». Здесь причина названа, но она ложная.

Два практических следствия:
1. Полное сканирование всех живых актов (`fetch_candidate_rows` без фильтров) на каждом удалении возврата — работа без результата.
2. Если БД уже находится в конфликтном состоянии (legacy-строки, прямые UPDATE'ы номера в обход каскада — сценарий, который сам проект воспроизводит в `html_act_render.rs:1550-1560`), удаление возврата упадёт с `Conflict` и пользователь не сможет почистить именно то состояние, которое надо почистить.

**Fix:** Убрать вызов из ветки `ActType::Return` в `delete_soft` — оставить только `recompute_parent_archived`:

```rust
if let Some(parent_id) = act.parent_act_id {
    // Phase 40.5 (D-01): displays of the remaining live returns do not
    // change when a sibling disappears, and `others` is untouched — a
    // delete can never CREATE a collision, so no post-check here.
    recompute_parent_archived(&tx, parent_id, now)?;
}
```

Если вызов сохраняется сознательно (например, как детектор уже-сломанной БД), это надо написать в комментарии буквально и добавить тест, доказывающий, что он что-то ловит.

### WR-02: «Наименьший свободный» никогда не перешагивает занятый номер → handover может стать невозвратимым навсегда

**File:** `crates/trackly-infra/src/repos/acts_sqlite.rs:446-478`, `crates/trackly-app/src/services/act_service.rs:1513, 1571`

**Issue:** `next_sub_number_for_parent` смотрит только на живых детей родителя и ничего не знает о пространстве ОТОБРАЖАЕМЫХ номеров, по которому потом судит `ensure_act_family_display_free_in_tx`. Аллокатор детерминирован: если позиция `k` свободна среди возвратов, он будет предлагать `k` бесконечно.

Сценарий (он же — часть A теста `display_number_space_covers_returns_in_both_directions`, `acts_numbering.rs:470-494`): существует акт передачи #42 без возвратов; пользователь создаёт отдельный handover с номером «42в1» — это разрешено и молча проходит. Теперь ЛЮБАЯ попытка возврата по #42 получает `sub_number = 1`, даёт display «42в1», ловит `Conflict` и откатывается. Акт #42 становится невозвратимым полностью, без пути выхода изнутри сценария возврата — пользователю нужно догадаться переименовать один из двух актов.

До фазы поведение было мягче: первый возврат показывал «42в» и проходил, конфликт возникал только на втором; и `MAX+1` со временем перешагивал занятую позицию. «Наименьший свободный» эту способность убрал — теперь дырка, совпавшая с чужим номером, блокирует семью навсегда.

Это **не** то, что вынесено в бэклог 999.2: там речь о превентивном предупреждении на маску. Здесь речь о том, что даже после предупреждения у пользователя нет выхода со стороны возврата, а сообщение об ошибке (`act_service.rs:3468-3473`) называет только свой номер («Акт №42в1 уже существует»), но не называет блокирующий акт.

**Fix:** Минимальный вариант — сделать аллокатор осведомлённым о занятости отображаемого номера, т.е. пропускать позиции, чей `{parent}в{k}` уже занят чужим живым актом:

```rust
// act_service.rs, do_return — вместо безусловного next_sub_number_for_parent
let mut sub_number = next_sub_number_for_parent(&tx, act_id)?;
while display_taken_by_other_family_in_tx(&tx, act_id, &parent.number, sub_number)? {
    sub_number += 1;
}
```

Это не нарушает D-05/D-06 (плотность и переиспользование сохраняются; пропуск происходит только там, где номер реально занят). Альтернатива дешевле — оставить поведение, но в сообщении `ensure_act_family_display_free_in_tx` назвать конфликтующий акт (`hit`-строка из `others`, а не из `own`), чтобы пользователь знал, что именно переименовать. Любой из вариантов должен быть покрыт тестом «после конфликта возврат становится возможен».

### WR-03: Новый док-комментарий утверждает гарантии, которых в коде нет (`BEGIN IMMEDIATE`, «структурный backstop»)

**File:** `crates/trackly-infra/src/repos/acts_sqlite.rs:441-445`

**Issue:** Комментарий гласит: «Single-writer + `BEGIN IMMEDIATE` — единственная защита от гонки, плюс `idx_acts_number_sub_unique` как структурный backstop». Оба утверждения неточны:

1. **`BEGIN IMMEDIATE` нигде не выставляется.** Все писательские транзакции открываются через `conn.transaction()` (`act_service.rs:388, 827, 1419, 1900, 2859`), а это в rusqlite `TransactionBehavior::Deferred`. Такого же необоснованного утверждения полны модульные док-комментарии сервисов (`act_service.rs:9` и др.) — но фаза 40.5 его тиражирует заново, в самом чувствительном к гонкам месте.
2. **Индекс не является backstop'ом для инварианта «уникальный `sub_number` внутри родителя».** `idx_acts_number_sub_unique` — это `UNIQUE(number, COALESCE(sub_number, 0)) WHERE deleted_at_utc IS NULL` (`migrations/V042__acts_number_text.sql:113-115`), то есть по `number`, а не по `parent_act_id`. Он закрывает нужный инвариант только при дополнительном условии «каждый живой возврат хранит КОПИЮ номера родителя», а это условие поддерживается исключительно каскадом переименования в сервисе (`act_service.rs:1229-1235`) и ломается при прямом UPDATE родителя (сценарий, который проект сам воспроизводит в `html_act_render.rs`). Добавленный тест `unique_index_rejects_duplicate_number_sub_number_pair` доказывает ровно то, что написано в его имени — уникальность пары `(number, sub_number)`, а не уникальность `sub_number` внутри родителя.

Функционально гонки нет (единственный writer действительно сериализует джобы), но комментарий — это контракт: следующий, кто добавит второй writer или второй путь записи, поверит несуществующей гарантии.

**Fix:**

```rust
/// ... Единственная защита от гонки — single-writer worker
/// (`db::writer_worker`: один `Connection`, джобы сериализуются через mpsc);
/// транзакции открываются как DEFERRED, `BEGIN IMMEDIATE` НЕ используется.
/// `idx_acts_number_sub_unique` — это UNIQUE(number, COALESCE(sub_number,0)),
/// то есть он закрывает уникальность sub_number внутри родителя лишь пока
/// каждый живой возврат хранит копию номера родителя (инвариант каскада
/// переименования, `act_service.rs`), и НЕ является независимым backstop'ом.
```

### WR-04: Три «анти-вакуумных» теста вакуумны — сравнивают чистую функцию с собой

**File:** `crates/trackly-app/src/dto/act.rs:580-593`, `crates/trackly-app/tests/acts_display_rule.rs:42-54`, `crates/trackly-app/src/services/act_service.rs:3536-3546`

**Issue:** D-14 требовал тест, который ПАДАЕТ на старой формуле и проходит на новой, и указывал инвертировать существующие якоря (`format_retroactive_promotion`). Инверсия выполнена так, что якорь потерял содержание:

```rust
let a = format_act_number(ActType::Return, "999", Some(1), Some("42"));
let b = format_act_number(ActType::Return, "999", Some(1), Some("42"));
assert_eq!(a, "42в1");
assert_eq!(a, b, "формула не должна зависеть от количества соседей");
```

`a` и `b` — это один и тот же вызов чистой функции с одинаковыми аргументами. `assert_eq!(a, b)` — тавтология: она не может упасть ни при какой реализации `format_act_number`. Единственная содержательная строка — `a == "42в1"` — побуквенно дублирует `format_single_return_uses_sub_suffix` строкой выше. То же и в интеграционной копии (`acts_display_rule.rs:48-53`).

Аналогично `compute_return_suffix_tests::return_suffix_is_unaffected_by_literal_v_in_parent_mask` (`act_service.rs:3536-3546`): весь «родительский номер с литеральной в» живёт в комментарии, а ассерт — `assert_eq!(compute_return_suffix(true, Some(1)), "в1")`, дубль `return_suffix_uses_sub_number` (строка 3527). Тест не может отличить исправленную реализацию от любой другой.

Настоящие анти-вакуумные якоря в фазе есть (`two_holes_smallest_free_fills_in_order`, `second_partial_return_assigns_sub_number_2_ret1_number_stable`, case 1 в `place_movements_timeline.rs`) — претензия только к этим трём.

**Fix:** Либо удалить эти три теста как дубли (инвариант «не зависит от соседей» после удаления параметра доказывается сигнатурой, а не ассертом), либо переписать так, чтобы они различали реализации. Например, для F7-теста — прогнать через ту функцию, которая реально видит родительский номер:

```rust
// перенести F7-проверку туда, где parent_number вообще есть — в dto::act::tests,
// и сверять с явным ожиданием, а не с format!("{parent}в1"):
assert_eq!(
    format_act_number(ActType::Return, "ignored", Some(1), Some("АКТв-2026/09-1")),
    "АКТв-2026/09-1в1"
);
```

(в `dto/act.rs:610-616` ожидание собирается тем же `format!("{parent}в1")`, что и проверяемый код, — ассерт слабее, чем мог бы быть).

### IN-03: Юнит-тесты `smallest_free` не покрывают вырожденные входы

Функция при этом корректно, но НЕЯВНО терпит дубли (`[1,1,2] → 3`) и неположительные значения (`[0,1] → 2`) — за счёт того, что ветка `n < candidate` проваливается без `break`. ### IN-04: Дублирующийся юнит-тест формулы

**File:** `crates/trackly-app/src/dto/act.rs:569-578`
