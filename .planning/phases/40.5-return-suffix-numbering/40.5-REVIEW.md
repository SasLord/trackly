## Warnings

### WR-01: Пост-проверка `ensure_act_family_display_free_in_tx` в `do_return` стала мёртвой; её док-комментарий утверждает обратное, а в уже-конфликтной БД она делает семью невозвратимой навсегда

**File:** `crates/trackly-app/src/services/act_service.rs:1589-1592` (вызов), `crates/trackly-app/src/services/act_service.rs:3460-3479` (док-комментарий), `crates/trackly-app/src/services/act_service.rs:1516-1534` (аллокатор)

**Issue:** Док-комментарий функции после правки утверждает:

> The check is still needed for a different reason: a NEW return gets its own number (`{parent}в{sub}`) that **was not pre-checked**… (e.g. someone created act `42в3` by hand and the next return gets sub_number=3), **this post-check is the only place the collision is detected**.

Это уже неверно — именно этот пример теперь закрыт до вставки. Доказательство совпадения двух множеств, шаг за шагом:

1. `do_return` (строки 1521-1526) берёт `fetch_candidate_rows(&tx, TemplateType::ActNumber)`, отбрасывает `r.family == act_id`, нормализует `normalize_number_key(&r.raw_value)` → `foreign_taken`.
2. `is_blocked(k)` проверяет `normalize_number_key(format_act_number(Return, parent_number, Some(k), parent_number))` — ровно та строка, которую вставленная строка потом покажет (`return_row.number = parent.number`, `parent_act_id = Some(act_id)`, а `fetch_candidate_rows` считает display из `a.number`/`a.sub_number`/`p.number`).
3. `ensure_act_family_display_free_in_tx(&tx, act_id)` делает `partition(|r| r.family == family)` с `family = act_id` — **тот же предикат разбиения**, та же нормализация, та же выборка, тот же срез транзакции (между п.1 и вызовом нет ни одной чужой записи: один writer, одна транзакция).

Значит для ЛЮБОГО номера, который создаёт сам `do_return`, пост-проверка сработать не может. Остаётся ровно один класс срабатываний: коллизия, существовавшая ДО этой записи (родитель или уже живущий соседний возврат конфликтует с чужим актом). И тогда:

- `own` содержит display уже существующего соседа (например «1в2»), `others` — чужой акт «1в2»;
- `find_map` попадает на соседа, транзакция откатывается, возврат не создаётся;
- аллокатор детерминирован, состояние не изменилось → **любая следующая попытка возврата по этому родителю отказывает так же. Семья становится невозвратимой навсегда** — ровно тот дефект, который GAP 1 закрывал.

Это внутренне противоречиво с тем, что раунд сделал в `delete_soft` (`act_service.rs:2985-2993`): там вызов убран с обоснованием «в уже-конфликтной БД он только мешал бы чистить». Новый тест `acts_returns.rs:1269-1320` (`deleting_a_return_succeeds_even_when_family_number_already_collides`) **строит ровно такое состояние БД** (сырой INSERT живого handover «1в2» рядом с возвратом «1в2») и доказывает, что удаление проходит — но не проверяет, что в этом же состоянии возврат по семье всё ещё возможен. Он не возможен.

Побочно: `fetch_candidate_rows(ActNumber)` — полное сканирование всех живых актов с построением `OccupyingRecordDto` (два `String` + `format!` на акт). Теперь оно выполняется **дважды на каждый возврат** ради проверки, которая по построению ничего не находит.

**Fix:** сделать пост-проверку в `do_return` точечной (только новый номер, только против «чужих»), или снять её, честно назвав пред-проверку единственным гейтом:

```rust
// do_return, вместо ensure_act_family_display_free_in_tx(&tx, act_id)?
// Аллокатор уже гарантировал свободу `{parent}в{sub}` по ТОЙ ЖЕ выборке и в
// той же транзакции (см. foreign_taken выше). Пост-проверка всей семьи здесь
// ловила бы только коллизии, существовавшие ДО этой записи, и блокировала бы
// возврат навсегда — ровно как это было в delete_soft до Phase 40.5 (WR-01).
debug_assert!(
    !is_blocked(sub_number),
    "аллокатор обязан был перешагнуть занятую позицию"
);
```

И переписать док-комментарий `ensure_act_family_display_free_in_tx`: единственный живой сценарий — каскад переименования (`act_service.rs:1240`), где номера семьи действительно меняются. Если пост-проверка в `do_return` сохраняется сознательно как детектор битой БД — это надо написать буквально и добавить тест «в конфликтной БД возврат отказывает с внятным сообщением», а не описывать её как защиту от непроверенного номера.

### WR-02: `smallest_free` — цикл без структурной верхней границы в публичном API инфра-слоя; завершение обеспечивает только вызывающий

**File:** `crates/trackly-infra/src/repos/acts_sqlite.rs:485-495` (+ сигнатура `:465-470`)

**Issue:**

```rust
fn smallest_free(live: Vec<i64>, is_blocked: &dyn Fn(i64) -> bool) -> i64 {
    let mut candidate = 1;
    loop {
        if !used.contains(&candidate) && !is_blocked(candidate) { return candidate; }
        candidate += 1;
    }
}
```

Сегодня цикл завершается — но исключительно потому, что единственный вызывающий передаёт предикат, построенный из конечного `HashSet<String>` с инъективным отображением `k -> строка`. Ни сигнатура (`&dyn Fn(i64) -> bool` — произвольный предикат), ни `pub`-обёртка `next_sub_number_for_parent` этого не требуют и не могут потребовать. Док-комментарий закрепляет отсутствие границы как намерение («поиск не имеет искусственной верхней границы»), то есть следующий вызывающий получит явное разрешение передать что угодно.

Цена ошибки здесь непропорциональна: `next_sub_number_for_parent` исполняется внутри транзакции **единственного writer-потока** (`db::writer_worker` — один `Connection`, джобы сериализуются через mpsc). Зависание в нём — это не «одна упавшая заявка», а полная и бессрочная остановка ВСЕХ записей приложения (десктоп + LAN-режим), без таймаута и без возможности восстановления кроме перезапуска процесса. Плюс `i64`-переполнение `candidate += 1` в релизной сборке молча заворачивается в отрицательные значения (в debug — паника в writer-потоке).

**Fix:** либо забрать у вызывающего возможность ошибиться, либо поставить потолок и упасть громко:

```rust
/// Потолок — не бизнес-ограничение, а страховка живости: эта функция
/// исполняется в единственном writer-потоке, зависание в ней останавливает
/// ВСЕ записи приложения.
const MAX_SUB_NUMBER_SCAN: i64 = 100_000;

fn smallest_free(live: Vec<i64>, is_blocked: &dyn Fn(i64) -> bool) -> Result<i64, AppError> {
    let used: BTreeSet<i64> = live.into_iter().filter(|n| *n > 0).collect();
    (1..=MAX_SUB_NUMBER_SCAN)
        .find(|k| !used.contains(k) && !is_blocked(*k))
        .ok_or_else(|| AppError::Internal {
            source_chain: format!(
                "smallest_free: свободный sub_number не найден в 1..={MAX_SUB_NUMBER_SCAN}"
            ),
        })
}
```

Альтернатива, закрывающая проблему структурно: принимать не предикат, а заранее посчитанное конечное множество заблокированных позиций (`&BTreeSet<i64>`), а отображение «display -> k» оставить в слое сервиса. Тогда конечность видна из типа и отдельный тест на неё не нужен.

### WR-03: «Это возврат?» решается сравнением строкового литерала `"return"` в пяти независимых местах; правило отображения собирается из собственной SQL-выборки в четырёх — фаза добавила четвёртую

**Files:**
- `crates/trackly-app/src/services/report_service.rs:1350-1357` (новое место, эта фаза)
- `crates/trackly-app/src/services/number_template_service.rs:829-844`

- `crates/trackly-infra/src/repos/acts_sqlite.rs:50-63`

**Issue:** `format_act_number` действительно единственный владелец формулы — но у неё четыре независимых поставщика аргументов, и каждый заново (а) пишет свой SQL, чтобы достать `act_type` / `sub_number` / `p.number`, и (б) хардкодит разбор строки `act_type`:

```rust
// report_service.rs:1355 (новое)
let display_number = match (act_type.as_deref(), raw_number) {
    (Some("return"), Some(raw)) => Some(format_act_number(ActType::Return, &raw, sub_int, parent)),

// act_service.rs:3118

```

Ветка `(_, raw) => raw` — тихая деградация: опечатка в литерале, смена значения в `ActType::to_sql()` или забытый `LEFT JOIN acts par` на новой поверхности дают **сырой номер родителя** вместо display, без ошибки компиляции и без падения теста. Это буквально тот дефект, который фаза 40 закрывала в таймлайне (WR-10/40-24), фаза 40.5 — в отчёте «Акты» (GAP 2), и который вернётся на пятой поверхности чтения. Память проекта (`invalidation_write_sites_enumerate_from_server`) описывает ровно этот способ терять полноту: перечислять точки по одной вместо сплошного захода от источника.

**Fix:** свести поставщиков к одному хелперу, который сам владеет и разбором `act_type`, и списком нужных колонок:

```rust
// dto/act.rs (рядом с format_act_number — единственным владельцем формулы)
/// Единственная точка, где строковое значение act_type превращается в display.
/// Неизвестное значение — Err, а не тихий откат на сырой номер.
pub fn display_number_from_sql_parts(
    act_type_sql: &str,
    number: &str,
    sub_number: Option<i64>,
    parent_number: Option<&str>,
) -> Result<String, AppError> {
    let act_type = ActType::from_str(act_type_sql)?;
    Ok(format_act_number(act_type, number, sub_number, parent_number))
}
```

…и вызвать его из всех четырёх мест (`report_service`, `number_template_service`, `act_number_display`, `acts_sqlite::from_row`), а `compute_return_suffix` перевести на `ActType` вместо `bool`, полученного сравнением строки. Тогда добавление пятой поверхности либо компилируется правильно, либо не компилируется.

### IN-06: `sub_number.unwrap_or(1)` — молчаливый дефолт в двух местах; коллизии внутри семьи не проверяются вовсе

**Files:** `crates/trackly-app/src/dto/act.rs:36`, `crates/trackly-app/src/services/act_service.rs:3552-3556`

**Issue:** оба места превращают «sub_number отсутствует» в настоящий номер 1. При этом `ensure_act_family_display_free_in_tx` сравнивает только `own` против `others` и физически не способен заметить два одинаковых display ВНУТРИ семьи. Сегодня такое состояние недостижимо: возврат с `sub_number IS NULL` даёт ключ `(number, COALESCE(sub_number,0))` = `(N,0)`, совпадающий с ключом живого родителя, и частичный уникальный индекс его не пускает. То есть инвариант держится на побочном эффекте `COALESCE` в индексе, и нигде не записано, что индекс выполняет эту работу.

**Fix:** либо описать это в док-комментарии `format_act_number` («`None` недостижим для живой строки — гарантирует `idx_acts_number_sub_unique` через `COALESCE`»), либо отказаться от дефолта и деградировать явно (например, вернуть сырой номер и залогировать), чтобы битая строка была видна, а не выглядела как нормальный «в1».
