## Pattern Assignments

### 1. Формула `format_act_number` — как убрать ветку «без цифры»

**Файл:** `crates/trackly-app/src/dto/act.rs:23-43`

**Текущий код** (полностью, для точечной правки):
```rust
pub fn format_act_number(
    act_type: ActType,
    number: &str,
    sub_number: Option<i64>,
    parent_number: Option<&str>,
    sibling_return_count: Option<i64>,
) -> String {
    match act_type {
        ActType::Handover => number.to_owned(),
        ActType::Return => {
            let sub = sub_number.unwrap_or(1);
            let parent = parent_number.unwrap_or(number);
            if sibling_return_count == Some(1) {
                format!("{parent}в")
            } else {
                format!("{parent}в{sub}")
            }
        }
    }
}
```
D-01/D-03 требуют убрать параметр `sibling_return_count` целиком и ветку `if`, оставив только
`format!("{parent}в{sub}")`. Doc-комментарий модуля (:1-9, «Single return for a parent: drops the
sub-number») тоже переписывается — он описывает отменённое правило D-Numbering-01.

**Unit-тесты рядом (та же секция файла, :551-620)** — стиль, которому следовать при добавлении/
правке тестов на формулу:
```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn format_handover_is_plain_number() {
        assert_eq!(
            format_act_number(ActType::Handover, "42", None, None, None),
            "42"
        );
    }
    // ... одна проверка = один #[test], имя = описание инварианта.
}
```

### 2. Инверсия якоря 1/4 — `format_retroactive_promotion` (ДВА места)

**Файлы:** `crates/trackly-app/src/dto/act.rs:583-592`, `crates/trackly-app/tests/acts_display_rule.rs:43-51`
(дубликат — оба требуют одинаковой правки).

**Текущий текст (дефект зафиксирован как ожидаемое поведение):**
```rust
#[test]
fn format_retroactive_promotion() {
    // Same row data — sub=1 — но при изменении sibling_count
    // отображение меняется с «42в» (один возврат) на «42в1» (два).
    // Это retroactive promotion из D-Numbering-01.
    let solo = format_act_number(ActType::Return, "999", Some(1), Some("42"), Some(1));
    let with_sibling = format_act_number(ActType::Return, "999", Some(1), Some("42"), Some(2));
    assert_eq!(solo, "42в");
    assert_eq!(with_sibling, "42в1");
}
```

**Образец правильной инверсии** (сохраняет намерение — «один и тот же вход даёт одно и то же
отображение», а не удаляется):
```rust
#[test]
fn format_is_stable_regardless_of_siblings() {
    // Phase 40.5 (D-01/D-05): та же row data — sub=1 — раньше меняла
    // отображение в зависимости от sibling_return_count (retroactive
    // promotion, D-Numbering-01, отменено). Теперь отображение НЕ зависит
    // от изменчивого состояния соседей — только от sub_number самого акта.
    let a = format_act_number(ActType::Return, "999", Some(1), Some("42"));
    let b = format_act_number(ActType::Return, "999", Some(1), Some("42"));
    assert_eq!(a, "42в1");
    assert_eq!(a, b, "формула не должна зависеть от количества соседей");
}
```
Обратите внимание: сигнатура `format_act_number` теряет параметр `sibling_return_count` — вызовы
теста меняются вместе с сигнатурой (4 аргумента вместо 5). Имя теста больше не должно содержать
слово «promotion» — семантика, которую оно описывало, отменена.

**Образец правильной инверсии** — переименовать (убрать «promotes»), доказывать «ret1 показывает
«в1» СРАЗУ, ещё ДО появления ret2»:
```rust
#[tokio::test(flavor = "multi_thread", worker_threads = 4)]
async fn second_partial_return_assigns_sub_number_2_ret1_number_stable() {
    tokio::time::timeout(Duration::from_secs(30), async {
        let (svc, _dir) = make_acts_service();
        let device_ids = seed_devices(&svc.writer, 3).await;
        let handover = create_handover(&svc, &device_ids).await;

        let it0 = &handover.items[0];
        let ret1 = svc.do_return(&Identity::trusted_admin(), handover.id, /* ... */).await.expect("ret 1");
        assert_eq!(ret1.sub_number, Some(1));

        // Phase 40.5 (D-01/D-05): ret1 обязан показывать «в1» СРАЗУ —
        // ДО появления ret2, а не мигрировать на неё позже.
        let ret1_before_sibling = svc.get(ret1.id).await.expect("get ret1 before sibling");
        assert!(
            ret1_before_sibling.number.ends_with("в1"),
            "ret1 must show «в1» immediately, before any sibling exists, got: {}",
            ret1_before_sibling.number
        );

        let ret2 = svc.do_return(/* оставшиеся 2 позиции */).await.expect("ret 2");
        assert_eq!(ret2.sub_number, Some(2));

        // И после появления ret2 — ret1 НЕ изменился (стабильность, не promotion).
        let ret1_after_sibling = svc.get(ret1.id).await.expect("get ret1 after sibling");
        let ret2_full = svc.get(ret2.id).await.expect("get ret2");
        assert_eq!(
            ret1_before_sibling.number, ret1_after_sibling.number,
            "ret1's display number must NOT change when a sibling return is created"
        );
        assert!(ret2_full.number.ends_with("в2"), "ret2 must show «в2», got: {}", ret2_full.number);
    }).await.expect("second_partial_return budget");
}
```
Это одновременно закрывает Anti-Vacuous Anchor (падает на старой формуле — там `ret1_before_sibling`
был бы «...в», не «...в1» — и проходит на новой).

**Файл:** `crates/trackly-app/tests/acts_clone_handover.rs`, тест

**Образец инверсии:**

```rust
assert_eq!(ret.sub_number, Some(1));
// Phase 40.5 (D-01): единственный возврат ВСЕГДА несёт цифру — «в1», а не «в».
let ret_full = svc.get(ret.id).await.expect("get ret");
```

Имя теста (`..._uses_v_suffix`) стоит переименовать в `..._uses_v1_suffix` — иначе имя лжёт о
том, что доказывает тело. Также требует правки doc-комментарий «G-7 семантика переключения»
(:396-399), который описывает retroactive promotion как ожидаемое поведение — этот комментарий

строка таблицы).

(:334-408) уже утверждает «в1» для единственного (пока) возврата — сегодня это на самом деле
дефект, задокументированный его собственным комментарием («Тут partial, но sibling_return_count = 1,
поэтому реально получим «в»... G-7 семантика переключения... происходит когда появляется
СЛЕДУЮЩИЙ return»). После фикса имя теста (`uses_v1_suffix`) наконец соответствует поведению —
проверить, что тело теста (сейчас ожидающее «в», не «в1», см. комментарий на :396-399) тоже
обновлено, иначе тест не пройдёт по новой формуле.

### 5. Wave 0 — новый тест «две дырки, порядок заполнения» (Success Criterion 2)

**Файл:** `crates/trackly-app/tests/acts_returns.rs` (новая функция, добавить в конец файла рядом
с другими `do_return`-тестами).

**Аналог для стиля вызовов** — `full_return_archives_handover` (:194-232) для паттерна
`create_handover` → цикл `do_return` → `svc.get()`; для `delete_soft` на return-акте — единственный
существующий пример в проекте:
```rust
// crates/trackly-app/tests/acts_clone_handover.rs:961 (контекст: undo_return_restores_archived_to_false)
svc.delete_soft(ret.id, ret.version)
    .await
    .expect(/* ... */);
```
`delete_soft` возвращает `Result<Vec<i64>, AppError>` (список затронутых id, см.
`act_service.rs:2849`) — сигнатура вызова: `svc.delete_soft(id, version).await`.

**Каркас нового теста** (собран из существующих хелперов файла — `make_acts_service`,
`seed_devices`, `create_handover`, все уже в файле, см. пункт 3 выше):
```rust
#[tokio::test(flavor = "multi_thread", worker_threads = 4)]
async fn two_holes_smallest_free_fills_in_order() {
    tokio::time::timeout(Duration::from_secs(30), async {
        let (svc, _dir) = make_acts_service();
        let device_ids = seed_devices(&svc.writer, 3).await;
        let handover = create_handover(&svc, &device_ids).await;

        // Три возврата подряд — sub_number 1, 2, 3 (одна позиция на возврат).
        let mut returns = Vec::new();
        for it in &handover.items {
            let ret = svc
                .do_return(
                    &Identity::trusted_admin(),
                    handover.id,
                    ActReturnDto {
                        bulk_condition: Some("Хорошее".into()),
                        bulk_place_id: None,
                        apply_to_all: true,
                        giver_name: None,
                        receiver_name: None,
                        handover_date_utc: None,
                        items: vec![ActReturnItemDto {
                            act_item_id: it.id,
                            device_id: it.device_id,
                            device_ids: vec![it.device_id],
                            quantity: 1,
                            condition_override: None,
                            place_id_override: None,
                        }],
                    },
                )
                .await
                .expect("seed return");
            returns.push(ret);
        }
        assert_eq!(
            returns.iter().map(|r| r.sub_number).collect::<Vec<_>>(),
            vec![Some(1), Some(2), Some(3)]
        );

        // Удаляем sub_number=1 и sub_number=3 — дырки {1, 3}.
        svc.delete_soft(returns[0].id, returns[0].version)
            .await
            .expect("delete return 1");
        svc.delete_soft(returns[2].id, returns[2].version)
            .await
            .expect("delete return 3");

        // ВАЖНО: удаление возвратов освобождает позиции у handover'а —
        // do_return снова требует свободные act_item'ы этого же handover'а,
        // либо создать НОВЫЙ handover с достаточным количеством позиций,
        // если существующий сценарий их не освобождает автоматически.
        // (План должен явно проверить это по коду do_return/delete_soft —
        // не предполагать.)

        let next = svc
            .do_return(&Identity::trusted_admin(), handover.id, /* один item */)
            .await
            .expect("first refill");
        assert_eq!(next.sub_number, Some(1), "smallest free hole must be filled first");

        let next2 = svc
            .do_return(&Identity::trusted_admin(), handover.id, /* следующий item */)
            .await
            .expect("second refill");
        assert_eq!(next2.sub_number, Some(3), "second smallest free hole (3), not 4");
    })
    .await
    .expect("two_holes_smallest_free_fills_in_order budget");
}
```
**Важная оговорка для исполнителя (не в аналоге, но обязана быть проверена по коду до финализации
теста):** RESEARCH.md не подтверждает построчно, что `do_return` позволяет вернуть УЖЕ возвращённую
позицию повторно после `delete_soft` родительского return-акта (какой статус получает `act_item`/
`device` при soft-delete возврата). План должен свериться с `delete_soft`'s `ActType::Return`
branch (`act_service.rs`, окрестности :1873, :2849) прежде чем фиксировать точный сценарий сидирования
третьего и четвёртого возврата — возможно, потребуется отдельный handover с бОльшим количеством
позиций, а не повторное использование одного и того же 3-item handover. Это Wave 0 риск, не
готовый рецепт.

```rust
        let handover = create_handover(&svc, &device_ids).await;

        let ret1 = svc.do_return(&Identity::trusted_admin(), handover.id, /* it0, sub=1 */)
            .await
            .expect("ret 1");
        let ret2 = svc.do_return(&Identity::trusted_admin(), handover.id, /* it1, sub=2 */)
            .await
            .expect("ret 2");
        assert_eq!(ret1.sub_number, Some(1));
        assert_eq!(ret2.sub_number, Some(2));

        let ret2_before = svc.get(ret2.id).await.expect("get ret2 before delete");

        svc.delete_soft(ret1.id, ret1.version)
            .await
            .expect("delete ret1");

        let ret2_after = svc.get(ret2.id).await.expect("get ret2 after delete");
        assert_eq!(
            ret2_before.number, ret2_after.number,
            "deleting a sibling must not change an already-created return's number"
        );
        assert_eq!(ret2_after.sub_number, Some(2), "sub_number itself must not shift either");
    })
    .await
    .expect("deleting_non_last_return budget");
}
```


### 9. D-09 — пересмотр `acts_numbering.rs` ПО СМЫСЛУ (не замена строк)

**Файл:** `crates/trackly-app/tests/acts_numbering.rs`

**Хелперы файла** (:34-93) — переиспользуются без изменений: `make_acts_service`, `number_input`,
`seed_devices`, `create_payload`.

**Тест, который требует ПОЛНОГО пересмотра сценария** (не механической замены "42в"→"42в1"):
`display_number_space_covers_returns_in_both_directions` (:465-533). Текущий сценарий:
1. Создаёт #42 с двумя устройствами, возвращает ОДНО → соло-возврат отображается «42в».
2. Проверяет, что "42В" (case-insensitive) занят через `is_occupied`, ожидает `hit.number == "42в"`.
3. Проверяет, что переименование #42 в «42в» — это НЕ self-conflict (иначе было бы «42вв»).
4. Создаёт handover «42в1»; ВТОРОЙ возврат #42 теперь конфликтует, потому что переименовал бы
   семью в «42в1»/«42в2».
5. Создаёт handover «43в»; каскадное переименование #42→#43 конфликтует.

**Почему механическая замена строк здесь дефект:** после D-01 шаг 1 больше не производит «42в» —
соло-возврат теперь ВСЕГДА «42в1». Значит:
- Шаг 2 должен ожидать `hit.number == "42в1"`, а проверять occupied-запрос на `"42в1"` (не `"42В"`).
- Шаг 3 («42в» — не self-conflict») теряет смысл: такого отображения не существует. Нужно
  переписать на «переименование #42 в «42в1» — не self-conflict со своим же единственным
  возвратом» (та же идея, другое конкретное значение).
- Шаг 4 (второй возврат конфликтует с существующим handover «42в1») **остаётся валидным как
  сценарий**, но теперь конфликт возникает на ПЕРВОМ возврате (а не втором) — единственный
  возврат #42 сразу претендует на «42в1», которое уже занято handover'ом «42в1». План должен
  переставить порядок операций: создать handover «42в1» ДО первого возврата, а не после.
- Шаг 5 (каскад переименования родителя) сохраняет структуру, но конфликтующий handover должен
  быть «43в1» (не «43в» — такого отображения больше нет).

Аналогично для `create_rejects_number_matching_live_return_display` (:129-176) и
`update_rejects_rename_to_number_matching_live_return_display` (:180-260) — оба буквально создают
handover, делают ЕДИНСТВЕННЫЙ (соло) возврат и ожидают, что его отображение «42в» конфликтует с
новым/переименованным актом. После фикса соло-возврат отображается «42в1» — заменить литерал
`"42в"` на `"42в1"` в payload новой попытки (`create_payload("42в1", ids[1])`), но **обязательно
перепроверить**, что комментарии над тестами (например :168-171 «A brand-new act attempting to use
"42в" (the return's DISPLAYED number...)») тоже переписаны — иначе комментарий будет утверждать
то, чего тест больше не проверяет.

## Shared Patterns

### A. Транзакционный вызов SQL-формулы внутри `WriterHandle`

**Источник:** `crates/trackly-infra/src/repos/acts_sqlite.rs:448-459` (текущий `next_sub_number_for_parent`)
**Применить к:** новой реализации выделения `sub_number` (D-04/D-07) — БЕЗ новых блокировок,
БЕЗ нового `UNIQUE`-индекса (уже есть `idx_acts_number_sub_unique`, `migrations/V042__acts_number_text.sql`).
```rust
pub fn next_sub_number_for_parent(
    tx: &Transaction<'_>,
    parent_act_id: i64,
) -> Result<i64, AppError> {
    tx.query_row(
        "SELECT COALESCE(MAX(sub_number), 0) + 1 FROM acts \
         WHERE parent_act_id = ?1 AND deleted_at_utc IS NULL",
        params![parent_act_id],
        |r| r.get::<_, i64>(0),
    )
    .map_err(map_rusqlite)
}
```
Новая версия остаётся `pub fn(tx: &Transaction<'_>, parent_act_id: i64) -> Result<i64, AppError>` —
меняется только SQL/тело, не сигнатура и не точка вызова (`do_return`, тот же `tx`).

### B. Позиционные индексы `SELECT_ACTS` / `from_row` (D-16, обязательная проверка после удаления подзапроса)

**Источник:** `crates/trackly-infra/src/repos/acts_sqlite.rs:31-91`
**Применить к:** любой правке, удаляющей `sibling_return_count` из `SELECT_ACTS`.
Текущий порядок колонок (индексы 0-19): `id(0) number(1) sub_number(2) parent_act_id(3)
act_type(4) giver_name(5) receiver_name(6) place_id(7) notes(8) deadline_utc(9) archived(10)
created_at_utc(11) updated_at_utc(12) deleted_at_utc(13) version(14) resolved_place_path(15)
parent_number(16) sibling_return_count(17) handover_date_utc(18) place_path_snapshot(19)`.
После удаления колонки 17 — `handover_date_utc` становится 17, `place_path_snapshot` становится 18;
`from_row` обязан пересчитать ВСЕ `row.get(N)?` после удалённой позиции, а не просто убрать одну
строку. Существующий тест `round_trip_insert_get` (:700-747) должен остаться зелёным И явно
проверять значения (а не только наличие) `handover_date_utc`/`place_path_snapshot` — если текущий
тест их не проверяет по значению, план обязан усилить именно этот тест как часть правки, иначе
сдвиг индекса пройдёт незамеченным (см. RESEARCH.md Pitfall 2).

### C. Постоянный гейт 40.4-05 против конкатенации номера в шаблонах (НЕ трогать, только пройти)

**Источник:** `crates/trackly-app/tests/html_act_render.rs:1650-1720`
**Применить к:** любой печатной логике, которая читает `act.number`/`act.suffix` в minijinja-контексте.

```rust
    assert!(!reconstructs_number_from_raw_plus_suffix(ACT_HANDOVER_HTML), /* ... */);

```
Это ОБРАЗЕЦ структуры «текстовый гейт с self-test на фикстурах» в Rust (одна функция-предикат +
позитивный тест на активном шаблоне + негативный тест на legacy-снимке `_legacy_defaults/v29/`,

исполнителя — переносить именно эту структуру (предикат + позитив + негатив-фикстура), не

внутри Rust-теста» в проекте нет; `no_io_deps.rs` (см. ниже) ближе по духу, но использует

### D. Структурная проверка через `cargo`-инструмент внутри Rust-теста (аналог «грепа как гейта»)

**Источник:** `crates/trackly-core/tests/no_io_deps.rs` (полный файл, 62 строки)
```rust

#[test]
fn trackly_core_has_no_io_deps() {
    let output = Command::new(&cargo).args(["tree", "-p", "trackly-core", /* ... */]).output()
        .expect("failed to execute `cargo tree`");
    // ... парсит stdout, assert!(offenders.is_empty())

```
Ближайший в проекте пример «постоянный тест, проверяющий структурное свойство кодовой базы, а не
поведение одной функции». Если D-03 (удаление `sibling_return_count`) или D-08 (отсутствие
`find('в')`) должны быть закреплены постоянным Rust-тестом (не разовым `grep` из VALIDATION.md),
такой тест шеллится в `grep`/`ripgrep` через `std::process::Command`, а НЕ в `cargo tree` —
структура (const-список запрещённых паттернов → shell-вызов → парсинг вывода → `assert!`) переносится.
**Но VALIDATION.md явно классифицирует критерии 4 и 5 как «grep-гейт (не cargo test)»** — то есть
это может быть одноразовая команда, которую прогоняет исполнитель/ревьюер перед закрытием фазы,
а не обязательный постоянный CI-тест. План должен явно решить, какой из двух путей выбран, и
назвать команду (см. VALIDATION.md критерии 4/5 — команды уже даны буквально).

### E. Фронтендовый реестровый гейт (НЕ требует правки, но требует regression-прогона)

**Источник:** `ui/scripts/check-act-number-no-regex-split.mjs` (249 строк)
Структура: zero-dependency ESM-скрипт, два независимых regex-правила
(`DIGIT_PREFIX_REGEX_LITERAL_RE`, `NUMBER_RAW_RE`) + explicit whitelist (`ALLOWED_NUMBER_RAW_FILES`,
только `ActFormBody.svelte`) + `--selftest` режим на встроенных in-memory фикстурах (7 штук: 5
позитивных, 2 негативных) + обычный режим сканирования `ui/src/**/*.{svelte,ts}`. Подключён в
`ui/package.json:16` (`"lint"` script) как ДВА последовательных вызова: сначала
`--selftest`, потом обычный прогон:
```json
"lint": "... && node scripts/check-act-number-no-regex-split.mjs --selftest && node scripts/check-act-number-no-regex-split.mjs && ..."
```
Ни regex, ни whitelist менять не нужно (Pitfall 3, RESEARCH.md) — фронтенд не меняется в этой
фазе. Прогнать оба вызова один раз как regression-проверку. Это ОБРАЗЕЦ для гипотетического
будущего Rust-аналога (см. пункт D выше), если такой понадобится: self-test на фикстурах ДО
основного прогона — тот же порядок вызовов.
