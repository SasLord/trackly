### Адъюдикация WR-01 (ревью 40.5-REVIEW.md) — утверждение ревьюера ПОДТВЕРЖДЕНО

Логика (чтение кода):
1. `do_return` (act_service.rs ~1516-1534) строит `foreign_taken` из `fetch_candidate_rows(ActNumber)`, отбрасывая `r.family == act_id`, и передаёт аллокатору предикат `is_blocked`.
2. `ensure_act_family_display_free_in_tx(&tx, act_id)` (стр. 1592) использует ту же выборку, тот же срез транзакции (один writer), то же разбиение `family == act_id`, ту же `normalize_number_key`. Для НОВОГО номера она сработать не может.
3. Остаётся класс «коллизия существовала до записи»: `own` содержит display существующего возврата, `others` — чужой акт с тем же номером. Откат; аллокатор детерминирован; повтор даёт тот же отказ.

Эмпирический зонд (временный файл `tests/zz_probe_wr01.rs`, копия helper-ов `acts_returns.rs`; после прогона УДАЛЁН, `git status` чист):
- Акт «1» на 4 устройства, возврат №1 -> «1в1».
- Отдельный акт (создан через сервис, затем `UPDATE acts SET number='1в1'` в обход сервиса) — живой handover «1в1».
- `do_return` по акту «1»: попытка 0 и попытка 1 — обе `Err(Conflict { "Номер «1в1» уже занят: Акт передачи, Передал: Сидоров С.С. · Принял: Кузнецов К.К. — …Переименуйте один из них." })`. Блокировка стабильна.
- После переименования блокирующего акта через `ActService::update` («999») следующий `do_return` проходит и даёт «1в2».

Вывод: семья действительно остаётся невозвратимой, пока пользователь не переименует названный в сообщении акт. Это СУЖЕНИЕ исходного GAP 1, а не его исчезновение:
- Достижимость. Из чистой БД через сервисы состояние не строится (create/update/каскад проверяют занятость, включая display возвратов). Оно достижимо (а) через БД, созданную ДО Фазы 40.5: там одиночный возврат показывался как «42в», поэтому посторонний «42в1» был легален; теперь тот же возврат (sub_number=1, «Существующие акты не перенумеровываются») отображается как «42в1» и сталкивается с ним (подтверждено чтением `git show c7f5726e:crates/trackly-app/src/dto/act.rs`: ветка `sibling_return_count == Some(1) => "{parent}в"`); (б) узкой гонкой TOCTOU: предпроверка `create` (стр. ~310) выполняется вне writer-транзакции; (в) правкой БД в обход сервиса.
- Смягчение. Сообщение называет блокирующий акт (D-18), выход есть (переименование), подтверждён зондом. Поэтому оценка — WARNING-уровень последствий, но истина 5 не выполнена полностью, а вывод фазы по цели «акт остаётся возвратимым» нельзя считать закрытым.
- Пробел тестов. `deleting_a_return_succeeds_even_when_family_number_already_collides` строит именно такую БД и не проверяет возврат в ней — на нём дефект не виден. Внутренне противоречиво: комментарий в `delete_soft` (стр. ~2985-2993) сам называет «legacy rows» причиной снятия проверки, а `do_return` оставлена с тем же дефектом.

Это НЕ похоже на намеренное отклонение (override не предлагается): исправление дешёвое и не меняет решений D-01..D-20.
