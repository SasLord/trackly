Образец для нового структурного гейта — `crates/trackly-app/tests/html_page_parity.rs` (49 строк,
читается целиком в Task 3's read_first): `const ... = include_str!("../templates/act_handover.html")`
на верхнем уровне файла + функция-хелпер, извлекающая регексом нужный фрагмент текста, + `#[test]`
с `assert!`/`assert_eq!` и информативным сообщением при провале. Тот же приём копируется для нового
гейта, меняются только извлекаемый фрагмент и условие.

**Что именно извлекается — и почему не диапазон markup.** Гейт проверяет **CSS по селекторам**, а не
диапазон разметки. Наивный вариант «текст между `{% include "_header.html" %}` и
`<div class="signatures">`» непригоден по построению: в текущем HEAD блок `<style>` занимает строки
41-106 и содержит **оба** объявления `border-bottom` (строки 75 и 97), а маркер `include` стоит
только на строке 110 — то есть весь CSS лежит **до** начала такого диапазона, и он дал бы ноль
вхождений всегда, независимо от регрессии. План 02 блок `<style>` никуда не переносит (его Task 1
правит строки 64-105 на месте), а разметка тела ссылается только на CSS-классы
(`class="value-blank"`), без инлайновых стилей. Поэтому хелперы работают в два шага: сначала
`extract_style_block` вырезает содержимое `<style>…</style>` целиком, затем `extract_rule_body`
достаёт тело CSS-правила по точному селектору (`.field-row`, `.value-blank`,
`.signature-field .signature-line`).
