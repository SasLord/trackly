# Phase 43: Надёжная доставка событий - Context

**Gathered:** 2026-11-26
**Status:** Ready for planning

<domain>
## Phase Boundary

События не теряются и не утекают. Клиент (браузерная SPA и десктоп Trackly) после любого обрыва
или переполнения очереди (`Lagged`) догружает пропущенное. Пользователь получает события только
своих бесед. Повторная отправка не создаёт дубликат. Сервер сам закрывает «мёртвые» соединения,
клиенты переподключаются автоматически. Требования: DLV-01, DLV-02, DLV-03, DLV-04.

В фазу входит **ядро модели мессенджера `im_*`** — ровно столько, сколько нужно, чтобы DLV-02/03
проверялись настоящими интеграционными тестами, а не пробным сигналом. Всё остальное по чату
(реакции, FTS-поиск, rich-документ и его валидатор, правки/удаления, закрепы, пересылка, UI)
остаётся в Фазах 47–50. Rust-клиент Link (tokio-tungstenite) остаётся в Фазе 44.

</domain>

<decisions>
## Implementation Decisions

### Граница с Фазой 47 (ядро im_*)
- **D-01:** В Фазе 43 создаётся минимальное ядро `im_*`: беседы (`im_conversations` с `last_seq`),
  участники (`im_members`), сообщения (`im_messages` с `seq`, `rev`, `client_msg_id`,
  `UNIQUE(conversation_id, seq)`, `UNIQUE(conversation_id, author_user_id, client_msg_id)`) —
  по схеме из `.planning/research/ARCHITECTURE.md` §3–§4. Фаза 47 НАРАЩИВАЕТ эту схему, а не
  создаёт заново. Колонки, которые понадобятся 47, можно заложить сразу, если это дёшево и не
  требует логики (на усмотрение планировщика). Тело сообщения в 43 — простой текст в обёртке
  версионируемого документа; валидатор rich-документа — Фаза 47/49.
- **D-02:** Наружу как настоящие маршруты `/api/v1/*` (с авторизацией по членству) выставляются
  только `im_send` и `im_sync`: их потребят Фазы 44 и 48. Создание бесед и изменение состава
  (добавить/исключить участника) в 43 — сервисные функции, вызываемые из тестов; маршруты для
  них появятся в Фазе 47.
- **D-03:** Клиентская сторона в 43 — общий JS-пакет `packages/transport` (браузер) и мост
  десктопа Trackly (`main.rs`, `trackly-event`). Протокол (кадры `hello`, `resync_required`,
  сигналы IM, ping/pong, тайминги) фиксируется документом (ADR или раздел в ADR 0003) и
  серверными тестами так, чтобы Rust-клиент Link в Фазе 44 реализовал его без догадок.
- **D-04:** Доставка — «сигнал + догрузка» по ADR 0003: сигнал несёт только
  `{conversation_id, rev}` и тип, без тела. `seq`/`rev` назначаются внутри замыкания
  единственного писателя. Получатели определяются в той же транзакции, публикация — после
  `.await?` (правило D-04 из `entities_broadcast.rs`). Маршрутизация по пользователям — отдельный
  компонент (`ImHub`, канал на пользователя); старый `WsEvent`/`ws_broadcast` для IM НЕ
  расширяется, `is_visible_to` для IM не используется.

### Членство и исключение (DLV-02)
- **D-05:** После исключения из беседы новые события этой беседы пользователю НЕ приходят сразу
  (следующий же сигнал после коммита исключения не попадает в его канал).
- **D-06:** Исключённый участник сохраняет **историю до момента исключения**: беседа остаётся у
  него в списке только для чтения, сообщения до момента исключения видны, новые не приходят и в
  `im_sync` не отдаются. Ядро обязано это заложить (например, граница видимости по `seq` на
  момент выхода в `im_members`, мягкий выход `left_at_utc`). Отличие от исследования: там
  предлагалось отдавать такую беседу в `removed:[ids]` — это решение пользователя отменяет.
  Изменения сообщений, сделанные ПОСЛЕ исключения (правка/удаление старых), исключённому не
  доставляются — его копия заморожена на момент выхода.

### Ресинк экранов Trackly (DLV-01)
- **D-07:** Ветка `Lagged(n)` перестаёт молча продолжать — в ОБОИХ местах: `http/ws.rs` и мост
  десктопа `main.rs` (~стр. 327). Сервер шлёт клиенту `resync_required`; мост десктопа —
  аналогичный сигнал в webview. Увеличение буфера 128 — не решение, не делать.
- **D-08:** Клиент на `resync_required` И на каждый успешный `onopen` после обрыва вызывает ресинк
  всех подписчиков. Перечитывается **всё, что слушает WS-события** (списки, открытые карточки,
  счётчики, колокольчик, чат заявки), а не только текущий раздел. Нужен гейт, который ловит
  подписчика без обработчика ресинка (по образцу реестровых гейтов проекта).
- **D-09:** Ресинк **тихий**: никакого отдельного тоста «данные обновлены». При `Lagged` без
  обрыва пользователь не видит ничего.
- **D-10:** Ресинк **не трогает несохранённый ввод** в открытых формах (карточка устройства, акт и
  т.п.) — так же, как обычное событие сегодня. Обнаружение конфликта правок — вне фазы.

### Защита от дублей (DLV-03)
- **D-11:** Идемпотентная отправка по клиентскому id применяется в трёх местах: `im_send`, чат
  заявок (`chat_service::send`) и **создание заявки** (`request_service::create`). Повтор с тем
  же id возвращает уже созданную сущность, а не ошибку и не дубликат. Для чата заявок и заявок —
  миграции с уникальным ключом (автор + клиентский id), как у `im_messages`.
- **D-12:** Поведение клиента при сбое сети: несколько тихих автоповторов с тем же id; если не
  удалось — сообщение остаётся в ленте с пометкой «Не отправлено» и кнопкой «Повторить» (тот же
  id). Очередь — только в памяти (живёт, пока открыта вкладка); оффлайн-режим вне ТЗ. Для формы
  создания заявки — тот же принцип: id держится формой до успеха, повторное нажатие уходит с тем
  же id.

### Мёртвые соединения и переподключение (DLV-04)
- **D-13:** Сервер шлёт `hello` первым кадром, ping каждые **25 с**, закрывает соединение без
  ответа **60 с**. Значения — константы в коде, не настройки.
- **D-14:** Тост «Соединение с сервером потеряно» показывается **с задержкой ~5 с**: если
  переподключились быстрее (проснулся ноутбук, мигнул Wi-Fi) — тоста нет. Существующие
  инварианты из `packages/transport/src/ws.ts` сохраняются: не больше одного тоста за эпизод,
  тост залипающий и снимается на `onopen`, при остановке сервера тост появляется гарантированно.
- **D-15:** Переподключение: backoff 1 с → ×2 → 30 с как сейчас, плюс **сброс ожидания и
  немедленная попытка** по событиям браузера «сеть появилась» (`online`) и возврату на вкладку
  (`visibilitychange`).

### Claude's Discretion
- Формат кадров и сигналов (имена полей, типы), версия протокола в `hello`.
- Порог `reload:true` в `im_sync` и размер страницы.
- Число и интервалы автоповторов отправки.
- Точная форма границы видимости исключённого (`left_seq` или иное) — при условии D-06.
- Как именно мост десктопа передаёт ресинк в webview (отдельное событие или кадр в `trackly-event`).
- Нужен ли отдельный ADR или дополнение ADR 0003 для протокола (D-03).

</decisions>

## Existing Code Insights

### Reusable Assets
- `crates/trackly-app/src/http/ws.rs` — WS-цикл `select!` (shutdown / broadcast / socket.recv); сюда добавляются ветка `ImHub`, `hello`, ping/pong-таймер, `resync_required` вместо молчаливого `Lagged`. Ветка shutdown и `CLOSE_SEND_TIMEOUT` обязаны сохраниться.
- `crates/trackly-app/src/main.rs` ~296–330 — мост `ws_broadcast` → `trackly-event` для десктопа, своя ветка `Lagged`.
- `packages/transport/src/ws.ts` — refcounted singleton, backoff, залипающий тост, `onWsEvent`; сюда — API ресинка, задержка тоста, `online`/`visibilitychange`.
- `crates/trackly-app/src/services/entities_broadcast.rs` — правило D-04 (рассылка после записи, вне замыкания) и реестровый гейт «мутация → рассылка».
- `crates/trackly-app/src/services/chat_service.rs::send` (~стр. 444) и `request_service.rs::create` (~стр. 345) — точки для идемпотентного id (D-11).
- `WsEvent::ChatMessage` несёт только id — прецедент «тело не по broadcast».

### Established Patterns
- Единственный писатель (mpsc 256, таймаут 5 с) — назначение `seq`/`rev` внутри замыкания записи.
- Двухтранспортность: Tauri-команды + `/api/v1/*`; для IM-команд пользователя tauri-близнецы не создаются (чат в десктопе скрыт) — проверить гейт паритета http↔tauri_cmds и внести исключение.
- Миграции: последняя `migrations/V057__history_events.sql`; новая миграция обязана ставить `PRAGMA user_version`; не полагаться на `foreign_keys=OFF` внутри refinery-транзакции при перестройке таблиц (уроки V042/V050).
- `ui/src/packages-compat.ts` ловит дрейф структурной копии `WsEvent` в пакете — новые кадры добавлять в обе стороны.

### Integration Points
- `AppCtx` (`crates/trackly-app/src/context.rs`) — новое поле `im_hub` рядом с `ws_broadcast`.
- Маршрутизатор `/api/v1` — `im_send`, `im_sync` с авторизацией по членству (`Action` + `authorize`; карта employee-маршрутов).
- Все экраны, подписанные через `onWsEvent`, — точки регистрации ресинка (D-08).

<specifics>
## Specific Ideas

- Поведение исключённого «как в мессенджерах после выхода из группы»: старая переписка остаётся у него только для чтения, новое не приходит (D-06).
- Тост об обрыве не должен мигать при пробуждении ноутбука, но обязан появляться при остановке сервера (D-14).

</specifics>
