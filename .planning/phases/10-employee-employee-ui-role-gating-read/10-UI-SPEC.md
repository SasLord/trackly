## Layout & Component Contract

*(Non-template section — included because this phase's primary deliverable is a NEW layout shell and
a NEW screen, which the standard template's spacing/typography/color tables under-specify for
structural decisions. This section is the load-bearing part of the contract for `gsd-executor`.)*

### D-UI-01 — Employee shell structure

**Decision: separate, dedicated shell component** (`EmployeeLayout.svelte`), NOT a conditional branch
inside `Layout.svelte`. Rationale: `Layout.svelte`'s `.app-layout` grid (`--sidebar-width` + content)
and `Sidebar.svelte`'s full `SIDEBAR_ITEMS` render are structurally wrong for the employee case — they
would require negative-space hacks (hiding the sidebar) rather than a layout actually built for a
single-purpose shell. A separate component is less code and zero risk of an employee CSS-inspecting
their way to a hidden nav item (defense in depth alongside the backend gate, even though the backend
remains the real boundary per D-RBAC-03/D-DENY-01).

**Structure** (mirrors `Layout.svelte`'s skip-link + semantic-landmark pattern, but header-based not
sidebar-based):

```
<a class="skip-link">Перейти к основному содержимому</a>
<div class="employee-shell">
  <header class="employee-header">          <!-- height: var(--header-height) = 56px -->
    <span class="employee-brand">Trackly</span>
    <div class="employee-header-actions">
      <span class="user-name">{fullName}</span>
      <span class="user-role">Сотрудник</span>
      <ThemeSwitcher />                      <!-- reused unchanged, existing component -->
      <Button variant="ghost" size="sm" onclick={logout}>Выйти</Button>
    </div>
  </header>
  <main id="main" class="employee-content">
    {@render children?.()}                   <!-- always renders RequestsPage-equivalent -->
  </main>
</div>
```

- **No sidebar grid** — single-column flex layout (`flex-direction: column`), header fixed at
  `--header-height` (56px, existing token), content area scrolls below it.
- **Background:** `--color-bg` for content area, `--color-surface` for header bar (same surface
  token `Sidebar.svelte` uses) with `border-bottom: 1px solid var(--color-border)` (mirrors
  `Sidebar.svelte`'s `border-right`).
- **No theme-toggle relocation needed visually** — `ThemeSwitcher.svelte` is reused unchanged,
  simply placed in the header instead of the sidebar footer.
- **Logout button** reuses `Button.svelte` (`variant="ghost"`, `size="sm"`) instead of `Sidebar.svelte`'s
  hand-rolled `.logout-btn` — this phase is an opportunity to consume the shared `Button` component
  rather than duplicate bespoke button CSS, since `EmployeeLayout.svelte` is new code with no legacy
  styling to preserve.
- **Skip-link** reused verbatim from `Layout.svelte` (`.skip-link` class + styles) — accessibility
  parity is not optional just because the shell is "simplified."

**Landing page:** employee's `'/'` root route renders the **same `RequestsPage.svelte` feature
component** already built in Phase 6 (master-detail Заявки view), NOT a new page. The existing
component already branches on `identity?.role === 'employee'` for the `requestedByUserId` filter and
empty-state copy (see `RequestsPage.svelte` lines 27-35, 169-192, already read and confirmed
present) — this UI-level filter becomes UX-only once the backend enforces D-REQ-01, exactly as
RESEARCH.md describes. **No new request-list UI component is needed.**

**Route map for employee:** reduce `routes.ts`'s route table when role is `employee` to exactly:
`'/'` → RequestsPage (reused), and the new `'/access-denied'` (or equivalent hash target) → the new
`AccessDenied.svelte`. All other existing route keys (`/devices`, `/acts`, `/printers`, `/cartridges`,
`/reports`, `/users`, `/settings`, `/map`) must resolve to the `AccessDenied` screen for an employee,
not 404 — this is a deliberate UX distinction (D-DENY-01): a forbidden route is not the same message
as a route that doesn't exist (`NotFound.svelte` stays reserved for truly unmapped hashes).

**Discretion note (per CONTEXT.md):** whether this is implemented as a `svelte-spa-router` `wrap()`
guard per protected route, or a single `$effect`/route-change listener in `App.svelte` that checks
`authStore.user.role === 'employee'` against an explicit allowlist (`['/']`) and redirects — is left to
the planner/executor, per RESEARCH.md Open Question #3. Either mechanism MUST produce the same visible
result: employee hitting any non-allowlisted hash sees `AccessDenied.svelte`, never the underlying
page's component tree (i.e., do not mount-then-hide the forbidden page — guard before mount, since the
forbidden page's `onMount` may itself fire API calls that get the now-correct 403 from the backend,
which is wasteful and could flash an error toast immediately followed by the access-denied screen).

### D-GATE-03 — Employee dashboard composition

**Decision:** the employee dashboard is **not a separate route** — it is folded into the top of the
employee's `'/'` landing page, above the existing `RequestsMasterDetail` list, as a single
`StatWidget`-style summary card titled **«Мои заявки»** showing the caller's own request counts
(Новые / В работе / Выполнено), reusing `StatWidget.svelte` exactly as-is (same props shape: `title`,
`mainNumber`, `mainLabel`, `breakdown`, `loading`, `error` — no new widget component). This satisfies
CONTEXT.md's explicit permission to "fold into requests view" (`<scope_note>`) and keeps the surface
genuinely small.

- **mainNumber/mainLabel:** total open+in-progress request count / «активных заявок»
- **breakdown:** `[{label: 'Новые', count}, {label: 'В работе', count}, {label: 'Выполнено', count}]`
- **No `warningItems`** prop usage (that's the low-stock-cartridge mechanism — explicitly out of
  scope per D-GATE-03's "no org-wide metrics" rule; do not wire it even if empty).
- Card sits in a `<div class="employee-summary">` with `margin-bottom: var(--space-lg)` above the
  existing `RequestsSearchAndTabs` + `RequestsMasterDetail` block — no new grid system, single
  full-width card (`max-width` unconstrained inside the existing `.page-content` padding).

### D-DENY-01 — "Нет доступа" screen

**Decision:** new component `AccessDenied.svelte`, structurally a near-exact copy of the existing
`NotFound.svelte` pattern (already read and confirmed — see Sources), changing only heading/body/CTA
copy and the CTA's destination hash.

```
<div class="access-denied">
  <h2 class="access-denied-heading">Нет доступа</h2>
  <p class="access-denied-body">
    У вашей роли («Сотрудник») нет доступа к этому разделу. Доступны только заявки.
  </p>
  <Button variant="secondary" onclick={() => (window.location.hash = '#/requests')}>
    К заявкам
  </Button>
</div>
```

- **Exact same CSS shape as `NotFound.svelte`**: `.access-denied` ≡ `.not-found` styles
  (flex column, centered, `padding: var(--space-2xl)`, `min-height: 300px`, `gap: var(--space-md)`),
  `.access-denied-heading` ≡ `.not-found-heading` (20px/600/`--color-text-primary`),
  `.access-denied-body` ≡ `.not-found-body` (14px/regular/`--color-text-secondary`).
- **Button variant: `secondary`** (not `primary`) — matches `NotFound.svelte`'s choice and keeps this
  screen visually neutral/non-alarming (it is a routing boundary, not an error state requiring urgent
  action). This also avoids overloading `--color-accent` outside its reserved list above.
- **No icon.** Text-only, consistent with `NotFound.svelte` and the project's icon-free convention
  for this kind of state screen.
- Rendered for: (a) employee navigating directly to a forbidden hash, (b) optionally also as the
  Tauri/HTTP 403 fallback destination if `client.ts`'s new 403 branch chooses to redirect rather than
  toast-only (see Copywriting Contract — recommend toast-only for mid-session API 403s, reserving this
  full-screen treatment for route-level denial only, since a mid-session 403 on, say, a stale list
  refresh should not yank the user away from a page they're legitimately allowed to be on).

### `client.ts` 403 handling

Add a symmetric branch next to the existing 401 handling (both Tauri-invoke and HTTP-fetch code
paths — this file already has both, see Sources):

- **HTTP path:** `if (res.status === 403) { pushToast('error', 'Недостаточно прав для этого действия'); }`
  then `throw err` (already happens unconditionally below the existing 401 `if`) — no redirect, no
  auth-store mutation (user is still authenticated, just forbidden for this one call).
- **Tauri path:** mirror the existing `code === 'UNAUTHORIZED' || 'Unauthorized'` check shape with
  `code === 'FORBIDDEN' || 'Forbidden'` (confirmed exact string: `AppError::Forbidden.code()` returns
  `"FORBIDDEN"` — verified directly in `crates/trackly-core/src/error.rs` line 167, resolving
  RESEARCH.md Open Question #2 definitively). Same toast-only behavior, no redirect.
- **Import requirement:** `client.ts` will need `pushToast` from `$lib/stores/toast.svelte` — confirm
  this does not create a circular import with `authStore` (both are independent leaf stores per
  existing codebase structure; `RequestsPage.svelte` already imports both side-by-side with no issue).
