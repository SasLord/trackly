Implement the two frontend-only decisions CONTEXT.md locks for Phase 10 that no prior plan covers: D-UI-01 (a genuinely separate, minimal `EmployeeLayout.svelte` shell — not a conditional branch inside the existing sidebar `Layout.svelte` — landing on the Employee's own Заявки) and D-DENY-01 (an `AccessDenied.svelte` screen shown when an Employee navigates directly to a forbidden route, plus the matching 403-handling branch in `ui/src/lib/api/client.ts` for both the Tauri and HTTP transports).

Without this plan, the frontend still renders the full Admin/Manager sidebar shell and routes for an Employee, so a 403 either crashes the page, shows nothing, or the Employee sees navigation links to sections they can never use. This plan makes the UI honest about what the Employee role can do, while keeping the real enforcement entirely server-side.

From ui/src/lib/api/client.ts (full file, 42 lines — current 401-only handling to extend with a symmetric 403 branch):
```ts
import { parseAppError } from './errors';
import { authStore } from '$lib/stores/auth.svelte';
const isTauri = typeof window !== 'undefined' && '__TAURI_INTERNALS__' in window;
export async function apiCall<R>(name: string, args = {}): Promise<R> {
  if (isTauri) {
    const { invoke } = await import('@tauri-apps/api/core');
    try { return await invoke<R>(name, args); }
    catch (e) {
      const err = parseAppError(e);
      if (err && typeof err === 'object' && 'code' in err) {
        const code = (err as { code: string }).code;
        if (code === 'UNAUTHORIZED' || code === 'Unauthorized') { authStore.user = null; window.location.hash = '#/login'; }
      }
      throw err;
    }
  }
  const res = await fetch(`/api/v1/${name}`, { method: 'POST', headers: {...}, body: JSON.stringify(args) });
  if (!res.ok) {
    const body = await res.json().catch(() => ({}));
    const err = parseAppError(body);
    if (res.status === 401) { authStore.user = null; window.location.hash = '#/login'; }
    // 403 → throw only (current behavior — this plan adds a toast here)
    throw err;
  }
  return res.json();
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Employee browser/Tauri UI → backend API | The UI route-gating and shell selection in this plan are NOT a security boundary — they are UX. The real boundary is the backend 403 enforced in 10-01/10-02/10-03 |
| Client-side `authStore.user.role` → shell/route selection | Trusted only for rendering decisions, never for authorization decisions — `authStore.user` is set from the backend's `auth_status`/session response, but a compromised or stale client value cannot grant access the backend would not also grant |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-04-01 | Spoofing/Elevation (client-side bypass) | `App.svelte` role branch, `routes.ts` employeeRoutes | accept | Client-side gating is explicitly documented as UX-only in this plan's objective; an Employee tampering with client state (e.g. via devtools) to force the admin `Layout`/`routes` to render would still hit real backend 403s on every API call per 10-01/10-02/10-03 — no data is exposed by a client-side bypass alone |
| T-10-04-02 | Information Disclosure (silent failure) | `client.ts` 403 handling | mitigate | Both Tauri and HTTP 403 paths now surface a visible toast instead of silently failing or crashing, so a user (or developer) is never left looking at a blank/broken screen with no signal (Task 2) |
| T-10-04-03 | Tampering (supply chain) | No new package installs in this plan | accept | Zero new npm dependencies introduced — only first-party `.svelte`/`.ts` files |
