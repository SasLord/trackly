## Файл хэшей и токенизация

**Вопрос 1.** Как гейт режет файл на токены и сверяет хэши?

| Option | Description | Selected |
|--------|-------------|----------|
| Слова + n-граммы 2–3 | Многословный маркер заносится целиком и ловится точно; общие слова в список класть не нужно. Цена — втрое больше хэшей на файл | ✓ |
| Только отдельные слова | Проще и точно по букве R6, но многословное название ловится лишь через самое редкое слово в нём | |
| Слова + склейка без пробелов | Ловит CamelCase и пути, но не фразу через пробелы | |

**User's choice:** Слова + n-граммы 2–3
**Notes:** → D-05.

**Вопрос 2.** Как нормализуется токен перед хэшированием (морфология уже отклонена SPEC)?

| Option | Description | Selected |
|--------|-------------|----------|
| lowercase + ё→е + NFC | Плюс срезание пунктуации по краям; словоформы заносятся отдельными токенами | ✓ |
| Плюс цифровая очистка | Телефон ловится в любом формате записи, но растёт риск совпасть с чужой цифровой последовательностью (случай Cargo.lock) | |
| Без нормализации | Точное побайтовое совпадение; маркер в другом регистре проходит сквозь | |

**User's choice:** lowercase + ё→е + NFC
**Notes:** → D-06.

**Вопрос 3.** Формат файла хэшей (коммитится в публичный репозиторий, виден в диффах)?

| Option | Description | Selected |
|--------|-------------|----------|
| Текст: хэш + класс | `<sha256> <класс A/B/C>`, `#`-комментарии, шапка с инструкцией для fail-closed; строки отсортированы | ✓ |
| JSON | Массив объектов {h, class, n}; комментарии-инструкции прячутся в служебный ключ | |
| Только хэши, без меток | Максимум скрытности, но сообщение гейта теряет диагностическую ценность | |

**User's choice:** Текст: хэш + класс
**Notes:** → D-07. Метка — только класс, никаких пояснений вида «фамилия такого-то».

**Вопрос 4.** SHA-256 короткого токена восстанавливается словарным перебором. Соль в репо не
спасает, KDF неприменим (хэшируется каждый токен каждого файла), секретов в CI нет.

| Option | Description | Selected |
|--------|-------------|----------|
| Принять и задокументировать | Файл хэшей — список стоп-слов без плейнтекста, а не криптозащита; значения и так в истории git (PRIV-03 принят осознанно) | ✓ |
| Хэш с фиксированной солью | Спасает от готовой радужной таблицы, от целевого словаря — нет | |
| Гейт без списка маркеров | Только регулярки по форматам; переоткрывает R6, оставляет ФИО и название организации без защиты | |

**User's choice:** Принять и задокументировать
**Notes:** → D-08.

## Язык гейта и подключение

**Вопрос 1.** На чём пишется гейт и где он лежит?

| Option | Description | Selected |
|--------|-------------|----------|
| Node .mjs в scripts/ | Zero-dependency ESM по образцу ui/scripts/*.mjs, но repo-wide; node:crypto одинаков на macOS и Linux | ✓ |
| Bash | Однородно с текущим скриптом, но sha256sum/shasum расходятся, а lowercase кириллицы и ё→е в bash — боль | |
| Rust-тест в crates/ | Единый язык с бэкендом, но cargo test на каждый коммит — десятки секунд | |

**User's choice:** Node .mjs в scripts/
**Notes:** → D-09.

**Вопрос 2.** Каталог хуков и способ включения?

| Option | Description | Selected |
|--------|-------------|----------|
| .githooks/ + setup-скрипт | `.githooks/pre-commit` + `scripts/setup-hooks.sh` (git config core.hooksPath) | ✓ |
| .githooks/ + только документация | Команда записана в документации, включать копипастом | |
| Автоподключение через pnpm postinstall | Меняет git-конфиг пользователя без его ведома, ломается в CI | |

**User's choice:** .githooks/ + setup-скрипт
**Notes:** → D-10.

**Вопрос 3.** Где документируется включение хука и правила гейта?

| Option | Description | Selected |
|--------|-------------|----------|
| Новый CONTRIBUTING.md | Каноническое место, GitHub показывает при создании PR, не засоряет пользовательский README | ✓ |
| Раздел в README.md | Всё в одном файле, но пользователь продирается через разработчицкие инструкции | |
| Шапка гейта + CLAUDE.md | Без новых файлов | |

**User's choice:** Новый CONTRIBUTING.md
**Notes:** Предъявлено, что README сейчас целиком пользовательский (установка, portable,
SmartScreen/Gatekeeper, контрольные суммы), CONTRIBUTING.md отсутствует. → D-10.

**Вопрос 4.** Что читает pre-commit и что делает без node?

| Option | Description | Selected |
|--------|-------------|----------|
| Staged-блобы, fail-closed | `git show :путь` — то, что реально уйдёт в коммит; нет node → exit 1 с инструкцией | ✓ |
| Staged-блобы, мягкий пропуск | Не блокирует работу, но защита может тихо исчезнуть | |
| Файлы рабочей копии | Проще, но расходится с содержимым коммита (`git add -p`) | |

**User's choice:** Staged-блобы, fail-closed
**Notes:** → D-11.

**Вопрос 5.** Где в ci-fast.yml стоит шаг гейта?

| Option | Description | Selected |
|--------|-------------|----------|
| Сразу после checkout | Node предустановлен на ubuntu-runner; утечка падает за секунды, а не после сборки SPA. В ci-full не дублируется | ✓ |
| На нынешнем месте | Минимальный diff в workflow | |
| После checkout + также в ci-full | Проверка кроссплатформенности гейта ценой трёх лишних прогонов | |

**User's choice:** Сразу после checkout
**Notes:** → D-12.

## Эксплуатация гейта

**Вопрос 1.** Как пополняется список маркеров, не оставляя значения в файле и истории shell?

| Option | Description | Selected |
|--------|-------------|----------|
| Интерактивный --add | Ввод без эха, нормализация тем же кодом, что и сканер, дозапись хэша и пересортировка | ✓ |
| Через stdin-пайп | Скриптуемо для пакетного занесения, но значение оседает в ~/.zsh_history | |
| Вручную через shasum | Без дополнительного кода, но нормализацию пришлось бы повторять руками | |

**User's choice:** Интерактивный --add
**Notes:** → D-15.

**Вопрос 2.** Что печатает гейт при срабатывании (логи CI публичного репозитория видны всем;
нынешний скрипт печатает само значение)?

| Option | Description | Selected |
|--------|-------------|----------|
| Путь + строка + класс | «file.md:42 — маркер класса B (ФИО)»; значение и содержимое строки не печатаются никогда | ✓ |
| Только путь и класс | Максимум скрытности, но маркер придётся искать глазами | |
| Строка с маскировкой | Удобнее всего, но окружающий контекст сам может быть наводкой | |

**User's choice:** Путь + строка + класс
**Notes:** → D-16.

**Вопрос 3.** Где живёт список исключаемых путей?

| Option | Description | Selected |
|--------|-------------|----------|
| Константы в коде гейта | Как ALLOWED в нынешнем скрипте: расширение исключений — правка кода, видимая в ревью | ✓ |
| Отдельный конфиг-файл | Править проще — и ослаблять гейт тоже проще | |

**User's choice:** Константы в коде гейта
**Notes:** → D-14.

**Вопрос 4.** SPEC R9 кладёт каталог самой Фазы 37 в исключения, но Constraints того же SPEC
требуют, чтобы артефакты фазы маркеров не содержали. Противоречие.

| Option | Description | Selected |
|--------|-------------|----------|
| Убрать исключение | Каталог фазы проверяется наравне со всеми; ловит срыв агента-исполнителя или ревьюера | ✓ |
| Оставить как в SPEC | Страхует от блокировки собственной работы, но создаёт слепую зону там, где агенты пишут про утечку | |

**User's choice:** Убрать исключение
**Notes:** Единственное содержательное отклонение от SPEC, зафиксировано в CONTEXT.md
как поправка к R9. → D-13.
