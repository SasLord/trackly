<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Local `git commit --no-verify` → CI | The hook is a local, bypassable opt-in; CI is the only boundary an attacker/careless committer cannot skip without repo-admin action |
| CI job env → public log output | `ci-fast.yml`'s step output is visible to anyone who can view Actions runs on a public repo |
| Populated `scripts/privacy-tokens.sha256` → git history | Once committed, the hash list itself becomes permanent — but per D-08 it is a stop-word list, not a secret, so this is an accepted disposition |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-37-05 | Repudiation / Tampering | `git commit --no-verify` bypassing the local hook | mitigate | Not solvable locally by design (git hooks are always locally bypassable) — the `ci-fast.yml` step is the backstop, documented explicitly in the kept comment block as "a strausback, not a duplication" per SPEC Constraints; this plan's Task 3 verifies the CI step actually runs and blocks on a positive fixture |
| T-37-02 | Information Disclosure | Production `scripts/privacy-tokens.sha256` | accept (D-08, restated) | Same accepted residual risk as plan 37-03's fixture; header text required by Task 1's acceptance criteria |
| T-37-14 | Elevation of Privilege (low) | `scripts/setup-hooks.sh` silently changing a developer's git config | accept | D-10 explicitly rejected the auto-wiring alternative (`postinstall`) for this exact reason — `setup-hooks.sh` is opt-in, one command, documented in `CONTRIBUTING.md`, never run automatically |
| T-37-15 | Tampering | `design-system-v2/` guillemet-flagged files "fixed" by weakening the gate instead of cleaning content | mitigate | Hard prohibition #4 explicitly forbids adding an exclusion/override; Task 3's action requires cleaning or untracking the specific flagged file(s) instead |
