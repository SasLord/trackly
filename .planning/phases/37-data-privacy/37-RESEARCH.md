  Edit-правки под протоколом (полагается на дисциплину) и полностью ручная чистка

**Файл хэшей и токенизация (R6)**

- **D-05: Токен = отдельное слово И скользящее окно из 2–3 слов (n-граммы).** Многословный
  маркер (полное название организации, ФИО целиком) заносится в список **целиком** и ловится
  точно, при этом общеупотребимые слова в список класть не нужно — иначе они дают ложные
  срабатывания по всему репозиторию. Цена: втрое больше хэшей на файл (десятки мс на весь
  репозиторий, SHA-256 короткой строки ~микросекунды). Отвергнуты: только отдельные слова
  (многословное название ловится лишь через самое редкое слово в нём — либо дыра, либо шум)
  и «слова + склейка без разделителей» (не ловит фразу через пробелы).
  > **Уточнение исследования (см. Common Pitfalls → Pitfall 1):** цена «десятки мс» верна для
  > `pre-commit` (staged-only). Эмпирический замер полного HEAD-скана на этом репозитории дал
  > ~6.9 млн хэшей за ~5.4 с — на два порядка больше, всё ещё приемлемо для CI, но не «десятки
  > мс». Решение не меняется, только формулировка цены в документации гейта.

- **D-06: Нормализация перед хэшированием — `lowercase` + `ё→е` + Unicode NFC + срезание
  пунктуации по краям токена.** Стемминга и морфологии нет (отклонено SPEC) — нужные
  словоформы заносятся в список отдельными токенами. Латинская транслитерация фамилии
  (`Ivanov`-подобная) — тоже отдельный токен, автоматически не выводится. Отвергнуты:
  дополнительная «цифровая очистка» (удаление пробелов/дефисов/скобок внутри числовых
  токенов — растит риск совпасть с чужой цифровой последовательностью, ровно случай
  `Cargo.lock`) и полное отсутствие нормализации (маркер в другом регистре проходит сквозь).

- **D-07: Формат файла хэшей — текстовый, строка = `<sha256> <класс A|B|C>`,
  `#`-комментарии, шапка с инструкцией по восстановлению.** Метка класса нужна, чтобы гейт
  мог сказать «маркер класса B (ФИО)», не называя значения (см. D-12), а шапка — чтобы
  fail-closed из R7 объяснял, что делать. Строки отсортированы: diff читаемый, порядок
  стабильный. Отвергнуты: JSON (комментарии-инструкции приходится прятать в служебный ключ)
  и голый список хэшей без меток (сообщение гейта теряет диагностическую ценность).
  **Метка — только класс.** Никаких пояснений вида «фамилия такого-то» — это наводка.

- **D-08: Остаточный риск словарного восстановления хэшей принят осознанно и
  документируется в шапке файла.** SHA-256 короткого низкоэнтропийного токена (фамилия,
  домен, аббревиатура) перебирается по словарю за секунды; соль, лежащая в том же
  репозитории, от целевого словаря не спасает; KDF с растяжкой неприменим, потому что
  хэшируется каждый токен каждого проверяемого файла; секретов у CI для этой проверки нет
  (Constraint SPEC). Ключевое: сами значения **и так** лежат в истории git — PRIV-03 принят
  осознанно, — поэтому маргинальный риск близок к нулю. Файл хэшей — это список стоп-слов
  без плейнтекста, а не криптозащита; так его и надо описать. Отвергнуты: фиксированная
  соль в коде гейта (нулевая цена, но и почти нулевая польза — создаёт ложное ощущение
  защиты) и отказ от хэшей в пользу одних регулярок по форматам (переоткрывает R6 и
  оставляет ФИО и название организации без защиты вообще).

**Язык гейта, размещение, подключение (R5, R10)**

- **D-09: Гейт — zero-dependency Node ESM (`.mjs`) в корневом `scripts/`.** По образцу
  `ui/scripts/check-print-isolation.mjs` (структурный гейт, самотест через аргумент-путь), но
  **не** в `ui/scripts/`: гейт repo-wide, а не фронтендовый, и в `pnpm --dir ui lint` он по
  решению SPEC не подключается. `node:crypto` даёт одинаковый SHA-256 на macOS и Linux, а
  юникод-нормализация из D-06 в bash практически неисполнима (`sha256sum` против `shasum`,
  lowercase кириллицы, `ё→е`). Отвергнуты: bash (текущий язык `check-privacy-requisites.sh`)
  и Rust-тест в `crates/` (`cargo test` на каждый `git commit` — десятки секунд, плюс в
  репозитории есть унаследованный висячий тест).

- **D-10: Хук — `.githooks/pre-commit` + односторочный `scripts/setup-hooks.sh`, который
  делает `git config core.hooksPath .githooks`.** Git не включает хуки сам; одна команда
  вместо запоминания синтаксиса. Отвергнуты: только документация без setup-скрипта и
  автоподключение через `postinstall` в `ui/package.json` (меняет git-конфиг пользователя
  без его ведома и мешает в CI).

- **D-11: `pre-commit` проверяет staged-блобы (`git show :путь`), а не файлы рабочей копии;
  при отсутствии `node` — `exit 1` с инструкцией (fail-closed).** Чтение рабочей копии
  разошлось бы с тем, что реально уйдёт в коммит: `git add -p` частичного ханка пронёс бы
  маркер мимо гейта. Мягкий пропуск без node отвергнут по той же логике, что R7 — защита не
  должна тихо исчезать. Отвергнуты: staged + мягкий пропуск и проверка рабочей копии.

- **D-12: Шаг гейта в `ci-fast.yml` переезжает наверх — сразу после `Checkout`.** Сейчас он
  стоит после `apt-get install`, `pnpm install` и сборки SPA, то есть утечка обнаруживается
  через 5–10 минут после старта. Гейту не нужны ни `setup-node`, ни `pnpm install`: на
  `ubuntu-latest` Node предустановлен. В `ci-full.yml` шаг **не** дублируется. Отвергнуты:
  оставить на нынешнем месте (минимальный diff, но обратная связь через 10 минут) и добавить
  такой же шаг в матрицу `ci-full` (три лишних прогона ради проверки кроссплатформенности,
  которую дешевле закрыть локальным запуском на macOS).

**Эксплуатация гейта (R7–R9)**

- **D-13: Каталог `.planning/phases/37-data-privacy/` НЕ исключается из проверки** — вопреки
  буквальному перечислению в R9. Артефакты фазы по её же дисциплине не цитируют значений,
  значит гейт им не мешает; зато он ловит именно тот срыв, который наиболее вероятен —
  агента-исполнителя или ревьюера, процитировавшего реальное значение из истории git в
  PLAN/SUMMARY/REVIEW. Оставшиеся исключения по путям: сам файл хэшей, `node_modules`,
  `target/`, `Cargo.lock` (известное цифровое ложное срабатывание).

- **D-14: Список исключаемых путей и allowlist бинарников — константы в коде гейта**,
  рядом с комментарием «почему», как нынешний `ALLOWED` в `check-privacy-requisites.sh`.
  Расширение исключения = правка кода гейта, видимая в code review. Отдельный конфиг-файл
  отвергнут: править проще — и ослаблять гейт тоже проще.

- **D-15: Пополнение списка — интерактивный режим `--add` без эха ввода.** Скрипт
  спрашивает значение и класс, нормализует **тем же кодом**, что и сканер (D-06),
  дописывает хэш и пересортировывает файл. Значение не попадает ни в файл, ни в
  `~/.zsh_history`, ни в контекст агента. Отвергнуты: пайп из stdin (значение оседает в
  истории shell) и ручной `shasum` с копипастом (нормализацию пришлось бы повторять руками —
  ошибка в регистре или `ё` даёт хэш, который никогда не совпадёт, и гейт молча слепнет).

- **D-16: Сообщение о срабатывании — `путь:строка — маркер класса X`, без значения и без
  содержимого строки.** Логи CI публичного репозитория видны всем; нынешний скрипт печатает
  само значение (`value: "…"`) — этот приём поглощаемый гейт **не наследует**. Номер строки
  утечкой не является: при `pre-commit` файл ещё не опубликован, а в CI гейт падает как раз
  на уже видимом содержимом. Отвергнуты: только путь и класс (в большом файле маркер
  придётся искать глазами) и печать строки с маскировкой маркера (окружающий контекст сам
  может быть наводкой).

**Ограничения, вытекающие из решений (выведены, не обсуждались)**

- **C-01: Самотест гейта не может использовать боевой файл хэшей.** Acceptance R6 требует
  фикстуру «с токеном, чей хэш занесён в список» — против боевого списка такая фикстура
  обязана содержать **реальное значение**, то есть тест сам стал бы утечкой. Следствие: гейт
  принимает путь к файлу хэшей аргументом (например `--hashes <path>`), а тесты гоняются
  против отдельного тестового списка с вымышленным токеном («Иванов И.И.», `example.local`).
  Тот же аргумент закрывает R7: несуществующий/пустой/нечитаемый файл → `exit 1`, и это
  проверяется передачей заведомо отсутствующего пути.

- **C-02: Регрессия старого поведения обязательна.** Поглощение
  `scripts/check-privacy-requisites.sh` не должно потерять ни одного его случая: allowlist
  литералов по ключам `inn|kpp|okpo|ogrn|phone|fax` в `*.rs`/`*.html` со всеми ~20
  утверждёнными плейсхолдерами (уточнено исследованием: 23 литерала, включая один пустой)
  и pattern'ом, различающим JSON-ish и Rust-struct-init формы. Acceptance: подставленный
  нефиктивный литерал `inn`/`ogrn` в `.rs` по-прежнему валит гейт.

- **C-03: Порядок коммитов внутри фазы.** Чистка (R1–R4) идёт отдельными коммитами ДО того,
  как гейт подключается в `pre-commit`/CI (R10) — иначе первый же коммит фазы блокируется
  собственным гейтом. Разработку самого гейта (R5–R9) можно вести параллельно с чисткой;
  запрещено только его **включение** до её завершения.

- **C-04: Артефакты фазы под собственным гейтом (следствие D-13).** Перед каждым коммитом
  фазы — прогон гейта по staged. Это же страхует от классической ловушки проекта:
  генерируемые агентами REVIEW/VERIFICATION цитируют реальные значения, вычитанные из
  истории git.

- **C-05: Сообщения коммитов фазы тоже не содержат маркеров.** Хук проверяет содержимое
  файлов, а не commit message — дисциплина здесь только процедурная, и планировщик обязан
  записать её в план явным запретом.

- **C-06: `.gitignore` и удаление из индекса — разные операции.** `git rm --cached` для
  `.planning/reference/act-word-source/` плюс запись в `.gitignore`; сам каталог на диске
  пользователя остаётся (образец нужен ему локально).

- **C-07:** Один `cargo test` за раз (память `cargo_no_concurrent_test`); в репозитории есть
  унаследованный висяк `login_remember_persistent_cookie` — прогонять со `--skip`
  (память `workspace_test_hangs_auth_remember_cookie`). Для этой фазы Rust-тесты почти не
  задействованы, но проверка «`ci-fast` зелёный» их затрагивает.

### Pattern 1: Один детектор, два режима входных данных

**What:** `check-privacy.mjs` не знает, вызван ли он из хука или из CI — он получает СПИСОК
`{path, content}` через общую функцию `collectTargets(mode)`, где `mode` = `'staged'` (читает
через `git show :путь` из `git diff --cached --name-status -z --diff-filter=ACMR`, что
автоматически пропускает удалённые файлы — статус `D` не входит в `ACMR`) или `'head'` (читает
через `git ls-files -z` + `fs.readFileSync`).
**When to use:** Всегда — это единственный способ выполнить требование CONTEXT «сканер общий».
**Example:**
```js
// Source: паттерн выведен из ui/scripts/check-print-isolation.mjs (аргумент-путь для
// самотеста) + git plumbing docs (git-diff, git-show)
import { execFileSync } from 'node:child_process';

function stagedPaths() {
  const raw = execFileSync(
    'git',
    ['diff', '--cached', '--name-status', '-z', '--diff-filter=ACMR'],
    { encoding: 'utf8' },
  );
  // NUL-delimited: "STATUS\0path\0STATUS\0path\0..." (rename adds an extra old-path field)
  const parts = raw.split('\0').filter(Boolean);
  const paths = [];
  for (let i = 0; i < parts.length; ) {
    const status = parts[i++];
    if (status.startsWith('R') || status.startsWith('C')) i++; // skip old path
    paths.push(parts[i++]);
  }
  return paths;
}

function readStagedBlob(relPath) {
  // ":путь" reads the INDEX version (stage 0), not the working tree — this is what
  // will actually be committed, including partial `git add -p` hunks (D-11 rationale).
  return execFileSync('git', ['show', `:${relPath}`], { encoding: 'utf8' });
}
```

### Pattern 2: n-грамм токенизация построчно (D-05/D-06)

**What:** Для каждой строки файла — извлечь run'ы `[\p{L}\p{N}]+` (буквы+цифры любого
алфавита, требует флаг `u`), затем скользящее окно 1–3 слова, нормализация перед хэшем.
**When to use:** mode 2 сканера, для отчёта `путь:строка`.
**Example:**
```js
// Source: паттерн проверен эмпирически на этом репозитории (см. Validation Architecture /
// benchmark below), Unicode property escapes — MDN RegExp Unicode property escapes
const WORD_RE = /[\p{L}\p{N}]+/gu;

function normalize(s) {
  return s
    .toLowerCase()               // Cyrillic case-fold не требует locale (проверено: "СМУ" → "сму")
    .replace(/ё/g, 'е')
    .normalize('NFC');
}

function lineNGrams(line) {
  const words = line.match(WORD_RE);
  if (!words) return [];
  const grams = [];
  for (let n = 1; n <= 3; n++) {
    for (let i = 0; i + n <= words.length; i++) {
      grams.push(normalize(words.slice(i, i + n).join(' ')));
    }
  }
  return grams;
}
```
Важное следствие для D-06: раз токенизация уже отбрасывает всё, кроме `\p{L}\p{N}`,
«срезание пунктуации по краям токена» **не требует отдельного шага** — пунктуация физически не
попадает в извлечённый run. Отдельная забота нужна только для многословных n-грамм: соединять
слова обычным пробелом (`join(' ')`), а не куском исходной строки — иначе дефис/тире/кавычки
между словами протекут в хэшируемую строку и дадут хэш, который никогда не совпадёт с хэшем
того же n-грамма, встреченного с другой пунктуацией между теми же словами (гейт бы тихо
слеп — ровно риск, который D-06 просит закрыть).

### Anti-Patterns to Avoid

- **Построчный `.split('\n')` + `.split(':')` парсинг вывода `git diff --name-status` без
  `-z`:** в РЕПОЗИТОРИИ УЖЕ ЕСТЬ файлы с пробелом в имени
  (`.planning/reference/design-system-v2/` — 2 файла с кириллическими именами, подтверждено
  `git ls-files | grep -c ' '` → 2). Наивный парсинг без NUL-делимитера либо разорвёт имя по
  пробелу, либо (для путей вне design-system-v2, если такие появятся) пропустит файл со
  спецсимволами молча — тихий пропуск прямо противоречит философии fail-closed этой фазы.
- **`exec()` со строковой интерполяцией пути в shell-команду:** `execFileSync('git', [...])` с
  массивом аргументов — не `execSync(\`git show :${path}\`)`. Пути с пробелами/кавычками иначе
  либо ломают вызов, либо (хуже) допускают shell-инъекцию через специально сформированное имя
  файла в PR с чужой веткой.
- **Смешивание allowlist-режима (mode 1) и хэш-режима (mode 2) в одном проходе по файлу без
  разделения:** allowlist-режим специально ограничен `*.rs`/`*.html` (C-02 регрессия должна
  остаться идентичной старому скрипту); если оба режима слить в общий цикл «для каждого файла
  все проверки», легко случайно расширить allowlist-режим на все файлы или наоборот сузить
  хэш-режим — держать как две независимые функции с независимым списком целевых файлов.

## Common Pitfalls

### Pitfall 1: Полная HEAD-стоимость n-грамм-хэширования занижена в CONTEXT

**What goes wrong:** D-05 оценивает стоимость n-грамм как «десятки мс на весь репозиторий».
Эмпирический замер на этом репозитории (335 файлов текста после исключения бинарников/лок-файлов,
336 146 строк, ~18 МБ) дал **6 898 522 хэша за 5421 мс** (однопоточный синхронный прогон,
Node 22, dev-машина). Это на два порядка больше заявленной оценки.
**Why it happens:** Оценка D-05, судя по формулировке («втрое больше хэшей... SHA-256 короткой
строки ~микросекунды»), экстраполирована с масштаба одного файла/staged-diff, а не всего HEAD
(336k строк).
**How to avoid:** Не менять решение D-05/D-06 (n-граммы остаются) — 5.4 с на **полный HEAD-скан
в CI** абсолютно приемлемы (job и так занимает 20–30 минут; фаза 37 явно хочет привязать этот
шаг к самому НАЧАЛУ пайплайна именно из-за его дешевизны относительно остального). Для
`pre-commit` (staged-only, обычно единицы файлов) оценка D-05 «десятки мс» ПОДТВЕРЖДАЕТСЯ:
экстраполяция по замеренному отношению 20.5 хэшей/строку даёт ~10 мс на файл среднего размера
(~230 строк). Единственное практическое следствие: не заявлять «десятки мс» как факт про CI-шаг
в документации гейта — заявлять реальное измеренное число или не заявлять число вовсе.
**Warning signs:** Если после реализации CI-шаг ci-fast.yml замедлится заметно больше ~10 с,
проверить, не читается ли каждый файл несколько раз (например, отдельно для mode 1 и mode 2)
или не создаётся ли новый `Buffer`/`Hash`-объект избыточно на каждый n-грамм при отсутствии
early-exit после первого найденного совпадения на файл.

### Pitfall 2: `.planning/reference/` содержит на 11 файлов больше, чем R4 явно называет

**What goes wrong:** R4/acceptance проверяют конкретно `.planning/reference/act-word-source/`
(3 файла класса D). D-04 (locked) требует игнорировать **весь** `.planning/reference/` —
и в HEAD на 2026-08-14 в этом каталоге уже есть ВТОРОЙ, не связанный с утечкой подкаталог:
`.planning/reference/design-system-v2/` — **11 файлов** (HTML-макеты дизайн-системы + JS,
2 из них с кириллическими именами и пробелами). `git rm --cached -r .planning/reference/`
untrack'ает все 14 файлов разом, не только 3.
**Why it happens:** D-04 в CONTEXT формулирует это как защиту от «нового» каталога-образца в
будущем («Узкий паттерн оставляет соседний НОВЫЙ каталог образцов версионируемым») — на момент
discuss-фазы, судя по формулировке, не было явно зафиксировано, что такой каталог уже
существует сегодня, а не гипотетически появится позже.
**How to avoid:** Не противоречит ни одному решению — D-04 и так требует untrack всего дерева.
Но планировщику нужно явно занести в план: (1) acceptance-проверку расширить с
`git ls-files .planning/reference/act-word-source/` (пусто) до `git ls-files
.planning/reference/` (пусто целиком); (2) один быстрый просмотр `design-system-v2/` на предмет
классов A/B/C самим автором чистки ДО untrack (не потому что это требуется R1–R3 — каталог вне
их пофайловой разведки, — а потому что untrack всё равно происходит и это дешёвая
дополнительная проверка). Найдено программно: 2 из 11 файлов содержат Cyrillic-текст в
guillemet-кавычках (типичный паттерн UI-лейблов дизайн-системы, не обязательно утечка) — не
проверялось предметно, это находка «есть сигнал, нужен взгляд человека», а не подтверждённый
класс A/B/C.
**Warning signs:** Если план R4 пишет только про 3 файла `act-word-source/`, а acceptance
проверяет только тот же подпуть — `design-system-v2/` останется версионируемым несмотря на
изменённый `.gitignore` (потому что уже ЗАКОММИЧЕННЫЕ файлы не перестают быть tracked от одной
правки `.gitignore` — нужен явный `git rm --cached`, см. Pitfall 3).

### Pitfall 3: `.gitignore` не untrack'ает уже закоммиченные файлы (C-06, известно, но легко забыть в acceptance-формулировке)

**What goes wrong:** Добавление пути в `.gitignore` останавливает БУДУЩИЕ `git add`, но ничего
не делает с файлами, уже находящимися в индексе. Без явного `git rm --cached -r
.planning/reference/` (сам файл остаётся на диске — флаг `--cached`, не `git rm -r` без него)
`git ls-files` продолжит показывать все 14 файлов даже после правки `.gitignore`.
**Why it happens:** Интуитивно кажется, что «добавили в gitignore → пропало из репо» — это
верно только для НЕотслеживаемых файлов.
**How to avoid:** Порядок операций: (1) `git rm --cached -r .planning/reference/` (снимает с
учёта, оставляет на диске), (2) добавить `.planning/reference/` в `.gitignore` (не даёт снова
попасть при следующем `git add .`), (3) `git status` должен показать каталог как
untracked-but-ignored (не отображается вовсе при `git status` без `-uall`, и НЕ отображается в
`git status --ignored` списком «Untracked», а в отдельной секции «Ignored»). Верификация в
acceptance criterion: `git ls-files .planning/reference/` — пустой вывод; `git check-ignore
.planning/reference/act-word-source/act-sample.docx` — код возврата 0 (путь действительно
игнорируется).
**Warning signs:** `git status` после уборки продолжает показывать каталог как untracked
(секция «Untracked files», а не «Ignored files» или отсутствие вовсе) — значит `.gitignore`
запись отсутствует или не матчит фактический путь.

### Pitfall 4: `setRawMode` недоступен вне TTY — `--add` должен явно проверять `process.stdin.isTTY`

**What goes wrong:** `process.stdin.setRawMode` — `undefined`, если stdin не является TTY
(подтверждено эмпирически: в неинтерактивном контексте `isTTY === undefined`,
`setRawMode === undefined`). Наивный вызов `process.stdin.setRawMode(true)` без проверки упадёт
с `TypeError: process.stdin.setRawMode is not a function` при запуске `--add` из CI, из пайпа
или из некоторых обёрток редакторов/агентов.
**Why it happens:** Raw-mode — терминальная фича; она физически не существует у пайпа/файла на
stdin.
**How to avoid:** `--add` в самом начале проверяет `if (!process.stdin.isTTY) { console.error(...);
process.exit(1); }` — соответствует духу D-15 (интерактивный режим, не пайп) и духу fail-closed
проекта: лучше явная ошибка, чем скрытое чтение мусора вместо значения.
**Warning signs:** Тест/самотест `--add` в CI зависает или падает с невнятной ошибкой вместо
понятного сообщения «--add требует интерактивного терминала».

### Заголовок-конвенция гейта (форма, скопированная с `check-print-isolation.mjs`)

```js
#!/usr/bin/env node
// [check-privacy] Постоянный гейт против утечки реквизитов организации и ФИО
// сотрудников (PRIV-01/PRIV-02). Репозиторий ПУБЛИЧНЫЙ; закоммиченное остаётся
// в истории git даже после удаления из HEAD (CLAUDE.md §Constraints) — поэтому
// единственная durable-защита — не дать маркеру попасть в коммит вообще.
//
// Режимы:
//   mode 1 (allowlist, унаследован от check-privacy-requisites.sh, C-02):
//     литералы по ключам inn|kpp|okpo|ogrn|phone|fax в *.rs/*.html должны быть
//     в захардкоженном ALLOWED-списке.
//   mode 2 (n-грамм SHA-256, R6): каждый файл токенизируется на n-граммы (1-3
//     слова), нормализуется (D-06) и сверяется с --hashes <путь> файлом хэшей.
//
// Zero-dependency: только node:fs/path/url/crypto/child_process/readline.
//
// Usage:
//   node scripts/check-privacy.mjs                      # весь HEAD (CI-режим)
//   node scripts/check-privacy.mjs --staged              # staged-блобы (pre-commit)
//   node scripts/check-privacy.mjs --hashes <path>        # переопределить файл хэшей (тесты, C-01)
//   node scripts/check-privacy.mjs --add                  # добавить токен интерактивно (D-15)
```

### Known Threat Patterns for этой фазы

| Pattern | STRIDE | Standard Mitigation |
|---|---|---|
| Обход гейта через `git commit --no-verify` | Repudiation / Tampering | Не решается технически (хук — локальная опция git) — закрывается CI-шагом как страховкой (D-12); задокументировано как «а не как дублирование» в Constraints SPEC |
| Словарный перебор SHA-256 файла хэшей для восстановления низкоэнтропийных токенов (фамилия/аббревиатура) | Information Disclosure | Осознанно принятый остаточный риск (D-08) — значения и так в истории git (PRIV-03 отложен пользователем); файл хэшей описан как «список стоп-слов, а не криптозащита» |
| Path traversal / shell-инъекция через специально сформированное имя файла в staged diff | Tampering | `execFileSync` с массивом аргументов, не строковая интерполяция в shell; NUL-делимитированный git-плампинг (см. Common Pitfalls / Pattern 1) |
| Тихий обход через файл, отсутствующий в `git diff --cached --diff-filter=ACMR` (например, TypeChange `T` или Unmerged `U`) | Tampering | `--diff-filter=ACMR` осознанно включает только Added/Copied/Modified/Renamed; при необходимости покрыть экзотические статусы — решение оставлено планировщику (не залочено CONTEXT), низкий риск для этого репозитория (нет submodule/symlink паттернов, подтверждено отсутствием `.gitmodules`) |
