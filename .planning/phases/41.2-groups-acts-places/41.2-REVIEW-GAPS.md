# Фаза 41.2 (gap-closure 17..30): отчёт ревью кода

**Проверено:** 2026-11-06
**Глубина:** standard (только хунки `git diff 8a0124f9..HEAD`, окружающий код читался для контекста)
**Файлов:** 33
**Статус:** issues_found

## Summary

Проверены изменения планов 41.2-17..30: откат членства и мест при удалении, правке и возврате
акта (D-40, D-42, D-44..D-48), выбор при разбиении группы (MoveGroup против Release), новые
маршруты предварительного вопроса в HTTP и Tauri, попапы выбора в UI, вкладки «Мест» (D-43) и
тишина при исчезнувшей группе (D-41).

Что сделано правильно:
- Атомарность удаления (D-42). Конфликт без выбора возвращает `DeleteRun::NeedsChoice` до
  `tx.commit()`, транзакция откатывается при drop, рассылка идёт только после коммита.
- Проверка `ensure_places_match` в `do_return` стоит до первой записи. В `update_return` она
  стоит после шагов 8–9, но там всё внутри одной транзакции writer'а, и `Err` откатывает её
  целиком.
- Все новые маршруты (`acts_return_group_split_preview`, `acts_update_return_group_split_preview`,
  `group_choices` в удалении, `group_split` в возврате и в правке возврата) проходят через
  `authorize(caller, &Action::MutateActs)`.

Главные проблемы:
1. Сервер молча подставляет `Release`, если выбора нет. Предварительный вопрос правки возврата
   считается по состоянию ДО отката удалённых позиций. Поэтому возможен случай, когда
   пользователя не спросили, а участник выведен из группы. Это прямо нарушает D-45.
2. При `MoveGroup` покрытые дочерние группы едут на место родителя-разбиения, а не на место
   возврата, которое для них указал пользователь. Проверка `places_match` на них не смотрит.

## Critical Issues

### CR-01: выбор по разбиению по умолчанию — `Release`, а предварительный вопрос правки возврата расходится с транзакцией. Группа разбивается молча (нарушение D-45)

**Status:** fixed — `9d5c494c` (`fix(41.2): CR-01 …`). Выбор передаётся как `Option` до сервиса;
разбиение без выбора ничего не пишет и отвечает `VALIDATION` по полю `group_split`. Вопрос правки
возврата считается тем же путём записи (`update_return_with_split` в режиме `Preview`, транзакция
всегда откатывается). Регрессия: `acts_return_split_http::http_update_return_split_after_restoring_removed_member_asks_and_writes_nothing`,
`acts_return_split_http::http_return_applies_group_split_choice`.

**File:** `crates/trackly-app/src/tauri_cmds/acts.rs:79`, `crates/trackly-app/src/tauri_cmds/acts.rs:151`, `crates/trackly-app/src/services/act_service.rs:2503-2615` (preview), `crates/trackly-app/src/services/act_service.rs:2928-3190` (транзакция `update_return_with_split`)

**Issue:** D-45: частично возвращаемая контейнерная группа «не освобождается молча», о ней
обязательно спрашивают. Сейчас вопрос задаёт только клиент, по ответу `*_group_split_preview`.
Сервер, получив запрос без `group_split`, выполняет `unwrap_or(GroupSplitChoiceDto::Release)`
и выводит возвращаемых участников из группы, ничего не сообщив. Поэтому любое расхождение
между предварительным вопросом и самой записью приводит к тихому разбиению.

Для правки возврата такое расхождение заложено в код. `update_return_group_split_preview`
строит `added_plan` и `retained_plan` по снимку групп с читающего соединения, то есть ДО
шага 9. В транзакции `added_plan` строится ПОСЛЕ шага 9 (строка 3189, и в комментарии прямо
сказано: «снимок групп должен учитывать возвраты групп на прежнее место»). На шаге 9
устройства, убранные из возврата, возвращаются в группу через `restore_membership_in_tx`.

Сценарий, который воспроизводится:
- контейнер G = {A, B}. Возврат R вернул A, A выведен из G, теперь G = {B};
- в правке R пользователь убирает A и добавляет B;
- preview видит G = {B}, B возвращается: группа покрыта, это `move`, вопроса нет, клиент
  шлёт запрос без `groupSplit`;
- в транзакции после шага 9 G = {A, B}, B возвращается один: это `split`, срабатывает
  умолчание `Release`, B молча выводится из группы, группа остаётся на месте;
- пользователю было показано (точнее, подразумевалось) «группа переедет», а получилось
  противоположное.

Та же гонка есть и у `do_return`: если между preview и отправкой другая сессия изменит
состав группы, сработает тот же тихий `Release`.

**Fix:** сделать выбор обязательным на сервере, по образцу `needs_group_restore` из D-42.
Если `plan.splits` не пуст, а выбора нет, запись не выполняется.
```rust
// apply_return_plan_in_tx / do_return_with_split / update_return_with_split
pub(crate) enum SplitDecision { Ask, Release, MoveGroup }
...
if !plan.splits.is_empty() && decision == SplitDecision::Ask {
    return Err(AppError::Validation {
        field: "group_split".into(),
        message: "Возврат разделяет группу: нужен выбор".into(),
    }); // или Ok(NeedsSplitChoice(dto)) по образцу DeleteRun::NeedsChoice
}
```
Транспорт: `group_split: Option<GroupSplitChoiceDto>` передавать как `Option` до самого
сервиса, без `unwrap_or(Release)`. Для preview правки возврата есть два способа:
(а) выполнять те же шаги 8–11 в транзакции writer'а и всегда откатывать её (dry-run), чтобы
у вопроса и записи был один источник правды;
(б) хотя бы применять к снимку эффект шага 9: вернуть в группы устройства из `removed`, у
которых есть `prior_release_effect_id_in_tx`.
Нужен интеграционный тест «убрать A + добавить B» с проверкой, что без выбора ничего не
записано.

### CR-02: `MoveGroup` увозит покрытые дочерние группы на место родителя-разбиения, а место возврата, указанное для них, теряется

**Status:** fixed — `f3864339` (`fix(41.2): CR-02 …`). В `places_match`/`target_place_id` разбиения
входит цель покрытых дочерних переносов, которые едут вместе с ним (общая функция
`return_move_target`). Регрессия: `group_act_plan::tests::split_places_match_counts_covered_nested_anchor_that_rides_along`,
`acts_groups::return_partial_move_group_with_nested_anchor_on_other_place_is_rejected`
(контроль: `..._on_same_place_moves_together`).

**File:** `crates/trackly-app/src/services/group_act_plan.rs:526` (`places_match` только по прямым членам), `crates/trackly-app/src/services/group_act_plan.rs:805-812` (пропуск `move` у ребёнка), `crates/trackly-app/src/services/group_act_plan.rs:957-970` (поддерево ребёнка добавляется в синтетический перенос)

**Issue:** при `MoveGroup` у разбиения S его покрытые дочерние переносы (`plan.moves`, у
которых `detach.parent_group_id == S`) не выполняются самостоятельно. Их
`subtree_device_ids` добавляются в синтетический перенос S и едут на `S.target_place_id`.
При этом:
- `places_match` и `target_place_id` у S считаются только по `returned_direct` (прямым
  членам), а места возврата устройств покрытого ребёнка не учитываются;
- у покрытой якорной группы-ребёнка цель берётся из места возврата её якоря, у покрытого
  контейнера-ребёнка — из `GroupMove.target_place_id`. Обе цели здесь отбрасываются.

Пример. Контейнер «АРМ» (прямые 10, 11, 12) с вложенной якорной группой «Системный блок»
(якорь 30). Возвращаются 10 и 11 на место X, якорь 30 на место Y. Preview пишет
`places_match = true`, и кнопка «Изменить расположение группы» доступна. После `MoveGroup`
устройство 30 и вся его группа окажутся на X: в `do_return` для `moved_device_ids` берётся
`group_placed`, то есть текущее место устройства. Место Y, явно выбранное в форме, молча
пропадает, а акт утверждает, что устройство вернули туда. По смыслу это то же расхождение
мест, которое D-46 запрещает для целиком возвращаемой группы.

**Fix:** при подсчёте `places_match` и `target_place_id` у разбиения учитывать места возврата
всех возвращаемых устройств покрытых дочерних переносов, которые поедут вместе с ним:
```rust
let riding_children: Vec<&GroupMove> = moves.iter()
    .filter(|m| m.detach.as_ref().is_some_and(|d| d.parent_group_id == g.id))
    .collect();
let mut devs = returned_direct.clone();
for m in &riding_children {
    devs.extend(m.subtree_device_ids.iter().copied().filter(|d| returned.contains(d)));
}
let places: HashSet<Option<i64>> =
    devs.iter().map(|d| return_places.get(d).copied().flatten()).collect();
```
Есть и другой вариант: при несовпадении целей не сливать ребёнка в перенос S, а выполнять
его отдельно с отцеплением. Нужен тест на вложенный якорь с другим местом возврата под
`MoveGroup`.

## Warnings

### WR-01: при «забывании» (D-48) переписывается эффект того же акта, а не следующего. Для двух переносов одной группы внутри одного акта история и `from_place_id` следующего акта получаются неверными

**File:** `crates/trackly-infra/src/repos/groups_sqlite.rs:1119-1134`, `crates/trackly-infra/src/repos/place_movements_sqlite.rs:295-348`, `crates/trackly-app/src/services/group_act_plan.rs:1340-1360`

**Issue:** у акта может быть два эффекта `move` одной группы: e1 P→X и e2 X→Y. Так бывает
при правке возврата со сменой места у якоря (D-13) или у члена контейнера (D-47). Пусть
затем группа уехала дальше, на Z, актом A2 (эффект Y→Z) или вручную, и после этого
удаляют акт A. Откат идёт в обратном порядке, e2 обрабатывается первым:
- `rebase_later_move_effects_in_tx(after = e2.id, from IS Y, new_from = X)` переписывает
  эффект A2: Y→Z становится X→Z;
- `forget_group_move_rows_in_tx` удаляет ОБЕ строки журнала акта A. Преемник строки X→Y
  получает «откуда» = X, хотя должно быть P. Строки одного акта исключены из поиска
  преемника, поэтому цепочка P→X→Y не сворачивается.

Затем обрабатывается e1 (группа на Z, а не на X, значит снова «забыть»).
`rebase(after = e1.id, from IS X)` берёт `MIN(id)` с `from = X`, и это сам e2: эффекты
удаляются только после цикла. Эффект A2 так и остаётся X→Z. В итоге в истории X→Z вместо
«до акта» (P)→Z. При последующем удалении A2 группа вернётся на X, на место, которое
существовало только внутри удалённого акта. Это нарушает D-48(2).

**Fix:** в `rebase_later_move_effects_in_tx` исключать эффекты того же акта
(`AND act_id != ?act`). В `revert_move_effect_in_tx` при «забывании» брать за `new_from`
`from_place_id` самого раннего `move` этого акта по группе. В
`forget_group_move_rows_in_tx` сворачивать цепочку строк одного акта по сущности: для
преемника брать `from` первой строки цепочки, а не последней. Нужен тест «два move одного
акта + перенос после».

### WR-02: дубликат ключа `{#each items as item (item.group_id)}`: одна группа может прийти дважды

**File:** `crates/trackly-app/src/services/act_service.rs:2606-2608`, `ui/src/features/acts/GroupSplitChoicePopup.svelte:32`

**Issue:** `update_return_group_split_preview` склеивает `out.items` из двух независимых
планов, `added_plan` и `retained_plan`, без дедупликации по `group_id`. Если одна и та же
группа разбивается и добавленными позициями, и сменой места удержанной (например, в
перенесённый этим актом контейнер после возврата добавили ещё выданное устройство), в
`items` будет два элемента с одним `group_id`. Svelte 5 на keyed-each с повторяющимся ключом
падает в рантайме с `each_key_duplicate`: попап не откроется, а форма останется в
неопределённом состоянии. svelte-check и `pnpm build` этого не видят.

**Fix:** на сервере сливать элементы по `group_id` (объединять `returned_names` и
`kept_names`, а `places_match` считать как `&&`). На клиенте как подстраховку использовать
ключ `(item, i) => \`${item.group_id}-${i}\`` или индекс.

### WR-03: «Изменить расположение группы» без общего места: попап обещает одно, сервер делает другое

**File:** `ui/src/features/acts/GroupSplitChoicePopup.svelte:46-49`, `crates/trackly-app/src/services/group_act_plan.rs:858-863`

**Issue:** если у всех возвращаемых прямых членов нет места (`None`), то `places_match = true`
и кнопка `MoveGroup` доступна. Попап пишет: «группа … переедет в «без места», остальные
устройства выйдут из группы». Сервер при `target_place_id = None` только кладёт возвращаемых
в `stationary_device_ids`: группа не переезжает, kept-члены НЕ выводятся, а возвращаемые
остаются в группе. Пользователь выбирает исход, который не наступит.

**Fix:** при `target_place_name == null` либо делать `MoveGroup` недоступным с пояснением
«не указано место возврата», либо привести текст к фактическому поведению («группа и все
устройства останутся на месте»). На сервере лучше отклонять `MoveGroup` без цели
валидационной ошибкой, симметрично D-46.

### WR-04: «забывание» переноса может записать в историю перемещение «место → то же место»

**File:** `crates/trackly-infra/src/repos/place_movements_sqlite.rs:325-341`

**Issue:** группа перенесена актом P→X, затем вручную X→P, после чего акт удаляют. Группа
стоит на P, это не `to` эффекта, поэтому срабатывает «забыть». Преемник X→P получает
«откуда» = P, и в журнале остаётся строка P→P. То же происходит с каждым устройством и
картриджем пакета. Журнал HST-02 покажет пустое перемещение.

**Fix:** после переписывания удалять преемника, если у него `from_place_id = to_place_id`:
```sql
DELETE FROM place_movements WHERE id = ?succ AND from_place_id = to_place_id
```
Или вовсе не переписывать: если `from` забываемой строки совпадает с `to` преемника, удалять
преемника вместе с ней.

### WR-05: теперь любая ошибка отправки возврата видна только как строка внизу формы, без тоста

**File:** `ui/src/features/acts/ReturnModal.svelte:356-362`

**Issue:** раньше ошибки `doReturn` и `updateReturn` (Conflict по версии, «устройство уже не
в работе», сеть) шли тостом. Теперь все они записываются в `formError`, который выводится
в конце секции позиций под таблицей. При длинном списке позиций сообщение оказывается за

неактуальная ошибка D-46 висит до следующего нажатия.

**Fix:** во встроенный блок выводить только `AppError::Validation` с `field == 'place_id'`
(D-46), остальное показывать тостом, как раньше. Сбрасывать `formError` в
`handleRowsChange` и при смене `bulkPlaceId` и `applyToAll`.

удаление, на экране нет никакой индикации. Двойной отправки нет, её не даёт guard
`deleting`.
**Fix:** обнулять `restorePrompt` после ответа (в `finally`) или передавать `loading`, не
размонтируя попап.
