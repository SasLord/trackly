# Phase 41.2 Plan 12: Group release confirmation popup Summary

Saving an act that would take items out of their groups now opens one popup listing every such item with its group name; Cancel returns to the untouched form, "Вывести и передать" re-saves with `confirm_group_release: true` on both the create and the update path, and a structural gate holds the order, the inert Cancel and the two-button contract.

GAM-01..GAM-04 stay `Pending` on purpose: `requirements-completed` is empty and REQUIREMENTS.md was not touched. Plan 41.2-16 owns completion.

## What was built

- **Popup.** `Modal size="md"`, title, intro and closing paragraph verbatim from UI-SPEC 13.4, semantic `<ul>` with a two-line `<li>` (name in `--tr-text-body-strong`, origin `из состава «…»` in `--tr-text-label` / secondary, group name as text, not a link), `max-height: 40vh`. Footer: `Отмена` (secondary) then `Вывести и передать` (primary, not destructive, R-06). No third button. White-space and text-align set explicitly on the content wrapper. Interpolation only, no `{@html}`.
- **Outcome handling.** In `submitCreate` and `submitEdit` the `needs_group_release` check now sits above the `created` branch (and so above `onSaved(`); it opens the popup through `openGroupReleasePopup` and returns. The state travels up through `onPopupChange({ kind: 'groupRelease', ... })` and `ActFormModal` renders it as a sibling of the form modal, so there is no modal inside a `backdrop-filter` container.
- **Confirmation lifetime.** `confirmedItemsSignature` holds a signature of the composition of positions made at the moment of confirmation. `groupReleaseConfirmed()` is evaluated when the payload is built, so any change of positions makes it false without an effect writing state. The signature is also dropped when a save attempt ends without a chain popup open (handleSubmit finally) and in the three number-chain closers (taken, mismatch, scriptWarning, and take-next), so a confirmation does not leak into an unrelated later save.
- **Cancel / Esc / cross / overlay** all run `closeGroupReleasePopup`, which only closes the popup and clears the signature. It does not touch `items`, does not call `acts.*` and does not call `onSaved`.
- **Place error.** The `place_id` server validation lands in `fieldErrors` through the existing catch; it is now shown inline under `PlacePicker` (with `has-error` and `invalid`). The text comes from the server; no literal in the file. The popup is not raised in that case (the server raises place validation before the confirmation outcome, plan 41.2-07 OQ-7).

## Deviations from Plan

**1. [Rule 3 - Blocking] Vocabulary allowlist entry moved from Task 3 into the Task 1 commit**
- The popup contains the word "групп*"; without the allowlist record `check-group-vocabulary` is red, and the pre-commit hook only runs the privacy gate. To keep every commit green the narrow entry (three markers: 'от своей группы', 'Остальной состав группы', 'вернёт эти позиции в группу'; not `markers: null`) lives in b86ba4bb. Task 3 therefore has no vocabulary change.

**2. [Plan-permitted ordering] union variant committed with Task 1**
- `ActFormModal` reads `numberPopup.items`, so the `'groupRelease'` variant of `ActNumberPopupState` had to exist in the Task 1 commit (the plan allowed editing both files back to back). The rest of ActFormBody is Task 2.

**3. [Rule 2 - Hardening] Signature wider than "sorted device_id of filled rows"**
- The signature is built from `device_id:quantity:picked group units` per row, so a quantity change or a different set of group units also invalidates the confirmation (T-41.2-51 covers "any change of composition"). Order-independent.

**4. [Rule 2 - Hardening] Confirmation also dropped when the attempt ends**
- The plan binds the confirmation to the composition only. The carry-forward requirement says it must not be sticky across unrelated saves, and a failure like a validation error would otherwise leave it valid for the next click. It is cleared in handleSubmit finally (unless a chain popup holds the attempt open) and in the number-chain closers; gate rule G holds it.

**5. [Detail] initialFocus selector**
- `Button` has no `id`/`class` prop, so the selector is the repo convention `.modal-footer .btn-secondary` (same as NumberMismatchPopup).

**6. [Extra gate rules] F and G added on top of A-E**
- F: ActFormModal renders the popup in the 'groupRelease' branch and the variant is declared and emitted (without it the popup is never drawn and nothing would notice). G: non-sticky confirmation. Also in D: `initialFocus` and no `{@html`.

**7. [Note] acceptance counting**
- `grep -c "check-act-group-confirm.mjs" ui/package.json` counts lines and returns 1, because `lint` is a single line; `grep -o | wc -l` gives 2 (selftest + run).
