> **Статус: `pending — требуется пользователь`.** Исполнитель плана 41.2-16 не запускал приложение
> и не закрывает ни один пункт. Ни один план фазы 41.2 не запускал приложение: компилирующие

> читают исходник, а не работающий экран. Поэтому каждый пункт ниже называет существующий
> компонент UI и **готовит условие, при котором дефект воспроизводим**.

> Пересказанное одобрение («исполнитель сообщил, что всё работает») пунктом не является. Пункт
> закрывает только пользователь, отметив результат в своей колонке.

## Как готовить стенд

1. **Свежая сборка фронтенда** перед проверкой в LAN-браузере: `pnpm --dir ui build`. Браузер
   по LAN отдаёт `ui/dist`, а `cargo tauri dev` обновляет только окно десктопа.
2. Запуск из ветки `main` (в ней уже лежит всё, что проверяется). Миграция V049 накатится на
   существующую БД сама; БД с актами, проведёнными ДО V049, годится для пунктов X2 и X8.
3. Данные **вымышленные**, реальных названий и ФИО в стенд не вносить.
4. Каждый пункт проверять в Tauri **и** в LAN-браузере (режим сервера); разные движки (WKWebView и
   браузер) дают разные дефекты. Консоль разработчика открыта: пункты H7 и H1 ищут в ней ошибку
   `effect_update_depth_exceeded`.

### D7. Фраза в окне подтверждения удаления обещает лишнее для акта до V049

- **Что сделано.** Окно подтверждения удаления акта (`ActsPage`, `window.confirm`) обещает: «Устройства,

### Наблюдения, найденные попутно (не входят в пункты чеклиста)

1. **Род глагола в тостах удаления зашит мужским.** На экране: «"Клавиатура #1" не вернул**ся**…».
   То же в тексте массового переноса: «переедут **1 группа** и весь **их** состав».
2. **Ошибка занятости называет сырой идентификатор.** При попытке передать устройство не со склада:
   «conflict: Устройство **id=2** больше не на складе», вместо имени устройства.
3. **Выпадающий список предлагает устройство, которое передать нельзя.** Член группы со статусом
   «В работе» показывается в секции «Устройства в составе групп» и вставляется в акт, а сохранение
   затем отклоняется по статусу.
4. **«Принтерность» имеет два независимых источника, и они расходятся.** `places_group_members`
   вернул для устройства со строкой в `printers` поле `"kind":"device"` — признак берётся из типа
   устройства, а не из таблицы `printers`. Связано с разбором проблемы «принтер в составе не попал
   в список принтеров» (см. отдельный разбор, `usb_host_device_id` из интерфейса не задаётся).

## Прогон на Windows (пользователь, 2026-10-28)

Сборка `v1.4.0-phase41.2`, десктопный путь (WebView2).

| Пункт | Результат |
|---|---|
| H4 | **Пройдено.** Удаление акта, переносящего группу целиком, откатывает перенос правильно. Попутно найден дефект интерфейса, не относящийся к откату, — см. ниже. |
| H5 | **Пройдено.** Комплектация печатается читаемо и не обрезана. Разбиение на несколько листов этим составом не достигается — чтобы проверить перенос через границу страницы, нужен акт с заметно большим числом устройств; на текущем объёме данных пункт считается рабочим. |

### Дефект, найденный при H4

**Удаление акта не спрашивает подтверждения.** На Windows акт удаляется сразу по нажатию
«Удалить» — пользователь не может передумать. В коде подтверждение есть
(`ActsPage.svelte:333`, `window.confirm` с полным текстом последствий), и в LAN-браузере оно
показывается; в десктопном webview диалог до пользователя не доходит. То есть предупреждающий
текст, проверенный в H3 через браузер, на десктопе не виден вообще.

Решение (одобрено пользователем): заменить нативный `window.confirm` на собственное модальное
окно приложения по образцу `GroupDeleteModal.svelte` — оно рисуется в DOM и потому ведёт себя
одинаково на обоих путях.
