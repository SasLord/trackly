# Phase 41.2 Plan 11: Returns with groups Summary

`do_return` and `update_return` now plan groups inside the writer transaction. A returned anchor takes its group, parts and printer cartridges to the return place as one batch journal (`source='act'`, `act_id` of the return, one `batch_id`); every other returned member of a group is released with a `release` effect of the return act.

## Source order in update_return

`revert_move_effect_in_tx` < `forget_moved_details_in_tx` (group level, once, before any per-device write) < per removed device: `prior_release_effect_id_in_tx` < `release_effect_for_removed_in_tx` < `anchor_restore_conflict_in_tx` < `restore_from_snapshot_in_tx` < `release_if_locked_device_in_tx` < `restore_membership_in_tx`. No effect is re-read after the release. The `added` and `retained_with_change` plans are read after step 9 on purpose, so the group snapshot sees groups already returned to their old place (root versions are checked on detach).

**Ordering is not covered by a behaviour test.** The plan for returns has no confirmation outcome, so there is no "return path before the first write" to observe, and for the order inside the removed branch a dropped transaction rolls everything back, so no counter can tell the orders apart. Behaviour covers the consequences (r7 for the anchor guard, r8 for the spent-effect trap); plan 41.2-16's source-order guard holds the order itself.

## Deviations from Plan

**1. [Rule 1 - Bug] `anchor_restore_conflict_in_tx` treated a part of a group moved by this very act as "moved after the act"**
- **Found during:** Task 3, scenario r8 (and the same defect on the plan 09 update path).
- **Issue:** removing a part of an anchor group that the act itself moved made the function compare the part's snapshot place with the group's place (the act destination), report a conflict, skip the restore and leave the part in the group. r8 and the plan's own text ("деталь выведена из группы, эффект release") were unreachable.
- **Fix:** in `group_membership.rs` the function returns `None` for a non-anchor device when the act has a `move` effect for that group whose `to_place_id` equals the group's current place. The anchor is excluded, and a group moved after the act has a place different from the destination, so r7 and u9 still conflict.
- **Files modified:** `crates/trackly-app/src/services/group_membership.rs` (not in the plan's file list).
- **Tests:** r8 and new u12 (the same defect on `update`), both red when the exemption is off.
- **Commit:** 5fcdbaf1

**2. [Rule 3 - Scope] r8 stops before `delete_soft` of the return**
- The plan asks r8 to end with `delete_soft` of the return and check the part is back in its group. `delete_soft` of an act containing an anchor still hits the anchor guard in `release_inner` until plan 41.2-13 (the same limit plan 09 hit in u11). r8 instead asserts the surviving release effect exactly once, with the group id the rollback restores from. **Plan 41.2-13 must add the `delete_soft` control to r8.**

**3. [Rule 3 - Structure] `GroupMove.anchor_device_id` and `AppliedGroupPlan.stationary_device_ids`**
- The return path needs the anchor of a move to look up its return place, and needs to know which subtrees did NOT move so their devices take the group's current place instead of the position's place. Two fields added in `group_act_plan.rs`; no behaviour of the existing planner changed (26 earlier tests green).

**4. [Rule 3 - Fixture] return DTO needs `apply_to_all = true` for "no return place"**
- `validate_return` refuses an item without place when `apply_to_all` is false, so r2 sends `apply_to_all: true` with no `bulk_place_id`.

## Behaviour notes for downstream plans

- `do_return` / `update_return` place for a device whose group placed it (moved or stationary) is the device's CURRENT place; the position's own override cannot make a part diverge from its group.
- A retained anchor whose return place changes gets a second `move` effect (from = current group place); rollback and un-return walk move effects newest first.
- `release_device_in_tx` in the return loops is kept (textual count and gate unchanged) but is now effectively a no-op for group members: `apply_return_plan_in_tx` released them before the loop.
- Plan 41.2-13 deletes the `release` effects a return writes (carry-forward from 41.2-04) and re-adds the `delete_soft` control to r8.
