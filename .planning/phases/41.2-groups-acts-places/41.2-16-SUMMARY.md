Anchors are found with an identifier boundary (`plan_in_tx(` is not a substring of `apply_plan_in_tx(`; self-test on `apply_plan_in_tx(x); plan_in_tx(y);` returns one position). Every function signature must occur exactly once and every anchor count is stated per function (exact or at-least), so a renamed function or anchor is a red `(cnt)` defect, not a skip; the file is read with `include_str!`, so a missing file is a compile error.

### IMPORTANT finding: "plan before the first write" does NOT hold on `update_return` -- by design

The instruction asked for the invariant on all four paths. On `update_return` it cannot be asserted: the removed branch (restoring snapshots, reverting group moves, returning membership) writes first, and the plan for the ADDED positions is read after it on purpose (plan 41.2-11: the group snapshot must see groups already returned to their old place). A return also has no confirmation outcome. What the guard holds there instead: (d) plan < apply < device write for each of the two stages, (e)/(e2) the removed-branch order, and (g) the plan-after-removed-branch order. `do_return` has no earlier write, so (a) holds on it literally.

### Anchor names differ from the plan text

The plan text names `apply_plan_in_tx(` for `do_return` and `update_return`; the final code uses `apply_return_plan_in_tx(` there (and `plan_for_return_in_tx(` twice in `update_return`, once per stage). The guard follows the code.

## Deviations from Plan

1. **[Rule 1 - plan text vs code] Anchor names.** `do_return` and `update_return` use `apply_return_plan_in_tx(` and `plan_for_return_in_tx(`, not `apply_plan_in_tx(`; the guard follows the code and states multiplicities per function.
2. **[Finding] "Plan before the first write" is not true on `update_return`.** See Task 1. The guard holds (d), (e), (e2), (g) there. The request that all four paths hold the literal invariant could not be met honestly; flagged for the verifier.
3. **[Plan expectation wrong] `acts_groups` stays green on the reorder mutant.** The plan said it would go red. It cannot; recorded as the reason for the guard.
4. **[Rule 1 - gate conflict] New broadcast tests are not named `scenario_*`.** The registry gate demands exactly one `scenario_<fn>` per `Broadcasts` row and flags any other as stale, so the acceptance grep "scenario_ count +2" cannot hold. Prefix `group_ids_` used; existing scenarios keep their `groups.is_empty()` controls.
5. **[Rule 1 - test expectation] Event names the moved ROOT only.** For a container with no direct device positions the event names the root, not the nested group, matching `move_group`'s convention (D-17). My first expectation (both ids) was wrong and was corrected after the test ran.
6. **[Rule 1 - fixture] e2e (b) releases three devices, not one.** In the full "АРМ #3" fixture a partially covered root releases all remaining units (D-05). The plan's "exactly one" is held by an added second test on a two-device container.
7. **[Rule 2 - rigor] Added guards beyond the plan:** (a) for `do_return`, (g) for `update_return`, (h) module-level enum, boundary self-test, and the whole-file `release_device_in_tx(` inventory with an explicit empty exemption list (coordinator request, commit `fb72ebff`).
8. **[Rule 3 - clippy]** `needless_range_loop` in the first version of the predicate, fixed before the commit.
9. **[Environment] No `timeout` binary on macOS;** a Python `subprocess` timeout was used for the sequential run. The 2 h limit was exceeded in total wall clock because of the binary-launch latency described above, not because of test time (all binaries together report seconds of test time).
10. **[Process] Mutation tooling slip,** described in Task 1 (wrong-function substitution; one aborted run restored by hand). No source change survived: `git diff --stat -- crates/trackly-app/src` is empty and `cmp` against the saved copy was byte-identical after every mutation.
