# Phase 41.2 Plan 13: Act rollback with groups Summary

## Carry-forward obligations

1. **Effect rows deleted** - `delete_act_group_effects_in_tx` runs after `restore_released_members_in_tx` in the same transaction (step 4). Every undo test calls `assert_act_clean` (no `place_movements` and no `act_group_effects` row for the act). M4, M4b, M6.
2. **`ActDeleteResultDto.notices` filled** - `GroupNotice` becomes `ActNoticeDto { message, group_id }`. Four texts exist: "группа удалена" (group_id None), "уже входит в «...»" (id of the other group), "группа теперь в другом месте" (id of the group), "после акта её переместили" (id of the group). Plan 15 gets non-empty fixtures from d3 (i..iii), d4, d9.
3. **Controls re-added** - `u11`: a second anchor group, same act without the anchor-removing edit, `delete_soft` returns the group and parts and leaves no act rows. `r8`: `delete_soft` of the return brings the part back into the group named by the surviving release effect, group goes back to the handover place, one `custom:group_member_restored` audit row. The anchor guard did not block either (no change to `release_inner` was needed).
4. **Existing inverses used** - `revert_move_effect_in_tx` / `revert_detach_effect_in_tx` are reached through `revert_group_moves_in_tx`; no parallel implementation. `#![allow(dead_code)]` removed from `group_act_plan.rs`: `revert_group_moves_in_tx` and `restore_released_members_in_tx` are now called, and clippy `-D warnings` is clean without it. `group_membership.rs` has no remaining `allow(dead_code)`.
5. **audit_log** - this plan needed NO second rewrite of `audit_log` and never calls `detach_act_link_in_tx`. `custom:group_moved_by_act` rows of a deleted act stay as history. Nothing to add to plan 16's "Решения вне CONTEXT" from here.
6. **Plan 11 exemption not regressed** - `group_membership.rs` is byte-identical to the base; r8 and u12 stay green (the M5 round also exercises them).

## Decisions outside CONTEXT

- Pre-V049 acts (no effect rows) roll back as before: groups are not reverted, membership not restored, no notices (d7 pins this). Goes into the UAT list as expected behaviour, not a defect.
- A group moved after the act produces several notices (see key-decisions); acceptable for the toast list, plan 15 may fold them per `group_id`.

## Deviations from Plan

**1. [Scope] Registry/gate files untouched** - none needed. `extend_unique` and `UndoOutcome` in `act_service.rs` did not require registry rows (`entities_changed_gate` 49 green).

**2. [Naming] New tests are `undo_*` rather than `d1_*`** - the file already names tests by prefix (`create_`, `update_`, `return_`); `undo_` is the new single prefix (11 `async fn undo_` including the helper). The `d1..d10` labels live in the comments above each test.

**3. [Scope] `assert_act_clean` helper instead of ten inline queries** - the plan's grep criterion counts the literal `place_movements WHERE act_id` (needs >= 10); the helper is called from every undo test, so the intent (every test checks both tables) holds, but the literal occurs once in the helper plus the pre-existing ones.

**4. [Scope] acts_undo regression** - the existing `delete_soft_returns_structured_result` already asserts empty notices; one new test (`delete_soft_of_an_act_without_groups_restores_places_and_has_no_notices`) pins places restored and notices empty for a group-free act.

**5. [Structure] `group_act_plan.rs` touched** - only the module-level `#![allow(dead_code)]` was removed (plan header said "remove any allow whose first caller you become").
