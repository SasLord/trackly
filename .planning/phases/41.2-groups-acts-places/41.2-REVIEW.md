## Summary

Scope was the 41.2 delta only (commits from `498894ae^` to HEAD), read against the surrounding code. Tests, structural gates and UI belong to part B and were not reviewed.

Things that were checked and found sound, so they are not repeated as findings:

- **Single-writer discipline.** Every group mutation in `group_act_plan.rs`, `group_membership.rs` and `group_place.rs` takes `&Transaction`. The only new reader (`act_expansion`) uses the reader pool. No second connection is opened on a write path.
- **Plan-before-write.** In `create`, the confirmation return happens before `insert_act_in_tx`. In `update` it happens before the add loop. A returned `NeedsGroupRelease` drops the transaction, so it rolls back.
- **Rollback order.** `undo_device_mutations_for_act` runs revert group moves, then restore snapshots, then restore released members, then `delete_act_group_effects_in_tx` last. All three consumers (`revert_group_moves_in_tx`, `anchor_restore_conflict_in_tx`, `restore_released_members_in_tx`) read the rows before the final delete. The dependency holds.
- **V049.** It contains only `CREATE TABLE` and `CREATE INDEX`: no `DROP`, no rebuild, no foreign keys, so the refinery `foreign_keys = OFF` no-op trap cannot fire. `act_id` and `group_id` carry no FK on purpose.
- **Transport parity.** Both new commands (`places_group_members`, `groups_act_expansion`) exist as a Tauri command and an `/api/v1/*` route. Both transports go through the same `build_*` functions, so the `authorize` calls are identical. The changed `acts_delete` return type is changed on both sides. The new `expand_groups` field has no serde default on either transport.
- **`detach_act_link_in_tx`.** The `WHERE` clause pins `entity_type`, `entity_id`, `action` and `act_id`, so it cannot match rows of another device, action or act. The rewritten rows keep `entity_type`, `entity_id` and `created_at_utc`, so `idx_audit_log_entity` still serves them.
- **Template escaping.** The kit line stored in `complectation_at_time` is rendered through the HTML-autoescape environment.

Nothing reaches BLOCKER level. The most serious defects are the planner trusting a field the act does not use, a planner/expansion inconsistency for groups with an empty child, and error swallowing in the rollback path that reports the wrong reason.

## Warnings

### A-WR-01: `create` plans groups from `item.device_id` even when `device_ids` is supplied, so a device that is not an act item can be moved or released

**File:** `crates/trackly-app/src/services/act_service.rs:490-499`
**Issue:** The planner input is built from `once(item.device_id).chain(item.device_ids)`. When `device_ids` is non-empty, the act actually uses only `item.device_ids` (`effective_device_ids`, line 589). `validate_create` never requires `device_id` to be a member of `device_ids`. It does not include `device_id` in the duplicate check either.

The UI builds `device_ids = group_ids.slice(0, quantity)`. The representative `device_id` is therefore not guaranteed to be inside the slice.

If `device_id` belongs to a live group:
- the group is planned as covered or released;
- it is moved to the act place, or one of its members is released from its group;
- no `act_items` row exists for it and no `before_json` snapshot is written.

The device's place or membership then changes with no trace in the act. Deleting the act reverts the group move through the effect row, but a released member is only rejoined if its place still matches.

`update` is not affected: it uses `added`, built from `device_id` only. The create and update paths therefore disagree on what "in the act" means.
**Fix:** Build the planner input from the same list the writer uses, and reject a stray `device_id`.
```rust
for item in &payload.items {
    let ids: Vec<i64> = if item.device_ids.is_empty() {
        vec![item.device_id]
    } else {
        item.device_ids.clone()
    };
    for id in ids {
        if !act_device_ids.contains(&id) { act_device_ids.push(id); }
    }
}
```
Also add `device_id`-in-`device_ids` validation to `validate_create`, or ignore `device_id` for membership when `device_ids` is present.

### A-WR-02: A container with an empty nested group can never be "covered", so picking it in the act releases every member instead of moving the group

**File:** `crates/trackly-app/src/services/group_act_plan.rs:200-232` (`covered`), against `act_units` at `:411-452`
**Issue:** `covered()` requires `kids.iter().all(|c| covered(c))`. An empty child group is never covered, because the `direct.is_empty() && kids.is_empty()` branch returns `false`. `act_units()` skips empty children and still lists all other devices of the container. The documented consistency property is only stated for a "non-empty group". It silently fails for a non-empty group with an empty nested group, and for a nested group whose only devices are soft-deleted.

The user picks the container. The expansion produces N positions that cover everything visible. The server plan sees an uncovered container. The result is:
- a confirmation dialog listing every member;
- on confirm, each member is released and the container stays behind empty, where D-04 promises that it travels whole.

**Fix:** Treat a group with no live members as vacuously covered when it is a child of a covered candidate, but still never a move root on its own.
```rust
if direct.is_empty() && kids.is_empty() { return parent_context_allows_empty; }
```
A simpler option is to have `covered` ignore empty children when evaluating the parent: `kids.iter().all(|c| is_empty_group(c) || covered(c))`. Add a planner test with an empty nested group.

### A-WR-03: Rollback swallows every error and reports it as "the group was moved after the act"

**File:** `crates/trackly-app/src/services/group_act_plan.rs:912` (`revert_move_effect_in_tx`), `:967` (`revert_detach_effect_in_tx`), `:1080` (`restore_released_members_in_tx`)
**Issue:** `Ok(None) | Err(_) => notice` collapses two different situations. One is "precondition no longer holds", which is the intended notice. The other is a real failure inside the savepoint: a constraint error, a `set_parent_in_tx` CAS or `teardown` validation error, or an I/O error. The latter is logged nowhere and shown to the manager as "после акта её переместили", which is false.

The effect rows are then deleted by the caller, so the failed revert can never be retried. The state is recorded as clean when it is not.
**Fix:** Keep the guard, but log the error and use a distinct message for the failure case.
```rust
Err(e) => {
    tracing::error!(act_id, group_id = effect.group_id, error = %e, "group move revert failed");
    out.notices.push(GroupNotice {
        message: format!("Группа «{label}» не возвращена на прежнее место: не удалось записать изменение."),
        group_id: Some(effect.group_id),
    });
}
```
Apply the same split to the detach and restore-member arms.

### A-WR-04: Removing a position that un-moves a dormant (place-less) group leaves its detail devices at the act's place

**File:** `crates/trackly-app/src/services/group_act_plan.rs:895-900` (the `from_place_id == None` arm of `revert_move_effect_in_tx`), with `forget_moved_details_in_tx` called at `act_service.rs:1351` and `:2768`
**Issue:** When the group had no place before the act, the revert only runs `set_subtree_place_in_tx(.., None)`. It does not touch the devices. Act items are then restored from their snapshots by the remove loop. Detail devices that are not act positions are not restored, because `forget_moved_details_in_tx` has just unlinked their `custom:group_moved_by_act` snapshot rows (precisely so a later delete cannot restore stale state).

Net effect for `update` and `update_return` on a dormant group:
- the group is place-less again;
- its non-item parts stay at the act place;
- no reverse movement row is written.

That breaks the "member lives in the group's place" invariant in the opposite direction from the usual one. Compare with the `Some(from)` arm, which moves every subtree device.
**Fix:** In the `None` arm, restore each moved detail from its `custom:group_moved_by_act` snapshot before unlinking. Alternatively, clear their `place_id` with a `custom:group_place_cleared` audit row. Do this inside the same `guarded` block, and add a test: dormant anchored group, hand over, remove the position, assert the parts' places.

### A-WR-05: Anchor conflict skips the whole snapshot, so status and state are not restored either

**File:** `crates/trackly-app/src/services/act_service.rs:4527-4545` (`undo_device_mutations_for_act`), with the same pattern at `:1441-1455` and `:2855-2870`
**Issue:** On a conflict (anchored group moved after the act) the code substitutes `place_before_undo.clone()` for the restore. The device keeps its post-act status (`в_работе`) and state even though the act is deleted or the position removed. Only the place conflicts with the group. The notice text says the place and state are not returned, but a device left "В работе" with no live act is an inconsistent record. It also leaves the item permanently ineligible under the normal picker rule, which only admits warehouse devices.
**Fix:** Restore every field except `place_id` on conflict, for example by patching the snapshot value before calling `restore_from_snapshot_in_tx`:
```rust
let mut snap = snapshot.clone();
snap["place_id"] = serde_json::json!(place_before_undo.place_id);
devices_repo.restore_from_snapshot_in_tx(tx, device_id, &snap, now)?;
```
If skipping everything is the intended D-09 behaviour, document that explicitly in the notice and in HUMAN-UAT, because the manager currently has no way to learn that the status stayed.

### A-WR-06: Picker rule D-02 lets any group member through regardless of status

**File:** `crates/trackly-app/src/services/act_service.rs:88-98` (`is_act_assignable`) and `crates/trackly-infra/src/repos/devices_sqlite.rs:100-112` (`group_members_only`)
**Issue:** The validity check is "on warehouse, or a member of any live group". A group member with status `списано`, `на_списание` or `в_ремонте` passes the server guard and is flipped to `в_работе` by the act. D-02 only intended to lift the warehouse filter for working group members. Server and picker apply no lifecycle exclusion, and a hand-crafted payload (or a stale list) can hand over a written-off device. Group members are also assignable again while already handed over by an earlier act, so a repeated handover has no conflict.
**Fix:** In `is_act_assignable`, accept group members only when the status code is `в_работе` or `на_складе`; reject `списано` and `на_списание`. Mirror the same restriction in the `group_members_only` list predicate so the picker never offers them.

### A-WR-07: `plan_in_tx` for `update` considers only newly added devices

**File:** `crates/trackly-app/src/services/act_service.rs:1076`
**Issue:** The planner sees `added` and not the final item set. Coverage is evaluated against the newly added devices only; members that are already act positions (unchanged) are invisible to the all-or-part rule. Example: a container {A, B, C} is handed over with A and B (both released from it, with confirmation). An edit then adds C. The container now holds only C, so it is judged "covered" and moves whole without any confirmation. Creating the same final set of positions in one step would have been judged differently. The create and update paths therefore give different answers for the same final set of positions. This is a design-level inconsistency, not a crash.
**Fix:** Either plan against the final item set and diff the resulting effects against `effects_before`, or document in 41.2-CONTEXT/HUMAN-UAT that update evaluates coverage over the added delta only.

## Warnings

### B-WR-01: `check-act-group-picker.mjs` stays green when the 100-position limit rejection is deleted

**File:** `ui/scripts/check-act-group-picker.mjs:155-170` (rule C), source `ui/src/features/acts/ActFormItemsTable.svelte:613-629`
**Issue:** Rule (C) claims to prove that the limit check stands before insertion and that no partial insertion is possible (R-11). It only compares `pick.indexOf('MAX_ACT_ITEMS')` with `pick.indexOf('onChange(')`. The first textual `MAX_ACT_ITEMS` in `pickGroupHit` is the computation `const free = Math.max(0, MAX_ACT_ITEMS - used)`, which sits above `onChange(` no matter what happens to the rejecting `if`.

I verified this by mutation on a copy under the scratchpad (`--src=`):
- deleting the whole `if (fresh.length > free) { ... return; }` block gives `PASS, 0 violations`;
- deleting only the `return;` after the error toast also gives `PASS, 0 violations`.

The selftest covers only a swap of the block below `onChange(`, not these two. Either mutant would insert more than 100 positions, and the server would then reject the whole act.
**Fix:** Parse the rejecting branch, not the first mention of the constant. Require in `pick` a `fresh.length > free` (or equivalent) condition whose block contains `return`, and that its position is below the `free` computation and above the first `onChange(`. Add the two mutants above to `runSelfTest` (delete the block; delete the `return;`), each anchored through `mutate()`.

### B-WR-02: `check-act-group-confirm.mjs` does not hold the confirmation-to-composition binding it claims (T-41.2-51)

**File:** `ui/scripts/check-act-group-confirm.mjs:236-246` (rules E and G), source `ui/src/features/acts/ActFormBody.svelte:471-512`
**Issue:** The header says the flag is "bound to the composition of positions". Rule (E) only checks that `groupReleaseConfirmed` contains `=== itemsSignature()` and `!== null`. Nothing checks that `confirmGroupRelease` stores a signature, or that `itemsSignature` actually depends on `items`. Two mutants on a copy of `ActFormBody.svelte`, both giving `PASS, 0 violations`:
- removing the line `confirmedItemsSignature = itemsSignature();` from `confirmGroupRelease`. The flag is then never true: the user confirms, the server asks again, and the popup loops forever. This is the kind of runtime break the compile gates cannot see.
- making `itemsSignature()` return `''` as its first statement. The confirmation then survives any change of positions, which is exactly the T-41.2-51 threat.

**Fix:** In rule (C), require that `confirmGroupRelease` assigns `confirmedItemsSignature = itemsSignature()` before `handleSubmit(` (position check, not presence). In rule (E), require that `itemsSignature` reads `items` and `device_id`, `quantity` and `group_ids`. Add both mutants to the selftest.

### B-WR-03: tab counters double-count a stray group member; the test pins the inconsistent numbers

**File:** `crates/trackly-app/tests/places_contents.rs` (test `expand_false_keeps_member_outside_group_place_visible`, `member_count == Some(4)` with the stray also asserted visible as its own row), consumer `ui/src/features/places/PlaceContents.svelte:276-300` (`counts`)
**Issue:** The test builds a legacy case where a group member lives outside the group's place. In collapsed mode the server returns the group row with `member_count = 4` (including the stray) and also returns the stray as a separate device row. `counts` then adds `member_count` for the group row and `+1` for the stray row, so the tab counter is one higher than in expanded mode. This violates the stated invariant (D-23: "the numbers do not change when the checkbox is toggled"), and the test asserts both halves of the contradiction without noticing.
**Fix:** Decide which side owns it. Either the server excludes members that are returned as separate rows from the group's `member_count`/`printer_member_count` (then change the assertion to `Some(3)`), or `counts` subtracts visible stray members. Add an assertion that the physical total is the same in both modes for this fixture.

### B-WR-04: the save confirmation is a bare boolean; what the user saw is not bound to what gets released

**File:** `ui/src/features/acts/ActFormBody.svelte:495-512, 548, 628`
**Issue:** `itemsSignature()` binds the confirmation to the client's list of positions only. The popup shows a list of `{name, groupName}` computed at time T0; on «Вывести и передать» the client sends `confirm_group_release: true`, and the server re-plans at T1. If a member was added to a partly covered group (or a group moved) between T0 and T1 by another LAN client, the server will release devices the user was never shown, with no second prompt. Seeing the server side is part A's scope, so I only flag the contract: nothing in the DTO lets the server verify that the plan it executes equals the plan that was confirmed.
**Fix:** Send the confirmed set (for example the sorted device ids shown in the popup, or a plan hash returned in `GroupReleaseWarningDto`) and have the server answer `NeedsGroupRelease` again if the recomputed set is not a subset of it.

### B-WR-05: a mutant in `group_write_sites.rs` relies on an unchecked `replacen(.., 1)` anchor

**File:** `crates/trackly-app/tests/group_write_sites.rs:2880-2889` (mutant 2 of `write_site_gate_act_restore_release_adjacent`)
**Issue:** The anchor `...ReleaseEffect::Skip,\n )?\n {\n extend_unique(` is replaced with `replacen(.., 1)` and only `assert_ne!(m2, src)` is checked. The project's own rule is that a non-unique anchor silently mutates the first match, which may be a different restore path than the comment says ("in undo"). Today it occurs once (line 4551 of `act_service.rs`), so this is latent, not broken.
**Fix:** Add `assert_eq!(src.matches(anchor).count(), 1, "якорь мутации должен быть уникален")` as the other mutants in this file already do.

### B-WR-06: `group_movements_journal.rs` uses `>=` where an exact count is known

**File:** `crates/trackly-app/tests/group_movements_journal.rs` (`journal_act_package_rows_have_act_source_and_batch_only_for_group_members`, `assert!(total >= 7)` and `assert!(batched >= 7)`)
**Issue:** The act moves 6 group devices plus 1 loose device, so the journal must hold exactly 7 rows for the act (6 batched plus the group row, depending on whether the group row has `act_id`; the sibling report test asserts 7 exact rows). With `>=`, a regression that writes each moved member twice (once on the act path, once on the group path) still passes; the "unbatched only the loose device" check does not catch duplicates among batched rows.
**Fix:** Replace both with `assert_eq!` on the real numbers (and assert `COUNT(DISTINCT entity_id)` equals the row count for `batched`).

## Info

### B-IN-01: `WRITE_MARKERS` in the order guard is a hand-kept name list

**File:** `crates/trackly-app/tests/acts_group_plan_order_guard.rs:123-134`
**Issue:** "First write" is the minimum over ten named calls plus the text `for &dev_id in &added`. The removed-branch writers (`revert_move_effect_in_tx`, `restore_from_snapshot_in_tx`, `restore_membership_in_tx`, `release_if_locked_device_in_tx`, `delete_act_group_effect_in_tx`, `forget_moved_details_in_tx`) are not in it. A new write helper called above `plan_in_tx` in `create`/`update`/`do_return` under a name not in the list would not turn the guard red. The structural cousin in `group_write_sites.rs` (inventory from the whole file) is the model to copy.
**Fix:** Derive the write set from the repository side: every call whose name ends in `_in_tx` and is not on an explicit read-only list (`fetch_*`, `get_*`, `list_*`, `plan_*`, `ensure_*`), with the exemptions written down.

### B-IN-05: `MAX_ACT_ITEMS = 100` is duplicated with no cross-check, and counts differently from `create`

**File:** `ui/src/features/acts/ActFormItemsTable.svelte:99`, server `crates/trackly-app/src/services/act_service.rs:263,872`
**Issue:** The gate pins the JS constant to 100, nothing ties it to the Rust literal `p.items.len() > 100`. Also, the client sums `quantity` of the other rows, while `create` counts rows (`items.len()`); only `update` counts units. The client is therefore stricter than `create` and consistent with the later `update`, which is probably the intent, but it is undocumented and could be silently changed on either side.

### B-IN-06: text-scanning helpers in `group_write_sites.rs` are fragile at the edges

**File:** `crates/trackly-app/tests/group_write_sites.rs` (`count_calls`, `code_of`, `writes_place_id_in_sql`)
**Issue:** (1) `line.split("//")` drops everything after a `//` inside a string literal on the same line, so a call following such a literal is not counted. (2) `writes_place_id_in_sql` looks for the exact text `UPDATE devices` / `INSERT INTO devices`, so `UPDATE OR IGNORE devices`, lowercase SQL, or `UPDATE \` plus a line-continuation break the marker and a new `place_id` writer would not be seen. The gate fails open in these cases.
**Fix:** Match case-insensitively with `\s+` between tokens after collapsing string continuations; strip string literals before looking for `//`.
