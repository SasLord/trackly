# Phase 11 Plan 01: Category display name + server-driven categories list Summary

**Closed D-CAT-01 end-to-end: request detail now shows the category's Russian name (e.g. «Программное обеспечение») via a LEFT JOIN on `request_categories`, and the create-request form's category dropdown is populated from a server `{ id, name }` endpoint instead of a hardcoded client-side array.**

## Performance

- **Duration:** ~50 min
- **Completed:** 2026-06-21
- **Tasks:** 2/2
- **Files modified:** 9

## Accomplishments

- `SELECT_REQUESTS` (requests_sqlite.rs) gained a `LEFT JOIN request_categories rc ON rc.id = r.category_id` with `rc.name AS category_name` appended as the last SELECT column (idx 18) — `get`, `list`, and `fetch_in_tx` all read the new field for free, since they share the same SELECT + mapper.
- `RequestRow` → `RequestDto` now carries `category_name: Option<String>` end to end; `RequestDetail.svelte` renders `request.categoryName` as text (auto-escaped by Svelte) instead of the raw numeric `category_id`, and shows no category block at all when there is none (free_form without category, or cartridge_replace).
- `requests_list_categories` (both Tauri command and axum handler) now returns `Vec<RequestCategoryDto { id, name }>` via `SELECT id, name FROM request_categories ORDER BY name`, replacing the old bare `SELECT name` → `Vec<String>` shape that gave the frontend no way to send a correct `category_id`.
- `RequestFormModal.svelte`'s hardcoded `const CATEGORIES = [...]` array (4 RU labels duplicating the DB seed) is gone — categories are now fetched via `requests.listCategories()` on modal open, same lifecycle as the existing printer list load.
- Added 2 new repository tests (`category_name` Some/None via two seeded requests in the same test, plus a dedicated `test_request_categories_list_has_id_and_name` asserting every category row carries a nonzero id and non-empty name) and extended the existing list-count assertion from 1→2 rows.
- `bindings-phase6.ts` (manually-maintained companion to the gitignored generated `bindings.ts`) updated with `categoryName` on `RequestDto` and the new `RequestCategoryDto` type.

## Decisions Made

- Appended `category_name` as the absolute last column in `SELECT_REQUESTS` (idx 18, after `r.ad_subtype`) rather than near `category_id` in the column list, to avoid shifting any of the other `row.get(n)` indices in `map_row_request` — confirmed safe by running the full `requests_sqlite` test suite (6/6 green) after the change.
- Kept `RequestCategoryDto` in the existing `dto/request.rs` file rather than creating a new module, consistent with how all other request-related DTOs already live together there; field shape copies the `PrinterDto` `#[specta(type = i32)]` id convention.
- Verified no explicit specta type registration was needed in `specta_export.rs` — it only lists command function paths via `collect_commands!`, and `tauri-specta` auto-derives the referenced DTO types (`RequestCategoryDto`) from the `requests_list_categories` command's return-type signature.
- `bindings-phase6.ts` is a hand-maintained file (confirmed via its own header comment and `.gitignore`, which only excludes the auto-generated `bindings.ts`) — updated it manually to keep `categoryName` and `RequestCategoryDto` in sync with the Rust DTOs, matching the existing precedent for `PrinterDto`/`RequestDto` in that same file.
- Reused the existing `field-hint` CSS class and loading-state pattern from the printer dropdown for the new categories dropdown, rather than introducing new markup/styles.
