<objective>
Закрыть последнюю неопределённость (Req-7) из 17-VERIFICATION.md: неотфильтрованный
`cargo test -p trackly-app` завис на 5+ минут внутри `devices_csv_import` — файла, который Phase 17
не трогала. Project CLAUDE.md/memory уже фиксирует: «один `cargo test` за раз — два процесса
конкурируют за `target/`-lock и выглядят как многоминутное зависание». Помимо этого,
`.github/workflows/ci-fast.yml`/`ci-full.yml` содержат явный, уже задокументированный прецедент
ТОЧНО ТАКОГО ЖЕ класса зависания: «--test-threads=1 serializes tests within each test binary...
running multiple such tests in parallel saturates worker threads... deadlocks build_health/
axum-oneshot tests (observed 30+ min hang...)» — оба integration-test-файла в этом крейте
(`template_edit.rs`, `devices_csv_import.rs` и другие) сами по себе документируют, что их
`#[tokio::test]`-функции «run in parallel by default» внутри одного тест-бинарника. Это сильная,
уже существующая в кодовой базе улика: верификатор, скорее всего, запустил `cargo test -p
trackly-app` БЕЗ `--test-threads=1` (и/или без `TRACKLY_AD_MOCK`/`TRACKLY_SNMP_MOCK`), воспроизведя
именно этот уже известный класс проблемы, а не столкнувшись с новым багом.

Purpose: Подтвердить фактами (не гипотезой), что полный набор тестов действительно зелёный под
корректным вызовом — единственное, что реально закрывает Req-7's "UNCERTAIN (partial)" статус.
Задокументировать корректный вызов прямо в файле, где произошло наблюдаемое зависание, чтобы
следующий верификатор/разработчик не наступил на те же грабли.

Output: Подтверждённый зелёный прогон `cargo test -p trackly-app` под корректным вызовом (env vars
+ `--test-threads=1` + свежий `ui/dist`); doc-комментарий в `devices_csv_import.rs`, фиксирующий
этот вызов и ссылку на CI-конфиг как канонический источник.
</objective>
