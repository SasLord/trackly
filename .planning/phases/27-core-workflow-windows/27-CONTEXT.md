## Phase Boundary

Фаза 27 переводит **три ключевых транзакционных окна БЕЗ готового макета** на дизайн-систему
Фаз 23–25 и оболочку Фазы 26:

- **Акты** (`ui/src/features/acts/`) — список, деталь/редактирование, диалог возврата, вызов
  печати. Требование **WIN-03**.
- **Картриджи** (`ui/src/features/cartridges/`) — модели, экземпляры, действия жизненного цикла.
  Требование **WIN-04**.
- **Принтеры** (`ui/src/features/printers/`) — список, деталь, агрегаты совместимости.
  Требование **WIN-05**.

**Ключевое отличие от Фазы 26:** у этих окон **нет `.dc`-макета**. Источник визуальной истины —
компонентная система Фаз 23–25 + прецеденты оболочки/окна Устройства из Фазы 26 (роадмап:
«вёрстка из компонентной системы»).

**Текущее состояние (из скаута):**
- Токены `--tr-*` уже мигрированы глобально (Фаза 23); legacy `--space-/--radius-/--font-size-`
  в этих трёх фичах = 0.
- **Все 9 модалок уже сидят на примитиве `Modal`** (чрома готова); bespoke осталась внутренняя
  разметка форм.
- `*SearchAndTabs` используют `Input`, но **не `Tabs`** — табы всё ещё самописные (ровно как
  `DeviceFilters` до D-10 Фазы 26).
- **Детальные панели** (`ActDetail`/`CartridgeDetail`/`PrinterDetail`) — самый большой bespoke-пласт:
  `detail-header`, `field-grid`, секции, `history-list`, `counter-row` — у каждого окна свои.
- Списки (`ActsList`/`CartridgesList`/`ModelsList`/`PrintersList`) — НЕ на `<table>`/`Table`
  (Фаза 25 закрыла только строки Устройств).

**В границах фазы:**
- Перевод трёх окон на токены/примитивы **повсеместно** — без остатков старых классов (SC #1–#3).
- Master-detail: закрытие принятого регресса D-13 Фазы 26 (инверсия фонов D-06) — D-02 ниже.
- Детальные панели: лёгкий общий паттерн + ре-токенизация — D-01.
- Списки → семантика `<table>` + `Table`/`TableRow` со своими колонками — D-03.
- `*SearchAndTabs` → примитив `Tabs` (как D-10 Фазы 26 для `DeviceFilters`).
- Полная ре-токенизация внутренностей модалок и фича-виджетов, без редизайна — D-04.
- Обе темы (светлая и тёмная) — унаследовано от D-17 Фазы 26.
- `DiscoveryResultsTable` (сырой `<table>`) → компонент `Table`.

**Вне границ:**
- **Любое изменение полей, действий, workflow, бизнес-логики, API, бэкенда** — фаза чисто
  визуальная (SC #4).
- **Редизайн раскладок** (новая иерархия секций детали, перекомпоновка форм модалок,
  смена master-detail на full-width) — сознательно не берётся, риск нарушить SC #4.
- **Мобильная переработка этих окон** — не в объёме (WIN-03/04/05 про токены/компоненты, не про
  адаптивность; WIN-12 покрывает только Дашборд/Устройства). Master-detail сохраняет свой текущий
  `<1100px` horizontal-scroll fallback; полноценный мобильный вид — потенциальный будущий объём
  (см. Deferred).
- **Окна Фазы 28** (Заявки, Отчёты, Настройки, Пользователи) и Фазы 29 (Логин, EmployeeLayout).
- AA-контраст, focus ring по новому дизайну, паритет Tauri vs LAN-браузер — QA-02/QA-03, Фаза 30.

## Implementation Decisions

### D-01: Детальные панели — лёгкий общий паттерн + ре-токенизация

`ActDetail`/`CartridgeDetail`/`PrinterDetail` — крупнейший bespoke-пласт, у каждого свой набор
классов (`detail-header`, `detail-section`, `field-label`, `fields-grid`, `history-row`,
`counter-row`, `meta-row`). Макета нет.

**Решение:** извлечь **лёгкий общий паттерн детальной панели** (шапка + секции + field-grid) —
по образцу того, как `PageHeader` был извлечён в Фазе 26 — чтобы Фазы 27–28 его переиспользовали.
Остальное ре-токенизировать. **Структура и поля не меняются (SC #4).**
**Обоснование:** Фаза 28 несёт ещё четыре окна с детальными панелями; общий паттерн окупается
так же, как `PageHeader`. Полный редизайн отклонён — выход за «чисто визуальный» SC #4.
**Действие для планировщика:** решить форму общего паттерна (компонент vs набор классов/snippets)
и где он живёт (`ui/src/lib/components/`). Точный состав секций каждой панели — на усмотрение, но
без изменения отображаемых полей.

### D-02: Master-detail — `--tr-surface-raised` + обёртка Table (закрытие D-13)

`*MasterDetail.svelte` = grid 35/65; сейчас master на `--tr-surface`, detail на `--tr-bg`. После
D-06 Фазы 26 (контент-область стала `--tr-surface`) панели сливаются с фоном — это **принятый
регресс D-13 Фазы 26, который Фаза 27 обязана закрыть**.

**Решение:** обе панели на `--tr-surface-raised` + `border` + `box-shadow var(--tr-elev-1)` —
тот же язык, что обёртка таблицы Фазы 26 (D-11) и карточки дашборда. **Структура master-detail
(grid 35/65, split) сохраняется — SC #4;** меняются только поверхности.
**Обоснование:** даёт глубину и разделение master vs detail поверх нового `--tr-surface`-контента,
единый визуальный язык с уже перенесёнными окнами.
**Осторожно:** проверить обе темы — в тёмной `--tr-surface-raised` относительно `--tr-surface`
читается иначе (урок D-17 Фазы 26).

### D-03: Списки → семантика `<table>` + `Table`/`TableRow`

`ActsList`/`CartridgesList`/`ModelsList`/`PrintersList` сейчас **не** на `<table>` (Фаза 25 дала
`<table>`/`Table`/`TableRow` только Устройствам). Свои колонки (статус-бейджи, даты, тонер).

**Решение:** перевести списки на семантику `<table>` + примитивы `Table`/`TableRow` со своими
колонками, переиспользуя обёртку/футер/пустые состояния `Table` — как в Устройствах.
**Обоснование:** архитектурная консистентность строк списков между всеми окнами; общая обёртка
(border/radius/elev/overflow-x при min-width) и футер-итог/пустые состояния бесплатно.
**Осторожно:** `Table`/`TableRow` — общие компоненты (Устройства, витрина, `ActFormItemsTable`).
Свои колонки этих окон не должны сломать существующих потребителей; строки Устройств (D-12 Фазы 26)
не трогать.
**Действие для планировщика:** сопоставить колонки каждого окна с API `TableRow` (CMP-06); группо-
вых строк, как у Устройств, здесь нет — раскладка плоская.

### D-04: Глубина — полная ре-токенизация без редизайна

Чрома модалок готова (все 9 на `Modal`), контролы уже на `Input`/`Select`. SC требует «без
остатков старых классов» **повсеместно**.

**Решение:** внутренняя разметка форм модалок (`OperationModal` 887 стр., `ModelFormModal` 580,
`CartridgeFormBody`, `CompatibilityEditor`) и фича-виджеты (`TonerGauge`, `LowStockBanner`,
`PrinterAlertBanner`, `CartridgeContextMenu`) переводятся на токены/примитивы **целиком** —
никаких bespoke-классов не остаётся. **Функция и раскладка не меняются.**
`DiscoveryResultsTable` (сырой `<table>`) → компонент `Table`.
**Обоснование:** только так SC #1–#3 («повсеместно», «без остатков старых классов») закрываются
честно. «Только верхний слой» отклонён — оставил бы глубокие модалки вне охвата.

### D-05: Табы фильтров → примитив `Tabs`

`*SearchAndTabs` уже на `Input`, но табы самописные. Перевести на `Tabs` (CMP-04) — прямое
повторение D-10 Фазы 26 для `DeviceFilters`.
**Риск (контракт, не деталь):** поведение фильтров (поиск, переключение статуса/вкладок,
счётчики) не должно измениться.

### Claude's Discretion
- Форма общего паттерна детальной панели из D-01 (компонент vs snippets/классы) и его размещение.
- Точное сопоставление колонок каждого списка с API `TableRow` (D-03).
- Дробление на волны/планы. **Порядок по прецеденту D-19 Фазы 26:** сперва общие/разделяемые
  артефакты (общий паттерн детали D-01, любые правки `Table`/`TableRow` под новые колонки), затем
  три окна параллельно — чтобы волны не дрались за общие файлы.
- Конкретные значения ре-токенизации там, где `.dc` их не задаёт — выводятся из `_tokens.scss` и
  прецедентов окна Устройства.

</decisions>

## Existing Code Insights

### Reusable Assets
- **Примитивы Фаз 24–25 покрывают почти всё:** `Modal` (чрома всех 9 модалок готова), `Input`/
  `Select`/`Checkbox`/`Button`/`Badge`, `Tabs` (для D-05), `Table`/`TableRow` (для D-03),
  `PageHeader` (шапки окон). Новый нужен максимум один — общий паттерн детальной панели (D-01).
- **`*SearchAndTabs` структурно совпадают с `DeviceFilters`** — работа сводится к замене
  самописных табов на `Tabs`, а не к проектированию (D-05).
- **`Table` уже владеет обёрткой (D-11 Фазы 26), футером и пустыми состояниями** — списки D-03
  встают в готовую инфраструктуру.

### Established Patterns
- Стили — scoped `<style lang="scss">` в каждом компоненте; глобальных классов почти нет.
- Пропсы — Svelte 5 runes (`$props`, `$bindable`, `$derived`), `Snippet` для children.
  **Ловушка Фазы 24:** `const` vs `let` при `$bindable()` — контракт, не стилистика.
- **Фронтенд-тестов нет.** Гейты: `pnpm lint`, `pnpm svelte-check`, `pnpm --dir ui build`,
  `check-tokens.mjs`. Проверка визуала — только глазами (D-18 Фазы 26).
- **`:global()` в plain `.scss` не работает** — `global.scss` обрабатывается sass/Vite, а не
  компилятором Svelte (урок Фазы 24). CI-гейта на это по-прежнему нет.
- **Гоча (память проекта):** перед проверкой через LAN-браузер нужен `pnpm --dir ui build` —
  серверный режим отдаёт `ui/dist`, `cargo tauri dev` хотрелоадит только desktop-webview.
  `prebuild` тянет `cargo test -p trackly-app --test export_bindings` — сборка ui тянет cargo.
- `*MasterDetail.svelte` = CSS-grid 35/65 c `<1100px` horizontal-scroll fallback; поверхности
  сейчас master `--tr-surface` / detail `--tr-bg` (меняется D-02).

### Integration Points
- **`Table`/`TableRow` — общие компоненты трёх потребителей** (Устройства, витрина,
  `ActFormItemsTable`). D-03 добавляет новые колонки/потребителей — регресс проверять во всех.
- **Оболочка (`Layout`/`Sidebar`/`PageHeader`) — общая, готова из Фазы 26** — эти окна её
  наследуют, менять не нужно.
- Витрина живёт за ролью admin — известный долг: гейт на пункте меню, но не на маршруте
  (24-LEARNINGS, backlog 999.1).
