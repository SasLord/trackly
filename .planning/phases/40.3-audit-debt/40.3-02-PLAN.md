foreign_key_check`) ТОЛЬКО внутри ветки `if pending { ... }` — то есть только когда были
миграции для применения. Если первый запуск успел закоммитить миграции ДО того, как код
решил отказать (refinery коммитит свою транзакцию раньше, чем наш `result.map_err(...)`
успевает сработать), `refinery_schema_history` уже содержит новую версию — на СЛЕДУЮЩЕМ
старте `pending=false`, ветка `else` выполняется БЕЗ единого вызова `fk_violations()`.
Приложение стартует с испорченной ссылочной целостностью навсегда, пока кто-то вручную не
почистит данные (находка N-4, `.planning/v1.4-MILESTONE-AUDIT.md`). Это особенно важно
перед перестройками `places` в Фазах 41/43 (forward risk F2 аудита).

Purpose: любое новое FK-нарушение после миграций блокирует ВСЕ последующие старты, не
только первый — но предсуществующие (legacy) нарушения по-прежнему не блокируют.
Output: `run_to` с безусловной, персистентной проверкой целостности + regression-тест.
