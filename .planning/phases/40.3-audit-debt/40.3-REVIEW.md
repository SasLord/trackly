правки в отдельности сделана аккуратно: SQL `CASE WHEN` на обоих write-path

что и `devices`-строка, и отказ при `type_id != Принтер` явный, а не тихий;
удалённый `PrinterCreateModal.svelte` не оставил висящих импортов, и
`devices.create()` убран из `ui/src/lib/api/devices.ts` вместе с единственным
потребителем. Гейты проходят: `cargo check --workspace --all-targets`,
`cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --check`,
`cargo test -p trackly-infra --lib db::migrations` (6/6), три миграционных
интеграционных теста (13/13), `check-place-tree-invalidation.mjs` и новый
`check-act-number-no-regex-split.mjs` — всё зелёное. Приватность: реальных
данных организации/ФИО/реквизитов в изменённых файлах НЕТ; тестовые IP из
RFC 5737 (`192.0.2.0/24`), имена устройств вымышленные, «Иванов И.И.» —
допустимый placeholder.

Тем не менее фаза не достигает заявленной цели в трёх местах, и два из них
воспроизводимы:

1. **WR-03 сделан на 5 полей из 6.** `DevicePatch.place_id` — единственное
   поле с той же семантикой double-Option — осталось БЕЗ
   `#[serde(default, with = "double_option")]`, поэтому на JSON-границе
   `{"place_id": null}` схлопывается в «поле не передано». Очистка «Места»
   через форму правки устройства/принтера по-прежнему молча не срабатывает —
   ровно тот баг, который фаза 40-28 объявила закрытым (единственный тест на
   него строит `DevicePatch` литералом Rust и serde не пересекает).
   Воспроизведено на изолированном serde-репро.
2. **N-2 (атомарный printer-блок) обходится при `Количество > 1`.** Поле
   «IP-адрес» видно в DOM независимо от количества, но ветка `qty > 1` уходит
   в `devices.bulkCreate()`, который printer-блок не принимает — введённые
   пользователем IP и community молча выбрасываются, тост говорит «Создано N
   устройств».
3. **N-1 закрыт в тосте, но не в том же файле строкой выше.** `ReturnModal`
   по-прежнему собирает номер на клиенте (`№{number_raw}в{N}`) и для ПЕРВОГО

Отдельный блок замечаний — self-heal бейзлайна FK: он опирается на `rowid`,
который перестраивающие таблицу миграции (в этом проекте — норма, V042/V043/

момент первого запуска с новым кодом, без единой записи в лог.

## Critical Issues

### CR-01: `DevicePatch.place_id` не получил double-Option на serde-границе — очистка «Места» по-прежнему молча игнорируется

**File:** `crates/trackly-app/src/dto/device.rs:212-213`
**Issue:**
Пять полей получили `#[serde(default, with = "serde_with::rust::double_option")]`,
шестое — `place_id` с идентичной семантикой `Option<Option<i64>>` — нет:

```rust
#[serde(default, with = "serde_with::rust::double_option")]
pub state: Option<Option<String>>,
#[specta(type = Option<Option<i32>>)]
pub place_id: Option<Option<i64>>,   // <— без serde-атрибута
```

Без атрибута serde десериализует `Option<Option<i64>>` из JSON-`null` во
ВНЕШНИЙ `None`. Проверено изолированным репро на serde 1 / serde_json 1:

```
explicit null -> None
absent        -> None
```

Далее `From<DevicePatch> for domain::DevicePatch` (строки 258-264) выполняет
`if let Some(inner) = dto.place_id` — ветка не срабатывает, `p.place_id`
остаётся `None`, SQL получает `?13 = 0` и `place_id = CASE WHEN 0 = 1 ... ELSE
place_id END` → место не меняется.

Путь пользователя замкнут: `DeviceFormBody.svelte:622` (`submitEdit`) отправляет
`place_id: placeId`, где `placeId: number | null`; сгенерированный биндинг —
`place_id: number | null` (`ui/src/bindings.ts:2180`), т.е. «отсутствие ключа»
клиент выразить не может в принципе. Очистка места в форме правки устройства и
принтера не работает — это в точности дефект, объявленный закрытым в фазе 40-28
(CR-03). Единственный тест, покрывающий `Some(None)`
(`crates/trackly-app/tests/place_movements_write_sites_devices.rs:572`), строит
`DevicePatch` Rust-литералом и serde не пересекает — та самая «тавтология»,
от которой предостерегает комментарий нового теста в `devices_crud.rs`.

Тот же дефект живёт в `crates/trackly-app/src/dto/auth.rs:78`
(`email: Option<Option<String>>` без атрибута) — «убрать email» так же не
работает через JSON.

**Fix:**
```rust
#[serde(default, with = "serde_with::rust::double_option")]
#[specta(type = Option<Option<i32>>)]
pub place_id: Option<Option<i64>>,
```
и регрессионный тест ПО ОБРАЗЦУ `device_patch_serde_double_option_distinguishes_absent_vs_null`,
но на `place_id` и через `serde_json::from_str`, а не литералом:
```rust
let p: DevicePatch = serde_json::from_str(r#"{"place_id": null}"#).unwrap();
assert_eq!(p.place_id, Some(None));
let p: DevicePatch = serde_json::from_str("{}").unwrap();
assert_eq!(p.place_id, None);
```
Плюс end-to-end: создать устройство с местом, послать `{"place_id": null}`,
проверить `fetched.place_id == None`. То же для `dto/auth.rs::email`.

### CR-02: printer-блок (IP/SNMP community) молча выбрасывается при «Количество > 1»

**File:** `ui/src/features/devices/DeviceFormBody.svelte:679-692` (ветка `qty > 1`), `ui/src/features/devices/DeviceFormBody.svelte:907` (условие показа блока)
**Issue:**
Блок IP/SNMP отрисовывается по условию, не зависящему от количества:

```svelte
{#if typeId === PRINTER_TYPE_ID && !isEdit}   <!-- строка 907 -->
```

а `quantity` остаётся редактируемым, пока инвентарный и серийный номера пусты
(`quantityDisabled = isEdit || inventoryNo.trim() !== '' || serialNo.trim() !== ''`,
строка 282) — для принтера без номеров это типовой случай. При `qty > 1`
`handleSubmit` уходит в ветку `devices.bulkCreate(newDevice, qty)`, которая
printer-блока не принимает вовсе: `bulk_create` вызывает
`sync_printer_row_in_tx(..., None)` (`device_service.rs:1596`). Результат:
пользователь заполнил IP и community, нажал «Создать», получил тост
«Создано N устройств», а в БД N принтеров с `ip_address = NULL`,
`community = 'public'`. Ни ошибки, ни предупреждения — введённые данные
потеряны. Это прямо подрывает заявленную цель N-2 («принтер заводится одним
запросом вместе с IP»).

Тот же класс — переключение типа на «Устройство» после ввода IP: `ipAddress`
остаётся в `$state`, блок исчезает из DOM, `printerBlock` не отправляется,
предупреждения нет.

**Fix:** выбрать одно из двух и закрыть гейтом:

```svelte
<!-- (а) блок доступен только тогда, когда он реально отправляется -->
{#if typeId === PRINTER_TYPE_ID && !isEdit && qtyEffective === 1}
```
```ts
// (б) либо запретить массовое создание принтеров с заполненным IP
const quantityDisabled = $derived(
  isEdit ||
  inventoryNo.trim() !== '' ||
  serialNo.trim() !== '' ||
  (typeId === PRINTER_TYPE_ID && ipAddress.trim() !== ''),
);
```
В обоих случаях добавить defense-in-depth на сервере: `bulk_create` при
`type_id == PRINTER_TYPE_ID` и непустом printer-блоке (когда он туда попадёт)
должен возвращать `AppError::Validation`, а не игнорировать — по образцу уже
сделанной проверки T-40.3-09 в `create_single_with_number_check_with_printer`.

### WR-01: бейзлайн FK опирается на `rowid` — перестройка таблицы ломает его в обе стороны

**File:** `crates/trackly-infra/src/db/migrations.rs:79-95` (`format_fk_baseline`), `:328` (`after.difference(&baseline)`)
**Issue:** элемент бейзлайна — кортеж `(table, rowid, parent, fkid)`.
`rowid` в SQLite не стабилен: любая миграция, перестраивающая таблицу через
`CREATE TABLE new → INSERT SELECT → DROP → RENAME` (в этом проекте это норма —
V042/V043/V044), переназначает rowid'ы. Последствия:
* **ложное срабатывание, теперь постоянное.** Легаси-нарушение, «усыновлённое»
  в бейзлайн на прошлом запуске с rowid=17, после rebuild получает rowid=12 →
  `difference` непустой → `Err` на КАЖДОМ последующем старте. Приложение не
  запускается после обновления, сообщение — `Internal`, пути восстановления в
  UI нет. Раньше этот эффект жил внутри одного запуска; персистентный бейзлайн
  переносит его через версии.
* **маскировка.** SQLite переиспользует rowid после удаления последней строки.
  Если «усыновлённое» нарушение (table, 100, parent, 0) удалили, а новая
  битая строка получила тот же rowid 100 — новое нарушение попадёт в
  `difference` пустым множеством и будет молча принято.

**Fix:** ключевать бейзлайн по устойчивой сигнатуре и сравнивать кратности:
```rust
// (table, parent, fkid) -> count
type FkSignature = (String, String, i64);
fn signature_counts(v: &BTreeSet<FkViolation>) -> BTreeMap<FkSignature, usize> { … }
// "new" = любая сигнатура, у которой count вырос относительно baseline
```
`rowid` оставить только для сообщения об ошибке (sample), не для сравнения.

### WR-02: bootstrap-бейзлайн молча «усыновляет» все существующие нарушения — на пострадавших установках N-4 ничего не находит

**File:** `crates/trackly-infra/src/db/migrations.rs:286-289`
**Issue:**
```rust
let baseline = match read_persisted_fk_baseline(conn) {
    Some(b) => b,
    None => fk_violations(conn)?,
};
```
На ПЕРВОМ старте с новым кодом персистентного бейзлайна ещё нет, поэтому
бейзлайном становится текущий снимок — включая нарушение, которое ввела
миграция предыдущей версии и которое N-4 как раз и должен был продолжать
блокировать. То есть на уже пострадавшей установке (единственной, где N-4
имеет смысл) фикс срабатывает как «всё чисто» и далее persist'ит грязный
снимок как норму. Ни `tracing::warn!`, ни поля в `MigrationReport`, ни
единого следа в логах — диагностировать постфактум нечем.

**Fix:** логировать bootstrap отдельно и громко, и вынести в отчёт:
```rust
let baseline = match read_persisted_fk_baseline(conn) {
    Some(b) => b,
    None => {
        let snapshot = fk_violations(conn)?;
        if !snapshot.is_empty() {
            tracing::warn!(
                count = snapshot.len(),
                "FK baseline bootstrap: {} pre-existing violation(s) grandfathered \
                 (they will NOT block startup) — sample: {:?}",
                snapshot.len(),
                snapshot.iter().take(10).collect::<Vec<_>>()
            );
        }
        snapshot
    }
};
```
и добавить `pub fk_baseline_size: usize` в `MigrationReport`, чтобы
диагностический экран мог это показать.

### WR-03: `persist_fk_baseline` превращает диагностику в блокировщик старта

**File:** `crates/trackly-infra/src/db/migrations.rs:120-143`, вызов на `:344`
**Issue:** чтение бейзлайна защищено полностью (`read_persisted_fk_baseline`
возвращает `None` на ЛЮБУЮ ошибку — включая отсутствие таблицы `app_settings`),
а запись — нет: `persist_fk_baseline(conn, &after)?` пробрасывает ошибку
наружу, и `AppCtx::build` (`context.rs:192`) падает. Сценарии отказа:
* `run_up_to(conn, v)` c `v < 16` — `app_settings` создаётся в V016, запись
  упадёт «no such table: app_settings». Сегодня все вызовы `run_up_to` —
  41/42/43, но тест-хук публичный (`pub fn run_up_to`) и приглашает к такому
  использованию;
* БД на read-only носителе / открытая в read-only (portable-режим, флешка,
  папка без прав) — раньше запуск без pending-миграций не писал в БД вообще,
  теперь пишет на КАЖДОМ старте;
* запись бейзлайна происходит вне транзакции миграций, т.е. может выполниться
  и после успешного `tx.commit()` миграции — частично применённое состояние
  с провалом старта.

**Fix:** сделать запись best-effort, как и чтение:
```rust
if let Err(e) = persist_fk_baseline(conn, &after) {
    tracing::warn!("FK baseline persist failed (non-fatal): {e}");
}
```
Гарантия N-4 при этом не теряется: без персиста поведение деградирует до
прежнего «бейзлайн — свежий снимок», а не до «приложение не стартует».

### WR-07: гейт `check-act-number-no-regex-split.mjs` обходится четырьмя очевидными способами

**File:** `ui/scripts/check-act-number-no-regex-split.mjs:60`

Проверено запуском гейта на временной копии со всеми реалистичными

Последняя строка особенно показательна: гейт, написанный против «склейки
`number_raw` + суффикс», не детектирует склейку `number_raw` + суффикс. Forward
risk F7 (фаза 41, акты АРМ) им не закрыт — закрыто только точное написание
уже исправленной строки.

**Fix:** сместить инвариант с «regex начинается с `\d`» на «поле `number_raw`
не участвует в отображаемой строке»:
```js
// 1) любое употребление `.number_raw` вне явного whitelist (сортировка/
//    префилл формы редактирования) — нарушение;
const RAW_USE_RE = /\.number_raw\b/g;
const ALLOWED = new Map([
  ['src/features/acts/ActFormBody.svelte', 1], // префилл редактирования
]);
// 2) расширить regex-паттерн: /\.replace\(\s*\/\^[\\(\[]?\\?[d0-9]/
// 3) ловить конкатенацию 'в' с любым выражением: /`[^`]*\$\{[^}]*\}в\$\{/
```
и добавить самотест гейта (`--src=` уже поддерживается) с фикстурой из
четырёх строк выше — сейчас гейт не проверен ни на одном положительном
примере.

### WR-08: `ReturnModal` по-прежнему собирает номер акта на клиенте и ошибается на первом возврате

**File:** `ui/src/features/acts/ReturnModal.svelte:222-223, 372`
**Issue:** тост исправлен (N-1 закрыт), но строкой выше в том же файле:
```svelte
Создаст акт возврата №{parentNumber}в{predictedSubNumber}
```
где `parentNumber = act?.number_raw ?? 0`, `predictedSubNumber = return_ids.length + 1`.
Сервер формирует номер по `format_act_number` (`crates/trackly-app/src/dto/act.rs:26-43`):
при `sibling_return_count == 1` суффикс печатается БЕЗ под-номера — «42в», а не
«42в1». То есть для первого возврата (самый частый сценарий) предпросмотр
показывает номер, который никогда не будет создан. Дополнительно
`return_ids.length + 1` не учитывает удалённые возвраты — после удаления
возврата предсказание разойдётся с серверной нумерацией и во второй раз.
Это тот же класс дефекта, который фаза объявила закрытым, в том же файле, и
новый гейт его не видит (см. WR-07).

**Fix:** не предсказывать номер на клиенте. Либо убрать номер из подсказки
(«Создаст акт возврата» без номера), либо получать предпросмотр с сервера
тем же вызовом, что и другие номера в фазе 40.2 (`NumberTemplateField`/
`peek`-эквивалент), а `parentNumber`/`predictedSubNumber` удалить вместе с
`?? 0`.

### WR-09: printer-блок авторизуется только `MutateDevices`, хотя пишет строку `printers`

**File:** `crates/trackly-app/src/tauri_cmds/devices.rs:77-85`
**Issue:** `build_devices_create_single_with_number_check` делает
`authorize(caller, &Action::MutateDevices)?`, после чего создаёт строку
`printers` с IP и SNMP community. Все остальные пути записи в `printers`
(`PrinterService::create_from_device`, `acknowledge_alert` и др.) гейтятся на
`Action::MutatePrinters`. Сегодня обе роли совпадают (`Admin | Manager`,
`crates/trackly-core/src/auth.rs:162-171`), так что эскалации нет — но
проект уже имеет прецедент расхождения политик (D-20: `MutatePlaces` только
Admin), и при любом будущем сужении `MutatePrinters` эта дыра откроется
молча, без падения тестов.

**Fix:**
```rust
authorize(caller, &Action::MutateDevices)?;
if printer.is_some() {
    authorize(caller, &Action::MutatePrinters)?;
}
```
плюс кейс в `role_endpoint_matrix.rs`, фиксирующий, что запрос с
printer-блоком требует обоих прав.

### WR-10: третий write-path устройства остался на COALESCE — `restore_from_snapshot_in_tx` не умеет вернуть поле в NULL

**File:** `crates/trackly-infra/src/repos/devices_sqlite.rs:461-476`
**Issue:** WR-03 исправлен в двух местах (`update_in_tx` inherent + trait impl),
но третий путь записи тех же пяти колонок остался прежним:
```sql
serial_number = COALESCE(?3, serial_number),
model         = COALESCE(?4, model),
condition     = COALESCE(?5, condition),
complectation = COALESCE(?6, complectation),
notes         = COALESCE(?7, notes),
```
Значения читаются из snapshot через `.and_then(|v| v.as_str())`, т.е.
JSON-`null` и отсутствующий ключ неразличимы (строки 445-452). Undo акта,
откатывающий устройство к состоянию, где поле было пустым, оставит текущее
непустое значение. Практический риск сегодня низкий (операции с актами этих
колонок не меняют), но инвариант «двойной Option на всех слоях», заявленный
в доккомментариях `domain::DevicePatch`, на этом пути не держится — и ничто
об этом не сигнализирует.

**Fix:** либо привести к тому же `CASE WHEN ?n = 1 THEN ?m ELSE col END` с
явным различением `snapshot.get(k)` → `Option<Option<&str>>`, либо
зафиксировать ограничение тестом и доккомментарием на самом методе (сейчас
доккомментарий утверждает обратное: «применяются, если присутствуют»).

### WR-11: тихое отбрасывание printer-блока в двух ветках `sync_printer_row_in_tx`

**File:** `crates/trackly-app/src/services/device_service.rs:236-260`
**Issue:** две ветки молча игнорируют переданные пользователем данные:
1. `if !printer_repo.exists_for_device_in_tx(tx, device_id)?` — если строка
   `printers` уже есть, `printer_override` отбрасывается целиком без ошибки.
   На create-пути сегодня недостижимо, но функция публична внутри сервиса и
   вызывается ещё из `update()`/`bulk_create()`; предпосылка нигде не
   проверяется (ср. прецедент 40/WR-01 «self-enforce precondition»).
2. `community` отбрасывается, когда `ip_address` пуст/из пробелов:
   ```rust
   let community_raw = if ip_address.is_some() { … } else { "public".to_string() };
   ```
   Клиент, приславший `{"ipAddress": "   ", "community": "secret"}`, получит
   `Ok` и принтер с community `public` — без единого указания, что его ввод
   отклонён.

**Fix:** в (1) — `debug_assert!`/`AppError::Internal` при
`printer_override.is_some() && exists`; в (2) — возвращать
`AppError::Validation { field: "printer.community", message: "SNMP community
можно задать только вместе с IP-адресом." }` вместо тихого сброса, по образцу
уже сделанной проверки T-40.3-09.

### WR-12: IP-адрес не валидируется нигде на единственном оставшемся пути заведения принтера

**File:** `crates/trackly-app/src/services/device_service.rs:238-244`, `crates/trackly-app/src/dto/printer.rs:159-162`
**Issue:** `ip_address` — произвольная строка: `trim`, отсев пустой, запись в
БД. Ни формата, ни длины, ни проверки на управляющие символы (сравните:
инвентарный номер на этом же пути проходит
`validate_number_value` — `device_service.rs:140`). Значение затем уходит в
SNMP-клиент (`printer_service::poll_single` → `printer.ip_address`) и
отображается в UI. Раньше тот же пробел был на пути
`printers.create`, но теперь это ЕДИНСТВЕННЫЙ путь заведения принтера, и он
же — публичный HTTP-эндпоинт в server-режиме.

**Fix:** валидировать на сервере (не только в форме):
```rust
let ip: std::net::IpAddr = s.parse().map_err(|_| AppError::Validation {
    field: "printer.ip_address".into(),
    message: format!("Некорректный IP-адрес: «{s}»."),
})?;
```
и тест на отказ (`"not-an-ip"`, строка с `\n`, 500-символьная строка).
