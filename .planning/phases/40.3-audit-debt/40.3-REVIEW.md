## Warnings

### WR-13: `--selftest` is not wired into `pnpm lint` or CI — the gate's self-proof can silently rot

**File:** `ui/scripts/check-act-number-no-regex-split.mjs`, `ui/package.json:16`
**Issue:**
`pnpm lint` calls `node scripts/check-act-number-no-regex-split.mjs` (the real
repo scan) but never `... --selftest`. No `.github/workflows/*.yml` references
`--selftest` either (confirmed by grep — zero matches). The 7-fixture self-test
that is this plan's entire evidence that the two detection rules
(`DIGIT_PREFIX_REGEX_LITERAL_RE`, `NUMBER_RAW_RE` + whitelist) actually catch all
5 known defect forms only ran once, manually, during plan execution. If a future
change to either regex (e.g. someone "simplifies" the pattern while touching an
unrelated part of the file, or a linter auto-fix reformats it into an equivalent
but differently-matching form) silently weakens detection, neither `pnpm lint`
nor CI would notice — the real-scan invocation only checks the CURRENT repo state
against the CURRENT (possibly weakened) rules, it has no independent oracle. This
is exactly the failure mode `40.3-VERIFICATION.md`'s WR-07 finding this plan was
written to close (a gate silently regressed without anyone noticing) — the new
gate is more resistant today, but the mechanism protecting it from the same class
of drift over time is not automatically enforced.
**Fix:**
```json
"lint": "eslint . --ext .ts,.svelte && prettier --check . && node scripts/check-tokens.mjs && ... && node scripts/check-act-number-no-regex-split.mjs && node scripts/check-act-number-no-regex-split.mjs --selftest",
```
or a dedicated `pnpm test:gates` step wired into CI that runs `--selftest` for
every `check-*.mjs` script that has one — establishing that as the actual pattern
for future gates with self-tests (the SUMMARY's own
`patterns-established` note frames this as a project pattern going forward, so
CI enforcement should exist from the first instance).

### WR-14: `DIGIT_PREFIX_REGEX_LITERAL_RE` is a loose text match, not anchored to an actual regex literal — plausible future false positive

**File:** `ui/scripts/check-act-number-no-regex-split.mjs:67`
**Issue:**
```js
const DIGIT_PREFIX_REGEX_LITERAL_RE = /\/\^\(?\\?(?:d|\[0-9\])/g;
```
This matches the literal substring `/^` + optional `(` + optional `\` + (`d` or
`[0-9]`) **anywhere in the file**, not just inside an actual JS `RegExp` literal
context, and the `\\?` backslash is optional — so it matches not only `/^\d`,
`/^(\d`, `/^[0-9]` but also `/^d...` **without** a backslash (e.g. a hypothetical
future `/^data:/`, `/^dev\//`, `/^default/` check for something unrelated to act
numbers, such as a MIME-type or path-prefix validator). It also fires inside
string/template literals and comments, not just code — a doc-comment that quotes
this exact pattern for explanation (as this very file's own header comment does,
harmlessly, only because the header is in a `.mjs` file the gate doesn't scan)
would trip the gate if written inside a `.svelte`/`.ts` file. Currently 0
violations in the real repo (verified: `node scripts/check-act-number-no-regex-split.mjs`
→ `PASS`), so this is not a live bug, but it is a foreseeable maintenance
false-positive that would make `pnpm lint` fail for a reason unrelated to act
numbering, likely confusing whoever hits it first.
**Fix:** tighten the pattern to require the digit-prefix construct is actually
inside a regex literal delimiter context, e.g. require a preceding `.replace(`/
`new RegExp`/bare `/.../ ` boundary, or at minimum require the backslash before
`d` (drop the `\\?` optionality for the bare-`d` case — `[0-9]` doesn't need it,
`\d` does) so `/^d[a-z]/`-shaped identifiers don't match. Not urgent — flag for
the next time this file is touched.

## Info

### IN-07: `run_to`'s `pending` branch reads `foreign_keys` PRAGMA state that is discarded on the `else` branch — asymmetric, harmless today

**File:** `crates/trackly-infra/src/db/migrations.rs:335-395`
**Issue:** Not a defect in the round-2 diff itself (pre-existing structure,
untouched by plans 06-09) — noted only because it sits directly inside the
function these plans hardened. The `pending` branch captures `fk_was_on` and
restores it after toggling FKs off for the rebuild window; the `else` (no
pending migrations) branch never touches the FK pragma at all, relying on
whatever `pragmas::apply_writer_pragmas` already set. This is correct given
`AppCtx::build`'s ordering, but the function's own inline comment ("Foreign keys
are disabled on the connection for the whole run") reads as if it always applies
— it only applies when `pending` is true. No fix required for this review; noting
for anyone extending `run_to` who assumes symmetry between the branches.

### IN-08: `NumberTemplateField`'s edit-mode `context` still reads `device_create`/`printer_create` — no dedicated edit context exists

**File:** `ui/src/features/devices/DeviceFormBody.svelte:807`, `ui/src/bindings.ts:3048`
**Issue:** `numberContext` (`typeId === PRINTER_TYPE_ID ? 'printer_create' :
'device_create'`) is passed unchanged to the edit-mode `NumberTemplateField`
instance added by this round. `TemplateContextDto` only has 5 create-flavoured
variants (`device_create | printer_create | act_create | cartridge_create |
drum_create`) — there is no `device_edit`/`printer_edit` to pass instead, so this
is not a mistake, just a reuse of the only available context (confirmed
server-side gating via `action_for_context` maps both to `MutateDevices`
regardless, so no authorization gap). Recorded as INFO only because a reader
tracing `context` values might reasonably expect an edit-specific context to
exist; it doesn't, and the plan's own SUMMARY explains the reuse is deliberate.
No fix needed unless a future phase adds edit-specific number-template behavior
(e.g. a different remembered-template-per-context split for edit vs create).
