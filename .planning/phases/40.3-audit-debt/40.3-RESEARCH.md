## Summary

(аудит 2026-09-22). Все четыре находки (WR-03, N-1, N-2, N-4) были прочитаны в реальном коде на

Главный вывод: **WR-03 сложнее, чем формулировка в ROADMAP.** Прикладной DTO-слой
(`crates/trackly-app/src/dto/device.rs::DevicePatch`) УЖЕ имеет `Option<Option<String>>` для
`serial_no`/`model`/`specs`/`kit`/`state` (сделано в Фазе 40.2 Plan 08 «за компанию» с
`inventory_no`/`place_id`, но не задействовано). Однако (1) ни один из них не несёт
`#[serde(default, with = "serde_with::rust::double_option")]`, поэтому JSON `null` **не
отличим от отсутствия поля** («классическая double-Option ловушка» serde — см. Pitfall 1); и
(2) доменный слой (`crates/trackly-core/src/domain/devices.rs::DevicePatch`) для этих пяти полей
до сих пор одинарный `Option<String>`, поэтому даже если DTO-слой различит «не передано» и
«очищено», разница стирается на границе `impl From<DevicePatch> for domain::DevicePatch`. Нужно
чинить оба слоя плюс SQL (сейчас `COALESCE`, нужен `CASE` — паттерн уже есть для
`inventory_number`/`place_id` в этом же файле).

**Primary recommendation:** для каждой из четырёх находок — точечная правка по уже
установленному в кодовой базе паттерну (place_id/inventory_no double-Option, DeviceFormModal
create-режим, is_occupied-подобный diff-бейзлайн). Ни одна не требует нового архитектурного
решения; VOLUME мал (оценочно 4 плана, возможно 1 волна каждая, но N-2 и WR-03 трогают оба
транспорта + фронт и заслуживают отдельных волн/тестов).

## Архитектурные паттерны (подтверждены чтением кода)

### WR-03 — очистка необязательных полей устройства

**Три слоя, все требуют правки:**

1. **`crates/trackly-core/src/domain/devices.rs`** (строки 44 области `DevicePatch`) — сейчас:
   ```rust
   pub serial_no: Option<String>,
   pub model: Option<String>,
   pub specs: Option<String>,
   pub kit: Option<String>,
   pub state: Option<String>,
   ```
   Нужно расширить до `Option<Option<String>>`, по образцу уже существующего
   `pub inventory_no: Option<Option<String>>` (строка 44) / `pub place_id: Option<Option<i64>>`
   в этом же файле — комментарий над `inventory_no` в файле объясняет ровно нужную семантику.

2. **`crates/trackly-app/src/dto/device.rs`** — `DevicePatch` (строка ~208) УЖЕ
   `Option<Option<String>>` для всех пяти полей. Требуется добавить
   `#[serde(default, with = "serde_with::rust::double_option")]` на каждое (см. Pitfall 1 —
   без этого атрибута JSON `null` неотличим от отсутствующего ключа). Конверсия
   `impl From<DevicePatch> for domain::DevicePatch` (строка ~217) сейчас **стирает** различие:
   ```rust
   if let Some(inner) = dto.serial_no { p.serial_no = inner; }
   ```
   После расширения domain-слоя (шаг 1) это должно стать точно как для `place_id` (строка
   ~246):
   ```rust
   if let Some(inner) = dto.place_id { p.place_id = Some(inner); }
   ```
   то есть `p.serial_no = Some(inner)` (сохранить внешний `Option`, не разворачивать).

3. **`crates/trackly-infra/src/repos/devices_sqlite.rs::update_in_tx`** (строки ~270-300 и
   зеркально ~700-720 — правка нужна в ДВУХ местах, вероятно `update_in_tx` и ещё один — грепнуть
   `serial_number.*COALESCE` перед планированием, чтобы не пропустить копию) — сейчас:
   ```sql
   serial_number    = COALESCE(?5, serial_number),
   model            = COALESCE(?6, model),
   condition        = COALESCE(?7, condition),
   complectation    = COALESCE(?8, complectation),
   ```
   Нужно заменить на `CASE WHEN ?N = 1 THEN ?N+1 ELSE column END` — **паттерн уже реализован в
   этом же файле** для `inventory_number` и `place_id` (строки 291-296), включая подробный
   doc-комментарий, объясняющий именно эту ловушку (`COALESCE` не отличает «не передано» от
   «передано NULL явно»). Нужно добавить 5 новых параметров-флагов (`is_some() as i64`) плюс 5
   значений — параметризация `rusqlite::params![...]` сдвинется, все позиционные `?N` ниже по
   списку нужно пересчитать.

**Фронтенд менять НЕ требуется** — `DeviceFormBody.svelte:591-596` уже шлёт
`serial_no: serialNo.trim() || null` и т.д. (проверено чтением кода submitEdit) — то есть
контракт с фронта корректен уже сейчас, баг целиком в трёх бэкенд-слоях выше.

### N-1 — тост возврата искажает шаблонный номер

**Файл:** `ui/src/features/acts/ReturnModal.svelte:329-334` (подтверждено чтением — фактическая
строка ближе к 329, не 332, из-за комментариев выше по файлу; искать
`ret.number.replace(/^\d+/, '')`):
```typescript
const suffix = ret.number.replace(/^\d+/, ''); // «в» / «в1»
pushToast(
  'success',
  `Создан акт возврата №${ret.number_raw}${suffix}. ${n} устр. вернулось на склад.`,
);
```
Бэкенд (`ActDto`, `crates/trackly-app/src/dto/act.rs:54-57`) уже отдаёт готовое `number: String`
(итоговое отображаемое значение, включая суффикс возврата) отдельно от `number_raw: String`
(исходное поле до форматирования). Правка — заменить склейку на прямое использование `number`:
```typescript
pushToast(
  'success',
  `Создан акт возврата №${ret.number}. ${n} устр. вернулось на склад.`,
);
```
`number_raw`/regex-склейка после этой правки в `ReturnModal.svelte` становится неиспользуемой —
если `number_raw` нигде больше в этом файле не читается, ESLint `no-unused-vars` не сработает
(это поле DTO, не локальная переменная), но стоит грепнуть весь файл на `number_raw` перед
закрытием находки, чтобы не оставить второй такой же баг рядом.

**Важно для success criteria п.2** («в UI не остаётся кода, который считает номер акта
начинающимся с цифр») — обязательно грепнуть весь `ui/src/` на `\.replace\(/\^\\d`, а не только
`ReturnModal.svelte`, поскольку F7 (forward_risk из аудита) явно предупреждает: «любой клиентский
код, собирающий номер из `number_raw` + суффикс, повторит N-1» — это не единичный инцидент, а
класс бага.

### N-4 — проверка целостности FK после миграций срабатывает один раз

**Файл:** `crates/trackly-infra/src/db/migrations.rs::run_to` (строки 178-232, подтверждено
чтением полностью).

**Точный механизм бага:** проверка новых FK-нарушений (`baseline` до / `after` после запуска
refinery) выполняется **только внутри ветки `if pending { ... }`** (строка 185). `pending`
вычисляется как `last_applied_version(conn) < goal` (строка 180-183). Если предыдущий запуск
успел зафиксировать миграцию (refinery коммитит свою транзакцию ДО того, как наш код успевает
вернуть `Err` из-за найденных нарушений — `result.map_err(...)` на строке 202 срабатывает уже
ПОСЛЕ `build_runner(target)?.run(conn)` на строке 195, то есть refinery уже применил и закоммитил
SQL к моменту, когда мы решаем «отказать»), то `refinery_schema_history` уже содержит новую
версию. На следующем старте `last_applied_version == goal`, `pending = false`, выполняется ветка
`else` (строка 226-232) — **без единого вызова `fk_violations()`**. Приложение стартует с уже
испорченной ссылочной целостностью навсегда, пока кто-то вручную не почистит данные.

**Рекомендуемое решение (архитектурный паттерн, не existing precedent в этом кодовой базе —
Claude's discretion по деталям хранения, см. Open Questions):**

Развязать «проверка целостности» и «есть ли что мигрировать» — гонять `fk_violations()`
БЕЗУСЛОВНО на каждом старте, сравнивая не с in-memory бейзлайном текущего запуска (который
существует только пока идут миграции), а с **персистентным** бейзлайном, обновляемым только
когда проверка проходит чисто:

1. Прочитать персистентный бейзлайн `B` (если отсутствует — первый когда-либо запуск этой
   проверки на данной БД: взять текущие `fk_violations()` ДО каких-либо изменений этим запуском
   как `B` — эквивалент сегодняшнего поведения «предсуществующие нарушения не блокируют»).
2. Запустить миграции, если `pending`.
3. Посчитать `after = fk_violations(conn)` (уже сегодня так и есть, просто не привязано к
   персистентному `B`).
4. `new = after \ B`. Если непусто → `Err` (блокирует старт), **не обновлять** `B` — при
   следующем старте (даже без pending-миграций) `new` будет вычислено снова из того же старого
   `B` и снова заблокирует. Это прямо удовлетворяет обеим половинам N-4.
5. Если `new` пусто → сохранить `after` как новый `B` (self-heal: если админ руками почистил
   данные, следующий чистый старт «подтягивает» бейзлайн вниз).

**Где хранить `B`:** таблица `app_settings` (`migrations/V016__cartridges_kind_color_settings.sql:37`,
`key TEXT PRIMARY KEY, value TEXT`) уже существует в схеме и уже используется для несвязанных
настроек (`low_stock_threshold`). Можно сериализовать набор нарушений (например, join строк
`table:rowid:parent:fkid`) в один `value`. **Пограничный случай:** на очень старой БД, которая
сама проходит миграцию V016 в ЭТОМ ЖЕ запуске, `app_settings` ещё не существует в момент, когда
нужно прочитать `B` ДО запуска миграций — это нормально, трактовать как «нет персистентного
бейзлайна» (шаг 1, случай «первый запуск») и писать `B` только ПОСЛЕ того, как миграции
(включая V016) гарантированно применились. Альтернатива — отдельная новая таблица через новую
миграцию (`V04N__migration_integrity_baseline.sql`) — чище по разделению ответственности (не
путать пользовательские настройки с внутренним состоянием раннера), но требует ещё одной
миграции в ТОЙ ЖЕ фазе, что чинит миграционный раннер — обе опции валидны, решение — за
планировщиком/discuss (см. Open Questions).

**Existing test scaffold:** `crates/trackly-infra/src/db/migrations.rs`, модуль `#[cfg(test)]`
(строка 250+) уже содержит `fresh_conn()` helper и `run_applies_all_known_migrations_on_fresh_db`,
`run_is_idempotent_on_same_connection` — новый тест для N-4 должен: (1) применить миграции на
свежей БД, (2) руками испортить FK (вставить осиротевшую строку через `PRAGMA foreign_keys=OFF`
+ `INSERT`), (3) вызвать `run_up_to`/`run` СНОВА без новых pending-миграций и убедиться, что
`Err` возвращается — это прямой регресс-тест на «блокирует не только в первый раз».

## Common Pitfalls

### Pitfall 1: serde `Option<Option<T>>` без `double_option` неотличим от отсутствующего поля

**Что идёт не так:** Стандартный `#[derive(Deserialize)]` на поле `Option<Option<T>>` без
атрибута `with = "serde_with::rust::double_option"` коллапсирует и «ключ отсутствует», и «ключ
присутствует со значением `null`» в один и тот же внешний `None`. Это классическая, хорошо
задокументированная ловушка serde (не специфична для проекта) — единственный способ различить
«не передано» / «явно очищено» / «новое значение» на JSON-границе — обернуть `Option<Option<T>>`
через `serde_with::rust::double_option` (обязательно вместе с `#[serde(default)]`, иначе
отсутствующий ключ станет ошибкой десериализации, а не `None`).

**Почему это опасно именно здесь:** `DevicePatch` (app-DTO) уже помечен `Option<Option<String>>`
для 5 полей — на первый взгляд паттерн «уже применён», и легко ошибочно решить, что достаточно
расширить domain-слой и SQL, не трогая serde-атрибуты. Без атрибута фикс не сработает через
реальный HTTP/Tauri транспорт (хотя сработает в юнит-тестах, которые строят `DevicePatch`
напрямую в Rust, минуя serde полностью — см. Pitfall 2).

**Как избежать:** добавить `#[serde(default, with = "serde_with::rust::double_option")]` на
каждое из 5 полей одновременно с расширением domain-слоя; убедиться, что `#[specta::Type]` не
конфликтует с этим атрибутом (specta умеет работать с `serde(with=...)`, но стоит проверить
сгенерированный `bindings.ts` — тип поля в TS должен остаться `string | null` с необязательностью
на уровне TS `?`, что уже совместимо с текущим `DeviceFormBody.svelte`, шлющим ключ всегда).

**Предупреждающие знаки:** если новый regression-тест строит `DevicePatch { serial_no: Some(None), ... }`
напрямую в Rust и он «зелёный», а живой UAT через `cargo tauri dev` показывает, что очистка поля
не сохраняется — это Pitfall 2 (тест не идёт через serde-границу).

### Pitfall 2: Unit-тест, строящий DTO напрямую в Rust, не ловит serde-ловушку

**Что идёт не так:** Проект содержит паттерн `devices_http_smoke.rs` (dual-transport smoke test),
который создаёт DTO-структуры напрямую в Rust-коде (`DeviceNew { ... }`) и передаёт их в
`build_devices_create(&ctx, &caller, new.clone())` — это НЕ идёт через `serde_json`
сериализацию/десериализацию, значит не может обнаружить double-Option коллапс.

**Почему это опасно:** Именно поэтому WR-03 «прошлым аудитом ошибочно названный невидимым» (цитата
из `v1.4-MILESTONE-AUDIT.md`, находка WR-03) — существующие Rust-юнит-тесты `devices_crud.rs`
строят `DevicePatch` напрямую и поэтому НЕ видят баг: `Some(None)` доходит до SQL-слоя без
проблем, если тест САМ его сконструировал в Rust, минуя JSON целиком.

**Как избежать:** регресс-тест для WR-03 обязан либо (а) идти через реальный HTTP-транспорт
(`build_router` + `Body::from(serde_json::to_string(&json!({...})))` с буквальным
`"serial_no": null` в JSON, по образцу `devices_http_smoke.rs`), либо (б) явно десериализовать
`DevicePatch` из строкового JSON через `serde_json::from_str::<DevicePatch>(r#"{"serial_no": null, ...}"#)`
и затем передать РЕЗУЛЬТАТ в сервис — не конструировать структуру literal'ом. Разница между «не
передано» (ключ отсутствует в JSON) и «передано null» (ключ есть, значение null) должна быть
явно закодирована в ДВУХ разных JSON-строках теста, дающих РАЗНЫЙ результат.

**Предупреждающие знаки:** verification-план, где единственная команда — `cargo test -p
trackly-app devices_crud` (существующий модуль, строящий DTO напрямую) — недостаточен сам по
себе для WR-03; нужен отдельный тест, специально идущий через `serde_json`.

### Pitfall 3: N-4 требует зеркальной правки в двух местах SQL (если копия найдётся)

**Что идёт не так:** `devices_sqlite.rs` содержит `COALESCE`-паттерн для затронутых полей как
минимум в одном месте (строки ~270-300, подтверждено чтением); в файле есть более одного
вхождения `patch.inventory_no.is_some()` (строки 294 и 715 по grep-результатам этого
research-сеанса) — это может означать вторую копию `update_in_tx`-подобной функции (например,
отдельный путь для bulk-операций или snapshot-восстановления), которую тоже нужно проверить и,
возможно, тоже починить. **Не проверено этим research-сеансом, требует grep на этапе
планирования:** `grep -n "COALESCE(?5\|COALESCE(?6\|COALESCE(?7\|COALESCE(?8" crates/trackly-infra/src/repos/devices_sqlite.rs`.

**Как избежать:** при планировании WR-03 явно включить задачу «найти ВСЕ SQL update-стейтменты
устройства, не только `update_in_tx`» — не полагаться на единственное найденное совпадение.

## State of the Art

Не применимо в классическом смысле (нет внешних библиотек, которые «устарели») — все четыре
находки внутренние. Единственный релевантный пункт: паттерн double-Option для partial-update DTO
(`Option<Option<T>>` + `serde_with::rust::double_option`) — стандартная, не новая техника в
экосистеме Rust/serde, уже частично применена в этом же проекте (`place_id`, DTO-уровень
`inventory_no`/etc до атрибута) — фаза не вводит новый паттерн, а достраивает уже начатый.

## Open Questions

1. **N-2: нужно ли поле IP/community в новом create-диалоге принтера сразу, или откладывать на
   «после создания через PrinterDetail»?**
   - Что мы знаем: `PrinterCreateModal` сегодня позволяет ввести IP/community в том же диалоге;
     `sync_printer_row_in_tx` создаёт строку `printers` с `ip_address: None` при отсутствии
     явного шага 2. `DeviceFormModal` в текущем виде не знает о полях IP/SNMP вообще (это домен
     `printers`, не `devices`).
   - Что неясно: ROADMAP формулирует success criteria N-2 только через призму «шаблоны
     номеров + INV-7 + тип ответа» — не упоминает IP/SNMP явно. Возможно, это осознанное
     упрощение (создать принтер без IP, настроить IP отдельно через PrinterDetail —
     уже работающий путь) или недосмотр формулировки.
   - Рекомендация: явный вопрос для discuss-фазы или явное discretion-решение планировщика —
     либо (а) DeviceFormModal в printer-режиме остаётся без IP/community (простейшая реализация,
     полностью по образцу аудита), либо (б) DeviceFormModal получает опциональный
     IP/community-блок, видимый только когда `typeId === PRINTER_TYPE_ID` (больше работы, ближе к
     паритету с текущим UX).

2. **N-4: новая таблица через миграцию vs переиспользование `app_settings`?**
   - Что мы знаем: обе технически работают (см. Architectural Patterns → N-4 выше).
   - Что неясно: у проекта нет явного прецедента «внутреннее состояние раннера миграций,
     хранимое в самой БД» — оба варианта одинаково новы для кодовой базы.
   - Рекомендация: `app_settings` — меньше кода (не нужна новая `.sql`-миграция ради
     инфраструктуры, которая сама эту миграцию должна пережить), но смешивает пользовательские
     настройки с внутренним состоянием раннера. Планировщик должен явно выбрать один вариант в
     плане, не оставлять «TBD» в реализации.

3. **WR-03: точный список мест, где ещё встречается тот же `COALESCE`-паттерн для этих пяти
   полей помимо `update_in_tx` (строки ~270-300)?**
   - Что мы знаем: второе вхождение `patch.inventory_no.is_some()` на строке ~715 того же файла
     (см. Assumption A2).
   - Что неясно: относится ли эта вторая функция к пути, которым проходит обычное
     `devices_update` (Tauri/HTTP), или это отдельный служебный путь (snapshot restore, bulk
     import), не участвующий в user-facing "очистить поле в форме правки" сценарии.
   - Рекомендация: планировщик должен включить явный grep-шаг в задачу (см. Pitfall 3), прежде
     чем считать WR-03 закрытым — цена пропуска второй копии: тот же баг остаётся в другом
     write-path, незамеченным до следующего аудита.

## Security Domain

### Applicable ASVS Categories

`security_asvs_level: 1` (из `.planning/config.json`), `security_enforcement: true`.

| ASVS Category | Applies | Standard Control |
|---------------|---------|-------------------|
| V2 Authentication | нет | Фаза не трогает аутентификацию |
| V3 Session Management | нет | — |
| V4 Access Control | частично | N-2: новая точка входа («Завести принтер» → `DeviceFormModal`) обязана проходить через ТЕ ЖЕ `Action::MutateDevices`/`role_endpoint_matrix`-проверки, что и существующий `DeviceFormModal`-путь на экране «Устройства» — поскольку это переиспользование существующего компонента, а не новый endpoint, RBAC-поверхность не расширяется (подтвердить существующим `role_endpoint_matrix.rs`, не заводить новых Case) |
| V5 Input Validation | да | WR-03: `trim()`-валидация уже существует на фронте (`DeviceFormBody.svelte`); backend должен продолжать валидировать пустую строку vs `null` идентично существующему `inventory_no`-пути (`number_value::validate_number_value`, хотя эти 5 полей — простой текст, не число, поэтому валидация проще — убедиться, что пустая строка после `.trim()` корректно превращается в `null`, а не сохраняется как `''` вопреки D-08-подобному паттерну, уже применённому к `inventory_no`) |
| V6 Cryptography | нет | — |

### Known Threat Patterns for стека

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| Двойная точка входа с разным уровнем проверки (N-2: `PrinterCreateModal` обходил D-01 цепочку) | Tampering (обход бизнес-инвариантов через альтернативный UI-путь) | Единственный backend-путь создания (`DeviceService::create`/`create_single_with_number_check`), к которому сводятся ВСЕ UI-точки входа — уже стандарт проекта (`ActFormModal`, `CartridgeFormModal` следуют этому же паттерну); N-2 просто устраняет последнее исключение |
| Потеря данных при partial-update (WR-03: молчаливое «не применилось» вместо явной ошибки) | Tampering / Repudiation (пользователь думает, что данные изменены, тост говорит «Устройство сохранено», а поле не изменилось) | Явное различение «не передано»/«очищено» на каждом слое (domain/DTO/SQL) — уже стандарт проекта для `inventory_no`/`place_id`, WR-03 доводит оставшиеся 5 полей до того же стандарта |
| FK-целостность, тихо нарушаемая миграцией и никогда не перепроверяемая | Tampering (данные) / отсутствие Integrity-гарантии на старте | N-4: безусловная проверка на каждом старте против персистентного бейзлайна — стандартный паттерн «fail closed, self-heal on clean state» |
