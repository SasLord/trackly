<objective>
Верификация фазы 40.3 (`40.3-VERIFICATION.md`, BLOCKER-2 / CR-02) нашла, что план 40.3-05
подключил IP/SNMP-блок к форме создания принтера (`DeviceFormBody.svelte`), но условие
видимости блока (`typeId === PRINTER_TYPE_ID && !isEdit`, строка 907) не согласовано с
условием разрешённости поля «Количество» (`quantityDisabled`, строка 282 — учитывает только
`inventoryNo`/`serialNo`, не `ipAddress`). Типовой сценарий для сетевого принтера без
предзаданных номеров: пользователь вводит IP, оставляет «Количество» редактируемым, ставит
> 1 — `handleSubmit` уходит в `devices.bulkCreate()`, которая printer-блок вообще не
принимает (`DeviceNew` не несёт полей IP/community). Тост говорит «Создано N устройств», в БД
— N принтеров с `ip_address = NULL`. Введённые данные теряются молча, без единой ошибки —
прямое нарушение цели N-2 («принтер заводится одним запросом вместе с IP»).

Фикс — вариант (b) из код-ревью (`40.3-REVIEW.md`, CR-01): расширить `quantityDisabled`, а
не менять условие видимости IP-блока. Выбран, а не вариант (a) («скрывать IP-блок при
qty>1»), потому что: (1) это ТОЧНО тот же UX-паттерн, что уже применяется к `inventoryNo`/
`serialNo` в этой же строке — принудительно блокировать «Количество», когда заполнено
уникальное для одной записи поле, без нового состояния/подсказки; (2) `handleSubmit` уже
вычисляет `qty = quantityDisabled ? 1 : ...`, поэтому расширение одного `$derived` полностью
устраняет путь к `bulkCreate()` без изменения самой ветки маршрутизации.

Server-side defense-in-depth (часть (b) требования BLOCKER-2, по прецеденту T-40.3-09):
`device_service.rs::bulk_create` сегодня СТРУКТУРНО не может получить printer-блок
(`DeviceNew` не несёт IP-полей вообще) — поэтому явной проверки там нет, а не потому что она
не нужна. Этот план вводит `bulk_create_with_printer(new, count, printer)` (по прецеденту
`create_single_with_number_check` -> `create_single_with_number_check_with_printer` из
40.3-04: старая 2-арг сигнатура остаётся тонкой обёрткой с `printer=None`, ноль изменений в
существующих вызывающих) с явным `AppError::Validation{field:"printer"}` при
`printer.is_some()` — гарантия, что ЛЮБОЙ будущий caller (транспортный слой, CSV-импорт,
рефакторинг фронтенда), который когда-либо попробует провести printer-блок через bulk-путь,
получит громкую ошибку, а не тихую потерю данных.

**Отложенный долг (вне объёма, явно отложено пользователем):** WR-06 (заведение принтера
через единый путь не пишет audit_log со своим `user_id` — `insert_new_and_get` использует
`user_id_opt: None`), WR-09 (printer-блок авторизуется только `MutateDevices`, не
дополнительно `MutatePrinters`), WR-11 (тихое отбрасывание `printer_override`, когда строка
`printers` уже существует, и `community` без `ip_address`), WR-12 (IP-адрес нигде не
валидируется как корректный IPv4/IPv6), IN-01 (тест «атомарности» не проверяет откат при
ошибке), IN-02 (доккомментарии ссылаются на удалённый `PrinterCreateModal.svelte`), IN-04
(переключение типа с «Принтер» на «Устройство» на экране «Принтеры» создаёт запись, которая
тут же пропадает из списка), IN-05 (два публичных метода с похожими именами), IN-06 (SNMP
community идёт через devices-эндпоинт, потенциально открытым текстом на HTTP fallback). Все
перечислены здесь как известный, сознательно отложенный долг — не переоткрываются в 40.3.

Purpose: IP/community, введённые пользователем при заведении принтера, никогда не теряются
молча, независимо от того, что происходит с полем «Количество».
Output: `DeviceFormBody.svelte` блокирует «Количество» при заполненном IP для типа Принтер;
`device_service.rs` несёт явную серверную защиту от непустого printer-блока в bulk-пути.
