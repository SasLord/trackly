# Phase 41: Группы: модель и редактор — Specification

**Created:** 2026-10-04
**Ambiguity score:** 0.128 (gate: ≤ 0.20)
**Requirements:** 14 locked

## Goal

Устройства можно собрать в группу с типом, своими свойствами и местом: тип задаёт поведение и
набор полей, группа владеет местом своих устройств, и раздел «Группы» даёт полный CRUD типов,
свойств, групп и состава.

## Background

Сущности «группа» в приложении нет ни в одном слое. Что есть сегодня:

- **Каркас редактора готов целиком**: `PlacesMasterDetail` / `PlaceTree` / `PlaceTreeNode` /
  `PlaceFormModal` (`ui/src/features/places/`), серверная часть — `places_sqlite.rs` +
  `place_service.rs` с циклобезопасным `move_node`, `subtree_stats`, `full_path`. Дерево групп
  ложится на этот каркас, но групп в нём нет.
- **Пользовательских свойств (EAV) нет нигде**: `org_settings` (V026) — таблица с фиксированными
  колонками, не key-value. Прецедента в проекте нет вообще, схема проектируется с нуля.
- **Журнал перемещений есть** (`place_movements`, V040) и в нём уже зарезервирован токен
  `source = 'workstation'`, который не пишет никто. `entity_type` принимает `'device' | 'cartridge'`
  без SQL `CHECK` (валидация только Rust-side, `from_str_lenient`), поэтому новый токен `'group'`
  не требует перестройки таблицы. Колонки для корреляции пакета (`batch_id`) нет.
  `from_place_id` / `to_place_id` — `NOT NULL`.
- **USB-привязка принтера к хосту уже существует**: `printers.usb_host_device_id` (V020, PRN-04).
  Это источник «USB-принтеров АРМ», новой связи для них не нужно.
- **Роли**: `admin | manager | employee` (`crates/trackly-core/src/auth.rs:18`, V002,
  `UserRole` в UI). Роли «Специалист» в коде нет.
- **AD-каталог** умеет только `resolve(sam_account_name)` — точное разрешение одного логина
  (`ports/ad_directory.rs:78`). Поиска по подстроке нет.
- **Сайдбар** — `ui/src/features/layout/sidebar-config.ts` с пометкой
  «PINNED: 12 items + 4 dividers = 16 entries — source of truth per UI-SPEC».
- **Слово «группа» уже занято**: в разделе «Устройства» так называется свёртка одинаковых
  устройств в одну строку с количеством (`DeviceGroupRow.svelte`, `list_grouped`).

Полный брифинг решений, значений по умолчанию и вскрытого техдолга —
`.planning/v1.4-GROUPS-MODEL-DECISIONS.md`.

## Requirements

1. **Тип группы: код и поведение**: тип несёт машинно-стабильный код и поведение из закрытого
   набора.
   - Current: сущности «тип группы» не существует
   - Target: таблица типов с `code` (уникальный, неизменяемый), `name` (редактируемый),
     `behavior ∈ {container, substitute, teardown}` (неизменяемый), `is_builtin`, `sort_order`,
     признак и подпись быстрого действия
   - Acceptance: попытка изменить `code` или `behavior` у существующего типа отклоняется на обоих
     транспортах; переименование проходит; создание типа с неизвестным `behavior` отклоняется

2. **Идемпотентный засев встроенных типов**: три типа появляются сами и не дублируются.
   - Current: засева нет
   - Target: при старте приложения отсутствующие типы с кодами `workstation`, `system_unit`,
     `teardown` создаются (имена «АРМ», «Системный блок», «Разбор», быстрые действия
     «Сформировать группу», «Замещение группой», «На разбор»); существующие не перезаписываются
   - Acceptance: тест переименовывает «АРМ» → «Рабочее место», перезапускает засев и проверяет,
     что типов с кодом `workstation` ровно один и его имя осталось изменённым; удаление
     встроенного типа отклоняется с ошибкой

3. **Редактор свойств типа**: администратор ведёт набор полей типа.
   - Current: свойств нет
   - Target: CRUD свойств с полями `name`, `data_type ∈ {text, number, ip, mac, users, device_refs}`,
     `sort_order`, `is_required`, `show_on_map`
   - Acceptance: для типа создаются свойства всех шести типов данных; изменение `sort_order`
     меняет порядок в форме группы; `show_on_map` сохраняется и возвращается API (потребитель —
     фаза 43)

4. **Защита заполненных свойств**: правка схемы не теряет данные молча.
   - Current: n/a
   - Target: удаление свойства с заполненными значениями выполняется как скрытие
     (`archived_at_utc`), значения сохраняются; смена `data_type` у свойства с заполненными
     значениями отклоняется; включение `is_required` у свойства, где есть группы с пустым
     значением, отклоняется с перечислением таких групп
   - Acceptance: три отдельных теста — скрытое свойство исчезает из формы, но его значения
     читаются из БД; смена типа данных отклоняется с `AppError::Validation`; включение
     обязательности отклоняется и называет группы-нарушители

5. **Серверная валидация значений**: типизированные поля проверяются на сервере.
   - Current: n/a
   - Target: `ip` принимает IPv4/IPv6 и нормализуется, `mac` принимает три разделителя
     (`:`, `-`, без) и нормализуется к одному виду в нижнем регистре, `number` отклоняет нечисловое,
     `users` принимает только id живых пользователей, `device_refs` — только id живых устройств
   - Acceptance: таблица-тест на валидные и невалидные значения каждого типа; невалидное
     значение отклоняется и в Tauri-команде, и в HTTP-обработчике (не только в UI)

6. **Раздел «Группы» и дерево**: редактор доступен из сайдбара.
   - Current: раздела нет; сайдбар зафиксирован на 16 записях
   - Target: пункт «Группы» между «Устройства» и «Акты», маршрут `/groups`, дерево слева (корни —
     типы, внутри — группы), панель справа: для типа — просмотр/правка и CRUD свойств, для
     группы — свойства и таблица состава; пометка PINNED в `sidebar-config.ts` обновлена
   - Acceptance: пункт виден `admin` и `manager`, не виден `employee`; выбор типа и выбор группы
     показывают разные панели; прямой переход на `/groups` под `employee` отдаёт «Доступ запрещён»

7. **CRUD группы и нумерация**: группа создаётся с предсказуемым именем по умолчанию.
   - Current: групп нет
   - Target: создание/правка/удаление группы; поля `type_id`, `name`, `seq`, `place_id`,
     `parent_group_id`; имя по умолчанию «{имя типа} #{seq}», где `seq = MAX(seq)+1` по типу,
     вычисленный из целочисленной колонки, а не разбором имён; имя редактируется, уникальность
     имён не требуется
   - Acceptance: две группы одного типа получают `seq` 1 и 2; переименование первой в «АРМ #99»
     не влияет на `seq` третьей (она получает 3); две группы с одинаковым именем сохраняются без
     ошибки

8. **Членство**: устройство принадлежит не более чем одной группе.
   - Current: связи устройство↔группа нет
   - Target: добавление существующих устройств в группу и явный вывод из состава; БД-ограничение
     «устройство не более чем в одной группе»; группа может содержать группу с защитой от циклов;
     тип с `behavior = teardown` групп не содержит
   - Acceptance: добавление устройства, уже состоящего в другой группе, отклоняется с понятной
     ошибкой; попытка вложить группу в её собственного потомка отклоняется; попытка вложить группу
     в группу типа `teardown` отклоняется

9. **Место группы и протаскивание**: место состава следует за местом группы.
   - Current: `devices.place_id` меняется только индивидуально
   - Target: смена места группы обновляет `place_id` у всех устройств состава, включая устройства
     вложенных групп; место вложенной группы производное от корневой и отдельно не редактируется;
     добавление устройства в группу с местом присваивает ему место группы
   - Acceptance: перенос группы из 6 устройств (2 из них во вложенной группе) меняет место у всех
     6; место вложенной группы в API только для чтения; устройство, добавленное в группу с местом,
     получает это место

10. **Журнал перемещений группы**: один перенос читается как одно событие.
    - Current: `place_movements` без корреляции пакета; `entity_type` не знает групп
    - Target: перенос группы пишет строку `entity_type = 'group'` и по строке на каждое устройство
      состава, все с общим `batch_id` и `source = 'group'`; отчёт HST-04 и история места по
      умолчанию показывают одну свёрнутую строку на пакет с раскрытием в состав; история
      конкретного устройства показывает его собственную строку; устройство без места, попадающее
      в группу, строку в журнал не пишет (нет «откуда») — событие уходит в `audit_log`
    - Acceptance: перенос группы из 6 устройств даёт 7 строк с одним `batch_id`; отчёт за период
      показывает одну строку с раскрытием; история одного из устройств показывает его строку;
      добавление устройства с `place_id IS NULL` в группу с местом не создаёт строк в
      `place_movements` и создаёт запись в `audit_log`; `batch_id` добавлен через
      `ALTER TABLE ADD COLUMN` без перестройки таблицы

11. **Запрет индивидуального перемещения**: место устройства в группе задаётся только группой.
    - Current: место устройства редактируется в форме устройства и в «Местах» всегда
    - Target: для устройства, входящего в группу, смена места отклоняется на сервере и
      заблокирована в UI с пояснением «место задаётся группой»; чтобы переместить устройство
      отдельно, его выводят из состава
    - Acceptance: `DeviceService::update` с новым `place_id` для устройства в группе возвращает
      ошибку; то же через HTTP; после вывода из состава смена места проходит

12. **Карточка группы**: видно состав, место, людей и принтеры.
    - Current: n/a
    - Target: панель группы показывает состав (с указанием вложенных групп), место, значения
      свойств, пользователей из свойства типа `users` (выбор только из таблицы `users` — локальные
      и ранее зарегистрированные AD-пользователи; один отмечен основным) и подключённые принтеры:
      производные от `printers.usb_host_device_id` для устройств состава (только чтение) плюс
      явные ссылки из свойства `device_refs`, с дедупликацией при отображении
    - Acceptance: принтер, у которого `usb_host_device_id` указывает на устройство состава,
      появляется в карточке без ручной привязки и не редактируется; тот же принтер, добавленный
      ещё и ссылкой, отображается один раз; отметка основного пользователя сохраняется и
      возвращается API

13. **Права доступа**: типы — администратор, группы — администратор и менеджер.
    - Current: прав на группы нет
    - Target: CRUD типов и свойств — только `admin`; CRUD групп, состава и значений свойств —
      `admin` и `manager`; `employee` не имеет доступа к разделу и его API. Роль «Специалист» =
      существующий `manager`, четвёртая роль не вводится
    - Acceptance: матрица тестов 3 роли × (тип, группа) на обоих транспортах; `manager` создаёт
      группу и получает отказ на создании типа; `employee` получает отказ на всём

14. **Переименование прежней «группировки»**: слово «группа» означает одну вещь.
    - Current: свёртка одинаковых устройств называется группировкой («Группировать одинаковые»)
    - Target: во всех пользовательских надписях раздела «Устройства» эта свёртка называется
      «Свернуть одинаковые»; слово «группа» в UI относится только к новой сущности
    - Acceptance: grep по `ui/src` не находит пользовательских строк, где свёртка одинаковых
      устройств названа группой; снимок/тест раздела «Устройства» показывает «Свернуть одинаковые»

## Boundaries

**In scope:**
- Схема: типы групп, свойства типов, группы, членство устройств, значения свойств (включая
  связи `users` и `device_refs`), `batch_id` в `place_movements`
- Раздел «Группы»: дерево типов и групп, панель типа (свойства), панель группы (свойства + состав)
- Создание группы «с нуля» и добавление в неё **существующих** устройств
- Протаскивание места на состав, журнал перемещений с корреляцией пакета
- Запрет индивидуального перемещения устройства, входящего в группу
- Права: типы — admin, группы — admin + manager
- Переименование прежней свёртки одинаковых устройств

**Out of scope:**
- Чекбокс «Сформировать на основе устройства», якорное замещение, разбор, статусы «На списание» и
  «В ремонте», контекстное меню устройства, правый/двойной клик — Фаза 41.1 (решение раунда 1:
  фаза 41 остаётся проверяемой как «контейнер + состав»)
- Выбор группы в акте, подтверждение выноса устройства актом, `act_id` в перемещениях членов,
  отображение групп в «Местах» и чекбокс «Разворачивать группы» — Фаза 41.2
- Вложения, ремонтные заявки, переписка, раздел «Устройства» для сотрудника — Фазы 41.3–41.6
- Ранжирование принтеров в заявке — Фаза 42 (фаза 41 только поставляет связи)
- Отображение свойств на карте и правило агрегации вложенных групп — Фаза 43 (в 41 флаг
  `show_on_map` только хранится и отдаётся API)
- Четвёртая роль «Специалист» — решено: это существующий `manager`
- Поиск по AD-каталогу и привязка пользователя, ни разу не входившего в приложение — в AD-слое
  есть только `resolve()` по точному логину; добавление поиска не входит в фазу
- Типы свойств Словари (enum), Списки, Файлы — GRPX-02
- Группы в отчётах, CSV-импорте и экспорте — GRPX-03
- Миграция существующих устройств в группы — не требуется, БД обнуляется

## Constraints

- **Миграции**: только аддитивные (`CREATE TABLE`, `ALTER TABLE ADD COLUMN`). Перестройка
  `place_movements` или `devices` запрещена: `PRAGMA foreign_keys = OFF` не действует внутри
  refinery-транзакции, и перестройка таблицы с детьми уже приводила к каскадной потере данных
  (V042 стирал `act_items`). `batch_id` добавляется колонкой, `entity_type = 'group'` не требует
  изменения схемы — SQL `CHECK` на этой колонке нет по решению Фазы 40.
- **Запись в БД** — только через единый writer (`spawn_blocking` + `mpsc`), WAL, `busy_timeout`.
  Протаскивание места на состав выполняется одной транзакцией: либо все устройства, либо ни одно.
- **Домен без serde**: типы в `trackly-core` без `Serialize`/`specta`, DTO — в `trackly-app`.
  Опциональные поля правки — двойной `Option` (`Option<Option<T>>`), как в `DevicePatch`,
  иначе «не передано» и «очистить» неразличимы на уровне SQL `COALESCE`.
- **Паритет транспортов**: каждая операция доступна и Tauri-командой, и в `/api/v1/*`; бизнес-логика
  живёт в сервисном слое, обработчики — тонкие адаптеры.
- **UI**: Svelte 5 runes, SCSS-токены дизайн-системы, выпадающие списки — компонент `Dropdown` из
  витрины, **не** нативный `<select>` и не обёртка `Select`; таблица состава — существующий
  табличный компонент с его правилом фокуса (inset-ring на первой ячейке).
- **Роли**: `admin | manager | employee`, новых не вводится.
- **Масштаб**: до ~5000 устройств, 100–150 устройств на место; дерево групп и панель состава
  открываются без заметной задержки на этом объёме.
- **Локализация и приватность**: UI только русский; в коде, тестах, фикстурах и планах — только
  вымышленные ФИО («Иванов И.И.») и placeholder'ы, репозиторий публичный.

## Acceptance Criteria

- [ ] `code` и `behavior` типа неизменяемы; переименование типа проходит
- [ ] Повторный засев после переименования «АРМ» не создаёт второй тип с кодом `workstation`
- [ ] Удаление встроенного типа отклоняется
- [ ] Свойства всех шести типов данных создаются, упорядочиваются и сохраняются
- [ ] Удаление свойства с заполненными значениями скрывает его, значения остаются в БД
- [ ] Смена `data_type` у заполненного свойства отклоняется
- [ ] Включение `is_required` при наличии групп с пустым значением отклоняется и называет их
- [ ] IP и MAC нормализуются; невалидные значения отклоняются на обоих транспортах
- [ ] Пункт «Группы» виден admin и manager, не виден employee; `/groups` под employee — отказ
- [ ] Имя по умолчанию «{тип} #{seq}» берётся из колонки `seq`; переименование не сдвигает счётчик
- [ ] Две группы с одинаковым именем сохраняются
- [ ] Устройство нельзя добавить во вторую группу; цикл вложенности отклоняется; вложение в
      `teardown` отклоняется
- [ ] Перенос группы из 6 устройств (2 во вложенной группе) меняет место у всех 6 одной транзакцией
- [ ] Перенос даёт 7 строк журнала с общим `batch_id`; отчёт показывает одну свёрнутую строку;
      история отдельного устройства показывает его строку
- [ ] Добавление устройства без места в группу с местом не пишет в `place_movements` и пишет в
      `audit_log`
- [ ] Смена места устройства, входящего в группу, отклоняется на обоих транспортах; после вывода
      из состава проходит
- [ ] USB-принтер устройства состава появляется в карточке группы автоматически, не редактируется
      и не дублируется, если добавлен ещё и ссылкой
