# Phase 40.1: Code Review Report

**Reviewed:** 2026-09-18T00:00:00Z
**Depth:** standard
**Files Reviewed:** 20 (diff scoped against `430653ec..HEAD`, the phase's own commits `40.1-01..04`)
**Status:** issues_found

## Summary

Phase 40.1 closes four audit gaps from the v1.4 milestone audit: BLOCKER-1
(place delete pre-flight missed `place_movements` FK references), BLOCKER-2
(missing «Тип устройства» filter control for the movements report), WARNING-1
(incomplete `notifyPlaceContentChanged` producer coverage across place-tree
write-sites), and WARNING-4 (CSV export header used raw column keys instead of
Russian labels). All four are implemented correctly and are backed by
targeted regression tests; I traced the SQL, the index-alignment between
`columns_for`/`column_labels_for` across CSV/PDF/screen, the minijinja
autoescape configuration for the new `filter_summary` template variable, the
`_legacy_defaults/v28` template-upgrade snapshot, and the Svelte-5 rune usage
in the new `notifyPlaceContentChanged` producers — no correctness defects
found in the changed logic itself, and no privacy violations (all test/demo
data is fictional, consistent with CLAUDE.md).

Two gaps remain in the review's focus areas, both Warning-level:

1. WARNING-1's own closure is incomplete — a fourth client write-site that
   changes a cartridge's `place_id` (the lifecycle-operation modal: install /
   return-to-stock / to-refill / from-refill / write-off) was not wired as a
   `notifyPlaceContentChanged` producer, and the new INV-7 gate does not cover
   it either, so it cannot catch a future regression there.
2. `build_movements_filter_summary`'s place-name resolution can hard-fail the
   entire PDF export (`AppError::NotFound`) if a filtered place is deleted
   between filter selection and export, unlike the sibling `device_type_name`
   lookup in the same function, which is explicitly designed to degrade
   gracefully instead of failing the whole export.

Two Info-level documentation staleness items are also listed below.

## Warnings

### WR-01: WARNING-1 gap-closure misses the cartridge lifecycle-operation write-site

**File:** `ui/src/features/cartridges/CartridgesPage.svelte:264-276` (see also `ui/src/features/cartridges/OperationModal.svelte:635-665`)
**Issue:** Phase 40.1-03 added `notifyPlaceContentChanged` producers to three
write-sites (`PlaceContents.svelte`'s edit-via-view-modal, `CartridgesPage.svelte`'s
edit form, `DevicesPage.svelte`'s edit/create form) and built a structural gate
(`check-place-tree-invalidation.mjs`, INV-7) asserting all three remain wired.
However, `CartridgesPage.svelte` has a second, pre-existing write-site that
also changes a cartridge's `place_id`: the lifecycle-operation modal
(`OperationModal.svelte`, reached via `handleMenuAction` for
`install`/`return_to_stock`/`to_refill`/`from_refill`/`write_off`), whose
payload explicitly carries `place_id: placeId` and is persisted server-side
via `CartridgeService`'s transition path (`crates/trackly-app/src/services/cartridge_service.rs:228`,
`UPDATE cartridges SET place_id=?1 ...`). Its success handler,
`handleOperationSuccess` (`CartridgesPage.svelte:262-277`), calls `loadAll()`
and reloads the selected cartridge's detail pane, but never calls
`notifyPlaceContentChanged`. Installing a cartridge into a printer, returning
one to stock, or sending one to/from refill are common, frequent actions that
change a cartridge's place — exactly the class of staleness WARNING-1 set out
to close — yet the tree counters for the affected places (old and new) will
not update until the user navigates away from and back to «Места». The new
INV-7 gate does not check this write-site at all, so a regression (or the
absence of this fix) here is invisible to the gate that this same plan
introduced specifically to prevent WARNING-1-class regressions.
**Fix:** Capture the pre-operation `place_id` (from `operationModalCartridge`,
already held before the modal opens) and the post-operation `place_id` (from
the cartridge returned by the transition call) in `handleOperationSuccess`,
and call `notifyPlaceContentChanged` the same way `handleFormSuccess` does:
```ts
function handleOperationSuccess(updated: CartridgeDto) {
  const oldPlaceId = operationModalCartridge?.place_id ?? null;
  const newPlaceId = updated.place_id ?? null;
  const changedPlaceIds = Array.from(
    new Set([oldPlaceId, newPlaceId].filter((id): id is number => id !== null)),
  );
  if (changedPlaceIds.length > 0) notifyPlaceContentChanged(changedPlaceIds);

  loadAll();
  // ...
}
```
and extend `check-place-tree-invalidation.mjs`'s INV-7 check to require a
second `notifyPlaceContentChanged(` occurrence (or a call inside
`handleOperationSuccess`'s block) in `CartridgesPage.svelte`, mirroring the
`tagBlock`-localized strategy already used for `PlaceContents.svelte`.

### WR-02: `build_movements_filter_summary` can hard-fail PDF export on a stale place filter, unlike its sibling lookup in the same function

**File:** `crates/trackly-app/src/tauri_cmds/reports.rs:462-495`
**Issue:** `build_movements_filter_summary` resolves three optional filter
values into a human-readable summary: `filter.type_id` via `device_type_name`
(returns `Result<Option<String>, AppError>`, explicitly documented as
"degrades gracefully rather than failing the whole export over a stale
filter value" — `reports.rs:436-440`), but `filter.from_place_id` /
`filter.to_place_id` via `ctx.places.full_path(caller, id).await?`
(`reports.rs:483,487`), which returns `AppError::NotFound` when the place row
no longer exists (`places_sqlite.rs::full_path_impl`, `QueryReturnedNoRows` →
`NotFound`). The `?` here propagates that error all the way out of
`build_reports_export_pdf`, failing the entire PDF/print export — not just
omitting the stale filter's name from the summary line. This is inconsistent
with the graceful-degradation design the same function applies one branch
later for `type_id`, and with the general RESTRICT-based design elsewhere in
this phase (BLOCKER-1) that treats "referenced but since-deleted" places as
an expected condition to handle, not an unhandled error. Concretely: a
manager opens the «Перемещения» report, sets an «Откуда» place filter, and
before clicking «Печать» another user (or an admin) deletes that place (legal
if it has no recorded movements of its own — the BLOCKER-1 fix only blocks
deletion of places that are themselves a movement's `from`/`to`, not places
that merely appear in someone's currently-open report filter). The print
button then throws a raw `NotFound` instead of rendering the report (with or
without that filter's name in the summary).
**Fix:** Resolve `from_place_id`/`to_place_id` the same optional way as
`device_type_name` — e.g. add a small helper that maps `AppError::NotFound`
to `Ok(None)` (or call `ctx.places.get`/`full_path` and match on the error
variant) so a deleted place degrades to omitting that one summary segment
instead of failing the export:
```rust
if let Some(from_id) = filter.from_place_id {
    match ctx.places.full_path(caller, from_id).await {
        Ok(path) => parts.push(format!("Откуда: {path}")),
        Err(AppError::NotFound { .. }) => {} // place deleted since filter was set — omit, don't fail
        Err(e) => return Err(e),
    }
}
```

### IN-01: Stale doc comment on `upgrade_replaces_v22_legacy_default_with_current_bundled_body`

**File:** `crates/trackly-app/src/pdf/html_templates.rs:490-495`
**Issue:** The doc comment claims: *"For `report.html` (2-element slice: v20,
v21) ... `bodies.get(2)` is `None`, so this test correctly `continue`s past
them and only exercises `act_handover.html`/`act_acceptance.html`"*. Plan
40.1-02 added a third element (`v28`) to `report.html`'s
`KNOWN_LEGACY_DEFAULTS` slice, so `bodies.get(2)` now returns
`Some(v28_body)` for `report.html` too, and the test genuinely exercises it

не завязан на имя папки... теперь реально упражняет и report.html"*). The
test logic itself is fine (index-generic, `assert_ne!` guards against a
false-positive pass) — only the comment's factual claim about which
filenames it covers is now wrong, which could mislead a future maintainer
tracing through why the test fails/passes for `report.html`.
**Fix:** Update the comment to drop the now-inaccurate "report.html ...
`bodies.get(2)` is `None`" claim, e.g. replace with a note that any filename
whose slice has fewer than 3 elements (currently only `_header.html`, empty
slice) is skipped.

### IN-02: Filter-summary joins parts with `"; "` without escaping a literal `;` in a place/type name

**File:** `crates/trackly-app/src/tauri_cmds/reports.rs:483-493`
**Issue:** `build_movements_filter_summary` joins resolved parts with
`"; "` (`parts.join("; ")`). Place names and device-type names have no
validation preventing a literal `;` character (`PlaceService::validate_name`
only checks non-empty/length, not character set). A place named e.g.
`"Склад; резерв"` would render as `"Откуда: Склад; резерв"`, visually
indistinguishable from two separate filter segments in the printed summary
line. This is cosmetic (no data corruption, no security impact — the value
is still HTML-escaped by minijinja's autoescape) but could confuse a reader
of the printed report.
**Fix:** Not required for this phase; if it recurs as a real complaint,
consider a less ambiguous separator (e.g. `" · "`) or escaping literal `;`
in resolved names before joining.
