- **Фикс:** `PlaceEntityViewModal`'s `onChanged` расширен до `(changedPlaceIds: number[]) => void`. Компонент уже держит старое место записи в `deviceDto`/`cartridgeDto` (загружены ДО правки, не меняются, пока открыт `editOpen`) и получает новое место из результата сохранения — `DeviceFormModal`'s `onSaved({ typeId, placeId })` (поле `placeId` уже было добавлено в Task 2 этого же плана для другого потребителя) и `CartridgeFormModal`'s `onSuccess(cart: CartridgeDto)` (полная сохранённая сущность). ## Полная инвалидация мест (40.1 exhaustive sweep, round-3 gap closure + registry gate)

После третьего раунда верификации, который нашёл целый непокрытый класс write-site
(«Акты приёма-передачи») поверх уже закрытых пяти, пользователь явно попросил ОДИН полный
проход вместо очередного точечного фикса: найти на сервере КАЖДОЕ место, меняющее
`devices.place_id`/`cartridges.place_id`, сопоставить с каждым клиентским потребителем, закрыть
все разом, и переделать гейт INV-7 так, чтобы он проверял ПОЛНОТУ списка потребителей, а не
присутствие отдельных вызовов.

### Метод

1. Сервер прочитан СНАЧАЛА, не UI: найдены все реальные `UPDATE devices/cartridges SET
   place_id` и симметричные repo-методы (`update_status_and_place_in_tx`,
   `update_full_in_tx`, `restore_from_snapshot_in_tx`), пройдены назад до сервисных методов и
   до Tauri-команд/HTTP-хендлеров, которые их публикуют.
2. Каждая серверная мутация сопоставлена с клиентскими вызывающими местами
   (`ui/src/features/**`), включая переиспользуемые модалки (несколько экранов рендерят один
   и тот же `<DeviceFormModal>`/`<PlaceEntityViewModal>`).
3. Каждый непокрытый клиентский обработчик закрыт вызовом `notifyPlaceContentChanged` со
   старым+новым местом (дедуп, null отброшены), по уже одобренному паттерну
   `CartridgesPage.svelte`/`RequestDetail.svelte`.
4. INV-7 (`check-place-tree-invalidation.mjs`) переделан из списка файлов в РЕЕСТР
   place-mutating поверхностей + скан всего дерева `ui/src/features` на каждое их
   использование — так что новый экран, добавленный ПОСЛЕ этого коммита, ловится
   автоматически.
5. Полная таблица инвентаря, что гейт теперь ловит/не ловит, и что оставлено осознанно — ниже.

### Что теперь делает INV-7 (registry-driven) — и чего НЕ делает

**Делает автоматически:**
- Реестр `MUTATING_COMPONENTS` (OperationModal/CartridgeFormModal/DeviceFormModal/
  ActFormModal/ReturnModal) + скан ВСЕГО `ui/src/features` находит КАЖДОЕ использование
  каждого компонента (`allTagBlocks`, не только первое) и резолвит подключённый колбэк
  (bare-идентификатор, Svelte shorthand `{onSaved}`, или inline-стрелка) в проверяемое тело.
- Реестр `FORWARDING_COMPONENTS` (`PlaceEntityViewModal`) — аналогично, но допускает форвард
  через собственный проп (`onChanged`) вместо прямого вызова, ОДИН хоп, зашитый явно.
- Реестр `DIRECT_CALL_MARKERS` (bulk move, `acts.delete`) — прямые вызовы вне любой модалки;
  обрамляющая именованная функция обязана звать `notifyPlaceContentChanged`.
- Новый файл, рендерящий уже зарегистрированный компонент без инвалидации, ловится
  АВТОМАТИЧЕСКИ — подтверждено синтетической фикстурой через `--src=` (см. ниже), не только
  утверждением.

**НЕ делает (явные blind spot'ы, задокументированы в самом гейте):**
1. Новый серверный мутирующий путь, заведённый НЕ через один из зарегистрированных
   компонентов/прямых вызовов, невидим гейту, пока человек не добавит его в реестр вручную —
   тот же класс пропуска, что и раньше, просто перенесённый с уровня «UI-файл» (меняется
   часто) на уровень «серверная place-мутирующая поверхность» (меняется редко — весь текущий
   список исчерпывающе перечислен в этом же проходе).
2. Резолюция колбэка — ТОЛЬКО в пределах одного файла: импортированный из другого модуля,
   bound-метод или member-expression обработчик не резолвится — это ВСЕГДА нарушение (громкий
   fail), никогда молчаливый skip.
3. Рекурсия `FORWARDING_COMPONENTS` — ровно один хоп (соответствует единственному реально
   существующему в этой кодовой базе хопу).
4. Гейт по-прежнему СТРУКТУРНЫЙ/текстовый — доказывает, что провод существует, не что
   переданные аргументы (старое/новое место) корректны. Это по-прежнему требует живой проверки.
