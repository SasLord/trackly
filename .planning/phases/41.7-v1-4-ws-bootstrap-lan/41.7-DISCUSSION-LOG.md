## WS-событие: форма и видимость (INT-01)

### Форма события

| Вариант | Описание | Выбран |
|---------|----------|--------|
| Один агрегат с id по видам | `EntitiesChanged { place_ids, device_ids, group_ids }` — одна рассылка на мутацию; id сущностей лежат готовыми под Фазы 43–45 | ✓ |
| Один агрегат, только `place_ids` | Минимум для сегодняшнего критерия; Фаза 43+ расширяла бы контракт заново по тем же точкам мутации | |
| Несколько узких вариантов | `PlaceChanged` / `DeviceMoved` / `GroupChanged` / `MovementAdded`; перенос АРМ из N устройств даёт N событий — риск `Lagged` при ёмкости 128 | |

**Выбор:** агрегат с id по видам (D-01).
**Примечание:** пункт критерия 1 про ёмкость канала закрывается формой события, а не увеличением буфера — 128 остаётся.

### Видимость (`is_visible_to`)

| Вариант | Описание | Выбран |
|---------|----------|--------|
| Admin \| Manager, шов записать | Тот же гард, что у `NumberSpaceChanged`; расширение под Ф.41.6 и Ф.41.5/MSG-03 фиксируется как шов | ✓ |
| Admin \| Manager + сразу фильтр по участникам | Поле-задел `visible_to_user_ids`; на сущностном событии осталось бы мёртвым — MSG-03 это другой вариант `WsEvent` | |
| Все аутентифицированные | Готово к Ф.41.6 без правки, но сотруднику текут id мест и устройств — шаг назад от BOLA-гарда T-11-03-I | |

**Выбор:** Admin \| Manager (D-02).

### Нагрузка `place_ids`

| Вариант | Описание | Выбран |
|---------|----------|--------|
| `changed_place_ids` — единый владелец | Событие несёт тот же список, что мутация уже возвращает в ответе; у мутаций `place_service` поле добавляется с тем же смыслом | ✓ |
| Только id мутируемой сущности | Раскрытие делает клиент; логика «что затронуто» раздваивается между сервером и клиентом | |
| Сервер раскрывает всё поддерево | Клиент глуп, но нагрузка события без потолка на большом поддереве | |

**Выбор:** `changed_place_ids` (D-03).
**Примечание:** находка обсуждения — мутации актов и групп уже вычисляют это поле и UI передаёт его дословно.

### Точка рассылки

| Вариант | Описание | Выбран |
|---------|----------|--------|
| В сервисах, после коммита | Вне writer-замыкания, по образцу `number_template_service::broadcast()`; один путь на оба транспорта | ✓ |
| В обработчиках `http/*` и `tauri_cmds/*` | Не надо трогать конструкторы сервисов, но рассылка пишется дважды на мутацию — тот же расход, что скрыл INT-04 | |
| Внутри writer-замыкания | Забыть невозможно, но событие уходит до коммита: второй клиент читает старое, на откате событие ложное | |

**Выбор:** в сервисах, после коммита (D-04).

## Источник инвалидации и гейт (INT-01)

### Судьба ~20 локальных вызовов `notifyPlaceContentChanged`

| Вариант | Описание | Выбран |
|---------|----------|--------|
| Остаются, WS — слой сверху | Локальный вызов работает при разрыве сокета (события разрыва не воспроизводятся); INV-7 сохраняет предмет; изменение аддитивное | ✓ |
| WS становится единственным источником | Один путь вместо двух, но при разрыве свой клиент не обновляется после своей операции, а INV-7 остаётся без предмета | |
| Остаются + схлопывание двойного вызова | Окно схлопывания в сторе; новый код и новые гонки ради одного дешёвого запроса | |

**Выбор:** WS — слой сверху (D-05).
**Примечание:** проверено по `ui/src/lib/api/ws.ts` — backoff до 30 с, replay отсутствует.

### Форма гейта

| Вариант | Описание | Выбран |
|---------|----------|--------|
| Rust-тест в `trackly-app/tests` | Рядом с предметом и с прецедентами; едет в `cargo test` вместе с `http_route_parity`, `groups_move` | ✓ |
| `.mjs`-скрипт рядом с `check-place-tree-invalidation` | Есть прецедент из 11 скриптов, но грепать Rust из JS — синтаксис извне: переименование или перенос мутации гейт не заметит | |
| Типовой гейт без реестра | Рассылка как обязательный шаг типа-обёртки; сильнее всего, но переделка подписей всех мутаций в фазе-разблокировщике | |

**Выбор:** Rust-тест (D-06).

### Состав гейта

| Вариант | Описание | Выбран |
|---------|----------|--------|
| Инвентарь от исходников + поведенческие кейсы | Слой 1 ловит дрейф (мутация без вердикта роняет), слой 2 проверяет само событие — наличие вызова в тексте не путается с работоспособностью | ✓ |
| Только инвентарь от исходников | Дрейф ловит, но рассылку с пустым списком или до коммита — нет | |
| Только поведенческие кейсы, как сейчас | Однородно с двумя существующими гейтами, но критерий 2 не выполняется: мутация без кейса гейт не роняет | |

**Выбор:** двухслойный (D-07).
**Примечание:** в `number_space_broadcast_gate.rs` дрейф реестра прямо описан в WR-06 как известный класс ошибки — именно он и закрывается.

### Освобождения и доказательство живости гейта

| Вариант | Описание | Выбран |
|---------|----------|--------|
| Реестр в гейте + selftest на фикстурах | Освобождение — строка с причиной, видимая в диффе; selftest по образцу `--selftest` в `check-act-number-no-regex-split.mjs` + мутационная проверка на реальном исходнике | ✓ |
| Маркер рядом с кодом | Причина не устареет в далёком файле, но заглушить гейт — одна строка в том же коммите, что добавляет мутацию | |
| Освобождений нет | Простое правило, но шумовые рассылки на мутациях, не трогающих места, и смысл вердикта пропадает | |

**Выбор:** реестр + selftest (D-08).

## Поиск по номеру возврата (INT-02)

### Источник выражения номера в SQL

| Вариант | Описание | Выбран |
|---------|----------|--------|
| SQL-функция, зовущая формулу | `format_act_number` опускается в `trackly-core`, регистрируется через `create_scalar_function` в обоих `apply_*_pragmas`; буквально один владелец, фикстура паритета не нужна | ✓ |
| SQL-фрагмент от Rust-функции + golden-фикстура | Крейты не трогаются, но формула физически существует дважды — класс, который память проекта помечает как требующий гейта-фикстуры | |
| Хранимая колонка `number_display` | Можно индексировать, но нужен бэкфилл и появляется третье состояние, способное разойтись с `number`/`sub_number` (против D-02 фазы 40.5) | |

**Выбор:** SQL-функция (D-09).
**Примечание:** `apply_writer_pragmas` / `apply_reader_pragmas` — единственные хуки открытия соединения (прод + ~30 тестовых фикстур), поэтому регистрация стоит две строки. Полный скан не регресс: `LIKE '%x%'` и сейчас сканирует.

### Семантика «запрос 42 различает родителя и возвраты»

| Вариант | Описание | Выбран |
|---------|----------|--------|
| Вся семья, каждый со своим номером | «42в1» → ровно один; «42» → родитель и возвраты, но каждый показан своим номером, а не тремя одинаковыми «42» | ✓ |
| То же + точное совпадение первым | Удобнее при длинных семьях, но трогает `ORDER BY` — лишняя поверхность для регресса | |
| «42» — только родитель | Самое буквальное чтение, но отнимает сегодняшнее поведение «найти семью по числу» | |

**Выбор:** вся семья с различимыми номерами (D-10).

### Покрытие тестами

| Вариант | Описание | Выбран |
|---------|----------|--------|
| Матрица с расходящейся фикстурой | Семья с двумя возвратами + посторонний акт; «42в1», «42в2», «42», ФИО; фикстура обязана быть красной ДО фикса | ✓ |
| Один кейс на «42в1» | Минимум по букве критерия; не ловит путаницу суффиксов внутри семьи и регресс поиска по ФИО в том же CTE | |
| Матрица + легаси-БД с «42в» | Полнее, но D-02 фазы 40.5 уже решил, что такие БД не поддерживаются — получился бы тест на неподдерживаемое состояние | |

**Выбор:** матрица (D-11).

## Bootstrap по LAN + 404 для /api/ (INT-03, F17)

### Форма пути для первого админа

| Вариант | Описание | Выбран |
|---------|----------|--------|
| Отдельный маршрут, проверка в транзакции | Публичный `POST /api/v1/auth_bootstrap`; «нуль пользователей» проверяется внутри той же транзакции (гонка двух браузеров закрыта), роль Admin навязывается сервером; `users_create` остаётся защищённым | ✓ |
| Исключение внутри `users_create` | Меньше кода и UI не меняется, но защита всего CRUD пользователей начинает зависеть от одного флага | |
| Отдельный маршрут, проверка до транзакции | Проще, но остаётся окно: два браузера на чистой установке могут завести двух админов с разными паролями | |

**Выбор:** отдельный маршрут с проверкой в транзакции (D-12).

### Дополнительная защита маршрута

| Вариант | Описание | Выбран |
|---------|----------|--------|
| Governor + запись в `audit_log` | Тот же rate-limit, что у `auth_login` (1/с, burst 5) по готовому образцу; след в журнале с пометкой «без автора» | ✓ |
| Только гард `needs_bootstrap` | Минимум кода: маршрут закрывается навсегда после первого пользователя | |
| Governor + audit_log + привязка к LAN | Новое понятие «доверенная сеть» и риск закрыть установку самому админу — ради угрозы, живущей секунды | |

**Выбор:** governor + audit_log (D-13).

### F17 — 404 для неизвестных `/api/`-путей

| Вариант | Описание | Выбран |
|---------|----------|--------|
| Префикс `/api/` → 404 JSON + тест | `spa_fallback` проверяет префикс первым делом; кейс в `tests/http_route_parity.rs`; нулевой риск для hash-роутера SPA | ✓ |
| То же + 404 для путей с расширением ассета | Полезно для отладки, но шире F17 и требует поддерживаемого списка расширений | |
| Перестроить на `nest("/api/v1", …)` | Архитектурно чисто, но переписывает пути во всех ~25 модулях роутера в фазе-разблокировщике | |

**Выбор:** префикс + тест (D-14).

### Живая проверка

| Вариант | Описание | Выбран |
|---------|----------|--------|
| Чеклист в конце, два браузера на macOS | Пункты собираются в один чеклист и отдаются пользователю, исполнитель не авто-одобряет; отдельный пустой каталог БД для INT-03; напоминание про `pnpm --dir ui build` | ✓ |
| Чеклист только для INT-03 | Для INT-01 довериться тестам рассылки — но клиентский мост остался бы непроверенным | |
| Живая проверка на Windows | Ближе к целевой среде, но для дефектов, не зависящих от ОС, лишний цикл сборки и передачи | |

**Выбор:** чеклист в конце, два браузера на macOS (D-15).
