## Summary

Фаза закрывается без новых внешних пакетов. Три неочевидные вещи, которые планировщик иначе обнаружил бы только на исполнении:

1. **`create_scalar_function` в `rusqlite 0.38` требует cargo-фичи `functions`, которая в проекте НЕ включена** (`Cargo.toml:32`: `features = ["bundled","serde_json","backup"]`; `cargo tree -e features -i rusqlite` показывает лишь `backup, bundled, cache, default, hashlink, modern_sqlite, serde_json`). Без неё `rusqlite::functions` не компилируется. Правка одна — в корневом `Cargo.toml` (`trackly-infra` и `trackly-app` берут `rusqlite = { workspace = true }`). Фича `functions = []` (`rusqlite-0.38.0/Cargo.toml:106`) новых зависимостей не тянет.
2. **Инвентарь мутаций шире, чем в CONTEXT.md.** Кроме восьми методов `place_service` и мутаций `group_service`/`act_service` место/состав меняют `device_service` (create*, update, delete_soft, import_csv_commit, bulk_create*) и `cartridge_service` (create, update, delete, transition). Критерий 1 называет три сервиса; «устройства» названы в заголовке INT-01 и в D-01. См. вопрос Q1.
3. **Мост `notifyPlaceContentChanged` покрывает меньше, чем формулирует критерий 1.** Стор читают ровно два потребителя: `PlaceTree.svelte:376` (только вытеснение счётчиков `statsCache`) и `GroupTree.svelte:385` (перезагрузка дерева групп, но `notify` на пустом `placeIds` ничего не делает — `placeContentEvents.svelte.ts:36`). Перезагрузка `places_list_all` (путь/имя места), `PlaceContents` (состав) стором не запускаются. Плюс `connectWs()` сегодня вызывается только из страниц запросов/принтеров/настроек и `EmployeeLayout` — на экранах «Места»/«Группы» сокета у админа нет. См. Q2, Q3.

**Primary recommendation:** внедрять в порядке «контракт события → инвентарь/гейт (красный) → рассылка в сервисах (гейт зеленеет) → клиентский мост»; SQL-функцию, bootstrap и F17 вести отдельными независимыми волнами. Layer (2) гейта строить на настоящем `AppCtx::build` (а не на ручной обвязке `with_ws_tx`), иначе забытый `.with_ws_tx` в `context.rs` останется невидимым.

## Инвентарь серверных мутаций

**Метод снятия.** Сплошной обход `services/*.rs` от исходников: для каждого `fn` (pub и приватных; блок `#[cfg(test)]` отброшен) найдено тело по балансу скобок и проверено вхождение `writer ... .execute(`. Скрипт одноразовый (в `scratchpad`, в репозиторий не кладётся). Результат подтверждён чтением тел методов. Поправка к CONTEXT.md: `act_number_display.rs` лежит в `services/`, а не в `dto/` (`crates/trackly-app/src/services/act_number_display.rs`).

**Главный методический вывод для гейта слоя (1).** Сканирование «`pub fn` с `writer.execute` в теле» **занижает** инвентарь: приватные помощники владеют записью, а публичные методы лишь зовут их — `place_service::set_archived` (`:401`, зовётся из `archive :381` и `unarchive :388`) и `device_service::insert_new_and_get` (`:310`, зовётся из `create`/`create_single_*`/`bulk_create*`/`import_csv_commit`, у которых `writer` в теле нет). Поэтому реестр обязан быть устроен так: **вердикт нужен на КАЖДЫЙ `pub (async) fn` файла из области гейта** (классы: `Broadcasts` / `Exempt(причина)` / `ReadOnly`), а `ReadOnly` проверяется отрицательно — тело не содержит `writer`; плюс каждый приватный `fn`, прямо владеющий `writer.execute`, тоже получает строку. Тогда новый публичный метод, который зовёт старый помощник, всё равно «без вердикта» и роняет гейт.

Легенда колонки «`changed_place_ids` в ответе»: ДА = поле уже есть в возвращаемом типе; НЕТ = надо добавить/вывести (D-03).

## Ловушки

Подтверждено/опровергнуто по коду.

1. **`#[serde(rename_all = "camelCase")]` per-variant — ПОДТВЕРЖДЕНО обязательным.** Tag-level `snake_case` не каскадирует на поля (`dto/printer.rs:233-249`); у каждого существующего варианта свой атрибут (`:254,:266,:275,:308`). Забыть — `placeIds` приедет как `place_ids`, клиент прочитает `undefined`. Страховка — юнит-тест на JSON-ключи.
2. **`#[specta(type = Vec<i32>)]` на `place_ids` — НЕ обязателен для сборки** (`WsEvent` не экспортируется в `bindings.ts`), но обязателен по прецеденту; `export_bindings` без него не упадёт. Падение `BigIntForbidden` реально только для DTO в сигнатурах команд — здесь это касается нового поля `changed_place_ids` в `PlaceDto`/возвратах `place_service` (если добавлять), там атрибут обязателен.
3. **Десктопный мост (`main.rs:240-330`) — делать НИЧЕГО не надо:** вариант доедет сам без `is_visible_to`; оператор десктопа admin-уровня; условие пересмотра (не-админ на десктопе / вариант с данными не для оператора) не наступает: нагрузка — числа id.
4. **`rusqlite` без фичи `functions` — НОВАЯ ловушка** (в запросе не упоминалась): `create_scalar_function` не соберётся. Правка в одном месте — `Cargo.toml:32`.
5. **Тестовые фикстуры без `apply_*_pragmas`** — перечислены в «Площадки подключения, п. 5»: все они либо только мигрируют, либо не исполняют `act_text_hits`; поиск актов в тестах всегда идёт через `test_writer_and_readers()`/`AppCtx::build`. Опровергнуто как риск при условии, что регистрация живёт ВНУТРИ `apply_writer_pragmas`/`apply_reader_pragmas`.
6. **LIKE по Cyrillic: SQLite сворачивает регистр только для ASCII** (комментарий `place_service.rs` у `search`: «SQLite's `LIKE` case-folds ASCII only, silently failing on Cyrillic»). Следствие: запрос «42В1» (заглавная кириллическая «В») НЕ найдёт «42в1». Пользователь, набирающий заглавную «В», получит пусто. Это не регресс (то же верно для ФИО в том же CTE), D-10 фиксирует LIKE — но кейс стоит знать (Q6).
7. **`notifyPlaceContentChanged([])` — no-op** (`placeContentEvents.svelte.ts:36`): мутации с пустым `place_ids` (переименование группы, `remove_devices`, `set_values`) не разбудят ни `PlaceTree`, ни `GroupTree` через мост (Q2).
8. **`PlaceDto`/`GroupDto` сериализуются в `audit_log`** (`place_service.rs:144 to_after_json`, `group_service.rs:171 to_json`): добавленное в них поле `changed_place_ids` загрязнит `before_json/after_json`. Класть id в отдельный тип ответа либо не сериализовать в аудит.

## Открытые вопросы к планировщику

1. **Q1 — граница области гейта (самый дорогой вопрос).** CONTEXT.md/критерий 1 называют `place_service`, `group_service`, `act_service`. Фактически место/состав меняют ещё `device_service` (create*, update, delete_soft, import_csv_commit, bulk_create*) и `cartridge_service` (create, update, delete, transition) — они влияют на те же счётчики `device_count + cartridge_count` (`PlaceTree.svelte:345`), и клиентский INV-7 уже считает эти экраны местозаписывающими. Заголовок INT-01 и D-01 говорят «устройства». Что известно: инвентарь выше. Что неясно: хочет ли пользователь рассылку и из этих сервисов в Фазе 41.7 (объём L → L+). Рекомендация: включить `device_service` и `cartridge_service` в область гейта; для каждого метода либо вердикт «рассылает», либо строка Exempt «вне критерия 1; INT-01 для устройств/картриджей отложен» — ТАК ИЛИ ИНАЧЕ строка реестра обязана существовать (требование D-07/D-08: молчание запрещено). Выбор «рассылает» vs «освобождён» вынести пользователю явным вопросом до планирования.
2. **Q2 — что мост реально обновляет.** Критерий 1 ждёт у второго клиента «счётчики дерева, путь места, состав и место группы». Мост по D-05/CONTEXT переводит событие ТОЛЬКО в `notifyPlaceContentChanged(place_ids)`; стор читают `PlaceTree` (вытесняет `statsCache`, `:376-391`) и `GroupTree` (`loadAll`, `:385`). НЕ обновляются: имя/путь места и структура дерева (`places_list_all` грузится по `refreshToken`/собственным мутациям, `PlaceTree.svelte:262,304`), `PlaceContents` (состав места, нет подписки), и всё, у чего `place_ids` пуст (переименование группы, `remove_devices`, `set_values`, `create_group` без места — `notify` на `[]` ничего не делает; `device_ids/group_ids` мост игнорирует «осознанно»). Варианты: (а) мост также вызывает перезагрузку (`refreshToken`-подобный сигнал) для `PlaceTree`/`PlaceContents`/`GroupTree` — минимальная доработка потребителей; (б) сузить критерий 1 до «счётчики + дерево групп при смене места». Рекомендация: (а), иначе живая проверка по пункту «путь места» гарантированно провалится; решение влияет на объём клиентской части и на чеклист D-15.
3. **Q3 — где открывается сокет.** `connectWs()` нет ни в `Layout.svelte`, ни в `PlacesPage`/`GroupsPage`. Нужна точка подключения моста: рекомендация — `Layout.svelte` (оболочка Admin/Manager; refcount-singleton, `ws.ts:115`) в `onMount` по образцу `EmployeeLayout.svelte:66-92` (флаг `disposed`, `release` идемпотентен). 4. **Q4 — `device_ids` в событии.** D-01 кладёт их «готовыми для Фаз 43–45». Где id под рукой: `add_devices` (`added`), `remove_devices` (внутри цикла), акты (`items`), `device_service.*`. ### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Захват свежей установки (кто первый открыл LAN-страницу) | Elevation of Privilege | окно живёт секунды до первой регистрации; след в `audit_log`; привязка к IP отвергнута (D-13) |
| Два параллельных bootstrap → два админа | Tampering | проверка в той же writer-транзакции; тест гонки |
| Brute-force/флуд публичного маршрута | DoS | governor per-peer-IP 1/с burst 5; предпроверка до argon2 |
| Утечка id мест/устройств сотруднику по WS | Information Disclosure | `is_visible_to` Admin\|Manager (D-02); тест Employee → false |
| Mass assignment роли | Elevation of Privilege | роль игнорируется, навязывается `admin` на сервере |
| SQL-инъекция через поиск | Tampering | параметр `?1`; `%`/`_` вычищаются (`act_service.rs:2730-2735`); функция чисто вычислительная |
