## Tests

### 1. Гашение залипающего тоста «Соединение с сервером потеряно» при возврате сервера
expected: сервер остановлен → тост появляется ОДИН раз и висит; сервер запущен снова (с
ДОВЕРЕННЫМ сертификатом) → сокет переподключается, тост исчезает сам, данные догоняются
why_human: нужен LAN-браузер с доверенным сертификатом. На macOS-стенде самоподписанный
`wss://` отклонялся (`The certificate for this server is invalid`), `onopen` не наступал, и
висящий тост был ВЕРНЫМ поведением — связи действительно не было. Корень: при пустом
`[server].cert_path` сертификат генерируется заново на каждом старте, поэтому исключение
браузера перестаёт совпадать (отдельный todo `2026-10-08-persist-self-signed-tls-cert.md`).
result: pass — проверено пользователем на Windows (сборка v1.4.0-phase41.7, 2026-10-09)

рассинхрона «закоммичено, но клиент видит ошибку» нет, повтор после перезапуска не даёт

why_human: автотест `tests/server_drain_on_stop.rs` использует спящую заглушку на голом

Остаточные риски, которые эта приёмка НЕ отменяет (они о редких сценариях, а не о
проверенном поведении):
- **Хвост WR-02** — остановка сервера при очереди записи, занятой почти весь свой
  `send_timeout` 5 с, и методы с несколькими `writer.execute`. `DRAIN_GRACE = 3 с`

- **Сертификат генерируется заново на каждом старте** при пустом `[server].cert_path`
  (механизм записи `server.crt`/`server.key` есть, но мёртв — файлы не читаются).
  Пункт 1 прошёл, значит сертификат на стенде был постоянным; по умолчанию это не так,
  и у пользователей каждый перезапуск сервера будет рвать WS до повторного принятия
  сертификата. См. `.planning/todos/pending/2026-10-08-persist-self-signed-tls-cert.md`.
