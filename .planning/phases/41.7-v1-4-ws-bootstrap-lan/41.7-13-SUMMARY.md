### Resolution (debug session `ws-disconnect-toast-no-show`, status `resolved`)

Closed by `/gsd-debug`, not by this plan. Commits `c42090cc`, `b4c787b9`, `e146d395`, `58cab3ee`.

- **Root cause (runtime-proven):** stopping server mode never closed ESTABLISHED WebSockets, so the
  browser's `ws.onclose` never fired and the toast was never requested. The cancel token broke only
  the accept loop; each accepted connection lived in a detached `tokio::spawn` that never received
  the token, and `handle_ws_socket` could not finish on its own because both `select!` arms were
  permanently pending (`socket.recv()` — the transport is server-push-only; `rx.recv()` — the
  `broadcast::Sender` lives in `AppCtx.ws_broadcast` and outlives the server). A first fix attempt
  failed and produced the decisive insight: dropping the hyper connection future does NOT close an
  upgraded WebSocket, because `hyper::upgrade::on` hands the IO to the task axum spawns in
  `on_upgrade`. The token must reach INSIDE the socket loop.
- **Second, independent defect:** the `warning` toast's 5000 ms TTL made a PERSISTING condition
  structurally unobservable — both repro branches are triggered from another window, so the toast
  had already expired by the time the user switched to the LAN browser. The indicator is now sticky,
  deduplicated by text, and cleared on a successful `onopen`.
- **Both invariants locked:** the `reconnecting` episode flag was deliberately KEPT, so Bug A's
  once-per-second spam cannot return. New lint gate `ui/scripts/check-ws-disconnect-toast.mjs`
  (wired into `pnpm lint`) guards both directions and catches 9 of 9 mutants — M6 catches removal of
  the episode flag (Bug A returning), M7 catches the toast call dying (GAP-1 returning).

### NOT a regression of phase 41.7

The root cause lives entirely in `crates/trackly-app/src/server/mod.rs`,
`crates/trackly-app/src/http/ws.rs` and the toast TTL — all older than this phase. Phase 41.7 only
added the socket to the Admin/Manager shell (`Layout.svelte:36`), which made a pre-existing defect
visible there. Confirmed by the user: the toast was absent on the EMPLOYEE screen too, and that
shell has held the socket since an earlier phase.

### Live re-verification — recorded honestly

- **PASSED (user, real LAN browser):** the disconnect toast now appears.
- **DEFERRED, NOT ticked:** the toast CLEARING on server restart. The user's console showed
  `The certificate for this server is invalid`, which proves the socket genuinely never reconnected,
  so `onopen` correctly never fired and the lingering toast is right behaviour, not a residual bug.
  Unverifiable on the macOS dev box; deferred by the user's own decision to a Windows LAN check after
  the next release build.
- **DEFERRED:** branch 2 (Cmd+Q) was not exercised separately. The TTL explanation is leading but
  unproven for that branch.
- **Adjacent issue found, filed separately, NOT fixed here:** with an empty `[server].cert_path` a
  new self-signed certificate is generated on every server start, so every restart invalidates the
  exception each LAN browser accepted. `main.rs:202-207` already writes `server.crt`/`server.key`
  "for reuse" but they are never read back (the read branch requires a non-empty `cert_path`), so
  that persistence is dead code. See `.planning/todos/pending/2026-10-08-persist-self-signed-tls-cert.md`.

### Orchestrator findings (investigation notes only, NOT fixes, NOT verified by the executor)

Passed on by the orchestrator to save the debug step time:

1. `ToastHost` is mounted globally in `ui/src/App.svelte:102`, outside the `{#if}` chain, so it renders
   on admin screens. Not the cause.
2. The lazy `import('$lib/stores/toast.svelte')` in `showReconnectingToast` (`ui/src/lib/api/ws.ts`
   around line 50) lands in the SAME built chunk as the ws close handler (the chunk holding the toast
   string and `api/v1/ws`), so a failed chunk fetch while the server is down is not the cause.
3. The stated reason for that lazy import ("avoid circular deps") is false and the comment is stale:
   `ui/src/lib/stores/toast.svelte.ts` has no imports, so no cycle is possible.
4. Leading remaining suspects, still unexamined:
   - the `reconnecting` episode flag in `ws.ts` (set true on the first close, reset only on a
     successful `onopen`; a guard added by the earlier `ui-ws-toast-reports-flicker` debug session,
     Bug A);
   - whether stopping the server from the desktop settings actually closes the browser's existing
     WebSocket at all. If the axum listener shuts down without closing established sockets,
     `onclose` never fires and the toast path is never entered. This would also explain the Cmd+Q
     case only if the process exit does not reset the socket promptly, so the two cases may have
     different causes and should be checked separately.

Executor's own observations from preparation that may be relevant to a reproduction (facts read from
source, not tested): the server is part of the desktop process (one binary), a self-signed cert is
regenerated on every start unless `cert_path` is set (the test environments used a fixed cert for this
reason), and `ws.ts` shows the toast only inside the `onclose` reconnect branch (`ws.ts:52`).
