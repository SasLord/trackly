# Phase 41.7: Code Review Report

## Summary

Reviewed the whole 41.7 change set against the five priority areas. Verdicts on the
priority areas first, because "no finding" is itself a result:

- **`POST /api/v1/auth_bootstrap` (priority 1) — no exploitable hole found.** The
  check/insert pair is genuinely atomic: `count_active_admins(&tx)` runs inside the same
  `conn.transaction()` as `insert_user_in_tx`, and `WriterHandle::execute`
  (`writer_worker.rs:89-105`) serialises closures onto one connection, so the deferred
  read→write upgrade cannot interleave with another writer. The client-supplied role is
  overwritten (`auth.rs`: `new.role = "admin"` **before** `validate_user_new`), the
  cheap `needs_bootstrap` pre-check runs before argon2, the route carries its own
  governor, and `users_create` is still session-gated (proved by
  `users_create_still_requires_session`). Two narrower problems remain — WR-01 (the
  bootstrap can *revive* an existing soft-deleted login) and WR-05 (the audit row cannot
  answer the question D-13 posed).
- **`spa_fallback` (priority 2) — no prefix bug.** `path == "api" || path.starts_with("api/")`
  after `trim_start_matches('/')` is a true segment-boundary match; `/apiary` is unaffected.
  No legitimate route regressed: every UI network call goes to a registered
  `/api/v1/*` path (`client.ts:29`, `adSso.ts:53`, `LoginPage.svelte:55`), and no embedded
  SPA asset lives under `api/`. One test-strength issue only (WR-08).
- **Broadcast placement (priority 3) — correct on all 31 sites.** Every
  `broadcast_entities(..)` call in the five services sits after the writer closure's
  `.await?`, outside it, unconditional with respect to the neighbouring
  `NumberSpaceChanged` guard, and unreachable on `Conflict` / stale-version / `NotFound`
  branches (those return through `?`). No lock or guard is held across an `.await`;
  `send_entities_changed` is synchronous. One ordering inconsistency (IN-01).
- **`trackly_act_number` (priority 4) — no defect found.** `acts.act_type` and
  `acts.number` are `NOT NULL` with a `CHECK` constraint (`V042:70,73`), so neither
  `ctx.get::<String>` can hit a NULL and the `ActType::from_str` error path is
  unreachable for real rows; the callback contains no `unwrap`/`panic!`/indexing and
  returns `Result`, so nothing crosses the FFI boundary as a panic. `SQLITE_DETERMINISTIC`
  is honest (output depends only on the four arguments). The search term stays a bound
  `?1` parameter — no injection surface was added. The function is used only in query
  text (never in an index/view/trigger/generated column), so a third-party `sqlite3` can
  still open the file.
- **GAP-1 WS shutdown (priority 5).** The fix is sound for WS itself — no task leak
  (the `CancellationToken::default()` fallback is a never-pending branch, the Close send
  is bounded by `CLOSE_SEND_TIMEOUT`, and the loop `break`s exactly once). But the same
  commit changed plain-HTTP connection lifetime, and that part can strand committed
  writes (WR-02).
- **Svelte 5 runes (priority 6).** No `$effect` cycle found: none of the four touched
  effects reads state it writes, `GroupsPage` correctly isolates its write in `untrack`
  with a non-reactive `lastReloadSeq`, and `PlaceContents`/`PlaceTree` write only
  state they never read back. Two UI defects found elsewhere in the bridge (WR-03, WR-04).
- **Privacy — clean.** Every new fixture uses «Иванов И.И.» / «Петров П.П.» /
  «Сидоров С.С.» / «Кузнецов К.К.»; no organisation name, requisites, address, phone,
  e-mail, serial or inventory number appears. `node scripts/check-privacy.mjs` → 0 violations.

No Critical findings. Nine Warnings follow, ordered by how much damage each can do.

## Warnings

### WR-01: unauthenticated bootstrap can REVIVE an existing soft-deleted account instead of creating a new one

**File:** `crates/trackly-app/src/services/auth.rs:1516-1545` (bootstrap writer closure) → `:2284-2320` (`insert_user_in_tx` revive branch)
**Issue:** `bootstrap_first_admin` delegates the row write to `insert_user_in_tx`, which was
extracted verbatim from `create_user` **including its revive branch**: when a row with the
same `login` exists and is soft-deleted, it is updated in place —
`full_name`, `password_hash`, `role`, `email`, `is_active = 1`, `deleted_at_utc = NULL` —
and its **id is reused**. In `create_user` that is deliberate and performed by an
authenticated admin. In `bootstrap_first_admin` the caller is anonymous.

Concrete scenario (no soft-deleted admin needed, so this is *not* the accepted T-41.7-09
risk): an install has no administrator but does have soft-deleted employee accounts — the
state `bootstrap_route_open_when_only_non_admins_exist` explicitly blesses. An anonymous
LAN client POSTs `auth_bootstrap` with `login` equal to a known deleted login. Result: that
historical identity is resurrected with `role = 'admin'` and the attacker's password, keeping
its primary key, so every row that references it by user id (`requests.requester_id`,
`audit_log.user_id`, assignment/history references) now attributes to the new account. The
audit row for this is `action = 'custom:bootstrap'`, `before_json = NULL` — indistinguishable
from a fresh create, so the takeover leaves no distinguishing trace. No test covers a
pre-existing soft-deleted login on the bootstrap path.

**Fix:** bootstrap must only ever INSERT. Give `insert_user_in_tx` an explicit mode and
reject the revive branch for the public path:
```rust
fn insert_user_in_tx(
    tx: &rusqlite::Transaction<'_>,
    caller_id: Option<i64>,
    action_override: Option<&str>,
    allow_revive: bool,          // create_user: true; bootstrap: false
    row: &NewUserRow<'_>,
) -> Result<i64, AppError> {
    // ...
    Some((_, Some(_))) if !allow_revive => {
        return Err(AppError::Conflict {
            reason: format!("Логин '{login}' уже занят"),
        })
    }
```
Add a test: seed a soft-deleted user, call the bootstrap route with that login, assert
`409`/`400` and that the old row stays `deleted_at_utc IS NOT NULL` with its original role.

### WR-02: stopping server mode now aborts in-flight HTTP requests whose database write has already been queued — the write commits, the client sees a network error

**File:** `crates/trackly-app/src/server/mod.rs:121-141` (new `tokio::select!` around `serve_connection_inner`)
**Issue:** Before this phase each accepted connection ran to completion. Now cancelling the
server token drops the connection future mid-request. That is required for WS, but it also
applies to ordinary API requests — and `WriterHandle::execute`
(`crates/trackly-infra/src/db/writer_worker.rs:94-104`) sends the job over an mpsc channel
and then awaits a oneshot; dropping the caller's future does **not** cancel the job. The
closure still runs on the writer thread and still `commit()`s; the dropped oneshot send is
swallowed by design (`let _ = reply_tx.send(...)`).

Concrete failure: a LAN user submits "создать акт"; the desktop admin presses «Остановить
сервер» (or Cmd+Q) in that window. The act, its `act_items`, the device place changes and
the audit rows are committed, but the browser gets a transport error and the
`EntitiesChanged`/`NumberSpaceChanged` broadcasts that live *after* the `.await?` never run
(the task was cancelled at that await). The user restarts and retries → a second act for
the same handover. The same hazard exists for multi-step service methods that issue more
than one `writer.execute` (e.g. act creation + PDF/number bookkeeping): cancellation
between two closures leaves the first committed and the second never queued.

**Fix:** keep the forced drop for upgraded connections, but give ordinary requests a short
grace period, e.g. race the connection against `cancelled()` *plus* a timeout rather than
cancelling instantly:
```rust
tokio::select! {
    _ = async {
        conn_shutdown.cancelled().await;
        tokio::time::sleep(DRAIN_GRACE).await;   // e.g. 2-3 s
    } => { /* give up on this connection */ }
    () = serve_connection_inner(..) => {}
}
```
WS is already closed independently by its own `ServerShutdown` branch, so the grace period
does not reintroduce GAP-1. If the instant drop is kept deliberately, record it as an
accepted risk with the duplicate-submission scenario spelled out.

### WR-03: the sticky disconnect toast can be silently evicted by the MAX_TOASTS cap — GAP-1 reproduces

**File:** `ui/src/lib/stores/toast.svelte.ts:52-55` (eviction) with `ui/src/lib/api/ws.ts:130-134` (`reconnecting` latch)
**Issue:** The eviction path drops the OLDEST toast regardless of `sticky`:
```ts
if (toastStore.items.length >= MAX_TOASTS) {
  toastStore.items = toastStore.items.slice(toastStore.items.length - MAX_TOASTS + 1);
}
```
When the server stops, the sticky «Соединение с сервером потеряно…» toast is pushed first
and every subsequent failing API call pushes an error toast (111 `pushToast('error', …)`
sites in `ui/src`). After nine further toasts the sticky one is evicted. Because
`reconnecting` stays `true` for the whole episode and is only reset on `onopen`,
`showReconnectingToast()` is never called again — the user is left with exactly the GAP-1
symptom this phase was reopened to fix, on a screen that is actively erroring. The new gate
does not cover this: `check-ws-disconnect-toast.mjs` E1-E4 never pushes more than a handful
of toasts.

**Fix:** exempt sticky toasts from eviction and add an E5 case to the gate.
```ts
if (toastStore.items.length >= MAX_TOASTS) {
  const keep = toastStore.items.filter((t) => t.sticky);
  const rest = toastStore.items.filter((t) => !t.sticky);
  toastStore.items = [...keep, ...rest.slice(rest.length - (MAX_TOASTS - 1 - keep.length))];
}
```

### WR-04: a pending reconnect timer survives `release()` and can resurrect a second live socket

**File:** `ui/src/lib/api/ws.ts:136-142` (`setTimeout(connectBrowser, delay)`) and `:183-196` (`activeCleanup`)
**Issue:** `activeCleanup` closes the socket only `if (ws)`. During a backoff window `ws` is
already `null` (nulled in `onclose`) while a `setTimeout(() => connectBrowser(), delay)` is
still pending, and nothing cancels that timer. Sequence, now reachable for Admin/Manager
because `Layout.svelte` holds the socket on every admin screen (D-18):

1. server stops → `onclose` → `ws = null`, timer armed for up to 30 s;
2. the admin logs out or the shell unmounts inside that window → `release()` → `refCount = 0`,
   `activeCleanup` is a no-op on the socket and is then set to `null`;
3. the timer fires → `connectBrowser()` opens socket **A** with no owner;
4. the admin logs back in → `connectWs()` (`refCount 0→1`) → `connectBrowser()` overwrites
   the module-level `ws` with socket **B**. Socket **A** is now unreachable but still has a
   live `onclose` that, with `refCount === 1`, will push another toast and arm another
   reconnect — i.e. N sockets fanning the same backend event out N times, which is exactly
   regression GAP-12-10 that the refcount singleton was built to prevent.

**Fix:** track and cancel the pending timer.
```ts
let reconnectTimer: ReturnType<typeof setTimeout> | null = null;
// in onclose:
reconnectTimer = setTimeout(() => { reconnectTimer = null; connectBrowser(); }, delay);
// in activeCleanup, before the `if (ws)` block:
if (reconnectTimer !== null) { clearTimeout(reconnectTimer); reconnectTimer = null; }
```

### WR-05: the bootstrap audit entry cannot answer the question D-13 asked it to answer

**File:** `crates/trackly-app/src/services/auth.rs:2322-2330` (`insert_user_in_tx` audit insert); handler `crates/trackly-app/src/http/auth.rs:358-366`
**Issue:** D-13 justifies the audit row as «чтобы остался след, если свежую установку занял
кто-то раньше владельца». The row that is actually written is
`('user', id, 'custom:bootstrap', NULL, NULL, NULL, <login>, now)` — the only
attacker-controlled datum it preserves is the login the attacker chose. The peer IP is
available at this point (`ConnectInfo` is injected for every request in
`server/mod.rs:176-178` and tower_governor already keys on it) but is never passed to the
service, so the one fact a victim would need — which LAN host claimed the install — is lost.
For the single unauthenticated privileged endpoint in the product this is the weakest part
of its forensic story.

**Fix:** thread the peer address into `bootstrap_first_admin` (an `Option<&str>`, `None` on
the Tauri path) and serialise it into `payload_json`:
```rust
payload_json: Some(serde_json::json!({ "login": login, "peer": peer }).to_string()),
```
Add an assertion to `bootstrap_route_open_when_needs_bootstrap` that the audit payload
carries the peer, so the field cannot rot.

### WR-06: the registry gate does not check that a broadcast happens AFTER the writer closure — only that it is not textually inside it

**File:** `crates/trackly-app/tests/entities_support/scan.rs:541-558`
**Issue:** The `Verdict::Broadcasts` arm asserts (a) a `broadcast_entities("<fn name>", ..)`
call exists in the body and (b) its `(` is not inside any `writer.execute( … )` paren range.
Nothing checks position relative to the writer call. A `broadcast_entities("create", …)`
placed at the TOP of `PlaceService::create`, before `self.writer.execute(..).await?`, passes
the gate while firing an invalidation for a mutation that may then fail validation or roll
back — the exact class of defect D-04 exists to prevent, and the one the module doc-comment
of `entities_broadcast.rs` states as the contract ("send ONLY after the writer closure's
`.await?`"). The behaviour layer (2) cannot catch it either: a scenario test that asserts
"one event was observed" still sees one event.

**Fix:** in the `Broadcasts` arm, require every call position to be greater than the end of
the LAST `writer.execute(..)` range in the body (functions with no writer range in the body
— the `archive`/`unarchive` wrappers — need an explicit allowance row or a delegation check):
```rust
if let Some(last_writer_end) = wr.iter().map(|(_, b)| *b).max() {
    if calls.iter().any(|(paren, _)| *paren < last_writer_end) {
        out.push(v(&f.name, Kind::BroadcastBeforeWriter, "...".into()));
    }
}
```
Add a selftest fixture with the broadcast moved above the writer call.

### WR-07: `Verdict::Exempt` rows receive no mechanical check at all

**File:** `crates/trackly-app/tests/entities_support/scan.rs:556` (`Verdict::Exempt(_) => {}`)
**Issue:** `ReadOnly` rows are verified (`ReadOnlyOwnsWriter`, `ReadOnlyCallsWriter`) and
`Broadcasts` rows are verified, but `Exempt` is a hole: an exempt function may own
`writer.execute`, may mutate places/devices/cartridges, and may even contain a
`broadcast_entities` call inside the writer closure — the scanner emits nothing. The only
constraint is that the reason text is ≥ 40 characters. Consequence for maintenance: moving a
row from `b(PLACE, "move_node")` to `ex(PLACE, "move_node", "<40 chars of prose>")` is a
one-line change in the very commit that breaks invalidation, which is the cost D-08 set out
to make high.

**Fix:** make `Exempt` carry its own obligation — at minimum, flag an exempt function that
owns `writer.execute` unless the row uses a distinct, louder constructor
(`ex_writes(file, func, reason)`), so "this function writes and is still exempt" is a
separate, visible verdict rather than the default silence. Add a selftest fixture for it.

### WR-08: the only guard against a `/api` prefix bug is skipped when `ui/dist` is not built

**File:** `crates/trackly-app/tests/http_route_parity.rs:641-660`
**Issue:** The `GET /apiary` assertion — the single test that would catch `starts_with("api")`
instead of a segment-boundary match — is nested inside `if ui_bundled`. It is there only
because the sibling `GET /` check needs the bundle, but `/apiary` does not: without the
bundle the fallback answers `404 text/plain`, which satisfies
`!(status == 404 && ct.contains("application/json"))` anyway. In any environment where
`ui/dist/index.html` is absent the test prints a notice and the segment-boundary invariant
goes unverified while the file still reports green.

**Fix:** move the `/apiary` probe out of the `if ui_bundled` block; keep only `GET /` inside it.

### WR-09: `PlaceTree`'s new store dependency is hidden from the INV-7 gate by a function indirection

**File:** `ui/src/features/places/PlaceTree.svelte:305` (`void reloadSeqNow();`) with `ui/src/lib/stores/placeContentEvents.svelte.ts:61-63`
**Issue:** `reloadSeqNow()` exists specifically so that the tree-loading effect can depend on
`placeContentEventsStore.reloadSeq` without the identifier `placeContentEventsStore`
appearing in a second `$effect` — which is what `check-place-tree-invalidation.mjs` counts.
The reactive dependency is real but invisible to the registry gate that owns this very file,
so a future refactor that drops the call (or renames the store field) breaks cross-client
invalidation of the place tree with INV-7 still green. The comment on the helper documents
the motive but does not restore the coverage.

**Fix:** teach `check-place-tree-invalidation.mjs` about the accessor: either count
`reloadSeqNow(` as a store reference when tallying the allowed effects, or add a dedicated
rule requiring exactly one `reloadSeqNow()` call inside the tree-loading effect of
`PlaceTree.svelte`.

## Info

### IN-01: `cartridge_service::transition` broadcasts after the read-back, unlike every other mutation

**File:** `crates/trackly-app/src/services/cartridge_service.rs:768-770`
**Issue:** `let dto = self.get(cartridge_id).await?;` runs before `broadcast_entities("transition", …)`.
Everywhere else (`act_service::create/update/do_return/update_return`,
`cartridge_service::create/update`) the broadcast precedes the read-back. If `get` fails on a
transient reader error, the transition is already committed but no other client is ever told.
**Fix:** move `self.broadcast_entities("transition", place_ids, device_ids, Vec::new());` above
the `self.get(..)` call, matching the sibling methods.

### IN-02: `auth_bootstrap` tests intentionally leak a temp directory per test

**File:** `crates/trackly-app/tests/auth_bootstrap.rs:36` (`let dir_path = dir.keep();`)
**Issue:** `TempDir::keep()` disarms cleanup, so each of the eight tests leaves a SQLite DB,
WAL/SHM files and a `logs/` directory in the system temp dir on every run.
**Fix:** hold the `TempDir` in the returned tuple (as `ws_close_on_server_stop.rs` does with
`_dir`) instead of leaking the path.

### IN-03: inconsistent "no place" handling between device and cartridge creation

**File:** `crates/trackly-app/src/services/device_service.rs:409-412` vs `crates/trackly-app/src/services/cartridge_service.rs:390-394`
**Issue:** Creating a device with no place sends `EntitiesChanged { placeIds: [], deviceIds: [id] }`,
which the bridge reads as "reload everything" (D-17) on every admin client; creating a
cartridge with no place sends nothing at all (all three lists empty). Both are defensible —
neither changes a tree counter — but the asymmetry will read as a bug to the next maintainer.
**Fix:** either drop `device_ids` for placeless device creation or add a one-line comment at
both sites stating why the two cases diverge.
