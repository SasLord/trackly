**Researched:** 2026-08-08
**Domain:** MiniJinja HTML-шаблоны печатных форм (partial-инклюды, safe-mode autoescape), CSS-типографика для печати (Paged.js), SQLite-миграции `org_settings`, механизм доставки апгрейдов шаблонов в установленные копии.

## Summary

Фаза 34 — не исследование нового стека, а точное применение уже отработанных в Фазах 16/17/20/33
паттернов к четвёртому файлу (`_header.html`) и новому полю `org_settings`. Всё необходимое
инфраструктурно уже в кодовой базе: файловый materialize/upgrade-on-startup механизм
(`html_templates.rs`), безопасный MiniJinja environment с автоэкранированием
(`minijinja_env.rs`), паттерн «Rust готовит безопасную строку → `| safe` в шаблоне»
(`org.logo_data_uri`), паттерн двух транспортных обёрток на команду (`tauri_cmds/` +
`http/`), и структурный regex-тест на согласованность трёх шаблонов
(`tests/html_page_parity.rs`, Phase 33 D-13).

Единственный source-of-truth для новой вёрстки — файл `target/debug/templates/act_handover.html`
(mtime 2026-08-08 17:55), который пользователь правил вручную и который погибнет при
`cargo clean` (в `.gitignore`). Этот файл прочитан и продиффен против канона; полный
привacy-очищенный инвентарь изменений — в разделе «Эталон вёрстки» ниже. **Самое срочное
действие плана — перенести эти изменения в `crates/trackly-app/templates/` до любого
`cargo clean`.**

Из нового по механике: (1) `minijinja::HtmlEscape` — уже транзитивно доступный (через
существующую зависимость `minijinja ^2.20`) публичный `Display`-хелпер для HTML-экранирования
вне рендера шаблона, что закрывает D-03 (экранирование → потом `<br>`) без добавления новой
внешней зависимости; (2) регистрация partial'а вторым именованным шаблоном в той же
`Environment` через `add_template_owned` — механически идентична уже существующей регистрации
одного шаблона в `render_with_timeout`, нужно только зарегистрировать оба перед `get_template`
основного имени; (3) серифная цепочка фолбэков для кириллицы должна закончиться на `Georgia`
(гарантированно есть и на Windows, и на macOS) и `serif`, а не на `sans-serif`, как в правке
пользователя.

**Primary recommendation:** перенести правку из `target/debug/templates/act_handover.html`
в канон дословно (геометрия, типографика, порядок реквизитов), заменить хардкод названия
организации на `org.full_name`/`org.name` (D-01…D-04), вынести шапку в `_header.html`
(D-12…D-14), зарегистрировать её вторым шаблоном без включения файлового загрузчика (D-13),
добавить срез `_legacy_defaults/v21/` (D-15) с warn-веткой (D-16), и только после проверки —
удалить `target/debug/templates/` (D-18).

## `overflow-wrap` / `hyphens` при жёстких 80mm (D-06)

Все три HTML-корня уже имеют `<html lang="ru">` (`act_handover.html:31`,
`act_acceptance.html:24`, `report.html:29`) — **предусловие для `hyphens: auto` уже
выполнено**, дополнительных изменений `lang`-атрибута не требуется.

Рекомендуемый набор объявлений на `.orgName` и `.requisites` (узлах внутри жёсткого
`width: 80mm` контейнера):

```css
.header .orgName,
.header .requisites {
  overflow-wrap: break-word;
  word-break: normal;
  hyphens: auto;
  -webkit-hyphens: auto; /* defensive — modern WKWebView (Safari 17+/macOS 13.5+) поддерживает unprefixed, но старые сборки WebView иногда только с префиксом */
}
```

- **`overflow-wrap: break-word`** (не `word-break: break-all`) — ломает слово посимвольно
  ТОЛЬКО когда естественный перенос по пробелам не вмещается в 80mm; `break-all` ломает
  агрессивнее (в т.ч. там, где это не нужно) и визуально хуже смотрится для кириллицы.
  `[ASSUMED — общее CSS-поведение, не library-specific, Context7 неприменим]`
- **`hyphens: auto`** — расставляет переносы по словарю переноса ОС/движка, а не произвольно
  посреди слова; для этого движку нужен `lang` на документе (уже есть) и словарь для этого
  языка. И Blink (Chromium/WebView2), и WebKit (WKWebView) поставляются со встроенным
  словарём русского языка — специальной установки словаря не требуется.
  `[ASSUMED — training knowledge о встроенных hyphenation-словарях Chromium/WebKit, не
  верифицировано в этой сессии через официальную документацию]`.
- **Paged.js**: полифиллит `@page`/пагинацию, не трогает text-layout CSS-свойства — `hyphens`/
  `overflow-wrap` работают как обычно под управлением браузерного движка ДО того, как Paged.js
  переразбивает контент на страницы; конфликтов не ожидается. `[ASSUMED]`.
- Для печати это же поведение действует одинаково — печатный вывод в этом проекте это тот же
  DOM, что и превью (Phase 33 D-04/D-06), значит `overflow-wrap`/`hyphens` применяются
  идентично на экране и на бумаге без отдельного `@media print` блока.

**Открытый вопрос для UAT**: насколько по-разному WebView2 (Chromium) и WKWebView (Safari)
расставляют переносы для одного и того же длинного русского слова — это не баг, а
допустимое лёгкое визуальное расхождение между транспортами (оба ниже уровня Success
Criterion #2, который требует идентичной ВЁРСТКИ/типографики, а не идентичного побайтового
переноса строк).

## HTML-escape → `<br>` порядок (D-03, security-значимо)

**Готовый инструмент уже в workspace, новая зависимость не нужна.** `minijinja` (уже
подключён, `^2.20`, `crates/trackly-app/Cargo.toml:53`) публично экспортирует
`minijinja::HtmlEscape` — tuple-struct-обёртку над `&str`, реализующую `Display` с той же
логикой экранирования, что использует внутренний движок автоэкранирования (`&`, `<`, `>`,
`"`, `'` → HTML-сущности). `[CITED: docs.rs/minijinja/latest/minijinja/struct.HtmlEscape.html]`

```rust
// Источник: minijinja::HtmlEscape (публичный API, docs.rs)
// D-03: сначала экранировать, ПОТОМ вставлять <br /> — обратный порядок = инъекция.
use minijinja::HtmlEscape;

fn full_name_to_html(raw: &str) -> String {
    let escaped = format!("{}", HtmlEscape(raw)); // шаг 1: экранирование
    escaped.replace('\n', "<br />")                // шаг 2: <br> ПОСЛЕ экранирования
}
```

**Почему порядок обязателен (threat model, для `/gsd-secure-phase`):**
- Угроза: поле «полное юридическое наименование» — это настройка организации, вводимая через
  authenticated Settings UI, но результат рендерится в HTML-документ, который в LAN-режиме
  показывается в браузере сотрудника (превью акта/отчёта) — тот же вектор, что уже
  задокументирован для `org.logo_data_uri` (T-16-05-подобный) и для основного autoescape
  (T-16-01).
- Если сначала вставить `<br>` в сырой (неэкранированный) текст, а потом пропустить весь
  результат через HTML-экранирование — сам вставленный `<br>` тоже превратится в
  `&lt;br /&gt;` (перестанет быть тегом, перенос строки не отрендерится — функциональный баг,
  не уязвимость).
- Если сначала НЕ экранировать вообще, вставить `<br>`, и напечатать в шаблоне через `| safe`
  без Rust-side экранирования спецсимволов организации-ввода — то любой пользователь с правом
  `ManageSettings`, вписавший в поле `<script>...</script>` или `<img onerror=...>`, получит
  этот HTML исполненным в браузере каждого сотрудника, открывшего LAN-превью документа
  (Stored XSS через настройку организации). Экранирование ДО вставки `<br>` (правильный
  порядок выше) нейтрализует это: любые `<`/`>`/`&` из пользовательского ввода становятся
  безопасными сущностями ДО того, как в текст добавляются настоящие `<br />` теги.
- STRIDE: Tampering / Elevation of Privilege (LAN browser preview context) — аналогично
  T-16-01 threat model, но новый vector (`org.full_name`) должен быть явно упомянут в списке
  митиг Фазы 34.

**C-04 doc-comment fix:** `minijinja_env.rs:51-52` содержит устаревшее утверждение
`"No | safe filter is used anywhere in the shipped templates"` — после D-03 это неверно
дважды (`org.logo_data_uri | safe` уже существовал; `org.full_name | safe` добавляется этой
фазой). Комментарий должен быть переписан, чтобы перечислять ОБА исключения и явно
фиксировать инвариант «`| safe` допустим только для значений, экранированных/собранных
исключительно на Rust-стороне из non-user-HTML-input», а не утверждать отсутствие `| safe`.

**Confidence:** HIGH (публичный API подтверждён через docs.rs, паттерн зеркалит уже
верифицированный прецедент `logo_data_uri` в этой же кодовой базе).

## Регистрация partial'а вторым шаблоном (D-13/D-14/C-03)

`render_with_timeout` (`minijinja_env.rs:68-107`) сейчас регистрирует РОВНО один шаблон на
рендер:
```rust
env.add_template_owned(name_owned.clone(), template_src_owned)?;
let tmpl = env.get_template(&name_owned)?;
tmpl.render(ctx)
```
`add_template_owned(name: String, source: String)` принимает владеющие `String`, поэтому
регистрация ВТОРОГО шаблона (partial'а) в этой же функции — вопрос вызова того же метода
ещё раз на том же `env` перед `get_template` для основного имени:

```rust
// Внутри render_with_timeout (или в новой сигнатуре, принимающей Vec<(name, src)>):
env.add_template_owned(header_name.clone(), header_src)?;   // partial первым
env.add_template_owned(name_owned.clone(), template_src_owned)?; // основной шаблон вторым
let tmpl = env.get_template(&name_owned)?;
tmpl.render(ctx)
```
Порядок регистрации (partial до или после основного) не важен для MiniJinja — `{% include %}`
резолвится в момент РЕНДЕРА, а не в момент регистрации основного шаблона, поэтому оба должны
быть в `env` до вызова `tmpl.render(ctx)`, но порядок вызовов `add_template_owned` между собой
не имеет значения.

**Изменение сигнатуры:** `render_with_timeout` сейчас принимает один `(name, template_src)`.
Для трёх call site'ов (act_service ×2, report_service ×1), каждому нужен ОДИН И ТОТ ЖЕ второй
шаблон (`_header.html`) — самый чистый вариант: расширить сигнатуру до приёма списка
`&[(&str, &str)]` пар (name, src) РЕГИСТРИРУЕМЫХ шаблонов + отдельного имени
рендерируемого шаблона, либо добавить параметр `extra_templates: &[(&str, &str)]`. Три
существующих `#[tokio::test]` в `minijinja_env.rs` вызывают `render_with_timeout` с текущей
4-аргументной сигнатурой — их нужно будет обновить под новую сигнатуру (или дать пустой
слайс по умолчанию), это ломающее изменение затрагивает и тесты, и все 3+1 (validate_preview)
call site'а.

**Никогда не регистрировать сырое чтение файла напрямую (C-03):** если пользователь удалит
`_header.html`, `{% include "_header.html" %}` должен по-прежнему резолвиться — на вшитый
дефолт. Значит источник для `add_template_owned(header_name, header_src)` — РЕЗУЛЬТАТ
`load_template(templates_dir, "_header.html", embedded_default)` (файл ИЛИ дефолт), НЕ прямой
`std::fs::read_to_string`. Это тот же вызов, что уже используется для основных трёх файлов —
паттерн просто повторяется для partial'а.

**Lifetime/ownership:** `add_template_owned` берёт `String` (не `&str`) — оба вызова внутри
`spawn_blocking`-замыкания получают уже `.to_owned()`-нные строки (как сейчас делает
`template_src_owned`), поэтому для partial'а source и name точно так же должны быть
`String`, переданные `move` в замыкание. Поскольку `env` — локальная `Environment<'static>`
внутри замыкания (не хранится между вызовами), никакого разделяемого состояния/гонки между
рендерами не возникает — та же гарантия, что уже задокументирована в doc-comment'е функции
(«environment is cloned per-render»).

**Confidence:** HIGH — весь механизм уже существует и виден в файле, единственное новое —
вызов того же публичного метода дважды.

В `upgrade_untouched_defaults_on_startup` (строки 134-162) сейчас есть ТРИ ветки:

- содержимое == текущий дефолт → `continue` (без лога — уже актуально, шумный лог не нужен)
- содержимое совпало с legacy-снимком → перезапись + `tracing::info!` (уже логируется)
- **иначе (файл не совпал НИ С ЧЕМ — пользовательская правка) → сейчас молча falls through
  комментарий `// else: user-customized ... — leave untouched, fail closed.`, БЕЗ лога.**

Это последняя, пропускаемая ветка (`// else:` в конце цикла тела `for`, после `if
legacy_bodies.iter().any(...)` блока) — именно сюда добавляется `tracing::warn!`:
```rust
} else {
    tracing::warn!(
        "Skipped auto-upgrade of {} — on-disk content matches neither current default \
         nor any known legacy default (user-customized); manual review needed if a \
         header/layout upgrade was expected.",
        path.display()
    );
}
```
Формулировка сообщения — на усмотрение исполнителя (Claude's Discretion), но должна называть
конкретный файл (`path.display()`) и явно говорить «апгрейд пропущен, потому что похоже на
ручную правку» — это единственный способ для администратора Trackly узнать постфактум, почему
шапка не обновилась на конкретной машине.

## Don't Hand-Roll

| Проблема | Не изобретать | Использовать вместо | Почему |
|---|---|---|---|
| HTML-экранирование строки вне рендера шаблона | Собственную функцию замены `&`/`<`/`>`/`"`/`'` | `minijinja::HtmlEscape` (уже в workspace через существующую зависимость) | Та же логика экранирования, что и внутренний autoescape движка — нулевой риск рассинхронизации поведения между «Rust escape» и «шаблонный escape», без новой внешней зависимости |
| Сравнение «файл на диске = дефолт или известный старый дефолт» для нового partial'а | Отдельный ad-hoc механизм детекции для `_header.html` | Тот же `DEFAULT_HTML_TEMPLATES`/`upgrade_untouched_defaults_on_startup`, просто добавить `_header.html` четвёртым элементом | Механизм уже общий по конструкции — специального кода под 4-й файл не требуется |
| Гарантия того, что три HTML-документа реально используют один и тот же блок шапки | Побайтовое сравнение целых файлов (сломается на первом же намеренном отличии тела акта в Фазе 35) | Regex-извлечение конкретно `<div class="header">...</div>` фрагмента + assert_eq (как `html_page_parity.rs` делает для `@page`) | Точечная, узкая проверка, не хрупкая к будущим изменениям остального документа |

**Key insight:** вся инфраструктура этой фазы уже написана в прошлых фазах (16, 17, 20, 33) —
задача не «спроектировать новый механизм», а «добавить четвёртый файл + новое поле в уже
существующие точки расширения», не создавая параллельных путей.

## Common Pitfalls

### Pitfall 1: `cargo clean` до переноса правки
**Что идёт не так:** эталонная вёрстка в `target/debug/templates/act_handover.html`
безвозвратно теряется.
**Почему это происходит:** каталог в `.gitignore`, стандартная гигиена репозитория
(`cargo clean`, переключение веток, CI checkout) удаляет `target/`.
**Как избежать:** первая задача плана — скопировать/законспектировать содержимое ДО любых
других git/build операций фазы; раздел «Эталон вёрстки» в этом документе — резервная копия на
случай, если файл уже утрачен к моменту исполнения.
**Признаки:** `ls target/debug/templates/` не находит файла или mtime не совпадает с
2026-08-08 17:55 — тогда полагаться ТОЛЬКО на инвентарь из этого RESEARCH.md.

### Pitfall 2: `UndefinedBehavior::Strict` роняет один из четырёх рендер-путей
**Что идёт не так:** `org.full_name` добавлен в `_header.html`, но забыт в одном из ЧЕТЫРЁХ
мест сборки контекста (act handover, act acceptance, report, preview stub) — рендер падает с
ошибкой "undefined variable" именно на том пути, который забыли.
**Почему это происходит:** partial усиливает связность — теперь ОДИН ключ нужен ВСЕМ ТРЁМ
формам одновременно (раньше `org.name` уже был везде, но новое поле — новый риск повторить
этот же список из 4 мест и что-то упустить).
**Как избежать:** чек-лист из раздела «Новое поле в org_settings» выше перечисляет все 10
точек касания явно — сверять с ним при code review.
**Признаки:** один из трёх видов документов рендерится с ошибкой `AppError::Validation` с
текстом "undefined variable" именно после добавления `org.full_name` в partial, а другие два —
нет.

### Pitfall 3: захардкоженное название организации просачивается в коммит
**Что идёт не так:** копирование `target/debug/templates/act_handover.html` "как есть" в
канон переносит и реальное название организации, зашитое в правке пользователя.
**Почему это происходит:** самый быстрый способ перенести вёрстку — скопировать файл целиком;
именно этот путь и опасен здесь.
**Как избежать:** копировать ТОЛЬКО структуру/CSS, вручную заменяя блок `.orgName` на
`{{ org.full_name | safe }}` + условный `({{ org.name }})` — раздел «Эталон вёрстки» уже даёт
готовый privacy-scrubbed вариант разметки для копирования.
**Признаки:** `git diff --cached` перед коммитом содержит текст, не являющийся Jinja-выражением
или плейсхолдером — grep на конкретное название организации (доступное исполнителю из
прочитанного файла, не публикуемое в этом документе) должен быть частью pre-commit ритуала
фазы, а не полагаться только на память.

### Pitfall 4: `add_template_owned` вызван для partial'а ПОСЛЕ `get_template`/`render` основного шаблона
**Что идёт не так:** `{% include "_header.html" %}` падает с ошибкой "template not found" во
время рендера.
**Почему это происходит:** MiniJinja резолвит include в момент рендера конкретного узла
дерева, но partial должен УЖЕ быть в реестре `Environment` к этому моменту — если
регистрация partial'а вызывается ПОСЛЕ `tmpl.render(ctx)` (а не до), либо в отдельном,
не переданном в `render` `Environment`, include не найдёт цель.
**Как избежать:** оба `add_template_owned` вызова — ДО `env.get_template(&name_owned)` и
`tmpl.render(ctx)`, на ОДНОМ И ТОМ ЖЕ `env` (см. раздел «Регистрация partial'а» выше).
**Признаки:** `AppError::Validation` с текстом "Template render error" упоминающим
`_header.html`/выбранное имя partial'а как "template not found".

### Pitfall 5: v21-снимок сделан ПОСЛЕ того, как канон уже переписан
**Что идёт не так:** `_legacy_defaults/v21/*.html` случайно содержит уже НОВУЮ (Phase 34)
вёрстку вместо старой — апгрейд-механизм больше не может отличить «старая незатронутая
установка» от «уже актуальная», detection ломается тихо (файл просто никогда не совпадёт с
v21-снимком, что не критично для fail-closed, но обесценивает саму цель снимка).
**Почему это происходит:** порядок задач — сначала переписали `act_handover.html` в каноне,
потом вспомнили про снимок и скопировали уже НОВОЕ содержимое.
**Как избежать:** зафиксировать v21-тела ДО первого коммита, изменяющего
`crates/trackly-app/templates/act_*.html`/`report.html` — либо явным `cp` до правок, либо
`git show <commit-до-фазы>:crates/trackly-app/templates/act_handover.html >
.../_legacy_defaults/v21/act_handover.html` после того, как правки уже закоммичены (git
история сохраняет старое состояние вне зависимости от порядка).
**Признаки:** `diff crates/trackly-app/templates/_legacy_defaults/v21/act_handover.html
crates/trackly-app/templates/act_handover.html` — пустой (нет отличий) — снимок бесполезен,
должен отличаться от текущего канона ровно на изменения этой фазы.

// Источник: minijinja::HtmlEscape, docs.rs/minijinja/latest/minijinja/struct.HtmlEscape.html
use minijinja::HtmlEscape;

/// Готовит org.full_name для `| safe` в шаблоне: экранирует HTML-спецсимволы,
/// ЗАТЕМ вставляет <br /> на месте пользовательских переводов строк (D-03 —

### Regex-извлечение блока шапки для render-гейта (по образцу `html_page_parity.rs`)
```rust
// Источник: паттерн из tests/html_page_parity.rs (Phase 33 D-13), адаптирован
// под <div class="header">...</div> вместо @page { ... }.
fn extract_header_block(html: &str, label: &str) -> String {
    let re = regex::Regex::new(r#"(?s)<div class="header">.*?</div>\s*</div>"#)
        .expect("valid regex"); // NB: реальный regex должен учитывать вложенность
                                  // .logo/.orgName/.requisites divs — planner должен
                                  // либо считать вложенные закрывающие теги явно, либо
                                  // использовать html5ever/scraper для точного парсинга
                                  // вместо regex, если вложенность окажется хрупкой.
    re.find(html)
        .unwrap_or_else(|| panic!("{label}: no header block found"))
        .as_str()
        .to_string()
}
```
**Предупреждение:** regex с `.*?` до второго `</div>` хрупок при вложенных `<div>` внутри
шапки (а они есть — `.logo`, `.orgName`, `.requisites` все являются вложенными `<div>`).
Планировщику стоит рассмотреть либо явный маркер-комментарий
(`<!-- HEADER-START -->...<!-- HEADER-END -->`) в partial'е для точного нерекурсивного
извлечения, либо использовать существующую в workspace библиотеку HTML-парсинга, если такая
уже есть (не обнаружена в `Cargo.toml` в этой сессии — вероятно, потребуется добавить `scraper`
ИЛИ придерживаться маркер-комментариев, что не требует новой зависимости).
