<objective>
Add the D-17 backend status endpoint: for each of the four template files the D-14/D-15 mechanism
(Plan 34-02) now manages, report whether it is untouched (matches the current bundled default) or
hand-customized (matches neither the current default nor any known legacy snapshot). This is
read-only, backend-only — no UI is added in this phase; it is a prepared foundation for the
future template-editor rework (`DOC-12`, deferred, see ROADMAP backlog).

Deliberately DIVERGES from the closest existing analog (`templates_list_for_editor`, which has no
authorization check at all) by requiring `authorize(caller, &Action::ManageSettings)` on BOTH
transports — this is a phase-level security decision (exposing which files an admin has hand-
customized is more sensitive than merely listing DB-backed template bodies) and must not be
"corrected" back to the unguarded pattern during implementation.

Purpose: give a future UI (out of scope here) a data source for "шаблон изменён вручную —
обновление не применено", and give admins/support a way to script/inspect upgrade status today.
Output: `TemplateStatusDto` + `TemplateFileStatus` in `dto/reports.rs`; `build_templates_status`
+ `templates_status` Tauri command in `tauri_cmds/settings_org.rs`; `handler_templates_status` +
POST route in `http/settings_org.rs`; a new integration test proving both status values.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-05-01 | Information Disclosure | `/api/v1/templates_status` response (which files are customized) | mitigate | Both transports require `authorize(caller, &Action::ManageSettings)` — the SAME guard `settings_save_org_fields`/`templates_update_body` already use — deliberately stricter than the closest structural analog (`templates_list_for_editor`, unguarded), per explicit phase-level security instruction. | T-34-05-02 | Tampering | `build_templates_status`'s filesystem read | accept | Read-only (`std::fs::read_to_string`), never writes — cannot be used to trigger the D-16 upgrade-write path or corrupt template state; worst case is a stale read if the file changes between the read and the response being sent (no security impact, informational endpoint only). |
| T-34-05-SC | Tampering | npm/pip/cargo installs | accept | No new package-manager dependency in this plan. |
