### CR-01: `_header.html` renders `org.full_name` unguarded

**Files modified:** `crates/trackly-app/templates/_header.html`, `crates/trackly-app/tests/html_header_parity.rs`
**Commit:** `e306b77`

Both names are now independently guarded, which makes the partial's own
doc-comment true rather than aspirational. The doc-comment was also corrected to
describe the actual behaviour, including the detail the review's suggested patch
left unaddressed: **when `full_name` is empty the short name renders bare, with no
parentheses** — matching the pre-Phase-34 (v21) header. The review's proposed fix
removed the stray `<br />` but kept `({{ org.name }})`, which still leaves the
"short name orphaned inside parentheses with nothing to parenthesize" that its own
Issue section complains about.

Regression gate `empty_full_name_renders_bare_short_name_without_stray_br_or_orphan_parens`
renders **all three forms** through the real pipeline and asserts the `.orgName`
node contains no `<br`, no parentheses, and exactly the bare short name. **Verified
non-vacuous:** run against the pre-fix template it fails with
`act_handover: .orgName must contain no <br /> ... got "\n    <br />(ООО Тест)\n  "`.

A placement detail worth knowing: the explanatory Jinja comment is deliberately
**outside** the `.orgName` div. `html_header_parity.rs`'s DOC-05 gate strips only
`{{ }}` and `{% %}` spans from that node before asserting no letters remain — it
does not strip `{# #}` — so a comment inside the div breaks that test.

### WR-10: Integration tests write into whatever `TRACKLY_TEMPLATES_DIR` points at

**Files modified:** `crates/trackly-app/tests/templates_status.rs`
**Commits:** `f32159f`, `63c3c01`

Tests bind `ctx.paths.templates_dir()` and additionally **pin**
`TRACKLY_TEMPLATES_DIR` to that tempdir under an `ENV_GUARD` — necessary because
`build_templates_status` itself resolves through the env var, so binding alone
would have made the test read a different directory than it wrote.

**Verified both ways.** With `TRACKLY_TEMPLATES_DIR` pointed at a populated
directory: pre-fix the run overwrote `act_handover.html` with the fixture's junk
and force-materialized the other three files; post-fix that directory is
byte-identical afterwards and the tests still pass.

Follow-up commit `63c3c01` switches the guard to `tokio::sync::Mutex` — the
`std` guard is held across `build_templates_status(..).await`, which is a
`clippy::await_holding_lock` violation and `ci-fast` runs clippy with
`-D warnings`. (Same choice `template_service.rs`'s test module already makes.)

**Note on the review's secondary citation:** `html_act_render.rs:463-470` was
checked and is **already correct** — it uses `paths.templates_dir()` on the
fixture, not `resolve_templates_dir`. It is a hermeticity nuisance under an
exported env var, never data loss. Left unchanged.

### WR-11: PRIVACY — real-looking requisites remain in public git history

**Files modified:** `.planning/STATE.md`, `scripts/check-privacy-requisites.sh` (new), `.github/workflows/ci-fast.yml`
**Commit:** `f12d652`

**PARTIAL BY INSTRUCTION — the history-rewrite half was deliberately NOT performed.**
`git filter-repo` + force-push is destructive, affects the shared remote and every
existing clone/fork, and requires the user's own separate authorization. No
`filter-repo`, `rebase`, `push --force` or `reset --hard` was run. Recorded as
decision **PRIV-01** in `STATE.md`: accept the history as-is, prevent recurrence,
and leave the rewrite open as a separately-authorized task.

Non-destructive half delivered in full — `scripts/check-privacy-requisites.sh`,
wired into `ci-fast` ahead of the build. Deliberately an **allowlist of approved
placeholder values**, not the review's proposed "does it look fake enough" regex:
that regex was actually tested against the current tree and would have red-flagged
most of the repo's legitimately-fictional fixtures (`87654321`, `771001001`,
`+7 495 000-00-01` match none of its `0000`/`1234`/`12345678`/`1027700` tokens),
while a heuristic by nature passes silently on whatever it did not anticipate —
the exact failure mode this gate exists to close.

**Verified both ways:** green on the current tree; red when a new
plausible-looking literal is introduced. All 15 existing values were read and
confirmed fictional before being allowlisted. **No real data is reproduced in
this report, in any commit message, or in the script.**

### IN-03: No length bound on `org_settings.full_name`

**Files modified:** `crates/trackly-app/src/services/org_db_service.rs`, `crates/trackly-app/tests/org_settings.rs`, `ui/src/lib/components/Textarea.svelte`, `ui/src/features/settings/OrgSettings.svelte`
**Commit:** `121f47f`

Bounded at 512 **characters**, not bytes — the review suggested
`chars().count() <= 512` and that detail matters here: 512 *bytes* of UTF-8 is only
~256 Cyrillic characters, which would cut a Russian legal name at half the length
of a Latin one, in a Russian-only product. Added a `maxlength` prop to the shared
`Textarea` component (it had none) and wired it on the org field. Boundary test:
at-bound accepted, one-over rejected on `field: "full_name"`, and the rejected
write provably does not land.

the XSS mitigation: `HtmlEscape` does not touch `\r` or `\n`, so the
escape-then-insert ordering the mitigation depends on is unchanged.
