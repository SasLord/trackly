### Phase 34: Единая шапка документов
**Goal**: Все три печатные формы (акт приёма-передачи, акт приёмки, отчёт) выводят одинаковую
шапку — лого, название и реквизиты организации из `org.name` — в единой типографике, и эта шапка
доходит до уже установленных копий Trackly после обновления, а не только до новых.
**Depends on**: Nothing (first phase of milestone)
**Requirements**: DOC-04, DOC-05, DOC-06
**Success Criteria** (what must be TRUE):
  1. Правки шапки, ранее сделанные пользователем только в `target/debug/templates/`, перенесены
     в канонический источник `crates/trackly-app/templates/` — не утеряны при `cargo clean`.
  2. Все три шаблона (`act_handover.html`, `act_acceptance.html`, `report.html`) рендерят
     идентичную по вёрстке и типографике шапку (лого → название организации → реквизиты),
     подтверждено рендером настоящего PDF/превью (не тестом извлечения текста), на обоих
     транспортах — десктоп и LAN-браузер (после `pnpm --dir ui build`).
  3. Название организации в шапке подставляется из настройки `org.name`; ни в одном из трёх
     поставляемых в бинарнике шаблонов нет захардкоженного реального названия организации.
  4. Установка Trackly с файлами шаблонов на диске, совпадающими с известным предыдущим
     дефолтом (срез `_legacy_defaults`), получает новую шапку при следующем запуске без
     удаления каталога `templates/` вручную; установка с пользовательскими правками — нет
     (апгрейд не затирает кастомизацию).
**Plans**: 6 plans in 3 waves

- [x] 34-01-PLAN.md — org_settings.full_name миграция V036 + DTO/OrgDbService wiring + org_full_name_html escape-хелпер (D-01/D-03)

**Wave 2** *(depends on Wave 1)*

- [x] 34-03-PLAN.md — регистрация partial'а в render_with_timeout + контекст org.full_name на всех 4 путях рендера + render-gate тест (D-13, C-03/C-04)

### Phase 35: Тело акта приёма-передачи
**Goal**: Текст акта приёма-передачи составлен в каноничной форме документа (две стороны,
«составили настоящий акт о нижеследующем», перечень, состояние, срок, подписи), согласован с
пользователем до вёрстки, без полосок-подчёркиваний под автоматически подставляемым текстом, с
горизонтальным блоком подписей — по строке на каждого подписанта с автоподставленными ФИО.
**Depends on**: Phase 34 (общий файл шаблона; шапка должна устояться прежде правки тела)
**Requirements**: DOC-07, DOC-08, DOC-09
**Success Criteria** (what must be TRUE):
  1. Финальный текст акта (преамбула с двумя сторонами, перечень, состояние, срок, подписи)
     явно согласован с пользователем ДО начала вёрстки тела — согласование зафиксировано как
     первый шаг фазы, а не как её итог.
  2. Согласованный текст сверен с каноном вёрстки Word-образца (см. память проекта
     `act-pdf-word-fidelity`) — изменения не ломают то, ради чего делались Фазы 15/16.
  3. В акте приёма-передачи нет полосок-подчёркиваний под автоматически подставляемыми полями;
     полоски остаются только там, где расписываются от руки (сами подписи).
  4. Блок подписей горизонтальный, отдельная строка на каждого подписанта (передающая и
     принимающая сторона), ФИО подставляются автоматически из `act.giver_name` /
     `act.receiver_name` без изменений бэкенда.
  5. Рендер настоящего PDF/превью (не текстовое сравнение) подтверждает вёрстку на обоих
     транспортах — десктоп и LAN-браузер.
**Plans**: 7 plans in 6 waves (Wave 5 — закрытие гэпа верификации; Wave 6 — закрытие гэпа re-verification, DOC-08/SC#4)

**Wave 1**

- [x] 35-01-PLAN.md — срез _legacy_defaults/v22 + регистрация в KNOWN_LEGACY_DEFAULTS + demo_context_for_kind act.giver_name

**Wave 2** *(depends on Wave 1)*

- [x] 35-03-PLAN.md — act_acceptance.html: дедупликация ФИО в таблице + горизонтальный блок подписей (D-09/D-06/D-07)

### Phase 36: Пагинация акта по количеству устройств
**Goal**: Разбивка акта приёма-передачи по листам зависит от количества устройств — один лист с
полным описанием для одного устройства, «Приложение №1» с полной таблицей со второго листа для
нескольких.
**Depends on**: Phase 35 (пагинация строится поверх переработанной формы тела и блока подписей)
**Requirements**: DOC-10, DOC-11
**Success Criteria** (what must be TRUE):
  1. Акт на одно устройство целиком умещается на одном листе вместе с полным описанием этого
     устройства — подтверждено рендером настоящего PDF на обоих транспортах.
  2. Акт на несколько устройств выводит на первом листе только перечень имён устройств и
     отсылку к «Приложению №1», без полного описания на этом листе.
  3. Со второго листа многоустройственного акта идёт «Приложение №1» с таблицей полного
     описания всех устройств; разрыв страницы и заголовок приложения корректно рендерятся
     через Paged.js (Фаза 33) — подтверждено живым превью, не тестом извлечения текста.
  4. Печать многостраничного акта на обоих транспортах не ломает изоляцию печатного DOM
     (durable-гейт `ui/scripts/check-print-isolation.mjs` остаётся зелёным).

### Phase 37: Приватность данных
**Goal**: Текущее состояние репозитория (HEAD) не содержит реальных реквизитов организации и ФИО
сотрудников, и повторная утечка ловится автоматической проверкой до попадания в репозиторий.
**Depends on**: Nothing (независима от направления шаблонов)
**Requirements**: PRIV-01, PRIV-02
**Success Criteria** (what must be TRUE):
  1. В коде, шаблонах и тестах на HEAD нет реального названия организации, ИНН/КПП/ОКПО/ОГРН,
     адреса или иных реквизитов — только `org.name`-подобные переменные и вымышленные
     placeholder-значения.
  2. В `.planning/`-артефактах (PLAN/SUMMARY/STATE/CONTEXT/брифы) на HEAD нет настоящих ФИО
     сотрудников — включая известные точки утечки: `.planning/PHASE-BRIEF-act-pdf-word-fidelity.md`,
     `.planning/STATE.md`, `.planning/quick/260805-lrs-.../PLAN.md` и `SUMMARY.md`.
  3. История git НЕ переписана (осознанное решение пользователя от 2026-08-08) — очистка
     затрагивает только HEAD; репозиторий остаётся публичным, остаточный риск в старых
     коммитах принят осознанно и не является предметом этой фазы.
  4. Новый durable-скрипт (по образцу `ui/scripts/check-contrast.mjs` /
     `check-print-isolation.mjs`) сканирует файлы на известные признаки утечки (настоящее
     название организации, ИНН/КПП/ОКПО/ОГРН, сконфигурированные реальные ФИО) и завершает
     проверку ошибкой при обнаружении совпадения; проверка подключена в существующую цепочку
     `pnpm --dir ui lint` (или эквивалентный CI-гейт) и запускается автоматически.
  5. Гейт проходит зелёным на очищенном HEAD — легитимные placeholder-значения
     («Иванов И.И.», `org.name`) не дают ложных срабатываний. Порядок внутри фазы:
     сначала чистка (критерии 1–3), затем гейт (критерии 4–5), иначе гейт падает на
     собственном репозитории с первого запуска.
