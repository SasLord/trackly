### Phase 42: Основа монорепо, ADR и пилот на доменных ПК

**Goal**: Репозиторий готов к двум клиентам: Link собирается отдельным приложением со своей версией на общих
пакетах, ключевые решения зафиксированы в ADR, а выполнимость раскатки на доменных ПК проверена пилотом до
вложений в дистрибуцию.

**Depends on**: Nothing (первая фаза вехи; предыдущая веха v1.4 закрыта)

**Requirements**: LNK-01, LNK-10, DST-06

**Research/spike**: ДА — пилот AppLocker/SRP, WebView2 и тихой установки NSIS на реальных доменных ПК (до плана Фазы 45); проверка pin SPKI на reqwest/ring и tokio-tungstenite; FTS5 trigram и `keyring-core` на трёх ОС.

**Success Criteria** (what must be TRUE):

  1. Link собирается из этого же репозитория отдельным приложением со своей версией (отдельный dry-run выпуска не задевает релизы Trackly); сборка Trackly и все прежние гейты остаются зелёными после переезда фронтенда в общие пакеты.
  2. Окно каркаса Link показывает узкий логотип «Link» слева вверху, вкладку «Чат» справа от него, сайдбар слева и область содержимого справа.
  3. Компонент, написанный один раз в общем пакете, отображается и в Trackly, и в Link без копирования.

### Phase 43: Надёжная доставка событий

**Goal**: События не теряются и не утекают: клиент после любого обрыва догружает пропущенное по курсору и получает события только своих бесед.

**Depends on**: Phase 42

**Requirements**: DLV-01, DLV-02, DLV-03, DLV-04

**Research/spike**: нет — стандартный паттерн «сигнал + догрузка».

**Success Criteria** (what must be TRUE):

  1. После обрыва связи или переполнения очереди событий экран Trackly и клиент догружают всё пропущенное без ручного обновления — потерянных событий нет (закрывает долг «WS Lagged»).
  2. Пользователь получает события только бесед, в которых состоит; после исключения из комнаты события этой комнаты перестают приходить сразу.
  3. Повторная отправка после сбоя сети не создаёт дубликат сообщения.
  4. Сервер сам закрывает «мёртвые» соединения, а клиенты переподключаются автоматически.

### Phase 44: Link — транспорт, пин сертификата и вход

**Goal**: Link работает как фоновый клиент: живёт в трее, стартует с системой, безопасно говорит с сервером и впускает сотрудника без лишних действий.

**Depends on**: Phase 42, Phase 43

**Requirements**: LNK-02, LNK-03, LNK-04, LNK-05, LNK-06, LNK-07, LNK-08, LNK-09, LNK-11

**Research/spike**: ДА — клиентский SPNEGO (SSPI) и совместимость с серверным SSO (SPN, имя хоста вместо IP); keyring на Windows/macOS/Linux; поведение трея в GNOME и при перезапуске Explorer.

**Success Criteria** (what must be TRUE):

  1. Link виден только иконкой в трее (нет кнопки на панели задач), стартует свёрнутым при входе в систему; закрытие окна прячет его, выйти можно только пунктом «Закрыть» в меню трея.
  2. Повторный запуск показывает окно уже работающего экземпляра; на терминальном сервере у каждого пользователя сеанса свой экземпляр.
  3. Сотрудник на доменном ПК входит автоматически без пароля; на ПК вне домена входит логином и паролем, вход запоминается и отзывается администратором. Доменный вход требует живой проверки на Windows с AD.
  4. При несовпадении отпечатка сертификата сервера Link показывает понятную ошибку и ничего не отправляет.
  5. При потере связи Link показывает «нет связи», переподключается сам и после сна ПК догружает пропущенное; на Linux без системного трея окно остаётся доступным.

### Phase 45: Дистрибуция и автообновление Link

**Goal**: Администратор раскатывает Link на сотни ПК и обновляет его с сервера Trackly без визитов на каждый ПК, с каналами «стабильный» и «тестовый».

**Depends on**: Phase 42 (пилот и ADR), Phase 44

**Requirements**: DST-01, DST-02, DST-03, DST-04, DST-05, UPD-01, UPD-02, UPD-03, UPD-04, UPD-05, UPD-06, UPD-07, ADM-01, ADM-02

**Research/spike**: ДА — updater при самоподписанном TLS (флаг vs собственный загрузчик с проверкой подписи), ротация ключа, откат, обновление при запущенном приложении, Authenticode, AUMID и тосты при установке из NSIS.

**Success Criteria** (what must be TRUE):

  1. Администратор по инструкции ставит Link на доменные ПК групповой политикой без прав администратора на ПК; пользователь вне домена ставит тем же установщиком вручную; адрес сервера и отпечаток задаются при установке, а не вшиты в публичный релиз. Требует живой проверки на доменных Windows-ПК.
  2. Администратор загружает сборку в разделе «Link», назначает её версией канала «стабильный» или «тестовый» и видит список клиентов (пользователь, компьютер, версия, канал, последний вход) с отзывом устройства; сервер отклоняет сборку без действительной подписи.
  3. Установленный Link на Windows сам обновляется с сервера без прав администратора; сквозной сценарий 0.0.1→0.0.2 проверен на Windows.
  4. Тестовый канал назначается отдельным пользователям и компьютерам (компьютер приоритетнее пользователя); клиент стабильного канала нигде не видит упоминаний о других каналах; откат канала на предыдущую сборку переводит клиентов на неё.
  5. Сборки Link выпускает отдельный CI-процесс, не задевая релизы Trackly; хранение и ротация ключа подписи, выпуск внутреннего сертификата и раздача доверия через GPO описаны в документации.

### Phase 47: Чат — серверная модель

**Goal**: Сервер хранит беседы и сообщения по правилам, которые не обойти клиентом: участие, роли, история и безопасное содержимое.

**Depends on**: Phase 43 (доставка и курсор), Phase 42 (общие DTO)

**Requirements**: CHT-01, CHT-02, CHT-03, CHT-04, CHT-05, CHT-06, CHT-12, CHT-13, RTE-09

**Success Criteria** (what must be TRUE):
