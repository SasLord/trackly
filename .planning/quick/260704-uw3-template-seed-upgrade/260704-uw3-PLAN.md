# Quick Task 260704-uw3: Auto-upgrade bundled default act templates on existing DBs

## Problem

`ActService::render` (`act_service.rs:1378`) renders via
`TemplateService::get_active("act_handover")`, which reads the template body
from the `document_templates` table in the DB — not from the bundled
`.minijinja` file directly.

`TemplateService::seed_defaults_on_startup` (`template_service.rs:70-100`)
only `INSERT`s the bundled default when `active_count == 0` for a given
`kind`. On any DB created before today (seeded back in Phase 03), an active
row already exists, so this early-return-via-count-check means the Phase
15-02 rewrite of `act_handover.minijinja` (new Phase 14 fields: Комплектация,
Технические характеристики, Срок до, мультиустройство) is **never applied**
to existing installations — only to brand-new DBs.

The schema already has an `is_default` column (migration V027):
`is_default=1` means "current body equals whatever the bundled default was
when last synced" (untouched by user); `update_body` sets it to `0`;
`reset_to_default` sets it back to `1`. This flag is the safety key that lets
us distinguish "safe to auto-upgrade" rows from "user customized, never
touch" rows.

## Approach

Enhance `seed_defaults_on_startup` (still one writer transaction, one pass
over `DEFAULT_TEMPLATES`) with a second branch:

- **Existing behavior (keep):** no active row for `kind` → `INSERT` bundled
  default (`is_default=1`, `version=1`).
- **New behavior:** an active row exists **and** `is_default = 1` **and**
  its stored `body_minijinja` differs from the current bundled `body` →
  `UPDATE document_templates SET body_minijinja=?, is_default=1,
  updated_at_utc=?, version=version+1 WHERE kind=? AND is_active=1 AND
  deleted_at_utc IS NULL` (same UPDATE shape as `reset_to_default`,
  `template_service.rs:196-206`). Log via `tracing::info!` that the default
  was auto-upgraded (kind + old/new version).
- Rows with `is_default = 0` (user has called `update_body`, i.e.
  customized) are **never** touched by this new branch — only the existing
  "no active row" branch can ever create a row for such a kind, and that
  branch is mutually exclusive with the `is_default=0` case since it
  requires an active row to already exist.
- Only write when `body` actually differs from the stored
  `body_minijinja` — avoids a needless `version` bump / write on every
  startup once already synced (idempotency requirement from the seed-startup
  doc-comment at the top of the file).

This is a pure extension of the existing per-`kind` loop inside the same
writer transaction — no new query pattern, no schema change, no new files.

   exists), then branch three ways: no row → INSERT (existing); row exists,
   `is_default=1`, body differs → UPDATE (new, mirrors
   `reset_to_default`'s UPDATE shape); row exists but `is_default=0` or body
   already matches → no-op. Update the module-level doc-comment

## must_haves

- truths:
  - On an existing DB where `act_handover`'s active row has `is_default=1`
    and a stale body, the next app startup upgrades it in place to the
    current bundled `act_handover.minijinja` body — no manual intervention
    or re-seed needed.
  - A user-customized template (`is_default=0`) is never overwritten by
    `seed_defaults_on_startup`, regardless of how the bundled default
    changes in future releases.
  - Startup is a no-op (no write, no version bump) once a template's stored
    body already matches the bundled default — repeated restarts don't
    inflate `version`.
  - Brand-new DBs (no active row for a `kind`) still get seeded exactly as
    before (`is_default=1`, `version=1`).
- artifacts:
  - `crates/trackly-app/src/services/template_service.rs` — extended
    `seed_defaults_on_startup` with the upgrade branch + 3 new regression
    tests in the `tests` module.
- key_links:
  - `seed_defaults_on_startup`'s new UPDATE branch mirrors the UPDATE shape
    in `reset_to_default` (`template_service.rs:196-206`): same SET clause
    (`body_minijinja`, `is_default=1`, `updated_at_utc`, `version=version+1`),
    same WHERE clause (`kind=?1 AND is_active=1 AND deleted_at_utc IS NULL`).
  - `ActService::render` → `templates.get_active("act_handover")`
    (`act_service.rs:1378`) is the consumer that benefits — no changes
    needed there; it already reads whatever is currently active.
