<objective>
Yesterday's quick task (260805-wik) taught `on_ad_bind_success` to resync an existing ACTIVE
user's `full_name` from the AD directory (`sync_active_user_name`, with 4 anti-corruption
guards). But `on_ad_bind_success` checks `is_admin_login(login)` FIRST and, for any login on the
`admin_logins` list, delegates entirely to `force_admin_provisioning` — which never calls
`sync_active_user_name` in any of its 4 non-INSERT branches. Result: an administrator's ФИО is
frozen at first login forever, unlike a regular employee. This is a documented gap in
`.planning/v1.3-MILESTONE-AUDIT.md` against requirement SSO-01.

The fix reuses `sync_active_user_name` verbatim (D-1: do not duplicate the write-guard logic — this
codebase has already paid once for a duplicated-predicate bug across 3 SQL builders and does not
want to pay it again). `NameSource` is threaded one level deeper, into `force_admin_provisioning`,
so the anti-corruption guard (an unreachable directory or an untrusted caller-supplied name must
never overwrite a stored ФИО) applies identically to forced-admin logins.

Purpose: administrators provisioned via `admin_logins` get the same directory-truth guarantee
(SSO-01) as every other AD user — no permanently-stale name, no risk of directory-outage
corruption either.
Output: `force_admin_provisioning` takes a `NameSource` parameter and calls
`sync_active_user_name` uniformly on the exit of every branch except `force_admin_insert_unknown`;
3 new regression tests in `ad_admin_logins.rs` pinning the update case, the anti-corruption case,
and the escalation-branch case specifically.
</objective>

```rust
// on_ad_bind_success (L493-543) — the shared post-bind seam for BOTH
// sso_login and try_ad_login. Currently forwards login/display_name only to
// force_admin_provisioning, dropping name_source on the floor.
async fn on_ad_bind_success(
    &self,
    login: &str,
    display_name: &str,
    role_hint: Option<Role>,
    name_source: NameSource,
) -> Result<UserDto, AppError> {
    if self.is_admin_login(login) {
        return self.force_admin_provisioning(login, display_name).await; // <- missing name_source
    }
    match self.find_user_any_state(login).await? {
        Some(found) if found.is_active && !found.deleted => {
            self.sync_active_user_name(found.id, login, display_name, name_source).await
        }
        // ...unchanged pending/blocked/unknown branches...
    }
}

// force_admin_provisioning (L565-584) — 5-way state machine. Only the None
// (unknown -> INSERT) arm writes full_name today.
async fn force_admin_provisioning(
    &self,
    login: &str,
    display_name: &str,
) -> Result<UserDto, AppError> {
    match self.find_user_any_state(login).await? {
        None => self.force_admin_insert_unknown(login, display_name).await, // writes full_name at INSERT — do not touch
        Some(u) if u.is_active && !u.deleted && u.role == "admin" => {
            self.get_by_login(login).await // <- no-op branch, needs sync
        }
        Some(u) if u.is_active && !u.deleted => {
            self.force_admin_escalate_active(u.id, u.role).await // <- needs sync after
        }
        Some(u) if !u.is_active && !u.deleted && u.has_open_register_request => {
            self.force_admin_activate_pending(u.id).await // <- needs sync after
        }
        Some(u) => self.force_admin_revive_blocked(u.id).await, // <- needs sync after
    }
}

// sync_active_user_name (L1597-1641) — REUSE VERBATIM, do not modify its
// body or guard order. Already re-reads current state via get_by_login, so
// callers only need to pass user_id + the raw candidate + provenance.
async fn sync_active_user_name(
    &self,
    user_id: i64,
    login: &str,
    candidate_name: &str,
    name_source: NameSource,
) -> Result<UserDto, AppError>;
```

  <action>
Add a `name_source: NameSource` parameter to `force_admin_provisioning` and update its single call
site in `on_ad_bind_success` (the `if self.is_admin_login(login)` branch) to pass through the
`name_source` it already receives as a parameter — no new logic needed there, this is a pure

In `force_admin_provisioning`, keep the `None` (unknown login) arm calling
`force_admin_insert_unknown` exactly as-is (D-3 — first-creation write is correct, do not touch).
For the remaining 4 arms, after the existing write completes, call
`self.sync_active_user_name(u.id, login, display_name, name_source).await` and return its result
instead of the branch's current return expression:
- "already active admin" arm: replace the current bare `self.get_by_login(login).await` with a
  direct call to `sync_active_user_name(u.id, ...)` (no need to call `get_by_login` first —
  `sync_active_user_name` already re-reads current state internally).
- "active non-admin" (escalation) arm: `await?` the existing `force_admin_escalate_active(u.id,
  u.role)` call first (propagate its error), then call `sync_active_user_name(u.id, login,
  display_name, name_source).await` as the arm's return value.
- "pending" (activate) arm: same pattern — `await?` `force_admin_activate_pending(u.id)` first,
  then `sync_active_user_name(...)`.
- "blocked/soft-deleted" (revive) arm: same pattern — `await?` `force_admin_revive_blocked(u.id)`
  first, then `sync_active_user_name(...)`.

This is deliberately uniform (per D-4: call the shared helper once per branch, at the exit, rather
than editing 4 separate helper functions to accept name_source individually) — it also means role
escalation, pending-request auto-completion, and blocked-user revival keep writing exactly what
they write today (D-5); the ONLY new write is the (already fully-guarded) `full_name`
UPDATE inside `sync_active_user_name` itself. Do not modify `sync_active_user_name`'s body,
`force_admin_insert_unknown`, `force_admin_escalate_active`, `force_admin_activate_pending`, or
`force_admin_revive_blocked` in any way beyond what's described above.

Update the doc comments on `force_admin_provisioning` (currently documents 5 branches without
mentioning `full_name`) to note that all branches except `unknown -> INSERT` now also resync
`full_name` via `sync_active_user_name`, reusing 260805-wik's anti-corruption guards unmodified
(reference this quick task, 260806-wk1, and requirement WK1-01/WK1-02).
