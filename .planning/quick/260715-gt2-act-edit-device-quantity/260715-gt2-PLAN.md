# Quick Task 260715-gt2: Allow qty>1 for newly-added positions when editing an act

## Problem

In `ActFormModal` edit mode (`mode='edit'`), `ActFormItemsTable.svelte` hard-codes
quantity to `1` for every row (qty-cell, ~line 690-697: `<span class="qty-fixed">1</span>`),
and both device pickers (`pickDevice` ~line 333, `pickGroup` ~line 446) force
`quantity: hasSerial || mode === 'edit' ? 1 : ...`. This was intentional at the time
(Plan 19-08/WR-02, because `ActUpdateItemDto` only carried one `device_id` per entry
and the UI had no expansion path for edit-mode submits), but it means a user editing
an existing act cannot add, e.g., 3 keyboards at once — they must add 3 separate
rows one device at a time even when the warehouse has 3+ identical devices in stock.

The backend already supports this: `ActUpdateDto.items: Vec<ActUpdateItemDto>` is a
**full replacement set**, one entry per device_id, and `ActService::update`
(`act_service.rs:578`) diffs `added`/`unchanged` device_id sets and loops over
`added: Vec<i64>` (`act_service.rs:667-754`), transitioning every added device to
`в_работе` + the act's location and writing one `act_items` row each — this loop is
already N-device-safe, it has just never been exercised with N>1 by any existing
test or by the UI. **No DTO or `ActService::update` change is required** — this is
a UI-only gap (verified by reading `act_service.rs:578-754`; confirmed by Task 1's
new regression test below, which locks the contract in place).

## Approach

Reuse the existing retained-vs-new discriminator (`FormItemRow.complectation_at_time`:
`undefined` = freshly added this edit session, `!== undefined` = retained from the
original act — see the doc comment at `ActFormItemsTable.svelte:39-47` and its use at
line 526) to gate the fix precisely:

- **Retained positions** keep qty fixed at `1` (you cannot pull "more of the same"
  onto an already-attached, specific device) — unchanged.
- **Freshly-added, non-serialised positions** (`complectation_at_time === undefined`
  and `!has_serial`) become qty-editable, bounded by the row's own
  `stock_available`/`group_ids.length`, reusing the exact same `qtyMax()` +
  `handleQtyInput()` clamping the create path already uses — no new bounding logic.
- **Serialised/inventoried positions** stay qty=1 in every mode (W-5 rule, unchanged).
- On submit, `ActFormBody`'s edit branch expands each freshly-added row with
  `quantity > 1` into N `ActUpdateItemDto` entries via
  `group_ids.slice(0, quantity)` — the exact same expansion pattern the create
  branch already uses a few lines below it (`ActFormBody.svelte:168-178`). Retained
  rows still emit exactly one entry each, unchanged.

This is a pure UI change (2 files) plus one backend regression test that locks in
the multi-device-add contract the UI is about to start relying on for N>1 (existing
backend test coverage only ever exercised N=1 add).

## must_haves

- truths:
  - Editing an act, a user can add a NEW position and set its quantity above 1
    (e.g. 3 keyboards) when the warehouse has enough devices in the same group —
    the qty field is editable and bounded to the stock group size, exactly like
    create mode.
  - Existing (retained) positions on the act remain fixed at quantity 1 and are
    never affected by this change.
  - Serialised/inventoried devices remain quantity 1 in every mode (W-5, unchanged).
  - Submitting such an edit attaches ALL N chosen devices to the act and removes
    all N from stock — proven end-to-end by a backend integration test asserting
    on `act_items` count and each device's `status_id`/`location_id`.
- artifacts:
  - `ui/src/features/acts/ActFormItemsTable.svelte` — editable, group-bounded qty
    input for freshly-added non-serial rows in edit mode; retained/serial rows
    unchanged (static "1").
  - `ui/src/features/acts/ActFormBody.svelte` — edit-mode submit payload
    `flatMap` expansion of `group_ids` for freshly-added rows with `quantity > 1`.
  - `crates/trackly-app/tests/acts_update.rs` — new
    `add_multiple_positions_transitions_all_devices` regression test.
- key_links:
  - `ActFormItemsTable.pickDevice`/`pickGroup` → `FormItemRow.quantity` /
    `group_ids` / `stock_available` — feeds both the qty-input's `qtyMax()` bound
    and the submit-side expansion source (`group_ids.slice(0, quantity)`).
  - `ActFormBody`'s edit-payload `flatMap` → `ActUpdateDto.items` (each entry
    `{device_id, complectation_at_time}`) → `ActService::update`'s `added` loop
    (`act_service.rs:667-754`), which transitions status to `в_работе` + act's
    location and inserts one `act_items` row per device_id — already proven
    N-safe by Task 1's regression test.
