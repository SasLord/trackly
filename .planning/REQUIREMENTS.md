# Requirements: Trackly

**Defined:** 2026-05-24
**Core Value:** Учёт устройств и картриджей с актами приёма-передачи и историей перемещений должен работать надёжно и быстро в режиме «одной кнопкой» — без обращения к Excel-таблицам, ручного присвоения номеров актов или потери истории при возврате на склад.

## v1 Requirements

### Foundation (FOUND)

Фундамент: схема БД, миграции, портативный режим, паттерн single-writer, базовая конфигурация. Обоснование сосредоточить это в Phase 1 — в SUMMARY.md (резолвинг конфликтов между ресёрчерами).

- [x] **FOUND-01**: Workspace из 3 крейтов (`trackly-core`, `trackly-infra`, `trackly-app`) с чёткими границами (core не имеет I/O-зависимостей)
- [x] **FOUND-02**: SQLite в WAL-режиме с разделёнными пулами: write pool = 1 connection через выделенную задачу `spawn_blocking`, read pool = 3-4 connections
- [x] **FOUND-03**: Refinery-миграции (forward-only), встроенные в бинарник, с `PRAGMA user_version` для контроля версии схемы
- [x] **FOUND-04**: Портативный режим: БД и конфиг рядом с исполняемым файлом, маркер-файл `portable.txt`, явный запрет на `app_data_dir()` / `dirs::*_dir()`
- [x] **FOUND-05**: `WEBVIEW2_USER_DATA_FOLDER` принудительно устанавливается до создания `tauri::Builder` (иначе WebView2 пишет в `%LOCALAPPDATA%`)
- [x] **FOUND-06**: Newtype `Secret<T>` для всех секретов (пароли, AD-пароли, community strings) с кастомным `Debug` → `***`
- [x] **FOUND-07**: Все timestamps в БД хранятся в UTC; форматирование в локали — через `chrono-tz` на UI-слое
- [x] **FOUND-08**: Базовая схема включает таблицы: `device_types`, `device_statuses`, `cartridge_states`, `cartridge_statuses` — как seeded таблицы (НЕ enum в Rust), допускающие расширение без миграции
- [x] **FOUND-09**: На каждой пользовательской сущности (`device`, `cartridge`, `act`, `request`, `user`): колонки `created_at`, `updated_at`, `deleted_at` (soft delete), `version` (optimistic lock)
- [x] **FOUND-10**: Таблица `audit_log` с записью всех мутаций (entity, entity_id, op, user_id, payload_json, created_at)
- [x] **FOUND-11**: ProcMon/процесс-аудит тест в CI: после полного цикла приложения убедиться, что НЕТ записей в `%APPDATA%`, `%LOCALAPPDATA%`, `~/.config`, `~/Library/Application Support`
- [x] **FOUND-12**: `tauri-specta` v2 для генерации TypeScript-типов из Rust DTO; единые типы для Tauri-invoke и HTTP-транспорта

### Devices (DEV)

- [ ] **DEV-01**: CRUD устройств с полями: Тип, Наименование, Инвентарный №, Серийный №, Модель, Технические характеристики, Комплектация, Состояние, Расположение, Статус
- [ ] **DEV-02**: Обязательные поля только: Тип, Наименование, Расположение, Статус
- [ ] **DEV-03**: Поддержка не-уникальных устройств (без серийного/инвентарного №) с указанием количества; устройство с любым из ID-номеров — уникальное (количество = 1)
- [x] **DEV-04**: Типы устройств (seeded, расширяемые): Устройство (по умолчанию), Принтер, Расходник (для бумаги, одноразовых флешек и пр. — НЕ для картриджей)
- [x] **DEV-05**: Статусы устройств (seeded, расширяемые): На складе, В работе, На ремонте, Списано
- [ ] **DEV-06**: Полнотекстовый поиск по устройствам (наименование, инвентарный №, серийный №, модель)
- [ ] **DEV-07**: Фильтр (свитч-бар со счётчиками) по статусу: Все / На складе / В работе / На ремонте / Списано
- [ ] **DEV-08**: Автокомплит-дропдаун для полей: Наименование, Модель, Технические характеристики, Комплектация, Состояние, Расположение — на основе ранее введённых значений
- [ ] **DEV-09**: Контекстный автокомплит: при уже выбранном Наименовании остальные дропдауны предлагают только значения, ранее использованные для этого Наименования
- [ ] **DEV-10**: Подсказки для поля Состояние (быстрый выбор): «Новое», «Новый в заводской упаковке, не вскрытый», «Новый в заводской упаковке, вскрытый, настроенное рабочее окружение (ОС)», «Хорошее», «Среднее», «Б/У»
- [ ] **DEV-11**: Группировка похожих позиций в табличном представлении с возможностью развернуть
- [ ] **DEV-12**: Импорт устройств из CSV (UTF-8 + автодетект CP1251, делимитеры `,` и `;`) с превью и обработкой ошибок построчно
- [ ] **DEV-13**: Экспорт списка устройств в CSV (UTF-8 BOM для совместимости с Excel)
- [ ] **DEV-14**: Формирование документа приёма товара на склад (печать + сохранение в PDF) с полями «Кто передал», «Кто принял»
- [ ] **DEV-15**: Редактируемый шаблон документа приёма товара (хранится в БД, переезжает с portable-сборкой)

### Acts (ACT)

- [ ] **ACT-01**: CRUD актов приёма-передачи устройств
- [ ] **ACT-02**: Свитч-бар Акты / Возвраты / Архив со счётчиками (количество в каждой группе)
- [ ] **ACT-03**: Поля акта: № (автопредложение «следующий по порядку», с возможностью переопределить), Дата, Сдал (ФИО), Принял (ФИО), Устройство (автокомплит по складу), Количество, Сроком до (опционально), Расположение (опционально, автокомплит «не на складе»)
- [ ] **ACT-04**: Поиск по актам (по номеру, ФИО, наименованию устройства)
- [ ] **ACT-05**: Действия над актом: Просмотр, Редактировать, Возврат, Удалить
- [ ] **ACT-06**: Удаление акта возвращает устройство на склад в исходное расположение и состояние
- [ ] **ACT-07**: Возврат акта — отдельная сущность типа «Акт возврата», с номером базового акта + суффикс «в» для полного возврата; для частичного: «в1», «в2», «в3»…
- [ ] **ACT-08**: При возврате — указание нового Состояния и Расположения на складе для каждого устройства; галочка «Применить ко всем» для bulk-применения
- [ ] **ACT-09**: Акт перемещается в Архив автоматически, когда все его устройства возвращены
- [ ] **ACT-10**: Удаление акта возврата восстанавливает Состояние/Расположение устройств к значениям из исходного акта
- [ ] **ACT-11**: Формирование документа Акт приёма-передачи (печать + сохранение в PDF) с шапкой организации и логотипом
- [ ] **ACT-12**: Редактируемый шаблон акта приёма-передачи (хранится в БД)
- [ ] **ACT-13**: Транзакционная гарантия: создание/удаление/возврат акта — единая транзакция, всё или ничего (нельзя получить акт без обновления статуса устройства)
- [ ] **ACT-14**: Автопредложение следующего номера акта потокобезопасно (атомарная генерация в single-writer task), gaps допустимы при ошибках, ручной override — пишет в `audit_log`

### Cartridges (CART)

- [ ] **CART-01**: Подраздел «Модели картриджей» — CRUD моделей: Название, Цвет (опционально), Примечание, Совместимые принтеры
- [ ] **CART-02**: Совместимые принтеры в модели картриджа — массив пар «Бренд + Модель» с автокомплитом ранее введённых; разные бренды допустимы (универсальные картриджи)
- [ ] **CART-03**: Подраздел «Картриджи (экземпляры)» — CRUD картриджей с полями: Код, Модель картриджа, Состояние заряда (Полный/Частичный/Пустой), Расположение, Примечания
- [ ] **CART-04**: Автогенерация Кода картриджа в формате `C-000001`, `C-000002`… (потокобезопасно, как ACT-14); пользователь может ввести свой код (например, штрих-код с приёмки)
- [ ] **CART-05**: Свитч-бар по статусу: Все / На складе / В работе / На заправке / Списано (счётчики в каждой)
- [ ] **CART-06**: Контекстные действия в зависимости от статуса:
  - «На складе» → Установить в принтер / Отправить на заправку / Списать / Редактировать / Удалить
  - «В работе» → Вернуть на склад / Редактировать / Удалить
  - «На заправке» → Забрать с заправки / Редактировать / Удалить
  - «Списано» → Восстановить / Удалить
- [ ] **CART-07**: При установке в принтер — указание: Дата, Кто выдал (ФИО), Кому выдал (ФИО), Расположение (автокомплит «не на складе»)
- [ ] **CART-08**: При возврате на склад — указание: Состояние заряда (по умолчанию Пустой), Расположение (автокомплит «на складе»), Примечания
- [ ] **CART-09**: Передача на заправку и возврат с заправки — аналогично выдаче/возврату с тем же набором полей
- [ ] **CART-10**: История перемещений картриджа доступна в карточке экземпляра (хронологический список из `audit_log`)
- [ ] **CART-11**: Поиск по картриджам (по коду, модели, расположению)
- [ ] **CART-12**: Баннер «низкий остаток» на дашборде и в разделе «Картриджи»: показывается, когда количество картриджей со статусом «На складе» + состоянием «Полный» по конкретной модели опускается ниже порога (см. SET-04)

### Printers (PRN)

Раздел мониторинга и учёта принтеров. Использует данные из DEV (где принтер заведён как устройство типа «Принтер»).

- [ ] **PRN-01**: Авто-сканирование подсети (диапазон IP, конфигурируется): SNMP-discovery, идентификация модели и производителя
- [ ] **PRN-02**: SNMP-мониторинг сетевых принтеров: уровни тонера/чернил, статус печати, страничные счётчики (используется `snmp2 0.4`, поддержка v1/v2c/v3)
- [ ] **PRN-03**: Поддержка целевых моделей: Pantum BM5100ADN (приоритет), Kyocera ECOSYS, HP LaserJet, Canon iR (по производитель-специфичным OID, fallback на стандартный Printer-MIB / RFC 3805)
- [ ] **PRN-04**: USB-принтеры на компьютерах: учёт подключения принтера к рабочей станции; механизм опроса (локальный агент vs WMI/RPC) уточняется через spike в Phase 8
- [ ] **PRN-05**: История статусов и уровней расходников (для отчётности и динамики расхода)
- [ ] **PRN-06**: Pantum-зависание: детекция стука (стабильный prtMarkerLifeCount + растущая очередь спулера, см. PITFALLS.md #15) с алертом администратору; авто-restart НЕ в v1 (см. PNT)
- [ ] **PRN-07**: Связь принтера в БД с моделью картриджа (отображение «какой картридж сейчас стоит»)
- [ ] **PRN-08**: Mock-имплементация SNMP-клиента для локальной разработки на macOS (без доступа к реальным принтерам)

### Requests (REQ)

- [ ] **REQ-01**: CRUD заявок (создание возможно из веб-интерфейса браузера)
- [ ] **REQ-02**: Два типа заявок: «Замена картриджа» (со связью к принтеру/модели картриджа в БД) и «Свободная форма» (произвольный текст, опциональные категории)
- [ ] **REQ-03**: Жизненный цикл заявки: Создана → Принять в работу / Отклонить → Выполнить
- [ ] **REQ-04**: Уведомление администратора/специалиста о новой заявке (in-app в v1; email/telegram/webhook — в финальной фазе уведомлений)
- [ ] **REQ-05**: Связь заявки на замену картриджа с операцией CART-07/08 (при выполнении заявки можно сразу выполнить установку картриджа)
- [ ] **REQ-06**: Заявки на регистрацию нового пользователя (см. USR-08): отдельный подтип, видим только администратору
- [ ] **REQ-07**: История заявок и их статусов

### Reports (RPT)

- [ ] **RPT-01**: Подраздел «Отчёты по устройствам» с категориями: Акты приёма-передачи, Возвраты, Что в работе, Что на складе
- [ ] **RPT-02**: Подраздел «Отчёты по картриджам»: Расход (динамика по моделям), Что в работе (где установлены), Что на складе, История заправок
- [ ] **RPT-03**: Выборка периода: По месяцу / По году / Диапазон дат
- [ ] **RPT-04**: Фильтры внутри отчёта (по локации, типу, статусу, модели)
- [ ] **RPT-05**: Поиск внутри отчёта
- [ ] **RPT-06**: Группировка списка по месяцам с визуальным разделителем (заголовок «Сентябрь 2026») при смене месяца
- [ ] **RPT-07**: Экспорт отчёта в CSV (UTF-8 BOM) и в PDF
- [ ] **RPT-08**: Печать отчёта (через системный диалог печати)

### Users & Roles (USR)

- [ ] **USR-01**: CRUD пользователей: Логин, ФИО, Пароль (argon2id, через `Secret<T>`), Роль, Email (опционально), Активен/Заблокирован
- [ ] **USR-02**: Три роли: Администратор (полный доступ), Специалист (CRUD устройств/картриджей/актов, выполнение заявок, без управления пользователями и настройками), Сотрудник (только создание заявок)
- [ ] **USR-03**: Сессии (cookie через `tower-sessions` с SQLite-store на rusqlite), логин по логин/пароль через веб-интерфейс
- [ ] **USR-04**: В Tauri-десктопе администратор работает без логина (локальная «trusted» сессия), однако опционально может включить требование входа и в десктоп-режиме
- [ ] **USR-05**: Возможность выйти и войти под другим пользователем в веб-режиме
- [ ] **USR-06**: Авторизация enforced и на API-слое, и в UI (нельзя обойти роль через прямой HTTP-запрос)
- [ ] **USR-07**: HTTPS в server mode по умолчанию: self-signed сертификат (`rcgen`) генерируется при первом включении; путь к собственному сертификату — конфигурируемый
- [ ] **USR-08**: AD-вход (поздняя фаза): пользователь домена входит через браузер по AD-логину (us100) и AD-паролю; bind через `ldap3 0.12` (simple_bind), пароли НИКОГДА не сохраняются
- [ ] **USR-09**: Если AD-пользователь не зарегистрирован в Trackly — отправляет заявку на регистрацию (REQ-06); администратор подтверждает + назначает роль
- [ ] **USR-10**: Подтягивание полного имени (ФИО) из AD по логину (`displayName` или `cn` атрибут)
- [ ] **USR-11**: Настройка «Автоприём заявок на регистрацию пользователя» (если включена — AD-пользователь автоматически создаётся с ролью «Сотрудник»)
- [ ] **USR-12**: Mock-имплементация AD-клиента для локальной разработки на macOS

### Dashboard (DASH)

- [ ] **DASH-01**: Виджет «Устройства»: общее количество + разбивка по статусам
- [ ] **DASH-02**: Виджет «Картриджи»: разбивка по статусам + alert о низком остатке
- [ ] **DASH-03**: Виджет «Динамика расхода картриджей»: график за последние 3/6/12 месяцев
- [ ] **DASH-04**: Виджет «Заявки»: количество активных/новых/выполненных за период
- [ ] **DASH-05**: Виджет «Принтеры»: количество онлайн/офлайн, проблемные (по PRN-06)

### Settings (SET)

- [ ] **SET-01**: Раздел «Организация»: название, реквизиты, адрес, логотип (используется в шаблонах документов)
- [ ] **SET-02**: Логотип хранится как BLOB в БД (для portable-совместимости)
- [ ] **SET-03**: Текущий путь к файлу БД с действиями: «Открыть папку» (системный file manager) и «Сменить расположение»
- [ ] **SET-04**: Порог «низкого остатка» картриджа (по умолчанию 2, настраиваемо)
- [ ] **SET-05**: Экспорт БД (бэкап-копия .db через SQLite `.backup` API, не файловое копирование)
- [ ] **SET-06**: Ручной бэкап БД (с одним кликом)
- [ ] **SET-07**: Автобэкап БД: настройка расписания (ежедневно/еженедельно), целевая папка, ретенция (количество хранимых копий)
- [ ] **SET-08**: Настройки сетевого доступа: порт сервера, bind-адрес (`127.0.0.1` или `0.0.0.0`), включение/выключение server mode
- [ ] **SET-09**: Управление шаблонами документов: редактирование Акта приёма-передачи и Документа приёмки (MiniJinja-шаблоны, валидация при сохранении)
- [ ] **SET-10**: Настройка «Автоприём заявок на регистрацию пользователя» (см. USR-11)

## v2 Requirements

### Map (MAP)

- **MAP-01**: Выбор локации, отображение схематичного плана помещений (не точный, упрощённый)
- **MAP-02**: Размещение устройств на плане кабинета: компьютер (с IP, подключённым USB-принтером, статусом, картриджем, логином пользователя), коммутатор/свитч/хаб/роутер, IP-телефон (с номером), сетевые принтеры
- **MAP-03**: Редактор плана: drag & drop устройств, рисование кабинетов
- **MAP-04**: Просмотр статуса устройств с карты (real-time через server mode WebSocket)

### Notifications (NTF)

Финальная фаза v1 — после того как основной функционал работает.

- **NTF-01**: In-app уведомления и баннеры (для дашборда)
- **NTF-02**: Email (SMTP) с настройкой сервера, отправителя, шаблонов
- **NTF-03**: Telegram-бот (настройка токена, чата)
- **NTF-04**: Общий webhook-выход с шаблоном payload
- **NTF-05**: Подписка на типы событий: новая заявка, низкий остаток картриджа, зависание принтера, окончание срока в акте

### Pantum Auto-Restart (PNT)

- **PNT-01**: Автоматическое обнаружение зависшего спулера для Pantum-принтеров (детекция уже в PRN-06)
- **PNT-02**: Опциональный удалённый restart спулера через WMI/RPC (после ручного подтверждения гипотезы и UAT)
- **PNT-03**: Журнал автоматических восстановлений
- **PNT-04**: Whitelist хостов, где restart разрешён

### Win7 32-bit (WIN7)

- **WIN7-01**: Сборка релиза для Windows 7 SP1 32-bit (i686-pc-windows-msvc) — best-effort, отдельный CI-джоб
- **WIN7-02**: Документация: требование TLS 1.2 на стороне ОС и WebView2 совместимости

### i18n (I18N)

- **I18N-01**: Выделение текстов UI в отдельные локализационные ресурсы
- **I18N-02**: Английская локализация
- **I18N-03**: Переключатель языка в настройках

### Advanced (ADV)

- **ADV-01**: Полноценный SSO (Kerberos / NTLM) для AD
- **ADV-02**: REST API наружу (для интеграций) — отдельно от внутреннего web API
- **ADV-03**: Подписи (электронные / picture pad) на актах
- **ADV-04**: Поддержка дополнительных производителей принтеров (Brother, Epson, Xerox, Ricoh)
- **ADV-05**: Миграция SQLite → Postgres для масштаба > 5000 устройств / > 20 одновременных пользователей

## Out of Scope

| Feature | Reason |
|---------|--------|
| Multi-tenant / SaaS | Продукт под одну организацию; multi-tenant выводит сложность на порядок |
| Облачная синхронизация | Только локальное развёртывание; нет облаков |
| Workflow engine для заявок | Цепочки согласований избыточны для одной организации; жизненный цикл прост (Создана→В работе→Выполнена) |
| Управление лицензиями ПО | Из категории asset tracking, но не нужно — у организации это решается иначе |
| Мобильное приложение | Веб-доступ из браузера в LAN считается достаточным |
| Real-time WebSocket по всему UI | Polling раз в N секунд достаточно; WS только для виджетов мониторинга принтеров |
| Plugin-архитектура | Преждевременная абстракция, нет реальных кейсов |
| Полноценный hot-reload шаблонов в рантайме | Шаблоны редактируются в настройках, валидация при сохранении; перезапуска приложения не требуется, но и live preview редактирования не нужен |
| Видеозаписи / фото активов | Хранение бинарей раздувает БД, портативность страдает |
| GeoIP / геолокация | Локации — это здания/кабинеты, не координаты на карте мира |
| Поддержка не-целевых принтеров в первой фазе мониторинга | Поддерживается best-effort через стандартный Printer-MIB; production-качества — только для 4 заявленных вендоров |
