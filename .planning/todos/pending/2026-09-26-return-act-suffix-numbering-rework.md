## Problem

Найдено пользователем при живой UAT фазы 40.4 (пункт 3 — печать номера акта).
Сам фикс NEW-2 подтверждён рабочим: номера в «Перемещениях» и в печатной форме
совпадают. Но выяснилось, что **само правило формирования номеров возвратов
неверно**. Два независимых дефекта, оба существуют задолго до фазы 40.4 —
это НЕ её регрессия.

### Дефект A — суффикс существующего акта меняется при появлении/удалении соседа

`format_act_number` (`dto/act.rs:37`):

```rust
if sibling_return_count == Some(1) { format!("{parent}в") }
else { format!("{parent}в{sub}") }
```

Это действующее правило **D-Numbering-01** («единственный возврат теряет
под-номер»), не случайный баг. Следствие: суффикс зависит не от самого возврата,
а от количества его живых соседей.

- один возврат → «42в»
- создали второй → первый **превращается** в «42в1», второй «42в2»
- удалили один из двух → оставшийся снова теряет цифру

**Чего хочет пользователь:** первый возврат сразу получает «в1», без
безцифрового варианта. Формулировка пользователя: «иначе будет не правильно,
если номер меняется».

**Почему это серьёзнее косметики:** номер уже распечатанного и подписанного акта
перестаёт совпадать с номером в системе. Бумажный документ — источник истины для
организации; расхождение с ним нельзя чинить задним числом.

### Дефект B — дыры в нумерации не переиспользуются (`MAX+1`)

`next_sub_number_for_parent` (`acts_sqlite.rs:453`):

```sql
SELECT COALESCE(MAX(sub_number), 0) + 1 FROM acts
WHERE parent_act_id = ?1 AND deleted_at_utc IS NULL
```

`MAX+1` не занимает освободившееся значение в середине диапазона.
Воспроизведение пользователя (подтверждено чтением кода):

| Действие | Живые `sub_number` | `MAX+1` | Итоговые номера |
|---|---|---|---|
| создано два возврата | 1, 2 | — | в1, в2 |
| удалён «в1» | 2 | 3 | — |
| создан новый возврат | 2, 3 | — | **в2, в3** ← дефект |
| (альтернативно) удалён «в2» | 1 | 2 | — |
| создан новый возврат | 1, 2 | — | в1, в2 ← корректно |

То есть при удалении НЕ последнего возврата нумерация навсегда съезжает.

### Развилка 1 — что делать с уже существующими актами (дефект A)

Отмена D-Numbering-01 меняет отображаемый номер у **всех** существующих
одиночных возвратов: «42в» → «42в1». Варианты:

- **(a) Сменить правило для всех** — единообразно, но у актов, распечатанных до
  обновления, бумага перестанет совпадать с системой (ровно та проблема, от
  которой уходим, но однократно и в прошлое).
- **(b) Зафиксировать отображаемый суффикс в БД при создании акта** — новая
  колонка; номер перестаёт быть производным от числа соседей вообще, старые
  акты сохраняют «в», новые получают «в1». Дороже (миграция + бэкфилл), но
  единственный вариант, который закрывает класс проблемы, а не текущий симптом.

Рекомендация: (b). Корень дефекта A в том, что номер — вычисляемая функция от
изменчивого состояния соседей; (a) оставляет эту зависимость на месте
(`sibling_return_count` всё ещё в сигнатуре), просто делает её сегодня
незаметной. При любом будущем изменении формулы дефект вернётся.

### Развилка 2 — плотная нумерация или строго возрастающая (дефект B)

- **(a) Плотная (`MIN` свободного значения)** — то, что просит пользователь:
  новый возврат занимает освободившуюся дыру. Но номер удалённого акта
  переиспользуется: если «в1» был распечатан, новый «в1» — это другой документ
  с тем же номером.
- **(b) Строго возрастающая без переиспользования** — сегодняшнее поведение;
  дыры остаются навсегда, зато номер уникален во времени.

Спросить пользователя прямо: **допустимо ли, чтобы номер удалённого возврата
достался новому акту?** Для учётного документа это обычно недопустимо — и тогда
(b) верно, а «дыра» это не баг, а след удаления. Если возвраты удаляются только
как исправление свежей ошибки ввода (до печати), то (a) безопасно.

Ответ определяет, баг это вообще или нет — поэтому уточнить ДО планирования.

## Обязательные проверки

- `sibling_return_count` приходит из join в `SqliteActRepository::SELECT_ACTS` —
  при смене правила проверить ВСЕ места чтения: `ActDto::from(row)`,
  `act_number_display.rs::resolve_movement_act_number` (таймлайн + отчёт
  «Перемещения»), `number_template_service.rs:810-845` (превью шаблона номера),
  печать (`act.number_display`, фаза 40.4-05).
- Постоянный гейт фазы 40.4-05 запрещает собирать номер конкатенацией
  `number_raw + suffix` — новая реализация обязана идти через `format_act_number`,
  иначе гейт справедливо упадёт.
- `ui/scripts/check-act-number-no-regex-split.mjs` — фронтендовый реестровый
  гейт против разбора номера регуляркой; при смене формата проверить его фикстуры.
- Тесты извлечения текста НЕ видят наложение в PDF — если суффикс удлинится
  («в» → «в1» — это +1 символ в поле фиксированной ширины), рендерить настоящий
  PDF. Память: `act-pdf-word-fidelity`.
- Полный `cargo test --workspace` в этой рабочей области ~80 минут; скоупить
  прогоны по целям, полный — один раз на границе.

**Размер:** не quick. Затрагивает продуктовое решение (D-Numbering-01),
вероятную миграцию БД, четыре места чтения номера и печатную форму.
Маршрут: `/gsd-spec-phase` отдельной фазой после ответов на две развилки.
