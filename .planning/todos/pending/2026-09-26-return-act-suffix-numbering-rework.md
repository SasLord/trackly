## Problem

Найдено пользователем при живой UAT фазы 40.4 (пункт 3 — печать номера акта).
Сам фикс NEW-2 подтверждён рабочим: номера в «Перемещениях» и в печатной форме
совпадают. Но выяснилось, что **само правило формирования номеров возвратов
неверно**. Два независимых дефекта, оба существуют задолго до фазы 40.4 —
это НЕ её регрессия.

### Дефект A — суффикс существующего акта меняется при появлении/удалении соседа

`format_act_number` (`dto/act.rs:37`):

```rust
if sibling_return_count == Some(1) { format!("{parent}в") }
else { format!("{parent}в{sub}") }
```

Это действующее правило **D-Numbering-01** («единственный возврат теряет
под-номер»), не случайный баг. Следствие: суффикс зависит не от самого возврата,
а от количества его живых соседей.

- один возврат → «42в»
- создали второй → первый **превращается** в «42в1», второй «42в2»
- удалили один из двух → оставшийся снова теряет цифру

**Чего хочет пользователь:** первый возврат сразу получает «в1», без
безцифрового варианта. Формулировка пользователя: «иначе будет не правильно,
если номер меняется».

**Почему это серьёзнее косметики:** номер уже распечатанного и подписанного акта
перестаёт совпадать с номером в системе. Бумажный документ — источник истины для
организации; расхождение с ним нельзя чинить задним числом.

### Дефект B — дыры в нумерации не переиспользуются (`MAX+1`)

`next_sub_number_for_parent` (`acts_sqlite.rs:453`):

```sql
SELECT COALESCE(MAX(sub_number), 0) + 1 FROM acts
WHERE parent_act_id = ?1 AND deleted_at_utc IS NULL
```

`MAX+1` не занимает освободившееся значение в середине диапазона.
Воспроизведение пользователя (подтверждено чтением кода):

| Действие | Живые `sub_number` | `MAX+1` | Итоговые номера |
|---|---|---|---|
| создано два возврата | 1, 2 | — | в1, в2 |
| удалён «в1» | 2 | 3 | — |
| создан новый возврат | 2, 3 | — | **в2, в3** ← дефект |
| (альтернативно) удалён «в2» | 1 | 2 | — |
| создан новый возврат | 1, 2 | — | в1, в2 ← корректно |

То есть при удалении НЕ последнего возврата нумерация навсегда съезжает.

## Solution

**РЕШЕНО пользователем 2026-09-26.** Обе развилки закрыты, планировать можно.

### Решение по развилке 1 (дефект A) — вариант (a), сменить правило для всех

Убрать из `format_act_number` ветку «единственный возврат теряет под-номер»
(D-Numbering-01 отменяется): возврат ВСЕГДА отображается как `{parent}в{sub}`.
Безцифрового «в» больше не существует.

Миграции и бэкфилла НЕ требуется: пользователь пересоздаёт БД с нуля, старые акты
менять не нужно. Это снимает главное возражение против варианта (a) — расхождение
уже напечатанных актов с системой — потому что печатать ещё нечего.

Следствие: параметр `sibling_return_count` в `format_act_number` становится
неиспользуемым. Его сквозная проводка (`ActRow.sibling_return_count`,
коррелированный подзапрос в `SELECT_ACTS`, отдельный подзапрос в
`act_number_display.rs`, чтение в `number_template_service.rs`, две точки
`sibling_return_count: None` в `act_service.rs`) — кандидат на удаление.
Удаление предпочтительно: именно зависимость номера от ИЗМЕНЧИВОГО состояния
соседей и была корнем дефекта A, и пока параметр жив, к нему можно вернуться.
Решить в плане, объёмом это ~7 механических точек.

### Решение по развилке 2 (дефект B) — плотная нумерация, вариант (a)

`next_sub_number_for_parent` меняется с `MAX(sub_number)+1` на **наименьший
свободный** положительный номер среди неудалённых возвратов родителя.
Суффиксы — только «в1», «в2», … «вN».

Точная семантика, подтверждённая формулировкой пользователя («следующий
созданный возврат должен заполнить эту дырку»):

- Существующие возвраты при удалении соседа **НЕ перенумеровываются**. Сразу после
  удаления «в1» из {в1, в2} остаётся {в2} — дырка существует; инвариант «в1..вN без
  разрывов» выполняется только после её заполнения.
- Дырку занимает следующий СОЗДАННЫЙ возврат. Создание нового даёт {в1, в2}.
- Если дырок несколько, занимается меньшая: из {в1,в2,в3} удалили в1 и в3 →
  следующий возврат получает 1, за ним следующий получает 3.

Перенумерация существующих актов сознательно НЕ закладывается — она противоречила
бы решению по развилке 1 («старые акты не менять») и была бы тем же дефектом A
в другой форме.

**Принятое следствие:** номер удалённого возврата достаётся новому акту, то есть
напечатанный «в1» и будущий «в1» — разные документы. Пользователю это озвучено,
выбор сделан осознанно, повторно не поднимать.

Параллелизм: выделение «наименьшего свободного» безопасно по той же причине, что и
`MAX+1` — single-writer + `BEGIN IMMEDIATE` в той же транзакции.

### Дополнительно в объём: убрать F7 вместе с корнем

`compute_suffix_from_display` (`act_service.rs:3496`) при несовпадении
`strip_prefix` ищет литеральную «в» ГДЕ УГОДНО в строке (`display.find('в')`) —
это риск F7 из аудита. При новом правиле суффикс всегда равен «в{sub}», то есть
выводится напрямую из `sub_number`, а не разбором отображаемой строки. Функцию
можно упростить или удалить — это закрывает F7 не заплаткой, а снятием причины.

### Радиус (промерен 2026-09-26, не оценка на глаз)

Логика контролируемая — `format_act_number` это ЕДИНСТВЕННАЯ формула, её
потребляют ровно четыре поверхности, и все следуют за ней автоматически:
`ActDto::from(row)`, `act_number_display.rs::resolve_movement_act_number`
(таймлайн + отчёт «Перемещения»), `number_template_service.rs` (превью),
`is_occupied` (скан занятости). Это прямой результат структурного гейта фазы 40.3.

Основная работа — в тестах: **~32 места** утверждают безцифровую форму «Nв» в
6+ файлах (`acts_numbering.rs`, `acts_display_rule.rs`,
`place_movements_timeline.rs`, `report_movements.rs`, `html_act_render.rs`,
юнит-тесты `dto/act.rs`).

**Не механическая часть, главный риск:** `acts_numbering.rs` проверяет
уникальность по ОТОБРАЖАЕМОМУ номеру — акт приёма-передачи нельзя создать или
переименовать в строку, которую сейчас показывает возврат, плюс каскад при
переименовании родителя (`is_act_number_occupied_including_returns` →
`is_occupied`, `act_service.rs:308` и `:791`). Смена правила меняет, ЧТО с ЧЕМ
конфликтует: handover «42в» больше не сталкивается с возвратом, а «42в1» — начинает.
Эти тесты требуют пересмотра по смыслу, а не замены строк.

## Обязательные проверки

- `sibling_return_count` приходит из join в `SqliteActRepository::SELECT_ACTS` —
  при смене правила проверить ВСЕ места чтения: `ActDto::from(row)`,
  `act_number_display.rs::resolve_movement_act_number` (таймлайн + отчёт
  «Перемещения»), `number_template_service.rs:810-845` (превью шаблона номера),
  печать (`act.number_display`, фаза 40.4-05).
- Постоянный гейт фазы 40.4-05 запрещает собирать номер конкатенацией
  `number_raw + suffix` — новая реализация обязана идти через `format_act_number`,
  иначе гейт справедливо упадёт.
- `ui/scripts/check-act-number-no-regex-split.mjs` — фронтендовый реестровый
  гейт против разбора номера регуляркой; при смене формата проверить его фикстуры.
- Тесты извлечения текста НЕ видят наложение в PDF — если суффикс удлинится
  («в» → «в1» — это +1 символ в поле фиксированной ширины), рендерить настоящий
  PDF. Память: `act-pdf-word-fidelity`.
- Полный `cargo test --workspace` в этой рабочей области ~80 минут; скоупить
  прогоны по целям, полный — один раз на границе.

**Размер:** не quick. Затрагивает продуктовое решение (D-Numbering-01), логику
выделения sub_number, четыре поверхности чтения номера, проверку уникальности по
отображаемому номеру и ~32 тестовых утверждения. Миграция БД НЕ нужна (решение
пользователя: база пересоздаётся с нуля).

Маршрут: отдельная фаза **перед Фазой 41 (АРМ)** — акты АРМ пойдут через тот же
контекст печати и унаследуют дефект (риск F7 из аудита), поэтому чинить надо до, а
не после. Развилки закрыты, `/gsd-spec-phase` можно запускать сразу.
