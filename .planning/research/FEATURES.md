# Feature Landscape

**Domain:** внутренний рабочий мессенджер (Link) для одной организации в Windows/AD LAN, десятки–сотни пользователей, только русский
**Milestone:** v1.5 «Trackly Link — клиент и Чат»
**Researched:** 2026-11-25
**Overall confidence:** MEDIUM. Поведение Telegram/Slack/Mattermost/Teams/Element описано по знанию поведения продуктов (обучающие данные, WebSearch/Context7 не запускались), это гипотезы для уточнения. Опора на код Trackly (чат заявок) — HIGH.

## Что уже есть в Trackly (не переизобретать, переиспользовать)

Чат заявок (`ui/src/features/requests/chat/`): простой `textarea` (MAX_LEN 4000, без rich-text), вставка из буфера и чипы вложений, разделители дней (`ChatDayDivider`), linkify, черновик в сторе (живёт только в памяти сессии), серверные счётчики непрочитанного (`unreadStore`, клиент не считает), mute на заявку (серверное состояние), системные события в ленте, WS-обновления с перечитыванием.

Следствие: **модель «непрочитано» уже серверная и per-user — расширять, а не заменять.** Rich-text редактор, ответы, реакции, упоминания, курсорная догрузка, закрепление, комнаты — новые.

## Table Stakes

Без этого мессенджер ощущается сломанным. Помечено: **[ЕСТЬ]** — пользователь назвал; **[НЕ ЗАЯВЛЕНО]** — пользователь не упоминал, но это ожидаемый минимум (вынести вопросом).

## Rich-text: что реально ожидается

Редактор из списка пользователя — очень широкий (таблицы с объединением ячеек, 5–6 уровней заголовков, sup/sub, выравнивание, отступы) — это возможности Word, а не мессенджера. В Slack/Teams/Mattermost — Markdown-подобное (жирный, курсив, зачёркнутый, код, цитата, списки, ссылки), таблиц в сообщении нет (Teams — есть вставка таблицы, объединения ячеек нет).

| Элемент | Стандарт в мессенджерах | Сложность | Рекомендация |
|---------|--------------------------|-----------|--------------|
| bold/italic/underline/strike, списки, цитата, ссылка, код | Везде | Med | Table stakes. Редактор: **TipTap/ProseMirror** (Svelte-обёртки есть) — выбор для STACK |
| Горячие клавиши (Ctrl+B/I/U, Enter = отправить, Shift+Enter = перенос) | Везде | Low | **[НЕ ЗАЯВЛЕНО]** Enter/Shift+Enter — настройка «Ctrl+Enter» возможно позже |
| Блок кода с подсветкой | Везде | Low–Med | Подсветку отложить, моноширинный блок + копировать |
| Заголовки 5–6 уровней, sup/sub, выравнивание, отступы | Нет в мессенджерах (Teams — заголовки 3 уровня) | Med | Дифференциатор/«перебор». Дёшево в TipTap, но раздувает санитайзер и рендер |
| Таблицы + merge/split ячеек | Только Teams (без merge) | **High** | Самый дорогой пункт. Merge/split = colspan/rowspan в модели + санитайзер + рендер + поиск + копирование. Рекомендую в отдельную подфазу после ядра; без merge — вдвое дешевле |
| Картинка inline в тексте | Нет (картинки — вложения) | Med | Свести к вложению-картинке с превью; inline-вставка = доп. хранение/санитизация |
| Формат хранения | Slack — blocks JSON, Mattermost — Markdown, Teams — HTML | Med | Хранить **структурный JSON (ProseMirror doc)** + plain-text проекцию для поиска/уведомлений/превью; НЕ хранить сырой HTML. Санитизация на сервере (allowlist узлов/атрибутов, схемы ссылок http/https/mailto) — XSS в чате, который читают все = критично |
| Вставка из Word/веба | Редактор получает грязный HTML | Med | Приводить к схеме редактора (strip), иначе в чат попадают чужие стили |

## Поведение, где нужны решения (спорные места)

### Read receipts: 1:1 vs комнаты
- Telegram: 1:1 — две галочки; в группах до ~100 человек «Просмотрели N» (с именами), больше — нет. Slack: нет вообще. Mattermost: нет по умолчанию. Teams: чат 1:1/группа — «Прочитано» (настраиваемо, можно отключить), каналы — нет.
- Рекомендация: хранить **одну позицию `last_read_seq` на (user, chat)** — этого хватает и для счётчика, и для «Информации о сообщении» (кто прочёл = у кого `last_read_seq >= seq`; «когда» = момент апдейта позиции, это ПРИБЛИЖЕНИЕ: время «прочитал по позиции», а не время открытия именно этого сообщения. Зафиксировать формулировку в UI/требовании). Индикатор «✓ / ✓✓» у своего сообщения в 1:1 — дёшево и ожидаемо. В комнатах — только через «Информация» (без значков на каждом сообщении).
- Приватность: обсудить, что работник видит «прочитано» у себя (Teams позволяет отключить). Для внутренней сети — оставить включённым, без настройки (меньше состояний).

### Typing indicator
- Есть у Telegram/Slack/Teams. Для внутреннего: «Иванов И.И. печатает…» в 1:1 — дёшево (эфемерное WS-событие, без БД, троттлинг 3 с, таймаут 5–6 с). В комнатах — по желанию («печатают 2 человека»). Рекомендация: **1:1 и комнаты, но как последняя по приоритету мелочь; безопасно отложить**. Нагрузка ничтожна на 100 человек.

### Presence / online
- Slack/Teams — зелёная точка + «отошёл» + DND, Telegram — «был(а) недавно». Реализация: счёт активных WS-сессий per user (+ клиент трея всегда подключён, поэтому «онлайн» = «компьютер включён», а не «человек за столом»). Это вводит в заблуждение → **без индикатора «не на месте»**; максимум «в сети» по факту WS. Рекомендация: **отложить; если делать — только «в сети/не в сети» без «отошёл», и без «был в сети в…» (давление на сотрудников — вопрос политики)**. Но презенс влияет на уведомления: не слать системный тост, если пользователь активен в окне Link (иначе дубль тост+баннер) — это решается локально по фокусу окна, а не presence-фичей.

### DND / «Не беспокоить»
- В v1.5 есть «mute всего приложения» — это и есть минимальный DND. Расписание/«до 18:00»/авто-DND по Windows Focus Assist — отложить. Рекомендовать: mute приложения с опциями «на 1 час / до завтра / бессрочно» (дёшево, Telegram-стиль) и отдельно решить, пробивают ли его упоминания (рекомендация: нет — приложение замьючено целиком = полная тишина, но счётчик растёт).

### Mute-семантика (рекомендуемая, единая для всех)
| Вопрос | Slack | Telegram | Mattermost | Рекомендация для Link |
|--------|-------|----------|------------|-----------------------|
| Mute считает непрочитанное? | Серый бейдж без числа | Да, серый бейдж с числом, не входит в «главный» счётчик | Да, без бейджа | **Да, считает, показывать серым; в суммарный счётчик трея НЕ включать** |
| Упоминание пробивает mute комнаты? | Да (настройка) | Да (настройка «упоминания») | Да | **Да: @-упоминание и ответ на моё сообщение пробивают mute комнаты (тост + красный бейдж), настройка не нужна** |
| Mute приложения | DND | Все чаты | — | Ничего не пробивает; счётчики остаются |
| Системные уведомления (от Trackly) | — | — | — | Не мьютятся комнатными настройками; mute приложения гасит звук/тост, не бейдж |
| Хранение | сервер | сервер | сервер | **На сервере per-user** (как уже сделано для заявок) — единое поведение в клиенте и браузере |

Переиспользовать существующий `mutedIds` из заявок как образец (D-G2/D-G3).

### Mentions
- Автокомплит по участникам чата (в 1:1 — не нужен). Хранить id пользователя в узле doc (не по тексту), чтобы переименование ФИО не ломало. Уведомление: тост + бейдж «@». Удалённый/ушедший из комнаты пользователь — упоминание рендерится как текст. `@all`/`@все` в комнате: Slack `@channel`, Mattermost `@channel` — часто злоупотребляют; рекомендовать **не в v1.5** либо только Создателю/админу.
- Упоминание человека, не состоящего в комнате: Slack предлагает пригласить; **для Link — не предлагать, запрещено** (иначе утечка).

### Reply vs forward vs pin vs quote
- **Reply**: поле `reply_to_seq` + снапшот превью. Цитата (блок quote в редакторе) — разное: quote — форматирование внутри текста, reply — ссылка на сообщение. Не смешивать в UI.
- **Forward**: отложить.
- **Pin**: см. дифференциаторы.

### Правка и удаление
- Лимита по времени на правку нет (рекомендация). На удаление своих — нет.
- Удаление: тело убирается из выдачи всем, кроме admin; реакции/ответы на удалённое остаются плашкой. Что с вложениями удалённого — **скрыть и пометить на физическое удаление при hard-delete** (файлы не должны оставаться «сиротами»). Уведомление о ранее присланном сообщении: помеченные в тосте уже показанные остаются — неизбежно.
- Hard-delete админом: каскад — реакции, прочтения не нужны, вложения, ответы-превью (превратить в «Сообщение удалено»), запись в FTS-индексе.

### Вложения: лимиты и ввод
- Telegram 2–4 ГБ, Slack 1 ГБ, Mattermost по умолчанию 100 МБ, Teams 250 ГБ (через SharePoint). Для SQLite/LAN-сервера: ограничение **на файл ~25–50 МБ**, итого на сообщение до ~10 файлов; квота хранилища — настройка админа; взять существующие лимиты модуля `attachments` из 41.3 (согласовать, проверить значение в коде — не перепроверено). Проверять размер на сервере и на клиенте. Антивирус — не наша зона, но блокировать исполняемые расширения (.exe, .bat, .ps1, .js, .lnk) — вопрос политики (**[НЕ ЗАЯВЛЕНО]**; в Trackly сейчас есть правило отказа `rejectText`).
- Вставка скриншота: Ctrl+V (Windows Snipping → буфер) — в чипы, имя `image.png` → давать осмысленное `Скриншот 2026-11-25 14-03.png`.
- Drag&drop: на область чата, с оверлеем.
- Просмотр: превью изображений, лайтбокс, скачать; PDF — открыть в системе. Переиспользовать из Заявок.

### Поиск
- Ожидаемо: строка наверху, группы результатов «Сообщения / Люди / Комнаты», фильтр по чату, дата; клик → переход к сообщению в контексте (окно вокруг `seq`) + подсветка. Нужны: ранжирование по свежести, а не по релевантности (для внутреннего достаточно), подсветка совпадений, префиксный поиск. Русская морфология — нет (FTS5 unicode61), оговорить: «найдёт форму слова лишь по префиксу». Права: только в доступных чатах; удалённые и чужие личные — исключены. Поиск пользователей для диалога — обычный `LIKE` по справочнику, отдельно от FTS.

### Закреплённые (pin) и прочие
- Закреп — в списке «если останется время»; не затрагивает схему кроме `pinned_at`.
- «Избранные» чаты/закрепление чатов вверху списка — **[НЕ ЗАЯВЛЕНО]**, но легко ожидаемо при >10 чатов: закрепить чат (Low).
- Сортировка списка чатов по последнему сообщению — обязательна.
- Архив чата/«скрыть диалог» — отложить.

## Зависимости между фичами

```
seq + курсорная догрузка (WS reliable)
  → last_read_seq → счётчики/разделитель «Новые»/прыжок к непрочитанному
  → «Информация о сообщении» (прочтения)
  → уведомления/трей-индикатор
  → клиент-идемпотентность отправки (client_msg_id)

Модель сообщения (JSON doc + plain-text проекция + серверный санитайзер)
  → поиск (FTS5), превью в тостах/списке, упоминания (id в узле), reply-превью
  → таблицы (merge/split) — самый тяжёлый узел схемы

Комнаты/участники/Создатель → упоминания (список участников), права на чтение истории,
  системные сообщения (получают seq), модерация

Вложения (модуль 41.3) → drag&drop/буфер/превью → удаление (каскад файлов)

Mute (серверное per-user) → правила пробива упоминаниями → бейдж/трей-суммa

Admin-раздел «Link» → просмотр удалённого → аудит-журнал → hard-delete каскад (FTS, файлы, превью)

Клиент Link (трей) → системные уведомления Windows (AppUserModelID) → единая логика «окно в фокусе → не слать тост»
Браузер (employee) → тот же чат на WS; Notification API требует secure context (самоподписанный cert)
```

Зависимости от существующего: `users`/роли (Admin/Manager/Employee) для видимости; WS-шина (после доработки seq); attachments 41.3; unread/mute-паттерны 41.5. v1.6 (объявления, вкладка заявок) требует готовой модели «чат + уведомление с важностью + подтверждение» → закладывать тип сообщения/системный отправитель сейчас.

## Рекомендации по MVP

**Первые (фундамент):** seq/курсор/WS-надёжность; модель сообщения (JSON doc + санитайзер + plain-text); диалоги 1:1 и список чатов; отправка (idempotent); `last_read_seq`, счётчики, разделитель «Новые».
