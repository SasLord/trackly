# Настройка входа через Active Directory

Этот документ описывает, как администратор включает и настраивает вход
сотрудников через Active Directory (AD) в Trackly.

## Что это даёт

После включения AD сотрудники смогут входить в систему через браузер
(серверный режим) под своим доменным логином и паролем — без создания
отдельной локальной учётной записи. Локальные учётные записи (с хэшем
пароля в БД) продолжают работать как раньше: при входе Trackly сначала
проверяет локального пользователя, и только если такого нет — пробует AD
(D-AD-01, прозрачный fallback, без выбора «тип входа» на экране входа).

> Вход через AD доступен только в серверном (браузерном) режиме. Десктоп-вход
> по-прежнему использует локальные учётные записи.

## Шаг 1 — включить Active Directory

1. Откройте **Настройки → Active Directory**.
2. Включите переключатель **«Использовать Active Directory»**.
3. Выберите режим регистрации новых пользователей (см. ниже).
4. Нажмите **«Сохранить настройки»**.

## Шаг 2 — режим регистрации новых пользователей

При первом успешном входе сотрудника через AD создаётся учётная запись Trackly,
привязанная к доменному логину. Доступны два режима:

- **«Автоматически принимать»** — новый доменный пользователь сразу получает
  доступ с ролью «Сотрудник». Заявка на регистрацию всё равно появляется в
  разделе «Заявки» (видна только администратору) — это информационная запись,
  доступ уже выдан.
- **«Требовать подтверждения»** — новый пользователь видит экран «Заявка
  отправлена» и не получает доступа, пока администратор не подтвердит заявку
  в разделе «Заявки» (кнопка «Подтвердить», с выбором роли).

Выбор роли по умолчанию в окне подтверждения — «Сотрудник» (можно изменить на
«Специалист» или «Администратор» перед подтверждением).

## Шаг 3 — параметры подключения (автоопределение)

На компьютере, введённом в домен Windows, Trackly пытается определить
параметры подключения к AD автоматически (DNS SRV-записи домена + переменные
окружения Windows). В большинстве случаев отдельная настройка не требуется.

Если автоопределение не сработало (например, нестандартная конфигурация
сети), откройте блок **«Расширенные настройки»** и проверьте параметры,
заполненные из конфигурационного файла `trackly.config.toml` (находится
рядом с исполняемым файлом — portable-режим):

| Поле | Описание |
|------|----------|
| Адрес сервера (host:port) | Адрес контроллера домена и порт LDAP/LDAPS |
| Домен | Например, `corp.local` |
| Base DN | Базовый Distinguished Name для поиска пользователей |
| Атрибут ФИО | Атрибут AD, из которого берётся отображаемое имя (по умолчанию `displayName`) |
| Не проверять TLS-сертификат | Только для тестовых стендов — отключает проверку сертификата LDAPS. **Не использовать в продуктивной сети.** |

Эти поля **не редактируются из интерфейса Trackly** — это сознательное
ограничение (см. `crates/trackly-app/src/dto/auth.rs`, `AdSettingsDto`):
изменения вносятся в `trackly.config.toml` и применяются при следующем
запуске приложения. В интерфейсе настроек они показаны только для
диагностики ("что сейчас используется").

Чтобы убедиться, что Trackly действительно может достучаться до указанного
сервера AD (без входа под доменной учётной записью), нажмите кнопку
**«Проверить подключение»** в блоке настроек Active Directory. Кнопка
доступна, когда AD включён, и выполняет сетевую/протокольную проверку
(подключение по LDAPS, анонимный bind) — это не проверка логина и пароля
конкретного пользователя, а диагностика доступности самого сервера.

## Безопасность

- Пароль для bind-запроса к AD **никогда** не сохраняется Trackly — он
  используется только в момент проверки логина/пароля и не попадает в БД
  и в логи.
- Подключение к AD выполняется по LDAPS (TLS). Отключение проверки
  сертификата (`no_tls_verify`) допустимо только во временной тестовой
  конфигурации.
- Сообщения об ошибке входа одинаковы для всех случаев неверных
  учётных данных или проблем с учётной записью (заблокирован, удалён,
  неверный пароль) — это сделано намеренно, чтобы не раскрывать
  посторонним существование или состояние конкретной учётной записи.
  Отдельное сообщение показывается только при технической недоступности
  сервера AD (сеть, контроллер домена недоступен) — это не ошибка
  пользователя.

## Восстановление доступа для заблокированных пользователей

Если сотрудник, чья учётная запись Trackly была отключена (или удалена)
администратором, успешно вводит свой доменный пароль на экране входа, попытка
входа сама по себе **не создаёт заявку** — она только проверяет пароль и
показывает экран блокировки с актуальным статусом последней заявки на
восстановление (если она была). Экран блокировки показывает один из трёх
вариантов:

- **Заявок не было** — экран **«Доступ закрыт»** с кнопкой **«Запросить
  восстановление доступа»**. Нажатие отправляет отдельный запрос (с теми же
  логином/паролем, повторно проверенными через AD) и создаёт первую заявку.
- **Заявка уже отправлена и ожидает решения** — экран **«Запрос на
  рассмотрении»**, без кнопки повторной отправки. Повторные попытки входа
  показывают тот же статус и не создают вторую заявку.
- **Заявка была отклонена администратором** — экран **«Запрос отклонён»**
  с указанием причины отклонения (если администратор её указал) и кнопкой
  **«Запросить снова»**. Нажатие создаёт новую заявку (старая отклонённая
  заявка остаётся в истории).

Во всех случаях заявка появляется в разделе «Заявки» с пометкой
«Восстановление доступа» (видна только администратору). Подтверждение такой
заявки восстанавливает прежний доступ пользователя; отклонение оставляет
доступ закрытым и переводит экран блокировки в состояние «Запрос отклонён»
при следующем входе пользователя.

## Отклонение заявок на регистрацию AD

В разделе «Заявки» администратор видит заявки с типом «Регистрация AD»
(и подпись «Восстановление доступа» — если это заявка восстановления).
При отклонении точная формулировка подтверждения зависит от ситуации:

- **Заявка ожидала подтверждения** (режим «Требовать подтверждения») —
  отклонение просто закрывает заявку, пользователь не получает доступа.
- **Пользователь уже создан автоматически** (режим «Автоматически
  принимать») — отклонение **удаляет** уже созданную учётную запись и
  закрывает доступ. Это безвозвратное действие в рамках текущей заявки.
- **Заявка на восстановление доступа** — отклонение оставляет
  заблокированную учётную запись в прежнем (заблокированном) состоянии.

## Локальная разработка и тестирование без AD-сервера

Для разработки/тестирования без доступа к настоящему контроллеру домена
используется переменная окружения `TRACKLY_AD_MOCK=1` — она переключает
backend на встроенный мок-клиент AD с тестовыми пользователями:

| Логин | Пароль | Отображаемое имя |
|-------|--------|-------------------|
| `us100` | `Passw0rd!` | Иванов Иван Иванович |
| `us200` | `Secret123` | Петрова Анна Сергеевна |

Запуск с моком: `TRACKLY_AD_MOCK=1 cargo run` (или соответствующая переменная
окружения в конфигурации запуска тестового стенда). В продуктивной среде эта
переменная не должна быть установлена.
