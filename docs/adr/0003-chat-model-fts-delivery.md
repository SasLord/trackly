# ADR 0003. Модель чата, полнотекстовый поиск и доставка

## Статус
Accepted

## Контекст
Чат заявок (`chat_*`) привязан к заявкам. Link нужен полноценный мессенджер с поиском.

## Решение
- Отдельная модель `im_*`; наращивание `chat_*` отвергнуто.
- Доставка «сигнал + догрузка по курсору»: события-сигналы только сообщают об изменениях, клиент догружает данные по курсору. Реализация в Фазе 43; протокол — в разделе «Протокол доставки (Фаза 43)» ниже.
- FTS5: токенайзер `trigram` плюс нормализация `ё->е` и в индексируемом тексте, и в запросе.
- Запрос короче 3 символов идёт отдельным путём (LIKE или запрет), решение в Фазе 47.
- Запрос всегда соединяется с членством внутри SQL.
- Задел: тест миграции «FTS5+trigram доступен» в Фазе 47.

## Протокол доставки (Фаза 43)

Раздел — спецификация для Rust-клиента Link (Фаза 44). Все значения сверены с исходным кодом на момент закрытия Фазы 43. Примеры вымышленные (беседа 1, пользователи «Иванов И.И.», «Петров П.П.»).

### 1. Соединение и авторизация
- Маршрут `/api/v1/ws`, авторизация cookie сессии. Без валидной сессии сервер отвечает 401 ДО upgrade (middleware перед `ws_handler`).
- Один сокет на клиента. Все события (общий канал и IM-сигналы) идут по нему.
- Идентичность без `user_id` (системный администратор десктопа) IM-сигналов не получает и в `im_send`/`im_sync` получает 403.

### 2. Кадры сервера -> клиент
| Кадр | Поля | Когда |
|------|------|-------|
| `hello` | `protocol` (=1, `WS_PROTOCOL_VERSION`), `pingIntervalSecs`, `idleTimeoutSecs` | первым кадром после upgrade |
| `WsEvent` | см. тип `WsEvent` как есть (поле `type`) | общий канал; проходит `is_visible_to(identity)` |
| `im_changed` | `conversationId`, `rev` | после коммита изменения беседы; тела сообщения нет; `is_visible_to` не применяется, получатели определены по членству |
| `resync_required` | только `type` | потеря событий (`Lagged`) общего канала или канала IM |
| `pong` | только `type` | ответ на текстовый ping клиента |
| протокольный Ping | WS-кадр Ping | каждые 25 с |

`resync_required` намеренно НЕ вариант `WsEvent`: иначе он попал бы в specta-биндинги и в фильтр `is_visible_to`. Служебные кадры клиент разбирает до диспетчера событий.

### 3. Кадры клиент -> сервер
- Текст `{"type":"ping"}` -> ответ `{"type":"pong"}`. Текст длиннее 256 байт и любой иной ввод игнорируются.
- Клиент Link обязан читать сокет непрерывно и отвечать на протокольный Ping (tokio-tungstenite делает это автоматически при чтении потока). Любой входящий от клиента кадр, включая Pong, сбрасывает серверный таймер тишины.

### 4. Тайминги
Серверные — константы кода, не настройки (D-13): ping каждые 25 с (`PING_INTERVAL`); закрытие после 60 с тишины любого рода (`IDLE_TIMEOUT`); таймаут отправки одного кадра 5 с (`SEND_TIMEOUT`), при его превышении соединение закрывается.

Клиентские: переподключение с backoff 1 с, затем x2 до 30 с; успешное открытие сбрасывает backoff до 1 с. Сигналы сети и видимости (`online`, `visibilitychange` в состояние visible) (D-15) отменяют ожидание и открывают сокет немедленно. Тост обрыва показывается не раньше чем через 5 с после обрыва (`RECONNECT_TOAST_DELAY_MS`, D-14), не более одного за эпизод. Дебаунс ресинка 500 мс (`RESYNC_DEBOUNCE_MS`, D-08). Проба живости 5 с (`PROBE_TIMEOUT_MS`).

Решение по клиентской пробе (на усмотрение исполнителя, допущение A1): при `online`/`visibilitychange` с открытым сокетом клиент шлёт ТЕКСТОВЫЙ `{"type":"ping"}` и рвёт сокет, если за 5 с не пришло ни одного кадра. Причина: браузерный JS не видит протокольных ping/pong, поэтому проверить живость сокета на уровне протокола из страницы нельзя. Rust-клиент Link видит протокольные кадры и пробу может не повторять, но обязан понимать текстовые `ping`/`pong`.

### 5. Ресинк
Клиент обязан перечитать всё в трёх случаях: получен `resync_required`; сокет открыт повторно после обрыва; мост десктопа отстал (`Lagged` в `desktop_event_bridge`) и эмитировал Tauri-событие `trackly-resync`. Ресинк тихий (D-09, тосты не показываются) и не трогает ввод пользователя (D-10). IM-клиент выполняет `im_sync` по всем известным беседам.

### 6. Контракт `im_send`
- `POST /api/v1/im_send`, тело `{"conversationId":1,"clientMsgId":"...","text":"..."}`; ответ `{"message":{...},"replay":false}`.
- `clientMsgId`: 1..=64 символов `[A-Za-z0-9_-]` (UUID подходит). Иначе 400.
- Ошибки: 404 — не участник беседы; 403 — участник вышел (read_only) или нет `user_id`; 400 — пустой текст, слишком длинный текст, недопустимый `clientMsgId`.
- Идемпотентность: ключ (беседа, автор, `clientMsgId`). Повтор возвращает ту же запись с `replay:true`; идентичность — `id`, тело повтора не сравнивается. Replay не публикует сигнал `im_changed`. Решение replay принимается в писателе внутри транзакции: сначала проверяется существование строки участника (404), затем поиск по ключу (replay), и только после него `can_post`. Поэтому 403 относится лишь к НОВОЙ отправке исключённого, а повтор уже сохранённого сообщения после исключения автора отвечает `replay:true` (D-11).
- `clientMsgId` в сообщениях отдаётся только автору.

### 7. Контракт `im_sync`
- `POST /api/v1/im_sync`, тело `{"cursors":[{"conversationId":1,"rev":0}],"limit":50}`; ответ `{"conversations":[{"conversation":{...},"messages":[...],"reload":false}]}`.
- Беседа без курсора: сводка и последняя страница сообщений (`reload:false`).
- Курсор отстал: сообщения с `rev > cursor` целиком. Если их больше `SYNC_RELOAD_THRESHOLD` (200), в ответе последняя страница и `reload:true` — клиент заменяет локальную копию беседы.
- Размер страницы: по умолчанию `SYNC_PAGE_DEFAULT` = 50, максимум `SYNC_PAGE_MAX` = 200. Не более 500 курсоров за запрос, остальные отбрасываются.
- Беседы, где вызывающий не участник, игнорируются молча. Актуальные беседы (`cursor >= last_seq`) в ответе отсутствуют; это не относится к `read_only` беседам исключённого (раздел 8).
- Сигнал + догрузка: `im_changed` несёт только `conversationId` и `rev`, отдельного маршрута одиночной догрузки в Фазе 43 нет, поэтому на любой сигнал (в том числе `rev == cursor+1`) клиент вызывает `im_sync` с текущими курсорами; сигнал с `rev <= cursor` игнорируется.

### 8. Исключённый участник (D-05, D-06)
- Выход фиксирует `left_seq` (последний `seq` на момент выхода) и `left_at_utc`. Беседа для него `read_only:true`, `leftSeq` задан.
- Окно видимости: `seq <= left_seq` И `rev <= left_seq`. Неизменённые сообщения с `seq <= left_seq` видны всегда. Окно ограничивает и дельту: выборка `rev > cursor` для исключённого идёт только внутри окна, поэтому сообщения после выхода и правки после выхода не просачиваются. Три случая: (а) нет курсора — последняя страница окна, `reload:true`; (б) курсор `< left_seq` — дельта `rev > cursor` в окне с `reload:false`, а при числе изменений больше `SYNC_RELOAD_THRESHOLD` последняя страница окна и `reload:true`; (в) курсор `>= left_seq` — на каждый `im_sync` возвращается сводка беседы с `read_only:true`, `leftSeq`, `messages` пуст и `reload:false`. Признак «знаю о выходе» в запрос не вводится (форма `ImSyncRequestDto` не меняется). Сообщение, у которого после выхода выросла `rev`, из окна выпадает.
- Принятое ограничение Фазы 43: сообщение, изменённое после выхода, не отдаётся вовсе (копия без снимка ревизии; путей правки в Фазе 43 нет). Фаза 47 обязана добавить снимок ревизии или надгробие, чтобы требование D-06 «история до выхода видна» выполнялось и для изменённых сообщений.
- D-05: о самом исключении сигнал не посылается — исключённый узнаёт при следующем `im_sync` или реконнекте. Сигнал, уже лежавший в буфере канала до коммита исключения, допустим и безопасен: он без тела, а `im_sync` ничего лишнего не отдаст.

### 9. Идемпотентность прочих мест (D-11)
- `chat_send`: необязательное `clientMsgId`, ключ (заявка, автор, id), те же правила replay и формат id.
- `requests_create`: необязательное `clientRequestId`, ключ (автор, id).
- Без клиентского id сервер работает по-старому. Ключи защищены частичными UNIQUE-индексами (V059).

### 11. Чек-лист Фазы 44 и точки расширения Фазы 47
Для Rust-клиента Link: читать сокет непрерывно; разобрать `hello` и проверить `protocol == 1`; отличать служебные кадры от `WsEvent` и `im_changed`; backoff 1 с -> 30 с со сбросом после успеха; ресинк (`im_sync` по всем беседам) после каждого повторного открытия и по `resync_required`; хранить `rev` курсора по беседе; генерировать `clientMsgId` при создании сообщения и повторять отправку с тем же id; считать ответ `replay:true` успехом; не ожидать сигнала об исключении; при `read_only:true` с пустым `messages` не заменять локальную копию беседы и помечать беседу только для чтения.

Точки расширения Фазы 47 (владелец): системное сообщение о составе беседы, снимок ревизии или надгробие для исключённого, реакции, FTS5.

## Результаты эксперимента (rusqlite 0.41 bundled, SQLite 3.54.1, 2026-11-26)

| Проверка | Результат |
|----------|-----------|
| trigram, подстрока по-русски без учёта регистра | находит |
| unicode61, подстрока (`коллег`) | 0 строк, работают только префиксы |
| trigram, запрос из 2 символов | 0 строк |
| `ё` и `е` в любом токенайзере | не склеиваются |

## Последствия
Нормализация `ё->е` обязана выполняться в обоих местах, иначе поиск расходится. Короткие запросы требуют отдельного пути.

## Отвергнутые варианты
- unicode61: не ищет подстроки.
- Расширение `chat_*`: смешивает домены заявок и мессенджера.
